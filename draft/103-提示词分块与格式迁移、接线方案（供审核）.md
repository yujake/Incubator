## 0. 一句话结论

这件事是**三条互相独立的轴**，必须分开做、分开验收 —— 混在一起做，就没有任何一条判据能说清"到底动了什么"：

| 轴 | 做什么 | 文本会变吗 | 硬判据 |
|---|---|---|---|
| **A 分块** | 六个大段切成块（段名 + order 现算） | **不变（逐字节）** | 十角色 `prompt_sha256` 逐格不变 |
| **B 迁移** | 手写文本从 Python 常量搬进预设目录（YAML + md） | **会变** | 原行守恒 + `PROMPT_VERSION` bump + 重冻 |
| **C 接线** | composition 行 → 段；instructions / contexts → user 消息 | 不变（新通道默认空） | 三态 + 预算 + 追加式 |

三条轴的**依赖方向**是 A → B → C：先有块（A）、块才谈得上"哪些块由文件给"（B）、
文件才谈得上"由哪一行挂进来"（C）。倒过来做（先接线）会得到一个"能挂但内容仍在代码里"的空壳。

**为每个智能体定制**这件事在数据上已经存在（§1.4 的实测：C 的边是空的、D 的次要官能是空的、
H 没有政策、M 没有姿态、V 有两套提示词），只是今天由 Python 的 `if` 表达；
本方案的 C 轴把它搬成**每个角色一份 composition**（§5 逐角色给组合）。

### 1.5 接线缝在哪（真实调用链）

复跑：`grep -n "ask_step\|system = \|_prompt(\|_maybe_compact" src/agentflow/agent_loop.py`。

```text
agent_loop.py:2690   run.prompt_audit = AP.prompt_audit(role, registry=…, **facts)     ← 审计读数（整份进 runs/*.json）
agent_loop.py:2691   system = AP.system_prompt(role, registry=…, **facts)              ← 每趟**算一次**
agent_loop.py:2699   messages = [user_message(_opening_transcript(…))]                 ← S-C 裁定 5甲：开场是第一条 user 消息
agent_loop.py:2871   messages = self._maybe_compact(messages, step=step, run=run)      ← 步边界上的压缩（在 ask_step 之前）
agent_loop.py:2872   data, call = self.seam.ask_step(self._prompt(messages, step=step),
                                                      system=system, task_id=…, face=face)
llmseam.py:512-525   ask_step(prompt, *, system="", …) → ask(prompt, system=system, …)
```

三条结论（决定了 C 轴怎么接）：

1. **段通道是"每趟算一次"**：`system` 在步循环之外算好，每步原样传下去 ⇒
   **在 `system` 里加块不会破坏 cache**（一趟之内是常量），但**跨趟**变了就会变。
2. **动态内容只能走 `messages`**：`instructions`（工作区指令）与 `contexts`（运行时快照）
   都必须是 user 角色消息，落点就是 `messages` —— 与 DSH 的分类逐字一致
   （段进 system，快照与工作区指令进 user 消息）。
3. **落点有两个**：开场（`:2699`，基线）与步边界（`:2871` 附近，增量）。
   压缩（`_maybe_compact`）在增量之前跑，所以"新到的指令"不会被刚压过的历史吃掉 ——
   这正是 DSH 的追加式纪律（`dsh-agent-instructions/README:181`："newly visible content follows
   the reusable request prefix"）。

### 1.6 端口现状（机制已经搬完的四件 + 两个真缺陷）

| 批次 | 提交 | 内容 |
|---|---|---|
| 1 | `d0d5390` | `promptkit.py` 补**动态上下文**（`Context` / 抑制 / supersede 头） |
| 2 | `12f574e` | `persona.py`：身份两个具名槽位 + `scope` 必填；已接进 `role_prompt_registry` |
| 3 | `4f45aa0` | `presets.py`：目录 = 一个预设、根优先级、坏预设带理由、挂一次 + 生成戳、复制式创作 |
| 4 | `3922e2f` | `instructions.py`：工作区指令的发现 / 去重 / maxBytes 降级 / 转义 / 追加式状态 |
| 5 | `17f06fd` | 预设层改用 **DSH 的 YAML 格式**；`⚠️ requires_human`（`pyproject.toml` 加 `PyYAML>=6.0`，FC-27 待 2 人签） |

两个真缺陷是判据抓出来的（不是推演出来的），它们直接决定 A/B 轴怎么写：

1. `PresetMount.is_stale()`：把"没挂过 + 组装文件不在"（两边都是 `None`）判成**不过期**，
   接着去取一个不存在的挂载值（`KeyError`）。
2. `instructions.render_baseline()`：第一版按"由宽到窄依次装"，于是**更宽的那一份恰好塞得下时，
   最具体的那一份被丢掉** —— 与 DSH 逐字口径相反。

两个缺陷的教训同一条：**"看起来没超预算"与"该装的那一份装进去了"是两件事**。
A/B 轴的判据因此都要"正面读数"（段名清单、sha256、行守恒），不能只判"没报错"。

### 2.3 批一**不许**动 `PROMPT_VERSION`

判据逐字（`tests/test_agent_prompts.py:1487-1489`）：

```python
if not changed and version != frozen_version:
    bad.append("PROMPT_VERSION 动了…而十格摘要一格没变 ⇒ 这一版号在说什么："
               "版本号是段的短名字，段没动就不该动它")
```

批一的十格摘要一格不变 ⇒ 动了版本号这条判据**必红**。所以"装配换了、文本没换"这件事
在版本轴上刻意不留痕 —— 它的留痕是 `prompt_audit["sections"]` 的段名清单（§7 判据 3）。

被 dump 成 `runs/*.json`（`:5161`，`cli.py:1667` 也打印）⇒ 每趟多约 35 个段名（≈0.6 KB/趟）。

| **必须留代码**（现算） | `FACULTIES`（现算三档，`faculties_text`）· `PARTNERS`（现算边/参数/接线态，`partners_lines`）· `TOOL_xx`（现算工具面，`tools_lines`）· `OUTPUT_CONTRACT`（现算动作表，`actions_lines`）· `TOOLCHAIN_FACTS`（这台机器的读数）· `WORKSPACE_FACTS`（版本与表名）· `TASK_FRAME`（这一次的运行时事实） | 它们的正文由注册表/能力表/磁盘现状决定。搬进文件 = 允许文件与事实各说一套，而那是本仓反复记过的那类缺陷（`draft/34` §3 的"必须生成"一栏） |
| **可以变文件**（写死的） | `ROLE_BRIEFS` 的六格（职责 / 边界 / 政策 / 姿态 / 签名错误 / 交付物）· `LOOP_PROTOCOL` · `PAPER_PACK` · `EVIDENCE_CONTRACT` · `HANDOFF_PROTOCOL` · `THREE_STATE` 的固定半 | 它们是手写散文；今天改一句话要动 Python 源码并重跑全量测试 |

**一张不变式**（A 轴与 B 轴的交界）：文件给的块与现算的块在装配后必须**互不覆盖** ——
同一个段名两次注册会抛（`promptkit.py:214-219`），所以"文件写了 `ROLE_BOUNDARY`、
代码又想生成 `ROLE_BOUNDARY`"这件事会**注册即炸**，不是静默后写赢。

### 3.2 目录布局（**实施时改过：以下是落地形态**）

实施 C1 那批时下面这份建议改了两处，两处都是被代码逼出来的（不是偏好）：

1. **随包根是 `roles/`，不是 `presets/`**。`presets.discover()` 把**根的每一个直接子目录**
   当成一个预设。根给 `presets/` 时，`roles/` 自己会被读成一个预设行（它没有组装文件）
   ⇒ 名册上多一条永远修不掉的坏行。
2. **共享块搬到名册之外**（`presets/shared/`）。原方案把 `_shared/` 放在 `roles/` 里，
   在"根 = `roles/`"之下它同样会变成一个坏预设行（id `_shared` 不合法）。

```text
agentflow/presets/                        # trust=system（随包根在它下面一层）
├── shared/                               # 十角色共用的写死块（一份；**不是预设**）
│   ├── evidence_contract.md              # 证据契约（判据同源：quoteverify / review_tools）
│   ├── handoff.md                        # 手稿协议（draft/37 §134 的逐字口径）
│   ├── three_state.md                    # 三态词表
│   └── loop_protocol.md                  # 循环协议全文（含 M 专段标记）
└── roles/                                # ← `composition.shipped_root()` 指这里
    ├── a/                                # 目录名 = 预设 id = `preset_id_of(role)`（小写化）
    │   ├── preset.yml                    # name / description / order
    │   ├── agent.agentflow.yml           # 组装：这个角色的块清单
    │   └── blocks/
    │       └── search_style.md           # A 的检索式（`draft/109` §2.1 的逐字草案）
    ├── b/ … v/ m/                        # 尚未迁移（每个角色先做 §3.5 的考察）
    └── prompts/                          # 可选：将来放"用户可加的规程"
```

**目录名为什么是小写**：预设 id 的字符集由 `presets.PRESET_ID` 定死（`^[a-z0-9][a-z0-9-]*$`，
照抄 `presetkit`：它同时是目录名、是 URL 里的一段、也是名册上的行标识），而角色 id 是本仓的
大写单字母（`schema.ROLES`）。映射写在唯一一处 `composition.preset_id_of`，并且有判据逐角色对账 ——
**实测**：目录叫 `A` 时预设读出来是"目录名不是合法 id：'A'"，于是**静默回落内置那份**，
除了 `prompt_audit["preset"]["problem"]` 之外没有任何别的读数会红。

`agentflow/presets/` 放在**仓库层**（与 `docs/` 同级）而不是 `src/agentflow/` 里：
放进 `src/` 就要在 `pyproject.toml` 里加 package-data，那是 FC-27（`pyproject.toml` 已在
端口批 5 命中过一次，还没签）。业主已裁定（`draft/106` §2 裁定 E）：**放仓库层**。

### 3.2b 共享块的漂移判据（**尚未落地**）

§3.3 那条"`shared/*.md` 每个文件至少被两个角色的 composition 引用"的判据今天**不成立**
（只有一个角色迁移了，任何共享文件都只被引用一次）。它的落地时点 = B 轴迁到第二个角色那一批；
在那之前它写出来就是一条恒假或恒真的判据（本仓对死判据的纪律：不留）。


### 3.3 与 DSH 的一处刻意偏差：**共享块不复制**

DSH 的预设是"整份复制"，它自己承认代价（`dsh-agent-presets/README:179` 逐字）：
"A copy is a snapshot that drifts … there is no patch semantics at this layer to express
'standard plus one change'"。它随包的 `cordis` / `code` 就是把 standard **抄一遍再改**。

我们**不照抄这一条**：十个角色的提示词共享三大块（证据契约 / 手稿协议 / 循环协议），
而它们是同一份判据、同一个来源（引文回验、手稿编号、三态词表）——
复制十份等于把"改一处、漂九处"制度化。所以：

- **共享块一份**（`_shared/`），每个角色的 composition 用**相对路径**引用；
- **角色专属块**每个角色一份（`blocks/`），它们本来就该各写各的；
- 漂移由一条判据守：`_shared/*.md` 的每个文件都必须被至少两个角色的 composition 引用
  （一个都不引用的共享文件 = 死文件；只有一个角色引用的共享文件 = 该搬进那个角色的 `blocks/`）。

这与 `draft/102` §2.2 的 order 表不冲突：order 是**渲染顺序**，引用是**内容来源**。

### 4.1b 接线契约：**预设覆盖"写死的块"，代码留着"现算的块"**（本轮定的）

上面那张表有个隐含的分工，实施前必须写下来 —— 它决定"一个角色的预设**必须**覆盖多少"：

| 类 | 有哪些段 | 谁给 | 预设必须覆盖它吗 |
|---|---|---|---|
| **写死的文本块** | `AGENT_IDENTITY`（`duty` 那一句）· `ROLE_BOUNDARY` · `ROLE_POLICY` · `STANCE` · `SIGNATURE_ERROR` · `DELIVERABLE` · `EVIDENCE_*` · `PAPER_*` · `HANDOFF*` · `THREE_STATE` · `LOOP_*`（B 轴之后） | **预设**（`agentflow.text_blocks` + `file:`） | **是**（这一批就只搬这些；没搬的仍由代码给，见下） |
| **现算的块** | `TOOL_00…` · `FACULTIES*` · `OUTPUT_CONTRACT` · `PARTNERS(+_AVAILABILITY)` · `TASK_*` · `TOOLCHAIN_FACTS` · `WORKSPACE_FACTS` · persona 两个槽位 | **代码**（解析函数现算；`agentflow.tool_blocks` 这类行只是"声明要它"） | 否（它们跟着注册表/能力表/当次事实走，搬进文件就等于允许文件与事实各说一套） |

**契约（一句话）**：**预设决定"写死的那些块由哪段文件给"；代码永远给现算的那些块。**
于是：

- 一个角色的预设**只列写死的块**（A 那份大约 6~8 行 + 共享块若干行），**不必覆盖全部 64 段**；
- **冲突纪律**：同一个段名被"预设"与"代码"同时注册 ⇒ `promptkit` 注册期就抛（同名两次）。
  所以代码侧必须知道"这一段有预设接管了" —— 落法是 `role_prompt_registry` 收一份
  `provided: set[str]`（预设声明的段名集合），注册写死块时跳过集合里的名字。
  这是**唯一**一处为接线加的机制，且它只影响"谁注册"、不影响"注册什么"。
- **验收判据因此可以很硬**：第一个角色（A）的预设把六段文本**逐字搬进文件** ⇒
  **A 的 `prompt_sha256` 必须一个字节都不变**（搬的是同一份文本）；其余九格也不许动
  （它们仍走代码路径）。这一条比"看起来对了"强得多，而且不需要新增机器判据。

```python
    ...                                        # 下面照旧注册，按 `provided` 跳过同名段
```

**回落是必须的**（三态纪律）：预设坏掉时不许"半组装"，也不许让整个系统起不来 ——
落点是"回落到内置注册 + 把回落这件事记进审计读数"（`prompt_audit` 加一格
`preset: {id, path, trust, rows, problem}`，`problem` 涵盖发现期与组装期两档）。

### 4.3 user 消息通道（动态）：instructions 与 contexts 的落点

| 通道 | 时机 | 落点 | 判据 |
|---|---|---|---|
| 运行时上下文快照 | 每趟开场 + 每次装配后变了 | `messages` 的**第一条**（在 `_opening_transcript` 之后）或步边界追加 | 空快照不发（`join_context_sections` 返回空串）；被抑制时 `contexts_suppressed=True` 是一个能点名的状态 |
| 工作区指令（基线） | 每趟第一次 `ask_step` 之前 | `messages` 追加一条 user 消息 | `render_baseline` 的 `byte_count <= maxBytes`；空链零 token |
| 工作区指令（增量） | 成功的 `read`/`write`/`edit` 之后**下一步** | 步边界（`agent_loop.py:2871` 附近）追加 | `InstructionState.plan()` 只报 add/replace/remove；`unchanged` 不注入 |

三处共同的纪律（逐字来自 DSH，`draft/101` §4.4）：**追加式**、**新内容排在可复用前缀之后**、
**提供者失败不加消息**（绝不产生半条）。

### 4.4 生成戳与挂一次在接线里怎么用

`PresetMount` 的语义是"一个预设挂一次、戳变了才换代"（`presets.py`）。
在本框架里，"挂"的产物**不能是一个进程级的注册表**（那是 DSH 的 Cordis 模型），
因为我们的 `role_prompt_registry` 每次调用都新建注册表（`agent_prompts.py:2016-2017` 的
逐字理由：混用全局注册表会让两次运行互相看见对方的任务）。

所以接线用 `PresetMount` 的**两件东西**、不用它的第三件：

- 用它：**生成戳**（"这个角色的预设文件变过没有"）与**代数**（`generation`），
  落到 `prompt_audit` 里 ⇒ 事后能回答"这次跑的是第几代预设"；
- 用它：**坏预设拒挂**（`mount` 抛 ⇒ 回落，见 §4.2）；
- 不用它：`_mounted` 那个进程级缓存 —— 我们的注册表是**每趟新建**的（prefix 稳定在
  "一趟之内"这个粒度上，`agent_loop.py:2691` 每趟算一次）。

### 4.5 J 裁定（乙）的落地设计：哪些事实会变、哪些冻结、`system` 什么时候重发

业主 2026-10-11 裁定 **J = 乙**（允许 `system` 在事实变了时重发），并确认它**覆盖**
`draft/99` 第 6 条 B2 当时的"丙 = 不做"。这一节的读数是本轮实读（`agent_loop.py` 的
`system`/`facts` 那一段），设计据此而定。

#### 4.5.1 现在进 `system` 的事实里，哪些会在一趟之内变（实测清单）

`system` 在 `agent_loop.py:2706` 每趟算一次，并在步循环里**每步原样传下去**（`:2872`）。
进它的事实有 14 个，按"会不会变"分三类：

| 类 | 事实 | 出处 | 会变吗 |
|---|---|---|---|
| **结构性（一生不变）** | `task` · `summoned_by` · `task_id` · `depth` · `parent_task_id` · `workspace_root` | `:2695-2699` | 不会 |
| **本机读数（一趟内不变）** | `toolchain_facts`（`AP.toolchain_facts_text()` 有 `lru_cache`）· `availability`（接线态） | `:2704`、`:2683` | 几乎不会（接线态要重启才变） |
| **会变（现在被冻结成开局那一版）** | **`budget_left`** · **`notebook`**（模型自己的草稿本，它每一步都可能写） · **`board`**（板项会被标 seen/close） · **`user_replies`**（迟到的回答） · `children`（这一趟新派的子代理） · `inbox`（新留言） | `:2695-2703`，全部在步循环**之前**算好 | **会** |

**最要紧的一条**：`budget_left` 在 `TASK_BUDGET`（order 4250）那一段里逐字渲染给模型看，
而它只在**开局**算过一次。花销每一步都在涨 ⇒ **从第 2 步起，模型读到的是一个偏大的旧数字**，
而循环协议里又逐字写着"花销预算耗尽时你必须收工" —— 它据以决定"还能不能继续"的那个数，
是这一趟开局时的数。`notebook` 同理：那是它自己的草稿本，而它读到的永远是开局那一版
（真机 `note` 是追加写盘的，见 `draft/107` §3.1 A14 那条更正）。

#### 4.5.2 设计（三档处置，按"值不值得换 KV cache 前缀"分）

| 档 | 事实 | 处置 | 为什么 |
|---|---|---|---|
| **甲：每步现算、变了就重发 `system`** | `budget_left` · `notebook` | 现算（纯算术 / 一次小文件读），拼出新的 `system`；**与上一版逐字相同就复用旧串**（不比就重发会让每步的前缀都变，白扔 cache） | 这两个是模型**据以决策**的数（还能不能继续、我自己写过什么），错了直接改变行为；且现算极便宜 |
| **乙：不开 `system`，走 user 消息增量** | `inbox` · `board` · `user_replies` · `children` | 保持"开局进 `system`"，新增部分由**每步的结果消息**带（`inbox` 已经是这么做的：协议逐字写"每做完一步，框架会把你收件箱里新到的消息附在结果里"）；`board` 的新项同路；`children` 的活视图走 `roster` 形状 | 它们是**追加式**的：增量消息比"重发整段前缀"便宜得多，而且 DSH 的纪律正是"新内容排在可复用前缀之后" |
| **丙：冻结** | 结构性 6 项 + `toolchain_facts` + `availability` | 不动 | 它们在一趟之内不会变；重算它们只会制造无意义的差异 |

#### 4.5.3 落地形状（判据也一起给）

```python
# 步循环里（`_prompt` 之前）：只重算"甲"档两格，拼一次 candidate；逐字相同就复用
cand_facts = dict(facts, budget_left=self._budget_text(), notebook=self._read_notebook())
cand = AP.system_prompt(self.role, registry=self.registry, **cand_facts)
if cand != system:
    system = cand                      # 从这一步起用新的
    changed_at = step
    SS.append(self.session_root, {"kind": "agent_note", "role": self.role,
               "note": f"system 重发（facts 变了）：第 {step} 步"}, sid=self.sid)
```

- 读数：`agent_step` 事件里已有 `prompt_sha256`? —— 没有（只有 `agent_run_start` 有）。
  本设计新增一格**每步的 `system_sha256`**（变了才写），于是"第 N 步的模型读的是哪一版 system"
  事后可答（今天只答得出"开局那一版"）。
- 判据（**不新增机器判据**，按业主口径 C；只扩现有正控）：现有"每步发消息序列"那条判据里
  加一跳 —— 花销变了之后**这一步的 system 与上一步不同**；没变时**逐字相同**
  （后半句防的是"每步都重发 ⇒ 前缀永远在变"）。
- 不做：不动 `prompt_audit` 的 `prompt_sha256` 语义（它是**开局**那一版，`agent_run_start` 里
  与 `prompt_version` 配对；每步那一格是**另一个读数**，两者不许混用同一个名字）。

#### 4.5.4 ✅ 已落地（2026-10-11，批 J1；业主裁定 J=乙）

落成 `agent_loop.AgentLoop._refresh_system(facts, system, *, step)`：在**每一个步边界**
（压缩判定之后、`ask_step` 之前）重算那两格，**逐字比**再决定发不发：

| 情形 | 行为 | 理由 |
|---|---|---|
| 两格都没变 | **原样返回旧串**（一个字节不动） | "没变却重发"会让每一步的前缀都变 ⇒ KV cache 全废 |
| 任一格变了 | 换新串 + 落一条 `agent_note`（带 `step` 与 `system_sha256`） | "变了不重发"更坏：模型会按一个偏大的旧预算决定要不要收工 |

两处实现口径：

- **只重算那两格**（`budget_left` / `notebook`），其余开局事实一趟之内不变 ——
  把它们也重算只会制造无意义的差异（§4.5.2 的"丙"档）；
- 渲染成本**实测 11.5 ms**（`AP.system_prompt` 一次，本机 20 次取平均），
  `notebook_digest` 是一次小文件读 ⇒ 不值得为省它而让模型按旧数决策。

**判据**（`tests/test_every_step_sends_a_message_sequence.py::test_the_system_is_resent_only_when_the_changing_facts_change`，**三跳一起判**）：
① 正控：非零价 ⇒ 花销涨 ⇒ 第 1 步的 system 与第 0 步**不同**；
② 负控：价 0 ⇒ 逐字相同（防"每步都重发"）；
③ 读数：变了才写那条 `agent_note`，价 0 那一趟**一条都不该有**。

**一处夹具陷阱**（第一版因此红过，记下来）：`LlmSeam.price` 的单位是**每百万 token**
（`modelcost.usd_for`），而替身模型每次只报 10 in / 10 out ⇒ 价给 0.001/0.002 时
算出来是 3e-8，`f"{usd:.6f}"` 渲染出来仍是 `0.000000` ⇒ 预算那一格**看不出变化**，
判据红而红的原因在夹具不在代码。夹具现在给 `(1.0, 2.0)`（每百万），
一次调用约 3e-5 美元 ⇒ 六位小数上看得见。

**本批不动提示词文本**：`PROMPT_VERSION` 仍是 p72、十格摘要一格不变 ——
J=乙 改的是"什么时候重发"，不是"发什么"。
