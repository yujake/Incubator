## §0 三条前置结论（先说风险，不埋在下面）

1. **唯一真正不可逆的面是 `schema.py` 的存储契约**。改它有两种：①**放宽**（把必填变可选：`proof_text`/`disclaimer`/`citations`）——历史 969 份快照在调查里已全部通过当前 schema，放宽后仍然通过，**安全**；②**加字段**（`grade`、`claims[].status`）——必须**有默认值或由代码派生**，否则历史行会被 `validate_table` 判死。**结论：可以改，但只能"放宽 + 带默认值新增"，不许"加必填字段"**；`SCHEMA_VERSION` 是否升版见 §3。
2. **读数口径一变，历史裁定就失去可比性**。`reviewed_proof_rows`/`document_rows`/`manuscript_rows` 的含义在 D64/D65 已经改过一次。**结论：每改一次口径，必须在 `draft/44` 那一行写下"从哪一趟起口径变了"**，否则以后没人能解释两趟读数为何不同。
3. **"贯彻不下去"的已知机制有三个**（都来自本项目自己的账）：①改一半留一半（提示词里留旧口径、代码里加新口径）；②改了代码没改它的镜像/快照/计数/文档（`specs/*`、两个 golden 快照、`README`/`DEVELOPMENT`/`ROLE-SPECS`、`AGENT-PROFILES.md`）；③改了判据没配"改前必红"的负控 ⇒ 判据恒真。**执行协议（§2）就是针对这三个机制写的。**

## §2 执行协议（针对"贯彻不下去"的三个机制）

**一批 = 一次闭环**，每批必须走完六步，缺一步不算做完：

1. **清引用面**（改任何文件之前）：`grep` 该符号在 `tests/`、`docs/`、`README`、`cli.py`、快照、`specs/*` 的引用；把清单写进该批的施工单行。
2. **改代码 + 配负控**：每条改动配一条"改前必红、改后必绿"的负控（用**独立口径**算，不抄实现）。
3. **真机回放**：在既有工作区（`p8e`/`p8f`/`p8g`/`p7b`/`p6q`/`p5-review-t17`）上跑改前/改后读数对比，确认红的正是"本来就该红"的那些；把两张读数贴回 `draft/44` 对应行。
4. **全量套件一次** + lint（日常/strict）+ 快照重冻。
5. **禁改区报备**：跑 `python -B scripts/noai_gate.py --git --since <基线>`，把 `requires_human` 与理由写进提交信息；**不自签** `.noai-approvals.json`。
6. **登记册回填**：该批每条改成"已落地 + 真机读数 + 发现的新问题（若有）"。

**硬约束**：不许跨批混改（避免读数说不清是哪条生效）；不许"提示词先删、代码后补"（顺序必须是代码先接住）；不许加**必填**新字段（只许放宽与带默认值新增）。

## §3 四道闸：如何确认"不引入更多问题"

1. **兼容闸（历史数据）**：任何 `schema.py` 改动后，先跑"969 份历史快照逐份 `validate_table`"（调查 C 已给出这个测法），要求**失败数不增**；任何读数口径改动后，要求历史工作区的门**不因新口径而变红**（除非刻意，且要在登记册写明）。
2. **负控闸（判据可伪）**：新增/收紧的每条判据必须有至少一条能红的样例；元判据本身用"注入式"负控（monkeypatch 改坏 ⇒ 必红）。
3. **真机闸（行为面）**：凡标 `行` 的条目，必须在一趟真机上看到预期变化（例：R-01 之后 `E.run_experiment` 的失败不再烧满 600 s；S-01 之后 `analysis_reports` 首次非 0 行）。看不到变化 ⇒ 不算落地。
4. **回滚闸**：每批是一个独立提交（或一组按文件分组的提交），提交信息里写"如何回滚"（因为 `schema`/`counters`/快照改动不可简单 `git revert` 时要手工处置）。
