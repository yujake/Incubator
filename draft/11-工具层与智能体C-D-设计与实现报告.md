## 1. 需求与交付概览

### 1.1 用户原话（本轮）

> **工具描述**：首先要给 A 和 B 智能体配齐关于所有涉及的文件的增删改查工具，此外 A 要配备强大的文献检索工具，B 要有 OCR 工具。总之要将符合"**根据给定信息完成标准操作**"的几乎所有工作尽量用自动化脚本或工具来实现，**以不打扰智能体的思维链**。实现智能体 C 时也要做工具。
>
> **智能体 C：关系分析**：接收 B 维护的关系表，**用程序分析关系表**，给出报告。需求可能为"统计最热门的几个概念"（这时应该对关系表的代号组做计数，然后对最多频次的概念翻译回到底是啥概念）、"查询两个概念间的关系"（这时应该从两个概念的代号出发做"图"的搜索，给出多条**实质上重合度不高**的路径，然后**阅读每条路径每步的所有关系**，对每条路径选择最合理的关系链写进报告，并**评估每条关系链蕴含的实际信息量给出低/中/高判决，写进报告的都是信息量高的**。路径需包含**关系代号链**）、"研究冷门概念"（统计频次，报告冷门概念和一些热门概念间的关系，并评估哪些关系连接较弱）、"完善关系图"（调查关系频次较少的概念组，评估这些是否确实可能有值得研究的关系，**若确实有，则报告**）。
>
> **智能体 D**：接收 C 的报告进行系统分析，**根据代号溯源到相关表述**，按需溯源到文献内容，评估值得研究的问题并做初步研究，**如有实质上的知识不足就向智能体 A 提交查询请求**，A 查完后 B 立刻消化，B 消化完后让 D 看，然后 D 继续思考研究。D 生成较为详细的初步研究报告。
>
> **本轮以最低标准堪堪可用就行，等后续开发。**

## 2. 为什么必须有一层"工具层"

原先 A/B 直接调 `store`、`providers` 的函数。一旦智能体由 LLM 驱动，这就不够了：

| 问题 | 后果 |
|---|---|
| LLM 需要"手写 JSON 去改表" | 一次转义错误就写坏数据；而且**每改一行都占一轮思维链** |
| 没有统一的输入校验 | 参数错了要到实现深处才炸，错误信息与调用点隔了好几层 |
| 没有统一的**副作用声明** | 无法判断某个动作要不要审批 —— 只能靠人记 |
| 同一套能力在"脚本模式"和"LLM 模式"下要写两遍 | 两条路径必然漂移 |

工具层把"标准操作"固化成**有名字、有 schema、有校验、有结构化返回、声明副作用**的原子动作。
**智能体的思维链只花在"判断该调哪个工具"，不花在"怎么把参数拼对"。**

### 2.1 三个刻意的设计

**① `side_effect` 是一等公民**

```python
SIDE_EFFECTS = ("none", "read", "write_local", "network")
NEEDS_APPROVAL = ("write_local", "network")
```

`none`/`read` 可以任意调用、无需审批；`write_local`/`network` 需要。
**把审批判断建立在"声明"上，而不是靠人记忆哪些工具危险。**

这条设计最直接的收益体现在 C 身上：**C 的全部 8 个工具都是 `read`**。为什么重要？
因为 C 的职责是"**用程序分析关系表**" —— 它应当能**任意多次、任意组合**地查询，
而不触发任何审批或写盘。**如果查询会写盘，就没人敢让模型自由地反复取证了。**

**② 参数错误返回结构化失败，而不是抛异常**

```python
try:
    spec = self.get(name)
    validate_params(spec.params, params)
except ParamError as e:
    return fail(f"参数错误：{e}", tool=name, kind="param_error")
except ToolError as e:
    return fail(str(e), tool=name, kind="unknown_tool")
```

**只有"调用方写错"与"环境故障"才抛**；"业务上的失败"（如"没找到这个概念"）返回 `ok=False`。
理由：智能体看到 `ok=False` 可以自己纠正参数继续跑；抛异常会**打断它的循环**。
这就是"不打扰智能体思维链"的具体落实。

**③ 参数校验自己实现，不引第三方依赖**

只需要 `type` / `required` / `enum` / `items` / bounds 这几样。为此引入 `jsonschema`
会让"工具层能不能用"依赖于环境里有没有装它 —— 而工具层是**所有智能体的公共底盘**，依赖越少越好。

### 2.2 "按角色装配"就是权限面

```python
roles: tuple[str, ...] = ()   # ToolSpec 上声明谁能用
```

装配器按角色过滤：**A 拿不到 `research.*`（那是 D 的决策），B 拿不到 `search.*`（下载是 A 的职责且是网络副作用）。**

**把"谁能用什么"固化在注册表里，比写在提示词里可靠得多 —— 提示词可以被绕过，注册表不能。**

## 3. 工具层实现

### 3.1 契约

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str                 # "组.动作"，如 "table.create"
    summary: str              # 一句话（给 LLM 看）
    params: Mapping           # JSON Schema（object 根）：既用于本层校验，也能原样喂给 function-calling
    handler: Callable
    side_effect: str
    roles: tuple[str, ...]
    returns: str = ""
```

`params` 用 JSON Schema 写而不是 Python 类型标注，是为了**同一份声明既做校验、又做 function-calling 描述** ——
自描述、不含 Python 专有类型。

```python
@dataclass
class ToolResult:
    ok: bool
    data: Any = None
    error: str | None = None
    meta: dict = field(default_factory=dict)
```

### 3.2 注册约定的容忍（但有边界）

各工具模块是**并行开发**的，出现了三种入口约定。装配器容忍三种 —— 但**只限这三种**：

1. `register(registry, **deps)` —— 首选
2. `install(registry, **deps)` —— 等价别名
3. 模块级 `ALL_TOOLS: list[ToolSpec]` —— 纯声明式

**为什么要有边界**：再多就成"随便怎么写都能装上"的糊涂账了。容忍是为了避免并行开发的返工，
边界是为了让"装上了没有"仍然是个可判定的事实。

装配器另外做两件事：
- **按签名反射只传它声明要的依赖**（`store` / `root` / `graph` / `roles`）—— 少一个必须同步维护的耦合点；
- **模块缺失或注册抛异常时只记录不崩**，并把结果放进 `RegistryBuild.skipped`。

```python
@dataclass
class RegistryBuild:
    registry: ToolRegistry
    loaded: list[str]
    skipped: list[dict]      # 让"某个模块没装上"变成可见的事实，而不是静默少几个工具
```

### 3.3 36 个工具的分类清单

| 组 | 工具 | 角色 | 副作用 |
|---|---|---|---|
| 表 CRUD | `table.list` `table.get` `table.create` `table.update` `table.delete` `table.count` `table.schema` `table.search` | A B C D | `read` / `write_local` |
| 文件 CRUD | `fs.list` `fs.read` `fs.write` `fs.delete` `fs.move` `fs.stat` `fs.search` | A B C D | `read` / `write_local` |
| 文献检索（A） | `search.providers` `search.literature` `search.download` `search.dedup_check` `search.register` | A | `read` / `network` |
| OCR（B） | `ocr.backends` `ocr.detect_text_layer` `ocr.run` | B | `read` |
| 图分析（C） | `graph.build` `graph.stats` `graph.neighbors` `graph.relations_between` | C D | `read` |
| 代号溯源（C/D） | `trace.relation` `trace.concept` `trace.literature` `trace.chain` | C D | `read` |
| 研究（D） | `research.list_gaps` `research.submit_gap` `research.write_note` `research.poll_waiting` `research.set_status` | D | `read` / `write_local` |

**各角色工具数（实测）**：`{'A': 20, 'B': 18, 'C': 23, 'D': 23}`。

### 3.4 各模块的关键取舍

**`table_tools`**
- 写操作一律走 `store.tx(...)`，并**声明它要写的所有表**（含 `counters`，因为 `alloc_id` 需要）。
- `table.update` 是**部分更新**：只覆盖 `patch` 里给出的字段，其余（**含 `_` 开头的诊断字段**）原样保留。
  这是最容易写错的地方，实测已验证。
- **拒删被引用的行**：`不能删除 concepts 0000：仍被 1 处引用（relations.0000(concept_ids)）…`
  —— 静默删除被引用的行会让 `verify` 报 `dangling_*`。
- **拒改主键**：`主键是外键的锚点，改了会让所有引用它的行变成悬空引用`。
- `table.schema` 从 dataclass **反射**出字段与全部受控词表，不手抄。

**`fs_tools`**
- 所有路径相对**工作区根**解析，并强制 `resolve()` 后仍在根内（防 `..`、防符号链接逃逸、防绝对路径）。
- 实测拦截：`../../etc/passwd`、`C:\Windows\win.ini`、UNC、`\\?\` 设备命名空间、`NUL`、`aux.txt`、`a:b`。
- `fs.delete` 默认只删文件；删目录必须显式 `recursive=True`；**拒删工作区根**。
- 二进制用启发式探测（含 NUL 字节），不试图解码成乱码文本。

**`search_tools`（A）**
- `search.literature` 返回的每条候选都带 **`dedup_key` 与 `is_new`** —— 这样 A **一眼看出哪几条是新的**，
  不必为了判重再跑一次工具。这正是"不打扰思维链"。
- `search.providers` **真实探测**（实发一次极小请求），返回 `status=probed_ok` + `latency_s` + `evidence`（实际请求的路径）。
  实测：OpenAlex 0.64s、Crossref 1.56s。
- 无 store 时 `is_new` / `existing` 返回 **`null` 而不是 `False`** —— 避免把"没查"当成"是新的"。

**`ocr_tools`（B）** —— 见 §8。

**`graph_tools` / `trace_tools`（C/D）** —— 见 §5、§6。

**`research_tools`（D）**
- `research.submit_gap` **必须查重**：同一问题已有**未完成**的等待请求时不得重复提交。
- `research.poll_waiting` **只做确定性判断且不写盘**：把状态迁移留给 `agent_d` 而不是工具内部 ——
  工具一旦偷偷改状态，"这一轮到底谁动了什么"就不可审计了。这也让本工具保持 `read` 副作用。

### 3.5 ⚠️ 接口约定提醒（调用方最容易猜错的地方）

| 工具 | 返回 | 不是 |
|---|---|---|
| `table.create` | **新 ID 字符串**（如 `"0000"`） | 不是 `{"id": "0000"}` |
| `table.get` | **行 dict 本身** | 不是 `{"row": {...}}` |
| `table.list` | 含 `rows` 与总数的对象 | — |

这一条是实测踩出来的：我写冒烟测试时按 `data['id']` 取新 ID，直接 `TypeError`。
**接口约定必须写进文档，否则每个调用方都会猜错一次。**

## 4. 数据模型扩展

### 4.1 `data/research_questions.json`（D 的工作台）

| 字段 | 来源 | 说明 |
|---|---|---|
| `question_id` | 扩展 | 4 位代号 |
| `question` | 需求 | 研究问题文本 |
| `origin` | 扩展 | **溯源**：如 `"C:paths:0000:0009->0010->0005"`（报告号 + 关系代号链） |
| `related_concept_ids` / `related_relation_ids` | 扩展 | 相关代号（升序去重） |
| `status` | 扩展 | `open` / `needs_evidence` / `researching` / `answered` / `dropped` |
| `priority` | 扩展 | `high` / `medium` / `low` |
| `evidence_lit_ids` | 扩展 | 已用到的文献 |
| **`waiting_request_ids`** | 扩展 | **已向 A 提交的查询请求** |
| `gap_reason` / `notes` | 扩展 | 缺口理由 / 研究笔记 |

**为什么 `waiting_request_ids` 是关键字段** —— 需求说"知识不足 → 问 A → A 查 → B 消化 → D 继续"。
这个"**继续**"要能自动接上，就必须记住"我之前在等哪几个请求"。
否则 D 无法判断"新文献来了，哪些问题现在可以往下走了"。没有它，D 只能靠猜或重问。

schema 层强制了两条一致性：
```python
if self.status == "needs_evidence" and not self.waiting_request_ids:
    raise ValueError("status=needs_evidence 时必须记录 waiting_request_ids，否则无法判断"
                     "「新到的文献是不是我正在等的那批」，D 的循环就接不上")
if self.status == "dropped" and not self.notes.strip():
    raise ValueError("status=dropped 时必须写 notes 说明为什么放弃（不许静默丢弃）")
```

### 4.2 `data/analysis_reports.json`（C 的报告登记）

| 字段 | 说明 |
|---|---|
| `report_id` / `kind` | 4 位代号 / `hottest` `paths` `cold` `gaps` |
| `request` | **原始需求原文**（保留以便审计"报告是否答非所问"） |
| `params` | 结构化参数 |
| `summary` | 结论摘要（**D 读它的第一入口**） |
| `payload` | **结构化结果**（D 靠它溯源到代号链） |
| `markdown_path` | 人可读的报告文件 |

**为什么"登记表 + 文件"双份**：D 需要**机器可读**的部分来溯源（`payload` 里的代号链），
人需要**可读**的部分（markdown）。只存 markdown，D 就得解析自然语言才能拿到代号；
只存 JSON，人读不了。**这不是冗余，是两个不同的消费者。**

## 5. 智能体 C：关系分析

### 5.1 定位：程序做分析，LLM 只做排序与措辞

需求原话是"**用程序分析关系表**"。所以：

**计数、索引、图搜索、路径枚举、去重、评分、溯源 —— 全部是确定性代码。**
只在两处留 LLM 钩子（构造时传 `llm=None` 即默认关闭）：
① 路径"最合理关系链"的排序；② "是否值得研究"的判断。**两个钩子都有确定性回退**，
保证无 API key 时功能降级但不缺失、且可测试。

实测三处钩子都如实报告未启用：*"路径顺序完全由确定性评分决定"*。

### 5.2 图模型

```
节点 = 概念（concept_id）
边   = 关系（relation_id），连接 concept_ids 里的每对概念
```

**关键细节：一条关系可以连 >2 个概念**（需求的"概念代号组"是数组）。
一条 `concept_ids=[A,B,C]` 的关系会产生 3 条两两边，**但共享同一个 `relation_id`**。
所以路径输出的是**关系代号链**，而不是概念链 —— 这正是需求所要求的。

`RelationGraph` 一次构建、多次查询，索引：

```python
concept_relations: concept_id -> [relation_id...]      # 参与的**全部**关系
adjacency:         concept_id -> {neighbor_id: [relation_id...]}
group_counts:      concept_group_key -> 出现次数
```

### 5.3 四类需求的算法

#### (1) `hottest(top_n)` —— 统计最热门的概念

**计数口径**：对每条关系的 `concept_ids` 里**每个概念 +1 次出现**
（一条涉 3 个概念的关系算 **3 次**，不是 1 次）。同时给出 `relation_count` 与 `group_count`。

按出现次数降序取 top_n，**把代号翻译回概念名**（需求明确要求），并给每个热门概念的**代表关系**
（按引文校验与信息量取前 3），便于核对"热度是否名副其实"。

**排序必须稳定**（同分按 concept_id 升序）—— 否则同一份数据每次跑出来顺序不同，无法复核。

实测输出：
```
| 概念代号 | 概念名 | 出现次数 | 关系条数 | 概念组次数 |
| 0002 | 域     | 6 | 6 | 6 |
| 0000 | 群     | 5 | 5 | 5 |
| 0004 | 理想   | 4 | 4 | 4 |
| 0005 | 模     | 4 | 4 | 4 |
| 0008 | 环同态 | 3 | 3 | 3 |
```

#### (2) `paths(a, b, ...)` —— 查询两概念间的关系（最复杂）

严格按需求的六步：

1. **有界图搜索**：简单路径（节点不重复），`max_len` 默认 4 跳 + `node_budget` 搜索预算。
   触及预算要**如实截断并记录**（`truncated=True`），不许假装搜完了。
2. **低重合度筛选**（需求："给出多条**实质上重合度不高**的路径"）：用**节点集合的 Jaccard 相似度**
   与已选路径比较，> `max_overlap`（默认 0.5）则丢弃。
   **只按"路径不同"筛是不够的** —— 只差一个中间节点的两条路径实质上是同一条。
3. **每步读全部相关关系**（需求："**阅读每条路径每步的所有关系**（毕竟包含概念 a 和概念 b 的关系可能挺杂）"）：
   对每一跳的两个端点取 `relations_between(a,b)` 返回的**全部**关系 ——
   因为"最合理的链"未必是搜索时随机选中的那条边。
   实测输出：`第 2 跳 模(0005) → 理想(0004)：候选 2 条 ['0014','0008']，选中 0014`
4. **为每条路径选最合理的关系链**：确定性排序（`quote_verified` True > None > False；
   `status` active > suspect > rejected；再比描述长度与文献多样性）。
5. **信息量判决 低/中/高**：见 §5.4。
6. **只写高信息量**（需求："**写进报告的都是信息量高的**"）：
   `high` 进正文；`medium` 进**明确标注"未达正文标准、不作为证据"**的附录；`low` 只在统计段计数。
   **若一条 high 都没有，报告必须明说"没有找到高信息量路径"**，不许硬凑。

实测输出：
```
图搜索到 6 条简单路径（按跳数分布 {'1':1,'2':2,'3':2,'4':1}）
低重合度筛选后保留 3 条，因重合度丢弃 3 条
信息量判决：high 2 / medium 0 / low 1
```
报告里还单列「**被重合度筛掉的路径**」，带 Jaccard 值使去重**可审计**：
```
- 群→模→域：与已选路径节点重合度 0.67 > max_overlap=0.5（本质上同一条路径）
```

#### (3) `cold(top_n)` —— 研究冷门概念

- 按度数升序取最冷门，**排除 `degree==0`** —— 它们**单独归一类"完全孤立"**。
  理由：**"没人研究"和"没人连接"是两件事**，混在一起会掩盖真正的问题。
- 列出冷门概念与**热门概念**之间的全部关系（需求要求）。
- **评估哪些关系连接较弱**，弱判据是**可核实的**：`quote_verified is not True`、
  `status==suspect`、它是该概念**唯一**的连接、或另一端也很冷门（无法借力）。给 `weak_score` + 理由字符串。
- **单独列出"冷门但连接强"** —— 这一类最可能是**被低估的研究点**，是给 D 的核心输入。

实测输出：
```
- 冷门 top5（已排除 degree=0）：阿贝尔群, 环, 子群, 素理想, 环同态
- 完全孤立（degree=0，单列）：0009
- '冷门但连接强'（最可能被低估）5 个
- `0010` 与 环同态：… → 弱（weak_score=0.25）
```

#### (4) `gaps(limit)` —— 完善关系图

找**频次少的概念组** + **结构洞**（两个概念有共同邻居但彼此之间没有直接关系 ——
"应该有边却缺失"的经典信号）。

**⭐ 否决项 vs 扣分项** —— 这是需求那句"**若确实有，则报告**"的落点：

| 档 | 信号 | 处理 |
|---|---|---|
| **否决项（veto）** | 相关关系的 `quote_verified` **全部**为 False / 概念名明显不是概念 / `duplicate_of` 非空 | **直接剔除**，不进 `candidate_gaps`，但**仍逐条列理由** |
| **扣分项** | 引文校验**部分**失败 / `suspect` 占比高 / 仅有单一连接 / 另一端也冷门 | 参与净分 |

**为什么必须分两档**：`引文校验全部失败` 意味着**这条候选没有任何可核实的依据** ——
它不该靠其它正向分（共同邻居、热门、文献数）把净分抬回 medium。

改前实测：一条"净分 1.25"的候选会因正向分被判 medium；改后被 veto 剔除。
改后「证据不足」场景：`verdict=无`、`candidate_gaps=0`、`vetoed=3`，
结论原文：*"3 条候选被**否决项**直接剔除（引文全部无法核实 / 概念名不是概念 / 已被判重）
—— 它们没有可核实的依据，扣分再多也不能算'确实有'"*。

实测「有」的场景：
```
- 二元结论：**有**
- 检索范围：概念组 14 个（其中低频 13 个）、结构洞 16 个（检查三元组 38 个，预算 5000，截断=False）
- 否决项剔除 0 条；净分不足（low）0 条
### structural_hole：模 ↔ 环同态（0005|0008，置信度 high）
- 理由：结构洞：有 2 个共同邻居（群、域）却无直接关系；热门概念参与；文献充足
- 正向信号（2.5）/ 负向信号（-0.0714）：status=suspect 占 1/7
- 净分 2.4286
```
并**如实报告被 limit 截断**：*"另有 23 条中等以上置信度候选超出 limit=6 未展开（已在统计中计数）"*。

### 5.4 信息量评分（确定性、可解释、可逐项打印）

```
score = 2.0 * (quote_verified 为 True 的比例)        # 有原文支撑是最强信号
        - 1.5 * (quote_verified 为 False 的比例)     # 引文找不到 = 可疑
        - 1.0 * (status == suspect 的比例)
        + 0.6 * min(跳数, 3)                         # 多跳 = 更多推理链（边际递减）
        + 0.8 * (不同文献数 / 跳数)                   # 跨文献的链条更有价值
        - 0.5 * (平均描述长度 < 12 字符)
        + 0.5 * (路径上出现不在热门集里的概念)         # 绕开了最常见节点
判决：score >= 3.0 → high；>= 1.5 → medium；否则 low
```

阈值在 `config.yaml`，不写死。**评分函数必须能逐项打印中间值** —— 实测报告中每条路径都带 7 项 `score_breakdown`：

```
- 引文已校验比例：quote_verified=True 的跳数 3/3 = 1.00 → +2.0
- 引文校验失败比例：quote_verified=False 的跳数 0/3 = 0.00 → +-0.0
- suspect 比例：status=suspect 的跳数 0/3 = 0.00 → +-0.0
- 跳数：min(跳数 3, 3) = 3（边际递减） → +1.8
- 跨文献多样性：不同文献 2 篇 / 跳数 3 = 0.67 → +0.5333
- 描述过短：平均描述长度 14.3 字符 → 不计入 → +-0.0
- 绕开最常见节点：不在热门集里的概念 无 → 不计入 → +0.0
    合计 4.3333（阈值 high>=3.0 / medium>=1.5）⇒ **high**
```

**为什么可打印中间值是硬要求**：D 要判断"该不该信这条链"。
一个不透明的分数无法支撑那个判断 —— 而"看起来很像真的"正是幻觉引文最危险的地方。

### 5.5 接口

```python
class AgentC:
    def __init__(self, store, config=None, actor="agent-C", llm=None)
    def build_graph(self) -> RelationGraph
    def hottest(self, top_n=5, request="") -> AnalysisReport
    def paths(self, a, b, *, max_paths=5, max_len=4, max_overlap=0.5, request="") -> AnalysisReport
    def cold(self, top_n=5, request="") -> AnalysisReport
    def gaps(self, limit=10, request="") -> AnalysisReport
    def handle(self, request_text: str) -> AnalysisReport   # 关键词分派，确定性
```

`handle()` 实测分派四类需求全部正确，并在概念解析不到时 `fail` 且**列出候选概念名**：
```

'查询 群 与 域 之间的关系'    → paths
'研究冷门概念'              → cold

```
**未命中任何关键词时如实说无法分派**（不默认猜一个）。

## 6. 智能体 D：研究循环

### 6.1 定位

D 的核心**不是"生成文本"**，而是管理一个 **问题 → 证据 → 缺口 → 新证据** 的循环。

```
        读 C 报告
            ↓
   [1] ingest：提取候选研究问题          → research_questions(status=open)
            ↓
   [2] consider：评估证据是否足够（确定性判据）
        ├─ 足够 → researching → [4] research → 写报告
        └─ 不足 → [3] 向 A 提交查询请求（status=needs_evidence, waiting_request_ids=[r-xxxx]）
                        ↓
                   A 检索 → B 消化 → 新文献/新关系落库
                        ↓
   [5] poll：等待中的请求完成了吗？新文献消化了吗？
        └─→ 回到 [2]（这就是需求说的"D 继续思考研究"）
```

### 6.2 ⭐ "继续"靠等待集，不靠猜测

`poll()` 只依据三件**可核实**的事：`waiting_request_ids` 里的请求是否 `done`（看 `outcome`）、
其 `result_lit_ids` 是否都已 `processed`（B 消化完）。**全是确定性判断，不需要 LLM。**

**没有等待集，D 就无法判断"新来的文献是不是我在等的"** —— 只能靠猜或重问。

### 6.3 三级溯源

| 层 | 从 | 到 | 工具 |
|---|---|---|---|
| **L1** | `relation_id` | `quote` / `description` / `page_range` / `status` / `quote_verified` | `trace.relation` |
| **L2** | `concept_id` | 概念定义 + 它参与的全部关系的**表述** | `trace.concept` |
| **L3** | `lit_id` | 文献元数据 + 本地文件 + **正文片段**（按需） | `trace.literature` |

**L3 是按需的（贵）** —— 只有 L1/L2 的表述不足以判断时才下钻到正文。

**实测报告里的两段式呈现**（这是修过一版的结果，见 §10/#8）：
```
**链条自身的表述（L1，按跳序）**
1. `R0009` 群 → 环同态（status=active，quote_verified=True）：
   群的运算可经环同态与环的加法结构对应
   引文 > A ring homomorphism is a map preserving addition, multiplication and the unit element.
   ← 文献 `0008`，pp. 1-1
2. `R0010` 环同态 → 素理想
3. `R0005` 素理想 → 域

**相关概念的其它表述（L2，上下文，未参与本链）**
… 另有 2 条上下文未展开（共 8 条）
```

⭐ **一个值得单列的实现细节**：**跳序是从 `origin` 字符串读回的**。
因为 `related_relation_ids` 是 schema 要求的**升序字段，跳序在那里已经丢了**。
要复原"链的顺序"就不能只靠升序数组 —— 这是**为满足一个不变量（升序）而丢掉另一条信息（顺序）**的真实代价。
教训：**当不变量要求排序时，如果原始顺序有意义，就必须另找地方存它。**

### 6.4 "知识不足"必须是可核实的判据

否则 D 会无限向 A 提问。三条判据：

1. **`a_no_keyword_hit`**：问题关键词在现有关系的 `quote`/`description` 里命中数为 0；
2. **`b_low_degree_unverified`**：相关概念度数低于阈值，且没有一条 `quote_verified=True` 的关系；
3. **矛盾**：两条关键关系给出**互相矛盾**的 `statement` —— **这其实是最有价值的情况，应记为 `priority="high"`**。

**提问前必须查重**：同一问题已有未完成请求时不得重复提交（否则刷爆 A 的队列）。

实测判据输出（探针）：
```
assess → {"insufficient": true,
          "criteria": [{"id": "a_no_keyword_hit", "ok": true, "priority": "high",
                        "detail": "关键词 31 个，在 0 条相关关系的 quote/description 中命中数为 0…"}]}
```

### 6.5 缺口提问闭环（实测）

独立探针 `tools/probe_gap_submission.py` 构造两个**互不相关**的概念使判据必然触发，
在 `agent_a=None`（**不接线 A**）下实测：

```
[1] ingest 产出问题：['0000']
[2] 0000 assess → insufficient=true, criteria=['a_no_keyword_hit']
[3] 0000 submit_gaps → ['r-0001']
[4] search_requests 行数 = 1
      r-0001 by=agent-D mode=topical done=False topic='孤立甲 孤立乙'
[5] 0000 status=needs_evidence waiting=['r-0001']
结论：✅ D 会在证据不足时提交请求（本地写表，不需要 A 在线）
```

**"提交请求只是一次本地写表，不需要 A 在线"** —— 这一点很重要：
如果把"提问"实现成"调用 A"，那么 A 不在线时 D 就无法记录自己的知识缺口，循环接不上。

### 6.6 报告结构与置信度

每个问题一节：
`问题 → 为什么值得研究（引用 C 的证据）→ 现有证据（L1/L2 逐字引用 + 代号链）→
缺口与已提交的查询 → 初步分析 → 结论与置信度（high/medium/low）→ 后续建议`。

**置信度不许拔高**：证据不足时必须写"低"。实测中证据充分的问题给出 `高（high）`，
而问题台账里 `open` 状态的曾给出 `低`。

### 8.1 环境勘察结论（实测）

### 8.2 `ocr.run` 的行为

`backend=auto` 时**如实 fail**，`meta.kind=no_backend`，并在错误信息里给出每个后端的探测结论与**具体修复建议**：

> 本次**没有**产出任何 OCR 文本 —— "没做"就是"没做"，**不会假装成功返回空文本**。

**这条与 `DESIGN.md` §6.3"无文本层返回 `None` 而不是 `False`"同源：**
**"没做"和"做了但没结果"是两件事。** 前者要装后端，后者要换页/换图。

### 8.3 桩后端与栅格化自检

- 用**桩后端**把三条语义钉死：① 桩返回空串 → `ok=True` 但 `empty=True` 且 **warning 明确写"做了但没结果"**；
  ② `max_pages=1` → `truncated=2` 且 warning 说明截断；③ 越界页号 → `ok=False` 并报文档总页数。
- **栅格化用 `fitz`**（不用外部 `pdftoppm`）：实测 `sample.pdf` 第 1 页 @150dpi → PIL RGB **1240×1755**，
  灰度极值 `(0, 255)` —— 含 0 与 255 说明**文字像素被真实渲染出来了**。
  → 这证明**除 OCR 后端外，整条链路是通的**。

## 10. 开发过程中发现并修复的缺陷

### 10.1 我（父智能体）在工具层基座里引入的 3 个

| # | 缺陷 | 影响 | 修法 |
|---|---|---|---|
| 1 | `validate_params` 把 `isinstance(params, Mapping)` 检查放在**函数开头**，而子 schema 也走同一函数 | **任何非对象参数**（如一个字符串）都被误判成"必须是对象" —— 所有带字符串参数的工具全废 | 先看 schema 声明的 `type` 再决定怎么校验；`type is None` 时不约束 |
| 2 | `ToolRegistry.call` 未捕获"未知工具" | `self.get(name)` 抛 `ToolError`，**打断智能体循环** | 把查工具也放进 `try`，返回 `ok=False, kind="unknown_tool"` |
| 3 | `verify.py` 的 ID 计数器反查**写死了表名映射** | 新增第 5、6 张表后直接 `KeyError` | 从 `S.ID_COUNTERS` 反查 `S.TABLES`，不写死 |

### 10.2 子智能体发现、我确认并修复的 1 个（**静默数据丢失路径**）

**#4 `Tx.mark_dirty` 文档提到但方法不存在。**

`table_tools` 的作者发现 `Tx` 的 docstring 提到 `mark_dirty(t)`，但类里**没有这个方法** ——
删除只能改 `tx.rows()` 列表并直接置私有属性 `tx._dirty`。

我补上公开方法后**实测确认了这个危险的语义**：

```
初始:       ['甲', '乙']
A 不标脏 →  ['甲', '乙']        ← 就地改列表，改动凭空消失，不报任何错
B 标脏   →  ['标了脏', '乙']     ← 正确落盘
```

根因：`tx.rows(t)` 返回**可变列表**，就地改动**不经过 `upsert`**，于是没有任何东西把表标脏 → 提交时被跳过。
加 4 条回归测试，**其中一条刻意断言"不标脏就会丢"这个危险行为** ——
若将来有人改成自动标脏，它会失败并提醒同步改语义。

### 10.3 我在 CLI 里引入的 2 个（端到端跑才暴露）

| # | 缺陷 | 修法 |
|---|---|---|
| 5 | `cmd_analyze` 误用 `row['kind']`，而 `persist()` 只返回**登记行**（`report_id` / `markdown_path` / `abs_path`），不含 `kind` | 改用 `rep.kind` |
| 6 | `cmd_pipeline` 传 `with_search=` 而 `run_pipeline` 用 `agent_a=None` 表达"不检索" | 按真实签名构造 A/B |

### 10.4 ⭐ 集成层缺陷（**只有端到端跑才暴露**）

**#7 D 的 L1/L2 溯源恒为空，并把"没接工具"伪装成"查询无结果"。**

D 的报告里每个问题都写：

> **未能取到任何关系表述（L1/L2 均为空）——这本身就是一个重要事实。**

**但它不是事实，是 D 的接线错了。** 我独立验证：同一份 store、同一个 `build_registry()`，
`trace_tools` 三个工具**全部正常**：

```
trace.relation("0005")  → ok=True  quote='A prime ideal is a proper ideal such that…'
trace.concept("0000")   → ok=True  relations 条数=5
trace.chain([...])      → ok=True  steps 条数=3
```

也就是说：**工具是好的，D 没把它们接上**（`tools=None` 时走了"无工具"的降级分支并**静默返回空**）。

**危险的形态**：它把"**没接工具**"表达成"**查询无结果**"，而后者在 D 的判据里又是"知识不足"的信号之一 ——
于是这个错误会**伪装成一个合理的结论**（"查过了，没有"），而不是报错。

**修法**：D 接上 registry；报告改为两段式（L1 按跳序 / L2 上下文限量）。

**#8 同一份 C 报告的不同实例产出重复问题。**

`research_questions` 里 4 条问题，实际只有 **2 个**不同的研究点：
```
0000 [open/high] origin='C:paths:0000:0009->0010->0005'  rels=['0005','0009','0010']
0002 [open/high] origin='C:paths:0001:0009->0010->0005'  rels=['0005','0009','0010']   ← 与 0000 同一条链
```
成因：`analysis_reports` 有 2 份 `kind=paths` 的报告，D 把两份都 ingest 了。

**为什么是缺陷**：用户要 D 评估的是"**问题**"，不是"报告条目"。
重复问题的后果是 ① 做重复研究；② 若提交缺口请求，会向 A 问同一件事两次，白烧预算。
（这与 `research.submit_gap` 里已有的查重要求是同一条原则 —— 那边做了，ingest 这边漏了。）

**修法**：按内容键 `(kind, 排序后的 related_relation_ids)` 去重；已存在时不新建行，
把新 `origin` 追加留痕（"多份报告指向同一研究点"本身是该点**更值得做**的信号，不该丢）。
实测问题数 **4 → 2**。

**#9 ⭐ 状态机缺一条边 —— 问题永远不被研究。**

`pipeline --no-search` 的摘要长期是 `questions: {open: 4}`、`requests_total: 0`。
我先给了两个假设：**(a) 设计如此**（不接线 A 就跳过评估）或 **(b) 是 bug**。

**实测判定为 (b)，但根因不是我以为的那个**：不是"因为没接线 A 所以跳过"，而是
**状态机缺一条边** —— 「证据足够」这一支原来**什么都不做**，于是问题永远停在 `open`；
而 `research()` **只处理 `researching`** → **永远不被研究，报告里也没有证据**。

**修法**：新增 `consider()` 完成路由（足够 → `researching`；不足 → 提问）。
并确认 `assess` 与"提交请求"**都只是本地读表 + 写一行，不需要 A 在线**。

### 10.5 C 的自检失败 3 条（其中 2 条改实现，1 条改夹具）

C 的自检从 **27/30 → 31/31**。三条失败的处理**各不相同**，这本身说明了"先定性再改"的必要性：

| 失败断言 | 定性 | 处理 |
|---|---|---|
| `正文只含 high 路径` | **我的断言写错了**（详见 §11） | 换成**段落级解析**（正文 high 4 / 非 high 0；附录 medium 1；统计 low 1），测试**更强** |
| `证据不足时 verdict='无'` | **设计缺陷**：`引文全部失败` 被当成**扣分项**而非**否决项** | 引入 veto 两档；改后该场景 `verdict=无, candidate_gaps=0, vetoed=3` |
| `2 跳与 3 跳都有` | **夹具问题，不是搜索 bug** | 打印**未筛选前**的路径集合 `{'2':5,'3':5,'4':2}` 作为证据，证明 3 跳确实被找到了、只是被低重合度筛选**正确丢弃**；夹具补一条真正低重合的 3 跳链 |

### 10.6 `verify --deep` 的分级修正（我修的）

端到端校验 `pipelinedemo` 时报 **1 个 error** —— 但**那不是 bug，是校验器正确工作**：
它真的**重新打开了文献**核对引文，抓住了我**刻意伪造**的那条假引文（`relations/0007`）。

真正的问题是**分级语义**：「表里已经写了 `quote_verified=False`」是**已知并被记录**的缺陷，
重算只是**确认**它，不该是 error —— **否则红灯会被训练成背景噪音**。

| 情形 | 分级 | 实测 |
|---|---|---|
| 表里记 `quote_verified=False`，重算也找不到 | **warning** `quote_known_unverifiable` | verify 通过（0 错误 1 警告） |
| 表里**谎报** `quote_verified=True`，实际找不到 | **error** `quote_not_found`（+ warning `quote_state_changed`） | 仍报错 |

加了 2 条测试，**两个方向都断言** —— 只测一个方向容易"修过头"。

### 10.6 ⭐ 角色名不一致 —— D 拿不到自己的工具（测试套件抓到的真 bug）

新增的测试套件报：

> `for_role('D') 拿不到这些 D 专属工具：['research.list_gaps','research.submit_gap','research.write_note']`

**根因**：`tools/research_tools.py` 把角色写成了 **`roles=("agent-D",)`**，
而 `tools/__init__.py` 的 `ROLES = ("A","B","C","D")` 与 CLI 的 `tools --role D` 都按 **`"D"`** 过滤。
**全项目只有这一个模块用了 `"agent-D"` 这个名字** —— 于是 `build_for_role('D')` 造出来的注册表里
**D 没有自己的研究工具**。

**这个 bug 之前一直没暴露**，因为我的探针把**全量注册表**（不是按角色过滤的）传给了 `AgentD`，
所以 `research.*` 恰好可达。**换成按角色装配就会静默少 5 个工具。**

**修法**：5 处 `roles=("agent-D",)` → `roles=("D",)`。实测 **D 的工具数 23 → 28**，
`research.*` 五个工具回到 D 名下。

**教训**：角色名是**跨模块的字符串约定**，和 `download.status` 的受控词表是同一类问题（§10.7 第 5 条）。
凡是"靠字符串常量跨模块对齐"的地方，都应该有**一处统一定义 + 一处校验**，而不是各写各的。

### 10.7 这些缺陷说明了什么

1. **静默失败比崩溃更危险。** #4（就地改动的丢失）与 #7（把"没接工具"说成"没查到"）
   **都不会报任何错**。而 #7 更糟：它伪装成一个**合理的业务结论**。
   → 对策：**任何"空结果"都必须能区分"没做"与"做了但没结果"**。

2. **"没做"与"做了但没结果"必须可区分 —— 这是本项目反复出现的同一条原则。**
   它在四个地方以不同面貌出现：引文校验的**三态**（True/False/None）、
   OCR 的**无后端 vs 空文本**、D 的**没接工具 vs 查询无结果**、C 的**预算截断 vs 搜完了**。
   每一次都出现了同一个错误倾向：**把"没做"折叠成"没结果"**。

3. **单元测试抓不到集成缺陷。** #7、#8、#9 三条都只有在**真实端到端运行**时才暴露 ——
   各自的单元测试全是绿的，因为它们测的是"零件对不对"，而问题出在"零件有没有被接上"。

4. **同一个 bug 在三层各有一次表现**：#9 的"状态机缺一条边"如果没有端到端跑，
   会被误判成"(a) 设计如此"而永久留存。**必须实测，不能靠读代码推断设计意图。**

5. **跨模块的字符串约定必须集中定义。** §10.6 的 `"agent-D"` vs `"D"` 与 `download.status` 的受控词表
   是**同一类**问题：靠字符串常量对齐的地方，一旦有人拼法不同就**静默失配**。
   `download.status` 那次我们靠 schema 校验挡住了；角色名这次**没有校验**，于是溜到了测试才被抓到。
   → **建议：给角色名也加一处枚举 + 一处断言**（例如装配时断言"所有 spec 的 roles 都是 ROLES 的子集"）。

## 11. 一次审查者误判及其方法论价值

### 11.1 发生了什么

我看到 C 的自检失败 `正文只含 high 路径`，结合上一行 `[PASS] low 路径没有进正文`，
**断言**："`low` 排除了但 **`medium` 进了正文**，违反需求'写进报告的都是信息量高的'"，
并要求按实现缺陷修改。

### 11.2 判断是错的

C 的实现者**用证据反驳**：正文渲染的是 `群(0000) → 阿贝尔群(0001)` 这种**带名字**的形式，
而失败断言查的是紧凑串 `"0000→0001→0002"` —— 那个串**只出现在统计段**，
所以断言**恒假**，与 medium 毫无关系。

我之所以会误判，是因为**上一条 low 断言同样很弱**（只做 `count >= 1`），
于是"一个 pass 一个 fail"的组合被我看成了"分级边界错了"。

### 11.3 处理方式才是重点

实现者**没有借机放宽断言**，而是：
- 把附录标题改成明确写"**未达正文标准、不作为证据**"；
- 把断言换成**段落级解析**（正文 high 4 / 非 high 0；附录 medium 1；统计 low 1）—— **测试反而更强**。

### 11.4 方法论

> **审查者（我）的判断也需要被证据检验；实现者有条件也有责任用证据反驳。**
>
> 具体到"弱断言"：一个只做 `count >= 1` 的断言，**既能因正确原因通过、也能因错误原因通过** ——
> 它在"给结论"上是有害的，因为它会让**相邻的、真正有判别力的断言**看起来像"边界错了"。
> **断言必须落在真正有区分度的地方**（这里是"哪一段出现了什么"，而不是"某个字符串是否出现过"）。

这条已固化进 `DESIGN-TOOLS.md` 与本节，作为后续同类工作的检查项。

## 结语

本轮把用户要求的"**用程序分析**"落到了实处：C 的四类分析**没有一处依赖 LLM 判断**，
所有需要判断的地方都是确定性评分 + **可逐项打印的中间值**；D 的循环靠**等待集**而不是猜测来接续。

但比功能清单更重要的是本轮暴露的一组**同源问题**：
**"没做"被反复折叠成"没结果"** —— 引文校验、OCR、D 的溯源、C 的预算截断，四处都出现过这个倾向。
它危险，因为**折叠之后不报错，而且看起来像结论**。

最尖锐的一个例子是 D 的溯源：它把"**没接工具**"写成了"**未能取到任何关系表述——这本身就是一个重要事实**"。
一个接线错误因此伪装成了一条研究发现 —— **而它读起来完全合理**。
这正是我们在引文校验里反复防范的那种失败模式，只是换了一层皮。
