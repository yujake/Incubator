# draft/41 系统调查报告（总）：这台机器现在是怎么工作的、哪里可能有逻辑 bug

> 调查方式：6 个只读子代理分层调查（编排 / 权限声明审计 / 数据与证据链 / 角色 A–D / 角色 E–F /
> 角色 G–H 与收工门），各自把报告写到 `draft/41-调查报告-<层>.md`；本文件是**汇总索引 + 跨层复核**。
> 本报告只描述**是什么**与**哪里可能有 bug**，不写修改方案（用户 2026-10-06 口径）。
> 复核标记：`[我复跑]` = 本文件作者独立重跑了子代理的探针或命令并核对过输出；`[子代理]` = 只有子代理的证据
> （报告里给了 `file:line` 与探针路径，尚未由我复跑）。

一次运行的数据流（各层的详细判据见各自报告）：

```
cli run-agent M ──> host.wired_llm_conductor（装配各角色的工具面与"缝"）
   M 循环（agent_loop）：每步一个 JSON → tool / summon / summon_many / message / note / ask_user / final
        │
        ├─ summon：conductor.summon → 任务行（tasks：pending→running→done/failed/refused）
        │      └─ 角色动作：确定性实现（A/B/C/D 的大部分）或"缝"上的 LLM 推理（E/F 的形式化与攻坚）
        │             └─ 写台账（data/*.json）+ 产物（out/tasks/<id>.json、out/experiments/*.log…）
        │             └─ out/tasks 摘要是 repr 前 2000 字节（见 §3-C1）
        ├─ 收尾：G 建稿/建论文包 → H 审校（机械 + 语义判据）→ 签名台账（DOC-SIGNATURES.jsonl）
        └─ closing 七格（anchor/contradictions/load_bearing/report_shape/user_pending/substance/acceptance）
               └─ acceptance 读 out/paper/ACCEPTANCE-CHECKS.json（M 手写的受控档行，逐档现算）
```
