## 1. 机制：一次 `run-agent M` 从头到尾发生了什么

### 1.1 启动

1. `cli.cmd_run_agent`（`cli.py:1457`）解析 `--drive`（`_parse_drive`，`cli.py:1390`；`--subagents`
   时把 A–H 全部动作塞进 LLM 接线表，`cli.py:1476-1495`），建 `Store(root)` 并 `init()`（`cli.py:1496-1498`）。
2. **会话身份在这一步定格**：`if not args.sid: args.sid = SS.session_id()`（`cli.py:1513-1514`，
   `sessions.session_id()` = 环境变量 `AGENTFLOW_SESSION`，否则当天日期，`sessions.py:53-58`）。
   之后所有装配都吃这一个 `sid`。
3. 造缝：`_agent_seam_factory`（`cli.py:1373`）→ `LlmSeam.for_role(..., sid=args.sid, meter=TokenMeter(store, budget_usd=...))`；
   没有 key ⇒ `seam.wired=False` ⇒ 直接返回退出码 2（`cli.py:1521-1524`）。
4. `H.wired_llm_conductor`（`host.py:413`）装配：
   - `eff_sid = sid or SS.session_id()`（`host.py:458`）；
   - `build_role_registry`（`host.py:316`）为 LocalBackend 造 `role -> ("factory", fn)`（A 没
     providers 就不进表，`host.py:334-336`）；
   - `conductor_for(store, policy=..., role_registry=..., backend="local")`（`host.py:511`）——
     按 `store.root` 缓存，**忽略后传参数**（`tools/conductor_tools.py:60-67`）；
   - 内层 `LocalBackend` 必须带 store（`host.py:532-535`）；
   - `LlmBackend(inner=LocalBackend, loops=table, session_root=root, sid=eff_sid, store=store,
     stop_file=...)`（`host.py:543-549`），然后 `if not isinstance(conductor.backend, LlmBackend):
     conductor.backend = backend`（`host.py:550-553`）；
   - `build_registry` 造工具面，回填 `backend.registry/conductor/store`（`host.py:554-559`）。
5. `AL.run_role(role="M", task, sid=args.sid, stop_file=... 或 "" , resume=...)`（`cli.py:1604-1614`）：
   M 走 `loop.run(task, summoned_by="M", my_task_id="", depth=1)`（`agent_loop.py:2868-2931`）——
   **M 自己不写 `tasks` 行**（`NON_SUMMONABLE`，`conductor.py:855-862`），这是后面很多判据失效的根源。
6. `_opening_transcript`（`agent_loop.py:599`）拼开头（任务 / 收件箱 / 处境），`agent_run_start`
   落会话（`agent_loop.py:1463-1476`）。

### 1.2 每一步（`AgentLoop.run`，`agent_loop.py:1401-1848`）

每步顺序（行号即实现顺序）：

1. `_user_stop_reason`（`:1509`）→ 命中就 `break`（人叫停，如实收尾而不是杀进程）；seam 预算检查（`:1524`）；
2. 读集体插话 `read_interjections`（`:1533`），拼进简报并 `mark_interjections_seen`（`:1539`）；
3. `seam.ask_step(prompt, system, task_id=my_task_id, max_tokens=8192, face=...)`（`:1547`）
   —— `face` 是原生工具函数面（`LL.build_tool_face`，`:1484`），拿不到就回落文本 JSON 协议并留 note；
4. `data is None`（`:1552`）：`judge_bad_args` ⇒ `bad_args`，「形状认不出/坏 JSON」⇒ `bad_json`；
   连击超限 ⇒ `bad_json_limit` / `bad_args_limit`（`:1588`、`:1595`）；整条原文落
   `out/invalid/<sid>-step<N>.txt`（`_dump_invalid_reply`，`:580`）；
5. `_shape_of`（`:918`）解码成八种形状之一（别名 `{"name","args"}` / `{"role","action"}` /
   `{"targets"}`，`_unwrap_alias`，`:949`）；
6. `final`：**强制 notify 表**（除 M 外，`_notify_gate`，`:2037`；打回重填、不代填，超
   `max_notify_rejections=3` ⇒ `stop_reason="no_notify"`，`:1660-1666`）；M 的 `summon`/
   `summon_many` 走 `_dispatch_notify`（`:1968`，模型填了用手稿、没填据派活派生，`:2005`）；
7. `_execute`（`:2100`）按形状分派：`_do_tool` / `_do_summon` / `_do_summon_many` /
   `_do_message` / `_do_handoff` / `_do_ask_user` / `_do_note`；
8. `_hear()`（`:1714`）把这一步之后新到的留言并进结果，并写 `agent_inbox` 投递登记；
9. 活性读数（`:1723-1752`）：`_call_key` 同调用连击 + `_call_reading` 同读数 ⇒ `dead`；
   `_stall_key`（主题 + 读数类）⇒ `stalled`；到 `dead_loop_nudge=3` 提醒、到
   `max_dead_loop=6` 以 `no_progress_limit` 收工（`:1777`）；
10. 参数类拒绝时把声明参数表回给模型（`:1759`，`_param_table`，`:2065`）；落 `agent_step`
    事件（`:1765`）+ `_step_line` 拼进 transcript（`:1769`）；
11. `ask_user` 返回 `pending`/`cancelled` ⇒ `waiting_for_user` / `ask_cancelled` 收工（`:1798-1815`）；
    循环走完 ⇒ `max_steps`（`:1816-1818`）。收尾写 `agent_run_end`（`:1830-1847`）并注销 pid（`:1824-1829`）。

### 1.4 子角色怎么被「当动作跑」

- `LocalBackend.resolve`（`conductor.py:178-222`）按 `(角色, 实例标签)` 惰性实例化注册项；
  `("class", cls)` 明确拒绝；工厂按签名决定给不给 `store=`/`instance=`。
  `LocalBackend.call`（`:227-288`）按 `ActionSpec.handler_name` 取方法，参数名对不上就
  `ParamError`（不静默丢弃），调用期间把 `CancelToken` 放进 `ContextVar`（`CX._CURRENT_TOKEN`）。
- `LlmBackend.call`（`agent_loop.py:2542-2568`）：`(角色, 动作)` 在 `loops` 里 ⇒ 造 `AgentLoop`
  跑一轮模型循环，产出写 `runs/<角色>-<时间戳>-<序号>.json`，返回 `llm_run_path`；不在表里 ⇒
  原样转交 `inner`（确定性 Python 实现）。`LlmBackend._running_row`（`:2589-2629`）优先按
  `task_id` 精确取行（并发多实例唯一可靠），取不到就如实报"未拿到台账号"，
  **不从 `params` 里猜**（`_summoned_by`/`_depth` 全仓无人生产）。

### 1.5 并发与波次

`Conductor.run_plan`（`:1415`）→ `scheduler.run_waves`（`scheduler.py:208`）：按
`policy.waves_of(calls, limit=max_concurrency)` 分波（写集互斥的贪心装箱，`policy.py:422`），
波内 `ThreadPoolExecutor`、波间串行，结果按输入下标回填（长度恒等于输入）。
两道闸：划分时的单波容量 + `threading.Semaphore(max_concurrency)`（`scheduler.py:232`）。
`ConcurrencyProbe`（`scheduler.py:144`）记 `peak` 与每窗口区间，是"真并发"的判据；
`Conductor.peak_running`（`conductor.py:972`）会低估（落 running 行本身要花 I/O 时间）。
`summon_many` 的读数 `waves` / `concurrent_peak` 由调用方在跑完之后**重新算一遍**
（`agent_loop.py:2160`、`tools/conductor_tools.py:351` 两处各算一次）。

### 1.6 锁与租约

- `store.tx(*tables)`（`store.py:890-989`）按 `LOCK_ORDER`（`store.py:66-90`）固定顺序取
  表文件锁，并把 `counters` 并入；事务体全程持有表锁，写者锁只在提交段（`:950`）拿；
  提交顺序是「先事件 + commit 标记，再逐张快照原子落盘」（`:966-979`）。
- `Conductor` 自己只用一把进程内 `_id_lock`（`:554`）保证「取号 + 建行」原子；
  并发度约束 `_running` 是**进程内内存集合**（`:424`、`:899-901`），没有 workspace 级租约。
- 租约（`store.lease_expired`/`make_lease`，`store.py:118-127`）只长在 `literature` 行的
  `claimed_by/lease_until` 上，由 A/B 的领取路径使用（`agent_a/core.py:178-196`、
  `agent_b/core.py:97-112`）；编排层不参与。
- `finish()` 在**事务体内**调用 `_write_task_digest`（`:1345`）做磁盘写（`out/tasks/*.json`），
  即持表锁做与台账无关的 I/O。

### 1.7 预算与配额（`policy.py`）

- 四类结构上限必须为正数：`max_depth=3` / `max_fanout=5` / `max_concurrency=4` /
  `max_tasks_per_run=200`（`policy.py:41-48`，`validate` 拒 0/None）。
- 资源上限：`wall_clock_sec=900`（CLI 缺省 3600，`cli.py:1549`）、`token_budget=None`、
  `usd_budget=None`（`None` = 不限，不折叠成 0）。
- 判定顺序（`policy.check`，`:233-355`）：角色/动作 → 不可召唤/边 → 深度 → 循环 →
  扇出 → 并发 → 总量 → 预算 → 墙钟。拒绝一律 `status=done, outcome=refused` 并落台账。
- 预算实际有四个检查点，输入各不相同：
  1. `AgentLoop.run` 每步开头：`seam.spend.usd` vs `seam.usd_budget`（`agent_loop.py:1524`）；
  2. `LlmSeam.ask`：同一对值，发起请求前拒（`llmseam.py:209-215`）；
  3. `Conductor._meter_guard`（`:630-662`）→ `TokenMeter.guard`（`tokenmeter.py:448`），
     读 `usage_ledger` 汇总 vs `policy.token_budget/usd_budget`；
  4. `autonomy._stop_before_round`：`baseline + shared.spend.usd` vs `usd_budget`（`autonomy.py:266`）。
- 步数只有 `AgentLoop.max_steps`（`cli.py:2331` 缺省 30）；墙钟只有 `Conductor.deadline`
  （`:431-432`、`:452`），且只在 `summon` 时判（到点后 `_signal_stop("deadline")`）。

### 1.8 停止 / 取消

- 停机开关：`stopctl` 写 `<工作区>/.agentflow-stop`（`stopctl.py:65-102`），一次性信号——
  被消费时记 `runs/stop-history.jsonl` 再撤走（`:156-194`）。三个观察点：
  `AgentLoop._user_stop_reason`（步与步之间，`agent_loop.py:1851-1930`）、
  `autonomy._stop_before_round`（轮与轮之间）、`conductor.stop`/`agentflow stop`（写入方）。
- M 的 `conductor.stop` 工具（`tools/conductor_tools.py:461-531`）：落开关 →（默认）发一条
  集体插话 `subject="叫停"` → `Conductor.cancel` →（非 force）有界 drain → `dispose()`
  →（force）`stopctl.kill_registered(exclude_pid=self)` 连子孙杀 → 写 `resume-brief.json`。
- `Conductor.cancel`（`:1445`）/`_signal_stop`（`:1429`）共享一个 `CancelToken`；
  `dispose`（`:1468-1502`）把仍在 `pending/running` 的行合成 `cancelled` + "结果未知"。
- 进程树：`AgentLoop.run` 开头 `stopctl.register_pid`（`runs/<角色>-<sid>.pid`）、收尾
  `unregister_pid`；强杀按这份登记 `jobobject` 优先、`taskkill /T /F` 兜底（`stopctl.py:392-446`）。
  `CancelToken.cancel` 主动杀本 token 名下子进程（`cancellation.py:233-240`）；
  `run_cancellable` 分段等待并每段查一次取消（`cancellation.py:483-557`）。
- 真机配平：`agent_run_start` 76 = 全新 72 + 续跑 1 + 被拒的续跑 3（`resume_refused`，无 end
  是刻意的），`agent_run_end` 73 = 全新 72 + 续跑 1 ⇒ 每个真实运行恰好一个 end；
  台账 2256 行全部是终态（`done` 2176 / `failed` 80），没有 `status=running` 的僵尸行。

### 1.9 relay「请代唤」

- 触发：`_needs_relay`（`agent_loop.py:2280`）= `RELAY_REFUSALS{forbidden_edge, depth_exceeded}`
  或（`invalid_params` 且目标不在 `partners_out(self.role)` 里）。受理形态：`_request_relay`

  `started_at >= 申请 ts` 的任务行"；任一会话文件有坏行则整表报"没查成"。

### 1.10 `ask_user` 与 `--resume`

- 只有 M 能当面问人（`_do_ask_user`，`agent_loop.py:2447-2461`；非 M 返回 `not_conductor`）。
- `userio.ask_user` 先落 `user_question` 事件再轮询磁盘上的 `user_answer`（`userio.py:493-529`），
  等待期间不产生 token；`timeout_sec=None` 一直等，`0` 立刻返回 `pending`。
- `pending` ⇒ 循环 `stop_reason="waiting_for_user"` + `waiting_for=qid`，退出码 3（`cli.py:1411`）。
- `--resume`（`run_role`，`agent_loop.py:2870-2929`）四态：无检查点 `no_checkpoint` /
  指纹不符 `checkpoint_mismatch` / 上趟已收工 `already_finished` / 还在等 `waiting_for_user`；
  然后 `resume_transcript`（`:2721`）从会话事件重建简报（与本趟逐字同源的拼法），
  从 `step0` 接着跑。被拒的续跑也落 `agent_run_start`（`resume_refused` +
  `resume_attempted_from`，`_note_resume_refusal`，`:2809`）。
- 步检查点：`runs/agent-<角色>-<会话号>.json`（`run_checkpoint_path`，`:2652`），
  `completed = run.resumed_from + len(run.steps)`（`:2932`）。

### 1.11 坏 JSON 与停滞检测

- 三类分开计数：`bad_json`（形状认不出）、`bad_args`（形状对了值写错 / 工具参数不合法）、
  `notify` 打回（也算进 `bad_args`，`_notify_bounce`，`:1944`）。**判停的是连击**
  （`bad_json_streak > max_bad_json=2`、`bad_args_streak > max_bad_args=3`），一有合法形状就清零
  （`:1642-1643`）。坏回复两类措辞分开：`_BROKEN_STRING_MARKERS` 命中（长文本未转义）⇒
  教它"落盘再引用"，否则重述协议 + 骨架（`_bad_json_line`，`:555`）；整条原文落
  `out/invalid/`（`:580`）。
- 停滞检测三档：`same_call`（同形状同参数）、`dead`（再加同读数，判停）、`stalled`
  （`_stall_key` = 目标 + 主题 + 读数类，只提醒不判停）。`_summon_reading_class`（`:344`）
  只取 `reason/status/outcome/verified` 这个"结论类"，不看数值。

### 1.12 四处落点各自写了什么

| 落点 | 写者 | 内容 |
|---|---|---|
| `data/tasks.json` | `_write_new_row` / `finish` / `_set_usage` | 每次召唤一行：身份（role/action/called_by/parent/depth/input_key/instance）、三态（status/outcome/refusal_reason/detail/error）、时间、`tokens/usd`、`artifacts`、`inputs`（含 `tokenmeter:settled` 标记） |
| `data/events.jsonl` | `store.tx` 提交 | `upsert`/`delete` + `commit` 标记（可 rebuild 的唯一输入） |
| `out/tasks/<task_id>.json` | `finish`→`_write_task_digest` | 返回值摘要：键集、规格化 JSON 的 sha256、字节数、前 2KB 预览 |
| `manuscripts/handoffs.jsonl` | `_do_handoff`（模型自写）/ `_derived_dispatch_notify`（框架派生） | 追加式交接账本：id/sender/to/summary/body/refs/note/task_id/sid |
| `sessions/<sid>.jsonl` | `sessions.append` | 叙事面：`llm_call`、`agent_step`、`agent_run_start/end`、`agent_message/inbox`、`user_question/answer`、`autonomy_*`、`task_end`、`agent_interjection*` |
| `ARTIFACTS.jsonl` / `runs/*.json` | `artifacts.record` / `save_run_checkpoint`、`autonomy.save_checkpoint`、`LlmBackend._write_run_artifact` | 产物归属（path/producer/kind/task_id）；步检查点 / 轮检查点 / 一整套循环记录 |

## 3. 可疑的逻辑 bug

### B1（拒绝行不进会话叙事）
- 【现象】网关层拒绝（`_refuse`）写了 `tasks` 行，但**不写** `task_end` 会话事件，

  在 `:856-942` 提前返回，永不到 `:1032` 的 `_charge_and_settle`）vs
  `conductor.py:1363-1376`（`task_end` 只在 `finish` 里写）。真机复算：p6d 157 行任务中
  8 行既无 `task_end` 也无 settled 标记、且全是 `outcome=refused, refusal_reason=invalid_params`
  （p6i 5 行、p6q 5 行同形）。全库（57 个工作区、2256 行）无 `task_end` 共 342 行，

  相同，而会话文件没一起复制），属拷贝产物、不算运行期缺陷。
- 【影响面】"框架拦住了它"这类行恰恰是事后最需要审计的（`conductor.py:22-23` 的自述），
  但任何"从会话叙事重建 M 的决策序列"的读者读不到它们：`task_end` 事件 1914 条与终态任务
  2256 行相差 342（其中 283 行由本判据产生，59 行是拷贝工作区）。
- 【已复现】是（命令：`python -B -c` 读 `data/tasks.json` 与 `sessions/*.jsonl` 求 `task_end` 差集；283 行跨 50+ 工作区，p6d/p6i/p6q 逐行核对为 8/5/5）。
