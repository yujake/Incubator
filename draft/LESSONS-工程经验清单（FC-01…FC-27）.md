## 经验 1：多智能体不是默认答案，它是一件高成本的特种工具

| 项 | 内容 |
|---|---|
| **经验** | 在"任务单一、上下文装得下、工具少"的场景里，**单智能体 + 工具循环**是正解；多智能体只在"广度优先检索、多线索并行、信息量超单窗口"时有强证据。 |
| **来源** | `02-多智能体协作协调方法综述.md` §0「什么时候是负优化？」（L31–58）、§5「成本与收益：token / 延迟 / 成功率三角」（L415–457）、§6「工程落地选型建议（if-then 决策表）」（L460–503）、§2.8「预算与轮次控制」（L325–331） |
| **证据/案例** | ① Anthropic 原文：`"agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats"` —— 智能体 ≈ **4×**、多智能体 ≈ **15×**（`02-...md` §5 成本端的硬数据）；② MAST 实测 7 个主流开源 MAS 框架，**失败率 41%–86.7%**，开篇即写 `"their performance gains on popular benchmarks are often minimal"`（`02-...md` §4 总纲）；③ 辩论类方法"常常打不过 CoT / Self-Consistency 却花更多算力"，原文 `"do not reliably outperform…such as self-consistency and ensembling"`（`02-...md` §1.3）；④ 决策表首行原文："任务单一、上下文装得下、工具少 → **单智能体 + 工具循环。别上多智能体。**"；§6 第一步伪代码："IF 单个强模型 + 工具循环能达到目标质量的 **80%** 以上 THEN 停"；§6 第四步调优优先级把"**最后才考虑「再加一个智能体」**"；⑤ **厂商自己对编码任务的明确否决**：`"most coding tasks involve fewer truly parallelizable tasks than research"` → 报告判语"**大部分写代码任务不该用多智能体——这是厂商自己说的**"（`02-...md` §0）；⑥ 非单调证据：投票类方法收益随调用次数**非单调**——简单问题上随调用数上升，**难题上反而下降**（`02-...md` §4.2）；⑦ "模型越强，相对收益越小"：o3 / Gemini-2.5-Pro 已把差距抹平很多，MAS↔SAS 级联再提 **1.1%–12%**、部署成本最多降 **20%**（`02-...md` §0）；⑧ 本项目原型进一步佐证：A/B/C/D 四个智能体之间的"协作"实际上**全部是共享存储 + 轮询 + 租约**，没有一条消息传递，收益来自**结构（表 + 不变量 + 质量门）**而不是智能体数量（`10-...md` §4、`11-...md` §7）。 |
| **对下一阶段的直接后果** | **该做**：新框架必须先给出"单智能体基线"，并给出**升格为多智能体的量化触发条件**（例如：单窗口装不下 + 子任务互不依赖 + 每子任务有独立可验证产出，三条同时成立）。<br>**不该做**：不要因为"我们是数学研究框架"就默认上多智能体；不要在没有基线对照实验的情况下声称多智能体更好；**特别注意 `02-...md` §0 对编码任务的否决**——本项目是"文献/数学研究"型任务，属于检索型，比编码任务更适合并行，但仍需按 §6 第二步（任务结构）选范式。<br>**必须落成数字**：框架的配置里必须有 `token 放大倍数预算`，默认按 `02-...md` §5 的 **4×（单智能体带工具）/ 15×（多智能体）** 做上限估算；且**不要假设框架会给你 token 预算**——`04-...md` §D3 ⑧ 明确警告："⚠ 注意 DSH 的 Ralph 目前**只有轮次上限**，token 预算是 deferred —— 别假设框架一定给你"。 |

## 经验 2：多智能体的失败主因是"系统设计"，不是"模型不够聪明"

| 项 | 内容 |
|---|---|
| **经验** | 多智能体失败可以归到固定的三类十四种；**改结构（谁有最终决定权、谁验收、什么时候停）比换模型便宜得多**。 |
| **来源** | `02-...md` §4「失败模式与避坑清单（基于 MAST 等实证）」§4.1 三类失败及其对应失败模式；§4.3 错误级联 |
| **证据/案例** | MAST：**14 个失败模式 / 3 大类**，6 名专家标注 150+ 轨迹、κ=**0.88**，MAST-Data 覆盖 7 框架共 **1642** 条轨迹。三类为 **FC1 System Design Issues / FC2 Inter-Agent Misalignment / FC3 Task Verification**（`02-...md` §4.1）。典型模式：**FM-1.1 Disobey task specification**、**FM-1.2 Disobey role specification**、**FM-1.3 Step repetition**、**FM-1.4 Loss of conversation history**、**FM-1.5 Unaware of stopping conditions**、**FM-2.1 Conversation reset**、**FM-2.2 Fail to ask for clarification**、**FM-2.6 Reasoning-action mismatch**、**FM-3.1 Premature termination**、**FM-3.2 No or incomplete verification**、**FM-3.3 Incorrect verification**。干预案例：ChatDev 里 CPO 在没得到 CEO 共识时擅自结束对话（FM-1.2），研究者**只改成"CEO 有最终决定权"这一条流程调整**，任务成功率 **+9.4%**（v3 数字；v1 为 +14%，引用时注意版本，见 `02-...md` §4 核查更正框）。 |
| **对下一阶段的直接后果** | **该做**：把 MAST 的 14 条直接做成框架的**评审检查表**；每条失败模式在框架里必须有一个**对应的结构机制**（如 FM-3.2 → 强制 `verify` 阶段；FM-1.5 → 显式 DoD 字段；FM-2.6 → 只信工具的观测结果，不信自然语言声称）。<br>**不该做**：不要用"提示词里写'请注意不要跑题'"来对付 FC1/FC2 类失败——MAST 的结论是需要**结构性重设计**。<br>**引用纪律**：不要把 CrewAI 写进 MAST 的结论（MAST 研究的 7 个框架是 ChatDev、MetaGPT、HyperAgent、AppWorld、AG2（MathChat）、Magentic-One、OpenManus，见 `02-...md` §4 核查更正）。 |

## 经验 3："没做"与"做了但没结果"必须可区分，而且这在本项目里出现了四次

| 项 | 内容 |
|---|---|
| **经验** | 系统里任何"空结果"都必须在**同一处**回答两个问题：**这一步执行了吗？** 如果执行了，**是真的没有，还是没能力做？** 用**三态**而不是布尔。 |
| **来源** | `10-...md` §6.3「无文本层返回 `None` 而不是 `False`：`verified` 是三态」、§6.5「空引文：绝不能因为'没得比'就判通过」；`11-...md` §8.2「`ocr.run` 的行为」、§10.4 缺陷 #7、§10.7 第 2 条、结语 |
| **证据/案例** | 同一原则在本项目**四个不同位置**以不同面貌出现（`11-...md` §10.7 第 2 条原文列举）：<br>① **引文校验三态**：`QuoteCheck(None, reason="no_text_layer")` / `QuoteCheck(None, reason="empty_quote")`，且 `agent_b` 必须用 `is True` / `is False` / `else` 三支计数（`10-...md` §6.3）。<br>② **OCR 无后端 vs 空文本**：`ocr.run(backend="auto")` 在本机"如实 fail，`meta.kind=no_backend`"，原文写着"本次**没有**产出任何 OCR 文本 —— '没做'就是'没做'，**不会假装成功返回空文本**"（`11-...md` §8.2）。<br>③ **D 的没接工具 vs 查询无结果**：D 的报告写"未能取到任何关系表述（L1/L2 均为空）——这本身就是一个重要事实"，而真相是 `tools=None` 走了降级分支**静默返回空**（`11-...md` §10.4 缺陷 #7）。<br>④ **C 的预算截断 vs 搜完了**：`paths` 触及搜索预算要"如实截断并记录（`truncated=True`），不许假装搜完了"（`11-...md` §5.3(2) 第 1 步）。<br>最危险的形态是 ③：**它把接线错误伪装成了一条读起来完全合理的业务结论**（`11-...md` 结语）。 |
| **对下一阶段的直接后果** | **该做**：框架层定义**统一的三态返回类型**（如 `Tri = Verified | Refuted | Unknown(reason)`），并强制所有"空结果"携带机器可判定的 `reason` 枚举；`reason` 必须是**受控词表**而不是自由字符串。<br>**不该做**：禁止任何形态的 `if not result: return []`——空列表必须与"未执行"分离。<br>**可判定判据**：任一"空结果"路径在测试中必须能构造出**两个不同的 `reason`**（"没做"与"做了但没有"），且两者在报告里的计数是**分开的**（对照 `10-...md` §6.3 的三个独立计数字段 `quote_verified` / `quote_unverified` / `quote_unknown`）。 |

## 经验 4：验证门 + 负控，缺一不可；负控要能"故意注入错误并确认被抓到"

| 项 | 内容 |
|---|---|
| **经验** | 一个验证门只有**在它能拒绝**的时候才存在。必须有一个**负控**：注入已知错误，确认验证门**变红**；否则你只有"绿灯"，而绿灯不能证明门在工作。 |
| **来源** | `09-DeepMath团队智能体项目调查报告.md` §3.2「六个机制」（L501–546）、§3.7「确定性验证与 CI 方法学」（L600–676）、§3.7.1「PR#4 引文真实性」、§3.7.2「PR#8 崩溃契约 + 负控 CI」、§3.7.3「三条可抄」；`10-...md` §10.8.3 回归测试、§10.10 结论 ①；`11-...md` §10.6「`verify --deep` 的分级修正」、§11.4 方法论；`08-数学自动化定理证明调查报告.md`（检查器 = 唯一的正确性来源） |

ID 持久可复用""陈旧进程对账标记 interrupted 且保留 checkpoint""只有有效结构化结果才推进 checkpoint""旧格式惰性升级"。<br>② **修复前的复现证据**：run `35058719984`（Ubuntu / Python 3.10，**修复前**）结果 **4 tests, 3 failures + 1 error**，且失败项**逐条对应契约**：失败尝试把 turn 3→4、崩溃后停在 4 而非 3、陈旧对账用控制器错误替换已接受摘要、`KeyError: checkpoint`。<br>③ **修复后的验证**：run `35059244958`（Win Server 2025 / 3.10）**26/26 passed**、另一 job（Ubuntu 24.04 / 3.10）**4/4 passed**；run `35059244985`（Stage 1 回归）Py 3.9 与 3.11 **均 success**。测试用**确定性替身**，"不启动真实 Codex 轮次、不需要模型/API 凭据"。<br>④ **真实数据上的负控**（`09-...md` §3.7.1）：`tools/verify_references.py` 用**五索引交叉**（Crossref / OpenAlex / zbMATH Open / Internet Archive / Open Library），匹配需"标题相似度 **且** 姓氏重叠 **且** 年份 ±2"**同时满足**——因此"真标题 + 伪造作者"无法通过；负控含"伪造引用被拒 / DOI 与标题不匹配被拒 / 页码被两个索引同时否证被拒 / 编号不连续与悬空引用被拒"，**22 个新用例、合计 39/39 bug，是校验器正确工作** —— 它真的重新打开文献，抓住了**刻意伪造**的那条假引文（`relations/0007`）（`11-...md` §10.6）。<br>⑥ 真正的缺陷是**分级语义**：「表里已经写了 `quote_verified=False`」是已知并记录的缺陷，重算只是**确认**它，不该是 error —— 否则"红灯会被训练成背景噪音"（`11-...md` §10.6 原文）。<br>⑦ 修复后**两个方向都断言**：`quote_known_unverifiable` 为 warning、谎报为 True 时仍是 error（`11-...md` §10.6 表）。<br>⑧ 一条更强的负控手法：`extract_text` 的测试替身被写成"**一被调用就抛 `AssertionError`**"，而不是返回假数据——"返回空只能证明没抽到东西，抛异常能证明**根本没去读那个文件**"（`10-...md` §10.8.3 第（4）点）。<br>⑨ 结构性证据：本项目 **9 条缺陷中 0 条**能被 happy-path 测试抓到（`10-...md` §10.10 结论 | **对下一阶段的直接后果** | **该做**：每个验证门必须配一条**负控用例**（inject known-bad → assert 变红）与一条**防误伤用例**（normal good → assert 变绿），两者缺一不可（对照 `11-...md` §10.6 的"两个方向都断言"）。<br>**该做**：照抄 `09-...md` §3.7.3 的**三条方法论**：① 把"评审模型的盲区"翻译成**确定性检查项**（能力切分）；② **负控先行**（先写契约 → 用 CI 复现 bug → 再修）；③ **诚实边界声明**（原文给出三个范例：`not an exactly-once execution guarantee`、`never judges whether a source supports a claim`、索引分歧只报警告不静默裁决）。<br>**该做**：验证门 **fail-closed**——证据不足（`inconclusive` / `None`）**不得**判通过（`09-...md` §3.2）。<br>**该做**：告警必须**分级**（`error` / `warning` / `info`），且分级规则写进文档；"已知且已被记录的缺陷"重算确认后降为 `warning`，只有"状态与事实矛盾"（谎报）才是 `error`。<br>**不该做**：不要因为"我们校验通过了"就认为系统正确——`10-...md` §9.7 已实测证明**结构不变量全绿 ≠ 知识可用**。 |

## 经验 6：静默失败 / 静默覆盖比崩溃更危险

| 项 | 内容 |
|---|---|
| **经验** | 崩溃会报警，静默失败不会。**"所有 API 都返回成功"是本项目最危险的状态**。框架必须为"静默"这一类失败专门设计检测手段。 |
| **来源** | `10-...md` §10.1（缺陷 #1）、§10.10 结论 ③「静默覆盖（#1）比崩溃更危险，因为它不报警」；`11-...md` §10.2（缺陷 #4 `Tx.mark_dirty`）、§10.7 第 1 条 |
| **证据/案例** | ① 缺陷 #1：`Store.alloc_id` 每次从磁盘重读 counters → **5 个候选全拿 `lit_id="0000"`** → 按主键 upsert **静默互相覆盖** → 表里只剩 1 行，而 `library/0000/` 下有 5 个文件。数据静默损坏（`10-...md` §10.1）。<br>② 更狠的一层：`result_lit_ids` 本来是 `["0000","0000","0000","0000","0000"]`，但 `sorted_unique()` 把它去重成 `["0000"]` —— "**`sorted_unique` 的正常用途是保证数组升序去重，但它在这里意外地掩盖了 bug**"；而 `verify` 只检查"是否指向存在的文献"，**不检查重复**，所以 verify 也发现不了（`10-...md` §10.10 结论 ③）。<br>③ 发现方式：**人眼观察 demo 打印的行数**（"5 个候选 → 只有 1 行文献"这个反常识数字）（同上）。<br>④ 本项目第二轮：`Tx.mark_dirty` 的 docstring 提到但方法不存在，调用方只能摸私有属性；补上方法后实测确认危险语义（`11-...md` §10.2）：<br>`初始: ['甲','乙'] → A 不标脏 → ['甲','乙']`（**就地改列表，改动凭空消失，不报任何错**）；`B 标脏 → ['标了脏','乙']`（正确落盘）。<br>⑤ 本项目第三例：角色名 `"agent-D"` vs `"D"` —— `for_role('D')` 拿不到 D 专属工具，`build_for_role('D')` 造出的注册表里 D **没有自己的研究工具**，**没有任何地方报错**（`11-...md` §10.6 第二个）、修复见 `src/abflow/tools/__init__.py:155-173` 的角色断言。 |
| **对下一阶段的直接后果** | **该做**：把"人眼可读的中间状态"当成**一等交付物**——任何端到端演示必须打印完整中间状态表（行数 + 关键字段），而不是只打印 PASS/FAIL（`10-...md` §10.10 结论 ③的第 4 条建议）。<br>**该做**：为"静默"设专门断言。可判定判据：<br>(a) 主键分配函数的断言必须是**精确序列**（`ids == ["0000",...,"0004"]`）而不只是"5 个互不相同"（`10-...md` §10.1）；<br>(b) 任何"就地修改可变返回对象"的路径，要么改成不可变返回，要么在提交时做**行数守恒断言**（进 vs 出的行数 + 内容指纹）；<br>(c) 任何跨模块字符串常量必须有一个**装配期断言**（对照 `tools/__init__.py:155-173`）。 |

| **证据/案例** | ① DSH 的**三维预算**（实测）：`maxConcurrentAgents` 默认 **`0` → `min(16, max(1, availableParallelism() - 2))`**（**留 2 个核给宿主 + 硬顶 16**，即使 128 核也不放 126 个并发 LLM 调用）、`maxTotalAgents` 默认 **1000**（runaway-loop 兜底）、`maxItemsPerCall` 默认 **4096**（`04-...md` §B1）。<br>② 其他真实上限：DSH jobs `maxConcurrentJobsPerOwner=10`、subagent `maxDepth=3`、ralph `maxRounds` 包默认 **256**（`dsh-base` 装配为 **64**）、workflow tool `maxResultChars=50000`、工具结果剪枝 `thresholdChars=8192`/head 4096/tail 1024、spill `maxInlineBytes=50000`（`04-...md` §B1 表）。<br>③ **HiveMind 消融的最反直觉结论**：**最关键的单一原语是"透明重试"，而不是准入控制**；但**原语组合起来效果最好**（`04-...md` §B1）。<br>④ **重试放大的真实数字（Google SRE 第 22 章）**：健康 `10,000 QPS` → 临界 `11,000` 开始级联失败 → 试图恢复 `9,000` **仍然救不回来** → 实际需要的恢复点约 **1,000**（因为此时只有约 10% 实例还健康）。推论："**如果你有 100 路并发 agent，provider 开始 429，你不能把并发降到 90 就指望恢复——你可能需要降到 10。**"（`04-...md` §B6）。<br>⑤ 取消语义：**没有一种通用机制能安全强杀正在执行的异步任务，取消都是协作式的**；DSH 的分层设计值得整套照抄：协作式取消 + 有界兜底（`disposeGraceMs` 到点强杀）、**一个共享 signal 覆盖所有在飞与待启动的子任务**（不能逐个取消，会漏）、终态**先到先得 first-wins**、**每个 start 事件有且仅有一个 end 事件**（死亡或强杀时**合成**缺失的 end 为 cancelled）、`dispose()` 幂等（`04-...md` §B5）。<br>⑥ 中断后**不自动重试**："interrupted tool calls recover with an **unknown outcome** instead of an automatic retry"（`04-...md` §B5），因为副作用可能已经发生。<br>⑦ 本项目现状：`Store` 的锁/租约语义有 **4 进程 × 20 次**的用例，但 **C/D 的并发未测**（两个 D 同时研究同一批问题）（`11-...md` §12 第 9 条）；**D 向 A 提问的预算本轮默认每问题 2 轮、全局 20 个请求，且报告明确标注"这条需要尽快定"**（`11-...md` §13 第 3 条）。 |
| **对下一阶段的直接后果** | **该做**：新框架启动时必须同时声明**三维预算**（瞬时并发 / 生命周期总量 / 单批规模）与**深度上限**；深度计数必须**持久化且单调**（resume/fork 不能重置，对照 `04-...md` §D2 反模式 16，其源码为 `return Math.max(agent.session.header.delegationDepth ?? 0, runtime ?? 0)`）。<br>**该做**：把 D 的提问预算**定下来并写进配置**（当前是待决项，`11-...md` §13 第 3 条）；预算按"token"而不是"请求数"设限（`04-...md` §B1 HiveMind 五原语之一），并注意 `04-...md` §D3 ⑧ 的警告——**别假设框架一定给你 token 预算**。<br>**该做**：并发上限的取值判据是 `min(CPU 并行度, RPM 额度, TPM 额度)`，而**通常 TPM 最先被打爆**（`04-...md` §B8）；**RPM 与 TPM 两个维度都要限**（§D2 反模式 32）。<br>**该做**：把工具中止从二分升级为**三态**——`04-...md` §F3 的两个中止码给出了可直接照抄的形态：`TOOL_ABORTED`（**只在工具主体已经调用后使用**）与 `TOOL_ABORTED_BEFORE_DISPATCH`（从未进入工具主体），并且明确"**`ABORTED_BEFORE_DISPATCH` 可以安全重试，`ABORTED` 不能**"。<br>**不该做**：不要用一个 semaphore 冒充并发治理；不要在没算过队列规模的情况下开大队列（SRE：队列 < 线程池的 **50%**，`04-...md` §D2 反模式 21）；不要在不确定结果时自动重试（§B5）。<br>**可判定判据**：配置文件里必须能同时看到 `maxConcurrent*` / `maxTotal*` / `maxDepth` / `tokenBudget` 四类键，且每类都有非空值；缺任一类，框架启动即 fail-closed。 |

## 经验 9：工具层的 `side_effect` 必须是一等公民，因为它是审批判据的唯一可信来源

| 项 | 内容 |
|---|---|
| **经验** | 工具不是"函数"，而是**有名字、有 schema、有校验、有结构化返回、声明副作用、声明角色**的原子动作。审批建立在**声明**上，不能建立在人的记忆上。 |
| **来源** | `11-...md` §2「为什么必须有一层'工具层'」§2.1 三个刻意的设计、§2.2「'按角色装配'就是权限面」；`design` 基线 `test/test1/DESIGN-TOOLS.md` §1 |
| **证据/案例** | ① 契约（`11-...md` §3.1）：`ToolSpec{name, summary, params(JSON Schema), handler, side_effect, roles, returns}`；`SIDE_EFFECTS = ("none","read","write_local","network")`，`NEEDS_APPROVAL = ("write_local","network")`。<br>② **最直接的收益体现在 C 身上：C 的全部工具都是 `read`** —— "因为 C 的职责是'用程序分析关系表'，它应当能**任意多次、任意组合**地查询，而不触发任何审批或写盘。**如果查询会写盘，就没人敢让模型自由地反复取证了。**"（`11-...md` §2.1 ①）。<br>③ 参数错误**返回结构化失败而不是抛异常**："只有'调用方写错'与'环境故障'才抛；'业务上的失败'返回 `ok=False`"，理由是"智能体看到 `ok=False` 可以自己纠正参数继续跑；抛异常会**打断它的循环**"（`11-...md` §2.1 ②）。<br>④ `params` 用 JSON Schema 写而不是 Python 类型标注：**同一份声明既做校验、又做 function-calling 描述**（`11-...md` §3.1）。<br>⑤ 角色即权限面：**A 拿不到 `research.*`，B 拿不到 `search.*`**；"把'谁能用什么'固化在注册表里，比写在提示词里可靠得多 —— **提示词可以被绕过，注册表不能**"（`11-...md` §2.2）。<br>⑥ 只读工具的关键取舍：`research.poll_waiting` **只做确定性判断且不写盘**，"把状态迁移留给 `agent_d` 而不是工具内部 —— 工具一旦偷偷改状态，'这一轮到底谁动了什么'就不可审计了"（`11-...md` §3.4）。<br>⑦ 但**声明也要能被检查**：本项目的 `ToolSpec.side_effect` 是自由字符串，虽然定义了 `SIDE_EFFECTS` 常量，报告里**未找到**"装配期断言 side_effect ∈ SIDE_EFFECTS"的记录（对照组：角色名断言**已落地**在 `src/abflow/tools/__init__.py:155-173`）。 |
| **对下一阶段的直接后果** | **该做**：`side_effect` 与 `roles` 都必须是**枚举**，并且**都在装配期断言**（不是只在文档里定义）。<br>**该做**：把"审批"实现为**对 `side_effect` 声明的纯函数**（`needs_approval = side_effect in ("write_local","network")`），并把该函数作为唯一判据；任何绕过它的路径都是缺陷。<br>**该做**：每个工具的返回结构必须**写进 `returns` 并附一条契约测试**——本项目实测"我写冒烟测试时按 `data['id']` 取新 ID，直接 `TypeError`"（`11-...md` §3.5），"接口约定必须写进文档，否则每个调用方都会猜错一次"。<br>**不该做**：不要让写工具"顺手"改别的表；不要让只读工具写盘。 |

## 经验 10：每一条断言都必须能追到原文——引文、代号链、以及"可重建不应重建出更少的信息"

| 项 | 内容 |
|---|---|
| **经验** | 知识产出（无论来自 LLM 还是程序）必须以**逐字可核的引文** + **可追溯的代号链**为最小单位；`None`（无法核验）与 `False`（核验失败）必须分开；并且**任何"可重建"的存储，重建后信息量不得少于重建前**。 |
| **来源** | `10-...md` §6「引文校验 —— 把'完全引用'变成可执行的质量门」§6.1–§6.5、§9.7.5、§11.10.1；`11-...md` §4.1、§6.3；`09-...md` §3.7.1「PR#4 引文真实性」（五索引交叉）；`08-...md` §B.0 / §D（证明必须由检查器验证；axiom 审计） |
| **证据/案例** | ① 设计裁决 C6：把"关系描述"拆成 `quote`（逐字原文，机器可校验）+ `statement`（规范化陈述），理由："只有独立保存逐字引文，B 才能**自我校验**引文确实存在于该文献；把两者混在一个字段就无法验证"（`10-...md` §2.1 / `test/test1/DESIGN.md` §0.1 C6）。<br>② 校验用**保守规范化后的子串匹配，而不是相似度**，因为需求要求"完全引用"；允许的差异仅限空白折叠 / 大小写 / 连字符与引号归一化 / 全半角，"**不允许**改词、省略号省略"（`10-...md` §6.1）。<br>③ 页码未知时**不做全文兜底**（默认 `allow_fulltext_quote_fallback=False`），因为"全文兜底会把'页码写错了'这个真实缺陷掩盖掉"——用**弱命题**（引文存在）冒充**强命题**（引文在所声称页码上存在），就是掩盖缺陷（`10-...md` §6.4）。<br>④ LLM 侧的第一原则：回验。原文："提示词里写'不要编造'是**降低概率**，回验是**消除后果**：编造的 quote 永远不会进库"（`10-...md` §9.7.5 引 `llm.py::_ground_relations` 注释）。<br>⑤ 更精妙一步：`_locate_verbatim` **返回原文里的确切切片而不是原样返回 `quote`** ——"调用方拿到的东西**天然**是 `text` 的子串，不需要再相信谁"（`10-...md` §9.7.5）。<br>⑥ 代号链：D 的溯源分 L1（`relation_id` → quote/description/page_range）/ L2（`concept_id` → 定义 + 全部关系表述）/ L3（`lit_id` → 正文片段，**按需**，贵）（`11-...md` §6.3）。<br>⑦ 真实数据上的正例：`realrun` 的 4 条关系引文在 **545,830 字节的真实 PDF**（Arıkan 论文）里**逐字命中**，`window=declared:X-X`（`10-...md` §9.7.2）。<br>⑧ "可重建不应重建出更少的信息"：`rebuild` 会丢 `_keys` 与 `_quote_check`，修复方式是**合并而非替换**（`canonical = obj.to_dict(); merged = {k:v for k,v in row.items() if k not in canonical}; merged.update(canonical)`），并明确"**规范值优先、诊断字段保留**"（`10-...md` §11.10.1）。<br>⑨ **外部权威参照（`09-...md` §3.7.1）**：该项目把"引文真实性"从模型手里拿走，用**五索引交叉**（Crossref / OpenAlex / zbMATH Open / Internet Archive / Open Library），匹配需"标题相似度 **且** 姓氏重叠 **且** 年份 ±2"**同时满足**——因此"真标题 + 伪造作者"无法通过；真实数据 **34/35 条来源通过**，唯一失败项（Riemann 1857，早于 zbMATH 1868 覆盖范围）工具报"**无法验证**"而**不是**"通过"。其问题陈述值得逐字记住：`"That is precisely where archives fail silently, because a hallucinated or miscopied citation still looks plausible to a reviewer model."`<br>⑩ **`09` 的诚实边界（照抄）**：该工具 `"never judges whether a source supports a claim"`——即"来源真实"与"来源支持该断言"**是两个不同的检查**。本项目的 `quote_verified` 同理：它只证明"这段文字在这份文档的第 X 页"，不证明"这句话讲了一个知识点"（`10-...md` §9.7.3）。 |
| **对下一阶段的直接后果** | **该做**：**每条断言都要能追到原文**——LLM 产出的任何"引用型"字段，入库前必须经"回到原文找一遍"，且**存回原文切片**而不是模型给的字符串。<br>**该做**：把"引文真实性"与"引文支持该断言"**分成两个独立的检查项**（照抄 `09-...md` §3.7.1 的边界声明），前者可确定性自动化，后者需人工/语义判断，**不得合并为一个字段**。<br>**该做**：每个知识实体携带**双向代号链**（本条引用了谁 / 被谁引用），且 `verify` 检查**悬空引用**。<br>**该做**：`rebuild` / 迁移 / 序列化路径必须有一条"**信息量守恒**"断言（重建前后诊断字段相等，见 §6 约束 12）。<br>**不该做**：不要用相似度代替逐字校验；不要在引文无法核验时判"通过"；不要因为"没得比"（空引文）就判通过——`"" in "abc"` 在 Python 里是 `True`，这条路径必须被显式挡住（`10-...md` §6.5）。 |

## P2 状态机缺边

| 项 | 内容 |
|---|---|
| **定义** | 状态字段定义了若干取值，但某些取值的**出边没有被实现**；对象进入该状态后永远出不来，而**外部表现为"进程正常结束"**。 |
| **实例** | `11-...md` §10.4 缺陷 #9：`pipeline --no-search` 的摘要长期是 `questions: {open: 4}`、`requests_total: 0`。根因不是"因为没接线 A 所以跳过"（这是作者的第一个假设，**错的**），而是**状态机缺一条边** ——「证据足够」这一支原来**什么都不做**，于是问题永远停在 `open`；而 `research()` **只处理 `researching`** → **永远不被研究，报告里也没有证据**。修法是新增 `consider()` 完成路由（足够 → `researching`；不足 → 提问）。<br>报告还记了一条方法论："**必须实测，不能靠读代码推断设计意图**"——作者当时给了两个假设 `(a) 设计如此` 或 `(b) 是 bug`，**实测判定为 (b)，但根因不是我以为的那个**（`11-...md` §10.7 第 4 条）。 |
| **预防机制** | **(a) 状态机必须是数据**：把 `状态 → 允许的迁移` 写成显式表（`TRANSITIONS: dict[str, set[str]]`），而不是散在 `if/elif` 里。<br>**(b) 可达性断言**：启动或测试时做一次**图可达性检查**——从初始状态出发，**每个状态都必须可达**，且**每个非终态都必须有出边**；孤立状态直接报错。<br>**(c) 进度断言**：端到端测试必须断言"经过 N 轮循环后，状态集合发生了变化"，而不只是断言"退出码为 0"。可判定判据：`assert states_before != states_after`，或 `assert any(s in ("answered","dropped") for s in final_states)`。<br>**(d) 终态必须留痕**：`status=dropped` 时必须写 `notes` 说明为什么放弃（本项目已在 schema 层强制，见 `11-...md` §4.1 的两条一致性校验——这是**正面范例**）。 |

## P3 缺省折叠

| 项 | 内容 |
|---|---|
| **定义** | 把"**没做**"（未执行 / 未接线 / 无能力 / 被预算截断）折叠成"**做了但没结果**"。折叠之后不报错，而且**看起来像结论**。 |
| **实例** | ① **D 的溯源（最尖锐的一例）**：D 的报告写"未能取到任何关系表述（L1/L2 均为空）——**这本身就是一个重要事实**"；而真相是 `tools=None` 走了"无工具"的降级分支并**静默返回空**。而"L1/L2 为空"在 D 的判据里又是"知识不足"的信号之一 —— "于是这个错误会**伪装成一个合理的结论**（'查过了，没有'），而不是报错"（`11-...md` §10.4 缺陷 #7）。<br>② `10-...md` §10.2 缺陷 #2：搜索**正常**返回空结果时 `done=true` 但既无 `result_lit_ids` 也无 `last_error` → schema 抛 `ValueError` 冒泡出 `run_once` → 请求留着 **900s 租约**把队列堵死 → 由此**被逼出** `outcome` 字段。<br>③ 引文校验：`None`（无文本层 / 空引文）vs `False`（找不到 vs 页码未知）（`10-...md` §6.3、§6.5）。<br>④ OCR：无后端 vs 返回空串（`11-...md` §8.1–§8.2）。<br>⑤ C 的预算截断 vs 搜完了（`11-...md` §5.3(2)）。 |
| **预防机制** | **(a) 三态返回类型**（不是 `bool`，不是"空列表"）：`Tri(value, reason)`，`reason` 为受控枚举，且"未执行"必须有自己的 `reason` 值。<br>**(b) 工具未接线必须炸**：`tools=None` 这类"降级分支"必须产生 `ok=False` + `kind="not_wired"`，**不得返回空数据**。可判定判据：任何"上游为 None 时返回空"的代码路径，必须有一条测试断言它**返回失败而不是空**。<br>**(c) 计数分离**：验证结果必须分开计数（本项目 `quote_verified` / `quote_unverified` / `quote_unknown` 三个独立字段，理由："一个'通过率 80%'的单一数字会掩盖'20% 是失败还是未校验'这个决定性差异"，`10-...md` §6.3）。<br>**(d) 截断必须留痕**：任何预算/limit 截断必须写出 `truncated=True` 与"另有多少条未展开"（本项目 `gaps` 实测："另有 23 条中等以上置信度候选超出 limit=6 未展开（已在统计中计数）"，`11-...md` §5.3(4)）。 |

## P4 检测到了却没有消费

| 项 | 内容 |
|---|---|
| **定义** | 上游**完全正确地**产出了一个状态，下游**从不知道有它**。没有任何单个模块的行为是错的，**三个模块的单元测试全绿**。 |
| **实例** | `10-...md` §10.8 缺陷 #8（第二轮新增）：下载器**正确**检测到"URL 以 `.pdf` 结尾但返回 `text/html`"并打了 `content_type_mismatch` 告警、如实放进 `FetchResult.error`（同时 `ok=True` 表示"字节拿全了"），但 **AgentA 仍记 `status="ok"`**，于是 **AgentB 照常去抽取那个 12.4 MB 的 HTML** —— 网页导航文字被当成"概念"落库。<br>三层层层递进的事实：① 那个 URL **以 `.pdf` 结尾**（按后缀判断类型会失败）；② 它返回 **HTTP 200 + 12.4 MB `text/html`**（按状态码判断成功也会失败）；③ 内容**会变**（两次下载差 464 字节、`sha256` 也不同）。<br>报告给出的三条可操作判据（`10-...md` §10.10 结论 ⑥）：<br>(1) 这个"状态"是**显式的受控取值**，还是**错误信息里的一个字符串前缀**？（前缀脆弱，改一个字就失效）<br>(2) 下游**真的**读它了吗？（不是"可以读"，是"读了并且据此分支"）<br>(3) 有没有一条**端到端**的用例，同时构造"上游产出该状态"与"下游消费它"？ |
| **预防机制** | **(a) 状态枚举化 + 入库**：把隐式约定提升为 `download.status ∈ {ok, failed, skipped, content_mismatch}` 这样的**受控取值**，并写进 schema 校验（`10-...md` §11.10.6 已修）。<br>**(b) 端到端交接测试**：`tests/test_download_handoff.py` 三条用例，其中一条把 `extract_text` 写成"一被调用就抛 `AssertionError`"，"比'返回空'更强：'返回空'只能证明'没抽到东西'，'抛异常'能证明**根本没去读那个文件**"（`10-...md` §10.8.3）。<br>**(c) 约定清单法**：把项目里所有"跨模块约定"列成表，逐条问"有没有会自动失败的检查"（`10-...md` §13.6 方法三，表格中"少了任何一处，它都只是文档里的一句话"）。<br>**(d) 违反约定的**下游**也要能自证**：B 侧把三种"不可读"合并为**同一个 `unreadable_reason` 变量 + 一段统一处置代码**，理由是"原来的 bug 正是'某个情况没被纳入同一个判断'"（`10-...md` §10.8.3 第（3）点）。 |

## P5 静默数据丢失 / 覆盖

| 项 | 内容 |
|---|---|
| **定义** | 写入路径上存在一条**不经过提交**的旁路（就地改可变对象、缓存未标脏、主键撞车），于是改动**凭空消失**或被**静默覆盖**；所有 API 都返回成功。 |
| **实例** | ① `11-...md` §10.2 缺陷 #4：`Tx` 的 docstring 提到 `mark_dirty(t)`，但类里**没有这个方法** —— 删除只能改 `tx.rows()` 列表并直接置私有属性 `tx._dirty`。补上公开方法后**实测确认了危险语义**：`初始 ['甲','乙'] → A 不标脏 → ['甲','乙']`（**就地改列表，改动凭空消失，不报任何错**）；`B 标脏 → ['标了脏','乙']`（正确落盘）。根因：`tx.rows(t)` 返回**可变列表**，就地改动不经过 `upsert`，于是没有任何东西把表标脏 → 提交时被跳过。<br>② `10-...md` §10.1 缺陷 #1：`Store.alloc_id` 每次从磁盘重读 counters → 同一事务内 5 次 `alloc_id` 全返回 `"0000"` → 5 次 `upsert` 按主键 `"0000"` 定位 → 前 4 次被第 5 次**替换** → 表里 1 行，`library/0000/` 下 5 个文件。<br>③ `10-...md` §10.4 缺陷 #4：`Store.tx` 只在**成功提交后**清空 `_dirty_counters`，异常路径不清理 → 下次 `alloc_id` 从"磁盘上并不存在的值"继续发号 → **ID 空洞**；跨进程时会**真撞号**并被 upsert 静默覆盖。 |
| **预防机制** | **(a) 不可变返回**：事务内的"读行"应返回**副本的只读视图**或显式 `Row` 句柄；任何修改必须过 `upsert`/`delete`/`mark_dirty` 之一，**没有第四条路**。<br>**(b) 行数守恒断言**：提交前断言 `len(out_rows) == len(in_rows) + inserts - deletes`，或直接对表内容取指纹比对。<br>**(c) 主键唯一性断言**：提交前断言本事务内新分配的 ID **互不相同且不带空洞**（本项目测试断言精确序列 `["0000","0001","0002","0003","0004"]`，并据此暴露了 #1）。<br>**(d) `finally` 清理**：所有"事务级缓存/脏标记"必须在 `finally` 里无条件清理（无论成功失败），"把清空移到 `finally` 块，无论成功失败都清"（`10-...md` §10.4）。<br>**(e) 危险语义必须有测试守住**：本项目为 `mark_dirty` 加了 4 条回归测试，**其中一条刻意断言"不标脏就会丢"这个危险行为** —— "若将来有人改成自动标脏，它会失败并提醒同步改语义"（`11-...md` §10.2）。 |

## P6 缓存 / 派生态与真源不一致

| 项 | 内容 |
|---|---|
| **定义** | 为性能或一致性引入的缓存/派生结构，本身成为新的漂移源；**修复一个 bug 时引入的缓存，往往就是下一个 bug 的成因**。 |
| **实例** | `10-...md` §10.4 末尾原文："这与缺陷 #1 是同一类故障的不同成因（一个是'同事务内重复发号'，一个是'失败事务泄漏号'），后果也一样（静默覆盖）。修复方式不同（#1 靠 `_dirty_counters` 缓存，#4 靠 `finally` 清缓存）—— **注意这两个修复是耦合的：#1 引入的缓存正是 #4 的泄漏源**。这是一个典型的'修复引入新问题'的模式，而测试把它抓住了。"<br>另一形态：派生态（`related_concepts`）"**不由增量 append 直接决定**，而是**由关系表派生**"，好处是**可自愈**（漏更新会在下次重算时修正），且 `verify` 会重算一遍与表中值比对（`test/test1/DESIGN.md` §6.2）。 |
| **预防机制** | **(a) 优先选"可重算的派生态"而不是"增量维护的缓存"**：`related_concepts` 的派生公式（`related_concepts(c) = sort(⋃ over relations r where c ∈ r.concept_ids : r.concept_ids \ {c})`）就是正面范例——漏更新会自愈，且 `verify` 能重算比对。<br>**(b) 每个缓存必须回答三个问题**：谁是它的真源？什么时候失效？失效失败会怎样？（本项目对最后一个问题的答案是"下次重算时修正"或"`finally` 无条件清"。）<br>**(c) 修复一个 bug 后，必须为"新引入的状态"补一条测试**——本项目正是这样抓住 #4 的。 |

## P7 校验器与写入方参数不一致

| 项 | 内容 |
|---|---|
| **定义** | "写入时校验 + 事后复核"的两段式设计里，两段**各自都对**，但**假设不同**（一份读配置、一份硬编码）。 |
| **实例** | `10-...md` §11.10.2：`agent_b` 用 `config.yaml` 的 `quote_widen_pages` / `allow_fulltext_quote_fallback`；`verify --deep` 用**硬编码**的 `widen=1, allow_fulltext_fallback=False`。后果："若用户把 `quote_widen_pages` 调成 2，写入时会用 ±2 页通过，`--deep` 复核用 ±1 页 → **假的 `quote_not_found` error**"。<br>报告给出的一般化结论：**"校验器必须与写入方共用同一套参数，否则假报警比不校验更糟。"** 并给了对比表：漏报的长期后果是"缺陷累积"；**假报警的长期后果是"人对告警脱敏——以后真的缺陷也无人看"，修复代价是"文化性损伤，几乎不可逆"**（理由引自 `verify.py` docstring："那是**假报警**，比不校验更糟，因为它会训练人忽略告警"）。 |
| **预防机制** | **(a) 单一配置源**：写入方与复核方必须从**同一份配置对象**取值，并把这个要求写进函数 docstring（本项目已这么做，见 `verify.py::verify_all` 的参数说明）。<br>**(b) 参数必须显式传参而非默认值**：`quote_widen: int = 1` 这种"有默认值"的签名是隐患——调用方忘了传就静默用错的窗口。可判定判据：**校验器函数的参数不得有默认值**，或默认值必须等于"拒绝执行"。<br>**(c) 一致性断言**：启动时断言"复核参数 == 写入参数"，不等即 fail-closed。 |

## P8 规则覆盖缺口

| 项 | 内容 |
|---|---|
| **定义** | 过滤/判据规则对**一种形态**生效，对**另一种形态静默失效**；代码本身没有 bug，只是**规则的作用域与作者的意图不符**。 |
| **实例** | `10-...md` §9.7.1 / §11.1：`RuleExtractor` 的代词黑名单 `_EN_STOP_SUBJECTS` **只在"单个词"时生效**：`if len(words) == 1 and words[0].casefold() in _EN_STOP_SUBJECTS: return False`。后果表：`It`（1 词）被拒 ✓；`This`（1 词）被拒 ✓；**`This paper`（2 词）通过 ✗**；**`This mapping`（2 词）通过 ✗**；**`when W`（2 词）通过 ✗**。<br>真实后果（`realrun/data/concepts.json` 的 40 个概念）：`This paper`、`If W`、`when W`、`with equality iff W`、`1 The ratio K/N`、`operator RN in the ﬁgure`、`havior`（`behavior` 被 PDF 连字切断的残片）等**句子的碎片**进了概念表。 |
| **预防机制** | **(a) 规则的"作用域"必须是显式的**：把 `len(words)==1` 这类前置条件提升为函数名的一部分或一个独立谓词（如 `is_single_pronoun` + `starts_with_pronoun`），避免"条件写在中间被忽略"。<br>**(b) 规则必须有一张"形态覆盖表"**：为每条过滤规则列出它覆盖的形态（单词 / 短语 / 含标点 / 中文 / 连字残片），逐格给一个测试用例。本项目 `_looks_like_term` 已有 5 类判据（长度、句读符、词数、代词、中文），但**只有代词那一类漏了多词形态**。<br>**(c) 产出质量必须有人看**：结构校验全绿时，**必须人工抽检一批产出**（本项目 §9.7 就是这么发现问题的）。 |

## P9 注释 / 文档与代码不一致（文档漂移）

| 项 | 内容 |
|---|---|
| **定义** | 注释或文档承诺了一个行为，代码没兑现（或相反）。 |
| **实例** | ① `10-...md` §10.5 缺陷 #5：`literature_keys` 的 docstring 说第三个键 `title:<norm>\|*` "**不是装饰**……它在 `find_existing_literature` 的第 3 轮里被真正使用"—— 而修复前它**确实是**装饰。报告点评："'不是装饰'这四个字透露了 bug 的存在：在修复前，它**确实是**装饰（生成了但没用）。写下这四个字（而不是简单描述功能）说明作者当时已经意识到'这个键很容易被写成装饰'。"<br>② `10-...md` §10.9 缺陷 #9：`http_get_json` 的注释说"JSON 解析失败通常不是瞬时故障，重试一轮后即放弃更省配额"，而代码 `if attempt >= retries or isinstance(exc, json.JSONDecodeError)` 的外层 `or` 对结果**没有任何影响**（`json.JSONDecodeError` 与 `TimeoutError` 行为完全相同，都重试到耗尽）→ **注释承诺的"重试一轮后即放弃"未实现**。<br>③ `10-...md` §10.10 结论 ④：共发现 **3 处过时注释**（`test_agent_b.py` 的 `relations_suspect` 描述、`providers.py::_parse_item` 读永远为 `None` 的 `language`、`http_get_json`），其中 2 处已修。<br>④ `10-...md` §11.10.5：`README.md` 与代码的若干不一致（文档漂移）。 |
| **预防机制** | **(a) 把注释里的承诺变成测试里的断言**（首选，不是改注释）："当你发现'注释与代码不符'时，**首选不是改注释，而是问'这条注释在承诺什么？能不能变成一条断言？'**"——本项目 `test_agent_b.py` 的修复方式就是**在注释旁边加三个断言**（`relations_suspect == 1` / `suspect_by_quote == 1` / `relations_added == 0`）（`10-...md` §13.6 方法五）。<br>**(b) 主动审查手法**：读 docstring / 行内注释里的**行为承诺**（"必须"、"绝不"、"会"、"不会"、"只在……时"）→ 在代码里找兑现那段承诺的语句 → 逐条对照"承诺的每个条件都真的实现了吗？有没有死代码？"（`10-...md` §10.10 结论 ④）。**这条手法零成本，且在本项目抓到了 2 条缺陷。**<br>**(c) 把"注释一致性审查"加入评审清单**（同上结论 ④的建议第 3 条）。 |

## P10 集成层接线缺失

| 项 | 内容 |
|---|---|
| **定义** | 每个零件的单元测试都绿，因为它们测的是"**零件对不对**"，而问题出在"**零件有没有被接上**"。 |
| **实例** | `11-...md` §10.4 三条（#7 D 未接 registry、#8 同一 C 报告的不同实例产出重复问题、#9 状态机缺边）**都只有在真实端到端运行时才暴露**。<br>① #7：D 拿不到工具（`tools=None`）却**静默返回空**，并把空包装成"一个重要事实"。<br>② #8：`research_questions` 里 4 条问题，实际只有 **2 个**不同的研究点（`0000` 与 `0002` 的 `origin` 分别是 `C:paths:0000:...` 与 `C:paths:0001:...`，但 `rels` 完全相同）—— 成因是 `analysis_reports` 有 2 份 `kind=paths` 的报告，D 把两份都 ingest 了。修法：按内容键 `(kind, 排序后的 related_relation_ids)` 去重，**已存在时不新建行，把新 `origin` 追加留痕**（"多份报告指向同一研究点"本身是该点**更值得做**的信号）。实测问题数 **4 → 2**。<br>③ #9 见 P2。<br>④ 同类：`11-...md` §10.3 两条 CLI 缺陷（`row['kind']` 而 `persist()` 只返回登记行；`with_search=` 而 `run_pipeline` 用 `agent_a=None` 表达"不检索"）——"端到端跑才暴露"。 |
| **预防机制** | **(a) 端到端用例是独立的一层**：本项目实测结论"**单元测试抓不到集成缺陷**"（`11-...md` §10.7 第 3 条）。框架必须有"最小完整链路"的 e2e 用例，且**必须跑真实数据/真实外部系统一次**。<br>**(b) 接线本身要可观测**：`RegistryBuild` 有 `loaded` 与 `skipped` 两个字段，"让'某个模块没装上'变成可见的事实，而不是静默少几个工具"（`11-...md` §3.2）。**可判定判据**：装配结果必须能回答"每个角色拿到几个工具"，且与预期值比对（对照 `11-...md` §9.1 实测 `{'A':20,'B':18,'C':23,'D':28}`）。<br>**(c) 内容级去重必须是通用能力**：任何"从外部产出中提取任务"的环节都要有内容键去重（P10 #8）。<br>**(d) "提交请求"必须是本地写表**：D 的 `submit_gap` 只是本地写表，**不需要 A 在线**——"如果把'提问'实现成'调用 A'，那么 A 不在线时 D 就无法记录自己的知识缺口，循环接不上"（`11-...md` §6.5）。 |

## P11 弱断言给假信号

| 项 | 内容 |
|---|---|
| **定义** | 一个只做 `count >= 1` 的断言"**既能因正确原因通过，也能因错误原因通过**"——它在"给结论"上是有害的，因为它会让**相邻的、真正有判别力的断言**看起来像"边界错了"。 |
| **实例** | `11-...md` §11：审查者看到 C 的自检失败 `正文只含 high 路径`，结合上一行 `[PASS] low 路径没有进正文`，**断言**"`medium` 进了正文，违反需求"。**判断是错的**：正文渲染的是 `群(0000) → 阿贝尔群(0001)` 这种**带名字**的形式，而失败断言查的是紧凑串 `"0000→0001→0002"` —— 那个串**只出现在统计段**，所以断言**恒假**，与 medium 毫无关系。<br>误判的根因"是因为**上一条 low 断言同样很弱**（只做 `count >= 1`），于是'一个 pass 一个 fail'的组合被我看成了'分级边界错了'"（`11-...md` §11.2）。<br>处理方式才是重点：实现者**没有借机放宽断言**，而是把附录标题改成明确写"**未达正文标准、不作为证据**"，并把断言换成**段落级解析**（正文 high 4 / 非 high 0；附录 medium 1；统计 low 1）—— **测试反而更强**（`11-...md` §11.3）。 |
| **预防机制** | **(a) 断言必须落在真正有区分度的地方**："这里是'哪一段出现了什么'，而不是'某个字符串是否出现过'"（`11-...md` §11.4）。<br>**(b) 结构化断言优先于字符串断言**：解析出结构（段落、分段、分级）再断言各段的**具体内容与计数**。<br>**(c) 过强的断言也要防止"修过头"**：新增断言时必须同时问"它会不会把合法的正确实现判错？"（对照 `11-...md` §10.6 的两个方向都断言）。<br>**(d) 审查者的判断也需要被证据检验**，实现者有条件也有责任用证据反驳（`11-...md` §11.4）。 |

## P12 可观测性缺口 ≠ 正确性缺口

| 项 | 内容 |
|---|---|
| **定义** | 数据本身仍然正确，但"**为什么**"的证据丢了。两者的严重性与修法依据不同（前者是"值得修"，后者是"必须修"）。 |
| **实例** | `10-...md` §11.10.1：`abflow rebuild` 之后 `literature._keys` 与 `relations._quote_check` **全部消失**（原因：`rebuild` 走 `row_from_dict`（过滤未知字段）+ `to_dict()`（只输出 dataclass 字段））。<br>探针实测（`tools/probe_rebuild_diagnostics.py`）：修复前 `literature._keys = None ← 丢了`；修复后相等；并且探针顺带实测 `判重是否仍能命中（靠 doi 兜底）：hit=True key=doi:10.1/probe` —— **这实证了"这是一个可观测性缺口而非正确性缺口"**。<br>报告给出的判据："一个**可重建**的存储，其重建结果的信息量**不应少于**重建前的快照。否则'可重建'就只是'能恢复到一个更差的版本'，而**审计与排障恰恰依赖那些'非必需的'附属字段**。" |
| **预防机制** | **(a) 诊断字段是数据，不是日志**：带下划线前缀的诊断字段必须在序列化/迁移/重建路径上被保留（本项目修复方式：`merged = {非 schema 键} + {规范值}`，**规范值优先**）。<br>**(b) 重建后必须断言信息量守恒**：`test_rebuild_preserves_diagnostic_fields` 同时断言"重建后 `_keys`/`_quote_check` 与重建前相等"**并且**"schema 字段仍被规范化"——"'无损'≠'原样抄回'"（`10-...md` §11.10.1）。<br>**(c) 幂等断言**：连做两次 rebuild，表文件必须**逐字节一致**（`test_rebuild_is_idempotent_and_keeps_tables_valid`）。<br>**(d) 坏事件容错断言**：往事件日志追加"截断的半行 JSON + 一行非 JSON"，rebuild **不抛异常**（`test_rebuild_ignores_corrupt_events_without_dying`）。 |

## P13 恒值计数器（沉默的指标）

| 项 | 内容 |
|---|---|
| **定义** | 一个恒为某个值的计数器，既可能是"正常"，也可能是"**这段代码从不执行**"；没人会注意到它。 |
| **实例** | `10-...md` §10.3 缺陷 #3：搜索失败**立即**置 `done=true`，于是 `attempts` **永远不会累积到 `max_attempts`**（因为第一次失败就 `done` 了，不会再被 claim）→ `_claim` 里的"放弃"分支**永远不会执行** → `outcome` 永远不会是 `gave_up` → `ARunResult.gave_up` **恒为 0**。<br>报告原文："`gave_up` 恒为 0 本身不是错误（可能确实没有请求需要放弃），所以**没有人会注意到它**。但如果有人看这一个指标并推理'我们的重试机制工作得很好，从来没有请求被放弃'，那就是被误导了。**这是一个可观测性陷阱**。" |
| **预防措施** | **(a) 每个"计数型指标"必须有覆盖率证据**：不能只说"它是 0"，要能回答"**它的分支被测试覆盖过吗？**"可判定判据：指标对应的代码分支必须有单元测试（本项目修法是加退避租约 + 用 `attempts >= max_attempts` 才置 `search_failed`，从而使该分支可达）。<br>**(b) 引入"反事实测试"**：断言"当条件满足时该计数**会**增加"（不只是"正常时为 0"）。<br>**(c) 指标必须有"应然值"而不是只有"实然值"**（如 `requests_with_gave_up > 0` 在注入持续失败后必须成立）。 |

## P14 外部契约只能实测，不能推断

| 项 | 内容 |
|---|---|
| **定义** | 字段名、接口行为、召回分布、编码格式的正确性**只能由外部系统回答**；mock/fixture 无法回答"`abst` 是不是一个合法的 select 字段名"。 |
| **实例** | `10-...md` §10.10 结论 ②：**9 条缺陷中有 3 条（#6、#7、#8）为纯离线测试永远抓不到**，而它们**全部由真实联网冒烟抓到**：<br>① #6：字段名的合法性是**外部系统的契约**，只能由服务器判定。<br>② #7：召回率是**真实数据分布**的函数，stub 数据的分布是假的。<br>③ #8：触发源是"**以 `.pdf` 结尾的 URL 返回 12.4 MB 的 HTML**"—— 这种畸形响应只有真实网络会给；**任何 stub 都是人先想到才会去模拟的**。<br>报告结论："**真实联网测试不可替代（3 条）** —— 而它只花了 **70 行代码**。**投入产出比最高**。"<br>另有正面范例：`providers.py` 的模块 docstring 已把"必须实测外部接口"写成原则（"`export.arxiv.org` 实测返回 406、`api.semanticscholar.org` 实测 429，均不纳入实现"），但报告指出"**缺陷 #6 是这条原则的一次漏执行**……这说明原则写在文档里不等于会被执行 —— 需要一个**机制**"。 |
| **预防机制** | **(a) 冒烟脚本独立于 pytest**：它"依赖网络，因此不适合进 pytest 套件。它的作用是回答一个 pytest 回答不了的问题 —— **'线上那条路真的通吗'**"（`10-...md` §10.10 结论 ②引 `smoke_real_provider.py` docstring）。<br>**(b) 脚本负责采集事实，人负责判断归因**：脚本输出"网络相关失败可能是环境/限流，**请人工判断**"（同上）。<br>**(c) 让原则有产物**：报告建议"**每个 provider 的字段清单必须有单字段探测脚本的产物**"（`10-...md` §10.6）。可判定判据：新增外部字段时，CI 必须要求提交一份单字段探测记录。<br>**(d) 修复必须走完三步**："①真实联网发现；②修复并写下实测依据；③**联网复验并同步文档**。**第 ③ 步是最容易被省掉的**"（`10-...md` §10.6 第二轮补充）。 |

## P15 顺序信息被不变量吞掉

| 项 | 内容 |
|---|---|
| **定义** | 为了满足"升序 / 去重"这类不变量，把**有意义的原始顺序**丢了；之后要复原它，只能从别的字段反解。 |
| **实例** | `11-...md` §6.3 的 ⭐ 实现细节：**跳序是从 `origin` 字符串读回的**。因为 `related_relation_ids` 是 schema 要求的**升序字段，跳序在那里已经丢了**。<br>报告原话："要复原'链的顺序'就不能只靠升序数组 —— 这是**为满足一个不变量（升序）而丢掉另一条信息（顺序）**的真实代价。教训：**当不变量要求排序时，如果原始顺序有意义，就必须另找地方存它。**"（同见 `11-...md` §13 第 6 条待决问题） |
| **预防机制** | **(a) 区分"集合"与"序列"**：如果顺序有语义，用序列类型（数组 + 保序约束），不要用"升序集合"。<br>**(b) 如果两种约束都要**，就存两份：一份排序（供集合运算）、一份保序（供重建）。<br>**(c) 反解路径必须有测试**：从 `origin` 字符串读回跳序的做法必须有一条往返测试（round-trip），否则一旦 `origin` 格式改动就静默失效。 |

## P16 修复过头 / 修复漏判引入误判

| 项 | 内容 |
|---|---|
| **定义** | 修复一个"漏判"或"死代码"时，把条件放宽/激活，结果把漏判换成了**误判**。 |
| **实例** | `10-...md` §10.5 缺陷 #5：激活第 3 轮"仅标题匹配"必须**同时补年份容差**，否则"教材第 1 版与第 3 版被合并成一行"。报告给了对照表：<br>"只激活第 3 轮，**不加容差**（只要标题相同就合并）→ 修复了漏合并，**引入了误合并**"；<br>"激活第 3 轮 + **年份容差** → 两者都对：预印本（年份差 1）合并；不同版本（年份差 60）不合并"。<br>测试**同时覆盖两个方向**：`test_literature_dedup_by_title_and_year`（同标题同年份 → 合并）与 `test_literature_dedup_same_title_different_year_is_new`（同标题不同年份 → **不**合并）。报告点评："如果只写第一条，那么'不加容差'的实现也会通过 —— 于是缺陷以另一种形式留下。" |
| **预防机制** | **(a) 修复"漏判"时，必须同时写一条"不该判的时候不判"的用例**（`10-...md` §10.5）。<br>**(b) 为每个修复配套一条"防止用错方式修好"的断言**（`10-...md` §13.6 方法一）：当一个缺陷有**多条修复路径**，而某条路径会"**让断言变绿但让语义变坏**"时，必须**再写一条断言把那条路径堵死**。本项目已有的 3 个实例：`test_precise_results_are_on_topic`（堵死"关掉过滤来消除归零"）、`test_agent_b_still_processes_normal_downloads`（堵死"把跳过条件写得过宽"）、`test_valid_download_statuses_are_accepted`（堵死"受控词表校验写得过严，把合法的 `ok` 也拒了"）。 |

# §3 数学研究相对一般软件工程的九处特殊性

> 从 `08-...md`（定理证明）与本项目（文献关系网络）提炼。每条都写"普通编程怎么做"vs"数学研究必须怎么做"。

| M4 | **数值实验的地位** | 性能数字可以宽松，趋势对就行 | 数值**只能作为交叉验证**，不能替代证明；同一个个例不能推广为定理 | `10-...md` §9.7（"结构不变量全绿 ≠ 知识可用"）；`09-...md` §6.2(1)（"验证通过≠数学正确"） |

## M4 展开：数值只是交叉验证

> ⚠️ **诚实标注**：`08-...md` 中**没有找到**"数值实验只能算交叉验证、不能替代证明"这一**方法论论断**（全文 grep 仅 8 处工程性提及：用 Python 执行做数值验证、`#eval`、`norm_num` 的符号性区分、Lean-Workbook-Plus 的 `disproved 3195 题`，均非等价论断）。**因此本节该条论断的支撑来自本项目实测与 `09-...md`，不来自 `08`。**

本项目内最接近"数值 ≠ 证明"的实测是 **§9.7「结构不变量通过 ≠ 知识质量可用」**（`10-...md` §9.7）：

| 层次 | 事实 | 意义 |
|---|---|---|
| 第一层 | `realrun` 真实数据上抽出的 **40 个概念**里，"肉眼可判断'像一个概念'的极少"：`havior`（`behavior` 被 PDF 连字切断的残片）、`This paper`、`If W`、`when W`、`1 The ratio K/N`、`operator RN in the ﬁgure` … | 产出质量可以**逐字核验地是垃圾** |
| 第二层 | 流水线**每一步都按设计正确工作**：10 行真实文献（真实 DOI）、3 个真实文件（`bytes` 与磁盘实际字节数逐一对上）、40 概念 4 关系如实落库、4 条关系引文在**真实 PDF** 里逐字命中、`counters` 与表行数一致 0 warning、136 条事件、`verify --deep` **错误 0 / 警告 0** | **结构完全自洽** |
| 第三层 | 结论："**结构不变量检查的是'结构自洽'，它不检查、也无法检查'这个概念名是不是一个概念'。**" | 三个绿灯（离线 demo 10/10、离线 129 passed + 联网 8 passed、真实数据 0 错误 0 警告）**叠加仍然不能证明系统有用，只能证明它自洽** |
| 反例 | 假设一个完全不工作的抽取器：把每页第一句话的前 10 个字符当概念名、把这句话当关系 —— 所有格式合法、所有引文**真的**是原文逐字切片、所有 `related_concepts` 都正确派生 → **`verify --deep` 会报 0 错误 0 警告** | "这个假想抽取器的产物与本项目的真实产物，**在不变量层面完全无法区分**" |

**对数学框架的直接含义**：一个"证明检查通过"的绿灯，与"这个证明证明的是我们想证的命题"是两个正交维度。框架必须同时持有：
1. **检查器级验证**（机械可判定：类型检查、子串校验、求解器输出）；
2. **命题级断言**（把"我们要证的命题"写成可判定的陈述，而不是自然语言）；
3. **来源级追溯**（每条前提的来源与页码）。

- [ ] E5 数值结果必须标注"**仅为交叉验证，不构成证明**"（`08-...md`）。

# §6 对下一阶段框架的具体设计约束

> **这是全文最重要的一节。** 每条约束写清：**为什么需要（Why）** / **判据（Criterion，可判定）** / **落地形态（Where）**。
> 编号 `FC-xx`（Framework Constraint）。共 **27 条**，按"数据 / 装配 / 验证 / LLM / 并发 / 领域 / 工程规范"分组。

## 6.1 数据与表示层

### FC-01 三态而非布尔：所有"判定"字段必须是 `True / False / None` + 受控 `reason`

| 项 | 内容 |
|---|---|
| **为什么** | 布尔无法区分"未校验"与"校验失败"，而这两者需要**完全不同的处置**（前者装 OCR / 补数据，后者改引文 / 剔除）。本项目在**四处**（引文、OCR、D 溯源、C 预算）都踩到同一坑（`10-...md` §6.3；`11-...md` §10.7 第 2 条）。 |
| **判据** | ① 代码里不得出现把 `None` 与 `False` 合并的分支（禁止 `if not chk.verified:` 这种写法）；必须用 `is True` / `is False` / `else` 三支（对照 `10-...md` §6.3 的 `agent_b` 代码）。<br>② 所有 `reason` 必须来自**受控枚举**，且枚举中必须至少有一个"未执行"值（如 `not_attempted` / `not_wired` / `no_backend`）。<br>③ 统计输出必须**分三个计数**，不得只报通过率。 |
| **落地形态** | 基础类型 `Tri[T] = Verified(T) | Refuted(reason) | Unknown(reason)`；schema 层校验 `reason ∈ REASONS`；`stats()` 输出 `verified/failed/unknown` 三字段。 |

### FC-02 每个产出带可追溯的代号链（双向）

| 项 | 内容 |
|---|---|
| **为什么** | 数学断言的价值完全取决于"它来自哪里"。本项目建立了 `search_requests.result_lit_ids` ↔ `literature.source_request_ids` 的双向链，并在 `verify` 中检查悬空引用（`10-...md` §3.6.3、§9.7.2）。 |
| **判据** | ① 每个知识实体都有稳定 ID + `origin`（形如 `C:paths:0000:0009->0010->0005`）。<br>② `verify` 能检出**所有**悬空引用（`dangling_lit_ref` 类检查）。<br>③ 任一实体都能回答"**我引用谁**"与"**我被谁引用**"两个问题，且两者互相一致（正向链与反向链的对称性断言）。 |
| **落地形态** | 表结构含 `origin` + `related_*_ids`；`verify` 的 `dangling_*` 检查集；装配期断言"每个外键字段名都有对应的 verify 检查"。 |

### FC-03 跨模块字符串约定必须集中定义 + 装配期断言

| 项 | 内容 |
|---|---|
| **为什么** | `"agent-D"` vs `"D"`、`download.status` 的受控词表、`title:...\|*` 通配键——本项目同族问题出现 **3 次**（`11-...md` §10.6、§10.7 第 5 条；`10-...md` §10.5、§11.10.6）。 |
| **判据** | ① 每个跨模块字符串集合只有**一处定义**（`ROLES` / `SIDE_EFFECTS` / `DOWNLOAD_STATUSES` / `REASONS`），其他地方只能 import。<br>② 框架启动时遍历所有注册对象，断言其字符串字段 ∈ 对应枚举；**不合法即 fail-closed（拒绝启动）**。<br>③ 有一条测试**故意注入非法值**，断言框架拒绝启动（负控）。 |
| **落地形态** | 一个 `constants.py` + 一个 `validate_registry(strict=True)`（本项目原型：`src/abflow/tools/__init__.py:155-173`，注释已写明理由）。 |

### FC-04 输入数据的受控词表必须在 schema 层强制

| 项 | 内容 |
|---|---|
| **为什么** | 本项目最后一条"未闭合的尾巴"就是 `download.status` 的受控词表没进 schema、`verify` 也不交叉检查（`10-...md` §10.10 结论 ⑥末尾），第三轮才补上（§11.10.6）。 |
| **判据** | ① 每个枚举字段在 schema 层有校验，非法值抛错。<br>② 每条"状态 ⟹ 其它字段的约束"都写成**交叉检查**（例：`content_mismatch ⟹ path 非空`；`status=needs_evidence ⟹ waiting_request_ids 非空`；`status=dropped ⟹ notes 非空`）。<br>③ 每条交叉检查都有一条"违反应被拒"的测试。 |
| **落地形态** | `schema.py` 的行校验函数 + `verify` 的交叉检查表（本项目已落地两个正面范例：`11-...md` §4.1 的两条一致性校验、`10-...md` §11.10.6 的 schema 级校验 + 7 条测试）。 |

### FC-05 顺序与集合分离：有语义的顺序必须单独持有

| 项 | 内容 |
|---|---|
| **为什么** | 本项目为满足"升序"不变量，丢掉了关系链的**跳序**，只能从 `origin` 字符串反解（`11-...md` §6.3、§13 第 6 条）。 |
| **判据** | ① 任何"数组字段"必须显式声明它是**集合**（升降序 + 去重）还是**序列**（保序）。<br>② 如果既是集合又需要顺序，字段必须**成对存在**（`related_relation_ids`（升序）+ `chain`（保序））。<br>③ 保序字段必须有 **round-trip 测试**（写→读→相等）。 |
| **落地形态** | schema 里给数组字段加 `x-sort: none|ascending` 标注；`verify` 据此选检查方式。 |

## 6.2 装配与权限层

### FC-06 角色即权限面：装配期断言 + 角色工具数快照

| 项 | 内容 |
|---|---|
| **为什么** | "把'谁能用什么'固化在注册表里，比写在提示词里可靠得多——提示词可以被绕过，注册表不能"（`11-...md` §2.2）。而角色名曾静默失配，导致 D **拿不到自己的工具**（`11-...md` §10.6）。 |
| **判据** | ① 每个角色的工具集是**可枚举、可打印**的事实（本项目实测 `{'A':20,'B':18,'C':23,'D':28}`）。<br>② 每个角色有一个**预期工具名清单**，装配后比对；缺失即 fail-closed。<br>③ 每个工具的 `roles` 是枚举成员（同 FC-03）。<br>④ 有一套测试断言"角色 X **不能**拿到 Y 的工具"（负向权限测试）。 |
| **落地形态** | `build_for_role(role, strict=True)` + `RegistryBuild{loaded, skipped}` + 一个 `expectations.yaml`。 |

### FC-07 工具声明必须完整，`side_effect` 与 `roles` 都是一等公民

| 项 | 内容 |
|---|---|
| **为什么** | `side_effect` 是审批的唯一可信判据（`11-...md` §2.1 ①）；C 的全部工具都是 `read` 这一点，是"让模型自由反复取证"的前提。 |
| **判据** | ① 每个 `ToolSpec` 六件套齐全（`name/summary/params/returns/side_effect/roles`），缺一即拒绝注册。<br>② `side_effect ∈ SIDE_EFFECTS`（装配期断言）。<br>③ `needs_approval(spec) = spec.side_effect in NEEDS_APPROVAL` 是**唯一**的审批判据函数；任何绕过它的路径在评审中视为缺陷。<br>④ 只读工具（`read`/`none`）有一条测试断言"调用后**工作区字节级不变**"。 |
| **落地形态** | `ToolSpec` dataclass + `validate_spec()` + `needs_approval()`；只读工具的不变性测试用目录指纹（hash 树）实现。 |

### FC-08 无工具 / 未接线必须显式失败，不得静默降级为空

| 项 | 内容 |
|---|---|
| **为什么** | 这是本项目最尖锐的缺陷（`11-...md` §10.4 #7）：D 没接上 registry 时走了"无工具"降级分支并**静默返回空**，报告写成"未能取到任何关系表述——这本身就是一个重要事实"。 |
| **判据** | ① 任何 `tools is None` / `registry is None` 的分支必须返回 `ok=False, kind="not_wired"`，**不得返回空数据**。<br>② 有一条测试构造"未接线"场景，断言**返回失败而不是空**。<br>③ 报告生成器遇到"未接线"必须**拒绝生成结论**（而不是写"没有找到"）。 |
| **落地形态** | 统一的 `ToolResult.fail(kind=...)`；把所有"降级为空"的分支在代码评审中列为**禁止模式**（可用静态检查：grep `if .* is None: return \[\]`）。 |

## 6.3 验证与负控层

### FC-09 每个验证门必须配负控

| 项 | 内容 |
|---|---|
| **为什么** | 只有绿灯不能证明门在工作。本项目用**刻意伪造的假引文**证明了 `verify` 真的会抓（`11-...md` §10.6），而 9 条缺陷中 0 条能被 happy-path 抓到（`10-...md` §10.10 结论 ①）。 |
| **判据** | ① 每个验证门（validate / verify / check / gate）在测试里至少有一条**注入已知坏数据并断言报错**的用例。<br>② 每个门同时有**防误伤**用例（好数据必须通过）——两个方向都要（`11-...md` §10.6）。<br>③ CI 里有一条"负控套件"独立可见，且**故意变红**时报错信息明确指出"这是负控，不该红"。 |
| **落地形态** | `tests/negative_controls/` 目录 + CI 步骤；或每个门的测试文件里以 `test_gate_<name>_rejects_*` 命名。 |

### FC-10 验证结果三分档计数，禁止单一通过率

| 项 | 内容 |
|---|---|
| **为什么** | "一个'通过率 80%'的单一数字会掩盖'20% 是失败还是未校验'这个决定性差异"（`10-...md` §6.3）。 |
| **判据** | ① 所有验证器的返回统计必须含 `verified` / `failed` / `unknown` 三个整数。<br>② 报告与 CLI 输出必须同时展示三个数字。<br>③ 有一条测试断言"注入一个无法校验的样本后，`unknown` 增加而 `failed` 不变"。 |
| **落地形态** | `VerifyReport` 的字段设计（对照 `store.py::stats` 的 `quote_verified` / `quote_unverified` / `quote_unknown`）。 |

### FC-11 校验器与写入方共享同一配置来源

| 项 | 内容 |
|---|---|
| **为什么** | 两段式设计里"两个模块各自都对，但它们的假设不同"会产生**假报警**，而"假报警比不校验更糟，因为它会训练人忽略告警"（`10-...md` §11.10.2）。 |
| **判据** | ① 校验器函数的这些参数**不得有默认值**（或有默认值时必须等于"拒绝执行"）。<br>② 启动时断言"复核参数 == 写入参数"。<br>③ 有一条测试：改配置后写入一条边缘样本，断言复核**不报错**（即两侧同步）。 |
| **落地形态** | 一个 `QuotePolicy` 配置对象（而非两个散装参数）；`verify_all(policy=...)` 强制传参。 |

### FC-12 可重建存储的信息量守恒

| 项 | 内容 |
|---|---|
| **为什么** | "一个可重建的存储，其重建结果的信息量不应少于重建前的快照。否则'可重建'就只是'能恢复到一个更差的版本'"（`10-...md` §11.10.1）。 |
| **判据** | ① 重建前后**诊断字段逐字段相等**（本项目断言 `_keys` / `_quote_check` 相等）。<br>② 重建**幂等**：连做两次，表文件逐字节一致。<br>③ 坏事件（截断的半行 JSON、非 JSON 行）不得让重建抛异常。<br>④ 重建后 schema 字段**仍被规范化**（"'无损'≠'原样抄回'"）。 |
| **落地形态** | `rebuild()` 的合并逻辑（规范值优先 + 保留非 schema 键）+ `tests/test_rebuild.py` 三条（本项目已落地，可直接照抄形态）。 |

### FC-13 告警分级必须写在文档里，且允许"已知缺陷"降级

| 项 | 内容 |
|---|---|
| **为什么** | 本项目实测：`verify --deep` 报 1 个 error，但"那不是 bug，是校验器正确工作"——真正的问题是分级语义。若不降级，"**红灯会被训练成背景噪音**"（`11-...md` §10.6）。 |
| **判据** | ① 每条检查有明确级别（`error` / `warning` / `info`），级别写在检查的 docstring 与文档表里。<br>② 级别规则可表述为两句：**"表里已记录的缺陷被重算确认" = warning；"表里记录与重算事实矛盾（谎报）" = error**。<br>③ 两个方向都有测试。 |
| **落地形态** | `Issue(level, table, id, kind, msg)` + 一张"检查 → 级别 → 理由"的表（对照 `11-...md` §10.6 的两行表）。 |

## 6.4 LLM 交互层

### FC-14 LLM 产出必须回验 + 存回原文切片

| 项 | 内容 |
|---|---|
| **为什么** | "提示词里写'不要编造'是**降低概率**，回验是**消除后果**"（`10-...md` §9.7.5）。 |
| **判据** | ① 所有 LLM 给出的引用型字段（`quote`、`evidence`、`cite`）入库前必须经"回到原文找一遍"。<br>② 定位成功后**存回原文的确切切片**（不是模型给的字符串）。<br>③ 定位失败必须**剔除 + 计数**（不是标记后入库）。<br>④ 有一条自检：用**会编引文的假 client** 验证 fail-closed 行为（本项目 `llm.py` 的 `__main__` 块就是这个形态）。 |
| **落地形态** | `_ground_relations()` + `_locate_verbatim()`（本项目已实现，可直接照抄设计意图）。 |

### FC-15 幻觉与"数据缺失"必须可归因分离

| 项 | 内容 |
|---|---|
| **为什么** | 本项目明确拒绝把可疑条目混进去，否则"报告里'校验失败'的数字就会同时包含'模型幻觉'和'页码窗口没给对'两种完全不同的原因，无法归因"（`llm.py::_ground_relations` docstring）。 |
| **判据** | ① 每一类失败有独立的 reason 与独立计数。<br>② 报告能分别回答"多少条是幻觉"、"多少条是页码缺失"、"多少条是无文本层"。 |
| **落地形态** | reason 枚举细分（`quote_not_found` / `not_found_page_unknown` / `no_text_layer` / `empty_quote`）。 |

### FC-16 确定性的部分绝不交给 LLM

| 项 | 内容 |
|---|---|
| **为什么** | 需求原话是"用程序分析关系表"；本项目的 C **没有一处依赖 LLM 判断**，所有需要判断的地方都是确定性评分 + 可逐项打印的中间值（`11-...md` §1.3、§5.1）。 |
| **判据** | ① 每个 LLM 钩子必须有**确定性回退**，且无 API key 时功能降级但不缺失、可测试。<br>② LLM 钩子的启用状态必须**如实报告**（本项目实测报告："路径顺序完全由确定性评分决定"，`11-...md` §5.1）。<br>③ 每个评分函数必须能**逐项打印中间值**（本项目每条路径带 7 项 `score_breakdown`，`11-...md` §5.4）。 |
| **落地形态** | `llm=None` 为默认；`score_breakdown` 结构；报告模板强制含"评分明细"段。 |

### FC-17 上下文预算：压缩 / 剪枝 / spill 三件套必须开

| 项 | 内容 |
|---|---|
| **为什么** | 极简集"**没有 compaction**"，长任务会硬撞上下文上限且**没有任何自动缓解**（`06-...md` §9.2）；200,000 token 会触发截断，Anthropic 因此必须先把计划写进 Memory（`04-...md` §D2 反模式 5）。 |
| **判据** | ① 配置里必须有 compaction 行、工具结果剪枝行（含 `thresholdChars` / `headChars` / `tailChars`）、spill 上限（`maxInlineBytes`）。<br>② 有一条测试：构造一个超大工具结果，断言被剪枝/落盘而非撑爆上下文。 |
| **落地形态** | 对照 `06-...md` §9.4 加固 5 的配置块与 `04-...md` §B1 的数值表。 |

## 6.5 并发与预算层

### FC-18 三维预算 + 深度上限必须同时存在

| 项 | 内容 |
|---|---|
| **为什么** | "只有并发上限 → 无限循环的扇出可以持续启动新任务，永不停止；只有总量上限 → 瞬时可能把配额打爆。"（`04-...md` §B1）。 |
| **判据** | ① 配置文件里同时存在 `maxConcurrent*`（瞬时）、`maxTotal*`（生命周期）、`maxItemsPerCall`（单批）、`maxDepth`（嵌套）四类键，且都非空。<br>② 缺任一类，框架启动即 fail-closed。<br>③ 深度计数**持久化且单调**，有一条测试断言 resume/fork 后深度**不重置**。 |
| **落地形态** | 预算对象（`Budget`）在启动时校验完整性；对照 `04-...md` §B1 的三维表。 |

### FC-19 token 预算是硬约束，重试也计入

| 项 | 内容 |
|---|---|
| **为什么** | "Each retry is another billed provider request"（`04-...md` §B6）；且框架**不能假设**它一定给你 token 预算——DSH 的 Ralph 目前**只有轮次上限**，token 预算是 deferred（`04-...md` §D3 ⑧）。 |
| **判据** | ① 每个子任务有 token 上限与最长轮次，超额即降级或返回当前最好答案（`02-...md` §5 实践建议）。<br>② 重试计入预算（可判定：注入 N 次失败重试后，预算消耗 ≥ N × 单次成本）。<br>③ D 向 A 提问的预算必须**已定值并写进配置**（本项目仍是待决项，`11-...md` §13 第 3 条——这是 P0）。 |
| **落地形态** | `token_meter` + 预算守卫 + 一条"重试也扣预算"的测试。 |

### FC-20 取消：协作式 + 一个共享 signal + 事件配对 + first-wins

| 项 | 内容 |
|---|---|
| **为什么** | 取消都是协作式的，没有通用安全强杀；"不能逐个取消，会漏"（`04-...md` §B5）。 |
| **判据** | ① 一个共享 signal 覆盖所有在飞与**待启动**的子任务。<br>② 终态**先到先得**，不可被重入回调改写。<br>③ **每个 start 事件有且仅有一个 end 事件**（死亡或强杀时合成 `cancelled` 的 end）。<br>④ dispose 幂等。<br>⑤ 取消后**不自动重试**，记录 "unknown outcome"。 |
| **落地形态** | 对照 `04-...md` §B5 的 DSH 五层设计。 |

### FC-21 部分失败语义：子任务可降级，整体绝不谎报成功

| 项 | 内容 |
|---|---|
| **为什么** | DSH 同时实现两种语义并明确区分：脚本内子 agent 失败**降级为 `null`**（脚本知道怎么补偿）；workflow 工具整体失败**绝不返回部分成功**（调用者不知道）（`04-...md` §B6）。 |
| **判据** | ① 编排层必须显式声明"子任务失败 → 降级"还是"整体失败 → 报错"，且该声明写进 API 文档。<br>② 有一条测试：注入一个子任务失败，断言"编排层拿到 null 并继续"，同时断言"最终结果不会被标为成功"。 |
| **落地形态** | 两种 API（`run_best_effort()` / `run_all_or_nothing()`），而不是一个含糊的 `run()`。 |

## 6.6 领域（数学）语义层

### FC-22 数值结果必须标注"仅为交叉验证"

| 项 | 内容 |
|---|---|
| **为什么** | 数学里数值实验不构成证明（`09-...md` §6.2(1) 明确"验证通过 ≠ 数学正确"）；而本项目实测证明了"结构自洽 ≠ 内容正确"（`10-...md` §9.7）与"三个绿灯叠加仍不能证明系统有用"（§9.7.4）。**⚠ 诚实标注：`08-...md` 中未找到"数值只能算交叉验证"的方法论论断**（全文仅 8 处工程性提及），因此本条不引 `08`。 |
| **判据** | ① 任何数值产出在数据结构里带 `evidence_kind ∈ {proof, cross_check, heuristic}` 字段。<br>② 报告模板中 `cross_check` 类结论必须**自动附加**"不构成证明"字样（模板强制，不靠人写）。<br>③ 有一条测试断言"没有 proof 级证据时，结论不得被标为已证明"。 |
| **落地形态** | `evidence_kind` 字段 + 报告模板 + 一条 gate 测试。 |

### FC-23 引用的外部定理必须显式标记为依赖，依赖集可检查闭合

| 项 | 内容 |
|---|---|
| **为什么** | 数学上把假设当公理会静默放大结论范围。`08-...md` §D 给出了**明确的绕过手段清单**：`sorry` / `admit` / 新增 `axiom` / `native_decide`，并指出 `#print axioms` 与 `get_axioms` 是"**审计必备**"、且"**不能只看 exit code**"。并用 **Flyspeck** 说明"过检查器 ≠ 数学正确"：未形式化原始证明（Hales 自述 `cannot assert`）、两个计算部分是 **explicit hypotheses**、常数 c 可依赖堆积且**不声称唯一性**——"**『Flyspeck 完成了』与『Kepler 猜想被完全形式化验证』在严格意义上是两句话**"。本项目对应机制的形态是 `lit_id` + `page_range` + `definition_source_lit_id` + `verify` 的悬空引用检查（`test/test1/DESIGN.md` §1.3、§1.4）。 |
| **判据** | ① 每条数学断言有**依赖集**字段（可枚举）。<br>② `verify` 检查依赖集**闭合性**（每条依赖都必须能追到已入库的来源）。<br>③ "引用了但不在依赖集里"必须能被检出（至少要有审查清单 + 抽检流程）。<br>④ 本项目缺口：**一条关系只能引一篇文献**（`test/test1/DESIGN.md` §0.1 C10）；新框架应支持 `supporting_lit_ids`（`10-...md` §13.1 P0-4 标注 ⚠️ 未完成）。 |
| **落地形态** | `dependencies: list[Dep]`，`Dep = {kind, lit_id, page_range, quote}`；`verify` 的 `dangling_dep` 检查。 |

### FC-24 基准口径是必填字段

| 项 | 内容 |
|---|---|
| **为什么** | 同一个 miniF2F 数字可以是四件不同的事：**97%（=97.5%）= LLM judge 分**、**69% = 论文引用的文献 prover SOTA**、**34.8% = 端到端且与原始非形式题面比对后的精确值**、**40% = 同口径在原始 miniF2F 上的成绩**；同对模型在 two-口径下差 **−13.5 ~ −29.5 点**（`08-...md` §A.5.5、Table 1/Table 2）。本项目内部的同族教训是 `precise` 的判据不能看条数（`10-...md` §10.7）；`09-...md` §6.2(2) 亦明确"报告中出现的 665 / 70% / 114 等数字属于不同工作，**不可互相背书**"。 |
| **判据** | ① 每个评测结果记录含 `benchmark` / `version` / `split` / `k` / `samples` / `uses_retrieval` / `allows_sorry`（或领域等价）/ `decontamination`（去污染声明）/ `date` / `source`。<br>② 缺任一字段的数字**不得进入对外报告**（用一个渲染层 gate 强制）。<br>③ "窄口径 vs 宽口径"的数字**不得直接比较**（用不同口径的字段做 guard）。<br>④ 照抄 `08-...md` 的**三元组规则**：引用任何基准成绩必须同时给 `(pass@k, 基准版本, 去污染声明)`。 |
| **落地形态** | `EvalResult` 结构化记录 + 报告渲染 gate + 三个必填字段（pass@k / 基准版本 / 去污染）。 |

### FC-25 "未证明 / 已证否 / 未搜索"三种否定必须分开

| 项 | 内容 |
|---|---|
| **为什么** | 数学上"未证明"与"已证否"有天壤之别；检索上"库里没有"与"这世上没有"也是两件事。本项目的正面范例是 `cold` 把 `degree==0` 单独归一类"完全孤立"，理由"**'没人研究'和'没人连接'是两件事**"（`11-...md` §5.3(3)）。 |
| **判据** | ① 否定型结论必须带 `negation_kind ∈ {disproved, not_proved, not_searched_here, no_local_evidence}`。<br>② 报告里这四类的计数分开。<br>③ 有一条测试：把"没搜索"样本喂进去，断言不会落入 `disproved`。 |
| **落地形态** | `negation_kind` 字段 + 统计分列 + gate 测试。 |

### FC-26 每个"缺口/结论"必须是可核实判据，不许"感觉"

| 项 | 内容 |
|---|---|
| **为什么** | 本项目 D 的"知识不足"必须是**可核实的判据**（否则 D 会无限向 A 提问），且给出了三条：`a_no_keyword_hit` / `b_low_degree_unverified` / 矛盾（`11-...md` §6.4）。C 的 `gaps` 更是明确区分**否决项 vs 扣分项**，理由是"引文校验全部失败意味着这条候选没有任何可核实的依据——它不该靠其它正向分把净分抬回 medium"（`11-...md` §5.3(4)）。 |
| **判据** | ① 每个"值得研究"的结论必须带**判据 id + 实测值**（不是分数，是事实）。<br>② 存在**否决项**机制：某些信号一旦成立就直接剔除，不参与加权（防止"正向分把明显无效的候选抬回来"）。<br>③ 有一条测试：构造一个"正向分很高但引文全部失败"的候选，断言它被 veto 剔除（本项目实测：改前会判 medium，改后被剔除，`11-...md` §5.3(4)）。 |
| **落地形态** | `criteria: [{id, ok, detail, priority}]` 结构（本项目 `assess` 的实测输出形态，`11-...md` §6.4）；`veto` 列表与 `score` 分离。 |

### FC-27 禁 AI 区（人类专属区）必须显式列出，且带独立的准入门槛

### FC-28 候选 · 批量文本改写工具必须先划出**语法边界**，再谈"看起来像什么"

**事情**：`lint` 规则 R009（注释/文档串里不许有成对 `**`）我踩了五次，于是写了个批量替换脚本
`temp/_r009_strip.py`，判据是"这一行里有没有 `**x**`"。它把一行**代码**改坏了：

```python
-        S.Task(**{**row, "error": None}).validate()
+        S.Task({row, "error": None}).validate()
```

**为什么没被立刻发现**：所有我跑过的判据都是"单文件/单族"的，没跑到那一行；
它最后由**全量门**撞出来 —— 而且表现为 `pytest` 的 **collection error**（整个套件一条都没跑），
门以 `exit=2` 结束。也就是说：**一次静默的批量改写，代价是整趟全量门作废**。

**判据**：凡是要按"文本形态"改源码的工具，先划**语法**边界再动手 ——
注释与文档串用 `tokenize`（`COMMENT` token + `ast` 里作为"第一条表达式语句"的字符串常量）定位，
代码里的 `**`（解包、幂运算）一个都不碰；改完先 `ast.parse` 自检，语法坏了就不写回。
本仓的落地版在 `temp/_r009_strip.py`（重写后幂等自检 0 处、只作用于注释与文档串）。

### FC-29 候选 · "上游改了名，下游的引用判据必然报警" —— 报警是对的，出口要另外造

**事情**：`webui.py`（1268 行）拆成 `webui/` 包之后，`draft/73–80` 里按旧文件写死行号的
引用一次报出 **72 条**"文件不存在"。判据没有错（那些坐标在盘上确实指不到东西），
