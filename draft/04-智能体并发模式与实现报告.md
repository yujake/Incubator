## 0. 术语对齐与报告边界

在讨论「并发」之前必须先拆开三个经常被混为一谈的词。混用它们是绝大多数并发事故的认知根源：

| 术语 | 定义 | 典型载体 | 是否真同时执行 |
|---|---|---|---|
| **并发 Concurrency** | 多个任务在**逻辑上**同时推进（交错执行、非阻塞） | async/await、事件循环、协程 | 否（单核时间片） |
| **并行 Parallelism** | 多个任务在**物理上**同时执行 | 多线程、多进程、多机 | 是 |
| **并行度 Parallelism Degree / 并发上限** | 允许同时在飞的**任务数量上限** | semaphore、worker pool、`maxConcurrentAgents` | —— 是旋钮不是模型 |

Prefect 官方文档对这个区分写得很直白：并发是「交错、非阻塞」，并行是「真正同时」[29]。本报告用「并发」统称两者，但在具体模式中会注明它实际落在哪一侧。

**另一个必须前置的边界**：智能体并发和传统程序并发有一个本质差异——**每个并发单元都是一个带独立上下文窗口的 LLM 调用**。这带来三个传统并发不存在的新约束：

1. **每个并发单元有自己的 token 账单**，并发 N 路 ≈ N 倍输入 token 成本；
2. **每个并发单元有独立的上下文窗口**，因此「共享状态」不能靠共享内存，只能靠显式传递或外部存储；
3. **并发单元的数量直接撞到 provider 的 RPM/TPM 配额**，而不是撞到 CPU。

Anthropic 在官方工程博客中给出的量化结论是：普通 agent 约消耗 chat 的 **4 倍** token，而多智能体系统约消耗 chat 的 **15 倍** token [1]。这个 15× 是本报告反复引用的成本基准。

### A1. 并行扇出 / 扇入（Fan-out / Fan-in，Map-Reduce over agents）

**人话解释**
一个任务拆成 N 份，N 个子智能体同时干，全部干完后由一个聚合者把 N 份结果揉成一份。这是「人多好办事」的最直接翻译，也是目前生产环境里出现频率最高的多智能体并发模式。

**图示**

```
                    ┌──────────────┐
                    │  Orchestrator│
                    │   (Lead)     │
                    └──────┬───────┘
              ┌────────────┼────────────┐        ← FAN-OUT
              ▼            ▼            ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │Worker 1 │  │Worker 2 │  │Worker N │   （各自独立 context window）
        └────┬────┘  └────┬────┘  └────┬────┘
             │            │            │
             └────────────┼────────────┘        ← FAN-IN（barrier：等全部完成）
                          ▼
                   ┌─────────────┐
                   │  Reducer /  │
                   │  Synthesizer│
                   └─────────────┘
```

**实现要点**
- **扇出端**：把任务切成互不重叠的子任务。Anthropic 明确强调：每个子智能体需要「一个目标、一个输出格式、工具与来源指引、清晰的任务边界」，否则会重复劳动或留缺口 [1]。
- **并发表达**：
  - Anthropic：Lead agent 直接**并行拉起 3–5 个 subagent**，subagent 内部再用 3+ 工具并行调用 [1]。
  - OpenAI Agents SDK：官方 cookbook 给出 `asyncio.gather(...)` 同时跑多个 agent 的范式 [4]。
  - DSH：`parallel(thunks)` hook —— 「并发运行零参函数并 **await ALL of them**（这是一个 barrier）」[DSH `dsh-tool-workflow/lib/types/index.js`:101]。
  - LangGraph：`Send(node, state)` 从条件边返回，用于 map-reduce 风格的动态扇出 [7][8]。
- **扇入端（聚合）**：必须有 reducer/合成者。LangGraph 的做法是用 `Annotated[list, operator.add]` 这类 **reducer** 声明「多个并行分支写同一个 key 时怎么合并」[7]。
- **上下文隔离**：DSH 的 `spawn` 后端「子智能体以空对话开始，任务提示必须能独立成立」，**默认不继承父上下文**[DSH `dsh-subagent-spawn-in-process/README.md`]。

**适用场景**
- 广度优先、子任务相互独立：多源检索、多文件审计、多方案调研、批量翻译/分类。
- Anthropic 的判据：多智能体在「重并行化、信息量超出单窗口、需对接大量复杂工具」的任务上最优；**大多数编码任务的真正可并行部分比研究任务少**[1]。

**坑**
- **无上限扇出**。Anthropic 自述早期版本「为简单查询生成了 50 个子智能体」[1]。这是扇出模式的头号反模式：扇出数必须由**查询复杂度规则**约束。Anthropic 的经验值是：简单事实查找 1 个 agent / 3–10 次工具调用；直接比较 2–4 个 subagent / 各 10–15 次调用；复杂研究 >10 个 subagent 且职责清晰划分 [1]。
- **扇入是 barrier，慢任务拖死全局**。扇出 N 路的总延迟 = `max(所有子任务延迟)`，木桶效应被放大。
- **重复劳动**。Anthropic 观察到「一个 subagent 研究 2021 汽车芯片危机，另外两个重复研究 2025 供应链」[1]——任务描述不够具体就会撞车。
- **成本线性放大**。N 路扇出 ≈ N 份 input token + 每个子任务自己的多轮 tool call。乘上 15× 基准，很容易失控。
- **子智能体结果通过 orchestrator 中转导致信息损耗**（Anthropic 称之为 "game of telephone"）。官方解法：让 subagent 把产物**直接写到文件系统/外部系统**，只把轻量引用回传给协调者 [1]。

### A2. 流水线并行（Pipeline / Streaming Stages，无 barrier）

**人话解释**
传统并行是「所有 item 完成 stage1 → 才开始 stage2」（barrier）。流水线并行是**每个 item 自己独立穿过所有 stage**，item A 可以在 stage3 时 item B 还在 stage1。像工厂流水线，而不是分批质检。

**图示**

```
【Barrier 式并行】—— 全局屏障，最慢的 item 决定一切
items:  A(fast) B(slow) C(fast) D(fast)
stage1  ████████████████            ← 等 B
stage2                  ████
stage3                      ████
                      ↑ 空转：A/C/D 在 stage1 完成后一直等 B

【Pipeline 无 barrier】—— 各 item 独立流动
stage1  A██  B████████  C██  D██
stage2     A██      B██████   C██  D██
stage3        A██        B██████   ...
                      ↑ 无空转，吞吐 = 1/max(stage_time)
```

**实现要点**
- DSH 的 `pipeline(items, ...stages)` 是这一模式的教科书式实现，其工具描述原文：
  > `pipeline(items, ...stages): Promise<any[]>` —— run each item through the stages independently with **NO barrier between stages**（prefer this for multi-stage work）。Each stage receives `(prev, item, index)`。An ordinary stage throw drops that **ITEM** to `null` and skips its remaining stages。
  > —— `dsh-tool-workflow/lib/types/index.js`:100

  注意这里有两个设计决策：**无 barrier**，以及**失败是 item 级隔离**（单个 item 抛错只把该 item 变 `null`，不杀死整条流水线）。
- 对照 `parallel(thunks)`：同一文件的 :101 行明确写着 `parallel` 是 **a barrier; use only when a stage genuinely needs every prior result together**。DSH 把这个权衡直接写进了给模型看的工具契约里。
- 通用工程实现：每个 stage 是一个 worker 池，stage 之间用有界队列连接；队列满产生**背压**（见 A4）。

**适用场景**
- 多阶段、每阶段耗时不均：抓取 → 清洗 → LLM 抽取 → 校验 → 入库。
- item 数量大、希望尽早出结果（流式下游）。
- DSH 明确推荐：multi-stage work 优先用 `pipeline` 而不是 `parallel`。

**坑**
- **误用 barrier 导致流水线停顿**（pipeline stall）。这是本报告要重点点名的反模式：只要中间插一个「等全部完成」，整条流水线的吞吐就退化为 `Σ(最慢 item 的各 stage)`。
- **单 item 失败语义要明确**。DSH 选择「drop to null」；但如果你的下游 reducer 不处理 `null`，就会静默丢数据。DSH 官方建议 `.filter(Boolean)`。
- **背压缺失会 OOM**。无界队列 + 快速 producer + 慢 consumer = 内存爆炸。
- **阶段间状态污染**。同一 stage worker 被复用时要小心上一 item 的残留状态（DSH 在 worker-thread 引擎里用「每次 run 一个全新 worker thread，无池化、无跨 run 脚本缓存」来规避，代价是每个 run 都要付线程启动费 [DSH `dsh-workflow-worker-thread/README.md` Known Limitations]）。

### A3. DAG 编排（有依赖的并行）

**人话解释**
把任务画成有向无环图，箭头表示「必须先做」。没有依赖关系的节点自动并行，有依赖的等上游。调度器做拓扑排序，**依赖一满足就立刻调度**（而不是等整层完成）。

**图示**

```
            ┌──────┐
            │  A   │
            └──┬───┘
        ┌──────┼──────┐
        ▼      ▼      ▼
     ┌────┐ ┌────┐ ┌────┐
     │ B  │ │ C  │ │ D  │   ← B/C/D 无相互依赖 ⇒ 三者并行
     └──┬─┘ └──┬─┘ └────┘
        └──────┤
               ▼
           ┌──────┐
           │  E   │            ← 等 B 和 C 都完成（join）
           └──────┘

关键：E 只需等 B、C；D 慢不影响 E。这是 DAG 优于「分层 barrier」的地方。
```

**实现要点**
- **Airflow**：调度器按 DAG 依赖把 TaskInstance 交给 executor；并发上限由 `[core] parallelism`（实例级）、`max_active_tasks_per_dag`（单 DAG 级）、`max_active_runs_per_dag` 控制；动态任务映射（`task.expand()`）让任务数在运行时由上游输出决定 [27][28]。
- **LangGraph**：用**超步（super-step）** 语义——「同一超步内运行的节点是并行的一部分；任一节点有多条出边时，所有目标节点作为下一超步的一部分**并行**执行」[7]。注意 LangGraph 是 **BSP 屏障模型**：超步之间是屏障，超步内部才是并行。这与「依赖满足即调度」的经典 DAG 有细微差别。
- **DSH 的 `pipeline` 是严格的 DAG 特例**（线性链）；DSH 没有暴露通用的 DAG 编排原语 —— 模型要写任意 DAG，必须自己在 `workflow` 脚本里用 `await` 手动编排依赖。**⚠ DSH 是否另有 DAG 引擎，本次未获取到证据。**
- **Google ADK**：用 `SequentialAgent` / `ParallelAgent` / `LoopAgent` 三种**确定性模板**组合出工作流；`ParallelAgent` 调 `run_async()` 时同时启动每个子 agent [19][20]。
- **Microsoft Agent Framework**：用 `WorkflowBuilder` 构建类型化图，`ConcurrentBuilder` / `SequentialBuilder` / `MagenticBuilder` 提供预置拓扑 [12]。

**适用场景**
- 任务间依赖关系明确且可静态或半静态表达：RAG 索引管线、CI 流水线、多阶段数据分析。
- 需要「尽早开始」而非「按层推进」的优化场景。

**坑**
- **DAG 内的 join 是隐藏 barrier**。E 等 B 和 C 是必要的，但如果误把「同层全部完成」当成 join 条件，就退化成 barrier。
- **并行写共享状态是硬错误**。LangGraph 对「多个并行分支写同一个没有 reducer 的 key」直接抛 `INVALID_CONCURRENT_GRAPH_UPDATE` [8]。这是唯一被主流框架写成**显式错误**的并发问题，值得警惕。
- **动态 DAG 的惰性代理陷阱**。Airflow 的 `task.expand()` 下游拿到的是 `LazySelectSequence`，直接 `print` 只显示 `[15 items]`，`list(...)` 会一次性拉全部上游值造成性能问题 [27]。
- **拓扑排序的死锁检测**。动态生成节点时若不小心形成环，运行期才暴露。
- **不确定性破坏重放**。Temporal 要求 workflow 代码确定：`Date.now()`、随机数、未包在 Activity 里的网络调用都会破坏重放确定性 [24]。

### A4. 工作池 / Worker Pool（任务队列 + 固定并发上限）

**人话解释**
不是「一次全放出去」，而是「挂一个队列 + 固定数量的工人」。工人满了新任务就排队等着，这就是**背压**。

**图示**

```
 producer ──► ┌─────────────────────────┐
              │   Bounded Queue (上限 K)│  ← 队列满 ⇒ producer 阻塞/拒绝（背压）
              └───────────┬─────────────┘
                          │ dispatch
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   ┌─────────┐      ┌─────────┐      ┌─────────┐
   │ Worker1 │      │ Worker2 │ ...  │ WorkerM │   ← M = 并发上限（semaphore）
   └─────────┘      └─────────┘      └─────────┘
        │                 │                 │
        └─────────────────┴─────────────────┘
                          ▼
                    results / done
```

**实现要点**
- **DSH `dsh-jobs-local` 用的是「败者即拒」而非排队**，这一点很值得学：
  > `maxConcurrentJobsPerOwner`（默认 **10**）：Maximum `running` plus `stopping` jobs per exact owner, or in the shared unowned bucket。
  > At capacity, `start()` **fails before the producer runs**, with an error that names the limit and tells the agent to kill an unneeded job, wait for it to finish, and retry — **the registry neither queues nor preempts**。
  > —— `dsh-jobs-local/README.md`

  即：**fail-closed 的准入控制**。`start()` 在调用 producer 之前就检查 controller service、spec 合法性、live ownership、容量，拒绝时「不留 job id，也不留执行资源」。
- **DSH 工作流引擎的三层上限**（`dsh-workflow-worker-thread/README.md` 配置表）：

  | 字段 | 默认 | 含义 |
  |---|---|---|
  | `maxConcurrentAgents` | `0` | `agent()` 并发上限；**`0` 时解析为 `min(16, max(1, availableParallelism() - 2))`**（实测源码 `dsh-workflow-worker-thread/lib/index.js`:883） |
  | `maxTotalAgents` | `1000` | 一次 run 允许启动的 `agent()` 总数——**runaway-loop 兜底** |
  | `maxItemsPerCall` | `4096` | 单次 `parallel()`/`pipeline()` 接受的 item 数 |
  | `syncTimeoutMs` | `5000` | 脚本初始同步片的 VM 超时 |
  | `disposeGraceMs` | `5000` | 强制结清与 worker 终止的界限 |

  这是一份非常干净的「并发预算」设计：**瞬时并发（maxConcurrentAgents）× 总量（maxTotalAgents）× 单批规模（maxItemsPerCall）** 三个维度分别设限。
- **Airflow**：`parallelism` = 实例级并发 task 上限；`max_active_tasks_per_dag` = 单 DAG 上限 [28]。
- **Prefect**：同步调用 task 默认在主线程阻塞；**只有 `.submit()` / `.map()` 才交给 task runner** 并发执行；默认 `ThreadPoolTaskRunner`，CPU 密集用 `ProcessPoolTaskRunner`，分布式用 `DaskTaskRunner` / `RayTaskRunner` [29][30]。

**适用场景**
- 任务数量远大于合理并发度（批量处理几百个文件）。
- 需要保护下游稀缺资源（provider 速率配额、数据库连接、磁盘 IO）。
- 需要「有界等待」而非「无界堆压」。

**⭐ 量化证据：无协调并发的真实失败率（HiveMind 论文，arXiv:2604.17111）**

这是本次调研中**最有说服力的并发实证**：

- **动机事故**：11 个并行 agent 中 **3 个**因连接重置与 HTTP 502 死亡 —— **27% 失败率**，而 API 的总容量其实**足够串行服务全部 11 个**。即：**并发把「容量足够」变成了「失败」。**
- **评测结果**（7 个场景、5–50 并发 agent）：

  | 指标 | 无协调 | HiveMind |
  |---|---|---|
  | 争用下失败率 | **72–100%** | **0–18%** |
  | 浪费的计算 | 基准 | **消除 48–100%** |

- **实现方式**：用**零改动的 HTTP 代理**把五个 OS 风格原语（admission control、rate-limit tracking、AIMD 背压 + 熔断、token 预算、优先级队列）叠加到 agent 请求路径上；代理额外开销 **<3ms**。
- **最反直觉的结论**：消融实验显示，**最关键的单一原语是「透明重试」，而不是准入控制**；但**原语组合起来效果最好**。 [46]

→ **推论：不要只上「并发上限」这一个旋钮。准入控制、重试、预算、优先级需要组合使用。**

**⭐ 队列长度的数学（Google SRE 第 22 章）**

「有界队列」不等于「合理队列」：
> 队列长度 = 线程数的 **10 倍**、单请求处理 **100ms** 时，一个请求要 **1.1 秒**才被处理完 —— **绝大部分时间花在排队**。

SRE 的建议是：**队列相对线程池保持在 50% 以下，宁可早拒绝（fail fast）**。并建议把 FIFO 改成 **LIFO 或 CoDel**，直接丢弃「用户早已刷新、结果已无价值」的请求 [47]。

→ 这与 DSH 选择「**neither queues nor preempts**」（超额直接 fail-closed 拒绝）是同一个判断：**排队会把过载隐藏成延迟，而延迟会摧毁用户体验。**

**坑**
- **忘了 `.submit()` 就退化成串行**。Prefect 的默认行为是最常见的「以为并发了其实没有」事故 [29]。
- **无界队列 = 没有背压**。队列上限必须显式设置。
- **队列开太大 = 尾延迟爆炸**（见上 SRE 的 10× 数字）[47]。
- **容量泄漏**。DSH 文档明确点出这个坑：「A producer cancel that returns without settling `done` stays indistinguishable from a slow stop and **can stall teardown while holding one capacity slot**」——一个静默失效的 cancel 会永久占用一个并发槽位 [DSH `dsh-jobs-local/README.md` Known Limitations]。
- **队列 vs 拒绝的语义选择**。排队会掩盖过载（延迟无限增长），拒绝会让上层看到真实压力。DSH 选了拒绝 + 明确的错误信息引导模型「kill 一个不需要的 job 再重试」。三种主流做法各有取舍：**排队**（隐藏过载）、**拒绝**（暴露压力，DSH）、**降级/丢最旧**（LIFO/CoDel，SRE 推荐给交互式负载）[47]。
- **线程池受 GIL 限制**（见 A9）。

### A5. 多智能体同时共享同一工作区（并发写冲突）

**人话解释**
多个 agent 同时在同一个目录里读写文件。这是最容易出事、也最少被框架保护的一种并发 —— 因为文件系统本身不是为多写者设计的。

**图示**

```
【危险：共享工作区，无保护】
  Agent A ──read f──► [old] ──modify──► write f ═══╗
                                                    ╠══► 谁后写谁赢（lost update）
  Agent B ──read f──► [old] ──modify──► write f ═══╝     A 的修改消失

【隔离方案对比】
  (a) git worktree      每个 agent 一个独立工作树，物理隔离，最后 merge
        main ──┬── worktree-A (branch a)
               ├── worktree-B (branch b)
               └── worktree-C (branch c)        ← 需要 merge 阶段（会冲突）

  (b) shadow workspace  每个 agent 私有影子副本，验证通过后提交回主工作区
  (c) 文件锁 / 乐观锁    同一份文件，靠锁或版本号串行化
  (d) CRDT              同一份逻辑文档，天然可交换合并，无需协调
```

**实现要点**
- **物理隔离（推荐默认）**：
  - **git worktree**：`git worktree add` 让同一仓库的多个分支各自检出到独立目录，各 agent 工作在自己的工作树里 [37]。社区已有专门讨论「并行 AI 编码 agent 用 git worktree」的工程文 [42]。
  - **shadow workspace（Cursor 的实现，有实测数据）**：把 AI 的编辑应用到一个**隐藏的 Electron 窗口**（同目录、独立 TextModel/LSP 状态），从而不污染用户的编辑 [49]。其代价与限制写得非常直白：
    - **内存开销约 2×**；靠限定扩展、**空闲 15 分钟自动杀掉**、opt-in 来缓解。
    - 因为**不能给每个 AI 各开一个窗口**，他们利用「AI 可被无限期暂停而不自知」的特性**交错**多个 AI 的编辑序列——作者自己类比为 **CPU 时间片**。
    - 想做**可运行**隔离时发现：`cp -r` 太慢（要带上 `node_modules`/`venv`/`target`）；macOS 的 `cp -c`（clonefile）对一个中型 monorepo 也要 **45 秒**；硬链接/软链接有误改真实文件的风险；理想方案是内核级文件夹代理（Linux 用 FUSE），但 **macOS/Windows 无法分发内核扩展**。
    - 另一个坑：`rust-analyzer` 必须让代码**落盘**才能出 lint，所以**影子工作区不支持 Rust 的 LSP 可用性** [49]。
      → **重要教训：隔离方案的能力边界由下游工具决定，不由隔离本身决定。**
- **同进程内的原子写**：DSH 的 `dsh-atomic-write` 是一个很具体的实现参考：
  > Zero-dependency atomic file replacement: **exclusive-create random-suffix temp + rename** carrying the caller-stated permissions（`writeFileAtomic`）
  > Its **writer lock serializes read-modify-write cycles across processes** so concurrent writers cannot overwrite one another with stale state。
  > —— `dsh-atomic-write/package.json` + `README.md`

  两个要点：**temp + rename 保证不暴露半写内容**；**writer lock 把 read-modify-write 跨进程串行化**，这正是消解 lost update 的标准手段。注意它明确声明「does not call `fsync`」，即不提供崩溃持久性保证。
- **乐观锁**：读时带版本号，写时校验版本，冲突则重试。适合冲突概率低的场景。
- **悲观锁**：直接对文件加排他锁。适合冲突概率高但粒度粗的场景（如 DSH 的 writer lock）。
  ⚠ **悲观锁在 agent 场景有个致命特性**：如果锁持有跨越一次 **30 秒的 LLM 调用**，整条流水线就被串行化了。**锁的持有时长必须短于最慢的 I/O，否则并发度归零。**
- **CRDT**：Conflict-free Replicated Data Type，通过数学上保证可交换的合并函数实现无协调收敛。Shapiro 等的 CRDT 综述（INRIA RR-7506）是奠基文献 [41][52]。⚠ CRDT 用于 agent 文本/代码协作的实际工程案例，本次未取得权威证据。
- **DSH 的隔离哲学**：**默认不共享上下文**。`spawn` 后端「子智能体以空对话开始」；`fork` 后端「用父的已完成轮次做种子……种子是一次性快照：之后的父轮次永远不到达子」**默认隔离** [DSH `dsh-subagent-spawn-in-process` / `dsh-subagent-fork-in-process` README]。

**⚠ 一条必须澄清的文献问题**：任务书中提到的论文 **"Working trees, not shared branches" 经核查无法验证存在**。搜索引擎把该标题指向 `arXiv:2609.00252`，而该文实际标题是 *Spec-Driven Development for Agentic Software Engineering*，与该说法无关。**本报告不引用该不存在的论文。**

**适用场景**
- 并行的代码修改 → git worktree / shadow workspace。
- 多个 agent 更新同一份结构化数据 → 乐观锁 + 版本号。
- 配置/状态文件的多写者 → temp+rename + 文件锁。
- 多副本弱一致协作（离线编辑） → CRDT。

**坑**
- **lost update（覆盖写）是最常见的静默数据损坏**。无保护的多写者场景下，它不报错，只是丢数据。
- **⚠ 隔离方案本身也会有 bug——真实事故**：Claude Code 仓库有 issue 记录 **worktree 隔离失效**：
  - `#83311`：**并行 worktree agent 会互相提交到对方分支，并改动主工作树（stash/HEAD），且在一个 batch 内行为不一致**。
  - `#83000`：worktree 被错误地 root 到**兄弟仓库**，且 Bash 与 PowerShell 两个工具下**边界执行不一致**。

  → **教训：隔离机制的实现正确性必须被验证，不能假设「用了 worktree 就安全」。** ⚠ github.com 在本环境被网络层拒绝，这两个 issue 仅能从搜索索引确认标题与编号，**未逐字读取正文**，引用时请自行核对 [50][51]。
- **文件锁的粒度与死锁**。粗粒度锁降低并发度；多把锁的获取顺序不一致会死锁。
- **git worktree 的 merge 阶段是新的串行瓶颈**，且必然产生冲突，需要额外的解决者（人或 agent）。
- **隔离的成本可能被低估**。Cursor 的实测：`cp -c`（clonefile）对中型 monorepo **45 秒**；影子工作区**内存 ×2**；`rust-analyzer` 完全不可用 [49]。
- **DSH 明确标注的跨进程限制**：
  > **Process-local residency** — the Activation inbox and ownership graph **do not coordinate two harness processes**; concurrent access to one persistence store needs a durable mailbox and cross-process lease protocol。
  > —— `dsh-subagent/README.md` Known Limitations

  也就是说，**DSH 的子智能体并发在单进程内成立，跨进程共享同一持久化存储尚未解决**。这是一个诚实且重要的边界。
- **沙箱是并发下的权限边界**。DSH 在 Windows 上用 `dsh-sandbox-windows-acl`（ACL 实现）划权限；本会话中父智能体执行 `dsh --profile web --dump-config` 时，DSH 需要写 `C:\Users\ysc20\.dsh\profiles\web\cordis.yml`，被沙箱以 **EPERM** 拒绝（工作区为 `D:\Incubator`）。这说明**并发/多实例场景下「工作区边界」是硬约束，不会因为你并发就放宽**。
- **半写文件**。不做 temp+rename 的写操作，在并发读时可能被读到半截内容。

### A6. 子智能体嵌套并发（Hierarchical / Recursive Fan-out）

**人话解释**
子智能体自己也能再派子智能体，形成一棵并发树。树形并发的核心问题是：**并发预算必须逐层衰减，否则指数爆炸**。

**图示**

```
深度 0        ┌─────────────┐
              │ Root Agent  │  预算 B
              └──────┬──────┘
         ┌───────────┼───────────┐
深度 1   ▼           ▼           ▼
      ┌─────┐    ┌─────┐    ┌─────┐
      │ C1  │    │ C2  │    │ C3  │   预算 B-1（每层递减）
      └──┬──┘    └─────┘    └──┬──┘
    ┌────┼────┐                │
深度 2 ▼   ▼   ▼                ▼
    ┌──┐┌──┐┌──┐            ┌─────┐
    │G1││G2││G3│            │ G4  │      预算 B-2
    └──┘└──┘└──┘            └─────┘
    ↑ 若 maxDepth=3 且不衰减，第 3 层可达 3^3=27 个并发

⚠ 若每层扇出 F、深度 D、总 agent 数 = F^D —— 指数爆炸
```

**实现要点**
- **DSH 的 `maxDepth`**：
  > `maxDepth` | `3` | Absolute delegation-depth cap（`0` forbids delegation）；`'provider-managed'` sends no cap to an out-of-process provider
  > —— `dsh-tool-subagent/README.md` 配置表

  「the tool stays visible at the cap — each attempted start **checks the calling agent's current depth** and rejects with an errored result」。即**工具一直可见，靠运行期检查拒绝**，而不是隐藏工具。
- **深度计数的单调性设计**（DSH `dsh-subagent/lib/types/depth.js`，逐字实证）：
  > The persisted session header is **authoritative and monotone**: runtime `AgentOptions.subagentDepth` may **DEEPEN** the count but can never **lower** it — a resumed child arrives with fresh options, and counting it from zero would let it delegate as if it were top-level。
  > `return Math.max(agent.session.header.delegationDepth ?? 0, runtime ?? 0);`

  这是一个极其重要的防绕过设计：**深度记在持久化 session header 里，运行期只能加深不能降低**。否则「resume 一个子智能体」就能把它洗成顶层 agent，递归上限形同虚设。
- **DSH 的总量兜底**：`maxTotalAgents`（默认 1000）是「**runaway-loop backstop**」——不管树长什么样，单次 run 的 agent 总数封顶 [DSH `dsh-workflow-worker-thread/README.md`]。
- **Anthropic 的层级实践**：Lead agent → subagents，官方明确说 Lead **并行拉起 3–5 个 subagent** 而非串行 [1]。但注意 Anthropic 也承认：
  > Currently, our lead agents **execute subagents synchronously**, waiting for each set of subagents to complete before proceeding. This simplifies coordination, but creates bottlenecks… the entire system can be **blocked while waiting for a single subagent to finish searching**。
  > —— [1]

  即 Anthropic 的生产系统实际上是**「一层并行 + 层间串行」**，嵌套并发尚未做到全异步。
- **Temporal 的层级上限**（真实数字）：默认最多 **2,000** 个未完成 Child Workflow；单个 parent 建议不超过约 **1,000** 个子工作流 [25]。

**适用场景**
- 任务可以自然递归分解：大规模调研、跨仓库重构、多级子问题求解。
- 需要「局部自治」——子团队自己决定怎么再分工。

**坑**
- **指数爆炸**。F 路扇出 × D 层 = `F^D`。必须有**独立的深度上限 + 总量上限**两道闸。
- **深度逃逸**。resume / fork 一个子智能体时若重新计数深度，递归上限就被绕过。DSH 的 `Math.max(header, runtime)` 是标准答案。
- **预算不衰减**。每层都用同一个并发上限，总量仍是 `F^D`。DSH 用 `maxTotalAgents` 全局封顶来解决。
- **错误传播与取消传播**。取消一个中间节点，它下面整棵子树怎么办？DSH 的做法是：`cancel()` **aborts the one signal shared by every pending and published child**；worker 被杀时「synthesizes any missing end as cancelled — every forwarded `workflow/agent-start` is paired exactly once」[DSH `dsh-workflow-worker-thread/README.md`]。
- **路由/模型选择的继承**。DSH 记录了一个真实的坑：改变 route 却不显式指定 effort 时，要**清掉继承来的 route-owned effort**，否则会用错推理档位 [DSH `dsh-subagent/README.md`]。

### A7. Actor 模型 / 消息驱动并发

**人话解释**
每个 agent 是一个 actor：有**私有状态**、**一个邮箱**、只通过**发消息**通信。Actor 之间不共享内存，因此天然没有数据竞争。Erlang/Akka 的思路。

**图示**

```
   ┌────────────┐  msg   ┌────────────┐  msg   ┌────────────┐
   │  Actor A   │───────►│  Actor B   │───────►│  Actor C   │
   │ ┌────────┐ │        │ ┌────────┐ │        │ ┌────────┐ │
   │ │ Mailbox│ │        │ │ Mailbox│ │        │ │ Mailbox│ │
   │ └────────┘ │        │ └────────┘ │        │ └────────┘ │
   │ [private   │        │ [private   │        │ [private   │
   │  state]    │        │  state]    │        │  state]    │
   └─────┬──────┘        └─────┬──────┘        └─────┬──────┘
         │                     │                     │
         └─────────┬───────────┴─────────┬───────────┘
                   ▼                     ▼
            ┌─────────────┐       ┌─────────────┐
            │ Supervisor  │──restart──► 失败的子 actor
            └─────────────┘
        「let it crash」+ supervision tree
```

**实现要点**
- **AutoGen v0.4+ 是真正的 actor 运行时**：`autogen_core.SingleThreadedAgentRuntime` 以 asyncio 单线程事件驱动，通过 `publish_message` + `TopicId`/`TypeSubscription` 做发布/订阅路由；分布式版是 `GrpcWorkerAgentRuntime` [11]。运行时内部有 `_process_publish(self, message_envelope: PublishMessageEnvelope)` 这样的消息处理入口 [11]。
- **Erlang/OTP 的 supervision tree**：监督者按策略（one_for_one / one_for_all / rest_for_one）重启失败的子进程，配合「let it crash」哲学 [38]。
- **DSH 的 actor 味道设计**：
  - **邮箱**：`dsh-subagent` 有 `inbox.ts`（"Activation-local Queue and Steer admission plus the synchronous closing cutoff"）。
  - **两种投递语义**：**Queue**（排队成独立轮次）vs **Steer**（在最近的一个 step 边界切入正在工作的目标）。DSH 原文：
    > A working target receives the Agent message through **Steer** at its nearest step; an idle target **starts a turn**, and only a direct child can be cold-resumed。
    > —— `dsh-subagent/README.md`
  - **监督/生命周期**：`lifecycle.ts`、`run-settlement.ts`、`child-agent.ts`（"Child composition, delegated policy, **depth helpers**"）。
  - **可发现性**：`list_agents` 列出直接子级与**完整后代树**——mode、activity、lineage——「**reading live session state and optional persistence, without loading any child**」。即**观测不需要唤醒**，这是一个很好的设计。
- **DSH 的生命周期状态**（本会话一手观察 + `list_agents` 工具描述）：`running` = 正在工作；`idle` = 已加载但处于轮次之间（可能在等它自己启动的 agent）；`ready` = 仅存在于存储中，**可恢复但不是终止**、也**不是待收集的结果**。
  > ⚠ **第二轮更正**：`ready` 是**面向模型的可发现性**概念。核心 `Agent` 的**运行期状态只有 `idle` / `running` 两态**，dispose 通过 `agent/disposed` 事件表达而**不占用 status 值**（官方 `AgentStatus` 类型明确说明）。详见 [E3 新增 4](#新增-4agentstatus-只有两态dispose-不是状态)。
- **DSH 的落定条件**（settlement）：
  > Settlement waits for Agent activity to finish, **an empty Inbox**, and **no owned children**
  > —— `dsh-subagent/README.md`

  即：**「我的活干完了」+「我的邮箱空了」+「我的孩子都结束了」三者同时成立**。这是 actor 模型里典型的「静默（quiescence）」定义。

**适用场景**
- 长生命周期、需要持续接收消息的 agent（常驻助手、持续监控）。
- 需要强隔离与故障容错（一个 actor 崩溃不影响其他）。
- 地理位置分散、需要消息中间件的分布式 agent。

**坑**
- **邮箱无界 = 内存炸弹**。Actor 模型必须配邮箱上限与背压策略。
- **消息投递语义含糊**。DSH 在 Known Limitations 里非常诚实地列了一串：
  > - **No durable parent mailbox** — child-to-parent messages require a resident continuable child and live direct parent, and provide **acceptance identity rather than exactly-once delivery**。
  > - **A direct parent must remain live for child-to-parent delivery** — the service has no durable parent mailbox; a missing parent **rejects** the message instead of accepting work it cannot wake。
  > - **No replay of accepted-but-unlogged messages** — a crash can lose an accepted prompt that never reached the child's session log; the lost message is **not replayed automatically**。
  > - **Wake gap during cancellation convergence** — a follow-up accepted after an interrupt signal but before the driver becomes idle **stays queued until another waking send**。
  > - **Pending injected context retains an Activation** — Context parked after the Agent becomes idle **keeps the child and its live ancestors resident** until a waking delivery claims it…
  > —— `dsh-subagent/README.md` Known Limitations

  「accepted ≠ processed」是消息驱动系统最经典的坑。设计时必须明确：**你要的是 at-most-once、at-least-once 还是 exactly-once？**
- **背压缺失时邮箱溢出**。
- **调试困难**。消息驱动的调用栈不连续，必须靠 trace 才能还原因果（见 B7）。
- **死信/毒丸**：处理不了的消息如果没有死信队列，会永久堵塞邮箱（见 B6）。

### A8. 异步 I/O 并发（单线程 EventLoop）

**人话解释**
一个线程，靠 `async/await` 在等 I/O 的时候切去干别的活。对「大部分时间在等网络」的 LLM agent 来说，这是**性价比最高的并发方式**：零线程开销、零锁、极低内存。

**图示**

```
单个线程 + 事件循环

        ┌──────────────── Event Loop ────────────────┐
        │                                            │
        │  ready queue: [T1] [T3] [T7]               │
        └───────┬────────────────────────────────────┘
                │ 取出 T1，跑到第一个 await
                ▼
   ┌───────────────────────┐
   │ T1: await llm_call()  │──► 挂起，注册回调，交出控制权
   └───────────────────────┘
                │
                ▼ 事件循环立刻取 T3（不阻塞！）
   ┌───────────────────────┐
   │ T3: await tool()      │──► 挂起
   └───────────────────────┘
                │
                ▼ I/O 完成，回调入 ready queue
        [T1] 继续执行 ……

✅ 等待期间 CPU 不空转   ❌ 任何同步阻塞调用（CPU 密集/阻塞 IO）会卡死整个循环
```

**实现要点**
- **Python asyncio**：`asyncio.gather` 并发等待多个协程；`asyncio.Semaphore` 限流；`Task.cancel()` 触发 `CancelledError`，**取消是协作式的**——任务必须在 `await` 点才可能被取消，且可以捕获 `CancelledError` 来清理，但不应吞掉它 [34]。
- **Node.js**：单线程事件循环；`Promise.all` 并发；CPU 密集必须移到 `worker_threads` [40]。
- **Rust tokio**：多线程 work-stealing 运行时，`tokio::spawn` + `JoinHandle`，`tokio::select!` 做竞速 [39]。
- **DSH 是 Node.js/TypeScript 事件循环架构**。它的关键设计选择是：**把可能阻塞事件循环的东西拿出来**。
  > Each run receives its **own worker thread**, so **synchronous loops do not stall the harness** and scripts that ignore cancellation can be terminated。
  > —— `dsh-workflow-worker-thread/README.md`
- **tokio 则走了另一条路**：多线程 work-stealing 运行时（`tokio::spawn` + `JoinHandle`，`tokio::select!` 做竞速）。其调度器的重写带来 `chained_spawn` **约 12×** 的性能提升与 Hyper 吞吐 **+34%** [39][48] —— **说明在 I/O 密集负载上，「调度器质量」本身就是性能**。
- **`tokio::select!` 是竞速（A12）的原生原语**：多个 future 同时推进，第一个完成者胜出，其余被丢弃。
- **DSH 的 in-process 子智能体与 workflow 是两种不同的执行位置**：
  - `dsh-subagent-in-process-driver`：**在宿主事件循环上**驱动子 agent（"creates one child agent through the host's agent factory… drives one task to completion"）。
  - `dsh-workflow-worker-thread`：**在独立 worker 线程上**跑模型写的编排脚本。
  这个区分很重要：**delegation 是异步 I/O（等模型），而模型写的脚本可能含同步死循环（必须隔离）**。

**适用场景**
- I/O 密集、任务数多、每个任务大部分时间在等网络 —— LLM agent 的绝大多数场景。
- 需要极低内存开销地支撑成百上千并发。

**坑**
- **一个同步阻塞调用卡死全部**。这是 asyncio/Node 的头号杀手。
- **DSH 的引擎边界说明了这个问题**：
  > **One worker thread is paid per run** — there is **no pool, warm runtime, or cross-run script cache**。
  > —— `dsh-workflow-worker-thread/README.md` Known Limitations

  每个 run 一个新线程，意味着**并发 N 个 workflow = N 个线程的启动成本**，且没有池化复用。
- **worker 不是安全边界**。DSH 反复强调：
  > The vm context shapes the script's API surface; **it is not a security sandbox**。
  > **The worker and vm are not a security boundary** — model-written code can escape `node:vm` and reach the worker's process authority。
  > —— `dsh-workflow-worker-thread/README.md`

  **线程隔离解决「卡死」，不解决「越权」。** 要真隔离必须上独立进程或容器。
- **取消是协作式的，不是强制的**。DSH 的兜底是「有界取消」：`disposeGraceMs`（默认 5000ms）到期后强制结清并 `worker.terminate()` [DSH]。而 `dsh-tool-call-timeout-policy` 明确声明做不到硬停：
  > A tool that **ignores or slowly handles cancellation can keep the caller waiting** because the package **cannot hard-stop downstream work**。
  > —— `dsh-tool-call-timeout-policy/README.md`
- **取消期间的竞态窗口**。DSH 承认：「Wake gap during cancellation convergence — a follow-up accepted after an interrupt signal but before the driver becomes idle stays queued until another waking send」[DSH `dsh-subagent/README.md`]。

### A9. 多进程 / 多线程 / 容器隔离并发

**人话解释**
用操作系统级的隔离手段拿真正的并行和故障隔离。代价是**共享内存变成不可能**，所有通信必须序列化。

**图示**

```
隔离强度与开销的权衡（越往下越隔离、越贵）

  同进程 async      │ 零隔离，零序列化   │ 最快，一个阻塞全死
  ──────────────────┼────────────────────┼──────────────────────────
  同进程 线程        │ 共享内存，有 GIL   │ 上下文切换开销
  ──────────────────┼────────────────────┼──────────────────────────
  worker_threads     │ 独立 JS realm      │ structured-clone 序列化
  ──────────────────┼────────────────────┼──────────────────────────
  子进程             │ 完全独立地址空间   │ 进程启动 + 序列化/IPC
  ──────────────────┼────────────────────┼──────────────────────────
  容器 / 微虚拟机    │ 内核级隔离         │ 启动慢（秒级），最安全
```

**实现要点**
- **GIL（全局解释器锁）**：CPython 中同一时刻只有一个线程执行 Python 字节码，因此**多线程无法加速 CPU 密集任务**；要真正并行必须用 `multiprocessing`（进程）或原生扩展释放 GIL。
- **DSH 的隔离载体分层**（实测包清单，`packages/` 仓库路径 → 机制）：
  | 包 | 隔离机制 |
  |---|---|
  | `dsh-subagent-in-process-driver` + `spawn-in-process` + `fork-in-process` | **同进程内**驱动子 agent（宿主机事件循环） |
  | `dsh-workflow-worker-thread` | **worker_threads 线程隔离**（跑模型写的脚本） |
  | `dsh-code-runtime-worker-thread` | **worker thread 跑代码**（"runs each program in a fresh Node worker"） |
  | `dsh-subprocess` / `dsh-subprocess-local` / `dsh-win32-process` | **子进程隔离**（Windows 专门有 `dsh-win32-process`） |
  | `dsh-sandbox-windows-acl` | Windows 上用 **ACL** 划权限边界 |

- **DSH `dsh-code-runtime-worker-thread` 的四面资源闸**（很值得抄的清单）：
  > Configurable **compute, wall-clock, heap, and output** limits terminate the run and bound its results。
  > Failures such as syntax errors, **budget expiry, aborts, memory exhaustion, and output overflow are returned instead of thrown**。
  > —— `dsh-code-runtime-worker-thread/README.md`

  四个维度：**CPU 时间 / 墙钟时间 / 堆内存 / 输出大小**。并且**失败以返回值而非异常的形式给出**，避免把并发失败炸成未捕获异常。
- **DSH 的跨边界序列化是显式的**：
  > Values leaving the script pass through **realm materialization**, which accepts plain lossless JSON data and **rejects exotic prototypes, functions, symbols, cycles, sparse arrays, non-finite numbers, and nested `undefined`**。Child results are projected and snapshotted before crossing from host to worker — a real process-like serialization boundary。
  > —— `dsh-workflow-worker-thread/README.md`
- **环境净化**：worker「以 scrubbed environment 启动——只有平台临时路径」，`process.env` 里的环境凭证不跨界。
- **子进程输出收集**：`dsh-subprocess-local`「keeps a **bounded in-memory tail** with optional **spill files** for full-stream recovery」——有界尾部 + 溢写文件，这是并发下防止输出吃光内存的标准手法。

**适用场景**
- 需要真正 CPU 并行（Python）→ 多进程。
- 需要故障隔离（一个 agent 崩了不能拖垮宿主）→ 子进程/容器。
- 运行**不可信代码**（模型生成的代码）→ 容器/微虚拟机（DSH 明确说 worker+vm 不够）。

**坑**
- **序列化开销可能吃掉并行收益**。DSH 特意说明它**没有**采用「同进程 workflow 事件的借用不可变值」那种零拷贝方案，而是选择「a real process-like serialization boundary」，这是**为了隔离而主动付的代价**。
- **Windows 上的进程管理差异**。本会话的运行时约定里明确记录：**Windows 上被强杀的进程以 `[exit code: 1]` 结算，且没有信号标记**——不能靠信号来判断「是被杀的」还是「自己失败的」。这是写跨平台并发代码时非常容易踩的坑。
- **容器启动延迟**。秒级冷启动对「每任务一容器」的模式是致命的，需要预热池。
- **GIL 让「加线程」成为无效优化**（Python）。
- **进程数 ≠ 越大越好**。上下文切换、内存翻倍、IPC 都会反噬。

### A10. 人机协同并发（Human-in-the-loop）

**人话解释**
有一步必须等人批准。核心问题是：**等人期间，其他任务怎么办？** 是把整个人类审批当阻塞点（同步），还是让审批异步到达（异步）？

**图示**

```
【同步阻塞式】——简单，但整条链卡住
  Agent ──► 需要审批 ──► ⏸ 全部停住 ──► 人批 ──► 继续
                           ↑ 其他可并行的任务也停了

【异步审批式】——吞吐高，但状态复杂
  Agent A ──► 需要审批 ──► ⏸ 挂起（存入 checkpointer）
  Agent B ──► 需要审批 ──► ⏸ 挂起
  Agent C ──► 无审批 ────► ✅ 跑完并返回        ← C 不被 A/B 阻塞
        人批准 A ──► 恢复 A 的线程（thread_id）──► A 继续
        人批准 B ──► 恢复 B

【失败关闭（fail-closed）】
  审批超时 / 审批通道挂了 ──► 默认拒绝（不是默认允许）
```

**实现要点**
- **LangGraph 的 `interrupt()`**：结合 checkpointer + `thread_id` 实现暂停与恢复。**关键坑**：恢复时**整个节点从头重跑**，所以 `interrupt()` 之前的副作用必须幂等。并行分支同时 interrupt 时要用 `Command(resume={interrupt_id: value})` 按 ID 配对 [10]。
- **Microsoft Agent Framework**：新增了 AutoGen 没有的 `request_info` / `response_handler` 人工介入机制 [12]。
- **DSH 的审批路径**：`dsh-user-approval` 服务 + `dsh-client-ui-approval` 客户端。审批是「工具调用前的守卫」。
- **DSH 的 fail-closed 哲学**贯穿多处：
  - Session checkpoint：**Checkpoint failures are fail-closed** —— 「a model adapter or top-level tool body **does not run until the durable write succeeds**」[DSH `dsh-session-checkpoint-policy/README.md`]。
  - 沙箱拒绝即终局：**Approval prompts are disabled in this session: actions that require approval are rejected automatically**（本会话运行时策略）。
- **DSH 的浏览器人类输入有两套投递语义**：「browser continuation prompt independently selects **Queue or Steer**」，并会**在投递前**把图片批次持久化到 attachment store；**若子智能体声明的模型不接受图片输入，则拒绝投递**（而不是投了再失败）[DSH `dsh-subagent/README.md`]。这是「预检而非事后报错」的好例子。

**适用场景**
- 高风险动作：删除文件、发邮件、转账、生产部署、执行 shell。
- 合规要求人签字的流程。
- 长时任务中的关键决策点。

**坑**
- **同步审批 = 全局停顿**。人类响应时间（分钟到小时）和 agent 的响应时间（秒）差 2–3 个数量级，人类是整条流水线上最慢的一环。必须异步化 + 持久化挂起状态。
- **挂起状态的内存泄漏**。DSH 记录了一个真实的坑：
  > **Pending injected context retains an Activation** — Settlement conservatively treats every Inbox occurrence as unfinished。**Context parked after the Agent becomes idle keeps the child and its live ancestors resident** until a waking delivery claims it…
  > —— `dsh-subagent/README.md`

  即**挂起的上下文会让整条祖先链常驻内存**。这是「等人」直接导致的资源占用。
- **超时必须 fail-closed**。审批通道超时若默认为「允许」，就是一个安全漏洞。DSH 的 checkpoint 是 fail-closed 的典范。
- **恢复时的重放副作用**（见 LangGraph 的节点重跑）。
- **审批风暴**。N 个并行 agent 同时请求审批时，人会被淹没；需要合并、优先级或批量审批。

### A11. 长时后台作业 + 事件通知（job id / 流式输出 / 完成回调）

**人话解释**
任务太慢，不能让模型干等。于是「启动 → 立刻返回一个 job id → 模型继续干别的 → 完成后收到通知」。

**图示**

```
  Agent                Job Registry                Worker
    │                       │                         │
    │── start(job) ────────►│                         │
    │                       │── run ─────────────────►│
    │◄── job id 立即返回 ───│                         │
    │                       │                         │
    │  (继续干别的活 / 开新 job)                        │
    │                       │                         │
    │                       │◄─── done ───────────────│
    │◄── 完成通知（注入下一步 或 唤醒新轮次）────────────│
    │                       │
    │── job_output(id, wait)►│  拉取：流式 = 增量；终态 = 完整结果
    │── job_kill(id) ───────►│  取消（结算后才算 killed）
```

**实现要点**
- **DSH 的完整作业模型**（`dsh-jobs` / `dsh-jobs-local` / `dsh-tool-jobs` 三件套）：
  - **稳定 id**：每个 job 拿到 `<kind>-N` 形式的稳定 id。
  - **所有权隔离**：「Ownership is scoped to the **agent session**, so **other agents cannot inspect or stop the job**」。这是并发安全的关键：**作业不能跨 owner 操作**。
  - **三种操作**：
    | 工具 | 语义 |
    |---|---|
    | `job_output(job_id, wait?, timeout_ms?)` | 读输出。**流式 job 只返回自上次读取以来的增量**；终态 job 在结算后返回结果。响应总以 `[status: ...]` 结尾。**除非 `wait: true`，读取是非阻塞的**；超时返回 `[status: running]` 并**让 job 继续存活** |
    | `job_list()` | 列出作业，含 kind 与 status |
    | `job_kill(job_id, reason?)` | **立即请求取消**；「the job settles as `killed` **once its work actually stops**」 |
  - **等待上限**：`waitTimeoutMs` 默认 **30,000ms**；`maxWaitTimeoutMs` 默认 **600,000ms**，模型给更长的值会被**向下钳制**。
  - **完成通知的两条投递通道**：
    > A **busy** agent has the notice **injected into its next step** — the turn cannot close while the inbox holds it, so several jobs settling together **cost one step rather than one turn each**。An **idle** agent is instead **woken with a follow-up turn**, because an unclaimed notice is a completion the model never learns about。
    > —— `dsh-tool-jobs/README.md`

    这个「busy → 注入；idle → 唤醒」的分流非常精巧：**busy 路径零额外成本**（多个 job 同时完成只花一个 step），**idle 路径保证不丢通知**。
  - **唤醒预算防自激**：
    > Waking is **bounded**: each owner may be woken `maxConsecutiveWakes`（默认 **3**）times before further notices **degrade to injection**, and claiming any user-authored message restores the budget。**The bound exists because the chain is self-exciting** — a woken turn may start the background job whose completion wakes it again。
    > —— `dsh-tool-jobs/README.md`

    **「被唤醒的轮次可能又启动一个后台作业，它的完成再次唤醒自己」**——这是事件驱动系统的经典自激回路，DSH 用「连续唤醒预算 + 用户消息重置」来打断。
  - **避免重复通知**：「A kill or a terminal read/wait **marks the completion reported and suppresses the redundant notice**」。
  - **有界输出**：「When a producer supplies `outputLimitBytes`, the complete model-facing result — output read, terminal kill snapshot, or completion notice — is **capped**」。
- **DSH 子智能体的后台模式有两档**（`dsh-tool-subagent`）：
  - `one-shot`：`run_in_background: true` 时「starts a **plain parent-owned background job** and returns `started background subagent job <id>`，collected with `job_output` and stopped with `job_kill`」。
  - `continuable`：`startContinuable()`「**resolves at inbox acceptance**：the child owns its own turns from there, so the call **neither waits for nor collects a result**」。
- **DSH 的 supervisor 提示词**（本会话直接可见）：
  > Track every background job id you start. You are notified in-session when a job finishes — **do not busy-poll or sleep on one**; keep working on independent steps and do not duplicate a running job's work。
  > —— `dsh-tool-jobs/README.md` Model Experience
- **DSH 的 `workflow` 工具在这一点上是反面案例并自我承认**：
  > **The parent turn blocks until the whole workflow settles** — there is **no background start/poll API**, and cancellation **discards partial output as an error**。
  > —— `dsh-tool-workflow/README.md` Known Limitations

  官方 Dev Note 把「background start/poll route so the parent turn does not block」列为**未决策的开放方向**。

**适用场景**
- 构建/测试/训练等分钟到小时级任务。
- 需要边跑边看输出的长任务。
- 需要同时推进多条独立工作流。

**坑**
- **busy-poll**。DSH 的提示词直接点名禁止。
- **通知风暴 / 自激循环**（见上，DSH 用 `maxConsecutiveWakes` 解决）。
- **无界输出**。长期运行的 job 输出可能几 GB；必须有 spill/上限（DSH：`maxInlineBytes: 50000` 的 spill 策略 + `thresholdChars: 8192` 的工具结果剪枝）。
- **静默失效的 cancel**：「A producer cancel that returns without settling `done` stays indistinguishable from a slow stop and **can stall teardown while holding one capacity slot**」[DSH `dsh-jobs-local/README.md`]。
- **进程退出即丢**：DSH 的 job registry 是进程本地的，「jobs die with the harness process and are **not durable across restarts**」。
- **结算竞态窗口**：DSH 承认「between the turn loop's last inbox check and the driver committing its idle phase the owner still reads as busy, so the notice is **injected and nothing wakes**」。

### A12. 竞争 / 博弈式并发（Best-of-N、Speculative Execution）

**人话解释**
同一个任务让多个 agent 各自跑一遍，**取最快/最好的那个**，其余作废。不是「分工」而是「竞速」。

**图示**

```
                 ┌──────────────┐
     任务 T ────►│  Dispatcher  │
                 └──────┬───────┘
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     ┌─────────┐   ┌─────────┐   ┌─────────┐
     │ Agent 1 │   │ Agent 2 │   │ Agent 3 │   同一 prompt / 不同 temperature
     └────┬────┘   └────┬────┘   └────┬────┘
        t=3.2s        t=1.8s ✅      t=4.1s
          │             │             │
          │        ┌────▼─────┐       │
          └───────►│  取消其余 │◄──────┘      ← 浪费 2 份成本，买 1.8s 延迟
                   └──────────┘

【Best-of-N（按质量）】      【Speculative（按速度）】
  全跑完 → 用 verifier/judge  第一个成功者胜 → 取消其余
  选最好的                      （乐观执行，抢占式）
```

**实现要点**
- **Best-of-N**：N 个独立采样，用验证器或 LLM-as-judge 选优。Anthropic 强调 LLM judge 的做法：「a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the **most consistent** and aligned with human judgements」[1]。
- **Speculative execution**：第一个成功的结果胜出，其余取消。DSH 原语里最接近的是 `tokio::select!`（Rust）/ `Promise.race`（JS）/ `asyncio.wait(FIRST_COMPLETED)`（Python）。
- **DSH 的 `workflow` 脚本天然支持竞速**：`agent()` 返回 Promise，脚本可以自己写 `Promise.race(...)`。⚠ 但 **DSH 是否提供内建的 race 语义原语，本次未获取到证据**——`dsh-tool-workflow` 暴露的 hook 只有 `agent` / `parallel` / `pipeline` / `phase` / `log`。DSH 明确说 `parallel(thunks)` 是「await **ALL** of them」。
- **成本换延迟的显式性**：竞速是唯一一种**主动浪费算力买延迟**的模式，必须显式记账。

**适用场景**
- 延迟敏感的交互场景（用户在前台等）。
- 结果正确率对采样敏感的推理任务（Best-of-N 提升准确率）。
- 「重试比等待便宜」的场景。

**坑**
- **N 倍成本 + (N-1)/N 的浪费**。配合 15× 的多智能体成本基准，Best-of-N 是最贵的模式之一。
- **取消时机与副作用**。竞速中落后者的**副作用无法回滚**——如果 Agent 2 已经写了文件/发了请求，取消它不能撤销。**竞速只能用于无副作用或可补偿的任务**。
- **verifier 的成本与偏差**。Best-of-N 需要一个 verifier，而 verifier 本身也可能是 LLM 调用（额外成本），且有偏好偏差。
- **取消不彻底**（见 A8 的协作式取消）——「取消」了但后台还在跑，仍然计费。

## B. 并发控制的核心机制

### B1. 并发上限（Semaphore / Concurrency Cap）与总 agent 上限

**定义**：并发上限约束「瞬时在飞的任务数」，总量上限约束「整个 run 的生命周期内启动的任务总数」。**两者缺一不可。**

**为什么两者都要**：
- 只有并发上限 → 无限循环的扇出可以持续启动新任务，永不停止（DSH 称之为 "runaway loop"）。
- 只有总量上限 → 瞬时可能把配额打爆。

**DSH 的三维预算（实测，`dsh-workflow-worker-thread/README.md`）**：

| 维度 | 字段 | 默认 | 语义 |
|---|---|---|---|
| 瞬时并发 | `maxConcurrentAgents` | `0` → **`min(16, max(1, availableParallelism() - 2))`** | `agent()` 并发上限 |
| 生命周期总量 | `maxTotalAgents` | `1000` | 一次 run 的总 child 数，**runaway-loop 兜底** |
| 单批规模 | `maxItemsPerCall` | `4096` | 单次 `parallel()` / `pipeline()` 的 item 数 |

**其他真实上限一览**：

| 系统 | 机制 | 数值 |
|---|---|---|
| DSH jobs | `maxConcurrentJobsPerOwner` | **10**（running + stopping，per owner） |
| DSH subagent | `maxDepth` | **3**（`0` 禁止委派） |
| DSH ralph | `maxRounds` | 包默认 **256**，`dsh-base` 装配为 **64** |
| DSH ralph | `maxHandoffChars` / `maxResultChars` | 各 **16384** |
| DSH workflow tool | `maxResultChars` | **50000** |
| DSH tool-jobs | `waitTimeoutMs` / `maxWaitTimeoutMs` | **30000** / **600000** |
| DSH tool-jobs | `maxConsecutiveWakes` | **3** |
| DSH 工具结果剪枝 | `thresholdChars` / `head` / `tail` | **8192** / 4096 / 1024 |
| DSH spill | `maxInlineBytes` | **50000** |
| LangGraph | `recursion_limit` | **1000** 超步（超出抛 `GraphRecursionError`）[7] |
| Temporal | 未完成 Child Workflow | 默认 **2000**；单 parent 建议 ≤ **1000** [25] |
| Temporal | Event History | **51200 events 或 50MB**（10240/10MB 告警）[24] |
| Airflow | `parallelism` / `max_active_tasks_per_dag` | 配置项 [28] |

**关键设计模式**：
1. **fail-closed 准入**：DSH 的 jobs registry 在**调用 producer 之前**检查容量，拒绝时「不留 job id，也不留执行资源」。
2. **不排队、不抢占**：DSH 明确选择「neither queues nor preempts」，把决策权交回给调用者（模型），并用错误信息引导：「kill an unneeded job, wait for it to finish, and retry」。
3. **`0` = 自动，但有上限**：DSH 的 `maxConcurrentAgents: 0` 解析为 **`min(16, max(1, availableParallelism() - 2))`**（实测 `dsh-workflow-worker-thread/lib/index.js`:883）。两个设计细节值得学：**留出 2 个核给宿主**（不要吃满 CPU），以及**硬顶 16**——即使机器有 128 核，也不会一次放出 126 个并发 LLM 调用。**这是「并发上限由下游配额而非 CPU 决定」的直接体现。**

**⭐ 五个必须组合使用的原语（HiveMind 的消融结论）** [46]：

HiveMind 用零改动 HTTP 代理验证了五类原语的组合效果：

| 原语 | 作用 |
|---|---|
| **Admission control** | 准入：超额在入口就挡住 |
| **Rate-limit tracking** | 跟踪 RPM **与** TPM 两个维度 |
| **AIMD 背压 + 熔断** | 按失败信号自适应降低并发 |
| **Token 预算** | 按 token 而非请求数设限 |
| **优先级队列** | 区分交互式与批处理 |

**消融实验最反直觉的结论**：**最关键的单一原语是「透明重试」，而不是准入控制**；但**原语组合起来效果最好** [46]。

→ **实务推论**：只加一个 semaphore 是远远不够的。**准入 + 重试 + 预算 + 优先级需要成套配置**，这也是为什么 DSH 用了 `maxConcurrentAgents` + `maxTotalAgents` + `maxItemsPerCall` + `maxConcurrentJobsPerOwner` + `maxDepth` + `maxConsecutiveWakes` 这么多个旋钮。

### B2. 调度策略：FIFO、优先级、公平调度、Work-Stealing

| 策略 | 机制 | 优点 | 坑 |
|---|---|---|---|
| **FIFO** | 队列先进先出 | 简单、无饥饿（理论上） | **队头阻塞**：一个慢任务卡住后面所有 |
| **优先级** | 按优先级排序 | 关键任务先跑 | **优先级反转**、**低优先级饥饿** |
| **公平调度** | 按所有者/租户配额分配（如加权公平队列） | 多租户隔离 | 实现复杂，短任务延迟上升 |
| **Work-Stealing** | 每个 worker 有本地双端队列，空闲时从别人队列**尾部**偷 | 负载均衡好、局部性优 | 任务必须无亲和性要求；偷取有同步开销 |

**⭐ 调度器设计的实证（Tokio 官方长文，含源码级论证）**

Tokio 重写调度器时给出的三种方案对比，是理解调度权衡的最好材料 [48]：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **单一全局队列 + 多 consumer** | 天然 FIFO 公平、实现简单 | 所有 processor **争用队头**；对「任务极短」的异步负载代价极高 |
| **分片队列**（每 processor 一个本地队列） | 几乎避免同步 | 负载不均时**部分核空转** |
| **Work-Stealing** ✅ | 负载不均时可重新分配 | 需要 throttle 与通知节流 |

**Go、Erlang、Java ForkJoinPool 都选择了 work-stealing** [48]。Tokio 的两个关键工程细节值得记住：

1. **Throttle stealing**：处于 searching 态的 processor 数量**上限设为处理器总数的一半** —— 用一点精度换吞吐 [48]。
2. **通知节流（这是惊群问题的正解）**：只在**没有 searcher 时**才唤醒兄弟线程。Tokio 0.1 的问题是「每次 push 都唤醒」，**立刻造成惊群（thundering herd）** [48]。

**真实收益数字** [48]：

| 指标 | 改进前 | 改进后 |
|---|---|---|
| `chained_spawn` 基准 | 2,019,796 ns/iter | **168,854 ns/iter**（约 **12×**） |
| Hyper hello-world 吞吐 | 113,923 req/s | **152,258 req/s**（**+34%**） |
| 每任务内存分配 | 2 次 | **1 次** |

另外，并发测试工具 **Loom** 抓出了 **10 个以上**其他测试漏掉的 bug —— **并发正确性需要专门的工具，不能靠常规测试。**

**Work-stealing 的理论界**：Cilk 的工作窃取调度界（Blumofe & Leiserson, JACM 1999）是该领域的经典结果 [53]。

**真实实现**：
- **Rust tokio**：多线程 work-stealing 调度器 [39][48]。
- **Airflow 的调度饥饿问题**：Apache 有一个专门的改进提案 **AIP-100 "Eliminate Scheduler Starvation On Concurrency Limits"**，正说明「按并发上限调度」在实践中会导致饥饿。
- **DSH 的公平性设计是「owner 维度」的**：
  > Controllers, completion listeners, and change observers are filed into the scope that registered them (`ScopedLayers`), and reads union the global layer with the owner's scope chain — so **one preset's job controls never hold `start()` open for an agent whose own composition loads none**, and a settlement reaches only the listeners its owner's composition registered。
  > —— `dsh-jobs-local/README.md`

  即**按 owner 划分作用域层**，避免一个 preset 的配置影响另一个 preset 的 agent。
- **DSH 的 inbox 有两种投递调度语义**：**Queue**（排队等下一个轮次）vs **Steer**（在最近的 step 边界切入）。这是「立即插队」vs「老实排队」的显式选择，比隐式优先级更可控。
- **Anthropic 的调度是「批」级的**：lead agent 一次拉起 3–5 个 subagent 为一组，**等整组完成**再决定下一批 [1] —— 这是 FIFO-批式调度，也是它承认的瓶颈来源。

**坑**：
- **无上限 + 无优先级 = 队头阻塞**。
- **优先级 + 长任务 = 饥饿**（低优先级永远排不上）。
- **公平调度会牺牲吞吐**。
- **公平性要按 keyspace 而非全局来做**。Google SRE 的建议：对共享资源按 keyspace 限制在途请求（例如**任一 client 最多占用 25% 的线程**），以保证高负载下的公平性 [47]。
- **惊群（thundering herd）**：无节流的「有任务就唤醒所有 worker」会让唤醒成本超过任务本身 [48]。

### B3. 同步原语：Barrier vs 无 Barrier、Join、Future/Promise、Channel

| 原语 | 语义 | 何时用 | 何时是坑 |
|---|---|---|---|
| **Barrier（屏障）** | 等**所有**并发分支到达才继续 | 真的需要全部结果才能做下一步（如投票、全局统计） | 流水线中被误用 → **吞吐崩塌**（见 A2） |
| **无 Barrier（流式）** | 各分支独立推进，来了就处理 | 多阶段流水线、流式输出 | 需要处理乱序、需要 item 级失败隔离 |
| **Join（汇合）** | 等**指定的一组**任务完成 | DAG 中的依赖汇合 | 把「一组」写成「全部」就退化成 barrier |
| **Future / Promise** | 代表「未来会有」的值，可组合 | 异步的基础设施 | 未处理的 rejection；Promise 泄漏（没 await） |
| **Channel（CSP）** | 有类型/有界的通信管道 | 生产者-消费者、背压 | 无界 channel = 内存炸弹；关闭时的竞态 |

**DSH 的实证对照**（同一文件的相邻两行，把 barrier 的取舍写进了给模型的契约）：
> `pipeline(items, ...stages)` —— run each item through the stages independently with **NO barrier between stages**（**prefer this for multi-stage work**）
> `parallel(thunks)` —— run zero-argument functions concurrently and **await ALL of them（a barrier; use only when a stage genuinely needs every prior result together）**
> —— `dsh-tool-workflow/lib/types/index.js`:100-101

**LangGraph 的 BSP 屏障**：超步之间是强制屏障，「同一超步内运行的节点是并行的一部分」（[7]）。这是**显式屏障模型**，好处是状态合并有明确的时点，坏处是慢节点拖慢整个超步。

**Temporal 的 `asyncio.gather`**：workflow 内用 gather 并发调度 Activity/Child Workflow，是 gather 式「全部完成再继续」[24]。

**⭐ 为什么 barrier 在 LLM 场景特别致命（straggler / 长尾效应）**

LLM 单次调用是**长尾延迟分布**（秒到分钟级，P99 可能是中位数的几十倍）。全局 barrier 让**最慢的那一个 agent 决定整批的完成时间** —— 这就是 **straggler 效应**。barrier 之间还会出现**流水线气泡**：快的 agent 只能空等 [48][34]。

一个放大倍数的直觉：Tokio 甚至为「唤醒 → 被调度」的延迟做了专门优化（把被唤醒的接收方放进 "next task" 槽位优先执行），说明**即使在微秒级任务里这个延迟都值得优化**。而在 LLM 场景，这个延迟被放大了 **6–7 个数量级** [48]。

⚠ **诚实标注**：本次**未找到专门量化「LLM agent barrier stall」的同行评审论文**。上述推理由通用并发理论 + Anthropic 的实践（lead agent 只在真正需要聚合处 join）推得，**属于推断而非实测**。

**中间态同步原语的真实教训**：
- LangGraph 的 `interrupt()` 恢复时**整个节点从头重跑** → interrupt 前的副作用必须幂等 [10]。
- LangGraph 的 `interrupt()` **不能包在裸 `try/except` 里**，也**不能在节点内用 `while True` 循环**（因为恢复本身会重放）[10]。
- Temporal 要求**确定性**：`Date.now()`、随机数、未包在 Activity 里的网络调用都会破坏重放 [24]。

### B4. 状态共享与隔离

三种范式的对照：

```
【共享内存】                    【消息传递】                 【上下文隔离】
  多线程/多进程                    Actor / CSP                  subagent
  ┌────┐ ┌────┐                  ┌────┐  msg  ┌────┐         ┌────┐   ┌────┐
  │ T1 │ │ T2 │                  │ A  │──────►│ B  │         │父  │   │子  │
  └──┬─┘ └──┬─┘                  └────┘       └────┘         └────┘   └────┘
     └──┬───┘                      无共享内存                   各自独立 context window
        ▼                                                     只通过显式 prompt 传递
   [共享变量] ← 需要锁！                                     零共享 ⇒ 零数据竞争
   最快但有数据竞争                                            但信息必须显式搬运
```

**核心结论**：**在 LLM agent 场景下，「共享内存」这个选项基本不存在**，因为每个 agent 的上下文窗口是物理隔离的。所以真正的选择是：

1. **消息传递**（DSH 的 inbox / Queue / Steer、AutoGen 的 topic 订阅）
2. **外部共享存储**（文件系统、session log、Memory）
3. **上下文快照复制**（DSH 的 `fork`：把父的**已完成轮次**复制给子）

**DSH 的三种隔离程度（实测，这是最干净的对照）**：

| 后端 | 上下文 | 说明 |
|---|---|---|
| `spawn` | **空对话** | 「The child starts with an **empty conversation**, so a task prompt must stand alone」 |
| `fork` | **父的已完成轮次快照** | 「seeds each child with the parent's **completed conversation turns**: the child sees **every finished turn and none of the in-flight one**」；「The seed is a **one-time snapshot** taken at fork time: **later parent turns never reach the child**」 |
| `workflow` 的 `agent()` | **各子独立** | 「They **never join the parent history directly**」 |

**DSH 对 Token / KV Cache 的显式说明**（很少见地把缓存效应写进文档）：
> Potentially many **independent child contexts are paid**, bounded by `maxConcurrentAgents`, `maxTotalAgents`, and `maxItemsPerCall`; they never join the parent history directly。
> **KV Cache effect**: Independent of the parent request cache and of sibling children。
> —— `dsh-workflow-worker-thread/README.md` Model Experience

**一个反直觉的观察**：DSH `fork` 后端**故意不提供模型选择**，理由是：
> Fork omits model selection so provider/model stay equal to the parent and the **inherited history remains eligible for KV Cache reuse**。
> —— `dsh-base/cordis.patch.yml`:356-358

即**为了保住 KV cache 命中，主动牺牲了模型选择的灵活性**。这是一个「并发/缓存权衡」的真实工程决策。

**共享状态的框架级保护**：
- **LangGraph**：并行写同一个**没有 reducer** 的 key 直接抛 `INVALID_CONCURRENT_GRAPH_UPDATE` [8]。默认 reducer 是**覆盖**，不是合并。
- **Google ADK**：官方警告 `ParallelAgent` 分支间**不共享 history/state**，要共享必须显式用 `InvocationContext`（**自己加锁防竞态**）或外部存储 [19]。
- **Temporal / Airflow / Prefect**：靠**不可变值传递**（Event History / XCom / result）从设计上规避共享可变状态 [24][27][29]。

### B5. 取消与中断（Cancellation / AbortSignal / interrupt / kill）、超时

**核心事实：没有一种通用机制能安全地强杀一个正在执行的异步任务。** 取消都是**协作式**的。

| 平台 | 机制 | 协作性 |
|---|---|---|
| JavaScript | `AbortSignal` / `AbortController` | 协作式：被取消方必须监听 signal [35] |
| Python | `asyncio.Task.cancel()` → `CancelledError` | 协作式：只在 `await` 点生效 [34] |
| Rust tokio | `JoinHandle::abort()` / `select!` | 协作式（`.await` 点） |
| 线程 | 无法安全强杀（`Thread.stop` 已废弃） | 不可取消 |
| 进程 | `SIGKILL` / `TerminateProcess` | **可强杀**（唯一的真取消） |

**各平台的取消语义细节（实证）**：

- **JavaScript / `AbortSignal`**：可组合、可向下传递的**一次性**取消信令；原生 `fetch` 等 API 直接消费它 [35]。
- **Python asyncio** [34]：
  - `CancelledError` 在**下一个 `await` 点**抛出，且它**直接继承 `BaseException`**（不是 `Exception`）——所以 `except Exception` 抓不到它。
  - 官方明确要求：用 `try/finally` 清理，并**「一般应继续向上传播」**。
  - **⚠ 吞掉 `CancelledError` 会让 `TaskGroup` / `timeout()` 行为失常** —— 因为它们**内部就是用取消实现的**。
  - 取消是协作式的：**同步阻塞代码不会被打断**。
  - **⚠ 官方明确警告的坑**：不保存 `asyncio.Task` 的**强引用**，任务可能在完成前**被 GC 掉**。
- **结构化并发**：`asyncio.TaskGroup`（3.11+）在**一个子任务失败时取消其余任务**并把异常聚合成 `ExceptionGroup`；Trio 的 cancel scope 与 Kotlin 协程（需在挂起点检查、用 `ensureActive` / `yield`）同理 [34][57][58]。
- **为什么不能安全杀线程**：Python `threading` **没有 kill API**；C++ `std::thread` 也没有 cancel，即使 C++20 的 `jthread` 也只提供**协作式**的 `stop_token`。硬杀会在线程**持有锁**或处于**不变量中间态**时破坏进程状态 [34]。

**DSH 的分层取消设计（非常完整，值得整套照抄）**：

1. **协作式取消 + 有界兜底**：
   > `cancel()` records the **first reason**, tells the worker to cancel, **aborts the one signal shared by every pending and published child**, and arms the `disposeGraceMs` timer; worker hooks then **throw `CANCELLED` at their next await**。If the run remains unsettled at the deadline, the host resolves it as cancelled, pairs stranded child lifecycle events, and **terminates the worker**。
   > —— `dsh-workflow-worker-thread/README.md`

   **「一个共享 signal 覆盖所有在飞与待启动的子任务」**是并发取消的关键——不能逐个取消，会漏。
2. **终态先到先得（first-wins）**：
   > Terminal outcome is **first-wins at host claim points**: an accepted external cancellation **overrides** a later non-cancelled worker result, and a result or worker death that claims first **cannot be rewritten** by reentrant cleanup callbacks。
3. **事件配对保证**：「The host keeps a ledger of forwarded child starts… death or force termination **synthesizes any missing end as cancelled** — every forwarded `workflow/agent-start` is **paired exactly once**」。**每个 start 事件必须有且仅有一个 end**，否则并发 trace 就断了。
4. **dispose 幂等**：「`dispose()` is idempotent… Per-child disposal is **memoized** so worker RPC, host cancellation, death cleanup, and public disposal **all join one operation**」。
5. **取消不丢信息**：`interrupt_agent`「stops a child's current turn **while keeping its inbox and descendants intact**」[DSH `dsh-tool-subagent-control/README.md`]。

**超时的正确实现（DSH `dsh-timeout`）**：
> `clampTimeout` fills a missing hint from a backend default, **caps it at the allowed maximum**, and rejects invalid values **before work starts**。
> `deadline` **combines the chosen timeout with upstream cancellation in one signal**, while the caller **remains responsible for actually stopping** its process, socket, or task。
> `idleWatchdog` counts **only time spent waiting for provider reads**, and **zero remains reserved for backend-owned untimed work** rather than public configuration。
> —— `dsh-timeout/README.md`

三个要点：**下限/上限钳制**、**超时与取消融合成一个 signal 但可区分归因**（「distinguish local timeout from upstream cancellation」）、**空闲看门狗只计等待时间**。

**DSH 的 checkpoint 与未知结果**：
> unfinished Assistant streams remain transient, and **interrupted tool calls recover with an unknown outcome instead of an automatic retry**。
> —— `dsh-session-checkpoint-policy/README.md`

**中断后不自动重试**——因为副作用可能已经发生。这是一个非常成熟的决定。

**坑**：
- **静默失败的工具无法取消**：DSH 明说「A tool that ignores or slowly handles cancellation can keep the caller waiting because the package cannot hard-stop downstream work」。
- **Windows 平台差异**：强杀进程后**没有信号标记**，只能看到 `exit code 1`，无法区分「被杀」与「自己失败」。
- **取消的传播有窗口**：DSH 承认「Wake gap during cancellation convergence」。
- **超时后资源未释放**：DSH 的 `disposeGraceMs` 就是为此而设。

### B6. 失败处理：部分失败、重试/退避、幂等、补偿、毒丸

**部分失败（Partial Failure）**——这是并发相对于串行最本质的新问题：**10 个并发任务，3 个失败，怎么办？**

两种截然不同的语义，DSH 把两者都实现了并且**明确区分**：

| 场景 | DSH 的语义 | 原文 |
|---|---|---|
| **Workflow 脚本内的子 agent 失败** | **降级为 `null`，脚本自己处理** | 「an ordinary child failure **resolves `agent()` to `null`** so the script can handle it」 |
| **Pipeline 中某 stage 抛错** | **该 item 变 `null`，跳过剩余 stage** | 「An ordinary stage throw **drops that ITEM to `null`** and skips its remaining stages」 |
| **Workflow 工具整体失败/取消** | **绝不返回部分成功** | 「Cancellation and execution failures return `Error: workflow run was cancelled` or `Error: workflow run failed: <error>`；**partial output is never reported as success**」 |
| **Ralph 中某一轮失败** | **整轮终止** | 「Ordinary child failure is **terminal for the run** — the fixed script reports the failed round and last successful handoff but **does not retry**」 |

**这是一组极好的设计对照**：**编排层要能容忍单个子任务失败（降级为 null），但绝不能把「部分完成」谎报为「成功」。** 两者的边界在于「谁知道怎么补偿」——脚本知道（所以给 null 让它决策），工具调用者不知道（所以必须报错）。

**重试 / 退避**：
- **指数退避 + 抖动（jitter）** 是标准做法（AWS 架构博客的经典文，Marc Brooker）[32]。**full jitter** 的形式是：
  ```
  sleep = random(0, min(cap, base * 2 ** attempt))
  ```
  **抖动是必须的**——否则 N 个同时失败的客户端会在同一时刻重试，形成**重试风暴 / 惊群（thundering herd）**。⚠ aws.amazon.com 在本环境被网络层拒绝，公式与定性结论属业界共识，**具体仿真数字未能逐字复核，按不确定处理**。

- **⭐⭐ 重试放大的真实数字（Google SRE 第 22 章）——这是本报告最值得记住的一组数字** [47]：

  | 阶段 | QPS | 现象 |
  |---|---|---|
  | 健康 | 10,000 | 正常 |
  | **临界** | **11,000** | **开始级联失败** |
  | 试图恢复 | 9,000 | **仍然救不回来** |
  | **实际需要的恢复点** | **约 1,000** | 因为此时**只有约 10% 的实例还健康** |

  → **过载是不可逆的：一旦进入级联失败，必须把流量压到远低于原始容量才能恢复。** SRE 把「**所有客户端使用随机指数退避**」列为对客户端的重点测试项。

  把这个数字搬到 agent 场景：**如果你有 100 路并发 agent，provider 开始 429，你不能把并发降到 90 就指望恢复——你可能需要降到 10。** 这直接说明**为什么必须在准入阶段就卡住并发，而不是靠重试兜底**。
- **DSH 的重试实现**（`dsh-llm-retry`）：
  > Provider `retryPolicy` settings choose **bounded normal-mode retries** or **unlimited always-mode retries**；**scheduled attempts reach the session log before backoff**, and **cancellation leaves consistent history**。Retries **re-run the failed step in the same open turn**, while direct `ctx.llm.stream()` calls remain **single-attempt**。
  > **Each retry is another billed provider request**。
  > —— `dsh-llm-retry/README.md`

  三个关键细节：**重试计划先落盘再退避**（崩溃可恢复）、**重试在同一 turn 内重跑该 step**、**每次重试都真金白银计费**。
- **LangGraph**：`durability` 三档 `"exit"` / `"async"` / `"sync"`；checkpointer 每个超步 + 每个任务级写入（`put_writes`）[9]。

**幂等（Idempotency）**：
- 重试的前提是**幂等**。非幂等的操作重试 = 重复副作用。
- 标准做法是 **idempotency key**（Stripe 的经典实践）[33]。
- **LangGraph 的具体坑**：`interrupt()` 恢复时节点从头重跑，「interrupt 前的副作用必须幂等」[10]。
- **DSH 的对应做法**：中断的工具调用恢复为「unknown outcome」而**不自动重试**。

**补偿事务（Compensating Transaction / Saga）** [55]：
- 长事务无法回滚时，**把跨服务事务拆成一组本地事务**，失败时**逆序执行补偿事务**。
- 在 agent 场景中，这对应「让 agent 自己撤销它做的事」（删掉刚建的文件、调 API 撤销、回滚 commit）。
- **Azure 架构中心列出的三类数据异常，正好覆盖 agent 并发场景**：**lost update、dirty read、nonrepeatable read**；对策包括**语义锁（semaphore）、可交换更新、版本文件**，并强调「**按风险选择并发机制**」[55]。
- **⚠ 官方明确警告：补偿事务「不一定成功」，可能留下不一致状态。** 所以 Saga 不是「回滚」，而是「尽最大努力收敛」。
- ⚠ 本次未取得 DSH 提供内建补偿机制的证据——DSH 的选择是「**不自动重试 + 记录 unknown outcome**」，把补偿交给上层。

**熔断器（Circuit Breaker）** [54]：
- 在连续失败达阈值后**直接快速失败**（不再打下游），给下游恢复时间，然后半开试探。
- HiveMind 把 **AIMD 背压与熔断组合成同一原语** [46]。
- 熔断与退避的分工：**退避处理「暂时性」失败，熔断处理「持续性」故障**。二者都要有，否则要么雪崩、要么无谓重试。

**毒丸任务（Poison Pill）**：
- 一个永远失败的消息/任务，会无限重试并阻塞队列。
- 标准解法：**重试上限 + 死信队列（DLQ）+ 熔断器**。⚠ 本次**未找到该点的权威一手来源**，按业界共识列出。
- **DSH 的对应设计**：
  - **总量上限兜底**：`maxTotalAgents: 1000` 防止无限循环。
  - **重复工具调用守卫**：`dsh-repeat-tool-reminder`（"**advisory reminders** when an agent loops on identical tool calls"）——注意是「建议性提醒」而非硬停，因为它无法区分「合理重复」与「死循环」。
  - **目标轮的阻塞计数**：「`dsh-tool-goal` defines **when repeated blocking stops continuation**」，且「Mark blocked only after the same blocking condition persists for at least 3 consecutive goal rounds」。
  - **fail-fast 的非法输入**：「Invalid, missing, or oversized reports **fail the workflow** instead of being truncated or mistaken for cap exhaustion」[DSH `dsh-tool-ralph/README.md`]。

### B7. 可观测性：并发 trace、span 父子关系、成本归集

**并发让调试难度上一个数量级**。Anthropic 对此的表述非常准确：
> Agents make dynamic decisions and are **non-deterministic between runs**, even with identical prompts。This makes debugging harder。For instance, users would report agents "not finding obvious information," but **we couldn't see why**。Were the agents using bad search queries? Choosing poor sources? Hitting tool failures? **Adding full production tracing let us diagnose why agents failed**。
> —— [1]

**三个必须做对的维度**：

1. **Span 父子关系**。OpenTelemetry 的 trace = 一棵 span 树；并行分支是同一父 span 下的**兄弟 span**，必须有唯一 span id + parent span id [36]。**并发系统里最忌讳的是「只知道发生了什么，不知道是谁触发的」。**
   - DSH 的做法：`workflow/start` → `workflow/agent-start` / `workflow/agent-end` 成对事件，且「paired **exactly once**」[DSH `dsh-workflow-worker-thread/README.md`]。
   - DSH 的 `dsh-session-telemetry-otel` 提供 OTel 导出。
   - DSH 的子智能体谱系：`list_agents` 会给出每个 agent 的 **depth 1 直接父 session id 与 depth**。
2. **成本归集**。每个并发单元是独立的计费请求，必须按 span/agent 归集。
   - DSH 显式建模：**每次重试都是另一次计费请求**；workflow 的 child token「never join the parent history」；`agentsStarted` 计数随结果返回。
   - DSH 的 `dsh-token-meter` / `dsh-session-stats` 是相关包。
   - **DSH 的一个诚实缺口**：Ralph 的「Only round count bounds aggregate effort — **token, price, and elapsed-time budgets are deferred**」[DSH `dsh-tool-ralph/README.md`]。即**目前只能用轮次数而不是 token/金额来约束总量**。
3. **并发 trace 与 Session log 的关系**。
   - DSH 的 `dsh-tool-workflow` 做了**分层记录**：只有 root transport execution 才把 run 投影到 Session（4 个 log-only 事件：run-start / member starts&endings / run-end），**嵌套调用正常执行但不写记录**。并且「The **first failed Session append disables later recording** for that run with one warning, leaving either **no record or a legal continuous prefix** without changing the tool result or cleanup」。
   - 这是一个很好的原则：**观测失败绝不能影响执行**，且**观测数据要么完整要么是合法前缀，不能是破碎的中间态**。

**⚠ DSH 的 Telemetry 有一个必须知道的限制**：
> The handoff is **non-blocking**, so reporting does not delay session processing。**Delivery is best effort, and queued records may be lost if the process crashes**。
> —— `dsh-session-telemetry/README.md`

即 **telemetry 是尽力而为、可能丢**——它不能作为计费或审计的唯一依据。

**⭐ 并发 agent 的 trace 三个硬要求（OTel 语义）** [36][56]：

1. **同一批并行 subagent 的 span 应是「同一父 span 下的兄弟」，而不是串成父子链。** 批内顺序关系用 **span link** 表达，否则**时长与因果关系会被误读**（看起来像 A 触发了 B，其实是并行的）[56]。
   - OpenAI Agents SDK 的做法：三个并发 agent 用 `with trace("Parallel translation")` 包起来，合成**一条** trace [62][4]。
2. **每跨一次 agent 边界都必须显式注入/提取 context**（HTTP 调模型、MCP 工具、子进程）。否则会出现**孤儿 span、trace 断裂**。W3C tracecontext 头是标准载体 [56]。
3. **成本归因要把 token 用量作为 span attribute 挂在「每一次模型调用」上**，而不是挂在会话或全局。⚠ OTel 的 GenAI 语义约定的具体 URL 与指标名**本次未验证**，请查阅 OTel 官方 semconv 仓库。

**⚠ 并发下的 trace 头号 bug**：用**线程局部变量或全局变量**存放「当前 span」，在 asyncio / goroutine 并发下会**串线**（A 任务的 span 被 B 任务覆盖）。正确做法是 **`contextvars`**（Python/Node 的 `AsyncLocalStorage`）或**显式传参**。另外 **fire-and-forget 的 task 会丢失 context** [56]。

**并发调试的实操清单**：
- 每个并发单元带**唯一 id**（DSH：`<kind>-N` job id、durable subagent id、run id）。
- **事件成对**（start/end 必须匹配，取消也要合成 end）。
- **记录归属**（enabled by：owner / session / scope）。
- **成本挂在 span 上**，而不是全局累加。
- **不要 busy-poll**（DSH 明确禁止），用通知。
- **⚠ 并发正确性需要专门的测试工具**：Tokio 用 **Loom** 抓出了 **10 个以上**常规测试漏掉的并发 bug [48]。对 agent 并发，对应的做法是**确定性重放 + 注入延迟/乱序**。

### B8. 并发下的 LLM 侧约束：Rate Limit、TPM/RPM、独立上下文、成本放大

**这是 agent 并发与普通并发最根本的区别所在。**

**(1) 并发上限的真实瓶颈是 provider 配额，不是 CPU。**
- OpenAI 与 Anthropic 都按 **RPM（requests per minute）** 与 **TPM / ITPM / OTPM（tokens per minute，分输入/输出）** 双维度限流 [3][6]。Anthropic 的限额按 usage tier 分层，并返回 `retry-after` 头提示退避时间 [3]。
- 含义：**你的并发上限应该由 `min(CPU 并行度, RPM 额度, TPM 额度)` 决定**，而通常 TPM 最先被打爆。
- **⚠ 只限 RPM 不限 TPM，仍会被 429 打爆** [46]。
- **两个可确证的结构性事实**：
  1. **Anthropic 的 RPM 门槛显著低于 OpenAI**（第三方汇总给出的 Tier 1 数字是 **50 RPM vs 500 RPM**，差一个数量级）[21]。
  2. **限额是组织级共享的** —— 所以「**给每个 agent 配一个 API key**」**并不能绕过限流** [21]。

  ⚠ **不确定**：具体的 tier 数值（Anthropic Tier 1 50 RPM / 40k TPM、Tier 4 4000 RPM / 400k TPM；OpenAI Tier 1 500 RPM / 30k TPM、Tier 5 10000 RPM / 5M TPM）来自**第三方博客汇总，未与官方文档核对**；且 platform.claude.com / platform.openai.com 在本环境**均无法抓取**。**引用这些数字前请自行到官方文档核对。**
- 超限的典型表现是 **429**，处理不当会形成**重试风暴**（见 B6）——注意 SRE 的 10k→11k→1k 教训：**过载后需要把流量降到远低于容量才能恢复** [47]。

**(2) 每个并发单元有独立的上下文窗口 —— 这既是优势也是成本源。**
- Anthropic 明确指出子智能体的核心价值在于**上下文压缩**：
  > Subagents facilitate compression by operating **in parallel with their own context windows**, exploring different aspects of the question simultaneously before **condensing the most important tokens** for the lead research agent。
  > —— [1]
- 但代价是：**「压缩」这个动作本身要花 token**，而且**父 agent 无法看到子 agent 的中间过程**（DSH：「The model sees one final outcome, **never intermediate child messages**」）。

**(3) 成本放大 —— 真实数字**：

| 指标 | 数值 | 来源 |
|---|---|---|
| 普通 agent vs chat | **约 4×** token | Anthropic [1] |
| **多智能体 vs chat** | **约 15×** token | Anthropic [1] |
| Token 用量对性能方差的解释力（BrowseComp） | **80%** | Anthropic [1] |
| 三因素（token / 工具调用数 / 模型选择）合计解释力 | **95%** | Anthropic [1] |
| 多智能体 vs 单 agent Claude Opus 4（内部研究评测） | **+90.2%** | Anthropic [1] |
| 并行化（3–5 subagent + 3+ 并行工具）带来的研究耗时下降 | **最多 90%** | Anthropic [1] |
| 改进工具描述后的任务完成时间下降 | **40%** | Anthropic [1] |
| 早期版本为简单查询生成的子智能体数 | **50 个**（反模式） | Anthropic [1] |
| 触发上下文截断的窗口 | **200,000** token | Anthropic [1] |
| 无协调 agent 在争用下的失败率 | **72–100%** | HiveMind [46] |
| 加协调后的失败率 | **0–18%** | HiveMind [46] |
| 并发中被**浪费掉**的计算 | **48–100%** | HiveMind [46] |
| 11 个并行 agent 的动机事故失败率 | **27%**（3/11 死于连接重置与 502） | HiveMind [46] |
| 协调代理的额外延迟开销 | **<3 ms** | HiveMind [46] |

> **HiveMind 的动机事故值得单独强调**：11 个并行 agent 中 3 个死亡，而 **API 的总容量其实足够串行服务全部 11 个**。也就是说——**并发把「容量足够」变成了「失败」**。这才是「并发不是免费的」最锋利的证据 [46]。

**Anthropic 的关键结论**（直接引用，这是选型的第一原则）：
> Multi-agent systems work mainly because **they help spend enough tokens to solve the problem**… **For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance.**
> Further, **some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit** for multi-agent systems today. For instance, **most coding tasks involve fewer truly parallelizable tasks than research**, and LLM agents are **not yet great at coordinating and delegating to other agents in real time**。
> —— [1]

**(4) 上下文隔离对 KV Cache 的影响。**
- 独立上下文的代价是**KV cache 不共享**。DSH 明确：「KV Cache effect: **Independent of the parent request cache and of sibling children**」。
- 反过来，**保前缀稳定就能保 cache**：DSH 在每个工具的 Model Experience 里都标注了「Prefix-stable while … unchanged」。
- **真实权衡案例**：DSH 的 `fork` 后端**故意关闭模型选择**，因为选不同模型会让继承的历史失去 KV cache 复用资格（`dsh-base/cordis.patch.yml`:356-358）。

**(5) 输出大小的并发放大。**
- N 个并发 agent 各返回大结果，父上下文瞬间爆炸。
- 三层防御（DSH 实测装配）：
  - `dsh-spill-policy`（`maxInlineBytes: 50000`）：超限结果变 head/tail 预览 + 落盘 locator。
  - `dsh-compaction-tool-result-pruner`（`thresholdChars: 8192`, head 4096 / tail 1024）：在会话压缩器之前先剪工具结果。
  - `dsh-output-retention`：`ItemRetainer` / `TextRetainer`，保证不返回**非法 UTF-8 切割**。

### C1. Anthropic 多智能体研究系统

**并发模型**：**Orchestrator-Worker**。Lead agent（Claude Opus 4）分析查询、制定策略、**并行派生 subagent**（Claude Sonnet 4），subagent 独立搜索并把发现回传，Lead 综合后再决定是否继续派生，最后交给 CitationAgent 处理引用 [1]。

**实现要点**：
- Lead agent 把计划**先存到 Memory**，因为「if the context window exceeds **200,000 tokens** it will be truncated and it is important to retain the plan」[1]。
- **两种并行化**：「(1) the lead agent spins up **3-5 subagents in parallel** rather than serially; (2) the subagents use **3+ tools in parallel**」。这两项改动让复杂查询的研究时间**最多减少 90%** [1]。
- **规模规则写进 prompt**：简单事实查找 1 agent / 3–10 次工具调用；直接比较 2–4 subagent / 各 10–15 次调用；复杂研究 >10 subagent [1]。
- **子智能体输出直写文件系统**，只回传轻量引用，以减少 "game of telephone" [1]。
- **生产可靠性**：durable execution + resume（不能从头重启，因为「restarts are expensive and frustrating」）、retry logic、regular checkpoints；用 **rainbow deployments** 让新旧版本同时运行，避免部署打断在飞 agent [1]。

**坑（官方自述）**：
- **同步执行是瓶颈**：
  > Currently, our lead agents execute subagents **synchronously**, waiting for each set of subagents to complete before proceeding… the lead agent **can't steer subagents**, subagents **can't coordinate**, and the **entire system can be blocked while waiting for a single subagent** to finish searching。Asynchronous execution would enable additional parallelism… But this asynchronicity adds challenges in **result coordination, state consistency, and error propagation**。
- **过度派生**：早期「spawning **50 subagents** for simple queries」。
- **职责重叠**：任务描述不具体导致多个 subagent 做同一件事。
- **错误复合**：「minor changes cascade into large behavioral changes」；「One step failing can cause agents to explore entirely different trajectories」。
- **不适合的场景**：多数编码任务；需要所有 agent 共享同一上下文的领域。

**来源**：[1]

### C2. OpenAI Agents SDK / Swarm

**并发模型**：SDK **不提供内建的 fan-out API**，而是把并发下放给宿主语言——Python 用 `asyncio.gather`、JS 用 `Promise.all` 并发跑多个 `Runner.run`。Agent 之间只有两种关系：**`handoff`（转移会话控制权）** 与 **agents-as-tools（不转移控制权）**[59][60][61]。旧版 `Swarm` 是被 Agents SDK 取代的实验性前身 [8]。

**实现要点**：
- **官方的并行写法**（`examples/agent_patterns/parallelization.py`）：
  ```python
  with trace("Parallel translation"):
      results = await asyncio.gather(
          Runner.run(spanish_agent, msg),
          Runner.run(french_agent, msg),
          Runner.run(italian_agent, msg),
      )   # 跑三次取最优
  ```
  注意 `with trace(...)` 把三个并发 agent 合成**一条 trace**——这是并发可观测性的正确做法 [62][4]。
- **`handoff` 的细节**：handoff 以**工具**形式暴露给 LLM，默认工具名 `transfer_to_<agent_name>`；`handoff()` 支持 `on_handoff`、`input_type`、`input_filter`、`is_enabled`、`tool_name_override` [60]。
- **`handoff` vs `as_tool` 的本质区别**：handoff 让新 agent **继承历史并接管对话**；`as_tool()` 只把生成的输入交给子 agent，**原 agent 继续持有对话** [60][61]。
- **Guardrails 默认就是并发的**：`input_guardrails` **默认与 agent 并发执行**，`runInParallel=False` 可改为阻塞等待 [5]。
- **运行入口**：`Runner.run`（async）/ `Runner.run_sync`；流式事件类型为 `raw_response_event` / `run_item_stream_event` / `agent_updated_stream_event`，嵌套 agent 可用 `as_tool(..., on_stream=...)` 消费子流 [61]。
- **状态管理三选一**：`session=` / `previous_response_id` / `conversation_id`，必须选定一种。官方提供 SQLite / Redis 等 session 后端。
- **托管侧并发原语** `ProgrammaticToolCallingTool()`：模型生成一段跑在托管 V8 里的 JavaScript，可循环/分支/**并行**调用多个工具，只回传一个结果——这与 DSH 的 `workflow` 工具是同一思路（模型写代码来编排并发）。
- **JS/TS SDK**：`Agent`、`handoffs: (Agent | Handoff)[]`、`Agent.asTool()`、`run(agent, input, { stream: true })` [63]。

**坑**：
- **`handoff` ≠ 并发**。handoff 是**独占式控制权转移**（同一时刻只有一个 agent 在跑）；要真并发必须显式 gather。这是最常见的概念混淆点。
- **`as_tool` 的嵌套 run 默认不继承父会话历史**，要显式传同一个 `session` [61]。
- **无内建并发上限**。SDK 不提供 semaphore 式闸门，**必须自己用 `asyncio.Semaphore` 包装**，否则很容易一次放出去几十个请求打爆 RPM/TPM。⚠ 官方文档未明文说明「无内建上限」，此结论来自其 API 表面（只暴露 running 原语，未暴露并发配置）——**按推断处理**。
- **错误处理要自己写**：`asyncio.gather` 默认遇到第一个异常就抛出，其余任务不会自动取消，需 `return_exceptions=True` 或 `TaskGroup` 才有「部分失败」语义 [34]。
- **限流、错误聚合、trace 归并（`groupId` / `trace`）全都要自己写**。
- **JS 侧 `Agent.clone()` 会与原 agent 共享 `tools` / `handoffs` 数组**——文档明确警告：改克隆体会影响原对象 [63]。这是并发下典型的**意外共享可变状态**。
- **`max_turns` 超限抛 `MaxTurnsExceeded`**；护栏触发抛 `GuardrailTripwireTriggered`。另外 **input guardrail 只对链上第一个 agent 生效，output guardrail 只对产出最终输出的 agent 生效** [5]——并发分支上的护栏覆盖有盲区。

**来源**：[4][5][8][34][59][60][61][62][63]

### C3. LangGraph

**并发模型**：受 Google Pregel 启发的**离散超步（super-step）消息传递模型**，属于 **BSP（Bulk Synchronous Parallel）** 屏障模型 [7]。

**实现要点**：
- **同超步并行**：「Nodes that run in parallel are part of the same super-step… any node with multiple outgoing edges → **all** destination nodes execute in parallel as part of the next superstep」[7]。
- **`Send(node, state)`**：从条件边返回，用于 **map-reduce 风格的动态扇出**（发送数量在运行期才知道）[7][8]。
- **`Command(update=, goto=, graph=, resume=)`**：把状态更新与路由合并到一个返回值。
- **reducer**：`Annotated[list, operator.add]` 或 `add_messages` 声明「多个并行写如何合并」；`Overwrite` 可绕过 reducer [7]。
- **`interrupt()` + checkpointer + `thread_id`**：HITL 的暂停/恢复 [10]。
- **`durability` 三档**：`"exit"` / `"async"` / `"sync"`；checkpointer 每个超步 + 每个任务级写入（`put_writes`）[9]。
- **上限/旋钮**：`recursion_limit` 默认 **1000** 超步（超出抛 `GraphRecursionError`）；`RemainingSteps` 托管值；`config["metadata"]["langgraph_step"]` [7]。

**坑**：
- **并行写同一个无 reducer 的 key 直接报错** `INVALID_CONCURRENT_GRAPH_UPDATE` [8]。**默认 reducer 是覆盖，不是合并**。
- **合并型 reducer 下返回空 list 不清空**——需要 `Overwrite`。
- **`Command` 只加动态边，静态边仍会执行**——两者混用会**双跑**。
- **并行分支同时 interrupt** 时要用 `Command(resume={interrupt_id: value})` 按 ID 配对 [10]。
- **interrupt 恢复时整个节点从头重跑** → interrupt 前的副作用必须幂等 [10]。

**来源**：[7][8][9][10]

### C4. AutoGen

**并发模型**：分两代。
- **v0.2**：`GroupChat` + `GroupChatManager`，**每轮串行**地「选一个说话人」，本质是串行对话循环 [13]。
- **v0.4+ AgentChat**：基于 `autogen_core` 的 **asyncio 单线程事件驱动 actor 运行时** —— 消息经 **topic 发布/订阅**路由给 agent，agent 处理 `on_message`，异步流式用 `on_messages_stream` [11]。

**实现要点**：
- `SingleThreadedAgentRuntime`：`publish_message`、`TopicId` / `TypeSubscription`、`send_message`；内部有 `_process_publish(PublishMessageEnvelope)` 这样的消息处理入口 [11]。
- 分布式版：`GrpcWorkerAgentRuntime`。
- `autogen_agentchat.teams` 提供 `RoundRobinGroupChat`、`SelectorGroupChat`（LLM 选说话人）、`Swarm`、`MagenticOneGroupChat`，统一 `termination_condition`（如 `StopAfterNMessages`）[11]。
- **上限旋钮**：`max_turns`、`termination_condition`、`max_tool_iterations`。

**坑**：
- **Team 是串行的**。round-robin / selector 都是「一次一个说话人」。**想并行必须绕过 Team，自己 `asyncio.gather` 跑多个 agent** [11]。
- **Team 本身无内置 checkpoint / HITL**——一旦启动就持续跑到终止条件。
- **迁移**：微软已发布《AutoGen to Microsoft Agent Framework Migration Guide》，AutoGen 的 `Team` 被类型化图 `Workflow`（`WorkflowBuilder`、`ctx.send_message(target_id=...)`、`ConcurrentBuilder` / `SequentialBuilder` / `MagenticBuilder`）取代，并新增了 AutoGen 没有的 **checkpointing**（`FileCheckpointStorage`，可从任意 superstep 恢复）与 **request_info / response_handler 人工介入**；`SelectorGroupChat`、`Swarm` 仍在路线图上 [12]。

**来源**：[11][12][13]

### C5. CrewAI

**并发模型**：`Process` 是一个 Enum，**只有 `sequential` 与 `hierarchical` 两个值** [64]。默认 `sequential` 是顺序流水线；`hierarchical` 引入 manager 做规划-分派-验收。**真正的并行只能靠 Task 级的 `async_execution=True` 做有限扇出，再用 `context=[...]` 扇入**。

**实现要点**：
- **`Process.sequential`**：任务按定义顺序执行，前一个输出作为后一个的上下文。
- **`Process.hierarchical`**：任务**不预先绑定 agent**，manager 按角色/能力动态分派并审核输出；**必须**提供 `manager_llm` 或 `manager_agent`，否则直接报错 [64]。
- **并行扇出**：`Task(async_execution=True)` —— crew **不等它完成**就继续下一个任务 [65]。
- **扇入**：后续 Task 用 `context=[task_a, task_b]` **等待并合并**这些异步结果 [65]。
- **执行入口**（这里有个大坑，见下）：
  | 入口 | 语义 |
  |---|---|
  | `kickoff()` | 单次执行 |
  | `kickoff_for_each(inputs=[...])` | **对每个输入依次执行（串行！）** |
  | `akickoff()` / `akickoff_for_each()` | **原生 async**，官方称「高并发负载推荐」 |
  | `kickoff_async()` / `kickoff_for_each_async()` | 线程池（`asyncio.to_thread`）包装 |
- **并发上限/旋钮**：
  | 层级 | 字段 | 默认 |
  |---|---|---|
  | Crew | **`max_rpm`**（**覆盖** agent 级 max_rpm） | — |
  | Crew | `memory`（短期/长期/实体）、`cache`、`planning` / `planning_llm`、`stream=True` | — |
  | Crew | `checkpoint` / `CheckpointConfig`（默认 `task_completed` 触发；`Crew.from_checkpoint()` 恢复） | — |
  | Agent | `max_iter` | **20** |
  | Agent | `max_retry_limit` | **2** |
  | Agent | `max_execution_time`、`allow_delegation`（默认 **False**）、`respect_context_window`（超窗自动摘要） | — |
  | Task | `guardrail` / `guardrails` / `guardrail_max_retries` | **3** |
- **`usage_metrics`** 提供成本统计。

**坑**：
- **`kickoff_for_each` 命名极具误导性——它是串行循环，不是并行**。这是 CrewAI 最容易踩的坑。要并发必须用多个 `akickoff()` 或 `akickoff_for_each()` 再配 `asyncio.gather` 组合；官方明确推荐原生 async，**因为 memory / knowledge 检索本身也是原生异步的** [64][65]。
- **并行粒度只到 task**。单个 task 内部仍是**单 agent 的顺序 ReAct 循环**，受 `max_iter: 20` 约束——所以 task 内的工具调用是串行的。
- **Hierarchical 多付一次 manager LLM 调用的成本与延迟**，且 manager 的决策质量成为**单点**（不像并行扇出有天然冗余）。
- **限流字段是 `max_rpm`**。⚠ 公开文档中**未发现名为 `rate_limiter` 的参数**——不要臆造。请按具体版本核对源码。
- **`allow_delegation` 默认是 `False`**：agent 之间默认**不能互相委派**，这与「多智能体」的直觉预期相反。
- 旧版 `allow_code_execution` / `code_execution_mode` 已弃用，`CodeInterpreterTool` 已从 crewai-tools 移除（官方建议改用 E2B / Modal 等外部沙箱）。
- ⚠ 内部的执行器实现（是否线程池、默认并发度）未取得官方一手证据。

**来源**：[14][15][64][65][66][67]

### C6. Microsoft Magentic-One

**并发模型**：**单 Orchestrator 的「轮次制」动态路由**——每一轮用 progress ledger 选出「下一个该发言的 agent」并下指令。**本质是串行委派 + 双账本闭环重规划，而不是并行扇出** [16][17][68]。

> 这一点必须说清楚：**Magentic-One 不是并发模式，而是「用重规划代替并发」的模式。** 把它列进本报告的价值正在于这个反例。

**实现要点**：
- **团队构成**：Orchestrator + WebSurfer（浏览器）+ FileSurfer（文件）+ Coder（写代码）+ ComputerTerminal（执行）[16][17]。
- **双账本机制**：
  - **外层 task ledger**：记录 given / verified facts、to-lookup、to-derive、educated guesses + 计划。
  - **内层 progress ledger**：由 **5 个问题**生成——任务是否完成 / 是否在原地打转 / 是否有进展 / 下一个该谁发言 / 下什么指令 [17]。
- **停滞处理**：停滞计数超阈值即跳出内层、反思重规划，并**强制所有 agent 清空上下文、重置状态**（论文实验中阈值 ≤2 继续）[17]。
- **ComputerTerminal 是确定性的**（不调 LLM，直接跑 Python/shell）；WebSurfer 用 **set-of-marks** 多模态定位 [17]。
- **实现基于 AutoGen v0.4**；默认模型 `gpt-4o-2024-05-13`，另有 outer loop + Coder 换 o1-preview 的配置 [17][68]。
- **已并入 Microsoft Agent Framework**，成为 Magentic 编排模式 [18]：
  ```python
  MagenticBuilder(
      participants=[...], manager_agent=...,
      max_round_count=10, max_stall_count=3, max_reset_count=2
  ).build()
  ```
  `RequirePlanSignoff` / plan review 提供 HITL 计划审批（**Python 默认关、.NET 默认开**）；事件 `MagenticPlanCreatedEvent` / `MagenticReplannedEvent` / `MagenticProgressLedgerUpdatedEvent`；Python 可用 `intermediate_output_from=[...]` 把参与者输出以 "intermediate" 事件流出 [18]。
- **评测工具 AutoGenBench**：每个任务起**全新 Docker**，并支持 "launch multiple tasks **in parallel**" 来加速评测 —— 注意**并发发生在评测层，不在 agent 层** [17]。

**关键数字**：GAIA **38%**、WebArena **32.8%**、AssistantBench accuracy **27.7%**。WebArena 自建 val/test 分裂：val **35.1%**（148/422）vs test **30.5%**（119/390），作者自陈存在 "mild over-fitting" [17]。

**坑**：
- **吞吐不随 agent 数量提升**（轮次制，无 fan-out）。加 agent 只增加每轮的可选性，不增加并行度。
- **每次重规划清空上下文** → 长任务反复丢失上下文，这是「重置换正确性」的代价。
- **Agent Framework 明确警告两点** [18]：
  1. **不要**在并发/交错的 workflow 之间共享有状态的 `manager` 实例——应使用 `manager_factory` 为每个 workflow 隔离状态。**这是一个典型的「共享可变状态」并发坑。**
  2. 原论文的 4 个专用 agent 是为特定任务设计的，**替换为自定义 agent 后「性能表现未被验证」**。
- **模型安全拒答是长任务系统的现实风险**：o1-preview 在 WebArena 上拒答了 **26%** 的 GitLab 任务与 **12%** 的 Shopping Admin 任务，使该配置无法公平比较 [17]。

**来源**：[16][17][18][68]

### C7. Google ADK / Vertex AI Agent Engine

**并发模型**：**确定性模板工作流**（`SequentialAgent` / `ParallelAgent` / `LoopAgent`）+ `LlmAgent` 通过 `sub_agents` 委派 [19][20]。

**实现要点**：
- **`ParallelAgent(sub_agents=[...])`**：调用 `run_async()` 时**同时启动每个子 agent**；**结果顺序不确定** [19]。
- **`LoopAgent(sub_agents=[...], max_iterations=N)`**：退出靠子 agent 工具里设 `tool_context.actions.escalate = True` [20]。
- **跨分支传数据**：靠 `output_key` 写入 session state。
- **`Runner.run_async(user_id, session_id, message)`**：产出 `Event` 流。
- **会话与记忆分层**：`SessionService` 管会话/state；`MemoryService` 管跨会话记忆 —— Vertex AI Agent Engine 的 **Sessions / Memory Bank** 即其云端实现 [21][23]。
- **A2A 协议**：Agent Card 发现 + Task 生命周期（`SendMessage` / `SendStreamingMessage` / `GetTask` / **`CancelTask`** / `SubscribeToTask` / push notification config），规范明确包含 **Asynchronous Processing** 与 **Idempotency** 语义 [22]。

**坑**：
- **无内建并发上限**：并行度只受 asyncio 事件循环与模型配额约束 [19]。
- **分支间不共享 history/state**：官方明确警告，要共享必须显式用 `InvocationContext`（**自己加锁防竞态**）或外部存储；**并行写同一个 state key 有竞态风险** [19]。
- **结果顺序不确定**：`ParallelAgent` 的返回顺序不保证，不能依赖。
- **ADK 2.0 已用 graph-based / dynamic workflows 取代模板工作流**（Python/Go）——即模板式的 `SequentialAgent`/`ParallelAgent` 属于上一代抽象 [19]。

**来源**：[19][20][21][22][23]

### C8. Temporal / Airflow / Prefect 在 agent 编排中的用法

#### Temporal —— 确定性重放 + 事件溯源

- **并发模型**：workflow 代码必须**确定性**，所有非确定性 IO 放进 Activity；状态通过 **Event History 重放**恢复 [24]。
- **并发表达**：workflow 内用 `asyncio.gather` 并发调度多个 Activity / Child Workflow（走 SDK 的确定性 event loop）[24]。
- **消息传递**：`@workflow.signal` / `@workflow.query` / `@workflow.update`（带 validator）[26]。
- **Child Workflow**：各自独立 Event History，**可跑在独立 Worker 上** [25]。
- **Activity 语义**：「只执行一次并把结果写进 Event History，重放时**复用结果不再重跑**」——这天然提供了**幂等性保障**，是 agent 编排里最有价值的一条 [24]。
- **硬上限**：单 Workflow Event History **51200 events 或 50MB**（10240/10MB 告警）；默认最多 **2000** 个未完成 Child Workflow；单 parent 建议 ≤ **1000** 个子工作流 [24][25]。
- **坑**：重放要求「同一 history 必须做同样决策」——`Date.now()`、随机数、未包在 Activity 里的网络调用都会破坏确定性；Query 不能改状态；Continue-As-New 不能在 Update handler 里用 [24]。

#### Airflow —— DAG 依赖驱动

- **并发模型**：调度器按 DAG 依赖把 TaskInstance 丢给 executor；**动态任务映射**让任务数在运行期由上游输出决定 [27]。
- **旋钮**：`[core] parallelism`（实例级并发 task 上限）、`max_active_tasks_per_dag`、`max_active_runs_per_dag`、`max_map_length`、`dagrun_timeout` / SLA [28]。
- **坑**：`task.expand(x=[...])` 只能传关键字参数；下游拿到**惰性代理** `LazySelectSequence`（直接 `print` 显示 `[15 items]`，`list(...)` 会一次性拉全部上游值造成性能问题）；推 XCom 时也会触发转换警告 [27]。
- **调度饥饿**：Apache 有专门提案 **AIP-100 "Eliminate Scheduler Starvation On Concurrency Limits"**，说明「按并发上限调度」在实践中会导致饥饿。

#### Prefect —— 显式 submit

- **并发模型**：**同步调用 task 默认在主线程阻塞执行**；**只有 `.submit()` / `.map()` 才交给 task runner** 并发执行 [29]。
- **task runner 选择**：默认 `ThreadPoolTaskRunner`；CPU 密集用 `ProcessPoolTaskRunner`；分布式 `DaskTaskRunner` / `RayTaskRunner` [29]。
- **用法**：`future = task.submit(...)` → `future.result()`；`task.map()` 做扇出 [30]。
- **坑**：**默认不并发，忘了 `.submit()` / `.map()` 就退化成串行** [29]；线程池受 GIL 限制。

**在 agent 编排中的价值**：这些引擎提供的是 agent 框架普遍欠缺的**durable execution + 幂等 + 可观测 + 重试**，代价是你必须在它们的约束内编程（确定性、序列化、Event History 上限）。

**来源**：[24][25][26][27][28][29][30]

#### C9.3 DSH 的并发原语与语义（实测配置与源码）

**(1) Workflow 引擎的脚本 hook 契约**（`dsh-tool-workflow/lib/types/index.js`:96-104，逐字）

| Hook | 签名 | 语义 | 屏障 |
|---|---|---|---|
| `agent(prompt, opts?)` | `Promise<any>` | 跑一个子 agent 到完成。无 `opts.schema` 时 resolve 为子 agent 最终文本；有 schema 时 resolve 为**校验过的对象**。**子失败 resolve 为 `null`** | — |
| `pipeline(items, ...stages)` | `Promise<any[]>` | 每个 item **独立**穿过各 stage，**stage 之间无 barrier**。stage 收到 `(prev, item, index)`。**普通 stage 抛错把该 ITEM 降为 `null` 并跳过其剩余 stage** | **无** |
| `parallel(thunks)` | `Promise<any[]>` | 并发运行零参函数并 **await ALL**。抛错的 thunk resolve 为 `null` | **有** |
| `phase(title)` | — | 开始一个进度阶段 | — |
| `log(message)` | — | 叙述进度 | — |
| `args` | — | 工具调用的 `args` 输入原样 | — |

> **契约要点**：「Misused hooks (bad arguments, unknown options, unsupported schemas, tripped caps) throw errors that **ALWAYS kill the script** — they never dissolve into a per-item `null`。」
> 即：**业务失败 → item 级降级；契约违反 → 全脚本致命**。这个二分是并发脚本设计的好范式。

**(2) 并发预算三维**（`dsh-workflow-worker-thread/README.md`）

| 字段 | 默认 | 说明 |
|---|---|---|
| `maxConcurrentAgents` | `0` | 并发 `agent()` 上限；**`0` 解析为 `min(16, max(1, availableParallelism() - 2))`** |
| `maxTotalAgents` | `1000` | 单 run 的 `agent()` 总量，**runaway-loop 兜底** |
| `maxItemsPerCall` | `4096` | 单次 `parallel()` / `pipeline()` 接受的 item 数 |
| `syncTimeoutMs` | `5000` | 脚本初始同步片的 VM 超时 |
| `disposeGraceMs` | `5000` | 强制结清/终止 worker 的界限 |

**(3) 子智能体并发**（`dsh-tool-subagent/README.md` + `dsh-base/cordis.patch.yml`）

| 字段 | 默认 | 说明 |
|---|---|---|
| `provider` | required | `spawn` / `fork` / `acp` / … |
| `backgroundMode` | `one-shot` | `one-shot` 默认前台；`continuable` 默认后台且需 provider 支持 |
| `enableRunInBackground` | `true` | 是否暴露 `run_in_background` |
| `maxDepth` | **`3`** | 绝对委派深度上限；`0` 禁止委派；`'provider-managed'` 交给外部 provider |
| `modelSelectionSettings` | `false` | 是否暴露 provider/model/effort 选择（需 provider 支持 `agentOptions`） |

DSH 的**同一插件双实例装配**（`dsh-base/cordis.patch.yml`:349-367 逐字）：

```yaml
    - id: tool-subagent
      name: '@deepseek-ai/dsh-tool-subagent'
      config:
        provider: spawn
        toolName: subagent
        backgroundMode: continuable      # ← 常驻、可续聊

    - id: tool-subagent-fork
      name: '@deepseek-ai/dsh-tool-subagent'
      config:
        provider: fork
        toolName: subagent_fork
        backgroundMode: one-shot         # ← 一次性
```

**同一插件、两个 id、两种并发/生命周期语义** —— 这是「能力复用 + 语义分化」的干净范例。而且 fork 行有一句关键注释：

> Fork omits model selection so provider/model stay equal to the parent and the **inherited history remains eligible for KV Cache reuse**。This base row stays one-shot; preset layers may select continuable mode **without adding a child-only system-prompt section or tool schema ahead of that history**。

**为了守住 KV cache 的前缀复用资格，主动放弃模型选择与额外 prompt 段落。**

**(4) 委派深度的防绕过设计**（`dsh-subagent/lib/types/depth.js` 逐字）

```js
export function delegationDepthOf(agent) {
    const runtime = agent.options.subagentDepth;
    if (runtime !== undefined && (!Number.isSafeInteger(runtime) || runtime < 0 || Object.is(runtime, -0))) {
        throw new TypeError('agent subagentDepth must be a non-negative safe integer');
    }
    // The header value was validated at the session boundary.
    return Math.max(agent.session.header.delegationDepth ?? 0, runtime ?? 0);
}
```

> The persisted session header is **authoritative and monotone**: runtime `AgentOptions.subagentDepth` may **DEEPEN** the count but can never **lower** it — **a resumed child arrives with fresh options, and counting it from zero would let it delegate as if it were top-level**。

**(5) 后台作业准入**（`dsh-jobs-local/README.md` 逐字）

| 字段 | 默认 | 说明 |
|---|---|---|
| `maxConcurrentJobsPerOwner` | **`10`** | 每个精确 owner（或共享 unowned 桶）的 `running` + `stopping` 作业上限 |

> The limit counts the exact owner's `running` and `stopping` records；all unowned jobs share one separate service-level bucket。**Terminal history does not occupy capacity**, and only a producer's `done` settlement releases a stopping job's place。**At capacity, `start()` fails before the producer runs**, with an error that names the limit and tells the agent to kill an unneeded job, wait for it to finish, and retry — the registry **neither queues nor preempts**。

**(6) 完成通知的投递策略**（`dsh-tool-jobs/README.md`）

| 字段 | 默认 | 说明 |
|---|---|---|
| `waitTimeoutMs` | `30,000` | `wait: true` 且未给 `timeout_ms` 时的等待 |
| `maxWaitTimeoutMs` | `600,000` | 模型可给等待的上限，超出**向下钳制** |
| `completionDelivery` | `wakeup` | `wakeup` 唤醒 idle owner；`quiet` 让通知留在待处理 |
| `maxConsecutiveWakes` | `3` | owner 被唤醒开轮的次数上限，超出则**降级为注入** |

> **The bound exists because the chain is self-exciting** — a woken turn may start the background job whose completion wakes it again。

**(7) 模型可见的并发指导（`dsh-tool-subagent/lib/index.js`:576-579 逐字）**

> Use `${toolName}` **in the background by default**。**Start independent delegations together in one assistant message and continue useful work while they run**。Set `run_in_background: false` only when your next action depends on it。

注意 `isConcurrencySafe: () => true`（同文件 :489）——DSH 显式把 subagent 工具标记为并发安全。

**(8) 并发安全与检查点**
- `dsh-session-checkpoint-policy`：在**模型请求前**、**顶层工具副作用前**、**下一个 agent step 前**做检查点；**fail-closed** —— 检查点写失败则模型调用与工具体都不执行。
- DSH 对**中断的工具调用**的处理：「recover with an **unknown outcome** instead of an automatic retry」。
- `dsh-atomic-write`：跨进程 writer lock 串行化 read-modify-write。

**(9) 定时并发的边界**（`dsh-schedule/README.md`）
- 重复提醒的最小间隔 **5 分钟**，且**对齐首次设定时间**。
- **due reminders appear as ordinary follow-up messages after the conversation becomes idle; the agent never interrupts a running turn**。
- 一个重复提醒错过多次触发时，「presents **only its latest due occurrence, not a backlog**」——**防雪崩的合并语义**。
- ⚠ **已知限制**：session 关闭时到期的提醒「stays overdue until a future live root agent resumes the session」「**nothing is sent outside the session**」；且「repeating reminders run on a **fixed interval only**」（无 cron 式规则）。

## D. 选型与踩坑

### D1. 并发模式选型决策表

| 任务特征 | 推荐模式 | 理由 |
|---|---|---|
| 子任务**完全独立**、数量已知 | **A1 扇出/扇入** + 有界并发 | 最简单、收益最直接 |
| 子任务独立但**数量在运行期才知道** | **A3 DAG + 动态扇出**（LangGraph `Send` / Airflow `expand` / `pipeline`） | 需要动态拓扑 |
| **多阶段、各阶段耗时不均** | **A2 流水线无 barrier** | 避免 barrier 造成的空转；DSH 明确 prefer `pipeline` |
| 需要**每一步都等全部结果**才能决策 | Barrier（DSH `parallel` / LangGraph 超步 / gather） | 只有这种场景才该用 barrier |
| 任务数 >> 合理并发度 | **A4 工作池 + 有界队列** | 背压保护下游 |
| 下游是稀缺资源（provider 配额/DB） | **A4 + fail-closed 准入**（DSH 的 no-queue 策略） | 早拒绝好过晚雪崩 |
| **多 agent 改同一份代码/文件** | **A5 git worktree / shadow workspace** | 物理隔离优于加锁 |
| 多 agent 改同一份**结构化数据** | **A5 乐观锁 + 版本号**，或**单向汇总**（reducer） | 避免 lost update |
| 递归可分解的任务 | **A6 嵌套扇出 + maxDepth + 总量上限** | 两道闸缺一不可 |
| 长时在线、持续收消息 | **A7 Actor / 消息驱动** | 邮箱 + 监督树 |
| **绝大部分时间在等 I/O**（LLM 调用的常态） | **A8 async/await** | 成本最低、最该默认 |
| 需要**真 CPU 并行**（Python） | **A9 多进程** | GIL 让线程无效 |
| 跑**不可信代码** | **A9 容器/独立进程** | 线程 + vm 不是安全边界 |
| 有**高风险动作需人批** | **A10 异步审批 + 持久化挂起 + fail-closed 超时** | 不能阻塞整条链 |
| 任务分钟～小时级 | **A11 后台作业 + 事件通知** | 不占用前台轮次 |
| **延迟敏感**且任务无副作用 | **A12 Best-of-N / 竞速** | 花钱买延迟 |
| **正确率敏感**、可自动验证 | **A12 Best-of-N + verifier** | 花钱买准确率 |
| 需要 **durable execution / 崩溃恢复** | Temporal / Airflow / Prefect（C8）或 DSH checkpoint | 框架级保障，别自己写 |
| **编码任务**（多数情况） | **单 agent 或小规模并行 + worktree 隔离** | Anthropic 明确说多数编码任务可并行部分少 [1] |

**第一原则（来自 Anthropic）**：多智能体之所以有效，主要是因为它**花掉了更多 token**。所以先问：**「这个任务的价值是否高到值得付 15× 的 token？」** 如果答案是否，就不要上多智能体 [1]。

### D2. 并发反模式黑名单

| # | 反模式 | 后果 | 真实案例 / 证据 | 正确做法 |
|---|---|---|---|---|
| 1 | **无限嵌套扇出** | `F^D` 指数爆炸 | Anthropic：「spawning **50 subagents** for simple queries」[1] | 深度上限（DSH `maxDepth: 3`）+ 总量上限（`maxTotalAgents: 1000`）**两道闸** |
| 2 | **无上限并发打爆 rate limit** | 429 风暴、退避雪崩 | OpenAI/Anthropic 的 RPM/TPM 双限流 [3][6] | semaphore + **指数退避 + 抖动** [32]；上限取 `min(CPU, RPM, TPM)` |
| 3 | **共享工作区覆盖写** | **静默 lost update** | LangGraph 对并行写无 reducer 的 key 直接抛 `INVALID_CONCURRENT_GRAPH_UPDATE` [8]；ADK 警告并行写 state 有竞态 [19] | worktree 隔离 / 乐观锁 / temp+rename+锁（DSH `dsh-atomic-write`） |
| 4 | **Barrier 导致流水线停顿** | 吞吐崩塌，慢 item 拖死全部 | DSH 明确区分：`parallel` 是 barrier「use **only** when a stage genuinely needs every prior result together」，多阶段应 prefer `pipeline` | 用无 barrier 的 pipeline |
| 5 | **上下文爆炸** | 成本失控、窗口溢出 | Anthropic：**200,000 token** 会触发截断，必须先把计划写进 Memory [1]；DSH 的 spill / 结果剪枝 | 子 agent 结果外部化（写文件回传引用）；输出上限 + spill |
| 6 | **retry 风暴 / 惊群** | 所有失败客户端同时重试，二次打爆 | AWS 的 jitter 经典文 [32] | **指数退避 + 随机抖动** + 熔断器 |
| 7 | **非幂等操作自动重试** | 重复副作用（重复下单/重复发信） | DSH：中断的工具调用「recover with an **unknown outcome** instead of an automatic retry」；LangGraph interrupt 恢复节点重跑需幂等 [10] | idempotency key [33]；不确定时不重试 |
| 8 | **静默失效的取消** | 永久占用并发槽位 → 容量泄漏 | DSH：「A producer cancel that returns without settling `done`… **can stall teardown while holding one capacity slot**」 | cancel 必须有「已停止」的确认信号 + 超时强杀 |
| 9 | **无界队列 = 无背压** | 内存爆炸 | 通用并发常识 | 有界队列 + 溢出策略（拒绝/降级/落盘） |
| 10 | **忘了显式提交** | 以为并发，其实串行 | Prefect：同步调用默认阻塞，**只有 `.submit()`/`.map()` 才并发** [29] | 显式 submit/map，并在 trace 里验证并发度 |
| 11 | **busy-poll 等作业** | 浪费 token 与配额 | DSH supervisor 提示词：「**do not busy-poll or sleep on one**」 | 事件通知 + `wait: true` 有界等待 |
| 12 | **通知自激循环** | 唤醒→起新 job→再唤醒，无限循环 | DSH：「the chain is **self-exciting**」，用 `maxConsecutiveWakes: 3` 打断 | 唤醒预算 + 用户输入重置 |
| 13 | **同步人机审批阻塞全局** | 人类延迟（分钟-小时）拖死全部并发 | Anthropic 承认同步执行「the entire system can be **blocked while waiting for a single subagent**」[1] | 异步挂起 + checkpointer + `thread_id` |
| 14 | **审批超时默认放行** | 安全漏洞 | DSH 全程 fail-closed（checkpoint、sandbox 拒绝即终局） | **超时 → 拒绝** |
| 15 | **污染 KV cache 前缀** | 成本上升、延迟上升 | DSH 为保 cache 复用**主动放弃 fork 的模型选择** | 保持 prompt 前缀稳定；别在历史前插入动态段落 |

| 28 | **护栏覆盖有盲区** | 并发分支绕过安全检查 | OpenAI Agents SDK：**input guardrail 只对链上第一个 agent 生效，output guardrail 只对产出最终输出的 agent 生效** [5] | 在每个并发分支上显式挂护栏 |

### D3. 可落地的并发设计 Checklist

**① 容量与限额**
- [ ] 定义了**瞬时并发上限**（semaphore / worker pool / `maxConcurrentAgents`）。
- [ ] 定义了**生命周期总量上限**（防 runaway loop；DSH 的 `maxTotalAgents`）。
- [ ] 定义了**单批规模上限**（防一次 fan-out 几千个；DSH 的 `maxItemsPerCall: 4096`）。
- [ ] 并发上限取 `min(CPU 并行度, RPM 配额, TPM 配额)`，而不是只拍脑袋。
- [ ] **RPM 与 TPM 两个维度都限了**（只限一个仍会被 429 打爆）[46]。
- [ ] **超额行为明确**：排队 还是 拒绝？（DSH 选**拒绝 + 明确错误**）
- [ ] **队列规模经过计算**，不是随手填（SRE：队列 < 线程池的 50%）[47]。
- [ ] 有**深度上限**（嵌套委派；DSH `maxDepth: 3`）。
- [ ] 深度计数**持久化且单调**，resume/fork 不能重置。
- [ ] 用了**超过一个**控制原语（准入 + 重试 + 预算 + 优先级 + 熔断），而不是只加 semaphore [46]。

**② 背压与队列**
- [ ] 所有队列**有界**。
- [ ] 队列满时的行为明确（阻塞 producer / 拒绝 / 降级 / 落盘）。
- [ ] 大输出有 **spill / 剪枝**（DSH：`maxInlineBytes: 50000`、`thresholdChars: 8192`）。
- [ ] 内存中的输出收集是**有界尾部 + 可选落盘**，不是无限缓冲。

**③ 同步语义**
- [ ] 每个并发点显式回答：**这里需要 barrier 吗？** 只有真需要全部结果时才用。
- [ ] 多阶段流程用**无 barrier 的 pipeline**。
- [ ] barrier 的代价被评估过（总延迟 = max(分支延迟)）。
- [ ] Join 的范围是「必要的那几个」而不是「全部」。

**④ 状态与隔离**
- [ ] 每个并发单元都有**私有上下文**（默认不共享，共享需显式）。
- [ ] 共享可变状态有 **reducer** 或**锁**或**版本号**。
- [ ] 并行写同一文件的场景有 **worktree 隔离** 或 **原子写 + writer lock**。
- [ ] 有共享存储时，明确**是否跨进程**（DSH 的 Activation 不跨进程 —— 这是硬边界）。
- [ ] 评估过 KV cache 前缀稳定性对成本的影响。

**⑤ 取消、超时、失败**
- [ ] 取消是**协作式 + 有界兜底**（DSH：共享 signal + `disposeGraceMs` 后强杀）。
- [ ] 取消信号**一个共享 signal 覆盖所有在飞与待启动的子任务**，不是逐个取消。
- [ ] 终态**先到先得（first-wins）**，不可被重入回调改写。
- [ ] 超时有**上下限钳制**，并能区分「本地超时」与「上游取消」。
- [ ] **取消不彻底时的资源回收**路径明确。
- [ ] 部分失败语义明确：**子任务失败可降级，但整体绝不谎报成功**。
- [ ] 重试有**指数退避 + 抖动**，有上限，且**幂等**。
- [ ] 不确定结果的处理是**不自动重试**（DSH 的 unknown outcome）。
- [ ] 有**毒丸防护**：重试上限 + 死信/放弃 + 重复检测。
- [ ] 每个 start 事件**有且仅有一个 end 事件**（含取消时合成的 end）。

**⑥ 人机协同**
- [ ] 审批是**异步**的，不阻塞其他并发单元。
- [ ] 挂起状态**持久化**（可跨重启恢复）。
- [ ] 审批**超时 → 拒绝**（fail-closed）。
- [ ] 并行审批有**合并/优先级**策略，避免审批风暴。
- [ ] 恢复时重跑的步骤是**幂等**的。

**⑦ 可观测性**
- [ ] 每个并发单元有**唯一 id**（run id / job id / child id）。
- [ ] trace 有**正确的 span 父子关系**（OTel）[36]。
- [ ] **成本按 span/agent 归集**，不是全局累加。
- [ ] 事件**成对**，取消时也合成配对的 end。
- [ ] 观测失败**不影响执行**。
- [ ] 不使用 busy-poll；用事件通知 + 有界等待。
- [ ] 通知有**防自激**预算。
- [ ] Telemetry 的可靠性边界被记录（DSH：best-effort，崩溃可丢）。

**⑧ 成本**
- [ ] 估算过 token 放大倍数（对照 Anthropic 的 **4×（agent）/ 15×（多智能体）**[1]）。
- [ ] 竞速/Best-of-N 的**浪费比例**被显式接受（N-1 份成本）。
- [ ] 每次重试都被计入预算（DSH：「**Each retry is another billed provider request**」）。
- [ ] 有 token/金额/时长维度的总量约束（⚠ 注意 DSH 的 Ralph 目前**只有轮次上限**，token 预算是 deferred —— 别假设框架一定给你）。

**⑨ 部署与运维**
- [ ] 部署时**在飞 agent 不会被打断**（Anthropic 用 **rainbow deployments**[1]）。
- [ ] 有**检查点/恢复**能力，重启不必从头（Anthropic：「restarts are expensive」[1]）。
- [ ] **工作区边界**在并发多实例下被验证（本会话实测：DSH 写 profile 目录被沙箱以 EPERM 拒绝）。
- [ ] 平台差异被覆盖（**Windows 强杀进程无信号标记，只有 exit code 1**）。

**⑩ 并发正确性验证（最容易被跳过）**
- [ ] 有**并发专项测试**，而不只是功能测试（Tokio 用 Loom 抓出 **10+** 个常规测试漏掉的并发 bug）[48]。
- [ ] 测试覆盖**乱序完成、部分失败、超时、取消传播、重复投递**五类场景。

### D4. 成本 / 延迟 / 复杂度三角分析

```
                     成本 Cost
                       ▲
                      ╱ ╲
                     ╱   ╲      三者不可兼得：
                    ╱ 可行 ╲     想同时压低三者，必须换架构或降低目标
                   ╱  区域  ╲
                  ╱         ╲
                 ╱           ╲
                ▼─────────────▼
        延迟 Latency ──────── 复杂度 Complexity
```

**三种典型取舍（含真实数字）**：

| 目标 | 手段 | 代价 | 真实数字 |
|---|---|---|---|
| **降延迟** | 并行扇出 / 流水线 / 竞速 | 成本↑（token 线性增长）、复杂度↑（结果协调、错误传播） | Anthropic：并行化让复杂查询研究时间**最多降 90%** [1] |
| **提质量** | 多智能体分工 / Best-of-N | 成本大幅↑ | Anthropic：多智能体 vs 单 agent **+90.2%**；但 token **15×** vs chat [1] |
| **降成本** | 减少并发、缩短上下文、子 agent 用便宜模型 | 延迟↑、质量可能↓ | Anthropic：多智能体用 Opus 4 lead + Sonnet 4 subagent 的组合（分层模型）[1] |
| **降复杂度** | 单 agent、串行执行 | 延迟↑、放弃并行收益 | Anthropic 承认同步执行更简单但「creates bottlenecks」[1] |

**关键量化锚点**：

1. **15× 成本基准**。多智能体 ≈ chat 的 15 倍 token，普通 agent ≈ 4 倍 [1]。**这是所有并发决策的成本基线。**
2. **Token 用量解释 80% 的性能方差**（BrowseComp），三因素（token / 工具调用数 / 模型选择）合计解释 **95%** [1]。
   → **推论：多智能体的性能提升主要来自「花了更多 token」，而不是「架构更聪明」。** 如果你能通过其他方式（更长思考、更多工具调用）花掉同样的 token，性能可能相近而复杂度更低。
3. **Anthropic 的适用性判据**（原文）：
   > multi-agent systems excel at valuable tasks that involve **heavy parallelization**, **information that exceeds single context windows**, and **interfacing with numerous complex tools**。
   > **most coding tasks involve fewer truly parallelizable tasks than research**, and LLM agents are **not yet great at coordinating and delegating to other agents in real time**。
4. **一个便宜的高收益优化**：改进工具描述带来任务完成时间 **降 40%** [1] —— 比加并发便宜得多。
5. **复杂度的具体体现**（Anthropic 自述的未完事项）：异步执行会带来「**result coordination, state consistency, and error propagation**」三个新问题 [1]。
6. **「并行不省钱，只买时间」的量化依据**：n 个 agent 的期望成本 ≈ `n × 15× chat`，再叠加 HiveMind 实测的 **48–100% 浪费计算** [1][46]。
7. **Agent 数量与吞吐不一定正相关**：Magentic-One 的轮次制表明，**加 agent 只增加每轮的可选性，不增加并行度**；CrewAI 的并行粒度只到 task，**task 内部仍是串行 ReAct**。

**实务建议的决策顺序**：
```
1. 先问：单 agent + 更好的 prompt/工具，够不够？
   （Anthropic：改工具描述降 40% 时间 —— 最便宜）
        ↓ 不够
2. 先问：任务真的有可并行结构吗？
   （多数编码任务没有 —— 别硬上多智能体）
        ↓ 有
3. 上最小并发：A8 async + 有界扇出，加并发上限
        ↓ 不够
4. 再上编排：pipeline / DAG，避免 barrier
        ↓ 任务价值确实高
5. 最后上多智能体编排 + durable execution + 完整可观测
   （此时接受 15× 成本，并准备好协调/一致性/错误传播的工程量）
```

### E3. 新增（14 条）—— 第一轮完全没写到的官方机制

#### 新增 1：五种事件分发模式 —— B3「同步原语」在 DSH 的完整落地

`docs/cordis-primer.zh.md` 给出 Cordis 的**五种**分发模式，每种事件只能用对应方法分发：

| 模式 | 是否 await？ | 分发顺序 | 是否有返回值？ | 对应本报告的模式 |
|---|---|---|---|---|
| `emit` | 否 | 按注册顺序观察 | 否 | 单向通知（fire-and-forget） |
| **`waterfall`** | 否 | 按注册顺序观察 | **是** | **环绕中间件 / 责任链（可短路）** |
| **`parallel`** | **是** | **所有监听器并行观察** | 否 | **A1 扇出（barrier）** |
| **`serial`** | **是** | 按注册顺序 | 是 | **A2 顺序流水线（无并行）** |
| `bail` | 否 | 按序，直到某监听器返回 bail 值 | 是 | 首个决策者胜出（短路） |

> **分发模式是事件公开约定的一部分**。新的 harness 事件通过 `@mode` 标签记录模式，以便生成的目录可以将声明与分发调用点做交叉校验。

**`waterfall` 的短路语义（B3「短路」的一手实现）**：

> `ctx.waterfall` 是**环绕中间件**。监听器接收 `(...args, next)`。调用 `next()` 会执行下游监听器；下游返回值通过 `next()` 返回当前包装层，可由该层包装后继续向外返回。**不调用 `next()` 直接返回则短路。**
> 对于单决策事件，**短路是设计意图**。策略监听器在拥有决策权时可以不调用 `next()` 直接返回，而**仅做标注或观察的监听器则必须委托**。
> 仅当监听器必须在普通注册之前运行时才使用 `prepend: true`。

→ 这是 A8「取消是协作式的」与 B3「短路」在**插件架构层面**的对应物：**中间件只有在明确拥有决策权时才允许中断链**，否则必须委托。「谁有权短路」被显式约定，比隐式的「谁先返回值谁赢」安全得多。

**`agent/*` 事件的分发模式（逐条核实）**：

| 事件 | 模式 | 并发含义 |
|---|---|---|
| `agent/assistant-stream` | emit | 进程本地流式发布；chunk 帧是瞬态的 |
| `agent/created` | **serial** | 按序且 **await**；AgentLoop 在所有监听器完成前**持有排队输入**；抛错则创建失败并跳过后续监听器 |
| `agent/disposed` | emit | 在 driver 静止与作用域注册回退之后、会话分离之前发出 |
| `agent/error` | emit | |
| `agent/inbox/inserted` / `claimed` / `discarded` | emit | 三类 inbox 变更通知 |
| `agent/pre-step` | **waterfall** | 「Reject a proposed step or replace the messages that enter it。**Calling `next()` preserves the current messages**」 |
| `agent/request` | **waterfall** | 「**Cancellation here or during subsequent `prepareCall()` resolution commits neither.**」 |
| `agent/request-error` | **waterfall** | 「A listener returns `{ kind: 'retry' }` **without calling `next()`** when it owns recovery」 |
| `agent/status` | emit | `idle` ⇄ `running` |
| `agent/turn-stopping` | **serial** | 见新增 2 |

#### 新增 2：`agent/turn-stopping` —— 轮次终止钩子，且**数据决定、顺序无关**

> The turn is about to close: the model owes no response (no live tool calls, no fresh steering). **Awaited before the boundary commits** — a listener that objects **steers (`agent.steer(...)`) and the machine re-reads its inbox**: fresh steering runs another step, none closes the turn. **Data decides, so listener order cannot change the outcome.** The inverse control (stop a tool loop early) is data too: a tool result carrying **`concludesTurn`** ends the turn at its step. The conclusion **never short-circuits already-submitted next-step work**: same-step `additionalContexts` or racing steering still runs, and the turn closes only when that inbox drains.

**三个可直接搬用的设计**：
1. `agent/turn-stopping` 是 **`serial` 且被 await** —— 关闭边界之前必须等完所有监听器。
2. **「Data decides, so listener order cannot change the outcome」** —— 终止决策**不看监听器注册顺序**，而看数据（inbox 里有没有新 steering）。这是避免「插件加载顺序改变行为」的关键设计。
3. **`concludesTurn` 是数据而非控制流** —— 提前结束工具循环靠**工具结果上带一个标记**实现，而非抛异常。且「**不会短路已提交的 next-step 工作**」⇒ **终止是「不再接新活」，不是「丢弃已接的活」**。对照 A11 的「已接受 ≠ 已完成」，这个语义在并发下极重要。

#### 新增 3：`keepInbox` 与 first-cause-wins —— 取消的精细语义

```ts
interface CancelOptions {
  /** Preserve queued and steering inbox items instead of discarding them. The
   * active turn is still aborted, but un-started and pending work survives for a
   * later turn and no canceled inbox splice is logged. */
  keepInbox?: boolean | undefined
}
```

> `cancel(cause, options)`：*"Clear queued and steering work — unless `keepInbox` — and abort the active turn or between-turn task. **The first cause wins for that activity.** With no active activity, cancellation is a **no-op and does not arm later work**."*

**三点补强 B5**：
1. **first-cause-wins**（与工作流引擎的「Terminal outcome is first-wins at host claim points」一致）。
2. **`keepInbox`** 把「取消当前工作」与「丢弃排队工作」**拆成两个独立决策** —— 比「一刀切 cancel」精细得多。
3. **无活跃活动时 cancel 是 no-op，且不给后续工作「预置」取消态** —— 避免「取消落在空档期导致下一轮被误杀」的经典竞态。

#### 新增 4：`AgentStatus` 只有两态，dispose 不是状态

> `idle` means no driver is active; `running` begins when waking input starts cancellable pre-step processing and lasts while the driver drains, closes, or checkpoints turns. **Disposal removes the agent from its registry; it is not a third observable status.**

→ **需要澄清的一处**：第一轮在一手观察里把 `list_agents` 的 `running` / `idle` / `ready` 并列为「三态生命周期」。准确说法是——**核心 `Agent` 的运行期状态只有 `idle` / `running` 两态**；`ready`（仅存在于存储、可恢复）是**可发现性**概念；dispose 通过 `agent/disposed` 事件表达，**不占用 status 值**。

#### 新增 5：Inbox 是两条有序列表 + 持久 splice 日志

```ts
interface Inbox {
  readonly nextTurn: readonly UserMessage[]   // 等待各自轮次的提示词
  readonly nextStep: readonly UserMessage[]   // 等待下一个步骤边界的输入
  clear(): void                                // 持久取消全部待处理输入，先清 next-step 再清 next-turn
  append / prepend / replace / remove / splice
}
type InboxTarget = 'next-turn' | 'next-step'
```

> 结构化 `Inbox` 方法会记录**规范化的持久 `agent/inbox/spliced` 变更**，并**拒绝重复的待处理 id**。
> `replace` / `remove` 通过 `MessageId` **跨两份列表定位**待处理消息；替换可以改变标识，并**先将旧消息作为 discarded 发布，再将新消息作为 inserted 发布**。
> 在步骤边界，`ReactLoopInbox` 通过**纯删除 splice** 移除拟进入步骤的批次——全部 `next-step` 输入，外加轮次边界上的**一条** `next-turn` 消息——**且不发出 discarded 通知**，随后逐条发出 claimed 通知。

→ **并发含义**：inbox 每次变更都**持久化**，所以「排队了什么、领取了什么、丢弃了什么」崩溃后可重建。这是 A7「邮箱无界 = 内存炸弹」与「accepted ≠ processed」的官方解法：**用持久日志把投递状态变成可审计事实**。

#### 新增 6：Agent Teams —— DSH 官方的多智能体协作层（实验性）

> **实验性 Agent Teams** 是 `ctx.agentTeams` 上**公开发布、显式启用**的协作 seam，**在可继续 subagent 之上提供持久 roster、任务板和 mailbox。**

这是第一轮**完全遗漏**的一层。核心机制：

| 机制 | 实现要点 |
|---|---|
| **身份** | `TeamId` = 具独立品牌的 **Root `SessionId`**；`TeamTaskId` 按 **`task-<n>` 单调分配**；`TeamMessageId` 是**全局随机值**；teammate 的 Session id 是持久身份，`name` 是不可变标签 |
| **成员生命周期** | 每 member 从 `provisioning` 起，**只到达一个终态**：`active` 或 `failed`；运行期 `running`/`inactive` **单独派生，绝不重写该记录** |
| **持久 mailbox** | **Lead Session 首先存储完整 queued message**；只有 target 的 pending inbox 条目或已记录用户消息持久化后，才写独立 acknowledgement event ⇒ **`queued-minus-delivered` 构成恢复 mailbox** |
| **投递语义** | **每条消息都尝试 Steer 投递**：running target 在最近步骤边界收到；inactive target 若已加载则启动一个轮次，否则**冷恢复**。**调用方不能选择其他模式**，故持久记录不存调度方式 |
| **去重** | target Session 在 pending inbox 条目与最终用户消息上保留消息身份与发送者归因；**跨 inbox 与历史折叠该 source 构成 target 侧去重键** |
| **任务 DAG** | 完整快照 + **`revision` CAS 乐观锁** + `blockedBy` **无环校验** |
| **写作用域** | **`writeScopes` 是规范化的提示性路径前缀，不是锁**；view 只添加「**write-scope 重叠警告**」，**不改变持久快照** |
| **有界等待** | `waitForChange(caller, timeoutMs, signal)` —— 等待时长限制在 **10 秒到 1 小时**；signal **只取消该等待** |
| **中断** | `interrupt(caller, targetName)` —— 中断 teammate 当前轮次，**但不清空其 pending inbox** |
| **回放** | `foldTeam()` 把 Root Session 回放成 roster / 任务板 / queued-minus-delivered mailbox；**按 `TeamId` 选取记录，故普通 fork 继承的 event 保留 ancestor id，绝不进入新 Root 的状态** |

**⭐「writeScopes 是提示性而非锁」是 A5 的重要一手对照**：DSH 面对「多 agent 改同一工作区」时，**没选文件锁，也没选 CRDT**，而是 **建议性路径前缀 + 重叠警告 + CAS revision 任务状态**：
- **任务状态**用乐观锁（CAS `revision`）保证不丢更新；
- **文件路径**只用**冲突预警**，不做强制互斥。

这是务实取舍：**强制锁会在 agent 场景产生「锁跨越一次 30 秒 LLM 调用」的串行化灾难（A5 已指出）**，所以 DSH 选择「先告知、让上层决策」。

> ⚠ **包可用性核实**：这三个包出现在 `dsh` 包的 **`devDependencies`**（`@deepseek-ai/dsh-experimental-agent-team`、`dsh-experimental-agent-team-profile`、`dsh-experimental-tool-agent-team`，均 `^0.1.5-rc.2`），但**本机 profile 的 `node_modules` 中并不存在**（全目录搜 `agent-team` 仅命中 `dsh` 自身 `package.json`）。故**未能读源码**，以上全部以官方文档 `docs/subsystems/agent-team.zh.md` 为准。

#### 新增 7：单写者租约 + `flush` 屏障 + 有界 write-behind 窗口

> **Freshness across handles**: once an `append` or `flush` resolves on a write handle, every read **STARTED afterwards** on the same backend instance — on any handle, or through `stat`/`list` — observes **at least that prefix**. **Reads concurrent with a mutation carry no ordering promise beyond the valid contiguous prefix.**

三个可直接搬用的并发设计：
1. **两档持久性**：`append` = best-effort（「accepted, ordered, and visible to reads on this backend instance」），**只有 resolved `flush` 承诺崩溃存活**。⇒ **「可见」与「持久」是两个不同的承诺**，必须分开表达。
2. **`close()` 是「幂等、异步、且刻意不可取消」** —— 释放资源的操作**不允许被取消**。这是 B5 里极易忽略的一条：**取消一个正在关闭的操作会留下不确定状态**。
3. **有界 write-behind 批处理，后续事件不重置截止时间**：
   > `session/event` 是一个**同步**通知；挂载的后端按会话 id 把它路由进活跃写句柄的**有界 write-behind 窗口**，而不阻塞生产方。**第一个待处理事件会开启固定的内部批处理窗口，后续事件会加入但不会重置其截止时间。**
   → **「第一个事件开窗、后续不重置」正是避免饥饿的关键**。若每次都重置截止时间，高负载下窗口永不关闭 ⇒ 永不落盘 ⇒ 延迟无上界。这是 B2「调度策略」的一个真实工程答案。

#### 新增 8：崩溃恢复「不在活跃轮次下竞速」

> 一个在轮次中途崩溃的日志以打开的 `turn/start` 而无 `turn/end` 结束。**持久化不会截断或修复它**……只有撕裂物理尾部——属于一次从未完成的 append——中不完整的碎片会被丢弃。
> 修复是读方的职责：resume（agent-loop）通过其写句柄读取已存储的日志，计算 **`interruptedTurnClosers`**——缺失的工具错误、任何未闭合的 `step/end`，以及一个合成的 `turn/end { reason: { kind: 'interrupted' } }`——并在发布 Session 之前把它们作为普通批次通过同一句柄追加。**`interrupted` 是唯一一个不由循环发出的 `TurnEndReason`。**
> 因此**修复只在写所有权之下写入**：活跃会话的写句柄由其生命周期所有者持有，故**并发的 `open(id, 'write')` 会以 `SessionAlreadyOwnedError` 拒绝，而不是让修复与活跃轮次竞速**。
> **只读观察方（session-query）仅在内存中用同样的闭合事件配平被中断的冷日志，不回写任何内容。**

**这是 A5 / B6 最好的工业范例**：修复者**必须先取得写所有权**才能写，因此**修复永不可能与活跃轮次竞速**；只读观察方**只在内存配平，绝不回写**。「读方负责修复，但只能在写所有权下修」把恢复的并发风险降到零。

#### 新增 9：「模型可见即已记录」是一条运行时不变量

> **模型可见即已记录。** 抵达模型请求的一切都必须能从日志重建，并由一项**运行时不变量**断言这一点。新增模型可见输入需要一个会话事件。修改现有消息内容的插件注册**纯消息投影**，独立读取器显式传入相同的处理器。

→ 对应本地包 `dsh-invariants` 与各包 `*/invariant` companion 的作用（第一轮观察到这些包存在，但不知其契约）。**「凡影响模型的都必须可重建，且有运行时不变量兜底」是并发/恢复场景下最值钱的一条约束。**

#### 新增 10：`withoutInitiator` —— 防止惰性共享资源错误继承「第一个初始化的 agent」

> Run an operation inside a boundary that hides any inherited initiating Agent. **Use this while creating lazy shared timers, queue pumps, pool maintenance, watchers, or exporters so they do not inherit the first Agent that happens to initialize them.** It clears only initiator attribution, not explicit fields, and **does not own or drain detached resources.**

→ 这是**并发下极易踩的归属 bug**：单例/池/定时器由「恰好第一个用到它的 agent」初始化，于是后续所有操作都被归因到那个 agent。解法是**显式开一个「无发起者」边界**；同时诚实声明**只清归属，不接管生命周期**。

#### 新增 11：`withInitiator` 的授权语义 —— 「存在 ≠ 存活 ≠ 授权」

> `withInitiator(agent, operation)`：*"@param agent - initiating Agent to inherit; **presence is neither liveness proof nor authorization**."*
> `requireInitiator()`：*"Use this for private helpers contractually below a driver, or for a deployment-owned outbound request whose contract forbids agentless calls."*

→ 对 B7「可观测性 / 归属」有用：**归属（attribution）与授权（authorization）必须分开**。trace 上的 parent 不能当权限凭据。

#### 新增 12：`AgentHandle.dispose()` 是**能力（capability）**，不是公开 API

> The disposer is a **CAPABILITY**: among consumers, **only the holder can tear this agent down**. The registered factory provider is also a **structural owner** because the scoped agent depends on that provider's service API; **provider unload stops and drains every live handle it made.**
> `dispose()` stops the loop, awaits its exit, unregisters the agent, removes its session from the store, and finally unwinds its scoped world.

→ **双重所有权模型**：**能力所有权**（只有拿到 handle 的调用方能主动拆）+ **结构所有权**（provider 卸载级联 drain 所有它造的 handle）。这解决了并发下「谁有权杀这个 agent」的问题，直接关联 B1「并发上限」与 B5「取消传播」。

#### 新增 13：Agent 创建的事务性（回滚保证）

> `setup` 拒绝、commit 抛出或所有者 dispose 都会**回滚事务，两个 id 均不发布**。
> 凡经 `agentCtx` 注册的内容都**先于 `agent/created` 与第一次提示词组装**存在。
> `CreateAgentOptions` 携带……**同级字段 `inheritedEventCount` 所表示的精确 fork cut**、可选的 `seed` 回放前缀、按 agent 的 `AgentOptions`、**仅创建期有效的取消 `signal`**。

→ **「两个 id（session id / agent id）要么都发布要么都不发布」是并发创建的核心保证**，避免「会话存在但没有 agent」的半成品。且取消 signal **仅创建期有效**，避免长生命周期信号泄漏。

#### 新增 14：会话格式的不可变 generation 与排他发布

> 已提交 generation 路径**绝不重命名、替换或删除**。
> **JSONL provider 负责物理 framing、压缩、generation 选择与排他发布，每个相邻迁移包只负责一个 `vN -> vN+1` 步骤。**
> 即使仍有较旧的可读 generation，**最高的未来 generation 仍会导致拒绝**。
> 该修订号是来自 `stat`/`list` 的**逐后端实例变更令牌**：**修订号相等可视为日志未变；不相等则不作任何承诺，且写所有权的变动绝不会改变修订号。**

→ 对 A5 的价值：这是一个**用「不可变 generation + 排他发布」替代「原地改写 + 锁」的真实工业方案**，可与乐观锁 / 文件锁 / CRDT 并列为**第四种思路**。「写所有权变动不改变修订号」也是细节好处：读模型缓存不会因为 agent 被 resume/dispose 而失效。

### F1. `docs/defensive-patterns.zh.md` —— 仓库指定的**并发必读**

`AGENTS.md` 明文规定：**「Read `docs/defensive-patterns.md` before lifecycle, concurrency, subprocess, or teardown work.」** 该文档自述「下面每条模式都是本项目**实际发布或差点发布的一类缺陷**，以防止其复发的规则形式陈述」。七条规则中四条直接属于并发范畴：

| # | 规则 | 原文要点 | 对应本报告 |
|---|---|---|---|
| 1 | **正交结果独立上报** | 「**进程可能已经超时，却仍以退出码 0 结束，因为它捕获了终止信号。** 每个独立事实（`timedOut`、`signal`、`exitCode`）都应单独上报；**切勿把一个标志的上报嵌套在另一个标志的分支中**，否则调用方可能把提前终止的运行误判为正常成功。」 | **A9 平台差异 / B5 超时归因** —— 这条正是本报告在 Windows 上观察到「强杀进程只有 `exit code 1`、无信号标记」的一般化形式：**退出码不可作为终止原因的单一证据** |
| 3 | **异步状态不是同步状态** | 「`agent.followup()` **没有逐消息的完成状态或结果**；后台任务的完成与轮次边界存在竞争；`reader.close()` 在 EOF 和 dispose 两种情况下都会触发。**切勿把 `agent/status` 或 `whenIdle()` 当作某次 `followup()` 的结果**：多条已排队的后续消息、steering 和注入工作可能共用同一个 `running` 区间，而取消或资源释放可能丢弃尚未启动的项。」 + 「**如果等待的转换永远不会发生，等待就会挂起**，因此应显式处理『无需等待』的分支。」 | **A11 后台作业 / B7 可观测性** —— 「多个任务共用同一个 `running` 区间」是「**并发区间不等于单任务生命周期**」的权威表述 |
| 4 | **dispose 必须达到完全停稳，而不仅仅是请求停止** | 「如果清理流程**只发出终止或中止信号便返回，而不等待工作真正停止，就会留下孤儿进程**。……还应在终止进程前**关闭监听器注册表和通知注册表，使迟到的完成事件保持静默**。」 | **A8/B5 取消与清理** —— 「**请求停止 ≠ 已经停止**」 |
| 5 | **在分发器中隔离回调异常** | 「用户提供的监听器如果抛出异常，**不得导致它所在的 promise 被 reject，也不得饿死排在它后面的监听器**。……一个行为不当的订阅者绝不能破坏核心生命周期。」 | **B7 可观测性** —— 与 DSH「观测失败只降级为合法前缀、不改变工具结果」同源 |

另两条属安全/文件系统，与并发写相关：**「可预测且全局可读的路径会引发符号链接竞态和信息泄露」**（临时/spill 文件须 0700 + 随机名 + `'wx'` + `0o600`）；**Windows junction 用 `rmSync` 会抛 `ERR_FS_EISDIR`，递归删除可能穿过 junction 进入其目标**（须先 `lstatSync().isSymbolicLink()` 再 `unlinkSync`）。

### F2. 轮次取消：`2026-07-16-explicit-turn-cancellation`（官方设计决策级）

本报告 B5 的 DSH 部分由「README 转述」升级为设计原文：

- **取消权限是「轮次级」而非「驱动器级」**：
  > AgentLoop 为**每个待启动轮次**私有地持有一个 `TurnCancellation`。它在**通知 `agent/status = running` 前安装**该持有者，使其中唯一的 `AbortController` 持续覆盖 **inbox 领取、`agent/pre-step`、提示词组装、每个步骤、模型与工具执行以及 `agent/turn-stopping`**；随后**在发布 `turn/end` 前立即清除**所安装的那个持有者。
  > 因此，即使驱动器状态可能在持久化刷新结算前保持 `running`，**终态事件观察者及其后的持久化刷新也无法取消已完成的轮次工作**。

  验证断言：「**同一轮次使用一个 signal，不同轮次使用全新的 signal**」。
- **明确拒绝竞速式取消**（直接回答本报告 A12/B5 的疑问）：
  > 取消仍然是协作式的。AgentLoop 会在异步等待边界前后检查中断，但**不会用 `Promise.race` 放弃进程内监听器、适配器或工具 Promise**。忽略 signal 的工作必须真正结算，`whenIdle()`、句柄 dispose 和作用域清理才会报告完全停稳。
- **被否决的替代方案（官方给出的理由）**：
  - 「在宽限期后放弃不协作的工作」→ 「**同进程工作仍在运行时就报告空闲状态，会破坏资源清理与资源归属保证。硬终止需要 worker 或进程隔离边界，不属于该控制边界。**」
  - 「把 signal 存入 AsyncLocalStorage」→ 「**ALS 会在整个驱动器生命周期内跟随异步后代，而取消权限在一个轮次结束时就已终止。泄漏的回调可能观察到陈旧 signal。**」
  - 「持久化自由文本原因」→ 允许拼写漂移、阻碍穷尽分支判断。
  - 「在 `turn/end` 中持久化类型化调用方原因」→ 「**把请求来源复制到终态结果会混淆两项事实**」；回放**不重复保存** `user`/`parent`。
- **一个真实 bug 记录**：cause **不可冻结**——「**undici 是在严格模式代码中执行该赋值的，被冻结的 reason 会让 `fetch` 以 `TypeError: Cannot add property stack` 取代中止原因而拒绝。**」
- 归因映射：**ACP 取消 → `user`；进程内 spawn/fork 传播 → `parent`**；dispose → `{kind:'disposed'}`，**终态分类先检查生命周期状态，dispose 结果优先**。

### F3. 工具取消：两个中止码区分**是否可能已产生副作用**

`2026-07-19-cooperative-tool-cancellation` 给出本报告**最有价值的单条并发洞察**：

> `dsh-tools` 导出 `TOOL_ABORTED = 'ABORTED'` 和 `TOOL_ABORTED_BEFORE_DISPATCH = 'ABORTED_BEFORE_DISPATCH'`。注册表**在调用 `ToolDefinition.execute()` 的前一刻记录工具主体已调用**。……`ABORTED` **只在工具主体已经调用后使用**。
> **后果：持久化结果的消费方可以区分「工具主体可能产生过副作用的调用」（`ABORTED`）和「从未进入工具主体的调用」（`ABORTED_BEFORE_DISPATCH`）。**

→ 这把本报告 B6 的「**部分失败**」从「成/败」二分升级为**三态**：**成功 / 未产生副作用的中止 / 可能已产生副作用的中止**。**重试决策的正确性完全依赖这个区分**——`ABORTED_BEFORE_DISPATCH` 可以安全重试，`ABORTED` 不能。

其他设计要点：
- **`signal` 必填且只读**；「注册表**不提供重载、默认控制器、永不中止哨兵或便捷执行路径**」。
- **可变性由流水线阶段决定**：只有 `tools/execute` 收到可变的 `ToolDispatchExecution`；前置/后置策略、结果观察者、守卫、工具实现只拿**只读视图**。注册表「在可变对象之外捕获必填的调用方信号，在工具主体调用前把**每次包装层替换与调用方信号融合**，在完成后移除仅属于本次调度的监听器，并**无条件恢复必填的上游信号**」。
- **进入时已中止在参数物化后短路**：**参数物化失败仍优先返回**；随后跳过 `tools/pre-execute`、审批、`tools/execute`、`tools/post-execute` 与工具主体，最后**发布且只发布一次**冻结的权威 `tools/result`。
- **已启动工作必须完全停稳**：「工具主体一旦启动，注册表就会**等待它完成**。……**注册表不会与其 promise 竞速或丢弃该 promise**。**不协作的同进程实现可能让注册表无限期保持等待。进程、worker、网络和提供方层仍负责各自的终止机制。**」
- 被否决的方案里直接点名本报告 A12 的做法：「**让工具 promise 与取消竞速**」→ 不予采纳，因为「这种方式会**在副作用仍可能存活时报告完成**」。
- 诚实的证据边界：「**任何注册表测试都无法证明任意第三方同进程代码会观察信号或在有界时间内停止。**」

### F4. `fork` 子智能体为何保持一次性 —— KV cache 前缀的显式权衡

本报告 C9.3 曾引用 `dsh-base/cordis.patch.yml` 的注释说明「为保 KV cache 放弃模型选择」；现在有了**官方设计原文**：

> fork 与 spawn 的差异在于：fork 会用 parent **已完成轮次的前缀**作为 child Session 的种子。**该种子会消耗 token，其预期收益是提供方侧的前缀复用**……**任何位于继承历史之前、仅属于 child 的系统提示词 section 或工具 schema 都会破坏这项收益。**

**已接受风险（罕见地对缓存假设的诚实声明）**：
> 「提供方侧前缀复用仍取决于选定的提供方和模型……**harness 证明的是自己组装出的请求头输入相等，而不是提供方的缓存行为。**」

→ 对 B8「KV Cache 与并发」的价值：这是一个**把「缓存前缀逐字节相等」当作可测试不变量来工程化**的完整案例，且明确划出了自己**不能**证明的边界。

### F6. master 的工作流执行改为 **PTC 受限进程**，并给出**真正的 FIFO 信号量**

**跨版本重大变更**：rc.2 用 `dsh-workflow-worker-thread`（worker_threads，`disposeGraceMs: 5000` 兜底）；master 的 4 个 workflow 包是 `workflow` / `workflow-ptc` / `tool-workflow` / `tool-ralph` —— **执行载体改为受限 Node 进程（PTC）**。

> `docs/subsystems/workflow.zh.md`：**「PTC 引擎没有整体经过时间截止；取消时立即中止受管进程。」**（对照 rc.2 的 `worker.terminate()` + 5 秒宽限）

**master 源码给出的 FIFO 信号量**（`packages/workflow/workflow-ptc/src/runtime.ts`，模块注释：「Workflow VM hooks, child callbacks, **ordinary concurrency limits** and result serialization. **PTC owns process confinement and cancellation.**」）：

```ts
/** Acquire one concurrency slot in FIFO order. */
acquireSlot() {
  if (this.activeSlots < this.limits.maxConcurrentAgents) {
    this.activeSlots += 1;
    return Promise.resolve();
  }
  return new Promise((resolve) => {
    this.slotWaiters.push(() => { this.activeSlots += 1; resolve(); });
  });
}
releaseSlot() {
  this.activeSlots -= 1;
  const next = this.slotWaiters.shift();
  if (next) next();
}
```

→ **这是本报告 B1「并发上限」与 B2「FIFO 调度」的一个完整、可照抄的参考实现**：`activeSlots` + `slotWaiters` 数组，`shift()` 保证 FIFO，`releaseSlot` 立即唤醒下一个等待者（**无惊群**）。

**同文件另外三条并发要点**：

1. **防止未处理拒绝杀死进程**：
   > `contain(promise)` —— 「Attach a no-op rejection consumer **WITHOUT changing what the caller receives**: if the script drops the promise, a host rejection cannot become an **unhandled rejection that kills the process**; if the script does await it, it still observes the rejection.」
   → 对 A1 扇出的价值：**并发脚本里被丢弃的 promise 会以未处理拒绝杀死整个进程**，这是一个廉价且必要的防护。
2. **fatal 与 item-null 的二分，且用跨 realm 不可伪造的 `instanceof` 判别**：
   > `WorkflowError.fatal` drives the combinator discipline: **`parallel()`/`pipeline()` re-throw a fatal error (a typo'd option or a tripped cap must kill the script loudly)**, and reserve the **per-item `null`** for child-run failures and ordinary in-stage script errors.
   > `isFatalWorkflowError(e) { return e instanceof WorkflowError && e.fatal }` —— 注释：「**fatality is host `instanceof` (unforgeable from a script realm)**」。
   → 这是本报告 A2「失败是 item 级隔离」的**安全强化版**：模型写的脚本**无法伪造**一个 fatal 错误来绕过 item 级降级。
3. **进度上报只允许一个在飞批次**：guest 侧 `flush()` 在 `inFlight !== undefined` 时直接返回，事件入队合并；结算前 `await drain()` 再 `disposeChild`。
   → 对应 A11/B7：**并发事件上报需要合并与有界在飞数**，否则观察者会被打爆。

`agent()` 选项白名单：`{ label, phase, schema, provider, model }`；`{ effort, isolation, agentType }` 属 **deferred，被显式点名拒绝**。

### F7. 会话日志、作业与子智能体的并发细节（master `docs/subsystems/`）

**持久化（`persistence.zh.md`）**补充 master 的实现级事实：JSONL provider 具备「**崩溃安全的原子实体化、逐批 `fsync` 的 append，以及在第一次新 append 之前截断撕裂尾部**」。

**作业（`jobs.zh.md`）**：
> 每个 job 拥有一个**有界的环**。拉取源被泵入其中，`JobHandle.append` 的推送整块落地；**模型通过注册表保管的游标（`JobRegistry.read`）消耗该环，任意数量的观察者按绝对字节偏移读取它（`JobRegistry.readAt`），二者互不干扰。** `JobChannel` 标记 `stdout`、`stderr` 与 `log`；**`log` 是只到达观察者、从不进入模型上下文**的通道。
> `JobView.owner` 携带划定访问边界的会话 id；**注册表为生命周期清理解析其背后的活体 `Agent`，从不把该对象交出去。**
> 订阅可见性：`{ owner }` / `{ owners: 'scope' }` / `{ owners: 'all' }` —— **一个 preset 不会听到另一个 preset 的 agent**。

→ **补充本报告 A11**：DSH 的作业输出是**单生产者 + 任意多消费者（按绝对字节偏移无协调读取）**模型，而不是「一个流一个读者」。这消解了 E 节写到的「stream reads are single-consumer」在 master 上的限制。

**子智能体（`subagent.zh.md`）**：
> **可继续后台 subagent**……**至多关联一个进程内的 `Activation`（激活）**。**Activation 不是请求、结果、取消或 Task：它可以执行多个 FIFO 轮次，并在其创建的后代仍在运行期间保持驻留。**
> **Agent 收件箱是唯一队列。** 每条 Agent 消息都使用 `Agent.steer()`：空闲目标启动一个轮次，运行中目标在最近的 step 边界领取消息。浏览器 `subagent.prompt` 另行携带 `delivery: 'queue' | 'steer'`。
> **调用方 signal 的权限边界**：对于 `startContinuable()`、`sendMessage()` 与浏览器 prompt 投递，**调用方 signal 仅在收件箱接受之前掌管查找、物化与准入。此后管理器独立掌管该 Activation：之后的调用方取消既不会取消已接受的轮次，也不会 dispose 子 agent。**

→ **这是本报告 A11「已接受 ≠ 已完成」的权威表述**：**取消权限止于「收件箱接受」这一刻**。之前可取消，之后不可。这与 E 节新增 6 的 mailbox 设计（`queued-minus-delivered` 构成恢复 mailbox）是同一模型的两面。
→ 另注：`maxDepth` 的设计理由是「**可见性而非权限**」（visibility, not authority）——工具在达到深度上限时**仍然可见**，靠运行期检查拒绝。

### F9. 工具执行流水线的**精确顺序**（master `docs/tool-execution-pipeline.zh.md`，4.6 KB）

```
tool/call (先记录) → presentCall(UI)
  → tools/pre-execute  waterfall   (hooks / permission / sandbox)
  → 注册的单调守卫                  (deny 或 abstain；identity protected)
  → [deny] 跳过工具主体
  → [ask]  ctx.approval 一次性询问  (缺失或无法回答 ⇒ deny)
  → tools/execute      waterfall   (timeout / retry / metrics ——「环绕分发」)
  → 工具主体 execute()
  → fs/write-intent | fs/edit-intent (仅 tool-fs 变更)
  → projectContent                 (执行后策略之前安装已准备内容)
  → tools/post-execute waterfall   (accept / block / replace / add context)
  → finalizeContent                (最后一道仅限内容的不变式)
  → tools/result                   **同步通知**，冻结的权威结果
  → additionalContexts FIFO        (在已记录工具结果之后注入 user/message)
```

**并发相关要点**：
- **审批是 fail-closed**：「`ctx.approval` 一次性询问；**缺失或无法回答：deny**」。
- **`tools/result` 是同步通知，且结果是冻结的权威值**；注册表对候选结果做**无损快照**，快照失败会先被规范化为 `isError`，之后仍由已随快照固定的 `finalizeContent` 强制执行其**同步且仅限内容**的不变式。
- **`additionalContexts` 走 FIFO**——这是 A10/A11 里「审批/注入必须保序」的实现。
- **PTC mode 的子调用特殊处理**：携带父级 token、记录 `tool/ptc-dispatch`、把拒绝呈现为**具有约束力的驳回**，并**省略 `additionalContexts` 以保持调用与结果相邻**。
- 三个 waterfall（`pre-execute` / `execute` / `post-execute`）**各可以改写一次调用**——与本报告 B3「环绕中间件」一致。
