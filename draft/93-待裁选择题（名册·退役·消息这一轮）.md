## §T23 读写面切割（业主新裁；施工口径，未在选择题里出现）

业主逐字：

> 「关于读写面，子代理只能读写父代理切割给它的读写面，且父代理原则上必须把各子代理的
> 读写面拆开。当然若子代理想新写文件，这个是允许的，毕竟不会有别人和它抢新文件。」

| # | 规则 | 落地形态（`draft/92` §3 有符号级伪代码） |
|---|---|---|
| T23-1 | **每个子代理有一个"面"**：一组**可写前缀**（默认一个目录）+ 一组**只读前缀** | 名册项新增一格 `surface`（`{"write":["runs/t-0011/**"], "read":["manuscripts/**","out/**"]}`），写进 `out/roster/<owner>.jsonl` 与 index |
| T23-2 | **子只能读写面内** | `fs.*` 已有的判据直接复用：`FsContext.root`（`fs_tools.py:166`）把一切路径 `resolve()` 后 `relative_to(root)` —— 面就是这个 `root`（**每实例一个**，不是共用工作区根） |
| T23-3 | **父原则上必须把各活跃子的面拆开**（不重叠） | 派活时秘书审核：与父名下**活跃**项的面重叠 ⇒ **受控拒绝**，除非父显式 `shared: true`（那时按既有写集冲突落到**不同波**，串行执行） |
| T23-4 | **新文件允许** | 面是**目录前缀**（不是文件白名单）⇒ 面内的新路径天然允许；面外一律拒（含"别人的面"与工作区外） |
| T23-5 | **退役 ⇒ 名字与面分两路**：**名字**进销号名单、**永久不复用**（B1）；**面归还"可分配池"**、可以再分配给后来的子代理（业主 2026-10-08 深夜补充：「退役后读写面释放进可分配池」） | 名字：`out/roster/<owner>-retired.jsonl`；面：`out/roster/<owner>-surfaces.jsonl`（事件流：`alloc` / `release` / `archive_failed`） |
| T23-6 | **面的编号与名字解耦**：池里的槽位叫 `S01` / `S02`…（**不编码本地名**）—— 否则 `D1` 退役后槽位 `D1` 被 `D2` 拿走，就成了"名字换人"的变体 | 面的路径 = `<workspace>/out/surfaces/<owner>/<slot>/`；名册项记 `surface`（槽位名）+ `surface_path` |
| T23-7 | **归还的三态 + 归档**：退役 ⇒ ① 面的内容**归档**到 `out/surfaces/archive/<owner>-<name>/` ② 槽位入池（"空闲"）③ 归档失败 ⇒ 槽位停在 **"待释放"**（**不入池**）并留读数 | 为什么必须归档：槽位一旦重分配，新子代理就会看到**前任留下的文件** —— 那是"别人和它抢文件"的另一种形态（业主原话的反面）；三态保证"没归档干净就不放回池" |
| T23-6 | **第一阶段不动写集冲突** | `WRITE_SETS` 是**角色级**（`capabilities.py:1267`），分波仍按角色（保守）；**第二阶段**再让分波用**实例面**（更细的并发，收益是"各写各的"能同波） |

- **判据（红/绿）**：正控 = 子在自己的面里写新文件成功、读只读前缀成功；
  **正控（池）** = 退役之后槽位回到池里，且**可以**分配给一个新的子代理（新子代理拿到的是
  **干净**的面）；负控 = ①写面外 ⇒ 拒 ②写**另一个子的面** ⇒ 拒 ③两个活跃子的面重叠且没声明
  `shared` ⇒ 派活被拒 ④**名字不因面复用而复用**（槽位 `S02` 给了 `D2` 之后，`D1` 这个名字
  仍然不可用）⑤归档失败 ⇒ 槽位**不入池**（停在"待释放"）；
  反真空 = 面读不成/没登记 ⇒ **拒绝**（不许当成"整工作区可写"）。
- **会碰**：`fs_tools.py`（`FsContext` 的构造点）、`host.py`/`tools/__init__.py`（按面造注册表）、
  `capabilities.py`（**不改**：写集仍是角色级；只在第二阶段才谈）、`policy.py`（分波第二阶段的读侧）。
- **批次**：**S1n**（排在 S1k 之后 —— 面的分配与审核要用名册与对照表）。

## B 组：判据细节（可与施工并行，但别晚于 S1k 落地）

### B1（= `draft/92` §7-⑦）序号要不要**严格按派活顺序** —— **已裁**

**裁定**：「如果曾派出过 D1 且 D1 被销号，后续不许复用 D1，且应该维护一个被销号的子代理列表
以便后续版本要做什么新功能。」⇒ 与 B3（不回收）合起来是三条规则：

1. **销号的名字永久退役**：`D1` 退役后，`reuse:"D1"` 与"再提名 `D1`"一律**受控拒绝**
   （理由"已销号"）；要派活就新起（`D2`）。
2. **维护"被销号的子代理列表"**：`out/roster/<owner>-retired.jsonl`（物化索引：名字 / 角色 /
   绝对编码 / 退役时间 / 依据哪一支）；名册文件里的 retire 事件仍是真源，这份列表是**读起来便宜**
   的那一份，且 `name_of` / `roster_add` 必须查它（防同名换人）。
3. **序号严格按派活顺序这一问被"销号"这一条盖住了**：既然名字一经分配就不再复用、销号也要记账，
   序号大小就不必承担时间语义 ⇒ 仍按**不承诺**（并发派活下 `D2` 的行号可能小于 `D1`）。

| 选项 | 机制 | 代价 |
|---|---|---|
| **甲（我的建议）** | 只承诺**名字唯一、稳定、不回收**；并发派活下 `D2` 的行号可能小于 `D1` | 读台账的人不能把"序号大小"当时间顺序 |
| 乙 | 严格按派活/建行顺序 ⇒ 把名册登记挪进建行的临界区 | 秘书锁与 `_id_lock` 交叉（违反 I-6 锁序）⇒ 有死锁面，且 `summon_many` 会被串行化 |
| 丙 | 序号由**父**显式指定（父说 `D3` 就是 `D3`，被占则受控拒绝） | 模型要自己维护序号（易撞名），但顺序完全可控；与 B2 的选项乙是同一件事 |

### B2（= `draft/92` §7-⑧）不提名时，**秘书替不替父选名字** —— **已裁（不是我给的三个选项）**

### D1 · 94 条空定义 —— **不是"怎么折"的问题，是写入侧缺陷**（业主 2026-10-09：「空串为什么会写入？」）

**现场根因（已核实）**：`Concept.validate()` **没有"定义非空"这一条** —— 它只要求

真机上的 94 条正是这么来的：样本 `Perfect Graph Theorem` / `2-connected` / `diameter` / `tree`
—— 从文献里抽到了**概念名**，没抽到**定义**，照样落了行；而且
**94 条全部没有 `definition_source_lit_id`**（连"定义该从哪篇来"都没留）。

**⇒ 处置（两半，第一半是修缺陷、不是裁项）**：

1. **写入侧**（动 `schema.py`，禁改区、按业主授权先改后审）：`Concept.validate()` 补一条
   **三态要求** —— `definition` 为空时**必须**给出"为什么没有"（`definition_source_lit_id`
   或一个受控理由），否则拒。两条候选：**(甲)** 定义非空才许落行（抽不到定义就**不落**概念行，
   落到读数里说"这个名字没抽到定义"）；**(乙)** 允许空定义但**必须**带来源/理由。
   **建议甲**（与"概念的定义是依赖项"那条口径同向：没有定义的节点不该进图）。
2. **历史 94 条**：来源与定义都空、名字是通用数学名词（回填要靠重新抽取，成本高且原文未必给）
   ⇒ 迁移时**照折 + 行内落受控读数**（"迁移自 concepts：原定义与来源都为空"）并逐条点名，
   **绝不编定义**。这与你说的"空串本来就不该写入"一致：**未来不再产生，历史如实标注**。

> **D1 已裁（2026-10-09）**：业主逐字「抽不到定义的概念就让A去网上搜，写入时定义内容留空，

  **仍然点名说"没上报"** —— 因为我的匹配只认三种载体：`ask_user` 的问/答、
  `agent_message`（给父的报文）、交差手稿（`handoffs.jsonl` 正文）。
- **要你定的那一句话**：**"写进交付说明（REPORT.md）"算不算"上报"？**

### D7 `dependencies.used_by` 的 `stmt:` 形态要不要"正式承认"

- **这是什么**：C 要找依赖链，链的**边**存在 `dependencies` 表里：`used_by`（使用点）→
  `source_*`（被依赖的东西）。"定理 A 用到定理 B"这条边，就是一行
  `used_by="stmt:A"`、`source_doc_id/…` 指向 B。
- **现场（已核实）**：`schema.py` 里 `Dependency.used_by` 的注释写着
  `"doc:0001#claim-3" / "relation:0007" / "experiment:0002"`，紧接着一句注释说
  「`used_by` → 本表的 `stmt_id` 是自然延伸」；但 `validate()` **只检查非空**。
  也就是说：**这条路设计上通、机器上没有一条判据承认它**。
- **要你定的那一句话**：这条路要不要在机器上被**正式承认**（写错的要被抓住）？
  - **不动 `schema.py`（建议）**：在 `verify_all`（事后审计）加一条不变量 ——
    `used_by` 的前缀必须是我们认的前缀（`CITATION_PREFIXES`）**且**指向一个存在的行。
    于是"`stmt:0007` 依赖 `stmt:0003`"这条边被审计看见，写错的成红的。
  - **改 `schema.py` 的 `validate()`**：把合法前缀写进字段校验（更严，但动禁改区的字段校验，
    且历史数据里可能有别的形态）。
- **代价**：一处不变量 + 一条判据（不动字段）。
