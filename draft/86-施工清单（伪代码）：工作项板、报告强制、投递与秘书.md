**在人签字落盘之前，S1 不动手。**

**状态机按 A3=甲+seen 是四档**（不是三档）：

```text
queued ──(写 running 行 = 接手 claimed)──▶ claimed ──(渲染进某一步的提示词 = 渲染 seen)──▶ seen ──(行为完成)──▶ done
                                                                                          ├─ acked      （expects=ack）
                                                                                          └─ completed  （expects=work）
```

`claimed` = **接手**、`seen` = **渲染**（业主 2026-10-08 晚定的措辞，全篇统一用这两个词）：
两档分开是因为"接了它"与"读到了它"是两件事 —— 空口 ack 的判据就是
**ack 与 `seen` 配不上**（不是与 `claimed` 配不上）。
`seen_by` / `seen_step` 两格是 A3 与 A5 的判据要的。
`tasks` 的两根轴（`status` 实例轴 / `item_state` 工作项轴）在 `draft/88` §3 有对齐表。

## §10 自查：还没展开的地方（U1–U8）与自查出的四条缺陷（D85–D88）

这一节是**对着上面的伪代码再读一遍代码之后**写的（不是重述设计）。凡我认为
"照现在这么写下去会出事"的，都给了两案与建议。

### U1 `claimed` 没有入口 —— 谁在什么时候 claim？

状态机里有 `claimed`，但 §2.1 只写了"有读者领走它"，**没有说谁触发**。两案：

| 案 | 机制 | 代价 |
|---|---|---|
| **①（建议）渲染即 claim** | 框架在把一项渲染进某一步的提示词**之前**，替它落 `claimed`（`by_task_id` = 那个实例） | 不需要模型做任何动作；`claimed` 的含义就是"有读者读到了"，与 D76 的第三态天然合一（**没读者 ⇒ 永远 `queued`**） |
| ② 加 `manuscripts.claim` 工具 | 模型显式领 | 多一件工具、多一步模型动作，而且"领了不做"会变成新的挂账形态；与"最小行为是 ack"重复 |

⇒ 建议 ①，并把"渲染即 claim"写进 §2.1 的注释与判据（**渲染一行 ⇒ 板上一行 `claimed`**；
两者数量必须相等，缺 ⇒ 红）。

### U2 板项与 `tasks` 行**没有共同键** → 立为 **D86**

`item_id`（板）与 `task_id`（实例）今天毫无关系：`tasks.input_key` 是幂等键（`consume:<rid>`），
板项的 `edge` 只是描述父子。于是"**这条 delegation 项对应哪个实例**"读不出来 ——
而消边谓词（T2）、"谁领的"（U1）、"做完没做完"全都要这个对应关系。修法（写进 §2.1）：

```python
# 开项**先**分配 item_id，派活时把它当实例行的 input_key（两处一个键）
item = MS.append_item(root, kind=MS.KIND_DELEGATION, ...)
res = cond.summon(role, action, params, by=by, input_key=f"item:{item['id']}")
```

**判据（红/绿）**：每个 delegation 项都能在 `tasks` 里找到 `input_key == f"item:{id}"` 的那一行；
负控：把那一行的 `input_key` 改掉 ⇒ 判据红。

### U3 板与会话**两份真相**谁权威？

状态在 `board.jsonl`，模型上下文在 `sessions/*.jsonl` 的 `agent_item_*` 事件。两份都可能坏。
建议写死（写进 §2.1 的模块注释）：**权威在板账本**（append-only + 可由状态行重算）；
`agent_item_*` 只是**投影**（丢了不致命：重放板账本即可重建"谁在哪一步 ack 了什么"）。
⇒ 判据：把 `agent_item_acked` 事件删掉 ⇒ 板上的状态**不变**（反负控：证明权威不在会话里）。

### U4 双轨期与 `agent_message` 的**退场计划**（先接住再退场）

既有工作区里有 **579 条** `agent_message`（`from` 全是 M 或用户），板是新增的。
所以共存期必须有，但不能"两处都写、两处都渲"（否则模型看到两遍、账上两条 ⇒ 立为 **D88**）。
建议三段（写进 §2.4）：

1. **共存期**：板 + 老留言都渲染，**板优先**；**新消息只开板项，不再写 `agent_message`**
   （`send_message` 只保留"给用户/公共频道"这一档，见 U8）；
2. **观察期**：一轮真跑之后 `agent_message` 的**新增**为 0（读数，不是断言）；
3. **退场**：`send_message` 退成"板的一个 kind"或整体下线 —— 那一步要单独裁定。

### U5 渲染窗口、重渲染时机与上下文预算

§2.4 写了 `backlog`，但**没定窗口大小**、**没定什么时候重渲染**、**没说与 `contextbudget`
（FC-17）的关系**。建议：窗口 `max_items` 进 `settings.json`（默认 8，与旧的 8 条同量级）；
重渲染节奏沿用既有的 `_hear()` 步边界；超窗**只记 backlog**（三项读数：
`rendered / open / backlog`），并把这三项并进 §2.6 的状态报告那一格。

### U6 `notice` 谁 ack？没有读者时怎么可见？

框架通报也是工作项（`expects=ack`），但**它可能永远没人读**（收件人是确定性动作角色）。
而 T13 的"父代读"之后，ack 会记在**父**名下 ⇒ "**子其实没读**"这件事必须可见。
建议：状态行的 `by_task_id` 之外再加一格 `via`（`"self"` / `"parent"`），
`via="parent"` 的项在 `conductor.board` 里单列一栏 ⇒ 父能一眼看出"哪些是我替它读的"。

### U7 并发与原子性

三处要定：① **开项 + 派活**不在一个事务里 ⇒ 可能开出项却没有实例（**孤儿项**，立读数）；
② 多实例同时 ack 同一项 ⇒ `ack_item` 必须**幂等**（第二次 ack 如实说"它已经消掉了"，
不重复落行、不改状态）；③ 交差 = **写 handoffs + 关板项**，两处都要拿锁 ⇒ 见 D87。

### U8 `send_message` 的未来（Y 系列待裁）

"留言进板"之后，`send_message` 的定位要么是"板的一个薄封装"（推荐：一处写入路径，
`kind=message`），要么保留成"给用户/公共频道的专用动词"。**这一条与 Y5（板落点）绑定**，
建议在 Y5 裁定之后一并定；在那之前 §2.4 的兼容分支是必需的。
