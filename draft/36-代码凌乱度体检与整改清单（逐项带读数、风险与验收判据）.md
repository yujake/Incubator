# 代码"凌乱度"体检与整改清单（逐项带读数、风险、验收判据）

> 起因：2026-09-30 用户转述一位工程师看完代码后的感觉 —— **"比较凌乱"**。
> 本文件是那份感觉的**可度量版本**：先把它翻译成几个能重复测量的数，
> 再给出**你可以自己挑**的整改项。每一项都带：证据（读数/位置）、
> 为什么它会让人觉得乱、风险、大致工时、**验收判据**、以及**是否碰 FC-27 禁改区**。
>
> 本文件**只出清单，不动代码**（这是用户选的那一档）。

## §1 口径：为什么先量再改

"凌乱"是一种感觉，而感觉不能直接变成行动：按个人口味重排代码，既证明不了变好，
又最容易在重构里引入真 bug（本仓库的血泪教训是"测试全绿、上线即越权"）。
所以这份清单的每一个数字都来自一条**可复跑**的命令，每一个整改项都带**验收判据**。

复跑命令（六组读数）：

```powershell
cd D:\Incubator
$env:PYTHONIOENCODING='utf-8'; $env:PYTHONUTF8='1'; $env:PYTHONDONTWRITEBYTECODE='1'
python -B temp\_mess_survey.py --top 18           # ①–⑥ 六组
python -B temp\_mess_counts.py                    # 阈值计数（>N 行的文件/函数）
```

> 这两个脚本目前在 `temp/`（**未纳入版本控制**）。若你决定把其中任何一项变成长期

## §3 这些读数对应"读代码的人会遇到的什么"

1. **打开哪个文件都是几千行**（②）：`agent_d.py` 4188 行 ≈ 一本小册子。
   新人第一眼不知道该读哪一段，只好从上往下读。
2. **一个函数 1175 行**（③的 `verify_all`）：它的 40 多个不变量检查是平铺的，
   读者要一次在脑子里装下 40 件事才能判断"这一段改了对不对"。
3. **代码被注释淹了一半**（④）：78.7% 的注释密度是**这个仓库最独特的地方**，
   也是"外人一看就乱"的最大来源 —— 注释里混着：为什么这样做、踩过什么坑、
   当时的读数、与别处的对照、对下一个人的叮嘱。信息量高，但**没有分层**：
   现在读者分不出"必须知道的契约"与"历史上的某次事故"。
4. **同一件事两处实现**（⑤）：读者会问"我该改哪一个"，而答案是"两个都要改，
   否则静默漂移"——这既是认知负担，也是真缺陷面。
5. **文档手抄代码**（⑥）：读者照文档做，可能照着过期的话做。

## §5 建议的执行顺序（如果你问我）

1. **T-1 + T-3 + T-4**（半天）：把"外人第一眼看不懂"和"文档手抄数字"这两件事解决掉 ——
   它们的性价比最高，且零语义风险。
2. **T-2**（半天到一天）：注释分层 + 3 个样板文件。这一条最关键：
   本仓库的注释密度是**资产**，不是负债；乱的原因是没分层，不是太多。
3. **T-5 或 T-7 挑一个**（一天）：先拆一个超长函数，把"先快照、后搬移"的流程跑通，
   形成可复制的做法。
4. **T-6**（一天）：并重复实现（禁改区的那一组留给人）。
5. **T-8 / T-9 / T-10** 择机；**T-11 最后**。

## §6 明确**不建议**做的三件事

1. **不要按"文件应该 <800 行"这类通用口味做全局重排** —— 本仓库里大文件往往是
   "一个角色的全部职责"（`agent_d.py` = D 的 14 个动作）。拆它必须先有
   公开面不变 + 测试全绿的判据，否则是拿风险换观感。
2. **不要为了降注释密度而删注释** —— 那些"为什么"与"实测读数"是本项目最重要的资产
   （`draft/LESSONS` 就是靠它们长出来的）。要动的是**分层与去重**（同一件事解释三遍的地方）。
3. **不要顺手改禁改区**（`capabilities.py` / `verify.py` / `providers.py` / `dedup.py` /
   `schema.py` / `store.py` / `tools/base.py` / `tools/__init__.py` / `interactions.py` /
   门禁脚本…）。把它们列进清单可以，动它们要人写或人逐行走查 + 2 名 reviewer。
