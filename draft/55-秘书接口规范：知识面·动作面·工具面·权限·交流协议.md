# draft/55 秘书接口规范：知识面 · 动作面 · 工具面 · 权限 · 交流协议

> 回答五个问题：**需要知道哪些 · 能做哪些 · 能用哪些工具 · 权限是什么 · 如何与智能体交流**。
> 与 `draft/53`（定位 v3：每智能体一名、发件侧职责 1/2、收件侧职责 4/3）配套；实现形态见 `draft/54 §2`。
> 本文件里的每个"读/写/调用"都对应仓库里的真实机制（`ROLE_BRIEFS`、`specs/*.py`、`capabilities`、
> `tools` 注册表、`store`、`closing` 读数），不引入新的表、新的工具组、新的角色。

## §1 需要知道哪些（知识面，全部只读）

分四层。**前两层是"硬性要求"，第三层是"委托事实"，第四层是"读数"。**

### 1.1 硬性要求（决定"能不能通过"）

| 要知道 | 从哪读（进程内对象 / 文件） | 用来做什么 |
|---|---|---|
| **动作的参数表**：每个角色每个动作的 `params`（类型、必填、枚举、`minLength`…） | `specs/<role>.py` 的 `ACTIONS`（`ActionSpec.params`）；权威表 `capabilities.CAPABILITIES` | 职责 1：把参数补齐/改正到能过校验 |
| **工具名与工具参数**：注册表里**真实存在**的工具名（点号串如 `conductor.stop`、`verify.verify_proof`）、每个工具的 `params`/`returns`/`side_effect`/`roles` | `tools.build_registry()` 的 `ToolSpec`（`registry.names()`）；`tools/__init__.py` 的 `_MODULES` | 职责 1：把工具名写成真名（治 13 次"无处可映"的错名） |
| **写集与边**：谁能写哪张表、谁能召唤谁 | `capabilities.WRITE_SETS`、`capabilities.ALLOWED_EDGES`、`agentspec` 的 `SIDE_EFFECTS` 词表 | 职责 2：判"这个委托在不在收件方的写集/边里" |
| **只读面与例外** | `tools.READ_ONLY_ROLES`、`READONLY_CALL_EXCEPTIONS` | 职责 2：判"只读角色能不能接这活" |
| **动作是否有实现** | `capabilities._KNOWN_UNMATCHED_ACTIONS`、`not_wired` 一族读数 | 职责 2：拦下"派了但没实现"的委托（今天 7 次） |

### 1.2 角色定位（**全部角色的组织图**，不是只读自己和收件方）

> **用户口径（2026-10-06）**："秘书应该能读**所有智能体**的角色定位。"
> ⇒ 定位面**对每名秘书全开**：这是职责 2（判"收件方真做得到吗"）与"建议改派"的前提。
> **注意它与"数据面"是两件事**：组织图（岗位定义）可以全读；研究数据（叙事/正文）另有约束（见 1.5）。

| 要知道 | 从哪读 | 用来做什么 |
|---|---|---|
| **每个角色的六字段 brief**：`duty` / `boundary` / `signature_error` / `deliverable` / `policy` / `stance` | `agent_prompts.ROLE_BRIEFS[<任意角色>]`（真身） | 职责 2/4：判匹配、判贴切、给改派建议 |
| **每个角色的十项官能轻重**（core / minor / denied） | `specs/<任意角色>.py` 的 `SPEC.emphasis` + `FACULTY_EMPHASIS`/`FACULTY_LOCAL` | 职责 4：把要求换成该角色"看得见"的说法 |
| **每个角色的能力面**：动作表、工具面、写集、边、是否只读、`needs` | `specs/<任意角色>.py` 的 `ACTIONS`/`SPEC` + `capabilities.CAPABILITIES`/`WRITE_SETS`/`ALLOWED_EDGES` + `tools.build_registry()` 的 `roles` | 职责 2：判"这活该派给谁"（含"改派给谁更合适"） |
| **产出物与验收口径** | 各角色的 `deliverable` +（收工侧）`closing` 的 30 档与附件三件套 | 职责 4：明确"要交什么、怎么算交到了" |

### 1.3 委托事实（决定"该不该派、有没有闭环"）

| 要知道 | 从哪读 | 用来做什么 |
|---|---|---|
| **委托本体**：谁→谁、动作、参数、终态、拒绝原因、`input_key`、`task_id`、`parent_task_id` | `tasks`（`store` 只读） | 职责 1/2/3 的全部判断 |
| **同 key 的既有终态行**（重复候选） | 同上，按 `(role, action, input_key)` 分组 | 职责 2：判"这次算重复还是正当重试" |
| **消息与叙事**：`agent_message`、`task_end` 等会话事件 | `sessions/*.jsonl`（只读） | 职责 3：判"有没有反馈"；E-03 的机器半写 `task_end`，秘书读它 |
| **收件箱**：未处理的委托、`search_requests`/`reprocess_requests` 的 pending | `tasks` + 两张请求表（只读） | 职责 3：闭环清单 |
| **手稿 / 交接通道**——`<ws>/manuscripts/handoffs.jsonl`（**是 JSONL 文件，不是库表**） | `manuscripts.read` / `list_all` / `query` / `row_of` / `rows` / `rows_for_task` / `read_index` / `ref_problem` | 职责 2/3/4：判"这条委托是不是重复、是不是已经交接过了"（**用户点名的"至少要能读 handoffs"**）、查引用链通不通、给加工后的委托附上前置手稿号 |

### 1.4 读数（只给 **M 的秘书**，用于收工侧）

| 要知道 | 从哪读 | 用来做什么 |
|---|---|---|
| **30 档逐档算得出/算不出、缺哪一环、哪些行是 `na`** | `closing.check_closing(..., checks=("acceptance",))` 的读数 | 原 `裁决 5` 的"覆盖面把握"（**只归 M 的秘书**） |
| **收工门七格与附件三件套的缺口** | `closing.DEFAULT_CHECKS` 的读数 + `closing.ATTACHMENT_FIELDS` | 同上 |
| **V 的验证台账** | `verifications/*.jsonl`（只读） | 判"这条命题验过没有"（不判内容对错） |

### 1.5 **信息面的两条界线**（一条全开、一条收紧）

**① 定位面：全开。** 每名秘书都可读**所有智能体**的角色定位与能力面（§1.2）—— 这是你 2026-10-06 的口径，
也是职责 2 能给出"改派建议"的前提。

**② 数据面：≤ 本体；且 V 的秘书另有更严的隔离。**

| 谁 | 数据面 |
|---|---|
| 一般角色的秘书 | 可见范围**不超过它服务的那名智能体**（本体看不到的，秘书也不许看、不许转述） |
| **V 的秘书** | **不读 F 的叙述、不读被审证明之外的上下文**。`draft/39 §3.21` 的 I12 靠"冷启动不给 store 句柄、不给 F 的叙述"保证审校独立性 ⇒ 若 V 的秘书读全库（含 `handoffs` 正文、会话叙事），**它就成了绕过 I12 的暗通道**。⇒ V 的秘书只读"委托本身 + 硬性要求 + 全角色**定位** + V 自己的台账"；它的 handoff **写**也只写 V 自己的验证结论 |

## §2 能做哪些（动作面：六类，全是"内部动作"，不是模型可见的工具）

| 类 | 动作 | 输入 | 输出 | 不许做 |
|---|---|---|---|---|
| **A 改写** | `optimize_outbound`（职责 1） | 待发消息/委托 + 硬性要求 | 通过硬性要求的新版本（**原文并列留痕**） | 不改实质主张（不替本体承诺、不改结论、不加证据） |
| | `rework_inbound`（职责 4） | 收到的委托 + 本角色定位 | 贴本角色定位的版本（补上下文、明确产出物与验收口径） | 不加码不减码 |
| **B 评估** | `assess_delegation`（职责 2） | 委托 + 收件方定位/能力面 + 同 key 既有终态行 | 结论 ∈ `{可派, 建议重排, 建议改派, 建议不派}` + 理由 + 依据（`file:line` 或读数） | 不擅自改派（改派权在 M） |
| **C 协商** | `negotiate` | 与另一名秘书的分歧点 | 提案 / 回应 / **结论**（秘书⇄秘书） | **最多 2 轮**；不成上报本体，再不成上报 M |
| **D 提醒** | `remind_closure`（职责 3） | 收件箱 + 事件流 | "未接手 / 未反馈 / 对方没看到"清单 + 提醒消息（经 M） | 不替本体做事、不伪造反馈 |
| **E 记录** | `note_decision` | 以上任一步的结论 | 追加一行台账（见 §5.3 的字段） | 不写任何既有表 |

| **F 通道** | `handoff_add`（职责 1/4） | 本体的交接/派活内容 + 收件方 | 在 `manuscripts/handoffs.jsonl` **执笔一行**（`sender` 仍是**被服务的角色**） | 不改归属；不替本体编内容 |
| | `handoff_revise`（新增能力） | 要订正的手稿号 + 订正内容 | **追加一条修订行**（旧行保留） | **不改旧行、不删行**（append-only） |
| | `handoff_query`（职责 2/3/4） | 手稿号 / `to` / `sender` / `task_id` / `refs` | 查询结果（判重复、判已交接、查引用链） | 只读 |

**六类之外一律不做**：不执行任务、不落库（**除手稿通道**）、不跑实验、不改门、不改提示词、不改体例、
**不代签**、不判研究内容对错、**不做统计**（见 §4 末）。

## §3 能用哪些能力（**不是"没工具"**：手稿通道的**增 / 改 / 查**归秘书，智能体只保留"查"）

> **更正（2026-10-06，用户指出）**：本规范 v1 写的"工具面为空"是错的。秘书必须能读写**手稿通道**
> ——否则它连"这条指令是不是重复委派"都判不了。用户原话："**至少要能读 handoffs**，且由于**所有信息交互
> 都由秘书过一遍手**，所以 **handoffs 的增改查能力都该给秘书，智能体只保留'查'的能力**。"

### 3.1 秘书持有的三样能力（进程内能力，不是模型可见工具）

| 能力 | 具体函数（既有 / 待新增） | 用途 |
|---|---|---|
| **增** | **既有** `manuscripts.write(root, sender=…, recipient=…, title=…, body=…, refs=…)`（今天由 `agent_loop._do_handoff` 调用，`:1673`/`:1708`） | 职责 1/4：把本体的交接/派活**执笔**成一行手稿 |
| **改** | **待新增** `manuscripts.revise(root, mid=…, …)`（今天**不存在**：`manuscripts.py` 只有 `write/read/list_all/query/row_of/index/ref_problem/…`） | 订正写错的手稿；**追加修订行、不改旧行**（保持 append-only，旧行留痕） |
| **查** | **既有** `manuscripts.read` / `list_all` / `query` / `rows` / `row_of` / `rows_for_task` / `read_index` / `ref_problem`；模型可见面已暴露 `manuscripts.read` / `manuscripts.list`（`manuscript_tools.py`） | 判重复、判"已交接过"、查引用链、找前置手稿号 |

### 3.2 智能体只保留"查"

| 项 | 今天 | 改成 |
|---|---|---|
| **循环形状 `handoff`**（`agent_loop.py:65` 的 `SHAPES` 里有 `handoff`；`:318`/`:484` 收它；`:1076-1106` 校验它） | 智能体**自己写**手稿（`_do_handoff`） | **关闭智能体的写路径**：形状保留（本体仍然"说我要交接什么"），但**执笔改为本体的秘书** |
| **`summon` / `summon_many` 的 `notify`**（`:1673`、`:1708` 派生写） | 框架据派活**派生**一行 | 同样**改由发件方秘书执笔**（并保留"框架派生"与"执笔"两个标记的区别） |
| **`manuscripts.read` / `manuscripts.list`**（工具） | 智能体可读 | **保留**（这就是"智能体只保留查"） |
| 其它读写面（`store`、`fs.*`、`table.*`） | — | **不动**；秘书不使用它们 |

### 3.3 为什么不给秘书"注册工具"

它拿到的是**三类内部能力**：① 手稿通道的增/改/查；② 注册表与工作区的**只读**读数；
③ 自己那份台账的追加写。**这三样都不是模型可见工具**（不进 `tools` 注册表、不扩 `for_role` 的工具面、
不占只读例外表）—— 所以它**不触发 #5、不改权限面的声明**，同时又有足够的手脚干活。

## §4 权限是什么（一句话：**≤ 它服务的那名智能体，且只多一份自己的台账**）

| 面对 | 权限 |
|---|---|
| **表** | **只读**：`tasks`、`sessions`（事件）、`search_requests`、`reprocess_requests`、`verifications`、（M 的秘书另加）`closing` 读数。**写集 = ∅（不写任何库表）** |
| **文件** | **两处写**：① **手稿通道** `<ws>/manuscripts/handoffs.jsonl` 的**增/改**（这是它从智能体手里接过来的权限）；② 自己的台账 `out/secretary/<role>.jsonl`（追加式）。**不许改任何受保护文件**（`.noai-paths` 里的一切） |
| **工具** | **不使用注册工具**；只用手稿通道 + 只读读数 + 台账三类**内部能力**（§3）。智能体的手稿**写**权关闭、**查**权保留 |
| **模型** | 用**本智能体自己的** `llmseam` 缝；`scope="secretary"`；花销进同一本 `usage_ledger`；**受预算约束** |
| **对人** | 不直接对人说话（**除 M 的秘书**在状态报告里）；**不代签、不批准、不作证** |
| **对本体** | 只能"建议 + 提醒 + 询问 + 执笔"；**不能替本体表态**，不能改本体的记忆/提示词 |
| **信息面** | **≤ 本体**；V 的秘书另有更严的隔离（§1.5） |
| **失败姿态** | **fail-open**：超时/超预算/自己出错 ⇒ **原样放行 + 留痕**；机器已有的硬闸仍 fail-closed |
| **FC-27** | 秘书模块本身不在名册；它**不触碰**名册内文件；它的判断**不构成**任何门的通过条件 |
| **不做统计**（用户 2026-10-06 明确去掉） | **不计算"拒绝率 / 重复率 / 闭环率"这类指标**。它是**判断者**，不是仪表盘；效果评估由**机器读数与人**来做（`tasks`/`sessions` 本来就能算）。同理**它也不做花销统计与花销告警** —— 那不在四条职责里 |

**归属与审计（写死）**：秘书执笔的手稿行里，`sender` 仍是**被服务的那个角色**（作者=角色，执笔=秘书）；
秘书台账记下"我替谁执笔了哪一行（`mid`）"；**D64 的 `manuscript_rows` 计数口径不变**（仍按 `sender` 计），
不许把秘书执笔的行标成"框架派生"。

## §5 如何与智能体交流（协议）

### 5.1 五个消息种类（都走既有的会话事件通道）

| kind | 方向 | 内容 | 谁看 |
|---|---|---|---|
| `secretary_optimized` | 秘书 → **本体的发件** | 加工后的委托/消息（**对本体透明**：本体发的就是加工后的版本） | 收件方 + 收件方秘书 |
| `secretary_handoff` | 秘书 → **手稿通道** | **执笔结果**：`mid` + `sender`（=被服务的角色）+ `to` + `summary`，以及"这是新写还是修订" | 交接口 + 收发双方 + 收工门（`manuscript_rows` 口径不变） |
| `secretary_notice` | 秘书 → **本体** | 提醒：未接手 / 未反馈 / 逾期 | 本体（+ 状态报告） |
| `secretary_proposal` | 秘书 → **本体** | 建议：重排 / 改派 / 不派（附理由与依据） | 本体；本体可采纳也可不采纳（**改派权在 M**） |
| `secretary_question` | 秘书 → **本体** | 实质缺陷的询问：缺什么、需要什么前提 | 本体（**等答复**；超时按 fail-open 原样放行） |
| `secretary_negotiation` | 秘书 ⇄ **秘书** | 提案 / 回应 / **结论** | 双方秘书 + **结论必须抄送双方本体**（否则本体不知道为什么任务变了） |
| `secretary_decision` | 秘书 → **台账 + 事件流** | 一条决定（§5.3） | 台账 + M 的秘书 + 状态报告 |

**必须遵守的三条**：
1. **不许冒充本体**：所有消息带 `from: secretary/<role>`，正文不得以本体的口吻承诺任何事；
2. **协商结论必须让本体看见**（否则"任务是变过形的"这件事对本体不可见）；
3. **过程的原文与加工后必须并列留痕**（可复核），本体看结果、人看过程。

### 5.2 时序与成本

| 时机 | 同步/异步 | 超时与上限 |
|---|---|---|
| 发件前（职责 1、2） | **同步**（本体在等） | **1 次模型调用、≤ 3 秒**；超时 ⇒ 原样放行 + 留痕 |
| **手稿执笔**（职责 1/4 的 `handoff_add`/`handoff_revise`） | **同步**（与发件同一步） | 同上；写失败 ⇒ **报错并留痕**（这一条**不许**静默放行，否则手稿会缺行） |
| 收件时（职责 4） | **同步**（本体在等） | 同上 |
| 反馈回来后 / 收工前（职责 3） | **异步**（不阻塞本体） | 每次最多 N 条提醒（默认 5），避免刷屏 |
| 秘书⇄秘书协商 | 异步 | **最多 2 轮**，之后上报本体；再不成上报 M |
| 出错名/调不到工具 | 异步（下次发件前生效） | 每个错名只复盘一次（避免反复烧钱） |

**机器预筛 + 按需介入**（`draft/53` §6）：只有预筛报警（参数/枚举/必填/工具名/边/实现）、
闭环逾期、或**首次遇见该形态**时才叫秘书 ⇒ 花销与**问题量**成正比。

### 5.3 台账字段（`out/secretary/<role>.jsonl`）

```jsonc
{
  "seq": 12,                       // 脚本发号，追加式
  "at": "2026-10-06T18:22:31+08:00",
  "role": "M",                      // 秘书服务的那名智能体
  "duty": 2,                        // 1 格式内容 / 2 委派评估 / 3 闭环 / 4 委托加工
  "kind": "secretary_decision",
  "target": {"to": "D", "action": "register_conjecture", "input_key": "..."},
  "before": "……原文……",
  "after": "……加工后……",            // 与 before 并列；无改写则省略
  "decision": "建议重排",            // 或 可派 / 改派 / 不派 / 已优化 / 已提醒
  "reason": "D 的写集不含该表；建议改走 propose_question 两步",
  "basis": ["specs/d.py:232-235", "capabilities.WRITE_SETS", "tasks: 同 key 已有终态行"],
  "negotiation": [{"round": 1, "with": "secretary/D", "outcome": "接受"}],
  "fail_open": false                // true = 秘书没跑成，原样放行
}
```

### 5.4 本体能不能拒绝秘书？

**能。** 秘书的产物分两类：
- **格式类**（优化到能过硬性要求）：本体不需要"同意"，因为机器本来就会校验；改不动就 `secretary_question`；
- **判断类**（重排/改派/不派）：**只是建议**，本体可拒绝并写明理由；改派最终由 **M** 决定。
  秘书**永远不会**因为自己的判断而让某条委托"消失"——它只能"建议不派"，最后由 M 或本体决定。

## §6 一页速查

| 你的问题 | 答案 |
|---|---|
| **需要知道哪些** | ① 硬性要求（动作参数表 / 工具真名与参数 / 写集与边 / 只读面 / 有没实现）② **全部角色的定位**（每角色的六字段 + 十项官能 + 能力面，**全开**）③ 委托事实（`tasks` / 会话事件 / 收件箱）④ **手稿通道**（`manuscripts/handoffs.jsonl` 的读）⑤ 读数（**仅 M 的秘书**：30 档与附件缺口、V 的台账）。**数据面 ≤ 本体；V 的秘书不读 F 的叙述** |
| **能做哪些** | 六类内部动作：**改写**（`optimize_outbound` / `rework_inbound`）· **评估**（`assess_delegation`）· **协商**（`negotiate`，≤2 轮）· **提醒**（`remind_closure`）· **记录**（`note_decision`）· **通道**（`handoff_add` / `handoff_revise` / `handoff_query`）。不执行任务、不落库（除手稿通道）、不改门、不代签、**不做统计** |
| **能用哪些能力** | **不是"没工具"**：持有**手稿通道的增/改/查**（增=`manuscripts.write`、改=**待新增** `manuscripts.revise`（追加修订行）、查=`read/list_all/query/rows_for_task/ref_problem`）—— **智能体只保留"查"**（工具面上的 `manuscripts.read`/`manuscripts.list` 保留，写路径关闭）；另有注册表与工作区**只读读数**、自己台账的**追加写**。三类都是**内部能力，不是模型可见工具** |
| **权限是什么** | **≤ 它服务的那名智能体**：库表只读（**写集 ∅**）、文件**两处写**（手稿通道增/改 + 自己的台账）、不使用注册工具、模型用本体自己的缝且受预算约束、不直接对人说话、fail-open、不触碰 FC-27 名册内文件、判断不构成任何门的通过条件、**不做统计**（拒绝率/重复率/闭环率一律不由它算）。手稿行的 `sender` 仍是被服务的角色（作者=角色、执笔=秘书），`manuscript_rows` 口径不变 |
| **如何与智能体交流** | 六种事件：`secretary_optimized` / `notice` / `proposal` / `question` / `negotiation` / `decision`；发件与收件**同步**（1 次调用、≤3 秒、超时放行），闭环与协商**异步**（协商 ≤2 轮）；**不许冒充本体**、**协商结论必须抄送本体**、**原文与加工后并列留痕**；本体可拒绝建议，改派权在 M |
