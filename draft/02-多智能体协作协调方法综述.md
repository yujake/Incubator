## 0. 先给结论（一页话总结）

### 多智能体到底在解决什么问题？

一句话：**当一个任务太大、太杂、或者需要多个"专业视角"时，让一个模型一口气干完会吃力；于是我们把任务拆开、分给几个各管一段的模型，再把结果拼起来。**

学术界对"为什么要上多智能体"有个很干净的五点归纳：**任务分解、并行加速、上下文隔离、不同模型的集成、多样化推理讨论**（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657) 对 MAS 的定义式总结）。

Anthropic 讲得更直白：搜索的本质是"压缩信息"。子智能体各自用**独立的上下文窗口**并行探索问题的不同侧面，把最重要的 token 压缩出来交给主控；而且每个子智能体还带来"关注点分离"——**不同的工具、提示词和探索路径**，从而降低"路径依赖"（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。

### 什么时候有用？

有三类场景有实证支撑：

1. **广度优先的检索/调研**：需要同时追很多条互不依赖的线索。Anthropic 报告：**Opus 4 当主控 + Sonnet 4 当子智能体**的多智能体系统，在其内部研究评测上比单智能体 Opus 4 **高 90.2%**（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。
2. **信息量超过单个上下文窗口**：必须分头装、分头读。
3. **要对接很多复杂工具**：一个提示词塞不下那么多工具说明时，分工能显著提升可靠度。

另外，Anthropic 给了一个很硬的经验：在 BrowseComp 基准上，**光是 token 使用量就解释了 80% 的性能方差**（三个因素合计解释 95%）——也就是说多智能体"能干更多活"确实是它有效的主因，而不是什么玄学（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。

### 什么时候是负优化？

这是本报告最重要的部分，因为**目前炒得多、硬证据少**。

**证据一：多智能体贵得离谱。** Anthropic 自己的数据：智能体用的 token 约为普通对话的 **4 倍**，而多智能体系统约为 **15 倍**。原文：

> "in practice, these architectures burn through tokens fast. In our data, agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats."

并且明确说：**只有在任务价值高到足以支付这个性能溢价时，多智能体才在经济上成立**（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。

**证据二：多智能体的性能提升常常很小，失败率高得惊人。** Berkeley 的 MAST 论文开篇就写："Despite enthusiasm for Multi-Agent LLM Systems (MAS), their performance gains on popular benchmarks are often minimal." 实测 7 个主流开源 MAS 框架，失败率区间 **41%–86.7%**（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。

**证据三：失败主要不是"模型不够聪明"，而是"系统没设计好"。** MAST 用扎根理论分析 150+ 条轨迹、由 6 名专家标注，提炼出 **14 个失败模式 / 3 大类**（系统设计问题、智能体间失配、任务验证），人类标注一致性 κ = **0.88**。作者的原话是：这些失败"often stem from system design issues, not just LLM limitations or simple prompt following"，并且**需要结构性重设计**，不是打补丁能解决的（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。

**证据四："加智能体"会边际递减，甚至倒退。** 《Are More LLM Calls All You Need?》发现投票类方法的表现在调用次数上是**非单调**的——简单问题上随调用数上升，**难题上反而下降**，需要模型来算最优调用数（[Chen et al., 2024](https://arxiv.org/abs/2403.02419)）。

**证据五：多智能体的收益常常打不过"同一个模型多答几遍再投票"。** 这是自一致性 / best-of-N 基线。Self-Consistency 在 GSM8K 上就有 **+17.9%**、SVAMP **+11.0%**、AQuA **+12.2%**（[Wang et al., ICLR 2023](https://arxiv.org/abs/2203.11171)）。腾讯的 Agent Forest 工作更极端：**只是采样多次然后投票**，性能就随"智能体数量"提升，且能与其它复杂方法叠加（[Li et al., TMLR](https://arxiv.org/abs/2402.05120)）——换句话说，**很多多智能体系统报告的收益，可能只是"多花算力"的收益**。

**证据六：模型越强，多智能体的相对收益越小。** 《Single-agent or Multi-agent Systems? Why Not Both?》发现 MAS 相对单智能体的优势**随 LLM 能力提升而衰减**（o3 / Gemini-2.5-Pro 这类前沿模型已经把差距抹平很多），并提出"MAS↔SAS 级联"方案，准确率再提 **1.1%–12%**，同时部署成本最多降 **20%**（[Gao et al., 2025](https://arxiv.org/abs/2505.18286)）。

> **一句话判断法**：如果你能用「一个强模型 + 工具循环」或「一个模型 + 多答几遍投票」拿到八成效用，就**别上多智能体**。多智能体是为"任务本身可并行、且单窗口装不下"准备的专用工具，不是通用提效手段。
>
> 这不是本报告的独家观点——Anthropic 在更早的工程文章里写得更直接（**第二轮已取到原文**）：
> > "we recommend finding the simplest solution possible, and only increasing complexity when needed. **This might mean not building agentic systems at all.**"
> > "For many applications, however, **optimizing single LLM calls with retrieval and in-context examples is usually enough**."
> > "you should consider adding complexity ***only*** when it demonstrably improves outcomes."
>
> （[Anthropic, *Building effective agents*, 2024-12-19](https://www.anthropic.com/engineering/building-effective-agents)）

## 1. 六种基本协调范式

下面 6 种是文献里反复出现的基本形态。真实系统通常是它们的混合体。

### 1.1 流水线 / SOP 分工（Assembly Line）

**人话**：像工厂流水线，每人只干一道工序，干完把半成品交给下一个人。

```
用户需求
   │
   ▼
[产品经理]──需求文档──▶[架构师]──设计文档──▶[工程师]──代码──▶[测试]
                                                              │
                                                              ▼
                                                          最终产物
        （每个环节产出结构化"文档"，而不是自由聊天）
```

**代表系统**
- **MetaGPT**：把人写的**标准作业程序（SOP）**编码进提示词序列，用"**流水线（assembly line）**"范式给不同智能体分配角色，让具备领域知识的智能体去**校验中间结果**、从而减少错误。论文的动机就是：朴素地把 LLM 串起来会因**级联幻觉（cascading hallucinations）**导致逻辑不一致（[Hong et al., 2023](https://arxiv.org/abs/2308.00352)）。摘要中 "Standardized Operating Procedures (SOPs)" 与 "assembly line" 均为原文用词。
- **ChatDev**：虚拟软件公司，分设计/编码/测试阶段，智能体在"聊什么（chat chain）"和"怎么聊（communicative dehallucination）"两个层面被引导（[Qian et al., ACL 2024](https://arxiv.org/abs/2307.07924)）。
- **CAMEL**：用**角色扮演（role-playing）+ 初始提示（inception prompting）**让两个智能体自主把任务聊完（[Li et al., NeurIPS 2023](https://arxiv.org/abs/2303.17760)）。

**优点**：流程可预测、好调试、好插人工审核点；环节间传结构化文档（MetaGPT 的设计），错误不容易层层传染。

**坑**
- **上游错了下游全废**（级联幻觉）。
- **僵化**：任务不符合预设 SOP 就卡住。
- **价值全在流程细节里**。MAST 的干预案例最能说明问题：ChatDev 里的 CPO 智能体在没得到 CEO 共识时就擅自结束对话（失败模式 FM-1.2「不遵守角色规范」）。研究者只是改成"CEO 有最终决定权"这一条流程调整，任务成功率就 **+9.4%**（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。

### 1.2 中心化编排者（Orchestrator / Supervisor / Manager）

**人话**：一个"包工头"负责拆活、派活、验收；其他智能体只干被派的那一份，干完汇报。

```
            ┌──────────────────────┐
            │   编排者 / 主管       │
            │ （拆解 · 派活 · 收口） │
            └───┬────┬────┬────────┘
                │    │    │
         ┌──────┘    │    └──────┐
         ▼           ▼           ▼
    [子智能体 A] [子智能体 B] [子智能体 C]
      独立上下文   独立上下文   独立上下文
         │           │           │
         └───────────┴───────────┘
                     │
              只回传"压缩后的结论"
```

**代表系统**
- **Anthropic 多智能体研究系统**：官方称之为 **"orchestrator-worker pattern"**（编排者—工作者模式）——一个 lead agent 协调全局，把任务委派给并行运行的专职子智能体。LeadResearcher 会把计划**写进 Memory 持久化**（因为上下文超过 20 万 token 会被截断），然后并行启动子智能体，最后还有一个专职的**引用核查智能体（CitationAgent）**收尾（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- **HuggingGPT**：ChatGPT 当**控制器（controller）**——规划任务、从 Hugging Face 里挑模型、派子任务、最后汇总（[Shen et al., 2023](https://arxiv.org/abs/2303.17580)）。
- **Magentic-One**（微软）：主控就叫 **Orchestrator**，负责规划、跟踪进度、出错时重新规划，并指挥浏览器/文件/Python 等专业智能体（[Fourney et al., 2024](https://arxiv.org/abs/2411.04468)）。
- **AutoGen**：以"多个可自定义、可对话的智能体"为基本抽象，**对话模式可以用自然语言或代码来编排**；框架内置群聊管理组件（群聊管理器出现在论文正文，摘要中并未出现该组件名）（[Wu et al., 2023](https://arxiv.org/abs/2308.08155)）。

**优点**：**上下文隔离**是最大红利——子智能体各读各的，主控只看压缩结论，因此能处理远超单窗口的信息量。

**坑**
- **编排者本身是瓶颈和单点故障**：拆得不好全盘皆输。Anthropic 承认早期智能体会**为简单查询生成 50 个子智能体**、无休止地找不存在的来源、互相用过多更新打扰彼此（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- **重复劳动是真实故障**：Anthropic 举了具体例子——**一个子智能体去查 2021 年芯片危机，另外两个在重复查 2025 年供应链**。原话："Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information."
- **token 爆炸**：15× 的成本主要就来自这里。

### 1.3 辩论与投票（Debate / Voting / Ensemble）

**人话**：让几个"人"各答一遍，然后互相看答案、互相挑刺，几轮后收敛；或者干脆各答各的，最后投票。

```
   ┌────────┐   ┌────────┐   ┌────────┐
   │ 智能体1 │   │ 智能体2 │   │ 智能体3 │    第 1 轮：各答各的
   └───┬────┘   └───┬────┘   └───┬────┘
       │            │            │
       └────── 互相可见 / 互相质疑 ──┘       第 2..n 轮：辩论
       │            │            │
       ▼            ▼            ▼
   ┌────────┐   ┌────────┐   ┌────────┐
   │ 智能体1 │   │ 智能体2 │   │ 智能体3 │
   └───┬────┘   └───┬────┘   └───┬────┘
       └──────┬─────┴─────┬──────┘
              ▼           ▼
          [投票 / 共识 / 裁判] → 最终答案
```

**代表系统**
- **Multi-Agent Debate**：多个模型实例在多轮里提出各自的回答与推理过程，最终收敛到一个共同答案；论文称这种思路为 **"society of minds"**，报告在数学与策略推理上提升、并降低幻觉（[Du et al., 2023](https://arxiv.org/abs/2305.14325)）。
- **MAD（分 divergent thinking）**：提出"**思维退化（Degeneration-of-Thought）**"问题——模型一旦自信，自我反思就产生不了新想法；用带裁判、"tit for tat" 的多智能体辩论来破解（[Liang et al., EMNLP 2024](https://arxiv.org/abs/2305.19118)）。
- **ChatEval**：把辩论做成"**多评审团**"，模仿人类多标注者做开放式评估（[Chan et al., 2023](https://arxiv.org/abs/2308.07201)）。
- **FORD 三方辩论**：分析 LLM 协作的"内部一致性"——模型能达成共识，但**能力不平衡会让强模型主导**；用 GPT-4 当权威裁判能提升协作效果（[Xiong et al., EMNLP 2023 Findings](https://arxiv.org/abs/2305.11595)）。
- **说服力与真实性**：让辩论者更具说服力，可以让非专家模型答对率升到 **76%**、人类升到 **88%**（朴素基线分别为 **48%** 和 **60%**）（[Khan et al., 2024](https://arxiv.org/abs/2402.06782)）。
- **MoA（Mixture-of-Agents）**：分层聚合，每层多个模型提案、上一层把它们当辅助信息综合。报告纯开源模型组合在 **AlpacaEval 2.0 上达 65.1%，超过 GPT-4 Omni 的 57.5%**（[Wang et al., 2024](https://arxiv.org/abs/2406.04692)）。
- **LLM-Blender**：先**成对比较排名**（PairRanker），再**生成式融合**（GenFuser）（[Jiang et al., ACL 2023](https://arxiv.org/abs/2306.02561)）。
- **单智能体版的同类方法**：Self-Consistency（同模型多路径采样后投票，GSM8K **+17.9%**，[Wang et al., ICLR 2023](https://arxiv.org/abs/2203.11171)）；Agent Forest（多实例纯采样投票，[Li et al., TMLR](https://arxiv.org/abs/2402.05120)）。

**优点**：不需要训练、开箱即用；对"答案可验证"的任务（数学、事实核查）能提准确率；天然带**置信度信号**（票数分布）。

**坑（这一节的反面证据特别强，务必看）**
- **辩论在现形态下并不稳定优于更简单的方案**：Smit 等人的结论是"multi-agent debating systems, in their current form, **do not reliably outperform** other proposed prompting strategies, such as **self-consistency and ensembling**"；他们补充说 MAD 对超参数极其敏感、难调优（[Smit et al., 2023/ICML 2024](https://arxiv.org/abs/2311.17371)）。
- **单智能体 + 强提示词几乎追平最好的辩论方案**：只有在提示里**不给示例（no demonstration）**时，多智能体讨论才占优（[Wang et al., 2024](https://arxiv.org/abs/2402.18272)）。
- **系统性评测：辩论常常打不过 CoT / Self-Consistency，尽管花掉多得多的推理算力**——而且发现**模型异构（heterogeneity）是普遍有效的解药**（[Zhang et al., 2025](https://arxiv.org/abs/2502.08788)）。
- **自我纠错本身就不太靠谱**：没有外部反馈的"内在自我纠正"对推理任务无效，有时还会让结果变差（[Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798)）——这直接削弱了"辩论能靠自我批评纠错"的前提。
- **轮次越多不一定越好**：投票类方法的收益在调用次数上**非单调**（[Chen et al., 2024](https://arxiv.org/abs/2403.02419)）。所以"多辩论几轮"必须靠实验定，别拍脑袋。

> **实践底线**：上辩论/投票之前，**先跑 best-of-N 和 self-consistency 基线**。MAST 也明确把 best-of-N 列为多智能体常常打不过的简单基线（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。

### 1.4 去中心化点对点 + 通信拓扑裁剪

**人话**：没有包工头，智能体之间直接互相发消息，形成一张网。关键问题是——**这张网太密了，消息费钱，所以要剪枝**。

```
   全连接（贵）                      剪枝后（省）
  A ── B                             A ── B
  │╲╱│╲│                              │
  │╱╲│╱│                              │
  C ── D                             C    D
  每对都传消息                       只留有用的边
  O(n²) 条消息                       边数大幅下降
```

**代表系统**

| 系统 | 做法 | 实测收益 |
|---|---|---|
| **AgentPrune**（[2410.02506](https://arxiv.org/abs/2410.02506)） | 首次形式化定义"**通信冗余**"，对时空消息传递图做一次性剪枝 | 成本 **$43.7 → $5.6**；token 降 **28.1%–72.8%**；对抗攻击下性能反升 **3.5%–10.8%** |
| **GPTSwarm**（[2402.16823](https://arxiv.org/abs/2402.16823)） | 把智能体系统看成**可优化的计算图**：节点优化（提示词）+ 边优化（连接关系＝编排），可递归组合成层次 | 摘要未给具体数字 |
| **DyLAN**（[2310.02170](https://arxiv.org/abs/2310.02170)） | 先"团队优化"选上场的人，再"任务求解"；用无监督的 **Agent Importance Score** | 部分 MMLU 科目最多 **+25.0%** |
| **AgentDropout**（[2503.18891](https://arxiv.org/abs/2503.18891)） | 每轮通信都优化邻接矩阵，剔除冗余智能体与连接 | prompt token **-21.6%**、completion token **-18.4%**、性能 **+1.14** |
| **Adaptive Graph Pruning**（[2506.02951](https://arxiv.org/abs/2506.02951)） | 硬剪枝（砍智能体数量）+ 软剪枝（砍拓扑） | 性能 **+2.58%–9.84%**，token 消耗降 **90%+** |
| **Optima**（[2410.08115](https://arxiv.org/abs/2410.08115)） | 生成-排序-选择-训练迭代，奖励同时兼顾效果、token 效率、通信可读性 | Llama 3 8B 上"**用不到 10% 的 token 取得最多 2.8 倍性能提升**" |

**优点**：没有单点故障；拓扑可学习，能自动发现"谁该跟谁说话"；**剪枝是当前性价比最高的优化方向之一**——上面几篇普遍是"token 大降、性能不降甚至升"。

**坑**：不剪枝就是烧钱（消息量平方增长）；剪枝本身也有开销，小任务未必回本；消息满天飞导致**调试与可解释性更差**（对应 MAST 的 FC2「智能体间失配」类失败）。

### 1.5 动态路由与 handoff（交接）

**人话**：不预先画死组织架构图，而是让当前负责的智能体**自己决定"这活该转给谁"**；或者由一个路由层按问题难度动态选模型/选协作模式。

```
   用户请求
      │
      ▼
   [分流 / 路由层] ──简单问题──▶ [便宜的小模型] ──▶ 答复
      │
      ├──中等──▶ [中档模型] ──▶ 答复
      │
      └──复杂──▶ [强模型 / 专家组] ──▶ 答复

   ── handoff（交接）形式 ──
   [前台智能体] ──"这事我处理不了，转给你"──▶ [专家智能体]
       （OpenAI Swarm 的语义：换 system prompt，聊天记录不换）
```

**代表系统**
- **OpenAI Swarm**：只有两个原语——`Agent` 和 **handoff**。关键语义细节（已从官方 README 原文确证）：**交接时只有当前智能体的 instructions 在生效**（即 system prompt 会换），但**聊天历史不变**；且 "Swarm is entirely powered by the Chat Completions API and is hence **stateless between calls**"。官方现已在 README 顶部声明：**Swarm 已被 OpenAI Agents SDK 取代**，后者是 "a production-ready evolution of Swarm"，并建议**所有生产用例迁移**（[openai/swarm README](https://raw.githubusercontent.com/openai/swarm/main/README.md)）。
  > 补充（原文）：handoff 对 LLM 而言**就是一个工具**——交接给名为 `Refund Agent` 的智能体，工具名就是 `transfer_to_refund_agent`；交接后接手方"**gets to see the entire previous conversation history**"，除非你用 `input_filter` 过滤（[handoffs.md](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/handoffs.md)）。
- **OpenAI Agents SDK**：Swarm 的生产化继任者。核心概念包括 Agents、**Agents as tools / Handoffs**、Guardrails（输入输出安全校验）、Sessions（跨轮历史管理）、Tracing（内置追踪调试）、Human in the loop（[openai-agents 官方包页](https://pypi.org/project/openai-agents/)）。
  > ✅ **第二轮已补齐（2026 年补充核查，原文见附录一节）**。官方文档 `docs/multi_agent.md` 原文分两条编排路线：**"Allowing the LLM to make decisions"** 与 **"Orchestrating via code"**；并把两种核心模式并列对比：

  | 模式 | 官方原文怎么运作 | 官方原文什么时候用 |
  |---|---|---|
  | **Agents as tools** | "A manager agent **keeps control** of the conversation and calls specialist agents through `Agent.as_tool()`." | "You want **one agent to own the final answer**, combine outputs from multiple specialists, or enforce **shared SDK guardrails in one place**." |
  | **Handoffs** | "A triage agent routes the conversation to a specialist, and that specialist **becomes the active agent for the rest of the turn**." | "You want the specialist to respond directly, keep prompts focused, or have the handoff switch the active instructions without requiring the manager to narrate the result." |

  一句话记忆：**agents as tools＝主管保留控制权（下属帮个忙就回来）；handoffs＝把话筒交出去（专家接手本回合）。** 两者**可以混用**。原文还有一句关键取舍："Use agents as tools when a specialist should help with a **bounded subtask** but should not take over the user-facing conversation. Use handoffs when **routing itself is part of the workflow**."

  ⚠️ **但官方文档同时暴露了一个容易踩的坑**（handoffs 页原文）：
  > "Handoffs stay within a single run. **Input guardrails still apply only to the first agent in the chain, and output guardrails only to the agent that produces the final output.**"
  也就是说，交接链中间的智能体**默认没有 guardrail 覆盖**——要想每个环节都有检查，得改用 tool guardrails。这与 MAST 的 FM-3.2「验证缺失/不完整」正好对上：**框架默认的验证范围，往往比你以为的窄。**
- **RouteLLM**：用人类偏好数据训练路由器，在强/弱模型之间动态分流；摘要称"**在某些情况下把成本降低 2 倍以上**"且不牺牲质量，并支持在推理时替换模型后仍可用（[Ong et al., 2024](https://arxiv.org/abs/2406.18665)）。
  > ⚠️ 网上流传的"降低 85% / 45% 成本"是论文正文中的具体实验数字，**不在摘要里**，本报告不采用，改用摘要原文。
- **MasRouter**：不只路由 LLM，还路由"**协作模式**"和"**角色分配**"，报告 MBPP 上 **+1.8%–8.2%**、HumanEval 上开销最多降 **52.07%**、即插即用场景降 **17.21%–28.17%**（[Yue et al., 2025](https://arxiv.org/abs/2502.11133)）。
- **Semantic Kernel 的 Handoff 模式**：官方描述为"根据上下文或规则在智能体之间动态传递控制权"，典型用于动态工作流、升级（escalation）、兜底（fallback）、专家转接（[Microsoft Learn](https://learn.microsoft.com/en-us/semantic-kernel/frameworks/agent/agent-orchestration/)）。

**优点**：**省钱的正确姿势**——大部分请求根本不需要贵模型或复杂协作；架构灵活，不必预先设计完整组织。

**坑**：交接语义在不同框架里不一样，必须搞清楚你到底交出了什么（否则会出现 MAST 的 FM-2.1「对话被重置」、FM-1.4「对话历史丢失」）；路由判断本身会错，把难题当简单题就直接翻车；交接链过长则延迟与成本双爆。

### 1.6 层次化嵌套（团队套团队）

**人话**：不止一层包工头。大包工头下面有小包工头，小包工头再管几个人。

```
                 [总编排者]
                 /    |     \
          [中层A]   [中层B]   [中层C]
          /    \       |      /    \
      [工人][工人]  [工人]  [工人][工人]
        （每层都做"拆解→派活→收口"，层数可以更深）
```

**代表系统**
- **MacNet**：把协作组织成有向无环图，支持 **1000 个以上智能体**；发现**不规则拓扑优于规则拓扑**，并给出"协作缩放律"呈**逻辑斯蒂增长（logistic growth）**（[Qian et al., ICLR 2025](https://arxiv.org/abs/2406.07155)）。
- **AgentOrchestra**：分层规划者 + 子智能体，报告在 GAIA Test 上达 **89.04%**（[Zhang et al., 2025](https://arxiv.org/abs/2506.12508)）。
- **Semantic Kernel 的 Magentic 模式**：官方说明其"受 Magentic-One 启发"，用于"复杂的通用多智能体协作"（[Microsoft Learn](https://learn.microsoft.com/en-us/semantic-kernel/frameworks/agent/agent-orchestration/)）。
- **GPTSwarm**：支持把优化好的图**递归组合**成更高层图，天然支持层次（[Zhuge et al., ICML 2024](https://arxiv.org/abs/2402.16823)）。

**优点**：可扩展到很大规模；每层只暴露"压缩后的接口"，总上下文可控；适合本身有天然层级的任务（公司组织、大型代码库）。

**坑**：成本随层数快速放大（每层都要重新描述任务）；信息在层间被反复压缩，越往上越可能丢关键细节——这正是 MAST 的 FM-3.2「验证缺失/不完整」与 FC2 类失配风险的高发区（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）；**规模大 ≠ 效果好**：MacNet 的逻辑斯蒂曲线意味着**存在饱和点**，越过它继续加人只加成本。

## 2. 协调靠什么机制落地

范式只是骨架，真正决定成败的是下面这些"关节"。

### 2.1 任务分解
把大目标切成可独立执行的子任务。判断标准很简单：**子任务之间是否真的能并行**。Anthropic 明确说多智能体适合"广度优先、需要同时追多条互不依赖方向"的查询；他们同时明确划出了**反面边界**：

> "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today. For instance, **most coding tasks involve fewer truly parallelizable tasks than research**, and LLM agents are not yet great at coordinating and delegating to other agents in real time."

（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）
**结论**：**大部分写代码任务不该用多智能体**——这是厂商自己说的。

### 2.2 角色定义
给每个智能体身份、职责边界、输出格式。MetaGPT 用 SOP + 角色分工（[Hong et al., 2023](https://arxiv.org/abs/2308.00352)），CAMEL 用 inception prompting 让角色扮演自动进行（[Li et al., 2023](https://arxiv.org/abs/2303.17760)）。

**坑**：角色写了不等于会遵守。MAST 专门有 FM-1.1「不遵守任务规范」、FM-1.2「不遵守角色规范」（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。所以角色定义必须配**可机器检查的产出格式**，不能只写"你是一个资深架构师"。

### 2.3 共享记忆 / 黑板（Blackboard）
**黑板**是经典多智能体概念：一块所有智能体都能读写的公共区域，大家往里贴结果、也从里面取别人的结果。

- **Generative Agents**：核心是**记忆流（memory stream）**——把全部经历用自然语言记下来，随时间**反思（reflection）**合成更高层的记忆，再**按需检索**用于规划行为；沙盒里跑了 **25 个智能体**。消融实验显示观察、规划、反思三者缺一不可（[Park et al., 2023](https://arxiv.org/abs/2304.03442)）。
- **MemGPT / Letta**：用操作系统思路做**虚拟上下文管理**——分层内存（快的主上下文 vs 慢的外部存储）+ **分页/数据搬运** + 中断机制，模拟"无限内存"（[Packer et al., 2023](https://arxiv.org/abs/2310.08560)）。
- **Letta 团队的后续工作 Sleep-time Compute**：让模型**离线时先"想好"**、预计算可能被问到的内容。报告在同等准确率下**测试时算力降约 5 倍**、缩放离线算力还能再涨 **+13%/+18%** 准确率、平均每查询成本降 **2.5 倍**（[Lin et al., 2025](https://arxiv.org/abs/2504.13171)）。
  > ⚠️ 核查说明：**不存在标题为 "Letta" 的论文**；"Letta context engineering" 更像是博客内容而非 arXiv 论文。
- **Anthropic 的做法**：主控把计划写进 **Memory** 持久化，避免上下文被截断后丢掉计划（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- **还有一个实用技巧**：把子智能体的输出**落盘到文件系统**，以减少"传话游戏（game of telephone）"式的信息损耗（同上）。

**坑**：共享状态是双刃剑——它解决"信息不通"，但也会把**错误传播给所有人**，而且容易让上下文迅速膨胀到截断。实践上要区分"谁写得进、谁只读得到"。

### 2.4 消息协议
智能体之间用什么格式说话。选项从"纯自然语言聊天"到"结构化文档"到"标准协议"：

- **结构化产出**：MetaGPT 让每个环节产出文档而非闲聊，是抑制级联幻觉的关键设计（[Hong et al., 2023](https://arxiv.org/abs/2308.00352)）。
- **链式自然语言消息**：Chain-of-Agents 让多个 worker 智能体按顺序处理分段文本、把结论用自然语言传给下一个，最后 manager 汇总；报告比 RAG / 全上下文 / 多智能体基线最多提升 **10%**（[Zhang et al., 2024](https://arxiv.org/abs/2406.02818)）。
- **跨厂商协议**：
  - **MCP（Model Context Protocol）**：连接 AI 应用与外部系统（数据源、工具、工作流/专用提示词）的开放标准；官方定位是**agent-to-tool 通信**（[modelcontextprotocol.io 介绍页](https://modelcontextprotocol.io/docs/getting-started/intro)）。
  - **A2A（Agent2Agent）**：面向"不透明智能体应用之间"的通信与互操作开放协议；最初由 Google 开发并**捐赠给 Linux Foundation**；官方明确写了 **"Not a sub-agent or tool-call protocol"**，即管的是 agent↔agent（[A2A 官方站](https://a2a-protocol.org/latest/)）。已发布稳定 v1.0，被 **150+ 组织**支持，并作为 Growth Stage 项目并入 Linux Foundation 旗下的 Agentic AI Foundation（[A2A 官方博客](https://a2a-protocol.org/latest/blog/2026/08/27/a-new-chapter-for-a2a-joining-the-agentic-ai-foundation/)）。官方对二者分工的说法：**"MCP 是纵向整合层（agent↔工具），A2A 是横向协议（点对点协作）"**。

  > ⚠️ **别搞混**：**MCP ≠ 多智能体协作协议**。它管"模型/智能体 → 工具与上下文"，不管"智能体 → 智能体"。
  > ⚠️ 核查说明：A2A 的 **"agent card"** 概念在本次可访问的官方页面中未逐字取到（相关 key-concepts 页未能抓取），故本报告不做细节展开。

### 2.5 终止条件
什么时候算干完了。这是被严重低估的机制。MAST 的失败模式里直接有 **FM-1.5「不知道停止条件」** 和 **FM-3.1「过早终止」**（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。Anthropic 的实测失败现象同样包括"无休止地搜索不存在的来源"（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。

**实践建议**：硬性轮次上限 + 明确的"完成定义"（Definition of Done）+ 外部可验证的验收信号，三者同时上。

### 2.6 结果聚合与置信度
- **投票**：Self-Consistency 是最省钱的一种（[Wang et al., ICLR 2023](https://arxiv.org/abs/2203.11171)）。
- **分层聚合**：MoA 让每层多个模型提案、上一层综合（[Wang et al., 2024](https://arxiv.org/abs/2406.04692)）。
- **先排序再融合**：LLM-Blender 的 PairRanker + GenFuser（[Jiang et al., ACL 2023](https://arxiv.org/abs/2306.02561)）。
- **可学习的聚合**：Optima 把 token 效率写进奖励，让模型学会"少说废话"（[Chen et al., 2024](https://arxiv.org/abs/2410.08115)）。

**坑**：投票只有在"错误不相关"时才有用。同一个底座模型的多个实例，错误高度相关，票数会给你**虚假的信心**——这也正是"**模型异构**"被证明是普遍有效解药的原因（[Zhang et al., 2025](https://arxiv.org/abs/2502.08788)）。

### 2.7 冲突解决
两个智能体给出矛盾结论怎么办。文献里的手段：多轮辩论收敛（[Du et al., 2023](https://arxiv.org/abs/2305.14325)）、引入**权威裁判**（Xiong 等人发现 GPT-4 当裁判能提升协作，[2305.11595](https://arxiv.org/abs/2305.11595)）、或由编排者按规则裁定。

MAST 的经验是**把最终裁决权明确写进流程**——ChatDev 那个"CEO 有最终决定权"的改动带来 **+9.4%**（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。
**一句话**：冲突解决不能靠"大家聊着聊着就一致了"，要明确指定**谁说了算**。

### 2.8 预算与轮次控制
- 多智能体 **15×** token、单智能体 **4×** token（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- 调用次数存在最优值，超过会变差（[Chen et al., 2024](https://arxiv.org/abs/2403.02419)）。
- 剪枝能省 **28%–90%** token（[AgentPrune](https://arxiv.org/abs/2410.02506)、[AgentDropout](https://arxiv.org/abs/2503.18891)、[AGP](https://arxiv.org/abs/2506.02951)）。
- 路由至少能省 **2×** 以上成本（[RouteLLM](https://arxiv.org/abs/2406.18665)），MAS↔SAS 级联最多再降 **20%** 部署成本（[Gao et al., 2025](https://arxiv.org/abs/2505.18286)）。

**实践建议**：把"预算"当一等参数——每个子任务设 token 上限和最长轮次，超了就降级到单智能体或直接返回当前最好答案。

### 2.9 人类介入点（Human in the loop）
- OpenAI Agents SDK 把 **Human in the loop** 作为内置机制，并提供 **Guardrails** 做输入输出校验（[openai-agents](https://pypi.org/project/openai-agents/)）。
- Anthropic 的经验：**小规模人工评估不能省**。他们的测试者发现早期智能体偏爱 SEO 内容农场而不是权威来源，加了"来源质量启发式"才修好；同时强调**别等能建几百条测试用例才开始 eval**——他们的建议是从约 **20 条查询**起步（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- 他们还总结了一条工程规律：**"Agents are stateful and errors compound"**（智能体是有状态的，错误会复利）——因此需要**持久化执行与可恢复（durable execution）**、全链路生产环境 tracing、以及渐进式发布（彩虹部署）。

**落点**：高风险动作（写数据库、发邮件、花钱、改生产代码）前挂人工确认，其余环节自动化。

## 3. 大厂工程实践对比

| 厂商 | 代表系统 / 协议 | 偏好范式 | 关键设计选择 |
|---|---|---|---|
| **Anthropic** | Claude Research 多智能体研究系统（2025-06-13 发布） | **中心化编排者（orchestrator-worker）+ 并行子智能体** | 主控（LeadResearcher）拆解并把计划写进 **Memory** 防截断；子智能体各自独立上下文窗口做并行"压缩"，并带来关注点分离（不同工具/提示/探索路径）以降低路径依赖；**公开承认 15× token 成本**并据此限定适用场景；明确说**共享上下文强依赖的领域（含大部分编码任务）不适合**；子智能体提示必须含目标、输出格式、工具/来源指引、清晰任务边界；**主控并行 3-5 个子智能体、子智能体再并行 3+ 工具**；用工具测试智能体重写工具描述，任务完成时间 **-40%**；把子智能体输出落盘以减轻"传话游戏"损耗（[来源](https://www.anthropic.com/engineering/multi-agent-research-system)） |
| **OpenAI** | Swarm → Agents SDK | **动态路由 / handoff** | Swarm 只保留两个原语：`Agent` + **handoff**；交接时**换 system prompt、保留聊天历史**；官方标注为 educational、不用于生产（[Swarm](https://pypi.org/project/openai-swarm/)）。Agents SDK 补上 Guardrails、Sessions、Tracing、Human-in-the-loop，并把 **Agents as tools** 与 **Handoffs** 并列为两种委派方式（[Agents SDK](https://pypi.org/project/openai-agents/)）。⚠️ 官方文档站本次不可达，"agents as tools＝LLM 编排 / handoffs＝代码编排"未逐字确证 |

## 4. 失败模式与避坑清单（基于 MAST 等实证）

MAST 的 **14 个失败模式 / 3 大类**（人工标注 κ=0.88，MAST-Data 覆盖 7 个框架共 **1642** 条轨迹）是本节主干（[Cemri et al., 2025](https://arxiv.org/abs/2503.13657)）。

> ⚠️ **核查更正**：MAST 研究的 7 个框架是 **ChatDev、MetaGPT、HyperAgent、AppWorld、AG2（MathChat）、Magentic-One、OpenManus**。**CrewAI 并未被纳入研究**；"AutoGen" 在论文中以 **AG2（AutoGen v0.2 的社区分支）** 的形式出现。请勿把 CrewAI 写进 MAST 的结论里。
> ⚠️ 另外两个版本差异需注意：
> - **干预收益**：v1 给的是 **+14%**，v3 给的是 **+9.4%**（ChatDev 任务成功率）。本报告采用最新的 v3 数字 **+9.4%**。两处都是"提示词/编排层面"的干预，**不是**"加了个 LLM 裁判验证器"带来的收益——这一点常被误传。
> - **三大类的名字**：v3 用的是 FC1「System Design Issues」、FC2「Inter-Agent Misalignment」、FC3「Task Verification」；v1 用的是「Specification and System Design Failures」「Inter-Agent Misalignment」「Task Verification and Termination」。引用时注意版本。

### 4.1 三类失败及其对应失败模式

**FC1 系统设计问题（System Design Issues）**

| 编号 | 失败模式 | 人话解释 | 对策 |
|---|---|---|---|
| FM-1.1 | Disobey task specification | 没按要求干 | 把要求写成**可机器检查**的约束，别只用自然语言嘱咐 |
| FM-1.2 | Disobey role specification | 越权、抢活、擅自收尾 | 明确"**谁有最终决定权**"（ChatDev 案例 +9.4%）；产出格式绑定角色 |
| FM-1.3 | Step repetition | 反复做同一步 | 加去重/进度状态；设硬轮次上限 |
| FM-1.4 | Loss of conversation history | 聊到后面忘了前面 | 持久化记忆（把计划写进 Memory）；定期摘要；子产出落盘 |
| FM-1.5 | Unaware of stopping conditions | 不知道啥时候停 | 显式"完成标准"（DoD）+ 最大轮次 |

**FC2 智能体间失配（Inter-Agent Misalignment）**

| 编号 | 失败模式 | 人话解释 | 对策 |
|---|---|---|---|
| FM-2.1 | Conversation reset | 对话被重置、上下文丢失 | 搞清楚框架的交接语义（如 Swarm 交接保留历史但换 system prompt） |
| FM-2.2 | Fail to ask for clarification | 不懂也不问，硬编 | 给智能体"提问"这个动作，并允许它暂停 |
| FM-2.3 | Task derailment | 跑题 | 每轮拿目标做一次对齐检查 |
| FM-2.4 | Information withholding | 有话不说，别人不知道 | 共享黑板 / 强制结构化交接 |
| FM-2.5 | Ignored other agent's input | 无视别人的意见 | 冲突解决要指定裁决者，别指望自动一致 |
| FM-2.6 | Reasoning-action mismatch | 说的和做的不一致 | 用工具执行结果做校验，别信"我说我做完了" |

**FC3 任务验证（Task Verification）**

| 编号 | 失败模式 | 人话解释 | 对策 |
|---|---|---|---|
| FM-3.1 | Premature termination | 没干完就宣布完成 | 外部可验证的验收信号（测试通过、编译通过） |
| FM-3.2 | No or incomplete verification | 没人验收，或只验了一部分 | 独立验证者智能体 **+** 自动化测试，二者都要 |
| FM-3.3 | Incorrect verification | 验错了（把错的判成对的） | 验证者别和生产者共享上下文/提示；用确定性工具兜底 |

### 4.2 通信冗余与成本类问题（可用指标量化）

| 问题 | 实证 | 对策 |
|---|---|---|
| 消息太多、全连接烧钱 | AgentPrune 形式化"通信冗余"，剪枝后成本 **$43.7→$5.6**、token 降 **28.1%–72.8%**（[2410.02506](https://arxiv.org/abs/2410.02506)） | 剪枝拓扑；限制可见范围 |
| 冗余智能体 | AgentDropout 剔除冗余智能体/边：prompt token **-21.6%**、completion token **-18.4%**、性能 **+1.14**（[2503.18891](https://arxiv.org/abs/2503.18891)） | 动态决定"这场谁上场" |
| 拓扑不对 | AGP：硬剪+软剪，性能 **+2.58%–9.84%**、token 降 **90%+**（[2506.02951](https://arxiv.org/abs/2506.02951)） | 让图结构成为可调参数 |
| 加智能体/加调用反而变差 | 投票类方法收益随调用次数**非单调**（[2403.02419](https://arxiv.org/abs/2403.02419)）；MAS 优势随模型变强而衰减（[2505.18286](https://arxiv.org/abs/2505.18286)） | 用实验定最优调用数；模型升级后**重新评估是否需要 MAS** |
| 单点故障 | 编排者拆错就全错；早期系统为简单问题生成 **50 个子智能体**（[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)） | 预算上限 + 拆解质量评估 |
| 重复劳动 | 一个子智能体查 2021 芯片危机，另两个重复查 2025 供应链（同上） | 任务描述必须具体；共享已完成的子任务清单 |

### 4.3 错误级联
MetaGPT 的出发点就是"朴素地串 LLM 会导致**级联幻觉**"（[Hong et al., 2023](https://arxiv.org/abs/2308.00352)）；Anthropic 的经验法则是"**智能体是有状态的，错误会复利**"（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）。

**对策**：每个环节都做中间结果校验（MetaGPT 的做法是让具备领域知识的上游/同行智能体验证），把产出结构化，并支持从断点恢复。**核心原则：不要让未经校验的中间产出直接进入下一步。**

## 5. 成本与收益：token / 延迟 / 成功率三角

```
        成功率
          ▲
          │        ★ 多智能体（广度优先调研、超长上下文、多工具）
          │       ╱
          │      ╱   ← 收益递减/饱和区（MacNet：逻辑斯蒂增长，有饱和点；
          │     ╱        且模型越强，MAS 相对优势越小）
          │    ╱
          │   ╱  ● 单智能体 + 工具循环
          │  ╱
          │ ╱ ○ 单次调用
          └──────────────────────────────▶ 成本（token × 延迟）
```

**成本端的硬数据**
- 多智能体 ≈ **15×** 普通对话的 token；带工具的智能体 ≈ **4×**（[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- 剪枝可省 **28%–90%** token，且性能往往不降反升（[AgentPrune](https://arxiv.org/abs/2410.02506)、[AgentDropout](https://arxiv.org/abs/2503.18891)、[AGP](https://arxiv.org/abs/2506.02951)）。
- 路由可降成本 **2× 以上**（[RouteLLM 摘要](https://arxiv.org/abs/2406.18665)）；MAS↔SAS 级联最多再降 **20%** 部署成本（[Gao et al., 2025](https://arxiv.org/abs/2505.18286)）。
- 离线预计算（sleep-time compute）在同等准确率下省约 **5×** 测试时算力（[Lin et al., 2025](https://arxiv.org/abs/2504.13171)）。

**收益端的硬数据**
- Anthropic 内部研究评测：多智能体比单智能体 **+90.2%**（[来源](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- 但通用基准上：MAS 增益"often minimal"，实测失败率 **41%–86.7%**（[MAST](https://arxiv.org/abs/2503.13657)）。
- 辩论类方法：常常打不过 CoT / Self-Consistency 却花更多算力（[Zhang et al., 2025](https://arxiv.org/abs/2502.08788)；[Smit et al., 2023](https://arxiv.org/abs/2311.17371)；[Wang et al., 2024](https://arxiv.org/abs/2402.18272)）。

**延迟端**
- **并行是唯一能同时改善延迟和覆盖面的手段**：主控并行开 3-5 个子智能体、子智能体再并行用 3+ 工具，Anthropic 报告复杂查询的研究时间最多**缩短 90%**（[来源](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- 反过来，串行辩论/多轮协商会**线性叠加延迟**。

**决策规则：**

| 情况 | 建议 |
|---|---|
| 任务单一、上下文装得下、工具少 | **单智能体 + 工具循环**。别上多智能体。 |
| 任务难，但"能不能一次答对"是核心 | 先试 **best-of-N / 自一致性投票**（GSM8K +17.9%），便宜且常常够用（[Wang et al., 2022](https://arxiv.org/abs/2203.11171)、[Li et al., 2024](https://arxiv.org/abs/2402.05120)） |
| 请求难度分布很宽、成本敏感 | 上**路由**（强/弱模型分流），比上多智能体便宜得多（[RouteLLM](https://arxiv.org/abs/2406.18665)） |
| 广度优先检索、多线索并行、信息超单窗口 | **多智能体（中心化编排 + 并行子智能体）**——这是唯一有强证据的场景（[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)） |
| 有强顺序依赖（含**大部分编码任务**） | **流水线 + 中间校验**，而不是并行智能体（[MetaGPT](https://arxiv.org/abs/2308.00352)；[Anthropic 明确不建议](https://www.anthropic.com/engineering/multi-agent-research-system)） |
| 答案客观可验证（数学/代码） | 辩论或投票**才可能**有效；且必须用**异构模型**，同模型多实例的票数会骗你（[Zhang et al., 2025](https://arxiv.org/abs/2502.08788)） |
| 高价值、长周期、要跨系统 | 多智能体 + 持久化记忆 + 人类检查点 + 全链路 tracing |

## 6. 工程落地选型建议（if-then 决策表）

**第一步：先问"能不能不用多智能体"**

```
IF 单个强模型 + 工具循环能达到目标质量的 80% 以上
   THEN 停。不要多智能体。（MAST：MAS 增益常常很小）
ELIF 只是"想让它答得更准"
   THEN 先上 self-consistency / best-of-N（GSM8K +17.9%），再考虑辩论
ELSE 继续 ↓
```

**第二步：按"任务结构"选范式**

```
IF 任务可拆成互不依赖的并发子任务，且信息量超单窗口
   THEN 中心化编排者 + 并行子智能体（Anthropic 模式）
        必配：子智能体提示含【目标 / 输出格式 / 可用工具与来源 / 清晰任务边界】
        必配：主控把计划持久化到 Memory；子产出落盘
        必配：主控并行 3-5 个子智能体，子智能体再并行用工具

ELIF 任务有明确工序顺序、每步可校验
   THEN 流水线 / SOP 分工（MetaGPT 模式）
        必配：环节间传结构化文档，不传自由聊天
        必配：每步让下游/同行校验上游；显式指定最终裁决者

ELIF 答案客观可验证（数学、代码、事实核查），且要提准确率
   THEN 辩论 / 投票，但必须先测 best-of-N 与 self-consistency 基线
        必配：用异构模型（同模型多实例的错误是相关的）
        必配：做调用次数消融（收益是非单调的！）

ELIF 请求难度差异大、成本敏感
   THEN 动态路由优先于多智能体
        深入后如仍不够，再叠 MasRouter 式的"模式 + 角色 + 模型"三级路由

ELIF 任务天然有组织层级 / 规模要上千智能体
   THEN 层次化嵌套（MacNet 模式），但先确认没到收益饱和点

ELIF 模型已经很强（o3 / Gemini-2.5-Pro 级别）
   THEN 重新评估是否还需要 MAS——MAS 相对优势随模型能力提升而衰减

ELSE 不确定
   THEN 从"单智能体 + 工具"开始，逐步加人；每加一个测一次
```

**第三步：无论选哪种，都要配的"安全阀"**

```
[ ] 预算：每个子任务设 token 上限
[ ] 轮次：硬性最大轮次，超限降级或返回当前最优
[ ] 终止：显式 Definition of Done + 外部可验证信号（测试 / 编译 / schema）
[ ] 验证：独立验证者（与生产者不同上下文）+ 确定性工具兜底
[ ] 裁决：冲突时谁说了算，写进流程（别靠"聊到一致"）
[ ] 记忆：计划与关键状态持久化，防上下文截断（FM-1.4）
[ ] 断点恢复：按"错误会复利"设计，支持 durable execution 与恢复
[ ] 拓扑：上规模前先剪枝（省 28%–90% token）
[ ] 观测：全链路 tracing，否则失败无法定位
[ ] 人工：高风险动作前挂 human-in-the-loop + guardrails
[ ] 评估：小规模 eval 立刻开始（Anthropic 建议从约 20 条查询起步）
```

**第四步：上线后的调优优先级（按投入产出比排序）**

```
1. 剪 / 优化通信拓扑        → token 降 28%–90%
2. 加模型路由               → 成本降 2× 以上
3. 优化工具描述             → 任务完成时间 -40%（Anthropic 实测）
4. 加并行（子智能体级 + 工具级） → 复杂查询时间最多 -90%
5. 修终止条件与验证环节      → 直击 MAST 中占比最高的失败类别
6. 换异构模型               → 辩论/投票类方法普遍有效的解药
7. 最后才考虑"再加一个智能体"
```

## 7. 术语表（大白话）

| 术语 | 大白话解释 |
|---|---|
| **Agent（智能体）** | 一个"会用工具的模型循环"——给它目标和工具，它自己决定下一步调什么，直到认为完成。Anthropic 的定义是 "LLMs autonomously using tools in a loop"。 |
| **Orchestrator（编排者 / 主管）** | 负责拆任务、派活、收结果的角色。它不必比下属聪明，但必须知道怎么分活。Magentic-One 里就叫 Orchestrator；Anthropic 管这套叫 **orchestrator-worker pattern**。 |
| **Handoff（交接）** | 把"话筒"从一个智能体交给另一个。注意框架语义不同——OpenAI Swarm 是**换系统提示词、保留聊天记录**。 |
| **Agents as tools（智能体当工具）** | 把下属当成一个"函数"来调用，调用完主管还在台前，控制权不转移。与 handoff 相对。（OpenAI Agents SDK 中两者并列为核心概念） |
| **黑板（Blackboard）** | 一块公共读写区，大家把中间结果贴上去、别人取用。解决"信息不通"，但也会传播错误。 |
| **共享记忆 / 记忆流（Memory stream）** | 把经历用自然语言持续记下来，需要时检索出来用。Generative Agents 的叫 memory stream，还带"反思"机制合成高层结论。 |
| **上下文隔离（Context isolation）** | 每个智能体有自己的上下文窗口，互不污染。好处是能处理超长信息；坏处是彼此不知道对方干了啥，容易重复劳动。 |
| **涌现（Emergence）** | 单个智能体没有的行为，在多智能体互动中自己冒出来（如自发分工、自发形成规范）。AgentVerse 的副标题就是 "Exploring Emergent Behaviors"。 |
| **验证者（Verifier）** | 专门检查别人产出对不对的智能体。关键是别用和生产者一样的上下文和提示，否则容易"一起错"。 |
| **投票（Voting）** | 多个答案里选票数最多的。便宜有效，但前提是错误**不相关**——同一个模型的多份输出错误是相关的，票数会骗你。 |
| **共识（Consensus）** | 大家聊到意见一致。听起来美好，但可能只是"能说会道的一方带偏了所有人"；研究还发现**能力不平衡会让强模型主导**对话。 |
| **Self-Consistency** | 同一个模型多采样几条推理路径然后投票。是多智能体投票最直接的"便宜替代品"（GSM8K +17.9%）。 |
| **best-of-N** | 生成 N 个答案，用打分器选最好的。MAST 用它作为检验多智能体是否真有价值的基线。 |
| **通信拓扑（Topology）** | 智能体之间谁连谁的图结构。全连接最贵（消息量 O(n²)），剪枝能省 28%–90% token。 |
| **剪枝（Pruning）** | 把没用的连接和没用的智能体删掉。AgentPrune / AgentDropout / AGP 都在做这个。 |
| **路由（Routing）** | 按问题难度把请求分给不同档次的模型或不同协作模式。 |
| **SOP（标准作业程序）** | 人写好的标准流程。MetaGPT 把 SOP 编进提示词序列，让智能体按流程走。 |
| **级联幻觉（Cascading hallucination）** | 上游编错了，下游照着错的往下做，错误像滚雪球。MetaGPT 就是为治它而设计的。 |
| **MCP（Model Context Protocol）** | 管"智能体怎么连工具/数据"的**纵向**协议。**不是**智能体之间的协作协议。 |
| **A2A（Agent2Agent）** | 管"智能体之间怎么互相通信与派活"的**横向**协议，官方明确"不是 sub-agent 或 tool-call 协议"；已到 v1.0、150+ 组织支持。 |
| **Group Chat（群聊）** | 所有智能体在一个群里交谈，由一个"群主"协调。Semantic Kernel 把它和 Handoff 列为两种不同编排模式。 |
| **休眠期计算（Sleep-time compute）** | 让模型在没被提问时先"离线想"，预计算可能被问到的内容，从而省下在线算力（约 5×）。 |
| **MAST** | Berkeley 出的多智能体失败分类法：**14 个失败模式、3 大类**、1642 条轨迹、κ=0.88。做 MAS 排障时最实用的检查表。 |

## 8. 本报告的三点提醒（含不确定性声明）

1. **别把"多智能体"当默认答案。** 最强证据（MAST 的 41%–86.7% 失败率、Anthropic 的 15× token、辩论类方法打不过 self-consistency 的多篇评测）都指向同一结论：**多智能体是高成本的特种工具，不是通用提效手段**。先用单智能体 + 工具 + 少量采样打基线。

2. **收益主要来自"结构"而不是"模型数量"。** MAST 的结论很重：失败根因是**系统设计**，需要结构性重设计；而剪枝/路由/工具描述优化这些"结构类"改动能带来 **28%–90%** 的成本下降——**优化结构比堆智能体划算得多**。

3. **本次核查发现并修正了若干常见错误归属（请勿再传播）**：
   - **CrewAI 没有自己的 arXiv 框架论文**；"CrewAI: A Framework for Orchestrating Role-Playing AI Agents" 这个标题**无法证实，请勿引用**。最接近的真实可引物是官方文档 [docs.crewai.com](https://docs.crewai.com/) 与系统评述 CrewAI 的综述（[Derouiche et al., 2025](https://arxiv.org/abs/2508.10146)）。
   - **ChatEval 是 arXiv:2308.07201**，不是 2305.19118（后者是 Liang 等人的 MAD，EMNLP 2024 主会）。
   - **GPTSwarm 是 2402.16823**、**DyLAN 是 2310.02170**、**AgentPrune 是 2410.02506**——这三个 ID 常被写错。
   - **CrewAI 并未被 MAST 研究**；MAST 的 7 个框架是 ChatDev、MetaGPT、HyperAgent、AppWorld、AG2、Magentic-One、OpenManus。
   - **Meta 与 DeepSeek**：Meta 的 **Matrix（2511.21686）编号已二次核实为真**（标题 *Matrix: Peer-to-Peer Multi-Agent Synthetic Data Generation Framework*，MLSys 2026），Meta **没有 MetaGPT 级别的代表作**（MetaGPT 不是 Meta 的）；**DeepSeek 未检索到多智能体协调方向的论文**——这是检索性否定结论，不代表证明不存在。
   - 厂商文档站 `openai.github.io`、`developers.openai.com`、`github.com`、`*.github.io` 在本次环境中不可达（根因：本机 hosts 被加速器把域名指向 `127.0.0.1`）。**第二轮已通过 `ghproxy.net` 代理补齐 OpenAI 侧原文**（详见下方附录节）；**Google ADK 的 "sub-agents vs AgentTool" 官方逐字差别表述仍未取到**，ADK 文档已迁至 `adk.dev`，正文已按可确证部分改写。
