# 20 · 多智能体协作的"管理层与责任链"重设计草案

> **缘起**（用户逐字）："如果把 A 到 H 这些智能体比作项目组的底层员工，那还应该有管理层对这些
> 员工的行为、遇到的困难等真实情况进行监控，根据具体情况制定战略目标派发新一轮任务来实现
> 灵活调度。毕竟这些子智能体无法知晓全局。请先运用管理学等专业知识分析现状，制定草案，
> 明确应让谁对谁负责并受谁监督。分析现状、制定计划、派发任务、交叉审核、员工协作、
> 资源倾斜、状态更新等等都需要在多智能体协作中有所体现。"
>
> **本文件的性质**：**草案**，待裁决。它**不改任何代码**；§6.2 的变更账逐条标了"谁做"
> 与"是否落在 FC-27 禁 AI 区"。
>
> **本草案不是"给 M 再加一层"**。恰恰相反：它把现有骨架**重画**，并明确列出要
> **收回、收窄、删除**的东西（§0.3 与 §6.4）。这一节是为了防止"增量式设计"——
> 即只往上堆角色与表格，而不动那些已经错位的东西。

## §0 结论摘要

### 0.1 一句话

现状把**三个管理层级塌缩成了一层**（A–H 是作业层，M 是唯一入口，而 M 被规范钉死为
**零 LLM 的确定性执行者**）；草案把组织重画成 **四条线 × 三个层级**，其中管理层的
**参谋与内审是 LLM 角色、而"管理周期"本身是确定性驱动**——目标与计划由人批准，
执行由 M 按既有策略层机械约束，**执行者自动约束计划者**，不新增一个"全知的经理智能体"。

### 0.2 骨架对照

```text
v1（现状）                                    v2（草案）
                                            
      用户                                        用户（所有者 / 董事会）
       │                                             │   ▲
       ▼                                             │   └── 越级直报线（任何角色 → Q → 用户）
   ┌──────┐                                          ▼
   │  M   │ 确定性执行者（无 LLM）            ┌───────────────┐
   └──────┘                                  │  管理周期      │ 确定性驱动（无 LLM）
       │  ALLOWED_EDGES                     │  CycleRunner   │
       ▼                                     └───────────────┘
  A ──► B ──► C ────┐                              │  参谋线（只建议，不指挥）
  D ──► {A,B,C,E,F} │                          N 现状官 / O 计划官
  E ──► {B,D}       │  无边界的横向自发扩张         │  保证线（独立，直报用户）
  F ──► {A,B,C,D,E} │                          Q 内审
  G ──► {D,E,F}     │                              │  批准的 plan（唯一派发依据）
  H ──► {G}         ▼                              ▼
                 作业层 A–H                  ┌──────┐
                                            │  M   │ 确定性执行者（语义不变）
                                            └──────┘
                                                 │  策略层 = 对计划的第一道机械约束
                                                 ▼
                                            作业层 A–H（横向协作改为"请求-授权-派单"）
```

### 0.3 净变化账（这是本草案与"增量更新"的分界）

| 类别 | 内容 |

### 0.4 三个必须先回答的问题（详见 §10）

1. 管理层的**参谋**要不要是**独立角色**？（草案主张：要，理由是"1 名 reviewer 与自审在结构上不可区分"是**本项目已有的裁决**）
2. 先做 **P0 接线**（让台账真的被写），还是先做**影子模式**（在测试数据上算诊断但不行动）？
3. **谁批准计划**：用户逐周期批准，还是给 O 一个"预算内自主"的授权额度？

## §1 现状体检：七个功能逐项查

> 证据口径：`文件:符号`。本节所有"没有"都是**全仓 grep + 调用点核实**的结论，
> 不是印象。

### 1.1 一条最关键的实测（它决定整个设计的顺序）

| 事实 | 证据 |
|---|---|
| 写 `tasks` 表的唯一实现是 `Conductor` 自己 | `conductor.py:422/454/635/951` 四处 `store.tx("tasks", actor="conductor")` |
| `Conductor` 的**生产调用方 = 0** | 全仓 `from agentflow import conductor` 只出现在 `tests/test_conductor.py:31`、`tests/test_scheduler.py:44`；`cli.py` / `pipeline.py` 都不 import 它 |
| `run_plan` 的调用点全在 tests | `test_conductor.py:381/416/437/…`、`test_scheduler.py:288/316/…` |
| 后端只有 in-process 一条真路 | `LocalBackend.call`（`conductor.py:196`）走 `capabilities.find_action` 找 handler；`SubagentBackend.call` **恒抛** `NotWiredError`（`conductor.py:229-256`）⇒ 记 `refused/not_wired` |

**含义**：今天的"召唤台账、预算账、拒绝码、取消码、深度/扇出判据"是一套
**在测试里被完整验证、但在生产路径上没有被使用**的机制。任何"监控员工真实行为"的
管理层设计，**第一步都不是加监控，而是先让被监控的行为落进台账**。这不是风格问题，
是数据源问题。

## §2 管理学诊断（八个结构性缺陷）

> 每条给：管理学概念（带出处）→ 代码证据 → 后果 → 同类组织怎么解。
> 出处见附录 A；经典文献我只标作者与年份，**未逐字核实原文**（诚实标注）。

| # | 缺陷 | 管理学概念 | 代码证据 | 后果 |
|---|---|---|---|---|
| **D1** | **三个控制层级塌成一层** | Anthony 三分层：战略规划 / 管理控制 / 作业控制 | 作业层 A–H 齐备；"管理控制"（目标分解、绩效测量、资源再分配）**没有任何落点**；M 是作业调度而非管理 | 只能回答"这一步跑完没有"，回答不了"我们离目标还差多少、资源该往哪挪" |
| **D2** | **自评自报，且无第二/第三道防线** | IIA 三道防线；Jensen & Meckling 代理成本（信息不对称 ⇒ 监督成本） | 现状统计（`stats()`）由 M 自己算；报告与台账可能分家（D8）；唯一的审校 H **受 M 调度**（`ALLOWED_EDGES["H"]={G}`，H 只能被 G 召唤） | 出了偏差时，"谁来判断"这件事本身是空的：作者即报告者即（间接）审核者 |
| **D3** | **统一指挥被无边界横向扩张破坏** | Fayol 统一指挥；矩阵组织的双重指挥代价 | `ALLOWED_EDGES` 允许 D→{A,B,C,E,F}、F→{A,B,C,D,E}、G→{D,E,F}；限制只有 depth/fanout/总量，**没有"是否符合当前目标"** | 任务可以因为"某个角色觉得需要"而产生，责任漂移到"没人负责的中间态"；资源被无计划地消耗 |
| **D4** | **管理幅度与信息过载；M 既是瓶颈又是单点** | Graicunas 幅度公式；Urwick 的 5–6 人建议；Galbraith 信息处理观 | M 直接面对 8 个作业角色的全部状态；横向交叉关系存在（8 个角色之间有 16 条边）；**没有任何组织化的信息压缩**（诊断/摘要都没有角色） | M 的"状态"只能是一堆原始行；想让 M"看全局"就得让它读 8 个角色的原始输出 —— 这正是用户说的"子智能体无法知晓全局"的另一面 |
| **D5** | **没有例外管理阈值：困难只在"失败"之后才可见** | Taylor 的例外原则（管理只看偏离）；管理例外（MBE） | 执行层可观测的终态只有 `failed`（崩了）与 `refused`（**框架**拒绝，不是子体申请）；`blocked` 只在 F 内部 | 卡点无法及时上升；等 M/用户看见时，已经烧掉了预算 |
| **D6** | **没有冗余、没有再分配** | Cyert & March 组织冗余（slack）；Galbraith 把冗余当作不确定性吸收器 | 预算静态、默认 None（守卫不生效）；`by_role()`/`retry_overhead()` 无调用方；无任何"从低产出挪到高产出"的代码 | 遇到有价值的卡点时没有可调度的余量；反过来，低价值分支会一直烧钱到全局上限 |
| **D7** | **责任与绩效无记录：回答不了"谁对什么负责"** | 责任会计（responsibility accounting）；RACI 的"唯一 A（Accountable）"原则 | `tasks` 有 `called_by`/`role`/`parent_task_id`，**没有 supervisor/owner/目标**字段；`schema.py` 里最接近的是 `subgoals[].owner`；12 张表里没有任何一张记录"目标、责任人、监督者、结论" | 用户的问题"应让谁对谁负责并受谁监督"今天在数据模型里**无处存放** |
| **D8** | **状态更新没有单一来源，且缺"没查成"档位** | 控制回路的基本要求：反馈信号必须唯一且可信；本项目自己的 FC-03 与 P4 | `stats()` 的 `reconcile` 用 `tasks` 求和而权威账是 `usage_ledger`（`conductor.py:1139-1142` vs `:305-308`）；tasks 健康判据两份实现（`capabilities.audit_task_ledger` vs `verify.py:653-716`） | 两处口径有一天会分家，而**没有任何一条判据会因此变红**（这正是 P4 的形态） |
| **D9** | **绩效口径里没有"如实上报困难"的位置（心理安全没有制度化）** | Deming 第 8 条"驱除恐惧"；Edmondson 心理安全与团队学习 | `outcome="refused"` 被正确地当成**成功执行**（`ROLE-SPECS.md` 纪律 5），但它**不进任何绩效视图**；`blocked_reason` 只在 F 内部；没有任何地方统计"未上报的失败" | 只要绩效口径隐含惩罚"报告困难"，角色就会隐藏困难 —— 这是控制系统最经典的失稳路径，而且它**必然**表现为"报告一切正常、最后一起爆" |

## §3 目标组织 v2

### 3.1 四条线

| 线 | 走什么 | 谁 | 是否可指挥 |
|---|---|---|---|
| **指挥线（实线）** | 已批准的 plan → 派单 → 作业 | 用户 → 管理周期 → M → A–H | 只有 M 能召唤（`NON_SUMMONABLE` 语义**加强**：M 仍是唯一召唤入口） |
| **参谋线（虚线）** | 现状 → 计划 → 批准 | N、O → 管理周期 → 用户 | **无指挥权**（参谋不派单；这是 line/staff 原则，也是防"两个老板"） |
| **保证线（虚线，直报）** | 审计结论 | Q → 用户（不经 M） | 无指挥权，但有**要求整改**权：只能登记，不能改业务数据 |
| **越级线** | 任何角色 → Q → 用户 | A–H、M、N、O 都能发起 | 用于"我的困难/异议没有被上面处理"（申诉通道） |

### 3.2 十二个职位

| 职位 | 一句话职责 | 决定权 | 是 LLM 吗 |
|---|---|---|---|
| **用户（所有者）** | 定目标意图、批计划、裁例外、终审 | 决定 | 人 |
| **管理周期 `CycleRunner`** | 按确定性脚本跑控制回路：读现状 → 算阈值 → 调 N/O → 收批准 → 交 M 派发 → 收 Q 结论 → 写管理台账 | 只执行，不决定 | **否（确定性）** |
| **N 现状官** | 把作业层与执行层的**事实**聚合成诊断（含"没查成"档位与数据来源） | 无 | 是（只读） |
| **O 计划官** | 基于诊断产出目标+任务草案+资源方案+风险与否决项 | 建议 | 是（只读业务表，写计划草案） |
| **Q 内审** | 程序面审核：越权、判据真空、自审、报告与台账不一致、阈值被绕过 | 登记 + 要求整改 | 是（只读） |
| **M 主控** | **唯一召唤入口**；过策略层；写台账；拒绝越界计划 | 执行期拒绝 | 否（确定性，语义不变） |
| **A–H 作业层** | 各自的领域工作；**如实上报困难**；对产出负责 | 各自领域内 | 是 |

### 3.3 为什么参谋必须是**独立角色**（这一条不是我拍的，是本项目已有的论证）

`AGENTS.md` 关于 FC-27 的逐字理由：

> "为什么是 2 而不是 1：1 名 reviewer 与'作者自己再看一遍'在**结构上**无法区分；
> 2 名才有互相独立的复核。"

同一条逻辑直接适用于管理层：**"让 M 顺便做一下现状分析"与"没有现状分析"在结构上
无法区分** —— 因为 M 的自评与 M 的执行共用同一个上下文、同一个目标函数、同一份立场。
所以 N/O/Q 必须是**结构上不同**的角色（不同工具面、不同权限、不同的"能写什么"），
而不是"M 的一个新动作"。

## §4 权责与监督矩阵

### 4.1 决策权矩阵（RAPID 混合 RACI）

> **R**=建议（Recommend）｜**A**=同意（Agree，可否决）｜**P**=执行（Perform）｜
> **I**=输入（Input）｜**D**=决定（Decide）。**每一行有且只有一个 D**。

| 决策 | 用户 | CycleRunner | N | O | Q | M | A–H |
|---|---|---|---|---|---|---|---|
| 目标意图（要解决什么） | **D** | I | I | R | I | — | I |
| 现状诊断口径（看哪些指标） | A | P | **D** | I | A | I | I |
| 本轮目标与任务草案 | **D** | P | I | **R** | A | I | I |
| 计划可行性（越界与否） | I | I | — | R | — | **D**（执行期拒绝） | I |
| 资源倾斜方案 | A | P | I | **R** | A | I | I |
| 预算上限（硬顶） | **D** | P | — | R | A | I | — |
| 派单（谁、何时、多少次） | I | P | — | R | — | **D** | I |
| 作业层产出 | I | — | I | — | A | I | **D**（本领域） |
| 横向协作请求是否成立 | I | I | — | **R** | — | **D** | R |
| 审核（内容质量） | I | — | I | — | A | — | **H 的 D** |
| 审核（程序合规） | I | I | I | I | **D** | I | I |
| 例外升级的处置 | **D** | P | R | R | I | R | R |
| 结项（这一轮算不算完成） | **D** | P | R | R | **A**（可否决） | I | I |

### 4.2 监督矩阵（谁监督谁、用什么判据、谁能越级）

| 被监督者 | 监督者（判据） | 越级对象 |
|---|---|---|
| A–H | H（内容：`review_findings`，证据必填）＋ N（事实：产出是否与台账一致）＋ Q（程序：权限面/判据） | Q → 用户 |
| M | Q（台账不变式 I-1…I-10、拒绝码受控、是否越权）＋ N（`stats()` 与权威账是否一致） | Q → 用户 |
| N（诊断） | Q 抽样**重算**（诊断里每个数字必须能由其声明的 source 重算出来） | 用户 |
| O（计划） | Q（引用完整性 + 目标可否判定 + 否决项）＋ **M 的策略层**（越界即拒，见 §5.3）＋ 用户（批准） | Q → 用户 |
| Q（审计） | 用户（唯一）＋ "无 findings 必须自证查过什么"＋ 用户可要求把 Q 的结论交给**机械判据**重算（`verify_all` / `audit_task_ledger`） | — |
| 管理周期 | Q（是否跳过诊断、是否绕过阈值、是否把 `unknown` 当通过） | Q → 用户 |

三条硬规则：

1. **无人可自审**：审核矩阵的对角元必须为空。落地判据：`audits.auditor_role != producer_role`，
   且 `verdict="pass"` 至少需要 **2 个独立角色的同意**（直接复用 FC-27 的"2 名"论证）。
2. **任何角色的困难与异议都有直达通道**：`escalations.raised_by` 允许任何角色，
   `to ∈ {用户, Q}`；**中游记不得过滤**（落地判据：`escalations` 行的 `raised_by` 与
   `handled_by` 不得为同一角色；`handled` 必须有结论）。
3. **`unknown` 不许当通过**：Q 与 N 的结论都必须是三态；"没查成"必须显式落表。

### 4.3 三道防线的落地

| 防线 | 谁 | 管什么 | 今天的落点（有/无） |
|---|---|---|---|
| 第一道（作业线自控） | A–H | 自己的产出质量、如实上报困难 | **有**：`review_findings`（H）、`SubGoal.blocked_reason`（仅 F）、`refused` 语义 |
| 第二道（管理与监督） | N（事实）、O（计划）、CycleRunner（阈值） | 现状、计划、资源、例外 | **无**（本草案新增） |
| 第三道（独立内审） | Q | 程序与合规：越权、判据真空、自审、报告与台账不一致 | **无**（本草案新增；今天的 H 受 M 调度，不构成独立） |

## §5 七个功能 → 机制与判据

> 每项：谁做 ｜ 输入（权威来源）｜ 产出 ｜ **可判定判据** ｜ fail-closed ｜ 负控。
> "可判定"的标准与 `DEVELOPMENT.md` §4.6 一致：一句话能答"是/否"。

### 5.1 分析现状（N）

- **输入（权威来源，不许另算）**：`tasks`（`Conductor.stats/tree`）、`usage_ledger`（`TokenMeter.spent/tokens_for/by_role/retry_overhead`）、`eval_results`、`verify_all` 的 Issue、执行层受控码（`REFUSAL_REASONS`/`CANCEL_CODES`）、`SubGoal.blocked_reason`、以及 §6.1 新加的 `tasks.progress_state`。
- **产出**：`diagnoses` 行 —— `metrics: {key: {value, source, coverage}}` + `anomalies[]` + `unknowns[]`。
- **可判定判据**：
  1. 每个指标必须带 `source`（`表.字段` 或 `模块.函数`）且 `coverage ∈ {complete, partial, unavailable}`；
  2. **引用完整性**：诊断里的每个数字都能由声明的 `source` 重算出来（Q 抽样重算，≥1 项/次）；
  3. **`coverage="unavailable"` 的指标不许省略**（省略就让"没查成"变成了"没问题"）。
- **fail-closed**：`tasks` 读不到或 `usage_ledger` 读不到 ⇒ `coverage="unavailable"` + 一条 `unknowns`；
  **不许**返回空诊断（空集会被读成"一切正常"）。
- **负控**：构造一个"台账里有 refused 但诊断没报"的样本 ⇒ 判据必须红。

### 5.2 制定计划（O）

- **输入**：一条**已落表**的 `diagnosis`（`diagnosis_id`），不读原始表（防止 O 自己重算，绕过 N）。
- **产出**：`mgmt_plans` 行 —— `objectives[]`（每条：`text` + `criterion` 可判定 + `falsifier` 否决项）、`tasks[]`（角色、动作、参数、预算、依赖提示）、`allocation`（见 §5.6）、`risks[]`。
- **可判定判据**：
  1. **引用完整性**：`plan` 里出现的每个数字都必须带 `metric_ref`，且 `metric_ref ⊆ diagnosis.metrics.keys()`
     —— 这一条**机械可查**，专门防"计划里编造现状"；
  2. 每个目标必须有 `criterion` 与 `falsifier` 各一条（复用本项目 FC-26 的形态：结论必须可核实 + 有否决项）；
  3. `plan` 不解释"为什么做"以外的任何执行细节（不许包含越权动作）。
- **fail-closed**：诊断缺 `coverage="complete"` 的关键指标 ⇒ 计划只能标 `provisional=true`
  且必须列 `unknowns` 对应的**探测任务**（先取证，再动手）。
- **负控**：把 `metric_ref` 指向一个不存在的 key ⇒ 判据必须红。

### 5.3 派发任务（CycleRunner + M）

- **链路（复用现成的）**：`CycleRunner` 把已批准的 plan 编译成 `TaskCall` 序列 → `Conductor.run_plan` → `run_waves`(写集相交分波) → `summon`(策略层九步判定) → backend。
- **结构性约束（本设计最省力的一环）**：**M 的策略层就是对 O 的第一道机械约束**。
  O 想派一个超深度/超扇出/超并发/超预算/成环/走禁止边的计划 —— `policy.check` 直接拒绝
  （`policy.py:223-332`）。**执行者自动约束计划者，不需要人为"监督"这个动作。**
- **可判定判据**：
  1. 每个 `tasks` 行必须带 `mgmt_plan_id`；`mgmt_plan_id` 为空的任务只允许 `called_by="user"`（用户直接指令）；  2. 派单顺序必须与 plan 的 `tasks[]` 顺序一致（今天 `waves_of` 保输入顺序，`policy.py:365-395`）；
  3. 被拒绝的派单必须落 `refused` + 受控 `refusal_reason`（`conductor.py:466-522`，已有）。
- **今天缺的**：优先级、依赖、抢占、重排（§1.2）。**本草案刻意不引入自动抢占**：
  抢占需要"谁的价值更高"的判断，那正是最容易出错的地方；先用"下一周期重排 + 预算回收"实现灵活性。

### 5.4 交叉审核（H + Q + 对偶审核）

- **三层**：
  1. **对偶审核**（作业线内）：产出者不能是自己的审核者。今天只有 `G → H`；
     草案要求 `D/E/F` 的**对外产出**（报告、实验登记、攻坚结论）也必须有一条对偶审核记录。
  2. **程序内审**（Q）：越权、判据真空（P16）、自审、报告与台账不一致、阈值被绕过。
  3. **机械复核**（`verify_all`）：能机械判的**永远优先交给机械判据**；Q 不重复实现判据，
     只**引用**（FC-03：判据只有一处实现）。
- **可判定判据**：
  1. `audits` 行必须有 `subject`（指向 doc/plan/diagnosis/task）、`criterion_id`、三态 `verdict`、
     `evidence`（非空，理由同 `review_findings.evidence` 的既有规定）；
  2. **`auditor_role != producer_role`**，且 `pass` 需 ≥2 名独立角色同意；
  3. **抽样必须自证**：`audits.sampled`（抽了几条）与 `sampled_of`（总体）必填；
     抽样率为 0 时必须显式写 `no_sample` 并给出理由（否则"没抽"会变成"通过"）。
- **fail-closed**：Q 长期只能给 `unknown` ⇒ 升级给用户（不许沉默地一直 unknown）。
- **负控**：构造"auditor = producer"的行 ⇒ 判据必须红；构造"抽样率为 0 但 verdict=pass" ⇒ 必须红。

### 5.5 员工协作（请求-授权-派单）

- **保留**：`ALLOWED_EDGES` 的横向能力（D↔F、F↔E、G→H…）是本项目最有价值的设计之一，
  **不删**。改变的是它的**性质**：
  - **在已批准计划范围内**的横向召唤：直接走 M 派单（今天的机制不变）；
  - **计划范围外**的横向召唤：产出一行 `requests`（谁、向谁、要什么、为什么、预估成本），
    由 O 在下一周期纳入计划草案，或由 M 按例外规则即时批准（小额度、可自动）。
- **可判定判据**：
  1. 计划外的横向召唤必须能追溯到一行 `requests`；
  2. 计划外横向召唤消耗的资源必须计入"例外额度"，超出即拒绝（复用 `Policy` 与每任务 `budget`）；
  3. `requests` 的受理必须有结论（`admitted` / `deferred` / `refused` + 理由），**不许悬空**。
- **为什么这样改**：今天的横向扩张只受"深度/扇出/总量"约束，**不受目标约束**；
  而"这件事要不要做"恰恰是管理层唯一无法外包给作业层的判断（D3）。

### 5.6 资源倾斜（O 出方案、CycleRunner 生效、M/TokenMeter 硬顶）

- **可倾斜的四个维度与实际落点**：

| 维度 | 今天能不能倾斜 | 落点 |
|---|---|---|
| 每任务 token/usd 额度 | **能**（现成） | `TaskCall.budget`（`scheduler.py:68`）→ `_meter_guard`（`conductor.py:525-557`） |
| 派发顺序 / 波次 | **能**（现成） | plan 的 `tasks[]` 顺序 + 写集分波（`policy.waves_of`） |
| 分支级并发配额 | **不能** | 需给 `run_waves` 增加"按波指定上限"（落点 `conductor.py`/`scheduler.py`，**非禁改区**） |
| 全局预算硬顶 | **能，但默认关闭** | `Policy.token_budget/usd_budget`（默认 `None` ⇒ 守卫不生效，`tokenmeter.py:282-293`）——**这是倾斜的前提：没有硬顶就没有"倾斜"，只有"不限制"** |

- **规则（全部可判定）**：
  1. `Σ shares ≤ pool - reserve`，`reserve` 必须 ≥ 10%（Galbraith 的冗余作为不确定性吸收器）；
  2. 每一项 share 必须带 `basis_metric_ref`（指向 diagnosis 的指标）——**禁止**
     "因为某个角色看起来更重要"这类无依据倾斜；
  3. 每项 share 带 `lease_cycles`，到期**自动回收**到公共池（防永久霸占）；
  4. **明确禁止**作为倾斜依据：提交者身份、任务新旧、"上一轮它是谁做的"；
  5. 倾斜方案必须由用户批准（或落在用户授予的自主额度内）。
- **默认关闭 + 影子模式**：`allocation` 先只计算不生效，记录"如果生效会怎么分"，
  跑够样本量后再开 —— 这是本项目 P15（告警噪音化）与 R009 校准纪律的直接应用：
  **没有量过触发率与假阳性的阈值，不许上线**。

### 5.7 状态更新（单一来源 + 三态 + 事件驱动）

- **单一来源**：所有数字都必须来自**既有权威函数**之一：`Conductor.stats/tree`（执行视图）、
  `Store.stats`（领域视图）、`verify_all`（完整性视图）、`TokenMeter.*`（账）、
  `audit_task_ledger`（tasks 健康，唯一实现）。
  **禁止**任何新代码再写第三份计数（P4）。
- **产出**：
  - 机器面：`diagnoses` / `audits` 行（JSON）；
  - 人读面：由这两者渲染的**周期报告**（谁在什么时候看什么，见 §7.3）；
  - **困难面**：`escalations` 行（见 §5.1 与 §6.1 的 `progress_state`）。
- **可判定判据**：
  1. 报告里的每个数字带来源（同 §5.1 判据 1/2）；
  2. 报告必须包含 `unknowns` 段（没有 unknowns 也要显式写"本次无未知项"，自证）；
  3. **频次**：只在周期边界与例外触发时更新（不许每步都报 —— P15）。
- **fail-closed**：任一路径读不到 ⇒ 报 `partial` 并列出缺哪一部分，**不许**给一个"看起来完整"的报告。

## §7 控制回路与阈值

### 7.1 管理周期状态机（MAPE-K 的落地）

> MAPE-K（Monitor–Analyze–Plan–Execute over shared Knowledge，Kephart & Chess）与
> "分析现状 / 制定计划 / 派发任务 / 状态更新"是同一件事的两种说法；本项目把它落成
> **一个确定性状态机**，每个状态有一个唯一的产出物与一条可判定判据。

```text
触发（周期边界 / 例外阈值 / 用户指令）
   │
   ├─[1] MONITOR  N 读权威来源 ──────────────► diagnoses（coverage 三态）
   ├─[2] ANALYZE  N 算阈值/异常 ─────────────► anomalies[] + unknowns[]
   ├─[3] PLAN     O 出目标+任务+资源 ────────► mgmt_plans（provisional? + falsifier）
   ├─[4] APPROVE  用户（或自主额度内自动） ──► mgmt_plans.status = approved（谁批、何时）
   ├─[5] EXECUTE  CycleRunner 编译 TaskCall → M.run_plan（策略层可拒）
   ├─[6] AUDIT    Q 程序审核 + verify 机械复核 ─► audits（三态 + 抽样自证）
   ├─[7] REPORT   N+Q 合成周期报告（含 unknowns 段）
   └─[8] CLOSE / REPLAN  结项需要用户 D + Q 的 A（可否决）
```

**幂等与重入**（这条不写清就会出"重复派单"事故）：
每个周期在 `[5]` 之前必须写下 `cycle_id`，且派单以 `(cycle_id, mgmt_plan_id, task_key)` 为唯一键；
重复执行同一周期必须**只**产生一次派单（负控：把周期跑两遍，断言 `tasks` 行数不变）。

### 7.2 例外触发词表（受控、带阈值、每个绑定一个负责人与动作）

| 触发码 | 阈值（草案初值，**必须先影子模式校准**） | 负责处置者 | 动作 |
|---|---|---|---|
| `no_progress` | 同一子目标连续 ≥3 轮无状态变化（复用 F 已有的 `stall_after_no_progress_rounds=3`，`agent_f.py:505`） | O | 换策略或降级为"记录卡点" |
| `repeat_failure` | 同一任务失败 ≥2 次 | O + M | 停止重派，转入诊断 |
| `budget_pressure` | 已花 ≥80% 且目标未达成 | O | 重排优先级 / 动用 reserve |
| `refusal_cluster` | 同一 `refusal_reason` ≥3 次 | N + Q | 上升为程序问题（可能是策略层配置错） |
| `unreported_failure` | 出现 `failure_without_reported_difficulty` | Q | 要求该角色补报（**不改它的绩效**） |
| `evidence_gap` | `proof` 级结论数 > 已闭合依赖数 | Q | 阻断"结项"（依赖未闭合不许说完成） |
| `unknown_streak` | 连续 2 个周期有 `coverage="unavailable"` | Q | 直报用户（内审停摆信号） |

**纪律**：① 阈值是**受控常量**（一处定义，不许散落）；② 每个触发码在影子模式下的
**触发率与假阳性率必须实测**，否则不许上线（P15）；③ 触发词表不许被"降级成 info"来消音。

### 7.3 状态更新的**频次**纪律

- 周期边界：一份完整诊断 + 一份审计结论；
- 例外触发：一条 `escalations` 行（只写差异，不重发全量）;
- **禁止**：每步都更新（P15 噪音化）；把"没有变化"写成一份报告（那会让"没有变化"和"没跑"难以区分）。

### 12.1 Q5 的评审修正（草案原本的建议方向不对）

草案 §10 原本建议"先 2 张表，理由是先证明诊断有用"。评审把两个成本分开算之后改判：

- **禁改区的人工成本是按批次付的**：改 `schema.py:TABLES`/`ROLES` 一次要人编写或逐行走查
  + **2 名 reviewer**；分两批登记 = **两次**这样的成本，不是一次。
- **schema 的不可逆性是按"已登记的表 + 已有数据"算的**：四张新表现在**一张都没有数据**，
  此刻改字段最便宜；一旦 P2 上线、`diagnoses` 里有了真实数据，再改字段就变成真正的迁移。
- 正解：**字段一次设计完（四张表全设计），登记按阶段分两批**。把"设计一次做完"与
  "登记分阶段"分开 —— 而不是像草案原来那样把设计也切两半。

## §14 角色工具箱：让每一次思考都花在真问题上

> **缘起**（用户逐字）："还有要给每个角色搭建全套工具箱，尽可能让他们的每一次思考都是在想真问题，
> 而非消耗在无聊的数据处理、信息查询上。把这些设计加入草案。"
>
> **细节层**：`../agentflow/docs/TOOLBOX-DRAFT-roles.md`（12 角色工具箱表 + 15 个新工具六件套 +
> 判据 + 反模式 + 风险）。本节只写**设计判断**与**它与前面各节的关系**，不重复那份表（FC-03）。

### 14.1 实测诊断：工具箱是"原料级"的，不是"任务级"的

口径 `build_for_role(role)`（不带 deps），脚本 `../temp/_tool_census.py`：

```
角色  工具数  取数  成型  本职  未分类   机械占比    思考单元
A       13     5     0     0     7      38%     检索策略与结果取舍
B       11     7     0     0     4      64%     整理期的语义决定
C       13    13     0     0     0     100%     结构分析
D       25    17     4     1     3      84%     研究判断
E       14     9     1     0     4      71%     数值实验与形式化设计
F       25    13     5     3     4      72%     攻坚
G       25    13     5     1     6      72%     撰写
H       19    13     5     1     0      95%     审校
M        0     0     0     0     0       0%     调度（不推理）
```

四条从数字里读出来的事实：

1. **同一批原料被反复发给不同角色**：`table.*` 出现在 6 个角色、`verify.*` 4 个、`attack.*` 4 个、`doc.*` 4 个；
2. **工作台最大的角色最远离本职**：D/F/G 各 25 个工具，机械占比 72–84%；
3. **H 的 19 个工具里 18 个是原料/成型**，属于"审校判断"的只有 `review.scan_document` 与 `doc.scan_claim`；
4. **C 的工具面 100% 是取数**，没有任何"结构解释"的产出工具。

### 14.2 设计：一层聚合 + 两个上限 + 一条默认路径

| 概念 | 内容 |
|---|---|
| **任务级聚合工具** | 一次调用 = 一个有意义的单位，且**返回即可推理**（带 provenance 的三态结构）。共 **15 个**（`brief.*` / `pack.*` / `queue.*` / 各角色本职的端到端工具） |
| **默认路径** | 聚合工具 + 该角色的本职判断工具；**≤ 12 个/角色**（实测设计后：A3 B3 C2 D4 E3 F3 G4 H3 N5 O4 Q4） |
| **下钻** | 原料工具**不删**，只在聚合结果标出"需下钻"时使用；下钻调用计入 `plumbing_ratio` |
| **两个上限** | 默认路径 ≤ 12；一个周期内 0 次调用的工具要么删、要么写清"何种情形用"（`unused_tool`） |

**为什么不是"把原料工具删掉"**：删了会丢能力（D 有时确实需要按 id 下钻），而"留但降级"能同时满足能力与预算 ——
这是 §2-D4（管理幅度）在同一条设计上的第二次应用：**默认路径窄、下钻深**，而不是"什么都摆在桌面上"。

### 14.3 六条判据（把"思考占比"变成可测的东西）

| # | code | 判据 | 数据来源 | 初值阈值（**影子模式校准**） |
|---|---|---|---|---|
| 1 | `plumbing_ratio` | 某角色下钻调用 / 总调用 | `tasks.action` + 默认路径声明 | ≤ 15% |
| 2 | `wasted_call_ratio` | `ok=False` 或空返回且无原因 / 总调用 | `tasks.outcome` + 工具返回 `meta.kind` | ≤ 10% |
| 3 | `unused_tool` | 周期内 0 次调用且规格里没写使用情形 | `tasks.action` | > 0 即 info |
| 4 | `toolbox_span` | 默认路径工具数 | 细节层 §3 的块（登记后由 `ToolSpec.roles` 取代） | ≤ 12 |
| 5 | `fc06_expected_tools` | 每角色**预期工具名清单**与实装逐项一致 | 细节层 §3 的 `default:` 列 + `cli tools` 普查 | 差异即报 |
| 6 | `empty_result_without_reason` | 空结果且无"为什么空" | 工具返回契约（三态纪律） | 一次即报 |

> **码 5 直接补上 FC-06 的缺口** —— `DEVELOPMENT.md` §9.2 记的"缺每角色的预期工具名清单"，
> 其草案形态**就是**细节层 §3 的 `default:` 列。这不是新增义务，而是把一份已经存在于设计里的
> 清单变成可对账的判据。

### 14.4 拟登记的反模式（`DEVELOPMENT.md` §6 → **P18**，需人审）

> **P18：让模型自己做机械劳动** —— 自己算术、自己拼上下文、自己转换格式、自己多轮试探找 id。

四类形态、四类替代、四条判据（详见细节层 §5）。它与既有的 **P16**（判据真空通过）同族：
P16 是"判据没执行"，P18 是"模型的思考没用在判断上" —— 共同后果都是
**报告看起来正常，而真正该发生的事没有发生**。
