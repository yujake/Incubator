## §0 成本序（逐字）与判读规则

| 位 | 成本（越靠前越不可接受） |
|---|---|
| **#1** | 智能体协作**无法推进数学研究** |
| **#2** | 智能体协作**对每种类型的任务预先设计了不同处理链条与产出格式** |
| **#3** | **产出无效内容或不符合数学研究特征** |
| **#4** | 会**干扰智能体正常行为**或给它**增加与定位相关度低的繁杂任务** |
| **#5** | 需要**设计更多新角色**或需要**维护新文件** |
| **#6** | **设计不合理或易留下后患** |

| **#9** | 需要**动禁改区** |

### 判读规则（lexicographic）

1. 一个方案的成本 = 它触发的**最靠前**的那一位。**比较两个方案时，谁的"最靠前位"更靠后，谁更可接受**
   （例如：只触发 #9 的方案优于触发 #6 的方案，即使前者要改 500 行、后者改 5 行）。
2. 最靠前位相同时，比第二位，依此类推。
3. 完全同级时，比**可逆性**（能整批回滚的优先）。

### 由这条规则直接推出的三个反直觉结论（也是本文件与 `draft/49` 分歧的根源）

- **A. 禁改区与代码量几乎是免费的。** `draft/49` 里我多次因为"要动 `schema.py`/`verify.py`"或"要改 80–150 行"
  而退回更小的方案 —— 按这条序，那是**错的取舍**：只要它不引入 #1…#6 里的任何一位，就该做。
- **B. "少建文件"比"留下设计缺陷"更重要。** #5 排在 #6 之前 ⇒ 为了接手/退场而新建模块、新角色、
  新脚本，**比"暂时不删、留着不动"更不可接受**。这条直接改写了 F14（14 条接手人）与 A10（秘书）的答案。
- **C. "给智能体加活儿"是 #4，比"改代码/动禁改区"严重得多。** 任何"让模型多做一次纠正、多填一个字段、
  多轮一次队列"的设计，都要先证明它**服务研究推进**，否则宁可不做。

### 三条口径假设（我按这个读你的序；若你另有读法，下面的结论要按新读法重算）

1. **#1 包含"机制存在但没接线/已死"**：我认为"协作无法推进研究"最典型的形态不是"智能体不会做数学"，
   而是"该干活的机制没有生产调用者、或门把没接线的东西标成绿"（`F7 L-13` 那族）。
2. **#2 覆盖任何"按动作/类型预设链条或产出格式"**：新增 kind 词表、按动作类型的落盘格式、
   "每个任务类型一套字段/段落"，都算 #2。**框架自身的发布门/运维脚本不算**（但 `E-06 九节` 与
   `F-06 生成式验收表` 处在灰区，见 §6）。
3. **#5 只数"项目要长期维护的新文件/新角色"**（模块、脚本、新角色），不数新增测试、也不数运行时产物。
