# draft/53 「秘书」定位（v3：每个智能体各有一名秘书）

> 依据：你 2026-10-06 的裁定 ——
> ① 四条职责（格式与内容优化 / 委派评估 / 闭环提醒 / 委托加工）；
> ② **"秘书是每个智能体都有的，可先建好一个秘书，再批量造其它智能体的秘书"**；
> ③ 此前的两条口径（"纪律尽量交给自动化工具，自动化不了就配秘书"；"切勿全写死成机器判据"）。
>
> **v1（我自拟五条职责）与 v2（单一秘书 / 新角色 S）都已作废**，以本版为准。

---

## §0 一句话定位

**秘书是每个智能体自带的随员**：它替这个智能体处理"委托"这件事 ——
**发出去的**委托由它加工到"能通过硬性要求、且对得上收件方角色"；
**收进来的**委托由它评估并改写成"贴本角色定位"的版本；并且盯住**每一条委托都要有处理、有反馈**。

它是**智能体的组成部分，不是同级角色**：不占 `ROLES`、不新增工具、不改权限面。

```
                     ┌─────────── 智能体 A ───────────┐
   发件  ──►  A 的秘书（职责 1、2）  ──►  发出
                     └────────────────────────────────┘
                                    │  （秘书对秘书协商）
                                    ▼
                     ┌─────────── 智能体 B ───────────┐
   收件  ──►  B 的秘书（职责 4、3）  ──►  B 本体
                     └────────────────────────────────┘
```

## §1 为什么是"每个智能体都有"，而不是一个全局秘书

| 职责 | 需要"知道谁" | 只有本角色的秘书才做得到的原因 |
|---|---|---|
| 1 格式与内容优化 | 硬性要求（参数表、工具名、验收列） | 与角色无关，但**要在发件那一刻做**，才来得及 |
| 2 委派评估（对方真做得到吗） | 收件方的角色定位 | 发件方的秘书**在发之前**就要判；等对方收到再拒就晚了 |
| 3 闭环提醒 | 自己的收件箱 | 谁收到谁盯 —— 全局秘书得轮询所有角色的收件箱 |
| 4 委托加工（改成贴本角色定位） | **自己的**角色定位 | 只有本角色的秘书最清楚"我这条线上要什么、我能交什么" |

一个全局秘书要做这四件事，就得反复查所有角色的定位、还要替每个角色说话 ——
既贵又容易越权。**每个智能体一名**，四件事都落在"最知道情况的那一方"手里。

## §2 四条职责在"发件侧 / 收件侧"的落位

| # | 职责 | 谁的秘书做 | 做什么 | 不许做 |
|---|---|---|---|---|
| 1 | **格式与内容优化** | **发件方**的秘书 | 对齐硬性要求：动作参数、必填字段、**工具名真名**、引用与编号格式、验收列名 | 不改变实质主张（不替它承诺、不改结论、不加证据） |
| 2 | **委派评估** | **发件方**的秘书 | 判"收件方**真能做到**吗、**该不该派**（重复/已有人在做/空转）"；错位 ⇒ 建议重排 | 不擅自改派（改派权在 M） |
| 3 | **闭环提醒** | **收件方**的秘书 | 盯自己的收件箱：未接手 / 未反馈 / 反馈了对方没看到 ⇒ 提醒（经 M） | 不替本体做事、不伪造反馈 |
| 4 | **委托加工** | **收件方**的秘书 | 按**本角色定位**把收到的委托改成贴切版本：补上下文、明确产出物与验收口径、把模糊要求变具体 | 不加码不减码（只改"怎么说"，不改"要什么"） |

**两条"实质性"红线**：格式补不全、或加工后发现**实质缺陷**（错的对象/缺前提/结论与证据不符）
⇒ **与对方协商，不静默修**（静默修复是本框架最忌讳的形态）。

### 2.1 它另外持有的：**手稿通道的增 / 改 / 查**

> 用户口径（2026-10-06）："如果秘书啥工具都没有，它怎么知道一条指令是不是重复委派？**至少要能读 handoffs**，
> 且由于**所有信息交互都由秘书过一遍手**，所以 **handoffs 的增改查能力都该给秘书，智能体只保留'查'的能力**。"

| 能力 | 实现 | 说明 |
|---|---|---|
| **增** | **既有** `manuscripts.write(...)`（今天由 `agent_loop._do_handoff` 调，`:1673`/`:1708`） | 秘书**执笔**本体的交接/派活；行里的 `sender` 仍是**被服务的角色** |
| **改** | **待新增** `manuscripts.revise(...)`（`manuscripts.py` 今天没有 `update/revise`） | **追加修订行、不改旧行**（保持 append-only、可追溯） |
| **查** | **既有** `manuscripts.read/list_all/query/rows/row_of/rows_for_task/read_index/ref_problem` | 判重复、判"是不是已经交接过"、查引用链、找前置手稿号 |

**智能体只保留"查"**：循环形状 `handoff` 的**写路径关闭**（形状保留 —— 本体依旧"说我要交接什么"，
但**执笔改由它的秘书**）；工具面上的 `manuscripts.read` / `manuscripts.list` **保留**。

### 2.2 它读的"组织图"是**全角色**的

**每名秘书都可读所有智能体的角色定位与能力面**（`ROLE_BRIEFS[<任意角色>]` + `specs/<任意角色>.py` +
`capabilities` 的写集/边 + `tools.build_registry()` 的角色归属）—— 这是职责 2 能给出"改派建议"的前提。
**但这不等于数据面全开**：数据面**≤ 它服务的那名智能体**，且 **V 的秘书另有收紧**（不读 F 的叙述 —— 见 `draft/55 §1.5`）。

## §3 秘书对秘书的协商

- **协商双方**：发件方秘书 ⇄ 收件方秘书（**不是**两个智能体本体出面）。
- **协商什么**：① 这条委托的**形态**（缺什么字段、该用哪个工具名）；② **角色匹配**（这活该不该我做、
  要拆成哪几步）；③ **可交付物**（我能交什么、你要的验收口径是什么）。
- **协商不成** ⇒ 上报**双方本体**；本体之间仍不一致 ⇒ 上报 **M**（有改派权与裁决权）。
- **本体看到的东西**：只有**加工后的**委托与协商结论 —— 这样智能体不必自己处理格式与错位问题（减免 #4）。

## §4 实现形态（一个共享模块 + 每角色一个实例）

| 项 | 做法 |
|---|---|
| **模块** | 新建**一个**共享模块（建议 `src/agentflow/secretary.py`，或 `agent_common/secretary.py`）：`class Secretary`，按传入的**角色上下文**（`ROLE_BRIEFS[role]` + `specs/<role>.py` 的能力面）工作 |
| **实例** | 每个智能体在装配时拿到**自己的** Secretary 实例（配置 = 自己的角色定位 + 自己的收件箱/发件箱路径） |
| **钩子位置** | **发件**：委托/消息离开本体之前；**收件**：委托/消息进入本体之前。落点集中在 `agent_loop.py`（所有角色共用的驱动）与 `conductor.py`（M 的派活路径）—— **两者都不在 FC-27 名册** |
| **不动的面** | **不占 `ROLES`**、**不加注册工具**、**不改权限面声明**（`capabilities`/`specs`/`tools` 的 `for_role` 面）、**不改 `llmseam` 的 enum**、**不重冻快照** ⇒ **不触发 #5**（只有一个新文件 + 两个钩子） |
| **要移交的写权** | **手稿通道的写权从智能体移到秘书**：关闭 `agent_loop` 的 `handoff` 写路径与 `summon` 的 `notify` 派生写，改由本体的秘书执笔（`manuscripts.write`）；新增 `manuscripts.revise`（追加修订行）。**行里的 `sender` 仍是被服务的角色**，`manuscript_rows` 的计数口径不变 |
| **台账** | 每个秘书写自己的一份：建议 `out/secretary/<role>.jsonl`（追加式、脚本发号，照 `verifications.py` 的形态） |
| **用的模型** | 用**本智能体自己的** LLM 缝（`llmseam`）；`scope` 建议记 `"secretary"`，花销进同一本 `usage_ledger`（这样 P-09 的粒度问题会暴露在一处） |

## §5 "先建一个，再批量"的具体做法

| 步 | 内容 | 为什么 |
|---|---|---|
| **1** | **先建 M 的秘书**（M 是主控，也是 838 次参数不合法与 565 行重复委托的**唯一来源**） | 先治最疼的，也先把"秘书⇄秘书"的协商协议跑通 |
| **2** | 效果由**机器读数与人**评估（`tasks`/`sessions` 本来就能算）—— **秘书自己不算任何指标**（用户 2026-10-06：拒绝率/重复率/闭环率那套统计是坏设计，去掉） | 秘书是**判断者**，不是仪表盘 |
| **3** | **批量给 A–H 装**：同一个 `Secretary` 类，每角色一份配置（角色定位 + 收件箱），加**每角色一条测试** | 批量 = 配置 + 测试，**不是新代码** |
| **4** | V 上线后，V 也装一个（与其他角色同一类；**它的数据面按 §12 收紧**） | V 也是智能体 |
| **5** | 最后给 **M 的秘书**加"全局未闭环"视角（它本来就最靠上） | 全局闭环与覆盖面判断落在 M 的秘书（见 §8） |

**批量时要防的两件事**：① 每个角色一份台账，别混写；② 每个角色的"没写 vs 写了空"三态不许折平。

## §6 成本控制：机器预筛 + 秘书按需介入

每条消息都过一遍模型 ⇒ 调用量与花销翻倍。**所以秘书不是"每条都介入"**：

| 机器先做（便宜、确定） | 只在下列情形才叫秘书 |
|---|---|
| 参数类型/枚举/必填、工具名是否在注册表、边是否允许、动作是否有实现 | 预筛**报警**（`invalid_params` / `unknown_action` / `not_wired` / `forbidden_edge` 的苗头） |
| 同一 `(role, action, input_key)` 是否已有终态行 | 出现**重复候选**、或闭环**逾期未反馈** |
| 收件箱里有没有未处理的委托 | **首次遇见**的委托形态（没见过的组合，让秘书给出加工版本，之后复用） |

⇒ 花销与"问题量"成正比，而不是与"委托量"成正比。这也是把 #1 治在源头的做法。

## §7 触发点

| 时机 | 谁的秘书 | 跑的职责 |
|---|---|---|
| 委托/消息**发出前** | 发件方 | 1 格式内容优化 + 2 委派评估 |
| 委托/消息**收到时** | 收件方 | 4 委托加工（然后交给本体） |
| **反馈回来后** | 收件方 | 3 闭环核对（销账） |
| 每趟**收工前** | 每角色各自 + M 的秘书做全局扫 | 3 未处理/未反馈清零检查 + 覆盖面把握 |
| **出错名 / 调不到工具**时 | 出错方的秘书 | 1 与 2 的复盘（并列候选 → 决定改法） |
| 人问"现在什么状态" | M 的秘书 | 状态报告（读数 + 决定 + 未闭环清单） |

## §8 它与 M、V 的分工（谁管什么）

| 事 | 归谁 |
|---|---|
| 报告**体例** | **M**（裁定）；各角色秘书只核对"M 声明的体例有没有兑现" |
| **改派 / 最终裁决** | **M** |
| 研究内容对错 | **V**（V 也有自己的秘书，但秘书不判内容） |
| 委托的形态、匹配、闭环（四职责） | **各智能体自己的秘书** |
| **全局未闭环清单 / 收工覆盖面把握**（原 `裁决 5`） | **M 的秘书**（体例与验收口径归 M，所以这层判断挂它） |
| 硬不变量（三态不折平 · 动作必留痕 · 不静默跳过） | **机器 / 门** |

## §9 边界（写死在模块里）

1. **不判研究内容对不对**（那是 V）；
2. **不裁定体例**（归 M）；
3. **不动硬契约**（30 档档名、`kind` 字符串、`SCHEMA_VERSION`、权限面）；
4. **不新增机器判据**（它写"决定 + 理由"，不写"规则"）；
5. **不静默修** —— 实质缺陷一律协商并留痕；
6. **不擅自改派、不代签** —— 协商不成上报本体，再不成上报 M。
7. **fail-open**：超时/超预算/自己出错 ⇒ **原样放行 + 留痕**（阻塞一条委托比放行更贵 —— 那是 #1）；
   只有机器已有的硬闸继续 fail-closed。

## §10 它接管之后，要改掉的机器设计

| 原设计 | 改成 |
|---|---|
| **E-01 机器侧"参数自动纠正"** | **撤掉**；改由发件方秘书（职责 1）优化 + 协商。机器只留 fail-closed 校验与留痕 |
| **E-03 `_refuse` 进叙事** | **保留机器半**（必须写 `task_end`）；闭环由收件方秘书（职责 3）负责 —— "留痕" ≠ "被处理" |
| **L-05h 错名回映（封闭别名表）** | 归**出错方的秘书**（职责 1/2）：机器并列候选（含 writers 子注册表），秘书决定改法 |
| **派活去重（`input_key` 硬拦）** | 归**发件方秘书**（职责 2，"该不该派"含"是不是重复"）；机器只把同 key 的既有终态行摆出来 |
| **F-05 待办/待核队列** | 生产端 = 机器（把降级/待核写出来）；消费端 = **各角色秘书**（自己的收件箱）+ **M 的秘书**（全局） |
| **智能体的手稿写路径**（`agent_loop` 的循环形状 `handoff`；`summon`/`summon_many` 的 `notify` 派生写） | **关闭写入**：形状保留、**执笔改由本体的秘书**；`manuscripts.read`/`list` 工具保留（智能体只保留"查"）；**新增** `manuscripts.revise`（追加修订行） |

## §12 接口规范（另见）

**知识面 / 动作面 / 工具面 / 权限 / 交流协议** 五件事已单独定死，见
**`draft/55-秘书接口规范：知识面·动作面·工具面·权限·交流协议.md`**。要点：
**工具面为空**（只用"注册表只读读数 + 工作区只读读数 + 唯一写=自己的台账"三种内部能力）·
**权限 ≤ 它服务的那名智能体**（表只读、写集 ∅、模型用本体自己的缝、fail-open、不碰禁改区文件）·
**交流走六种事件**（`optimized/notice/proposal/question/negotiation/decision`），
发件与收件同步（1 次调用、≤3 秒、超时放行）、闭环与协商异步（协商 ≤2 轮）、
**不许冒充本体**、**协商结论必须抄送本体**、**原文与加工后并列留痕**；
**V 的秘书另有更严的信息隔离**（不读 F 的叙述，否则会绕过 I12 的审校独立性）。
