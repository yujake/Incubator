## 0. 一句话结论

DSH 的提示词机制（有序段 + persona + 预设 + 工作区指令 + 技能目录）**没有"协作"这一层**：
它只有"子代理"这一件工具（`dsh-tool-subagent`）。而我们的系统里，协作是**独立的一等成分**：
11 种循环形状里有 **8 种**是协作（`summon` / `summon_many` / `message` / `handoff` /
`roster` / `interrupt` / `retire`，加上 `final`.`notify`），另有**代唤**（relay）、
**五元位**（一条命题的状态由多个角色的产出合成）、**手稿**（盘上可复核的交接）三件 DSH 完全没有的东西。

所以"在 DSH 的设计上继续改造"这句话在本主题上落成三步：
① **沿用** DSH 的机制（块 / order / scope 遮蔽 / 空段消失 / 预设目录 / 追加式 user 消息）；
② **新增**我们自己的块族（协作、父子、五元位、代唤、名册）；
③ **先把说不清的地方裁清**（§4 的 10 条），否则写出来的协作块会把"框架的真实行为"
写成另一套 —— 而提示词与实现不一致，正是本仓最贵的那类缺陷。

## 1. 协作面：真实证据

### 1.1 三种指称（这是协作里最容易混的一件事）

| 指称 | 形状 | 谁分配 | 什么时候变 | 出处 |
|---|---|---|---|---|
| **台账号** `task_id` | `"t-NNNN"` | 框架（秘书/Conductor） | 一生不变 | `schema.py:2223` 逐字：`task_id: str  # "t-NNNN"（过程记录，不占 4 位编号空间）` |
| **实例标签** `instance` | `"A#2"`（空串 = 只有一个实例） | 派活的人（`summon(..., instance=…)`）；同一批里同角色多次且没给 ⇒ 框架自动补 `<角色>#N` | 一生不变 | `schema.py:2239-2247`；`agent_prompts.py:196-197`（自动补的规则写进了提示词） |
| **名册名** | `"D1"` | **父可以自己提名**（`name`），或由**秘书分配** | 一经分配**不再改**；`retire` 之后**永久不再复用** | `agent_prompts.py:172-177`；`secretary.py:3050`（`next_name` 按已用最大序号推） |

**一条已经写下来的纪律**（在拒绝文案里，不在提示词正文里）：`agent_loop.py:1684-1685`
逐字："`retire` 需要 `name`（名册名，例如 \"D1\"）：「要退谁」只能用名册名说，
**绝对编码不是父子之间的指称**"；`interrupt` 同一条（`:1691-1692`）。
而 `AGENT_IDENTITY` 又把 `task_id` / `parent_task_id` / `children` 渲染给模型
（`agent_prompts.py:2057-2061`），理由是"编号用来对账与回报"（`:2061-2062`）。

⇒ **两处各说一半**：一处说"台账号用来对账"，另一处说"指称只能用名册名"。
缺的是一句**总判据**（见 §4.4）。

### 1.2 协作的通道清单（11 种形状里 8 种是协作）

`agent_loop.py:65-66` 逐字：`SHAPES = ("tool", "summon", "summon_many", "message", "handoff",
"note", "ask_user", "final", "retire", "roster", "interrupt")`。

| 形状 | 协作语义 | 关键约束（代码） |
|---|---|---|
| `summon` | 唤起一个伙伴做一件事 | 过边表 / 深度 / 扇出 / 并发 / 总量 / 预算（`policy.check`） |
| `summon_many` | 一次唤起一批（并发） | 按**写集**分波（`policy.waves_of`，`:528`）；返回带 `waves` / `concurrent_peak`（`agent_loop.py:3991-4004`） |
| `message` | 传信息（不要求对方立刻做事） | 私聊要求**至少一条协作边**（`agent_prompts.py:207-208`） |
| `handoff` | 交接手稿（盘上可复核） | 编号由脚本分配，落在 `manuscripts/handoffs.jsonl` |
| `roster` | 看名册（只读） | `of` 可以是 `self` / 我名下某子代理名 / `scope="descendants"`（全树） |
| `interrupt` | 停某个子代理**当前那一轮** | 只停它那一轮：排队消息还在、它自己的子代理继续跑、不递归（`agent_prompts.py:250-254`） |
| `retire` | 让子代理退役 | 父决定；名字永久不复用；**面归还**可分配池（`secretary.py:213, :3374`） |
| `final.notify` | 收工顺手写一份手稿 | 主控例外：它的 final 是给用户的回复 |

**框架侧还有一条提示词里没有的通道**：**代唤**（relay）。见 §2.6 与 §4.1 —— 它是本轮
最要紧的一处不一致。

### 1.3 `#public` 的可见面：**不是"所有人"**

`agent_prompts.py:202-205` 逐字："to 也可以是 `#public`：那是一条**公共频道**的消息 ——
它的可见面是**你名下的直接子代理**（业主 T20/T21）：只有它们会在收件箱里看到它……
而同级的兄弟、你的父、别的支都**看不到**"。

代码侧两格判它：`agent_loop.py:1152` 逐字："`parent_task_id` / `parent_role` 是公共频道可见面的两格
（S6-a，业主 T21 附二 乙）"；`:4527` 逐字："S6-a（业主 T20/T21 附二 乙）：公共频道的可见面 =
发信人的直接子代理"。叫停广播也因此收窄过（`conductor_tools.py:530`）。

⇒ "公共频道"这个词的直觉是"全树可见"，而设计是"我的直接子树"。提示词写了，但**词与语义相反**，
值得在协作块里用一句更强的说法（§4.8）。

### 1.4 五元位：多个角色的产出如何合成"一条命题的状态"

`evidencebits.py:85` 逐字："把各方标下的读数组装成五元位（纯函数：不读盘、不写盘）"；
`:123` 逐字："台账里的一行 ⇒ 五元位（唯一的读入口：判据、门、状态报告都走这里）"；
`:205` 逐字："五元位 ⇒ 等级（唯一的等级来源；**任何角色自报的等级都不认**）"。

位的 owner（`agent_v/core.py:378` 逐字："五元位第 3 位 owner 是 V"；
`agent_prompts.py:1520` 逐字："H 的职能是稿件级正式审查（五元位第 5 位）"）：

| 位 | owner | 证据 |
|---|---|---|
| 第 3 位（审过） | **V** | `verifications.py:252-258`（`成立` 且没有未解决的 error 才签） |
| 第 5 位（稿件级审查） | **H** | `agent_prompts.py:1520`、`agent_v/core.py:6` |

⇒ 这是**协作的骨架**：一条命题的"可信到什么程度"不是任何单个角色说了算，而是五个位各自落账、
由 `evidencebits` 合成。**提示词里今天没有任何一块讲这件事**（只有 V 的边界里提到"五元位第 3 位"）。
这是 §5 新增块里最该写的一块（M/G/H/V 尤其需要）。

## 2. 父子代理：真实证据

### 2.1 四类上限（真实数字在这里，提示词里一个都没有）

`policy.py:9-20` 逐字给了"缺一不可"的表：

| 只有 | 会被怎么绕过 |
|---|---|
| `max_tasks_per_run`（总量） | 瞬时把并发打爆：总量对了，但 200 个任务同时开跑 |
| `max_concurrency`（瞬时） | 扇出可以无限持续：每秒 4 个，跑一天 |
| `max_depth` | 每一层都能无限宽（深度 5，每层 9999 个） |
| `max_fanout` | 链可以无限深（每次只派生 1 个，但派生 10000 层） |

实测默认值（`policy.py:88-106`）：

```text
max_depth        = 5     # 主控发起 = 1 ⇒ M(1) → A(2) → B(3) → C(4) → D(5) 已到底
max_fanout       = 5     # 单个任务"同时在飞"的子代理数；主控那一档 = 20（FANOUT_LIMIT_BY_ROLE，:163）
max_concurrency  = 4     # 全局同时运行的任务数（瞬时）
max_tasks_per_run= 200   # 一次 run 的召唤总数（生命周期总量）
wall_clock_sec   = 900   # 全局墙钟（None = 不限）
token_budget     = None  # 不限
usd_budget       = None  # 不限
```

而提示词只说"过策略"，没有数字（`agent_prompts.py:268` 逐字）：
"唤起伙伴要过能力表与策略（允许的边 / 深度 / 扇出 / 并发 / 总量 / 预算）"。
模型知道自己的 `depth`（`AGENT_IDENTITY` 里的 `{{depth}}`，`agent_prompts.py:2065`），
但不知道上限是 5；也不知道"同时最多派 5 个（M 20 个）"。

### 2.2 扇出的口径 = **同时在飞**（不是累计）——业主 2026-10-08 逐字裁定

`policy.py:32-33` 逐字：

> 「我认为的"派活上限"不是累计的，是单时刻的，即 M 同时派出在后台运行的子代理数
> 不超过 20，各角色智能体允许同时向其它智能体派活数不超过 5，智能体返回后腾出空间。」

`policy.py:35-36` 逐字："所以分子 = 子行里仍然在飞的那些（`status ∈ {pending, running}`）；
子代理一返回（`done` / `failed` / `cancelled`，都带 `ended_at`）就腾出名额 —— 与它返回得好不好无关。"

被取代的旧口径也记着（`policy.py:40-42`）：累计口径下 T1 第 18/19 趟在第 51–88 步就用完了 20 个名额，
后续 `G.build_document` 与修好的 Lean 重派全部进不去。

### 2.3 名额是**逐实例**的：D#1 满了就另起 D#2 ——业主 2026-10-08 逐字

`policy.py:53-55` 逐字：

> 「如果 D 外派了 5 个智能体，又有其它人向 D 派活且不是之前唤起 D 的那个人，
> 这时应该是唤起另一个 D2 而非让这个 D 去接手。于是理论上最大可并行智能体数为
> 20*(5*5*5*5*……)。我们限制递归调用深度为 5。」

落在数据上（`policy.py:59-64`）：`Decision.fanout` 数的是"**这一个父任务**此刻在飞的子代理"，
不是"这个角色一共有几个子在飞"。⇒ 别人再向 D 派活 ⇒ **新建一行 D 任务（D#2）**，它自己的在飞数是 0。

### 2.4 触顶先等：`fanout_wait_sec = 900` 与 `wall_clock_sec = 900` 是同一个数

`policy.py:46-49` 逐字："触顶时先等（所有者 2026-10-08 补的下一句：「当达到派活上限后，
父智能体或主控只可等待子智能体返回结果」）：等待发生在 `Conductor.summon`（`fanout_wait_sec`，
默认 900s；等到一个返回就照常派）"。
实测：`conductor_tools.py:133` `DEFAULT_FANOUT_WAIT_SEC = 900.0`，而 `Policy.wall_clock_sec = 900`。
`Conductor.summon` 的默认是 **0（不等）**，真跑批那一处才显式传 900（`conductor.py:580`）。

### 2.5 父子关系的唯一权威来源是台账，不是调用栈

`schema.py:2228-2229` 逐字："父任务 id。主控发起的为 None。这条链是"深度"的唯一权威来源 ——
不靠调用栈，因为跨进程/跨会话之后调用栈就没了。"
`schema.py:2231` 逐字："召唤链的深度（主控发起 = 1）。单调不减，resume 后不重置（FC-18 ③）。"
`schema.py:2226-2227`：`called_by` 可以是 `"M"` / 角色名 / `"user"`（人直接指派）。

### 2.6 名册视图是**快照**，不是实时的

`agent_loop.py:2170-2171` 逐字："它是这一趟开始那一刻的名单（提示词在 `run` 里渲染一次）：
这一趟里新派的子代理不会自己出现在这里。不假装实时 —— 那需要每一步重渲染，见 `draft/85` §5.2。"

而 `AGENT_IDENTITY` 把它渲染成"**此刻**你名下的子代理"（`agent_prompts.py:2059-2060`）。
活的视图只能靠 `roster` 形状现查（`:242-248`，带 `status` / `in_flight` / `last_reading`）。

### 2.7 取消语义（FC-20）

`schema.py:2213-2220` 逐字三条：① 每个 start 有且仅有一个 end；② 终态**先到先得**
（`ended_at` 一旦写下不许再改）；③ `dispose` 幂等。
`policy.py:96-101` 逐字："到点之后新召唤一律被拒，已在跑的走协作式取消 —— **不是强杀**。
强杀会让"取消"与"完成"在同一瞬间争夺同一个 `ended_at`……「结果未知」是必须如实记下的状态。"

### 2.8.1 四条结论（都直接改变本文件的建议）

1. **父子链在真机上不存在**（最长两层、只有 2 个父有子；另一轮读数里 `parent_task_id` 全空）。
   ⇒ 提示词里那套**停 / 退 / 复用 / 面切割 / 槽位池**讲的是一个真机上还没发生过的世界。
   它们不该消失（那是设计），但**不该占据提示词的重量级位置**。
2. **但"一次派一批"是真在用的**（`summon_many` 689 次、占步数 13%）⇒
   `summon_many` 那一块**不许瘦身**；要瘦的是它周围的父子机制（停/退/复用/面）。
3. **上行（子 → 父）消息 0 条**（579 条留言里 564 条是 M 发的）；而**手稿 1562 行**里
   `to=ALL` 有 **427** 行、且**没有一行是模型自撰**（全由框架派生）。
   ⇒ 真机的主形态是"**M → 角色** + **框架派生的交接**"，
   提示词里那一大段教模型"怎么自己写一份好手稿"的文本，在真机上产出 **0** 行自撰。
4. **四类上限一次都没触发过**，`forbidden_edge` 只有 7 次 —— 而真正压倒性的失败是
   **`invalid_params` 838 次**。

### 2.8.2 由此对 §4/§5 的优先级重排

| 主题 | 我原来的建议 | 按真机读数改后 |

## 4. 需要澄清的点（每条：现象 / 两侧证据 / 风险 / 建议口径 / 谁裁）

### 4.1 ★ 代唤的收件人：提示词说"发给 M"，代码发给**直接父**，业主裁定也是"父"

- **提示词**（两处）：`agent_prompts.py:270-273` 与 `:1836-1841`（见 §3-③④）——
  逐字是"给主控（M）的代唤申请" / "换目标为 M" / "直接把 message 发给主控 M"。
- **代码**：`agent_loop.py:4434-4435` 逐字："「请代唤」该发给谁：**直接父的角色**（顶层 / 读不到 ⇒ 落回主控 M）"，
  并写明这是业主 2026-10-09 的口径、改前的写法"写死发给 M（越级：中间那一层看不见，M 被当路由器）"
  （`:4436-4439`）。落回 M 的四种情形：没有父 / 父那一行就是我自己 / 台账读不成 / 父那一行没有 role（`:4441-4457`）。
- **业主逐字（`draft/97:1542`，本轮复核过）**：
  「最常见的定义不明极可能是 A 查论文要 B 消化时遇到生僻定义，**这时和父代理 A 交流即可**」
  ⇒ 裁定站在**代码那一侧**，提示词是没跟上措辞的那一方。
- **为什么提示词会写着 M（立项根据，我复核过）**：`draft/43-旧设计调查-A:37` 逐字记着
  用户原话「至少要能**向主控申请**唤起别的智能体」（`draft/28:18097-18100`，实现 `draft/28:18138`）。
  ⇒ **提示词那两句话是"立项时的措辞"，2026-10-09 的裁定改了收件人而没改提示词**。
  这就是修复的形状：把立项措辞换成裁定的措辞（不是"新增设计"）。
- **过期文档（同一条漂移的另一半）**：`draft/28:18138`"给 M 发一条 `subject=请代唤` 的留言"、
  `draft/37:397`"自动转成给 M 的申请" —— 两处都停在改前口径。
- **第三方证据**：`specs/m.py:56` 的 M 政策逐字："收到 subject=「请代唤」的留言…**本轮内必须处理**"；
  而通知面 `conductor_tools.py:171-180` 的 `relays` 视图是给 M 看的。
- **风险**：模型照着提示词**手动**把申请发给 M（而不是等框架自动发），于是"越级"这件事又被模型自己做了回来；
  M 的注意力被占，而真正的父那一层仍然看不见。反过来，模型以为"框架已经发给 M 了"，
  于是**什么都不做**地等 —— 而申请其实在父那里。
- **建议口径**（三选一，我推荐甲）：
  - **甲**：提示词改成"框架会把这次被拒自动转成一条**给你直接父**的代唤申请（顶层就是 M）；
    你也可以自己写一条 message 给**直接父**"。同时把 M 的 policy 那一句改成
    "**若某条「请代唤」落到你这里**（顶层或父读不到时）⇒ 本轮内必须处理"。
  - 乙：代码改回"发给 M"（推翻 2026-10-09 的裁定）—— 不推荐，那条裁定有明确理由（M 被当路由器，
    且业主 2026-10-09 又逐字说了"和父代理 A 交流即可"）。
  - 丙：发给"直接父 + M 各一份"（父执行、M 知情）—— 代价是两处状态要对账。
- **谁裁**：业主（这是 2026-10-09 裁定的措辞没有跟到底，不是新设计）。
- ✅ **已落地（2026-10-11，批 P2；甲案）**：提示词三处（循环协议那一条、伙伴表的代唤通道、
  上报规则）全改成"直接父（顶层 / 父那一行读不成才是 M）"；`specs/m.py` 那一句**看了不用改**
  （它只说"收到就处理"，与新收件人不冲突）⇒ 本批没有第二次动禁改区。
  读数与判据见 `draft/103` §4.1b-7。

### 4.2 ★ `{{children}}` 说"此刻"，实际是**这一趟开始那一刻**的快照

- **提示词**：`agent_prompts.py:2059-2060`："此刻你名下的子代理…`{{children}}`"。
- **代码**：`agent_loop.py:2170-2171` 逐字："它是这一趟开始那一刻的名单（提示词在 `run` 里渲染一次）：
  这一趟里新派的子代理不会自己出现在这里。不假装实时"。
- **风险**：模型在这一趟里派了三个子代理，回头看提示词发现名单里没有它们 ⇒
  可能得出"派活没成功"的结论（而实际上成功了）；或对已退役的子代理继续派活。
- **建议口径**：把那一句改成"**这一趟开始那一刻**你名下的子代理（快照；要看活的用
  `{"roster": {"of": "self"}}`）"。这是一处**纯文案**改动，但它把"静态快照 / 活查询"
  的分工一次说清 —— 这是协作块必须写对的一句。
- **谁裁**：业主（文案，B 轴批次里做）。
- ✅ **已落地（2026-10-11，批 P2）**：`AGENT_IDENTITY` 那一句改成
  "这一趟开始那一刻你名下的子代理（名册摘要：名字 · 一句简介 · 状态。**这是快照** ——
  这一趟里新派的不会自己出现在这里，要看活的用 `{"roster": {"of": "self"}}`）"。
  读数见 `draft/103` §4.1b-7。

### 4.3 四类上限的**真实数字**要不要写进提示词

- **提示词**：只说"要过策略"（§3-②），没有任何数字。
- **代码**：真实数字见 §2.1；拒绝时会回理由码（`depth_exceeded` / `max_fanout` 等），
  模型可以靠被拒学习 —— 但那是**试错式学习**，而派活是"先规划再派"的动作。
- **风险**：一个父计划"这批活分给 6 个人"，第 6 个必被拒（上限 5）—— 它事先无法知道。
- **建议口径**：把**三个数**写进块里（"你同时最多 ×× 个在飞的子代理；链最深 5 层，
  你现在在第 {{depth}} 层；全局同时最多 4 个在跑"），**不写** `max_tasks_per_run=200`
  那种生命周期总量（它会让模型把"还能派几次"当成配额去省着用）。这一条要业主裁，
  因为它实质上是"把策略面暴露多少给模型"。
- **谁裁**：业主。

### 4.4 三种指称混用：缺一句总判据

- **提示词**：`AGENT_IDENTITY` 渲染台账号（`:2057-2061`，理由"编号用来对账与回报"）；
  `retire` / `interrupt` 只认名册名（`:253-258`）。
- **代码**：拒绝文案逐字说"绝对编码不是父子之间的指称"（`agent_loop.py:1685`），
  但那条文案**只在模型犯错之后**才看得到，不在提示词正文里。
- **风险**：模型用台账号去 `retire`（被拒一次，浪费一步）；或者反过来，在对账时用名册名
  （名册名会被复用面上回收，对账对不上）。
- **建议口径**：在协作块里写一句总判据，例如：
  "**台账号用于对账，名册名用于指称**：`summon` 按角色走、`retire`/`interrupt` 只能点名册名、
  报告里引用产出用 `experiments:0003` 这种台账引用。"
- **谁裁**：我（文案级）—— 但要在施工单里登记为"新增一句判据"。
- ✅ **已落地（2026-10-11，批 P3）**：新段 `COLLAB_NAMES`（order 5220），四句 ——
  台账号用于对账与回报 / 名册名用于指称（`interrupt` / `retire` / `roster` 只认它，
  写台账号会被受控拒绝）/ 实例标签分实例 / 引用产出用台账引用。
  受众按业主口径 C 收窄成"出边非空"（原表写"全部"，而 C 一辈子没有子代理）。读数见 `draft/103` §4.1b-8。

### 4.5 `depth` 同名不同义（代码内部）

- `schema.py:2232`：`Task.depth`（**召唤链**深度，主控发起 = 1，`< 1` 抛）。
- `schema.py:1390-1391`：`AttackPlan.depth`（**嵌套攻坚**深度，默认 0，`< 0` 抛）。
- **风险**：两个 `depth` 都进台账、都可能出现在报告的同一段话里；提示词只说"召唤链上的深度"
  （`agent_prompts.py:2065`），没有区分词。
- **建议口径**：提示词里把召唤链那个叫"**召唤深度**"，攻坚那一个叫"**攻坚轮次深度**"；
  台账字段名不改（那是 schema，禁改区）。
- **谁裁**：我（文案级）。

### 4.6 等待 900 秒与墙钟 900 秒是同一个数

- 实测：`DEFAULT_FANOUT_WAIT_SEC = 900.0`（`conductor_tools.py:133`）与
  `Policy.wall_clock_sec = 900`（`policy.py:102`）。
- **风险**：一次扇出触顶后的等待，可能正好吃掉整轮墙钟预算 ⇒ 这一趟以"墙钟到点"收工，
  而模型读到的原因是超时而不是"我在等名额"。
- **建议口径**（要业主裁）：等待上限应当**显著小于**墙钟（例如 60s，或墙钟的一个比例），
  否则"等名额"与"整轮结束"是同一件事。
- **谁裁**：业主（这是数字与语义的口径，不是文案）。

### 4.7 M 不可召唤 + B/F/V 不由 M 直接控制 ⇒ 代唤是**结构性必需**

- 边表：`capabilities.ALLOWED_EDGES` 里 `M` 的出边是 6 个（`A/C/D/E/G/H`），

- 提示词：M 的伙伴表是"可见 9 个、出边 6 个"，其中 B/F/V 带"你唤不起它"标记

- **澄清点**：`draft/101` §8 已经把它记为待裁；本文件补一条**证据**：既然 M 唤不起 B/F/V，

### 4.11 ★★ `invalid_params` 838 次：真机上的**第一失败形态**，而提示词只给了它两句话

- **真机读数**（`draft/41-总:134` 逐字）：`invalid_params` **838** · `unknown_action` 52 ·
  `not_wired` 7 · `forbidden_edge` 7 · `deadline_exceeded` 1。
  ⇒ 它比第二名多 16 倍，比四类上限加起来（**0**）多 838 倍。
- **提示词今天给的**：`agent_prompts.py:262-266` 两句（"参数提示只列必填，它不是全部可用键：
  可用键是封闭集合……被拒时框架会把该工具/动作的完整参数表回给你"）+ 每个工具/伙伴行后面的
  `（必填 …）`。兜底本体是 `agent_loop._param_table`。
- **风险**：这是 838 次真实代价，而协作块（§5）如果按"把父子机制写全"的路子走，
  会把预算花在一个**从未发生**的世界里，而继续把 838 次的那个世界留成两句话。
- **建议口径**：协作块**不该挤掉**参数块；相反，`PARAM_*` 这一类块（每工具必填 + 被拒时的
  重写纪律 + 封闭集合）应当在每个角色的组合里占一个**固定位置**，
  而"停/退/复用/面"合起来**不超过一页**（§4.12）。
- **谁裁**：我（分块与配重），但配重比例要让业主看一眼 —— 它直接决定 31% 的循环协议要不要瘦身。

### 4.12 四类上限从未触发 ⇒ "把数字写进提示词"要降级

- 见 §2.8.2 与 `draft/41-总:134` 的"零 `depth_exceeded/fanout_exceeded/concurrency_exceeded/budget_exceeded`"。
- **建议口径**：§4.3 从"写三个数"降为"**在角色专属块里按需写一句**"：
  只有真会当父的角色（M / D / F）写"你同时最多 5 个（M 20 个）在飞的子代理"，
  其余角色不写 —— 它们的失败形态不是撞上限，而是参数写错。
- **谁裁**：业主（与 §4.3 同一条，改的是配重不是对错）。

### 4.13 代唤：触发条件真机发生过（`forbidden_edge` 7 次），而代唤记录 **0～1 次**
