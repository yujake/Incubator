## 1. 依据：我把哪些东西算作"vibe coding 忌讳"

判断标准来自两处，且**都不是凭印象**：

1. **本课题自己的调研报告** `07-大型编程项目开发规范调查报告.md` §C（Vibe Coding 专题）
   与 §D.2 的 **25 条反模式黑名单** —— 这是阶段①就做完的作业，本轮直接复用。
2. **本轮外部参考**：`anti-slop` 技能的分类目录（自然语言 / 代码 / 设计三类）。
   其中与代码有关的高优先项是：通用名（`data`/`result`/`temp`）、复述式注释、
   无谓抽象、复制粘贴、magic number、**过度文档化**、以及**装饰性文本**
   （该目录明确把"excessive emoji and inspirational quotes"列为 README 级忌讳）。

关键在于：**这些清单只能提供候选，不能提供判据**。清单里的每一条都要在
**真实样本**上量一遍，否则就会落入本项目 §6 的 **P15（告警噪音化）**：
"假报警会训练人忽略告警"，而且这种损伤"几乎不可逆"。

所以本轮的做法是：**先量，再决定要不要改**（第 6 节整节都是量出来的数字）。

## 2. 清洗范围与它为什么只能这么划

### 2.1 只动注释与 docstring

| 部位 | 是否清洗 | 为什么 |
|---|---|---|
| 注释（`#` / `#:`） | ✅ 清洗 | 不会被渲染器消费。写在里面的成对星号到了读者眼里只是星号 |
| docstring（模块/类/函数） | ✅ 清洗 | 同上；且本仓库的 docstring 是**给读代码的人**看的，不是给文档生成器渲染成网页的 |
| 普通字符串字面量 | ❌ **不动** | 见下 |
| 禁 AI 区（FC-27）的 13 个文件 | ❌ **不动** | 按 FC-27 只能由人编写或人逐行走查，且各需 2 名 reviewer 批准 |

### 2.2 为什么普通字符串字面量必须排除（实测 1522 处）

用 AST 数了一遍（脚本 `../temp/_strings_audit.py`）：

| 部位 | 带装饰的字符串字面量 |
|---|---|
| 禁改区外 | **1522 处 / 59 个文件** |
| 禁改区内 | 251 处 / 7 个文件 |

这 1522 处**绝大多数是产物而不是风格**：

- `agent_d.write_report` / `claimanatomy` / `tools/doc_tools.py`（86 处）——
  这些模块**生成 Markdown**，`**` 在那里真的会被渲染（是"粗体"这个语义本身）；
- `gates.py`（148 处）与 `tools/review_tools.py` —— G/H 的门产出的是**报告正文**，
  下游要渲染成 `docs/` 里的 markdown；
- 测试夹具里刻意写出的 `"**加粗**"` 字面量 —— 它们是 R009 的**正样本**。

而"哪些字符串会被渲染成 markdown、哪些只会 `print` 到终端"**没有机械判据**
（同一句 `**` 在一个模块里是产物，在另一个模块里就是噪音）。给一个分不清的判据
等于给一条会误伤的判据 —— 所以本轮**不动字符串字面量**，把它作为显式的
人的待办记在第 6.10 节，而不是用一个粗糙的脚本去猜。

## 3. 清洗的执行：两遍，以及我自己工具里的一个真缺陷

### 3.1 工具与安全网

工具是 `../temp/_clean_deco.py`（**只作用于注释与 docstring**，禁改区文件按
`.noai-paths` 逐条跳过）。它带两条自检：

1. 清完之后，**代码跨度之外**不许再有 `**`（`` `2**20` ``、`` `a/**/b` ``、
   `` `handler(**params)` `` 这类字面语法必须先摘掉再判，且摘掉的原文要**按编号还原**）；
2. **AST 代码签名逐字符不变** —— 抹掉 docstring 内容后 `ast.dump` 必须与清洗前完全相同。

第 2 条比"跑一遍测试"更强：测试只覆盖我们想得到的情形，而它覆盖**全部语法结构**
（常量、运算符、装饰器、默认值、类型注解）。

### 3.2 第一遍：2195 处（99 个文件）

逐处前后对照在 `../temp/deco-diff.txt`（4588 行，99 个 `### 文件` 段，
段头括号里的处数相加 = 2195）。

### 3.3 第二遍：12 处（11 个文件）—— 这里有一个真缺陷

第二遍是**复核时**发现问题的：用探针（`../temp/_r009_nonzone.py`）重新数，
**区外还剩 12 处**，而清洗工具自己报告"0 处"。

根因不在正则，而在**判据的来源**：

```python
# 出错的判据（第一版）
new, diffs = clean_source(text, rel)
if not diffs:          # ← 拿"对照报告"当"要不要写盘"的判据
    continue
```

`diffs` 里记的是"**span 起始行**的前后文本"。模块 docstring 的 span 从第 1 行开始，
而粗体往往在第 3 行 —— 于是这一处改动**既没进对照表、也没被算作"有改动"**，
整个文件（如果它只有这一处）就被**静默跳过**。11 个文件、12 处正好是这个形状：

| 文件 | 处数 | 漏掉的原文 |
|---|---:|---|
| `scripts/__init__.py` | 1 | 这些脚本**不是运行期依赖** |
| `tools/probe_gap_ledger.py` | 1 | 从**全部**已登记报告 ingest |
| `tools/probe_rebuild_diagnostics.py` | 1 | 带下划线前缀的**非 schema 诊断字段** |
| `tools/smoke_real_provider.py` | 1 | 它**依赖网络** |
| `tests/demo_dataset_helper.py` | 1 | 它**只**负责"构造到指定目录" |
| `tests/test_agent_a.py` | 1 | 经裁决**以 DESIGN 为准** |
| `tests/test_demo_end_to_end.py` | 1 | **绝不**写 `test/test1/demo/run/` |
| `tests/test_pipeline.py` | 1 | 只跑**离线静态分析模式** |
| `tests/test_quoteverify.py` | 1 | 用**构造的 DocumentText 替身** |
| `tests/test_rebuild.py` | 1 | 带下划线前缀的**诊断/扩展字段** |
| `tests/test_tools_base.py` | 2 | **必须逐项一致** / 锁的是**契约** |

**这就是本项目 §6 的 P16（判据真空通过）的又一形态**，而且它比前几次更隐蔽：
判据不是"解析出了空集"，而是**判据被一个格式细节（改动落在 span 的第几行）
过滤成了空集**。修法有两条，两条都做了：

1. 判据改成**"文本真的变了"**（`new == text` 才 `continue`）——
   让改动本身决定落盘，而不是让**报告**决定落盘；
2. 对照表改成取**段内第一处变化的行**（`_first_changed_line`），
   于是"记了几处"与"改了几处"不再是两个可以分家的数字。

修完重跑：12 处（11 个文件），对照在 `../temp/deco-diff-r2.txt`。
**这一次是"先有独立探针、后有清洗工具的自报"才抓住的** —— 如果只看工具自己的
"合计 0 处"，这个缺陷会以"清洗完成"的形态留在报告里。

## 4. 立门：新增 linter 规则 R009

只清一次是不够的：这类标记会**扩散**（下一段注释照抄上一段的写法，几十个文件后
就成了默认风格）。所以把它变成一条机器可查的规则。

### 4.1 判据

`scripts/lint_rules.py::rule_R009_decoration_in_comments`：

- 扫的**只有**注释与 docstring（`tokenize` 给注释、`ast` 给 docstring）；
- 判三种形态：**成对的星号强调**、**未配对的残留星号**（"清了一半"的形态）、**emoji**；
- 判前先把**代码跨度**（`` `…` `` 与 `` ``…`` ``）换成等长空格 ——
  于是 `` `2**20` ``（幂）、`` `a/**/b` ``（glob）、`` `handler(**params)` ``（解包）、
  以及规则自己文档里要写出的 `` `**` `` 都**不会被误判**；
- 两级：**禁改区外 `error`**，**禁改区内一条汇总 `info`**。

### 4.2 为什么禁改区内只报 `info`（不是"手软"）

禁改区按 FC-27 只能由人改，每个文件的改动还要 2 名 reviewer 批准。
对它们报 `error` 等于造一条**永远红**的灯：它只能靠人去改 13 个人类专属文件才可能变绿。
本项目的教训（R001/R006 都栽在这上面）是：**一条永远红的门与一条永远绿的灯
一样没有信息量**。所以区内给一条能看见、不阻塞、且**点名要清哪几个文件**的 `info`。

### 4.3 立项前的校准（四类候选，都在真实树上量过）

| 候选形态 | 区外命中 | 结论 |
|---|---:|---|
| 成对的星号强调 | 12 | **采用** |
| 未配对的残留星号 | 12 | **采用**（它是"清了一半"的形态） |
| emoji | 1 | **采用** |
| 单个星号强调（`*…*`） | 7（其中 6 处假阳性） | **放弃** —— 它们是 `# -*- coding: utf-8 -*-`（编码声明）与 `search.*`（glob 写法）。真命中里混着同形态的 glob，单靠字符分不开 |
| Markdown 链接 `[文字](url)` / 删除线 | 0 | **不立项** —— 一条没有真实正样本的规则无法校准，它只是"看起来更严" |

**emoji 的字符范围也校准过一次**：第一版把箭头（`→` `⇒`）也算进 emoji，
于是全仓得到 **915 处**命中，绝大多数是本仓库正常的流程写法 `A → B`。
范围因此收窄为"emoji 平面 + 杂项符号 + 变体选择符"，并在代码里写下这条理由。

### 4.4 这道门怎么处理"查不了"（三态纪律）

| 情形 | 结论 |
|---|---|
| 禁改区清单读不到 / 解析失败 | `error` —— 分不清区内区外，**本次没有真正检查**（分不清时若默认"都是区外"，命中会落到人专属文件上，反过来诱导人去改禁改区） |
| 一个源文件都没扫到（根写错） | `error` —— "没扫到"不能读成"干净" |
| 判据自检不过 | `error` —— 见下 |
| 文件读不出 / 解析不了 | 一条汇总 `warning` —— **"未知"不是"干净"** |

**判据自检**（P16 的正解）：规则在扫真树之前，先在一段人造样本
（1 个 docstring + 1 个注释）上证明自己的扫描器"接上了"。
第一版没有自检，改用"整棵树解析出的注释数为 0 ⇒ error"当反真空判据 ——
结果在一棵**真的没有注释**的合成树上误报，被既有测试当场抓住
（`test_linter_runs_all_rules_and_reports_counts`）。
这条误报本身很有价值：**"树里没注释"与"扫描器坏了"在输出上完全一样**，
所以判据必须建立在**自检样本**上，而不是建立在被检对象上。
这两条互为负控（`test_r009_fails_when_its_own_scanner_is_broken` /
`test_r009_accepts_tree_without_any_comment`）。

### 4.5 狗粮：R009 上线后先抓的是我自己

## 6. 逐类审计：哪些改了，哪些**刻意不改**，为什么

这一节是本报告的主体。**"不改"也是结论，且必须带数字和理由** ——
否则读者无法判断是"审过之后决定不改"还是"根本没审"。

### 6.1 通用名（`data` / `result` / `temp` / `item` / `value`）—— 53 处，不改

实测：公开名或形参里出现通用名 **53 处**（`value` 14、`item` 8、`result` 4、`res` 3…）。

不改的三条理由：

1. **参考体例自己写明了豁免**：`anti-slop` 的 code-patterns 在"Context Matters"一节
   明确列出"**Generic names in small scopes**: `i`, `x`, `acc` in a 3-line function is fine"。
   本仓库的这 53 处几乎全是这种形状：`contextbudget.value(...)`、
   `noai_gate._parse_reviewer(item)`、`providers._parse_item(value)` ——
   在**它们各自的上下文里**，`value` 就是 JSON 里那个值，改名不会增加信息。
2. **改公开形参会破坏关键字调用**：这些是 `ToolSpec` handler 与库函数的形参，
   调用方（含测试与 `tools.json` 派生的 schema）可能按关键字传参。
   为风格改签名，风险远大于收益。
3. **通用名本身不是 AI 特征**：它出现在 1970 年代以来的所有代码里。
   把它当"AI 味道"的判据，只会得到一条误伤率极高的门。

**真正值得抓的是"同一个名字在不同作用域里指不同东西"**（那才是 `result` 的病），
而这一条本仓库已经有更准的门：R003（同名不同契约的重复实现）。

### 6.2 占位名（`foo` / `bar` / `baz` / `My*` / `testN`）—— 正则 35 处命中，**真命中 0**

35 处全部是**路径**里的 `test/test1`（被 `\btest\d\b` 匹配到）。
在**产品代码**里一个真占位名都没有。⇒ 不改，且**不立规则**（假阳性率 ≈ 100%）。

### 6.3 复述式注释（"# 返回结果"那种）—— 正则 14 处命中，**真命中 0**

逐条看过 14 处，全是**判据说明**而不是语法复述，例如：

- `scripts/lint_rules.py:284`：`# 调用方拿到 None 依然分不出"没做"与"做了没有"。`
- `src/agentflow/agent_a.py:812`：`# 检查器的"没跑成"与"跑成了、发现缺陷"是两件事，但两者都不是"通过"。`
- `src/agentflow/tools/ocr_tools.py:365`：`# 返回空串在这里是诚实的：调用方本来就知道它不做 OCR。`

它们都以动词开头（所以被正则抓到），但说的都是**为什么**而不是**做什么**。
这恰好是本项目 §2.4 要求的东西（docstring/注释必须含"为什么"）。
⇒ 不改。

### 6.4 注释掉的代码 —— 正则 14 处命中，**真命中 0**

14 处全是"用参数写法说明调用点"的注释，例如
`# auto_build_c=False：本步刻意测 replay 模式（只用已登记的报告）。`、
`# gpu=False：本机只有 CPU torch；verbose=False：避免每次识别都刷一堆日志。`
—— 这些**看起来像代码，其实是给人读的调用点说明**。⇒ 不改。

### 6.5 超长函数 —— 184 个（区外 157 个），**本轮不改**

最长的一批：

**为什么不改**：拆分这些函数的收益是"可读性"，代价是**动到全系统的核心路径**；
而它们**已经**是本项目缺陷密度最低的地方 —— 每个函数都有一份"这个数字/判据为什么长这样"
的成文理由，拆开会让理由与代码分离。更重要的是：**这一轮的任务是清风格，不是重构**，
把 157 个函数的重构混进一次风格清洗，会让"风格清洗"这件事本身失去可验证性
（一旦测试红了，没人能快速判断是风格改动还是重构引起的）。

⇒ 列为**可选后续**（要做的建议单独一轮，一次只拆一个，并配"拆分前后行为一致"的断言）。

### 6.6 函数内 import —— 294 处 / 68 个文件，**不改**

绝大多数是**刻意的延迟导入**，两类原因：

1. **避免导入环**：`store ↔ tools ↔ agent_*` 之间有成对依赖，顶层导入会形成环；
2. **重依赖只在使用时才付代价**：`PyPDF2` / `easyocr` / `torch` 这类只在真正要 OCR 时才 import，
   否则 `python -m agentflow.cli tools` 会变慢、或在无后端机器上直接失败。

本项目的 linter 里已经有对这条的**显式容忍**（R004 的 `_is_forwarder` 对懒加载宽容）。
⇒ 不改，也不立"禁止函数内 import"的规则（它会先咬到上面这两类正确做法）。

### 6.7 `sys.path` 改写 —— 15 个文件，**报告但不改**

`tests/conftest.py` 已经统一注入 `src/`；另外 14 个文件（`tools/probe_*.py`、
`tools/smoke_*.py`、`src/agentflow/agent_c.py` 的自检入口等）各自插一次。
它们的共同点是**都能独立作为脚本运行**（`python tools/probe_gap_ledger.py`），
不能依赖 conftest。⇒ 不改。**但这是本轮唯一一处"我知道它重复、但收益不值当"的地方**，
如实记在这里。

### 6.8 未使用的 import —— 29 处（区外 21 处），**不改，并给出反例**

审计脚本（AST 级，排除了 `from __future__ import annotations`）报 29 处。
逐条核过之后**决定不动**，理由是一个具体的反例：

> `src/agentflow/tools/attack_tools.py:95`
> `from ..schema import ATTACK_TERMINAL_STATUSES as TERMINAL_STATUSES`
> 在**这个文件内部**没有任何引用 —— 脚本会判它"未使用"。但它是一处**刻意的再导出**：
> `agent_f.py:101` 写 `TERMINAL_STATUSES = AT.TERMINAL_STATUSES`，
> 而 `tests/test_fc05_contract.py:407` 断言 `AT.TERMINAL_STATUSES == S.ATTACK_TERMINAL_STATUSES`
> —— 这正是**单一来源（FC-03）**在代码里的形态。删掉它，那条断言会红，
> 或者更糟：有人会"顺手"在 `agent_f` 里再写一份名单，于是单一来源被拆掉。

这条反例说明：**"未使用 import"在 Python 里不是一个可脚本化的判据**
（还有 import 期自检、`__all__`、类型注解字符串、插件注册等四类正当理由）。
⇒ 不改，也不立规则。要清它需要**逐条人判**，收益是删掉 20 行死代码。

### 6.9 调试残留 —— 795 处 `print`，**逐类看过，不改**

`src/agentflow` 里有 **613 处** `print`（22 个文件）。去掉 `_selftest`/`main` 里的
还剩 300 处 —— 逐条看过，它们是**各模块演示/审计函数的报告输出**

不是调试残留。本项目的自检约定就是"跑一个模块，打印一份可读的报告"。
⇒ 不改。`breakpoint()` / `pdb` / `sys.settrace` 之类**真的**调试残留：**0 处**。

### 6.10 字符串字面量里的装饰 —— 区外 1522 处，**本轮不动（人的待办）**

数字与理由见第 2.2 节。这里补一条**取舍的代价**，因为它不全是"产物"：

`scripts/lint_rules.py`（68 处）与 `scripts/noai_gate.py`（112 处）的 `**`
是**打到终端的消息**，那里确实不会渲染 —— 也就是说，**这两处是真该清的**。
之所以没清，是因为同一类的另两个文件在**禁改区**里：

只清前两个、留下后两个，会得到"四个 CLI 工具两种输出风格"的局面 ——
