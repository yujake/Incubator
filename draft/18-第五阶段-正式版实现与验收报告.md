## 2. 正式版的结构：为什么是现在这个形状

### 2.1 一个主控 + 八个角色，边是**声明**出来的

用户要求"主 Agent 按需唤起 A–H，A–H 也可以互相唤起"。落地成
`capabilities.ALLOWED_EDGES`，**它是一张被导入期断言核过的表**，不是注释：

| 发起 | 可召唤 | 刻意设计的边 |
|---|---|---|
| **M** | A B C D E F G H | 用户可以驱动它召唤任何人 |
| **A** | B | 检索完请 B 整理（A 不自己抽概念） |
| **B** | C | 整理完请 C 看图的形状 |
| **C** | **（空）** | ⚠️ 只读角色，**连"请求"都不直接发** |
| **D** | A B C E F | 研究循环的四个出口 |
| **E** | B D | 引文不可核实→B；发现反例→回 D |
| **F** | A B C D E | 攻坚要能扩张检索面与求证面 |
| **G** | D E F | 写稿时发现缺证据 → 回去要 |
| **H** | **仅 G** | ⚠️ 审校者若能让别人改数据，就同时是发现者与修正者 |

**"没人能召唤主控"**用 `NON_SUMMONABLE` 显式表达，而不是靠
"ALLOWED_EDGES 的值里碰巧没有 M"这个**偶然事实** —— 后者会在有人加一条 `→ M` 的边时
静默失效（那条边会合法化）。

### 2.2 四层分表：**"跑过什么"与"知道了什么"分开**

| 层 | 表 |
|---|---|
| 领域对象 | `research_questions` `attack_plans` `experiments` `documents` `dependencies` `review_findings` |
| 知识 | `literature` `concepts` `relations` |
| **运行记录** | `tasks`（编排台账） `usage_ledger`（token 账） `eval_results`（评测口径） |
| 策略 | 无表；`policy.py` 的判定 + `capabilities.py` 的声明 |

### 2.3 ★ `status` 与 `outcome` 是**正交**的两个轴（本轮最重要的口径决定）

| 轴 | 取值 | 回答的问题 |
|---|---|---|
| `status` | `pending` / `running` / `done` / `cancelled` / `failed` | **跑完了没有** |
| `outcome` | `ok` / `no_result` / `not_applicable` / **`refused`** / `failed` / `cancelled` | **产出了什么** |

**`refused` 是一次成功执行** —— 框架正确地说了"不"。这条口径的直接后果：

- "主控拒绝了这次召唤"必须落一行 `status=done, outcome=refused, refusal_reason=…`，
  **不是**"没有这一行"（没有这一行就分不出"拒绝"与"忘了"）；
- `refusal_reason` 受 `schema.REFUSAL_REASONS` 受控词表约束，
  且 `octet` 规则由 `schema.Task.validate` 机械执行（I-4 的落地）。

## 3. 本轮的关键裁决（逐条，含**为什么不选另一条**）

> 这一节是本报告的主体。每条裁决都写明：**选项**、**选定**、**理由**、**代价**。
> 只写"选了 A"而不写代价的，是没做裁决。

### 3.1 C 的 I3 写入（写 `search_requests`）：**登记为受控例外，不消除**

- **现象**：`AgentC._submit_gap_requests()` 会写 `search_requests`，而 C 是**只读角色**
  （`tools.READ_ONLY_ROLES`，工具面 45 个只读工具、零写工具）。
- **选项**：(a) 登记为受控例外；(b) 把写入上移到编排层（C 只产出候选，由 M 去写）。
- **选定：(a)**。三条理由：
  1. **C 的工具面仍然全量只读** —— `graph.gaps` **刻意不暴露** `submit_requests`，
     所以"C 的推理链不能写任何东西"这条**没有被破**；
  2. **写的是过程记录，不是知识**：三张知识表（`literature`/`concepts`/`relations`）
     **零写入点**，绕过 B 引文回验的风险来自"写知识"，不来自"请求检索"；
  3. **方案 (b) 有实质代价**：I3 的设计意图就是"C 的 `candidate_gaps` **直连** A"，
     上移会**多一跳、多一份失真**，而 C 依然要把它算出来 —— 挪的只是"谁来写这一行"。
- **代价（如实登记）**：`C ∩ A = C ∩ D = {search_requests}` ⇒ **C 与 A/D 不再并发**。
  这是**保守方向**的改变；它被写进了 `test_estimate_write_conflict_disjoint_is_false`
  的正方向断言与 `test_waves_of_keeps_input_order_and_mutual_exclusion` 的期望值。
- **防止"例外变成空白支票"**：`assert_capabilities()` 的断言**只放宽不删除** ——
  从"只读角色的写集必须为空"改成"只读角色的写集必须**只含已登记的受控例外**"。
  删掉那条断言会让这个例外**再也不会被复核**；负控测试
  `test_readonly_exception_is_not_a_blank_cheque` 仍在（给 C 塞一张未登记的表 ⇒ 当场抛）。

### 3.2 ★ FC-19 的 token 账：**`usage_ledger` 是权威账，`tasks.tokens` 由它派生**

- **现象**：主控有一个**进程内**的 `MemoryBudgetTracker`，同时把用量写进 `tasks.tokens/usd`；
  而 FC-19 的 `TokenMeter` 会写 `usage_ledger`。**两套账并存**时
  `verify.py` 的 `usage_task_total_mismatch` 会把 `tasks.tokens` 与 `usage_ledger` 汇总
  对不上报出来 —— 而**两边各自都自洽**。
- **选定**：`usage_ledger`（`TokenMeter.charge`）是**权威账**；
  `MemoryBudgetTracker` 降级为"本次 run 的即时视图"（它只回答"还能不能再召唤"，
  **不再声称是账**）；`tasks.tokens/usd` **由 `TokenMeter` 的返回值写入**。
- **理由**：`usage_ledger` 此前是**零写入方**（表存在、无人写）—— 一张有表无人写的表
  迟早会被当成"没有这个功能"。而"两处各算一遍但愿它们相等"是最坏的形态：
  它们**迟早不相等**，且不相等时**没有任何东西会告诉你是谁错了**。
  改成"由构造保证相等"之后，`usage_task_total_mismatch` 变成一条**恒真**的一致性检查 ——
  它的价值从"发现两边不一致"变成"发现有人又加了一条独立的记账路径"。
- **重试按次计费**：`tokens = (tokens_in + tokens_out) × attempts`。
  这条口径必须落在各 agent 的 `_call` 而不是 `summon` —— 因为**重试发生在 `_call` 内部**，
  只在 `summon` 记账会把 3 次尝试记成 1 次，于是 `retry_overhead()` 恒为 1.0。
- **代价**：`guard()` 必须能**在开工前**拒绝（它是"守卫"不是"审计"）。
  若只做事后记账，超预算的后果是"跑完了才发现超了" —— 那就不是预算，是账单。

本轮 `scripts/lint_rules.py` 从 `error 20 / warning 34` 改到 `error 3 / warning 2 / info 14`
（**最终实测见 §4.2**），**规则一条没删**。改的全是**判据的精确度**：

### 3.4 禁 AI 区（FC-27）在这个环境里**结构上无法验证** —— 于是给它做了 hash 台账

- **现象（实测，不是推测）**：`D:\Incubator\agentflow` **不是 git 仓库**，
  所以 `noai_gate.py --git` **恒为 `unknown(2)`**。而 2026-09-24 这一轮里，
  **13 个禁改区文件全部被 AI 改过**（mtime 07:14–07:53），其中 12 条是本轮改动、
  1 条（`quoteverify.py`）本轮未动。在此之前，**没有任何机器可执行的记录**
  能说明"哪些改动已被 2 名 reviewer 走查过"。
- **门的三种结论本身是对的**（`unknown` 与 `clean` 分得开），但**没有任何东西会因为
  `unknown` 而停下来**。这正是 FC-27 自己援引的那句"测试全绿、上线即越权"的**更安静的形态**：
  **测试全绿、门也在、门查不了。**
- **处置**：`.noai-approvals.json` —— **hash 钉住的批准台账**。
  它比 git 更强的一点是：git 只知道"文件变了"，而 hash 台账能抓到
  **"批准之后又被改了"**（`stale`：台账里那一版的 hash ≠ 磁盘这一版）。
- **"登记"与"批准"是两个动作**：`--baseline` 写 hash（**永远不写 `reviewers`**），
  `--approve` 才追加走查记录，且**先断言 hash 与磁盘一致**（否则你批准的是一个不在盘上的版本）。
- **台账自指禁止**：台账自己也被登记进禁改区（它的理由是"改它等于改审计记录本身"），
  且永远判 `unapproved`（理由码 `ledger_self_approval`）—— 堵的是
  "AI 把自己的改动写进台账并声称已批准"这条路。
- **人读侧**：`NOAI-REVIEW-REGISTER.md` 逐条给出"改了什么 / 复核人该读哪些符号 / 批准栏"，
  并**列出了它自己做不到的五件事**（§5）。

### 3.5 G/H 的升级：**断言解剖学的 12 字段 + H 的 G1–G15 门**

（细节与实测见 `docs/SCHEMA-MIGRATION-PROPOSAL-claims.md` 与 §4。）

**两条最重要的制度**（来自参考体例 `draft/17-…md` §8.4）：

1. **零发现必须自证**：某道门报"零发现"时，报告里**必须**带"我用了什么过程、数出了什么数字"
   （"扫了 37 条断言、15 个引用、0 个未解析"）。**只写"无问题"不合规**。
   这条做成**结构强制**：返回对象里"零发现"与"自证数字"必须同时存在。
2. **报告必须钉住被审版本的 hash**（否则行号/结论会失效），
   且**报告里必须有"我这一轮犯的错"一节，缺失则退回**。

**一处必须由人做的**：给 `documents.claims` 加 12 个字段意味着**改磁盘格式契约**，
而 `schema.py` 在禁改区。所以本轮的做法是：新字段**今天就能写、能读、能过 JSON 往返**
（`Document.validate()` 不拒绝未知键 —— 这一点用测试证明了），
而**存储层的强制**写成
`docs/SCHEMA-MIGRATION-PROPOSAL-claims.md` 交人批准。
理由是 AGENTS.md 那句：**"测试全绿、上线即越权"** —— schema 迁移错在想不到的输入上。

### 3.6 一次**越界改动**的处置：**登记，不回滚**

一个"修工具层缺陷"的子代理改了 `src/agentflow/tools/verify_tools.py`
（它不在该子代理的任务范围内）。处置**不是**回滚 —— 回滚会丢掉一个可能正确的修复，
而它可能已经被别的代码依赖。处置是：
**把它登记进台账、标 `authored: "ai-agent"`、`reviewers: []`，由人决定接受还是重写。**
本项目**不许**用"补一个 `# noqa`"或"补一句注释说它合规"来消掉这类命中 —— 那是共谋。

### 3.7 已接受的缺口**必须继续出现在报告里**

`agent_e.install_e_tools` 与 `agent_f.install_f_tools` 的装配路径**确实没有 roles 校验**。
正确的关法是**把断言下沉到 `ToolRegistry.register*`**（`docs/PROPOSALS.md` 的 P-1），
而 `tools/base.py` 在禁改区。裁决：**继续报 `warning`，不加进豁免名单**。
理由：一个被接受的缺口**必须继续可见**，否则"接受"会伪装成"已修复"，
而下一次发布的人不会再看到它。这与 `unknown ≠ clean` 是同一条纪律。

```text
$ python scripts/lint_rules.py

[linter] error 0 / warning 2 / info 14                            # 退出码 0

[linter] error 0 / warning 40 / info 13                           # 38 条逐模块的 R007 warning
```

**`error` 归零**，而**规则一条没删、豁免一条没加**。最后 3 条 R001 补的都是**具体**理由，
不是空洞的 `# noqa`：

| 位置 | 代码 | 为什么**真的可以忽略** |
|---|---|---|
| `tools/fs_tools.py::_decode_text` | `except UnicodeDecodeError: pass` | 这是**回退链**（utf-8 → gb18030 → 带替换的 utf-8）。UTF-8 解不开不表示"读不出来"，只表示"该换下一个编码试"；真正的失败形态由最后一行如实回报（`had_errors=True`） |
| `tools/fs_tools.py::fs.move` | `except ValueError: pass` | `Path.relative_to` 抛 `ValueError` **只有一种含义：不是子路径 ⇒ 这次移动合法**。它不是"出错了" |
| `tools/graph_tools.py::__main__` | `except Exception: pass`（stdout `reconfigure`） | 切编码失败的唯一后果是中文乱码；而"因为控制台编码问题自检根本没跑成"是更坏的结局（它会把一次真实的判定失败伪装成"没输出"） |

**仍然保留的 2 条 `warning`** 是 `docs/PROPOSALS.md` 的 **G-1**（`agent_e` / `agent_f`
的装配入口确实没有 roles 校验）—— **刻意保留可见**：一个被接受的缺口必须继续出现在报告里，
否则"接受"会伪装成"已修复"。

### 4.2b ⭐ 本轮新增的两道**结构性门**（都在 `release_check.py` 之外，如实说明为什么）

`scripts/release_check.py` 的八项只覆盖"代码跑不跑得对"。而本轮的 objective 里有两条是
**文档/规范**要求 —— 它们同样会**静默退化**，所以也做成了门：

| 门 | 判什么 | 三档退出码 | 为什么不在 `release_check` 里 |
|---|---|---|---|
| **`tools/release_all.py`** | **一键发布检查**：把 `release_check.py` 八项 + **验收测试 P1–P9** + 论文复现（5 实验 + 7 负控）+ 角色规格完整性 + 零测试函数风险分档串成一条命令 | `0` 全 pass / `1` 任一 fail / `2` 有 unknown 且无 fail | 用户点名的"一键发布检查"包含**验收测试**，而 `release_check.py` 的八项**没有**它（见 `PROPOSALS.md` **P-11**）。`release_check.py` 在禁改区，加一项要人审 ⇒ 编排层放在区外 |
| `tools/verify_role_specs.py` | `docs/ROLE-SPECS.md` 的结构完整性：**9 个角色节（A–H + M）× 8 个必备子节**都在，顺序与 `schema.ROLES` 一致，每节标题里能读出**工具条数**（供与普查对账） | `0` 完整 / `1` 有缺失 / `2` **没查成** | 同上（发布门之外的一道并列门；`release_check.py` 加项要人审） |
| （同一套测试里的）**规范 ↔ 门一致性断言** | ① 每条 lint 规则都挂进了 `RULES` 且编号连续无洞；② 每条规则都在 `DEVELOPMENT.md` §6 出现过；③ **反向**：§6 里写的 `R0NN` 编号必须真的有对应规则 | 作为 `tests/test_lint_rules.py` 里的三条断言 | 它就是测试，不是独立脚本 |
| （同一套测试里的）**逐个工具的契约覆盖** | 装配出来的**每一个**（55 个）工具都必须在 `ROLE-SPECS.md` 里有契约行；且 §R0 标题里的**总数** == 实时装配数 | 作为 `tests/test_role_specs_complete.py` 的两条断言 | 同上 |

**`release_all.py` 的两条刻意取舍**（改它们等于改门的强度，所以它**自身已登记进禁改区**）：

1. **`--skip` 掉的步骤记成 `unknown`，不是 `pass`** —— 否则 `--skip acceptance`
   就成了"发布门全绿"的捷径；
2. **超时 / 起不来 ⇒ `unknown`，且 `timed_out` 必须先于退出码判断** ——
   Windows 上被强杀的进程退出码常是 1，与"检查发现问题"的 1 **无法区分**。

> **一次真事（记在案，因为它就是"测试抓到我自己的缺陷"）**：`release_all.py` 的第一版把
> "未知步骤 key"的校验写成 `bad = (skip | (keys - only)) - keys` —— 于是
> **`--only lin`（打错一个字母）算出来的"跳过集"正好是整个 `keys`，`bad` 为空**，
> 脚本静默地什么都没跑然后退出码 2。退出码凑巧是对的，**理由却是错的**；
> 而如果哪天有人把跳过记成 `pass`，这个拼写错误就会变成一次"全绿的空跑"。
> 是 `tests/test_release_all.py::test_cli_unknown_step_key_is_rejected_with_exit_two`
> 把它抓出来的。判据必须打在**用户输入**上，不是打在派生结果上。

**角色规格那道门立刻赚回了它的成本**：第一次跑就抓到一处真实缺口 ——
`§C.4 工具面 —— **两层**` **没写工具条数**，于是"逐个工具的契约"这一节无法与

**这次实跑当场抓到了编排层自己的一个真缺陷**（值得单列，因为它就是本项目的核心教训）：

| 现象 | `release-check` 的 `exit=2` 被编排层判成了 **`fail`** |
|---|---|
| 根因 | `classify()` 把所有非零退出码一律当"发现问题"，而 `release_check.py` **自带三态**：`0=pass / 1=fail / 2=unknown`。本环境里它的第 6 项**必然**返回 `unknown`（不是 git 仓库） |
| 后果 | **"没查成"被读成了"发现问题"** —— 而且发生在**"用来挡住这类错误的那一层"**里 |
| 修法 | 每一步**显式声明自己的退出码表**（`TRI_STATE_EXIT` / `PLAIN_EXIT`），四条自带三态的工具用前者；并配 4 条测试（含"三态步骤的 2 ⇒ `unknown` 而不是 `fail`"这条点名的负控） |

**这是本轮第二次由"真跑"而不是由"读代码"发现的自身缺陷**（第一次是 `--only lin` 打错一个字母
被静默接受，由单元测试发现）。两条都写进了代码注释。

**逐项解释为什么是这三个非绿**（**都不是"门坏了"；最终一次实跑：`pass=6 fail=1 unknown=1`**）：

### 6.4 一条必须单独说的：**"三个绿灯叠加仍然不能证明系统有用"**

离线 `demo` 全绿 + 千条测试全绿 + 真实数据 `verify --deep` 零错误零警告 ——
**三者叠加仍然只证明它自洽**。不变量检查的是"结构自洽"，
它**不检查也无法检查**"这个概念名是不是一个概念"、"这条断言在数学上对不对"。
本轮新增的 G1–G15 门把"稿件有没有把自己说清楚"这件事推到更严，
但 **H 依然不能发现数学错误** —— 一个声称"我检查了证明"的自动审校器比没有审校器更危险。

### 7.2 ⭐ 这一轮新长出来的六条经验（每条都带实证）

#### 经验 1：**门必须在真实样本上量过假阳性率才能上** —— 否则第一次运行就失去可信度

`scripts/lint_rules.py` 的八条规则在这一轮被**校准了五次**，**规则一条没删**，
改的全是判据的精确度。数字：

| 规则 | 第一次在真实代码上运行的假阳性 | 校准方式 |
|---|---|---|
| R001 | 29 个 error 里 **22 个是刻意且带注释**的设计决定 | 只有**没有解释**的吞掉才算违规 |
| R002 | `_literature_rows` 的 `return [], "未配置 store（不是表坏了）"` —— 这**恰恰是三态纪律的正确写法** | 关键词判据之外加**结构**判据：伴生值非 `None` ⇒ 不算折叠 |
| R003 | 转发体里的一条**惰性 import** 被判成"两份独立实现" | 剥掉前导 import 并把别名解析回同名 |
| R004 | **四次**：自检脚手架（17 处里大多数）、**docstring 里提到** `ToolRegistry(` 被当成真的构造、命中点在嵌套小工具而祖先才是自检、`install_h_tools` 先跑了 `build_registry` 却被判绕过 | 改用 AST 找**真实 `Call` 节点**；按**整条嵌套链**判脚手架；已登记的校验器/装配入口即算已校验；其余要求逐点登记并写理由 |
| R005 | 第一版判据命中 **6 处全合法**的模块级子集声明 | 收紧为"≥6 个不同角色字母"（即它在试图枚举全部角色） |

结果：`error 20 → 3`、`warning 34 → 2`。
**关键不是数字降了，而是"每一条降下来的都是假阳性，不是被豁免的真缺陷"** ——
唯一刻意保留的两条 warning（`agent_e` / `agent_f` 缺 roles 校验）写进了
`docs/PROPOSALS.md` 的 **G-1**，并明确要求"**被接受的缺口必须继续出现在报告里**"。

#### 经验 2：**"写了但没人读"比"没写"更坏** —— 因为它看起来是做了

本轮抓到三种同族形态：

1. **`agent_a` 的退避租约**：失败分支写 `lease_until = now + backoff` 并把 `claimed_by` 置空，
   而 `_claim` 的跳过判据**同时**要求 `claimed_by` 非空 ⇒ **那条租约永远不会被读到**，
   同一实例立刻重打同一条 API。docstring 甚至写着"那条租约正是靠这个分桶生效的"（**这句是错的**）。
   **本轮已修**，而且修的过程本身给出了 §7.2 经验 3 的最尖锐证据：
   模块自检当时断言的是"**租约被写入了**"，那个缺陷对它是完全盲的；
   把缺陷改回去时**旧检查仍然 PASS**，只有新增的"**写了且被遵守**"检查变红。
   修复还顺带分出了一档新的 `skipped_reason="pending_requests_all_in_backoff"` ——
   "全被别人持着"与"全在退避中"是两件事，压成一个值就是在诊断信息里说谎。
2. **`usage_ledger` 是一张有表无人写的表**：接线前 `grep 'usage_ledger\|UsageEntry' agent_*.py` **零命中**。
   一张没人写的表迟早会被当成"没有这个功能"。（**本轮已接**：`conductor._charge_and_settle`
   → `TokenMeter.charge`，且 `tasks.tokens` 由 `tokens_for()` 抄回 —— 于是**"读的人"与"写的人"
   是同一个判据的两端**。逐次尝试粒度仍未接，见 §6.1 第 1 条。）
3. **H 的 `writers=` 注入参数零校验**：`tools=` 有 fail-closed 断言，而 `writers=` 完全没有 ——
   "落点被钉死"只剩一句注释。（**本轮已修**：按副作用等级内联 fail-closed 断言，
   `_H_WRITABLE_TOOLS` 逐个点名。）

**共同点**：三者都能通过"我看过代码，它写了"的检查。**只有"有没有人读"才是判据。**

#### 经验 3：**断言错对象** —— 一条"永远为真"的测试比没有测试更危险

最尖锐的一例：`agent_a` 的模块自检断言的是
`bool(r3["lease_until"]) and r3["claimed_by"] is None` —— 即"**租约被写入了**"。
它对本轮那个缺陷**完全盲**。修复时把它升级成"**写了且被遵守**"（再跑一次 `_claim()` 领不到、
`attempts` 不增），并且变异试验直接证明了这一点：把缺陷改回去时，
**旧检查仍然 PASS**，只有新检查 RED。

同族还有：`tests/test_tools_table_fs.py` 断言空表得 `"r-0000"` ——
它编码的是"取最小可用号"语义，而那个语义会**复用已删行的号**，
让 `literature.source_request_ids` 的溯源**静默指向另一条请求**（比崩溃危险）。
这条断言被改成 `"r-0001"`，并在 docstring 里写明"这是修正编码错误行为的断言，
**不是**放宽断言掩盖失败"。

#### 经验 4：**同一判据多处实现必然漂移** —— 本轮抓到 **7 组**

| # | 判据 | 两/三处 | 漂移的实际后果 |
|---:|---|---|---|
| 1 | `slugify` | `textutil` vs `fetch` | 中文标题整块消失（`'…群论'` → `'…'`） |
| 2 | `normalize_doi` | `dedup` vs `providers` | **同一篇论文两个主键** ⇒ 判成两篇，无报错 |
| 3 | `r-NNNN` 取号 | `table_tools` / `research_tools` / `interactions` | 空表分歧 `r-0000` vs `r-0001`；**复用已删号** ⇒ 溯源指错 |
| 4 | tasks 台账审计 | `conductor.verify_tasks` vs `verify.py` | 两份实现，判据可能分叉（已收敛为唯一实现 + 一致性测试） |
| 5 | 引用解析 | `verify.py` vs `doc_tools.citation_ref_parts` | G 认为合法 / verify 认为悬空（登记为 **P-5**） |
| 6 | 角色名单 | `cli.py` 的 argparse `choices` 写死 A–D | `cli tools --role E` 被拒；**命令一边说"工具总数 55"、一边只列 4 个角色** |
| 7 | 前端重复校验 | `tools/base.py::for_role`（实现）vs `tools/__init__.py::READ_ONLY_ROLES`（声明） | 清单自己要求"两者必须**同时**人审" —— 这是**刻意**保留的两处，不是漂移 |

**可判定的处置形式**只有两种：**改成转发**，或**加一致性测试** +
在那条测试的 docstring 里写明"两处必须同时改"。
**"写一句注释说两处应该一致"不算处置** —— 那正是这条经验要防的形态。

#### 经验 5：**多 agent 并发写同一个工作区，代价是真实的、可实测的**

本轮 10 个子代理并行工作，实测到的代价（**全部记在案，因为它们才是"协同框架"这个词的真实含义**）：

| 现象 | 实例 |
|---|---|
| **全量测试的红点每次都不同** | 同一个 commit 状态，四个子代理各跑一次得到：`1090 passed` → `12 failed` → `1 failed` → `3 failed, 1137 passed`。**单文件复跑全绿** |
| **踩到别人的半成品** | `tools/trace_tools.py` 一度 `SyntaxError: unmatched ')'` ⇒ 整个套件**无法收集** |
| **测试名在两次运行之间被改掉** | `python -m pytest "tests/…::test_scan_document_checks_match_scan_claim_both_ways"` 报 **`ERROR: not found`** |
| **行号在几十分钟内漂移** | `dedup.normalize_doi` 26→44；`tools/base.for_role` 310→335；`schema.TABLES` 1525→1632 ⇒ `.noai-paths` 的理由**改用符号名** |
| **"登记"本身也会过期** | `NOAI-REVIEW-REGISTER.md` 写完 24 分钟后，`tools/verify_tools.py` 又被改了一次（mtime 07:35 → 07:59:55） |
| **一次越界改动** | 一个"修工具层缺陷"的子代理改了不在它范围内的 `tools/verify_tools.py` |

**处置（这一条是本轮最有复用价值的产出）**：
对着**基线快照**判定（"基线 33 个测试文件 + 我的新文件 = 675 passed"），
而**不是**对着瞬时全量判定。每个子代理都被要求报告"我开工时的基线"与"完工时的实测"，
并且**任何归因都必须用隔离复跑证明**（"单文件跑绿 + 与我的文件同跑也绿"）。

#### 经验 6：**在非 git 仓库里，禁改区门结构上无法验证** —— 于是给它做了 hash 台账

见 §3.4 与 §4.5。一句话：**mtime 只能看出"变过"，hash 才能指出"你批准的那一版
与盘上这一版不是同一版"**。而台账自己也被登记进禁改区（**台账不能批准自己**），
否则"AI 把自己的改动写进台账并声称已批准"就是一条通畅的路。

### 7.3 一条反过来的经验：**"没人拥有"不等于"不是缺陷"**

本轮有两个文件的缺陷**在本轮任何实现者的所有权清单之外**，于是它们在两轮审计里
被两边都跳过：`attack_tools.py`（失败类型被压平 + 2 条声明漂移）与
`graph_tools.py`（`StoreError` 逃逸 + `returns=` 漂移 + 不可截断的 `neighbors`）。
我把它们登记成 **G-2 / G-3**，而不是让它们消失在某次汇报的措辞里；
本轮派工关闭，**两条都已修完**（见 §6.1 第 4/5 条）。

**这条经验的形态是**：分工清单**本身就是一张会漏东西的表**，
所以必须有一个地方收"没有归属的已知缺陷"。

### 7.4 ⭐ 第七条经验：**评审者的诊断本身也会错** —— 而且错得很有规律

用户最初的要求里就写着这一条（`DEVELOPMENT.md` §7.3：
"**实现者必须用证据反驳评审者**"）。本轮它**真的发生了两次**，都在我写的 G-2/G-3 简报里：

| 我的诊断 | 实测 | 实现者的处置 |
|---|---|---|
| "`PlanError` / schema 的 `ValueError` 会逃成 `kind="unexpected"`" | 它们**没有**逃 —— `agent_f.PlanError` 早已继承 `ToolError`，schema 的 `ValueError` 也已被包成 `PlanError`；**只有 `StoreError` 真的逃了** | **没有照字面改**，而是按真实根因（"**具体失败类型被压进笼统的 `tool_error`**"）修，并在报告里**明确写出"我没有谎称它逃过"** |
| "`graph.neighbors` / **`graph.concepts`** 的 `returns=` 不一致" | **`graph.concepts` 这个工具根本不存在**（`register` 只注册 4 个） | **没有为了对上简报而凭空造一个工具**；逐条核对后反而核出**第三处真实漂移**（`graph.relations_between` 漏 5 个键） |
| "36 处 `returns=` 全都能机器化" | **7 个**的 `data` 是**标量或行对象**（`table.count` 是 `int`、`table.get` 是"行对象，形状由表 schema 决定"）—— **硬编键就是造假** | 做成**显式豁免清单**（7 条，理由写在声明字符串**本身**里），并**主动报出"所以实际覆盖是 48/55 而不是 55/55"** |
| （我给的合规样例）"顶层键即可" | 仓库既有的合规声明**含嵌套键**（`graph.neighbors` 的 `neighbors[]` 内字段）⇒ 子集判据必须**递归**取键，否则 4 个**本来就对**的声明会假红 | 先按顶层实现，**实测那 4 个真的红了**，才改成递归 |
| （我未声明的判据边界） | 这条判据**只抓"声明了却没给"**，**抓不到"给了却没声明"** | 用变异 M4 证明它仍 GREEN，并**主动指出**"它不能支撑『docstring 与实现完全一致』这个更强的结论"，把范围写进测试常量

**为什么这一条值得单列**：这两处如果被"照着简报修"，会产生两种典型的坏结果 ——
① 为了让"它逃成 `unexpected`"这句话成真，去**故意去掉**已有的 `ToolError` 收编；
② 为了对上"`graph.concepts` 有漂移"，**凭空造一个工具**。
两者都会让代码**朝着简报的错误方向**走，而且**测试会跟着一起错** ——
因为测试是实现者写的，它会忠实地把那个错误方向钉住。

**更值得记的是第三处发现（由实现者顺着"为什么漂移没被抓到"挖出来的）**：
`returns=` 的"声明 vs 实现"判据的正则**只抓单引号键**，于是不带引号的 `returns=`
被抽成**空集**，而 `declared - actual == {}` **永远成立** ——
**这条判据在 36 / 55 个工具（65%）上从来没有真正执行过**（见 `PROPOSALS.md` **G-4**）。
它再一次证明：**审计的对象不只是工具，还包括"检查工具的那些判据"。**

**同一枚硬币的另一面（必须一起记）**：实现者的报告里也有**一条错诊断**。
它把 `attack.check_budget` 的
`f"预算完整：{ {k: budget[k] for k in _REQUIRED_BUDGET_KEYS} }"`
报成"打印了整个 budget 字典"。**主控实测（一条命令）证明它打印的正好是那四个必需键** ——
f-string 里外层花括号是替换字段、内层是 dict 推导式。已登记为 `PROPOSALS.md` 的 **N-3**
并附上那条命令作为判据。

**所以这条经验要对称地写**：**评审者与实现者都会诊错**；
唯一的判据是**一条能重跑的命令的输出**，不是任何人的转述 —— 无论那个人是主控还是子代理。
否则"照着错误诊断修"会同时污染代码与其测试。

### 7.5 第八条经验：**同一个表面语法承载两套命名空间** —— 撞号与"批量替换改错指针"

本轮**同一个根因**以三种形态各出现了一次，而且**都是我造成的**：

| 形态 | 具体 | 为什么它不会自己报错 |
|---|---|---|
| **编号撞号** | 两条并发新增的登记项都被写成 **`G-9`**（一条讲 `criterion_revision`，一条讲 106 个零测试函数），而其中一条的号**已被测试文件引用** ⇒ "`G-9` 指哪一条"在那一刻没有答案 | `PROPOSALS.md` 里两条都写着 `## G-9`，**看起来完全正常** |
| **悬空引用** | 一份测试的 docstring 写着"已登记进 `docs/PROPOSALS.md` 的 **G-5** 条"，而 `G-5` **当时不存在**（编号从 G-4 跳到了 G-6） | 引用是一条自由的字符串，**没有任何东西校验它指向的东西存在** |
| **批量替换改错指针** | 我用一次全文件 `§8.5 → §8.6` 的替换给 `DEVELOPMENT.md` 重新编号，结果把 `docs/ROLE-SPECS.md` 里指向**另一份文档**（`draft/13`）的 `§8.5` 也一起改了 ⇒ 那些指针从"`last_tool_errors` 惰性创建"**静默转向**"`_deploy_e` 没有降级路径" | `§8.5` 这个**表面语法**在两份文档里都有意义，替换工具**不可能知道**哪一处是哪个命名空间 |

**三种形态的共同点**：**表面上是同一串字符，实际属于两套互不相干的命名空间**
（PROPOSALS 的条目号 vs 角色动作表里的 `| G-5 |`；`DEVELOPMENT.md` 的 §8.5 vs `draft/13` 的 §8.5）。
**而它们全都不会自己报错。**

**处置**：新建 `tests/test_proposals_register.py` 把前两种变成红点 ——
① 编号唯一；② **提到 PROPOSALS 的地方**引用的每个编号必须真的存在
（⚠️ 判据**必须有作用域**：第一版没有"提到 PROPOSALS"这个限定，`ROLE-SPECS.md` 里的角色动作表
`| G-5 |` 立刻假红 —— **过严的门和过松的门一样有害**）；
③ 编号空洞必须写明"留空、不要复用"。
第三种（跨文档指针）**没有机械门**，只能靠"替换时限定作用域"这条纪律 —— 它已写进本报告。
