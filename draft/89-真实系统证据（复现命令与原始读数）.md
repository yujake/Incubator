## §5 被证据**修正**的三条断言（这是本附录最值钱的部分）

### 5.1 `input_key` 不是空的、也不只是幂等键 —— 它是 `<动作>@<12 位指纹>`（2276/2276）

原始读数（采样 + 形态分布）：

```text
input_key 形态分布: word=2274  top:=2
样本:
  t-0001 [G.revise] input_key='revise@4b9122efd0dc'
  t-0003 [G.build_document] input_key='build_document@4dca7cff5098'
  t-0007 [A.run_once] input_key='run_once@4213853de372'
  t-0008 [B.run_once] input_key='run_once@4213853de372'
```

**修正了什么**：`draft/86` §10 的 U2 曾提议"开项时把 `input_key` 当 `item:<id>` 用"。
证据说明这**不能做**：`input_key` 在真机上是**每次派活自动生成的"动作 + 参数指纹"**
（2274/2276 是这个形态，只有 2 行是 `consume:`），而 `Decision.key = (role, action, input_key)`
正是**循环判定的键**（`policy.check` 第 [4] 步：同一 key 出现在祖先链上 ⇒ `cycle_detected`）。
占掉它 = 拿掉循环判据 + 抹掉幂等指纹。
⇒ **A1=甲 的收益比原先记的更大**：它让 `item_id` 直接等于 `task_id`，从而**根本不需要碰 `input_key`**。
（此条已回改 `draft/86` §10 U2 与 §11.5 的 D86 行。）

### 5.2 "92 行全是框架派生" —— 精确分解是 **967（据动作结果）+ 593（据派活）+ 2（空 note）= 1562**

**修正了什么**：原稿只说"全框架派生、0 自撰"，但没有说清**它们分成两条路**，
而这两条路对 `task_id` 的处理**正相反**（一条 967/967 带，一条 0/593 带）。
这个分解让 D77/T14 的修法从"可能"变成"**只差两个实参**"（证据链：note 文本 → 代码行 → 该行有没有 `task_id`）。

### 5.3 老 `tasks` 行**全是终态**（done 2196 / failed 80，没有 pending/running）

**修正了什么**：原稿担心"加列之后老行还处在中间态怎么办"。真机读数说**没有这种情况**
⇒ 迁移风险比原先评估的低一档：加列之后老行一律 `kind==""`，既不进板、也没有"半途的板项"要接管。

### 5.4 `tasks` 行有**三个模块**在写，不只 `conductor`（修正 `draft/86` §2.1 的一句断言）

```powershell
Select-String -Path D:\Incubator\agentflow\src\**\*.py -Pattern 'upsert\("tasks"|write_new_row\('
```

```text

conductor.py:831   tx.upsert("tasks", ordered, note=note)      ← 同上（带键序归一那条路）
```

**修正了什么**：`draft/86` §2.1 我写过"一行 `tasks` 的写入路径在 `conductor` 里**只有一条**"
—— 这句**不准确**：`conductor` 内部确实只有 `_write_new_row` 那一处新建 + 两处就地更新，
但**另外两个模块（`projects.py` / `runflow.py`）也直接写 `tasks` 行**（老管线，
与前面审计记的"两套入口、只有一套开 tasks 行"同源）。

**对设计的含义（写进 `draft/86`）**：

1. 板读侧必须**只认 `kind != ""`** 的行 —— 老管线写出来的行不设 `kind`（缺省 `""`）⇒ 天然不进板；
2. 由此多一条**判据**：凡**不经过** `_open_item` 的 `tasks` 写入（`projects.py` / `runflow.py` /
   任何新路径）⇒ 写出来的行 `kind` **必须为空**；负控：手工给一行老管线的行塞 `kind` ⇒ 判据红
   （否则"老管线的行"会混进板，"板上还挂着什么"从此不可信）；
3. `runflow` / `projects` 属于"旧机制"，本批**不改它们**（改了会动 T1 的历史基线）——
   上面的判据正是"不改它们也不出事"的机器保证。

```text
"conductor.state": {},                    # ← 夹具里真调，键集与 returns= 比对
"conductor.stop": {}, "conductor.resume_brief": {}, "conductor.cancel": {},
"conductor.ledger": {"view": "stats"}, …  # 每个工具一行
```

**⇒ 对 S1 的三条硬约束（之前只写了"会动金标"，其实还动这里）**：

1. `conductor.state` 若加 `board` 一格 ⇒ **必须同笔改它的 `returns=` 声明**，否则那条判据红；
2. 新工具 `conductor.board` / `manuscripts.items` / `manuscripts.ack` ⇒
   **各要一行 `observations` 夹具**（真跑一次，键集才会被比对）+ 各自的 `returns=` 声明；
3. 新增的三件工具要进 `EXECUTED_KEY_SOURCE`（它们是"真跑出来的"那一档），
   否则那条"键名来源可核"的判据会把它们算成缺登记。
