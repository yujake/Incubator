## 0. 摘要（先读这段）

DSH 的权限控制**不是**把「工作区 / 写权限 / 工具集」三件事塞进一个配置文件，而是拆成四个**互相正交、各自有独立归属方**的机制：

| 机制 | 归属包 | 你调的旋钮 |
|---|---|---|
| 工作区根（workspace root） | `dsh-sandbox-policy`（+ 会话不可变 `SessionHeader.cwd`） | `workspaceRoot` 配置 + 会话 cwd |
| 文件沙箱模式 | `dsh-sandbox-policy` → 消费方 `dsh-fs-sandbox` / `dsh-bash-sandbox` / `dsh-pwsh-sandbox` | `mode` = `read-only` \| `workspace-write` \| `danger-full-access` |
| 审批策略 | `dsh-user-approval` | `policy` = `ask` \| `never` |
| 工具栏（工具集） | `dsh-tools` 注册表 + `dsh-agent-presets` 预设挂载 | 预设 YAML 里逐行 `disabled` / `insert` / `config` |

**最关键的一条架构事实**：在 `web` profile 下，**工具、prompt 段落、skill 都不属于 host 组合树**，而被下移到「agent preset」（预设）这一层。host 树只保留**注册表本身、沙箱与审批栈、持久化、模型路由**。

证据：`C:\Users\ysc20\.dsh\profiles\node_modules\@deepseek-ai\dsh-web-app\cordis.patch.yml`（第 351–484 行）——该文件把 `tool-bash`、`tool-fs`、`tool-skill`、`tool-web`、`tool-todo`、`agent-instructions`、`tool-subagent*`、`tool-workflow`、`tool-ralph`、`plan-mode`、`compaction-basic` 等**全部 `disabled: true`**，注释原文：「The agent plane moves behind agent presets… The Web surface disables them here and lets each session mount a preset instead.」

**这条结论现已升级为官方设计依据**（不再只是 grep 归纳）——官方 Agent Note `2026-08-10-host-plane-ownership-after-presets.zh.md` 给出了**明文判据**：
> 「**当一个单元的空值与真实值无法区分时，只要它注册进的那张表是进程级的，它就不能是逐组装的。**」
详见 §2.3「官方给出的『什么属于 host 平面』判据」。

**第二个最关键的事实**：**「插件默认值安全」不等于「部署默认值安全」**。`dsh-sandbox-policy` 自身默认是故障安全的 `read-only`，但随附 bundle 把它覆盖成两个相反的值——
- `dsh-base`（web/headless/sdk/acp 的底座）→ `workspace-write`
- **`dsh-sdk-minimal`（独立树，不叠 base）→ 写死 `danger-full-access`，且完全没有审批插件、没有文件工具**——它唯一的能力是**不受约束的持久 shell**。

→ **永远用 `dsh --profile <n> --dump-config` 核实实际生效值**，不要读插件 README 猜。（证据见 §2.2b；这是本报告发现的最严重的「看起来像轻量 SDK、实际是全开」陷阱。）

因此 **DSH 里「精细设定工具栏」的正确姿势 = 写一个自定义 agent preset**，而不是改 host 配置。本报告第 4、5、6 章给出可直接照抄的模板，并以本机真实存在的用户自定义预设 `math-research` 作为完整实例（附录 C）。

**本会话自身的配置事实**（可作为机制生效的活体证据，见本会话 runtime context 与系统提示词）：
- file policy = `workspace-write`
- 工作区 = `D:\Incubator`
- 观察到的拒绝标记：`[sandbox: file access denied under <mode> mode]`
- 本会话（作为**被委派的子智能体**）被授予的运行时上下文里包含一句：`Approval prompts are disabled in this session: actions that require approval are rejected automatically — do not request sandbox escalation (do not set sandbox_permissions).`
  —— 这两句与 `dsh-user-approval` README 中 `never` 策略的贡献文本**逐字一致**（证据：`...\@deepseek-ai\dsh-user-approval\README.zh.md`，「Never 策略贡献」代码块 + 官方子系统文档 `docs/subsystems/approval.zh.md`），因此可确认**本子会话的 approval policy = `never`**。

> **⚠️ 层级归属（本报告第一版写错过，此处更正）**：`never` 是**子会话**的取值，**父会话（顶层会话）是 `ask`**。这不是矛盾，而是**同一次运行、同一个策略继承机制在两个层级上的两个取值**：
> - 父会话 runtime context：`Approval policy: ask. Operations that require approval may ask through the configured answerers; without an available answerer, the request fails closed.`
> - 子会话 runtime context：`Approval prompts are disabled in this session: …`
>
> 原因是 `dsh-subagent\lib\types\child-agent.d.ts` 的 `captureDelegatedPolicyOverrides` 把子 agent 审批**无条件钉死为 `'never'`**。
> **这构成了 §4.7「子 agent 不能比父权限更大」的一次同进程、同运行的一手对照实验**，详见 **§4.7.1**。

## 1. 概念模型

### 1.1 五个正交概念

#### (1) 工作区（workspace）

DSH 里「工作区」有**三层含义**，务必区分，混用会导致「我明明配了路径却还是能写到别处」这类事故：

| 层次 | 语义 | 证据 |
|---|---|---|
| **会话工作目录 `cwd`** | 会话创建时写入的**不可变** `SessionHeader.cwd`；它是路径解析的默认基准，也是 `workspace-write` 的写入边界 | `...\dsh-sandbox-policy\README.zh.md`：「会话的不可变 `cwd` 先按文件系统语义规范化，再成为工作区根目录」 |
| **回退工作区根 `workspaceRoot`** | 仅用于**无 agent 调用或没有 cwd 的会话**；普通 agent 调用不使用它 | 同上：「无 agent 调用或没有 cwd 的会话在 `workspace-write` 下可写入的回退根目录；普通 agent 调用改用会话的不可变 cwd」 |
| **Workspace 项目注册表** | GUI 侧边栏的「项目」分组（命名目录 + 会话列表），**对模型完全不可见**、零 token | `...\dsh-workspace\README.zh.md`：「它对模型不可见，不增加任何提示词或请求上下文成本」 |

CLI 层：**「运行命令时所在的目录将作为默认 workspace 根目录」**——证据：`C:\Users\ysc20\AppData\Roaming\npm\node_modules\@deepseek-ai\dsh\README.zh.md`（「Profile」上一段）。

本机示例（GUI 项目注册表实存数据，脱敏无涉）：证据 `C:\Users\ysc20\.dsh\storages\workspace.json` 记录两个项目 `C:\Users\ysc20\Desktop\投影度量论` 与 `D:\Incubator`，后者 `sessionIds` 含本会话 id `session-9e5ec71f-…`。

**关键限制（务必记住）**：`SandboxExecutionPolicy` **每个会话只有一个工作区根**。证据：`...\dsh-sandbox-policy\README.zh.md`「已知限制」第 1 条：「**每个会话只有一个主要工作区根目录**——策略解析 `SessionHeader.cwd`；额外可写根目录不属于 `SandboxExecutionPolicy`。」另见类型定义 `...\dsh-sandbox\lib\types\index.d.ts`：`SandboxExecutionPolicy` 只有 `mode`、`workspaceRoot`、`sessionId?` 三个字段，**没有 `additionalDirectories` / `writableRoots` 之类数组**。

> **【推断】** 这意味着 DSH **当前版本没有** Claude Code 那种 `additionalDirectories` / Codex 那种 `writable_roots` 的「多可写根」能力。「只允许改某几个目录」（不含 cwd）在 DSH 里**不能直接表达**。可行的等价手段见第 6.3 节（把 cwd 设到这些目录的公共父目录 + 用工具白名单/guard 收敛，或改用 MCP/自定义工具），但这**不是**内核级保证。

#### (2) 权限（读 / 写 / 执行 / 网络）

DSH 的沙箱模式**只管文件写效果（file-effect）**，这是被反复强调的边界：

- 证据：`...\dsh-sandbox\lib\types\index.d.ts` 对 `SandboxMode` 的 JSDoc：「File-effect policy for confined processes… **Network and process visibility are outside this vocabulary.**」
- 证据：`...\dsh-sandbox-policy\README.zh.md`「已知限制」第 2 条：「**仅限文件操作模式**——`SandboxMode` 管控文件操作；网络和进程策略不在其词汇中，因此这里没有限制它们的旋钮。」
- 证据：`...\dsh-bash-sandbox\README.zh.md`「已知限制」第 1 条：「**限制只覆盖文件影响**——不提供网络限制和统一的进程可见性保证，因此这些模式不是通用安全沙箱。」

更狠的一条：**沙箱只做写侧交叉检查，读侧不设防**。证据：`...\dsh-sandbox-windows-acl\README.zh.md`「已验证边界」：「**写入受限；读取、网络与进程可见性不受限。** `WRITE_RESTRICTED` 只交叉检查写访问，因此受限子进程可以读取调用者可读的任何文件并打开套接字；`read-only` 因而需要读侧策略才能表达。」

| 能力 | DSH 沙箱是否管辖 | 说明 |
|---|---|---|
| 文件**写** | ✅ 管辖 | `read-only` 全拒；`workspace-write` 限工作区 + 平台临时区 |
| 文件**读** | ❌ 不管辖 | 完全由调用者身份权限决定 |
| 进程**执行** | ⚠️ 部分 | 命令本身能跑，但被 wrap 进受限 runner；进程可见性因后端而异 |
| **网络** | ❌ 不管辖 | `bash` 工具描述里那句「Network access depends on the task environment」就是这个意思（证据：`...\dsh-agent-presets\presets\minimal\agent.cordis.yml` 第 44 行） |

#### (3) 沙箱模式分级

只有三个值，**闭集合**：

```ts
// 证据：...\dsh-sandbox\lib\types\index.d.ts
export type SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access';
```

| 模式 | 文件效果 | 证据 |
|---|---|---|
| `read-only` | 任何位置都不可写；`/dev` 中仅 `/dev/null` 可写（`>/dev/null` 仍可用） | `...\dsh-bash-sandbox\README.zh.md` 模式表 |
| `workspace-write` | 只能写**策略的工作区根** + **平台临时区** | 同上；可写根集合的唯一定义见 `...\dsh-sandbox\lib\types\roots.d.ts` |
| `danger-full-access` | 不限制；**绝不咨询提供方**（完全绕过 `ctx.sandbox`） | `...\dsh-bash-sandbox\README.zh.md`；`...\dsh-sandbox\lib\types\index.d.ts` 的 `ConfinedSandboxMode = Exclude<SandboxMode, 'danger-full-access'>` |

`workspace-write` 的可写根**唯一定义处**（这是防止「文件工具写不了 /tmp 但 bash 能写」这类不对称的设计）：

```ts
// 证据：...\dsh-sandbox\lib\types\roots.d.ts
/**
 * The roots one confined execution may WRITE under — the mode's meaning as a
 * canonical, deduplicated allow-list. `read-only` allows nothing;
 * `workspace-write` allows the policy's workspace root, the host `/tmp`, and
 * the per-user platform temp dir (`os.tmpdir()`)…
 */
export declare function writableRoots(policy: SandboxExecutionPolicy): string[];
```

**故障安全默认值是 `read-only`**，不是 `workspace-write`。证据：`...\dsh-sandbox-policy\README.zh.md`「最小配置」：「用默认模式加载本包；故障安全默认值是 `read-only`，想要可写工作区 agent 的部署需要显式选择 `workspace-write`。」

**但这个「故障安全默认值」在两个随附组合包里都被覆盖了，且方向相反**：
| 组合包 | 实际 `mode` | 证据 |
|---|---|---|
| `dsh-base`（web/headless/sdk/acp 的底座） | `!!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'` | `...\dsh-base\cordis.patch.yml` 第 208–212 行 |
| `dsh-sdk-minimal`（独立树，不叠 base） | **写死 `danger-full-access`** | `D:\Incubator\temp\evidence\bundle-layers\dsh-sdk-minimal.cordis.patch.yml` 第 41–45 行 |

→ **「插件默认值安全」不等于「部署默认值安全」。** 详见第 2.2b 节。

#### (4) 审批策略（approval）

只有两个值，**闭集合**：`ask` \| `never`。证据：`...\dsh-user-approval\README.zh.md`「设置策略」表：`policy` 默认值 `ask`。

| 策略 | 行为 | 证据 |
|---|---|---|
| `ask` | 每个请求发给「应答者」（answerer）；**应答者缺失或失败 → `unavailable` → 以拒绝方式关闭（fail-closed）** | `...\dsh-user-approval\README.zh.md`「组合应答者」 |
| `never` | 在交互式分发**之前**确定性地拒绝每个请求；之后以 `prepend` 注册的监听器也无法绕过 | 同上「分发」：「`never` 策略在服务内部、waterfall 分发之前执行」 |

三条硬限制（决定了 DSH 审批**不能**当 Claude Code 的 permissions 用）：
- **只有一次性授权**：结果词汇是 `allowed-once`，**没有 `allow-always`、没有已记住的规则、没有撤销、没有授权存储**。证据：`...\dsh-user-approval\README.zh.md`「已知限制」第 2 条。
- **请求不携带工具参数**：应答者只看到工具名、原因、可选 call id。证据：同上第 3 条。
- **没有内置应答者**：无头/不完整组合 → `unavailable` → fail-closed。证据：同上第 4 条 + 「服务自身绝不会提示人类」。

另外，`ask` 的批准**只对当次调用有效**，不会改成会话模式；升权重试是「新的一次调用，带更宽策略」。

#### (5) 工具栏（工具集）

模型可见的工具集合由 **一层注册表 + 多层作用域过滤** 决定：

```
全局注册层（host 组合树注册的 + MCP 桥接进来的）
   ↓ 每个 preset 的「层」注册自己那一份
   ↓ 每个 agent / 子 agent 的 ToolRestriction{allow,deny} 取交集
= 该 agent 的最终可见 schema 集
```

证据：
- 注册：`...\dsh-tools\README.zh.md`「注册一个工具就足以让它可见——注册表会自动把其 schema 送入系统提示词组装。」
- 过滤：`...\dsh-tools\lib\types\index.d.ts` 第 471–480 行：

```ts
/**
 * Per-scope filter over global tools. Restrictions intersect and do not affect
 * scoped registrations or the reserved PTC mode transport.
 */
export interface ToolRestriction {
    /** Global tool names that stay visible; everything else is removed. */
    readonly allow?: readonly string[];
    /** Global tool names removed from visibility. */
    readonly deny?: readonly string[];
}
```

- 硬阻断（比过滤更强）：`ctx.tools.guard(guard)` 是**单调同步守卫**——返回理由即拒绝，**后续监听器无法把拒绝翻回允许**。证据：`...\dsh-tools\README.zh.md`「对调用实施策略」：「`ctx.tools.guard(guard)` 在可扩展的 `tools/pre-execute` waterfall 之后注册单调同步守卫：返回的理由会拒绝调用，后续监听器无法把该拒绝重新变为允许。」类型证据：`...\dsh-tools\lib\types\index.d.ts` 第 481–489 行。
- 三段决策：`PreToolDecision = {kind:'allow'} | {kind:'deny', reason} | {kind:'ask', reason?}`。证据：`...\dsh-tools\lib\types\index.d.ts` 第 413–427 行。**`ask` 只有审批服务返回 `allowed-once` 才放行**——这就是审批策略与工具栏的耦合点。
- 呈现模式：`mode: native | ptc | both`（`config` 键），默认 `native`。证据：`...\dsh-tools\README.zh.md`「配置呈现模式」表 + `maxParallelSubCalls`（默认 10）。
  **官方 catalog 补充的两条关键约束**（证据：`D:\Incubator\temp\05-sources\config-catalog.zh.md` → `@deepseek-ai/dsh-tools`）：
  1. **PTC 模式要求一个 `ctx.ptcRuntime`，且其 `language` 必须已注册 SDK 渲染器（TypeScript 或 Python）**；缺失或无渲染器时**让提示词组装失败**（不是静默降级）。
  2. **在 `ptc` 模式下，`toolOrder` 里的原生工具名是无效的。**
  → 因此把 `DSH_TOOLS_MODE=ptc` 设上**不会自动可用**，必须先挂 `dsh-code-runtime-worker-thread`（本机 web/headless bundle 都插了这一行）。这是 `DSH_TOOLS_MODE` 被标注为「TEMPORARY workaround」之外的一个隐性前置条件。

```
   │  ctx.fs 后端                    ctx.shell 执行器          │

   │  (dsh-fs-local 为基)            dsh-pwsh-sandbox          │
   │        │                              │                  │
   │        └──────────┬───────────────────┘                  │
   │                   ▼                                      │
   │        ctx.sandbox: dsh-sandbox-local                    │
   │          linux: bwrap → Landlock                         │
   │          darwin: Seatbelt                                │
   │          win32: dsh-sandbox-windows-acl (受限令牌)        │
   └──────────────────────────────────────────────────────────┘
```

**耦合点 1：沙箱模式在两个能力族之间共享同一份解析结果。**
证据：`...\dsh-fs-sandbox\README.zh.md`「围栏行为」：「有效模式来自调用会话的覆盖值或升级授权… `workspace-write` 只允许目标规范化后位于工作区根目录或平台临时区域…**与 Seatbelt profile 授权的可写集合相同**」。且两族都从**同一个** `writableRoots()` 派生——见 1.1(3) 的代码引用。设计意图写在 `...\dsh-sandbox\lib\types\roots.d.ts` 的模块注释里：「so 'the write tool cannot write /tmp but bash can' asymmetries cannot arise between them」。

**耦合点 2：沙箱拒绝 → 审批升权的单行道。**
模型在受限模式下被拒 → 工具返回 `[sandbox: file access denied under <mode> mode]` + 升权提示 → 模型用 `sandbox_permissions` + `justification` **重试同一次调用** → 审批服务介入 → 批准则**仅该次调用**带上更宽模式。严格更宽阶梯，**不允许降级**（`read-only` 是地板，没有东西能升权到它）。

证据：`...\dsh-sandbox\lib\types\escalation.d.ts` 全文，尤其：「the strictly-wider ladder… resolves a `sandbox_permissions` request through a user-approval channel BEFORE anything executes」、「A non-widening request never prompts a human.」另见 `...\dsh-bash-sandbox\README.zh.md`「模型体验」中三条标记的逐字文本。

**耦合点 3：权限预设 = 把「沙箱模式」和「审批策略」捆成一个用户可见选项。**
证据：`...\dsh-permission-presets\README.zh.md`：「权限预设让用户通过一个选择器同时应用沙箱模式和审批策略」。内置表（`dsh-base` 实配）：

```yaml
# 证据：...\dsh-base\cordis.patch.yml 第 229–241 行；亦见 dump-web-config.yml 第 126–138 行
- id: permission
  name: '@deepseek-ai/dsh-permission-presets'
  config:
    presets:
      read-only:        { sandbox: read-only,          approval: ask   }
      workspace-write:  { sandbox: workspace-write,    approval: ask   }
      danger-full-access: { sandbox: danger-full-access, approval: never }
```

注意内置表把 **`danger-full-access` 与 `never` 捆绑**——「完全放开」的语义是「既不管文件写，也不再问」。而 `danger-full-access` 一旦是部署默认，`dsh-base` 的审批默认值也会自动切成 `never`（见 2.7 节的 `!!js` 表达式）。

Web GUI 侧的中文标签：「仅可查看」「工作区内修改」「完全权限」。证据：`...\dsh-client-ui-permission-presets\README.zh.md`「选择器」。

**耦合点 4：工具可见性与权限是两件事，不能互相替代。**
- 藏掉 `bash` 工具 ≠ 禁止写文件（`write`/`edit` 还在）。
- 设 `read-only` ≠ 藏工具（工具 schema 照旧可见，只是执行被拒）。
- 唯一能「既不可见又不可调用」的是 preset 里不挂载该行 + `ToolRestriction`。

**耦合点 5：`fs-observation-policy` 是「先读后写」门禁，与沙箱正交。**
它不管你能写哪里，只管「你有没有先读过这个文件、以及读完之后它变了没有」。证据：`...\dsh-fs-observation-policy\README.zh.md`：
- 无先前观测的编辑 → `FS_NOT_OBSERVED`，原因 `edit requires reading "<path>" first`；
- 观测后文件变化 → `FS_STALE_VERSION`；
- 读取缺失路径 → 授权带防护的创建（`createIfAbsent`），仍防覆盖并发创建；
- **观察记录不跨会话持久化**——恢复的会话必须重新读取。

官方架构文档原文：

> 「`web`、`headless`、`sdk`、`sdk-minimal` 和 `acp` 作为模板随发行版交付。」
> 「`dsh-base` 是 `web`、`headless`、`sdk` 与 `acp` profile 的共享第一层：模型适配器、工具、持久化、**沙箱与审批策略**、设置、凭据、遥测。`dsh-sdk-minimal` 是刻意保留的例外：一个组合包拥有完整的显式 SDK 配置树，不应用 `dsh-base`。」

此外还有**第 6 个运行入口：Electron 桌面应用**（不是随附模板，是独立 app）——证据：`docs/architecture.zh.md`「桌面应用」节：

**两条必须记住的 patch 语义**（`dsh-base\cordis.patch.yml` 文件头注释 + 官方架构文档双重确认）：
- 「A patch replaces the targeted row's whole `config` **rather than merging into it**」——**patch 替换整个 config 块，不合并**。你的覆盖必须重述每个想保留的键。官方架构文档：「一条 patch 按 id 定位某个条目并**替换其整个 config**」。
- 「Later bundle patches and the user's profile `cordis.patch.yml` address these rows **by id**, with the **last write winning per row**」——按 `id` 定位，逐行后者胜。

**bundle 通过 `dsh.bundle` 字段声明自己**（官方原文：「两者都在各自的 `package.json` 中通过 `dsh` 字段声明自己：`dsh.profile` 列出一个 profile 的组合包，**`dsh.bundle` 指向一个组合包的 patch 文件**」）。本机实测该字段的真实形态是**一个内联表**：
```json
// 证据：...\@deepseek-ai\dsh-base\package.json 等 6 个 bundle 包
"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
```
（本报告第一版把它写成字符串 `dsh.bundle.patch`；准确说法是**对象 `dsh.bundle` 的 `patch` 键**。）

**patch 条目只有三种操作**（profile `cordis.patch.yml` 文件头注释原文）：
```yaml
# 证据：C:\Users\ysc20\.dsh\profiles\web\cordis.patch.yml
# Your patch layer for this dsh profile, applied after every bundle layer:
# a top-level YAML array of loader patch entries (id-targeted config
# overrides, disables, and insert lists; `!!js` expressions allowed).
[]
```
① **按 `id` 定向覆盖 `config`**：`- id: <row> \n  config: {...}`（整块替换）
② **禁用一行**：`- id: <row> \n  disabled: true`
③ **插入新行**：`- insert: [ ... ]`
外加 `!!js` 表达式，可读环境变量、按平台分支（`!!js process.platform === 'win32'`）。

### ⚠️ 2.2b 一个必须单独指出的安全发现：`sdk-minimal` 是「无沙箱 + 无审批 + 无文件工具」

`dsh-sdk-minimal` bundle **不叠加在 `dsh-base` 之上**，它是完整的独立 Cordis 树。结果是它与所有其它随附 profile 的权限姿态**完全相反**：

| 项 | `sdk-minimal` 实际值 | 其它 base-backed profile |
|---|---|---|
| `sandbox-policy.config.mode` | **`danger-full-access`（写死，无环境变量出口）** | `DSH_PERMISSION_MODE ?? 'workspace-write'` |
| 审批插件 | **完全没有挂载**（无 `dsh-user-approval`） | `ask`（或 `danger-full-access` 时 `never`） |
| 权限预设 | **没有挂载** `dsh-permission-presets` | 三档预设表 |
| 文件工具 | **没有** `tool-fs` / `tool-fs-search` | `tool-fs` + `tool-fs-search` |
| 网络工具 | **没有** `tool-web` | `tool-web`（search + fetch） |
| 委派/工作流 | **没有** subagent / workflow / ralph | 全套 |
| 人格/上下文 | `includeHarnessIdentity: false`、`includeRuntimeContext: false` | 有 harness 身份 + 运行时上下文 |
| shell | `dsh-tool-bash-persistent` / `dsh-tool-pwsh-persistent`（持久 PTY，`timeoutMs: 300000`） | 一次性 `tool-bash` / `tool-pwsh` |
| 会话持久化 | `compression: none` | 默认压缩 |

证据（逐行核实）：`D:\Incubator\temp\evidence\bundle-layers\dsh-sdk-minimal.cordis.patch.yml` 第 41–45 行：
```yaml
    - id: sandbox-policy
      name: '@deepseek-ai/dsh-sandbox-policy'
      config:
        mode: danger-full-access
        workspaceRoot: !!js process.cwd()
```
以及该文件全文中**不存在** `dsh-user-approval`、`dsh-permission-presets`、`dsh-tool-fs`、`dsh-tool-web`、`dsh-tool-subagent`、`dsh-fs-sandbox`、`dsh-fs-observation-policy` 任何一行。

**工程含义**：
- `sdk-minimal` 的**唯一**权限边界是**持久 shell 的进程能力**——没有文件沙箱、没有审批、没有文件工具。它的模型**不能**用 `read`/`write`/`edit`，**只能**用持久 shell 干一切事，而 shell **不受 `workspace-write` 约束**（因为模式是 `danger-full-access`）。
- 它**设计上就是给「可信的、程序化嵌入的 SDK 调用方」用的**（注意 `includeRuntimeContext: false` + `system-prompt` 可被 `DSH_SYSTEM_PROMPT` 环境变量替换）。
- **绝对不要**把 `sdk-minimal` 当作「轻量版编码 agent」给不可信输入使用。**这是本报告发现的最严重的一个「看起来像安全默认值、实际是全开」的陷阱。**

**【推断】** 这个设计的意图是：SDK 调用方自己就是可信编排者，权限由宿主程序而非 harness 负责。但这与「`dsh-base` 系列刻意收紧」形成强烈对比，**极易被误用**。

> (a) 用 `--patch` 起一个专门 profile，让整个进程用更严的模式；
> (b) 让 preset 只挂一个「只读工具子集」（藏掉 `write`/`edit`/`bash`），用工具栏替代沙箱；

#### ⭐ 官方给出的「什么属于 host 平面」判据（证据：Agent Note `2026-08-10-host-plane-ownership-after-presets.zh.md`）

本报告 §2.3 的核心结论「preset 只能配工具栏/人格/指令/skill/委派，不能配沙箱/审批/模型」，最初是作者从 `dsh-web-app\cordis.patch.yml` 里 19 行 `disabled: true` **grep 推出来的**。现在有了**官方专文的明文判据**，该结论可以升级为官方设计依据。

该 Note 处理的正是「preset 拿到 agent 平面之后，什么必须留在 host 平面」这个问题。它给出的**判据**是：

> 「这正是 `tasks` 与 `goals` 已经采用的判据，只是这次适用于一个因**投影**触达面而不该归 preset 所有的 Service：**当一个单元的空值与真实值无法区分时，只要它注册进的那张表是进程级的，它就不能是逐组装的。**」

那篇文章的具体裁决（`dsh-token-meter`）：
- **问题**：`tokenMeter` 曾被挂进每个 preset 的 `compaction` realm，但它拥有 `tokenUsage`、`contextPressure`、`contextBreakdown` 三个**投影单元**，而 `sessionProjections` 是**一张进程级、没有作用域分层的表**。→ 「从某个 preset 内部注册的单元会**替所有会话作答**：一个 `minimal` 会话是否显示 context meter，取决于本次启动以来有没有**别的**会话挂过 `standard`；而只跑过 `minimal` 的进程根本不显示。」
- **决策**：「**meter 属于宿主平面。** `dsh-token-meter` 回到宿主组装，并离开各 preset 的 `isolate` 映射……**preset 保留 realm 与压缩后端——preset 选择的是它的 agent 是否压缩，而不是它的 token 是否被计。**」
- **被明确否决的替代方案**（很能说明边界在哪）：有人提议「基于同样的投影理由，把 `plan-mode` 与 `tool-todo` 也搬离 agent 平面」。**官方否决**：「两者**确实是逐 preset 的能力**，且对从不使用它们的会话，其单元算出的就是空值，而客户端本来就按值读取……**只有空值与真实值无法区分的单元——meter——才被迫归宿主所有。**」

**另一条同 Note 的硬不变量**：「不变量 companion 检查 `system-prompt/assemble`……**未加入任何 preset 的 agent 在使用模型时失败。**」
> 原文背景：「没有加入任何 preset 的 agent 也无人指出。加入是一条 **scope 父链链接**；缺了它，`tools`、`system-prompt` 与 `skill` 的视图都解析到**空的全局层，模型什么也收不到——不报错，也没有空目录可看，只是一个无法行动的 agent**。」
> 证据：`packages/preset/agent-preset-registry/tests/invariant.spec.ts`「拒绝未加入的 Agent 组装，并接受已加入的 Agent、Host 读取和历史 scope 读取」（该 Note 的 Testing 节）。

**这套判据的可操作版本**（**【推断】**，由上面两例归纳，用于判断新的服务该放哪一层）：

| 判据 | 归属 |
|---|---|
| 它注册进**进程级、无作用域分层的表**（如 `sessionProjections`），且**空值与真实值无法区分** | **host 平面**（例：`tokenMeter`、`tasks`、`goals`） |
| 它是**真正的逐 preset 能力**，且不使用时单元算出的是**可区分的空值**，客户端按值读取 | **agent 平面 / preset**（例：`plan-mode`、`tool-todo`、`compaction-basic`、`tool-result-pruner`） |
| 它是**沙箱与审批策略**（安全不变量，不是可配置能力） | **host 平面**（本报告 §1.2 的核心） |
| 它是**注册表本身**（tools / skills / subagents / goals 的 registry） | **host 平面**，preset 只贡献**行** |

### 2.4 settings 文件位置与优先级

**用户设置文档**（单一 YAML/JSON）：默认 `<harness home>/settings.yaml`，即 `$DSH_HOME/settings.yaml`（本机 `C:\Users\ysc20\.dsh\settings.yaml`）。

证据：`...\dsh-settings-file\README.zh.md`「最小配置」表：

| 字段 | 默认值 |
|---|---|
| `path` | `<harness home>/settings.yaml`（扩展名决定格式：`.yaml`/`.yml`/`.json`） |
| `dshHome` | `$DSH_HOME` 或 `~/.dsh` |
| `watch` | `true`（热重载） |
| `debounceMs` | `100` |

`$DSH_HOME` 解析优先级（证据：`...\dsh-home-paths\lib\index.js` 第 11–15、65–94 行）：**显式配置的 path > `$DSH_HOME` 环境变量 > `~/.dsh`**；纯空白的 `$DSH_HOME` 视为未设置。

**设置的三层解析**（证据：`...\dsh-settings\README.zh.md`「设计理念」）：
```
schema 默认值  →  注册方的组合 base（= 插件行的 config）  →  用户文档分节
```
写入只触碰**用户层**；`replace({})` 是真正的重置（重新继承 base 与默认值）。`update()` **深合并进用户分节，绝不进 base**。

#### ⭐ 官方权威的「配置来源解析顺序」（证据：Agent Note `2026-08-04-configuration-source-ownership.zh.md`）

上面那个三层解析**只是 settings seam 内部的顺序**。官方另有一篇专文给出 **harness 解析一切面向用户的值的统一顺序**——这把本节从「settings 的层级」升级为「配置来源的完整阶梯」：

```text
explicit for this run     per-operation override, CLI argument          ← 最高
> user settings           settings.yaml
> composition             profile bundles, user patch layers, --patch overlays
> this launch's shell     inherited process environment
> discovered file         <invocation cwd>/.env, then $DSH_HOME/.env
> defaults                schema default, provider public default        ← 最低
```
证据原文（Agent Note 中文版）：「**非机密值走同一条顺序。** 每个本身不是凭据的可配置值都按同一顺序解析；各领域的差别只在于哪些层存在。」

**四条必须记住的推论**（都引自该 Note 原文）：

1. **settings 在 composition 之上**，因为 settings seam 把插件的 cordis entry config 注册为 `base` 层，用户 section 叠加其上——**seam 无法区分某个值是 profile 的 bundle 设的，还是它的用户 patch 层或某个 `--patch` overlay 设的**（它们都以 entry config 的形式抵达）。
   → **实践后果**：需要把某字段**钉死、不被用户已存 settings 覆盖**的部署方，「应自带 bin 或 loader 配置树，或者干脆不挂载 settings 提供方」。**产品 CLI 没有高于已存 settings 的手段。**
2. **composition 高于环境** → 「shell 里陈旧的 `DEEPSEEK_BASE_URL` 无法改写已配置的 endpoint」。
3. **凭据走一条更窄的独立阶梯**（本 Note 明确不并入上表）：
   ```text
   inherited process environment      (read-only, wins)   ← 最高
   > $DSH_HOME/.credentials.yaml      (provider-managed, writable)
   > <invocation cwd>/.env
   > $DSH_HOME/.env                                       ← 最低
   ```
   继承环境优先，因为 `DEEPSEEK_API_KEY=… dsh`、CI 机密与容器 `-e` 是运维必须能**按次施加**的覆盖；而它无法从进程内部修改，就必须**可见地只读**。**配置本应只携带引用——解析哪个名字——该名字本身遵循上面的非机密顺序。**
4. **「信任不延伸到改变 harness 本身」——这是本报告 §4.3 / §4.4 最重要的一条安全设计**：
   `loadLayeredEnv` 会在加载时、且在物化任何内容之前，**拒绝任何设置了下列变量的 `.env`**：
   - 决定进程如何启动的：`PATH`、`SHELL`、`NODE_OPTIONS`、`LD_PRELOAD`
   - 决定由哪个环境程序处理一项操作的：`EDITOR`、`PAGER`、`BROWSER`
   - 决定运行时先执行哪些代码的：`BASH_ENV`、`PERL5OPT`、`PYTHONSTARTUP`、`RUBYOPT`、`JAVA_TOOL_OPTIONS`、Git 的钩子命令
   - 决定模型可见指令从哪里加载的：**整个 `DSH_*` 命名空间**、`HOME`、`XDG_*`
   - 决定网络如何访问与建立信任的：proxy 与 CA 变量
   匹配**不区分大小写**（`https_proxy` 不是绕过手段）。
   > **原文理由**：「`DSH_PERMISSION_MODE` 会关掉让『信任项目』根本成立的那道审批，而 `BASH_ENV` 会在 bash 工具每次发出 `bash -c` 时执行项目指定的文件——**项目的代码在 agent 的策略下运行是约定，项目改写那份策略不是。**」
   > 「一个变量一个变量地枚举是必输的游戏，所以**整个 `DSH_*` 命名空间被拒绝**而不是只拒绝一份经审查的子集……**不设逃生门：逃生门本身总得从某处读取，而任何被发现的文件能设置的东西，就是那个漏洞本身。**」

   **唯一豁免**（记录在 `2026-08-27-outbound-proxy-policy.zh.md`）：四个代理名可从 **`$DSH_HOME/.env`** 接受——因为**没有任何 `.env` 能挪动该文件**（`DSH_HOME` 本身被拒绝）——但仍拒绝来自**调用目录**文件的同名变量。

   → **实操影响（很重要）**：把 `DSH_PERMISSION_MODE` 或 `BASH_ENV` 写进**仓库的 `.env` 会让 DSH 启动失败**，这是刻意且响亮的破坏。
   > ⚠️ **【推断/风险】本报告 §2.7 与 §5.4 里推荐的 `DSH_PERMISSION_MODE=... dsh ...` 写法必须放在 shell 里或 CI 的环境块里，不能放在仓库 `.env` 里**——这不是风格问题，是会被拒绝的硬规则。

   另有一条**被官方明确记录为残留风险**的立场：「**harness 被启动于其中的项目默认可信，且不做询问。** 一个 checkout 可以携带自己的 endpoint、自己的普通变量和自己的密钥；密钥排在受管存储之下，因此通过 Models 页存下的密钥绝不会被 checkout 中恰好带有的那一个顶掉。」官方把「克隆一个携带 `.env`、其中指定了另一个 endpoint 或密钥的仓库」列为「残留风险是真实的、值得写明」。

本机实况（如实写出，含全部内容）：
```yaml
# 证据：C:\Users\ysc20\.dsh\settings.yaml（全文 4 行）
ui-onboarding:
  welcomeNoticeVersion: 2026-08-13.1
ui-theme:
  preference: dark
```

→ 说明**本机没有任何权限相关的用户覆盖**，一切权限行为都来自组合默认 + 会话事件。

### 2.5 fs-observation-policy 的语义

见 1.2 耦合点 5。补充三条工程含义：
1. **它是事件门禁，不是服务**——「插件只通过 `fs/*` 事件影响外部世界，因此不注册 `ctx.fsPolicy` 服务」。移除它不会破坏 `dsh-tool-fs`。证据：`...\dsh-fs-observation-policy\README.zh.md`「设计理念」。
2. **授权依据是版本新鲜度，而非视图完整性**——「任何窗口读取都会授权对未变文件执行全文件覆盖，这有意弱于完整视图规则」。证据：同上「已知限制」第 4 条。**含义：模型只读了 10 行也能整体覆写这个文件。** 这是设计取舍，不是 bug。
3. **直接 `ctx.fs` 读取不发 `fs/observed`**——只有通过 `read` 工具的读取才算观测。证据：同上第 3 条。

### 2.9 如何新增自定义工具

**范式**：写一个 Cordis 插件，`apply(ctx)` 里 `ctx.effect(() => ctx.tools.register(defineTool({...})))`。

API 形状（证据：`...\dsh-tools\README.zh.md`「注册工具」）：
```ts
import { defineTool } from '@deepseek-ai/dsh-tools'

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true, description: 'Absolute file path' },
    offset: { type: 'number' },
    limit: { type: 'number' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args, exec) {
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))
```

**本地零依赖插件的真实写法**（从本机 preset 学到的关键技巧）：preset 行可以直接写**相对文件路径**，Node 会 import 该文件；但**文件内的 `import '@deepseek-ai/...'` 解析不到**（因为解析基准是 harness 而非 preset 目录）——所以本地插件必须**零 npm 依赖**，只消费 host registry。

证据（`math-research` preset 注释原文）：
> 「Local plugin file (zero-npm-dependency ESM; **a bare specifier here would resolve against the harness, not this preset directory**).」
> 「零依赖原因同 danus-console.mjs：预设行引用的本地文件由 Node 直接 import，文件内 `import '@deepseek-ai/...'` 解析不到，故只消费 `systemPrompt`（host registry），不发布服务 → 无需 isolate realm。」

**最小可用的「只加一个 prompt 段落」本地插件全文**（61 行，可直接照抄改造）——证据：`C:\Users\ysc20\.dsh\.agent-presets\math-research\danus-prompt.mjs`：

```js
export const inject = ['systemPrompt']

export function apply(ctx) {
  ctx.effect(() => ctx.systemPrompt.section({
    name: 'danus:collaboration',
    order: 20,                     // persona=0 之后、tool 段之前
    text: `# Danus Collaboration — offload heavy thinking
...`,
  }))
}
```

配套的 preset 行：
```yaml

  name: './danus-prompt.mjs'
```

**「注册一个工具」版的最小骨架**（**【推断】** 骨架由 `defineTool` API 形状 + `ctx.effect` 约定合成；本机 `math-research` 的 `danus-console.mjs` / `paper.mjs` / `mo.mjs` / `ocr.mjs` / `global-deadline.mjs` 五个文件都是这一形态，作者未逐一通读其 47KB/61KB 源码）：
```js

export const name = 'my-tool'
export const inject = ['tools']        // 不发布服务 → 无需 isolate realm

export function apply(ctx) {
  ctx.effect(() => ctx.tools.register({
```

### 2.10 如何通过 MCP 挂载外部工具

证据：`...\dsh-mcp-client\README.zh.md`。

```yaml
# 证据：...\dsh-mcp-client\README.zh.md「最小配置」
- id: mcp-github
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: github
    transport: stdio
    command: npx
    args: ['-y', '@modelcontextprotocol/server-github']
    env:
      GITHUB_TOKEN: !!js process.env.GITHUB_TOKEN

- id: mcp-web
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: web
    transport: streamable-http
    url: http://localhost:3000/mcp
    headers:
      Authorization: !!js '`Bearer ${process.env.MCP_TOKEN}`'
```

要点：
| 项 | 值 / 语义 |
|---|---|
| 工具命名 | `mcp__<serverName>__<rawName>`，如 `mcp__github__create_issue`；与 Claude Code / Codex 同一命名形态 |
| `serverName` | `[A-Za-z0-9_-]{1,32}`，一个注册作用域内唯一；**不采用远程 `serverInfo.name`**（不可信、不唯一、可漂移） |
| 重连 | `reconnect.enabled` 默认 true，500ms 起翻倍至 30s，`maxAttempts` 默认 10 |
| 超时 | `toolCallTimeoutMs` 默认 60000 |
| 启动失败 | `failOnStartupError` 默认 false（harness 照常启动，该服务器工具缺失） |
| **环境清洗** | stdio 子进程环境以 `scrubbedParentEnv()` 为基座——**删除匹配 `/KEY\|PASSWORD\|SECRET\|TOKEN/i` 的环境名与所有 `DSH_*`**，再合并你配的 `env` |
| 只桥接工具 | MCP **resources 与 prompts 不受支持** |

**MCP 挂在哪一层？** README 说「每台服务器配置一条记录」但未明说 host/preset。**【推断】** 若按 `dsh-mcp-client` 只 `ctx.tools.register`（README 原文：「MCP 服务器发现工具后，用服务器的 schema 调用 `ctx.tools.register()`」，证据：`...\dsh-tools\README.zh.md`「扩展点」）——则**放在 preset 里最合理**，这样每个 preset 可挂不同 MCP 集。需要实测确认。

**⭐ 一个真实的 MCP 配置实例（master，官方随附 overlay）** —— 这印证了上面的形态是**一个 `insert` overlay 层**，而不是必须写在 preset 里：

```yaml

# the pinned executable first; DSH starts it but does not run a package manager.
- insert:
    - id: memory-mcp-reference
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: reference_memory
        transport: stdio
        command: mcp-server-memory
        cwd: !!js process.cwd()
        env:
          MEMORY_FILE_PATH: !!js >-
            process.env.MEMORY_FILE_PATH?.trim() || process.getBuiltinModule('node:path').join(process.getBuiltinModule('node:os').homedir(), '.dsh-mcp-reference-memory.jsonl')
```

该目录下共有**三个真实 overlay**：`mcp-reference-memory.cordis.yml`、`engram.cordis.yml`、`memorix.cordis.yml`（三者的 `transport` 都是 `stdio`）。
**三条可直接迁移的工程经验**（来自这段官方实例）：
1. **官方自己用顶层 `- insert:`** 来挂 MCP，而**不是**改 preset → **【推断修正】MCP 行的归属比本报告上一版说的更灵活：`insert` overlay（profile patch / `--patch`）是官方示范路径**，放在 preset 里同样可行（覆盖面不同：overlay 影响整个 profile，preset 只影响该 preset 的 agent）。
2. **`cwd: !!js process.cwd()`** —— MCP 子进程的工作目录**默认不继承**会话 cwd，官方显式传 `process.cwd()`。**安全含义**：若你用 `${workspace}` 之类的意图却忘了显式设置，stdio MCP server 会在**启动 dsh 时的目录**里运行，可能与会话工作区不一致。
3. **注释原文：「Install the pinned executable first; DSH starts it but does not run a package manager.」** —— DSH **只启动**你给的 `command`，**不会**替你 `npm install`/`npx -y` 兜底。→ **必须预先安装固定版本的可执行文件**；这也是「MCP server 供应链安全」的第一道人工闸门。

```yaml
    workspaceRoot: D:\Incubator        # 仅无 cwd 调用/无 agent 会话使用
```
> ⚠️ **普通 agent 会话根本不读 `workspaceRoot`**——它用 `SessionHeader.cwd`。要让会话锁在某个目录，**从该目录启动 dsh**（「运行命令时所在的目录将作为默认 workspace 根目录」，证据：`@deepseek-ai\dsh\README.zh.md`），或经 Web GUI 的项目/目录选择器建会话（证据：`...\dsh-api-workspace-controller`、`...\dsh-host-directory-picker-auto`）。

**(ii) 如何只允许改某些目录**
见 1.1(1) 的关键限制：**每个会话只有一个工作区根，`SandboxExecutionPolicy` 没有多根数组**。
**【推断】** 可行的近似手段（都不是内核级保证）：
1. 把会话 cwd 设为这些目录的**公共父目录**，再用自定义 `tools/pre-execute` 插件对 `write`/`edit` 的 `file_path` 做路径白名单校验（`dsh-tool-fs` 的入参名是 `file_path`，证据：`...\dsh-tool-fs\README.zh.md`「工具」表）；
2. 只保留 `read`/`read_image`/`glob`/`grep`，藏掉 `write`/`edit`/`bash`/`pwsh` —— 这是 **preset 层**能做到的、最干净的做法；
3. 用 `read-only` 模式 + 把要改的内容交给一个受限的自定义工具。

**(iii) 如何要求审批**
- **默认就是 `ask`**（除非 `DSH_PERMISSION_MODE=danger-full-access`）；
- 但 `ask` **只在有应答者时才真的问人**：`web` profile 挂 `@deepseek-ai/dsh-client-ui-approval`（证据：`...\dsh-web-app\cordis.patch.yml` 第 252–253 行 + `...\dsh-client-ui-approval\README.zh.md`）提供浏览器批准面板；**面板只提供「仅本次允许 / 拒绝」**，没有 always-allow；
- 强制显式（防止被 `DSH_PERMISSION_MODE` 意外放开）：
```yaml
- id: approval
  config:
    policy: ask          # 写死，不给 !!js 留口子
```

**(iv) 如何完全放开**
```yaml
- id: sandbox-policy
  config: { mode: danger-full-access, workspaceRoot: !!js process.cwd() }
- id: approval
  config: { policy: never }
```
或一次性 `DSH_PERMISSION_MODE=danger-full-access`（它会把两者一起切过去）。
> Web GUI 里选「完全权限」**始终需要显式确认风险**——证据：`...\dsh-client-ui-permission-presets\README.zh.md`：「完全权限始终需要显式确认风险」、「完全权限选项携带 `confirmation` 载荷，由共享弹窗外壳渲染为页内风险门」。

### 2.12 Windows 平台实现细节（单独成节，因为是本机平台）

**DSH 在 Windows 上没有容器、没有 bwrap，用的是 NTFS ACL + 受限令牌。**

runner 链（证据：`...\dsh-sandbox-local\README.zh.md`「runner 选择」）：
| 平台 | runner 链 |
|---|---|
| linux | `bwrap` → Landlock |
| darwin | Seatbelt（`sandbox-exec`） |
| **win32** | **ACL 受限令牌 runner**（`dsh-sandbox-windows-acl`） |

机制（证据：`...\dsh-sandbox-windows-acl\README.zh.md`「机制」）：
- 调用者令牌复制为 `WRITE_RESTRICTED` **受限令牌**，其 restricting SIDs 携带彼此独立的工作区 / 私有临时目录能力；
- Windows 做**两次访问检查**（先正常 SID、再 restricting SID），只有两次都通过才授予写类访问；
- **工作区 SID 由规范工作区路径确定性派生**（`workspaceWriteSid`）→ 工作区 ACE 每机器每工作区只物化一次，之后每次会话/调用/重启命中精确 ACE 跳过；
- **每个活跃的会话/工作区对**获得随机私有临时目录 + 从该路径派生的 SID（`tempWriteSid`）→ 共享工作区的会话共享写权限，但**无法写彼此的临时目录**；
- 模式对应的 restricting 列表：
  - `workspace-write` = 登录 SID + Everyone + 工作区 SID + 临时 SID
  - `read-only` = 登录 SID + Everyone（**不含任何写入 SID**）
- 受限子进程的 `TMP`/`TEMP` **被改写**为该私有目录；
- `init()` 任何 Win32 失败都抛异常 —— **子进程绝不会不受限制地 spawn**（fail-closed）；
- runner 失败签名：向 stderr 打印 `windows-acl-run: <detail>` 并以 **127** 退出。

**六条必须在 Windows 上知道的边界**（证据：同 README「已验证边界」+「已知限制」）：

| 边界 | 后果 |
|---|---|
| **Everyone 必须保留在两种 restricting 列表中** | 外部 NTFS 对象若其 DACL 向 Everyone 授予写权限，**在两种模式下都可写** |
| **硬链接是文件对象别名，而非路径别名** | 可继承的工作区 ACE 会修改底层同一文件的安全描述符 → 同一对象可通过外部别名写入；**不能**拒绝工作区中的多链接文件（pnpm 正常安装就在用硬链接） |
| **只管辖写** | 受限子进程可读调用者可读的任何文件、可打开套接字；**没有网络限制** |
| **`read-only` 下 PowerShell 降级为 ConstrainedLanguage** | `Add-Type`、非核心 .NET 静态调用、COM、反射**全部失败**（因为无法在临时目录创建 AppLocker 探针文件）；`workspace-write` 下保持 FullLanguage |
| **受限孙进程的管道 stdio 捕获不可用** | libuv 的管道 stdio 用 NAMED pipe，受限进程内 `spawn(..., {stdio:'pipe'})` 以 **EPERM** 失败；`inherit`/`ignore` 可用，PowerShell 自己的管道（匿名管道）可用 |
| **ACL 授权是对真实目录的驻留改动** | 工作区 ACE **按设计常驻、绝不撤销**（复用缓存）；临时 ACE 由 `dispose()` 撤销；**手工 `icacls` 清理无法回收**（`ERROR_NONE_MAPPED` 1332） |

另外：`enforcement` 报告为 **`partial`**（不是 `full`）——「受限令牌必须保留 Everyone，且 NTFS 硬链接会把同一文件对象别名为多个路径」。证据：`...\dsh-sandbox-local\README.zh.md`「受限执行与强制执行」。

> **实践结论**：在 Windows 上，`read-only` 是**唯一**能真正阻止「模型改文件」的模式（因为 `workspace-write` 的 Everyone 边界可被 DACL 宽松的外部对象绕过）；但 `read-only` 会让 PowerShell 退化成 ConstrainedLanguage，**很多脚本会莫名失败**——这是 DSH Windows 用户最容易踩的坑。

**本会话的直接验证**：DSH 的沙箱拦截发生在进程级写路径上，连 `dsh` 自己写自己的 profile 目录都被拦：
```
Error: EPERM: operation not permitted, open 'C:\Users\ysc20\.dsh\profiles\web\cordis.yml'
```
（本会话运行时观察——执行 `dsh web --help` 时触发；因为 `C:\Users\ysc20\.dsh` 在 `D:\Incubator` 工作区之外，`workspace-write` 模式拒绝写入。）

#### 2.14.1 ⭐ preset 的数据模型（真源码，master）

rc.2 的 preset 是**目录内联**（`presets/<id>/agent.cordis.yml`）。master 把它重构成**声明式**：preset 现在就是**普通 Cordis 配置里的一行**。两个包的源码给出了正式的**类型契约**：

**`packages/preset/agent-preset/src/index.ts`（全文 30 行）**：
```ts
/** Definition submitted to the preset registry. */
export type Config = PresetDefinition

/** Registers child plugin configuration without owning Agents using older revisions. */
export default class AgentPreset {
  static inject = ['agentPresets']
  /** Preserve child expressions until their own plugins activate. */
  static readonly [EntryGroup.key] = true
  static Config: z<Config> = z.object({
    id: z.string().required(),
    name: z.string(),
    description: z.string(),
    order: z.number(),
    // Cordis owns individual plugin schemas; the registry validates entry structure.
    plugins: z.array(z.any()).required(),
  }) as z<Config>
  ...
}
```

**`packages/preset/agent-preset-registry/src/definition.ts` —— preset 的正式数据模型**：
```ts
/** Identity, display fields and child Cordis plugins of one preset. */
export interface PresetDefinition {
  readonly id: string
  readonly name?: string
  readonly description?: string
  readonly order?: number
  readonly plugins: readonly (Omit<EntryOptions, 'id' | 'disabled'> & { id?: string; disabled?: EntryOptions['disabled'] | JsExpr })[]
}
```

**从这两段源码能读出的 5 条硬事实**（这是本报告此前只能从 YAML 实例归纳的）：

1. **`plugins` 是 preset 的**唯一**能力字段**——preset 的全部内容就是「一个子插件行列表」。**没有** `sandbox`、**没有** `approval`、**没有** `workspace`、**没有** `model` 字段。→ **§2.3 的核心结论被类型契约坐实。**
2. **`PresetDefinition` 里 `id` 必填，`name`/`description`/`order` 可选**，全部是**展示与排序**用途（`order` 只影响名单顺序）。
3. **`disabled` 允许是 `JsExpr`**——这就是 `!!js process.platform === 'win32'` 能用在 preset 行上的类型依据；且 `id` 在 preset 的子行里是**可选**的（`id?: string`），与 host patch 层不同。
4. **`EntryGroup.key = true`** —— master 的 preset 行本身是一个 **Cordis EntryGroup**，即它的 `plugins` 会被当作**嵌套的 loader 条目组**加载，并「Preserve child expressions until their own plugins activate」（保留子表达式直到其自身插件激活）。
5. **registry 侧的校验函数 `entryListProblem()`** 明确要求：组装的**顶层必须是插件行列表**；每一行必须是**含 `name` 字符串的 map**；`group === true` 时递归校验其 `config`。错误文案逐字为 `the composition must be a top-level list of plugin rows` / `group <at> must hold a list of plugin rows` / `<label> is not a plugin row (expected a map with a "name")` / `<label> names no plugin (a "name" string is required)`。

**注册表侧的运行时契约**（`agent-preset-registry/src/types.ts`，全文 63 行）——preset 的**错误词汇**与**会话投影**：

```ts
export interface AgentPresetRow {
  readonly id: string
  readonly isDefault: boolean      // 会话未命名 preset 时是否组装它
  readonly name?: string
  readonly description?: string
  readonly broken?: string         // 为什么它无法组装会话；能组装时不存在

/** RemoteErrorDetailsMap 的三个错误码 */
'agent-preset/not-found': { agentPreset; available: string[] }
'agent-preset/invalid':   { agentPreset; reason: string }
'agent-preset/locked':    { sessionId; agentPreset }   // 会话对话已开始，组装已固定
```

#### 2.14.3 ⭐ 网络出口控制：master 有了官方出站代理策略（补强本报告 §4.4）

**它承认的现实与本报告 §4.4 的结论一致**（rc.2 与 master 早期都如此）：
> 「Node 内置的 `fetch` 会忽略 `HTTP_PROXY` 与 `HTTPS_PROXY`……**Harness 并没有**：`setGlobalDispatcher`、`ProxyAgent` 与 `EnvHttpProxyAgent` 在 `packages/` 与 `apps/` 中出现次数为零，因此**模型请求、每次 web 搜索、`web_fetch`、走 HTTP 的 MCP 与 OTLP 导出器全部直连，且是静默的，任何地方都没有诊断。**」

**master 的解法**（这是 §4.4 应当补上的一层）：

- **覆盖范围**：Node 的 `fetch` 解析的正是 undici 的全局 dispatcher，因此**每一处普通 `fetch()` 以及每一个最终落到 `globalThis.fetch` 的 SDK 都无需改动即被覆盖**——「撰写时是九个调用点，未来新增的也自动覆盖」。

- **代理名的豁免只给 `$DSH_HOME/.env`**，项目 `.env` 里的代理名被拒绝（同 §2.4 结论 4）。
- **loopback 始终绕过**；`ALL_PROXY` 为两种协议兜底；空值视为未设置。
- **`web_fetch` 经由代理时不再解析与固定地址**：「经由代理时没有可固定的对象——origin 的 DNS 由代理执行——而固定后的直连会彻底绕开代理。因此**代理转发的一跳跳过解析，配置代理即表示信任该代理进行目的地选择**。」被策略绕过的一跳（含每个 loopback 与 `NO_PROXY` 条目）**仍走原有的解析并固定路径**。
- **URL 层策略未受影响**：「仅 `http(s)`、禁止内嵌凭据、长度上限与跨域重定向拒绝**在每一跳上依然生效**」。

- **一处已记录的接缝**：「此类上下文按 Node 自己的规则匹配绕过条目，其分隔符与 IPv4 区间支持与本包不同，且该标志仅存在于 Node 22.21+ 与 24+。」

#### 2.14.4 ⭐ 工作区文件的「读权限」归属（补强本报告 §1.1 与 §4.1）

证据：Agent Note `2026-09-09-workspace-file-read-authority.zh.md`（2,827 B）+ `2026-09-05-workspace-files-service.zh.md`（24,489 B）。

**决策原文**：
> 「`read`、`readBytes` 与 `stat` **继承被寻址 Session 的文件系统后端读取权限**。**工作区根是输入相对路径的基准，而不是读取边界**；只要后端允许，就可以读取绝对路径和离开工作区的相对路径。服务仍要求普通文件、**拒绝符号链接**，并应用文本和字节上限。
> `list` 与 `changes` **仍限于工作区**，因为它们暴露工作区导航和观察，而不是读取一个具名文件。」

**它明确记录的后果（本报告 §4.1 的最小权限原则必须承认这一点）**：
> 「**持有有效 Session 文件地址的调用方可以接收 Session 文件系统后端允许读取的每个普通文件的字节，包括工作区外文件。** 开启开发者工具时，预览的 HTML 文档**可以执行已打包的本地 JavaScript，并发起网络请求**。工作区外文件不会产生 `changes` 帧，因此其预览需要显式刷新才能观察更新。」

**官方自己也承认这是一处有意接受的安全取舍**：
> 「开启开发者工具时，Document Preview 把有界、静态声明的本地脚本与样式表打包进带 `sandbox="allow-scripts"` 的 HTML Blob iframe；不透明源阻止访问父应用，但**浏览器保留正常网络访问**。**这种暴露是为渲染静态生成 HTML 而有意接受的安全取舍。**」

以及被否决的替代方案：「**允许根外读取，但阻断 iframe 的全部网络。** 更严格的 CSP 可以降低数据外传风险，但也会拒绝静态 HTML 预览有意保留的外部资源与网络行为。**不透明 sandbox 保护父应用，但不承诺网络隔离。**」

> **对本报告的意义**：这**坐实了 §4.1 与 §4.2 的核心论断「DSH 的沙箱只管写，读侧靠后端权限」**，并补充了一个 rc.2 README 没突出的事实：**`workspace-files` 服务的文件读取是「后端权限决定」，不是「工作区决定」**——与 `...\dsh-api-workspace-files\README.zh.md`（本报告 §A.4 已引）的说法一致，但这里有官方决策记录级的表述与后果声明。

### 3.1 Claude Code

> 一手来源：[配置权限](https://code.claude.com/docs/en/permissions)、[设置文件和优先级](https://code.claude.com/docs/zh-CN/settings)（该站点支持在 URL 后加 `.md` 抓取原始 markdown）。

#### 权限系统的分层结构

| 工具类型 | 例子 | 是否需审批 |
|---|---|---|
| 只读 | 文件读取、Grep | **否**（限工作目录 + `additionalDirectories` 内） |
| Bash 命令 | shell 执行 | 是，除内置只读命令集 |
| 文件修改 | Edit/Write | 是 |
| Web fetch | WebFetch | 是，除内置的预批准文档域名 |
| Web search | WebSearch | 是 |

「Yes, and don't ask again」的行为**分工具不同**：Bash 命令与 WebFetch 域名**按仓库永久保存**到 `.claude/settings.local.json`（经 worktree 解析到主检出）；**文件修改的批准只持续到会话结束**，不落盘。

#### 规则语法与判定顺序（最关键）

规则格式：`Tool` 或 `Tool(specifier)`。

```
Bash                               匹配所有 Bash 命令（等价于 Bash(*)）
Bash(npm run build)                精确匹配
Read(./.env)                       匹配读当前目录的 .env
WebFetch(domain:example.com)       匹配到 example.com 的抓取
Bash(npm run *)                    通配；等价写法 Bash(npm run:*)
mcp__*                             工具名 glob：拒绝所有 MCP 工具
mcp__github__get_*                 allow 规则必须先有字面 mcp__<server>__ 前缀
Agent(model:opus)                  按输入参数匹配（仅 deny / ask 可用）
Bash(run_in_background:true)       同上
```

**判定顺序（官方原文）：「Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order.」**

推论（官方明写）：
- `Bash(aws *)` 的宽 deny **会**拦住更窄的 allow `Bash(aws s3 ls)`——**allow 不能从 deny 里凿例外**；
- 同一个 ask 与 allow 之间也是 ask 优先；
- **跨层也是 deny 优先**：「if user settings allow a permission and project settings deny it, the deny rule blocks it. The reverse is also true: a user-level deny blocks a project-level allow, because deny rules from any scope are evaluated before allow rules.」

**两条重要的语义区别**：
1. **裸工具名的 deny 会把工具从模型的上下文里整个移除**（Claude 根本看不见它），而带作用域的 deny（如 `Bash(rm *)`）保留工具、只在调用时拦截。
2. **无法用参数匹配主内容字段**：`command`（Bash/PowerShell）、`file_path`（Read/Edit/Write）、`path`（Grep/Glob）、`url`（WebFetch）都不可匹配——因为 `Bash(command:rm *)` 会被复合命令绕过，Claude Code **直接忽略并告警**。必须写成 `Bash(rm *)`。

**复合命令感知**：识别 `&&`、`||`、`;`、`|`、`|&`、`&`、换行；**规则必须独立匹配每个子命令**。deny/ask 规则在**任一子命令**匹配时生效，包括嵌套在子 shell、命令替换或 `for` 循环体里的命令。

**通配符位置陷阱**：`*` 必须放在子命令之后。`Bash(git log *)` 只允许 `git log` 开头的命令；`Bash(git *)` 允许所有 git 命令。**allow 规则在子命令之前放 `*`（如 `Bash(git * main)`）会在启动时告警。** 「space before a trailing `*` is part of the rule」——`Bash(ls *)` 不匹配 `lsof`，`Bash(ls*)` 匹配。

```json
{
  "permissions": {
    "allow": ["Bash(npm run *)", "Bash(git commit *)"],
    "deny":  ["Bash(git push *)"]
  }
}
```

#### 权限模式

`defaultMode` 在 settings 文件里设置，取值：

| 模式 | 描述 |
|---|---|
| `default` | 每个工具首次使用时提示（CLI 中标注为 Manual，接受 `manual` 作为别名） |
| `acceptEdits` | 自动接受文件编辑与常见文件系统命令（`mkdir`/`touch`/`mv`/`cp`），限工作目录或 `additionalDirectories` 内 |
| `plan` | 读文件、跑只读 shell 探索，不改源文件 |
| `auto` | 带后台安全检查的自动批准 |
| `dontAsk` | 自动拒绝所有本会提示的调用 |
| `bypassPermissions` | 跳过权限提示（**除「任何模式都不自动批准的动作」**） |

防锁死：`permissions.disableBypassPermissionsMode` 或 `permissions.disableAutoMode` 置为 `"disable"`。

> ⚠️ 官方 Warning：`bypassPermissions` 下连**受保护路径**（`.git`、`.claude`）的写入都跳过提示。「Only use this mode in isolated environments like containers or VMs.」

#### Settings 优先级与托管层

`allowManagedPermissionRulesOnly` 让托管设置成为**唯一**的权限规则来源。`disableBypassPermissionsMode` 通常放在托管设置里执行组织策略，但**任何作用域都能设**（用户可以用它把自己锁在 bypass 模式之外）。

**优先级**：managed settings 最高——**没有任何层级（包括命令行参数）能覆盖托管的权限规则**。`--allowedTools` 无法覆盖托管的 deny；`--disallowedTools` 可以在托管设置之上**追加**限制。

**托管设置的物理位置**【本机 `@anthropic-ai/claude-code` 2.1.233 内置 schema 交叉核对，**无对应官方网页 URL**】：Linux/macOS 链为 `/etc/claude-code`；Windows 为 `C:/Program Files/ClaudeCode/managed-settings.json`，另可经注册表 `HKLM\SOFTWARE\Policies\ClaudeCode`（WSL 下需管理员在 HKLM/Program Files 启用链、用户再在 HKCU 确认，Windows 来源优先）。

**hooks 事件表**【同上，本机产物】：`PermissionRequest`（权限弹窗前）、`PreToolUse`（可阻断）、`PostToolUse`（成功后）、`PostToolUseFailure`（失败后）、`Notification`、`Stop`、`PreCompact`、`PostCompact`、`UserPromptSubmit`、`SessionStart`。hook 类型三种：`command`、`prompt`、`agent`（后两者仅限 `PreToolUse`/`PostToolUse`/`PermissionRequest`）。hook 经 stdin 收到 `{session_id, tool_name, tool_input, tool_response?}`，可回 JSON 控制行为（`continue`、`decision: "block"`、`hookSpecificOutput`）。

#### 权限与沙箱的关系（这是本报告最该借鉴的一段）

官方明确二者是**互补的安全层**：
- **权限（permissions）** 控制 Claude Code 能用哪些工具、能访问哪些文件或域名；适用于 Bash、Read、Edit、WebFetch、MCP 及所有其他工具。
- **沙箱（sandboxing）** 提供**操作系统级**强制，限制 shell 命令及其子进程的文件系统与网络访问；**只适用于 Bash、PowerShell 与 Monitor 命令**。

「Use both for defense-in-depth, since sandbox restrictions still apply even if a prompt injection bypasses Claude's decision-making.」

一个重要的默认行为：**开启沙箱且 `autoAllowBashIfSandboxed` 保持默认 `true` 时，被沙箱的 Bash 命令不再提示**——即使你的权限里有裸 `Bash` ask 规则或 `Bash(*)`。**沙箱边界替代了整个工具的提示。** 例外：内容作用域的 ask 规则（如 `Bash(git push *)`）仍强制提示；显式 deny 仍生效；针对**关键路径**的 `rm`/`rmdir` 仍走常规权限流。

#### workspace trust（针对供应链攻击）

`permissions.allow` 与 `permissions.additionalDirectories` 在项目 `.claude/settings.json` 里是**授予能力**，因此**只有在你接受该目录的信任对话框后才生效**。`deny`/`ask` 规则不受影响（它们只收紧）。

关键事实：
- 信任的键：在仓库内按 **git 仓库根**，在 worktree 里用主检出的根；仓库外按**启动目录**。
- **`claude -p` 或 SDK 会话永远不显示信任对话框**——因此在这些场景下，项目的 allow 规则与 `additionalDirectories` **不被使用**，并打印 `this workspace has not been trusted` 警告到 stderr。
- **但 hooks、`env` 块、`apiKeyHelper`、以及 skill 的 `allowed-tools` 在任何情况下都会被使用**（「Workspace trust never gates a skill's `allowed-tools` in any session」）。
- 项目 `.mcp.json` 里的服务器：交互式会话会先问；`claude -p`/SDK 则**不问就连**。
- 官方建议在不可信仓库里跑 `claude -p` 时：`--setting-sources user`、`--bare`、`--settings '{"disableAllHooks": true}'`、`add disabledMcpjsonServers`。

#### 对 DSH 的可迁移启示

| Claude Code 做法 | DSH 对应物 | 差距 |
|---|---|---|
| `deny > ask > allow` 的严格序 | `ToolGuard` 单调 deny（但**没有 ask > allow 的显式规则表**） | DSH 缺少「规则表」这一层，只有 `restrict`（allow/deny 掩码）+ `guard`（deny） |
| `additionalDirectories` / `--add-dir` | ❌ **无对等物**（每会话一个 workspace root） | **最大差距** |
| 「裸工具名 deny = 从上下文移除」 | `ToolRestriction.deny` 或 preset 里不挂该行 | 等价 |
| 「参数匹配某些字段可被复合命令绕过」 | `ctx.tools.guard` 在**解析后的参数**上判定 | DSH 更彻底（在规范化参数上判定） |
| 权限 + OS 沙箱双层 | 沙箱模式 + `ToolRestriction`/`guard` | 概念一致；DSH 缺网络侧 |
| workspace trust（供应链） | **preset 与 shell 同等级信任**（无信任对话框） | **DSH 更宽松也更危险**：加载别人的 preset 目录 = 任意代码执行，没有信任门 |
| 「沙箱开启后 bash 不再提示」 | 无此优化（Sandbox 拒绝后才走升权） | DSH 会在沙箱边界处频繁打断 |

### 3.2 OpenAI Codex CLI

> **证据分级（本章最需要注意的一节）**：本环境 `developers.openai.com` 返回 **403**、`learn.chatgpt.com` 解析到非公网 IP。因此本节有**两类**证据：
> 1. **【本地实测】——最强证据**：本机真实安装了 `@openai/codex` **0.148.0**。以下凡标【本地实测】的配置键名与枚举值，直接读自该版本 CLI 的 `--help` 输出与二进制内嵌 schema 字段表，**是权威产物而非网上二手内容**，但没有可引用的官方网页 URL。
> 2. **【镜像】——补充语义**：官方文档的第三方镜像（[mintlify.wiki](https://mintlify.wiki/openai/codex/configuration/reference)）。镜像与 0.148.0 实测**存在冲突**，冲突处以【本地实测】为准并显式标注。

#### 配置文件位置与分层

**【本地实测】** 主配置 `~/.codex/config.toml`；`CODEX_HOME` 可改写 home；`--ignore-user-config` 表示**完全不加载** `$CODEX_HOME/config.toml`（auth 仍用 `CODEX_HOME`）。
**【本地实测】** profile 的真实形态是**独立文件叠加**，官方帮助原文：`Layer $CODEX_HOME/<name>.config.toml on top of the base user config`——**不是**旧式的 `[profiles.x]` 内联表（内联表只出现在镜像文档里）。
**【本地实测】** `-c/--config <key=value>` 支持点路径覆盖任意嵌套键（帮助示例含 `-c 'sandbox_permissions=["disk-full-read-access"]'`、`-c shell_environment_policy.inherit=all`）；`--strict-config` 遇未知字段直接报错。

**【镜像】** 声称的分层顺序（后者覆盖前者）：
```
1. 内置默认值
2. 全局 config（~/.codex/config.toml）
3. 项目 config（.codex/config.toml）
4. Profile 覆盖（--profile）
5. CLI flags（--model、--approval-policy）
6. 环境变量
```
> ⚠️ **冲突**：0.148.0 的 `--help` 未出现 `.codex/config.toml`，`ConfigToml` 字段表中也未出现项目级配置项。**项目级配置是否真的受支持存疑**，需官方 `docs/config.md` 仲裁。

```toml
# 【镜像】最小示例
model = "o4-mini"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```
> ⚠️ 镜像把默认模型写成 `o4-mini`，且 `codex exec` 选项表与 0.148.0 实际选项不符——**镜像不应作为权威依据**。

#### 沙箱模式（三档）——【本地实测】硬枚举

`-s/--sandbox` 的取值在帮助里是硬枚举：
```
[possible values: read-only, workspace-write, danger-full-access]
```
语义（【镜像】[Sandboxing](https://mintlify.wiki/openai/codex/concepts/sandboxing)）：

| 模式 | 允许 | 用途 |
|---|---|---|
| `read-only` | 读**任意位置**文件；**无写操作**；网络（若启用） | 代码分析、搜索、评审 |
| `workspace-write`（**默认**） | 读任意位置；写工作目录（`cwd`）；写 `--add-dir` 指定的额外目录；**受保护路径保持只读**；网络（若启用） | 开发、测试、改文件 |
| `danger-full-access` | 无文件系统限制、无网络限制、完整系统访问 | 仅在可信环境 |

**受保护路径（`workspace-write` 下也永远只读）**：`.git/`、`.codex/`、`gitdir:` 符号链接。**递归强制**（如 `.git/hooks/` 也只读）。

**`[sandbox_workspace_write]` 表键 ——【本地实测】** 二进制中结构体 `SandboxWorkspaceWrite` 的字段名精确为：`writable_roots`、`network_access`、`exclude_tmpdir_env_var`、`exclude_slash_tmp`。**四个键名已本地确认**，但**默认值与精确语义未能取到官方原文**。

**工作区范围相关 flag ——【本地实测】**：`-C/--cd <DIR>`（工作根）、`--add-dir <DIR>`（原文「Additional directories that should be writable alongside the primary workspace」）、`--skip-git-repo-check`、`--approve-for-me`（原文「Route approval requests through automatic review using the workspace-write sandbox」）、`--dangerously-bypass-approvals-and-sandbox`。

**平台实现 ——【镜像】**：Linux 用 **Landlock + seccomp**（可选 Bubblewrap 管线 `-c features.use_linux_sandbox_bwrap=true`）；macOS 用 **Seatbelt**（profile 按「沙箱模式 + 可写根 + 受保护路径 + 网络设置」动态生成）；Windows 用 **受限令牌 + job objects**（`windowsSandbox/setupStart` via app-server API）。

> **注意**：Codex 的 Windows 实现（**受限令牌 + job objects**）与 DSH 的 Windows 实现（**`WRITE_RESTRICTED` 受限令牌 + `KILL_ON_JOB_CLOSE` job**）**是同一套底层思路**（`...\dsh-sandbox-windows-acl\README.zh.md` 提到 runner「把子进程包进 `KILL_ON_JOB_CLOSE` job」）。两者都受同样的 Everyone / 硬链接类边界制约。

#### 审批策略 ——【本地实测】只有三值，与镜像冲突

**`codex --help` 的 `-a/--ask-for-approval` 帮助原文（0.148.0）**：

| 取值 | 帮助原文 |
|---|---|
| `untrusted` | Only run "trusted" commands (e.g. ls, cat, sed) without asking for user approval. Will escalate to the user if the model proposes a command that is not in the "trusted" set |
| `on-request` | The model decides when to ask the user for approval |
| `never` | Never ask for user approval. Execution failures are immediately returned to the model |

> ⚠️ **三源冲突（重要）**：
> 1. **【本地实测】0.148.0 的 `-a` 帮助里没有 `on-failure`**，只有上述三值；
> 2. 【镜像】[Basic Configuration](https://mintlify.wiki/openai/codex/configuration/basic) 把 `on-failure` 标为 **DEPRECATED**，并把默认写成 `untrusted`；
> 3. 【镜像】[Approvals](https://mintlify.wiki/openai/codex/concepts/approvals) 又把默认策略写成 **`unless-trusted`**，并把四个值列为 `on-request / unless-trusted / never / on-failure`。
>
> **结论：`ApprovalPolicy` 的权威完整枚举未能确定**；`unless-trusted` 与 `on-failure` 的存在性未能核实；默认值未能核实。**本报告第一版照抄镜像列出的四档（含 `unless-trusted`）是不可靠的，此处更正。** 生产使用请以 `codex --help` 的实测输出为准。

**【镜像】审批提示的五个选项**：`[a]` Accept once、`[s]` Accept for session、`[p]` **Accept and add to policy**、`[d]` Decline、`[c]` Cancel turn，并显示 Suggested rule。**这是 Codex 相对 DSH 的一个明显优势：DSH 只有 `allowed-once`，Codex 可以「接受并加进策略」。**

#### Execution Policies（Starlark 规则）

**【镜像】** 用 **Starlark**（类 Python 语法）写 `prefix_rule()`，**在沙箱之前求值**：

```python
prefix_rule(
    pattern = ["command", ["arg1", "arg2"]],  # 有序 token；列表 = 备选
    decision = "allow",                        # allow | prompt | forbidden
    justification = "Why this rule exists",
    match = [["command", "arg1"]],             # 必须匹配的示例（单元测试）
    not_match = [["command", "other"]]         # 必须不匹配的示例
)
```
`decision` 三值：`allow` / `prompt` / `forbidden`（**完全阻止执行**）。

**【本地实测】可确证的 flag 层**：`codex exec --help` 有 `--ignore-rules`（原文「Do not load user or project execpolicy `.rules` files」）——**说明规则文件确实存在且分 user/project 两级**；但 `prefix_rule` 的完整字段只能引镜像。

#### `codex exec` 非交互模式【本地实测】

`codex exec`（别名 `e`）：prompt 可作参数、可用 `-` 或管道从 stdin 读；子命令含 `resume`、`fork`、`review`。
关键开关：`--json`、`--ephemeral`（不持久化会话）、`--output-schema <FILE>`、`-o/--output-last-message <FILE>`、`--color`、`--skip-git-repo-check`、`--ignore-user-config`、`--ignore-rules`、`-s/--sandbox`、`-a/--ask-for-approval`、`--add-dir`、`-C/--cd`、`-p/--profile`、`--dangerously-bypass-approvals-and-sandbox`。
`codex review` 另有 `--uncommitted`、`--base <BRANCH>`、`--commit <SHA>`、`--title <TITLE>`。

#### `AGENTS.md` 与项目文档【本地实测】

0.148.0 二进制中同时存在 `AGENTS.md`、`AGENTS.override.md`、`project_doc_max_bytes`、`project_doc_fallback_filenames`、`project_root_markers`；内置评审指令原文写明优先级为 **`AGENTS.override.md` → `AGENTS.md` → 配置的回退文件名**，「More-specific guidance wins on conflict」。
【镜像】补充三处位置：`~/.codex/AGENTS.md`（全局）、仓库根 `AGENTS.md`、当前工作目录 `AGENTS.md`，三者合并、越靠近越优先。

> **与 DSH 的对照**：DSH 的对应机制是 `dsh-agent-instructions`，候选名单 `['AGENTS.md','CLAUDE.md']` + 本地 overlay `['AGENTS.local.md','CLAUDE.local.md']`，项目根标记 `['.git']`，**逐目录内容去重**且**没有 override 层**。Codex 用 `AGENTS.override.md` 提供了显式的「更高优先级覆盖」文件，**DSH 没有对等物**——DSH 里要覆盖，只能靠更具体目录的 `AGENTS.md`。

#### 与 DSH 的对照要点

| 维度 | Codex | DSH |
|---|---|---|
| 沙箱三档 | `read-only` / `workspace-write` / `danger-full-access` | **完全同名同序**（DSH 明显借鉴了这套词汇） |
| 多可写根 | ✅ `--add-dir` / `writable_roots` | ❌ 无 |
| 受保护路径 | ✅ `.git/`、`.codex/` 递归只读 | ⚠️ 不在沙箱词汇内（靠 `fs-observation-policy` 与工具层，不是内核保证） |
| 网络控制 | ✅ 独立于文件沙箱的开关；Linux 有托管网络代理 | ❌ **不在词汇中** |
| 审批档数 | 实测 3 值（`untrusted`/`on-request`/`never`） | 2（`ask` / `never`） |
| 「接受并加进策略」 | ✅ | ❌ 只有 `allowed-once` |
| 命令级规则语言 | ✅ Starlark `prefix_rule`（allow/prompt/forbidden + 内联测试） | ⚠️ 无声明式规则语言；需写插件的 `ctx.tools.guard` |
| 指令覆盖层 | ✅ `AGENTS.override.md` | ❌ 无 |
| Windows 隔离 | 受限令牌 + job objects | `WRITE_RESTRICTED` 受限令牌 + `KILL_ON_JOB_CLOSE` job |
| 子 agent 权限收敛 | — | ✅ **DSH 独有且明确**（审批钉 `never`） |

#### 未能核实（Codex）
- **`ApprovalPolicy` 的权威完整枚举与默认值**（三源冲突，见上）。
- **`[sandbox_workspace_write]` 四键的默认值与精确语义**（尤其 `exclude_tmpdir_env_var`、`exclude_slash_tmp`、`network_access`）。
- **项目级 `.codex/config.toml` 是否受支持**（镜像称支持，0.148.0 帮助与字段表未显示）。
- **`[profiles.x]` 内联表是否仍受支持**（帮助只描述文件叠加）。
- `[mcp_servers]` 表结构（0.148.0 字符串池未直接命中 `mcp_servers`，但 `codex mcp add` 帮助称会写入 `~/.codex/config.toml`）。
- `execpolicy` 规则文件的准确路径与 `prefix_rule` 全字段语义（仅本地确证 `--ignore-rules` 与 `.rules` 文件形态）。
- Windows / Linux bubblewrap 沙箱的配置入口（仅镜像描述）。
- `--approve-for-me` 的「automatic review」具体策略、`default_permissions` 的取值集合。

### 3.3 Cursor（IDE Agent + CLI）

#### 规则/指令文件

四类规则：Project Rules（`.cursor/rules/**/*.mdc`，随仓库版本控制）、User Rules（账号级）、Team Rules（Dashboard 下发）、`AGENTS.md`（纯 markdown 替代）。Project Rules **必须**是 `.mdc` 扩展名——同目录的普通 `.md` 因无法声明 frontmatter 而被**忽略**。

frontmatter 三字段的交互：`alwaysApply: true` 无条件注入并忽略 globs/description；`false` + `globs` 在匹配文件进入上下文时附加；`false` + `description` 由 Agent 自行判断；三者皆无则仅 `@` 提及时生效。

**优先级**：Team Rules → Project Rules → User Rules，全部**合并**注入，冲突时靠前者优先；Team Rules 可标 "Enforce this rule"，成员无法关闭。`AGENTS.md` 支持嵌套，**更具体者优先**。旧 `.cursorrules` 属 legacy（"will be deprecated"），等价于 alwaysApply。

```markdown
---
globs: src/components/**/*.tsx
alwaysApply: false
---
- Use named exports, not default exports
```

#### 权限：IDE 与 CLI 是两套不兼容的系统（重要）

**IDE 侧**（`~/.cursor/permissions.json` 用户级 + `<workspace>/.cursor/permissions.json` 仓库级，两文件**数组合并**；顶层键**仅** `mcpAllowlist`、`terminalAllowlist`、`autoRun`）：

```jsonc
{
  "mcpAllowlist": ["github:*", "linear:list_issues"],
  "terminalAllowlist": ["git", "npm:install*"],
  "autoRun": {
    "allow_instructions": ["Read-only inspections of build artifacts under ./dist are fine."],
    "block_instructions": ["Every AWS CLI command should go through approval first."]
  }
}
```
- 一旦文件定义了某个键，**完全覆盖** IDE 内该类型白名单（设置项变只读）；优先级 team admin > permissions.json > IDE 设置。
- `autoRun` 只是给分类器的**自然语言引导**，官方明言 "steering, not enforcement"。
- **IDE 侧没有 denylist 键**（黑名单能力只在 CLI）。

**CLI 侧**（`~/.cursor/cli-config.json` 全局 + `<project>/.cursor/cli.json` 项目级，**项目级只能配 `permissions`**），token 语法，**deny 优先于 allow**：

```json
{
  "version": 1,
  "permissions": {
    "allow": ["Shell(git)", "Read(src/**/*.ts)", "Write(package.json)",
              "WebFetch(docs.github.com)", "Mcp(datadog:*)"],
    "deny": ["Shell(rm)", "Read(.env*)", "Write(**/*.key)"]
  },
  "approvalMode": "auto-review",
  "sandbox": { "mode": "enabled", "networkAccess": "sandbox.json" }
}
```

**Run Modes（GUI 三档）**：Auto-review（白名单命中即执行，其余进沙箱或交分类器）、Allowlist（仅白名单免审批）、Run Everything（**无沙箱、无分类器**）。3.5 起 "Ask Every Time" 弃用（等价于空白名单的 Allowlist）。

**`.cursorignore`**：`.gitignore` 语法，阻断 Agent/Tab/Inline Edit 与 `@` 引用。**关键缺陷（官方明写）：终端与 MCP server 工具无法被 `.cursorignore` 阻断。**

#### 隔离

`sandbox.json` 控制 `type`（`workspace_readwrite` / `workspace_readonly` / `insecure_none`）、`disableTmpWrite`、`networkPolicy.{default,allow,deny}`（**默认 deny**，deny 恒胜；RFC1918 与 `169.254.169.254` 默认封以防 SSRF）。永久写保护路径含 `.cursor/*.json`、`.vscode/**`、`.git/hooks/**`、`.git/config`、`.cursorignore`。

平台实现：macOS **Seatbelt**（`sandbox-exec`）；Linux **Landlock + seccomp**（需内核 ≥6.2 且开启非特权 user namespace；**不满足则回退为逐命令审批**）；**Windows 无对应实现**。

**不隔离之处**：① Run Everything 全无沙箱与分类器；② "需要完整系统访问"的命令**绕过沙箱**并请求审批；③ **Agent 修改工作区文件默认无需审批**（仅配置文件需审批）；④ `.cursorignore` 对终端/MCP 无效；⑤ Cloud Agents 不适用 Run Modes。

**官方自认**：Auto-review 分类器**不是安全边界**，且它跑在 Cursor 托管的小模型上——企业若禁掉那些模型，Auto-review 会被禁用。

#### 未能核实
- IDE 侧是否存在独立 **terminal denylist** 键（参考页只列三个键）。
- `.cursorrules` 与 `.mdc` 同时存在时的**精确运行时优先级**（文档只给迁移步骤）。
- 沙箱内具体 syscall/路径白名单实现细节。

### 3.4 Cline

#### 规则

聚合多来源：`.clinerules/`（或 `.cline/rules/`）、`.cursorrules`、`.windsurfrules`、`AGENTS.md`（含 `~/.agents/AGENTS.md`），全部在 Rules 面板可见且可**逐个 toggle**。全局规则目录：Windows `Documents\Cline\Rules`，macOS/Linux `~/Documents/Cline/Rules`；另搜索 `~/.cline/rules` 与 `~/Cline/Rules`。**工作区规则 > 全局规则**。

支持**条件规则**（frontmatter `paths` glob 数组）：无 frontmatter = 永远生效；`paths: []` = 永不生效；**YAML 解析失败时 fail open**（原文 "Cline fails open"）。

```yaml
---
paths:
  - "src/components/**"
  - "src/hooks/**"
---
# React Component Guidelines
```

#### 权限：Auto Approve + YOLO，**无固定白名单**

Auto Approve **按工具调用逐次评估**，粒度是**开关类别**而非命令模式：Read project files、Read all files、Edit project files、Edit all files、Execute safe commands、Execute all commands、Use the browser、Use MCP servers、Enable notifications。

**Cline 没有固定白名单**：命令的 `requires_approval` 标志由**模型**按命令与参数自行标注。官方只给示例：「通常安全」`npm run build` / `npm test` / `git status` / `ls -la`；「通常需审批」`npm install <pkg>` / `rm -rf <path>` / `mv` / `sed -i`。

**YOLO Mode** 勾选后免审批范围覆盖任意位置文件操作、所有终端命令、浏览器动作、MCP 工具、**以及 Plan→Act 模式切换**；官方以 "**Warning: This is dangerous.**" 标注它关闭全部安全检查。

**`.clineignore` 即将弃用，且官方明确它「不是安全或访问控制边界」**——被忽略的文件仍可通过显式 `@` 提及或 shell 命令读到。唯一被文档化的强制型 denylist 是用户自写的 **`PreToolUse` hook**（工作区 `.clinerules/hooks/PreToolUse`、全局 `~/Documents/Cline/Hooks/`；文件名须与事件名完全一致、无扩展名、需 shebang 与可执行位）。

#### 隔离：**完全没有**

Cline 文档中**没有任何 OS 级沙箱或容器机制**。它的约束全部是「审批门 + 模型自报风险 + 可回滚快照 + hook 拦截」。

**它的真正安全网是 shadow Git 快照**：Checkpoint 指示器提供 **Restore Files**（回滚文件、保留对话）/ **Restore Task Only** / **Restore Files & Task**；基于独立于项目 Git 的 **shadow Git 仓库**，**默认开启**，**能捕获未被 Git 跟踪的文件**。官方明确：Checkpoints 让 Auto Approve "变得可行"。

**Plan / Act**：Plan mode 可读代码、跑搜索，但**不能改文件、不能执行命令**；Act mode 才放开。

#### 未能核实
- Auto Approve / YOLO 的**持久化配置键名**（官方只描述 UI 开关）。
- Auto Approve 每个类别到**具体工具名**的完整映射。
- 是否存在 MCP **server 级或工具级**的更细 auto-approve 粒度。
- `.clinerules/` 与 `.cline/rules/` 同名文件的消解规则。

### 3.5 Google Gemini CLI

#### 上下文文件与层级发现

默认 `GEMINI.md`，三层：① 全局 `~/.gemini/GEMINI.md`；② **环境/工作区**——工作区目录及**父目录**向上搜索，止于 `context.memoryBoundaryMarkers`（默认 `[".git"]`）；③ **JIT 上下文**——工具访问某文件时向上扫描到 trusted root。所有命中文件**拼接**后随每次 prompt 发送。

**键名纠正**：不是 `contextFileName`，官方键是 **`context.fileName`**（可传数组）：

```json
{
  "context": {
    "fileName": ["AGENTS.md", "CONTEXT.md", "GEMINI.md"],
    "discoveryMaxDirs": 200,
    "memoryBoundaryMarkers": [".git"],
    "includeDirectories": ["path/to/dir1", "~/path/to/dir2"],
    "loadMemoryFromIncludeDirectories": true,
    "fileFiltering": { "respectGitIgnore": true, "respectGeminiIgnore": true }
  }
}
```
`@./components/instructions.md` 可模块化导入；`/memory show` 查看拼接结果；`.geminiignore` 用 `.gitignore` 语义。

#### 审批与工具策略：**Policy Engine 是唯一确定性机制**

**审批模式**：`general.defaultApprovalMode` 只接受 `default` / `auto_edit` / `plan`；**YOLO 只能经命令行启用**（`--yolo` 或 `--approval-mode=yolo`，二者**不能同时使用**）。

**Policy Engine（TOML）**——官方已将 `tools.exclude` 标记为 **deprecated**，推荐改用 `decision = "deny"` 的规则；**无 `argsPattern` 的全局 deny 会把该工具完全从模型记忆中移除**：

```toml
# ~/.gemini/policies/my-rules.toml
[[rule]]
toolName = "run_shell_command"
commandPrefix = "rm -rf"
decision = "deny"
priority = 100
denyMessage = "Deletion is permanent"

[[rule]]
mcpName = "my-jira-server"
toolName = "search"
decision = "allow"
priority = 200
modes = ["default", "autoEdit"]
```

规则字段：`toolName`（含 `*`、`mcp_server_*` 通配）、`mcpName`、`argsPattern`（正则作用于参数的稳定 JSON 串）、`commandPrefix` / `commandRegex`（互斥）、`subagent`、`toolAnnotations`、`decision`（`allow`/`deny`/`ask_user`）、`priority`(0–999)、`modes`、`interactive`、`allowRedirection`。

**优先级公式**：`final_priority = tier_base + toml_priority/1000`，tier base 为 Default 1、Extension 2、**Workspace 3**、User 4、Admin 5。

旧式键仍存在：`tools.core`（**不是 `coreTools`**，内置工具 allowlist）、`tools.allowed`（免确认）、`tools.confirmationRequired`（**优先于 allowed 与 core**）、`tools.exclude`（deprecated）。

**MCP**：`mcpServers` 逐服务器配置；`trust: true` **绕过该服务器全部工具确认**；`excludeTools` **优先于** `includeTools`；与扩展配置合并时排除项取并集、包含项取**交集**。

#### 沙箱

**默认关闭**。启用优先级：`-s`/`--sandbox` ＞ `GEMINI_SANDBOX` 环境变量 ＞ `settings.json` 的 `tools.sandbox`（配置参考称其为 "Legacy full-process sandbox"）。**注意：`--yolo` 会默认启用沙箱。**

五种后端：macOS **Seatbelt**（`SEATBELT_PROFILE` 六档）、**Docker/Podman**（默认镜像 `ghcr.io/google/gemini-cli:latest`）、**Windows 原生**（`icacls` 打 Low Mandatory Level，**改动持久化**，需手动复位）、**gVisor/runsc**、**LXC/LXD**（实验性）。`SANDBOX_MOUNTS="/host:/ctr:rw"`（默认 `ro`）。

另有 **Tool-level sandboxing**：`security.toolSandboxing`（默认 `false`）只隔离单个工具。以及**沙箱权限扩展**弹窗：命令因沙箱拒绝失败时请求目录/网络权限，仅对该次运行生效。

**Workspace trust**（`security.folderTrust.enabled`，**默认关闭**）：不信任时忽略工作区 `.gemini/settings.json`、忽略项目 `.env`、禁止改扩展、**禁用工具自动接受**、禁止 MCP 连接。headless 下遇不信任工作区抛 `FatalUntrustedWorkspaceError`。

#### 不隔离之处（官方明写）

① 沙箱**默认关闭**，`security.toolSandboxing` 默认 `false`；
② **Workspace 策略层当前完全失效**——`.gemini/policies` 下的策略 "will not have any effect"，请用 User 或 Admin 策略（官方引 **issue #18186**）；
③ 管理员策略有安全前提（Linux/macOS 标准目录须 root 所有且组/他人不可写；Windows `C:\ProgramData` 下普通用户不得有写权限），否则该目录策略被**忽略**；
④ `trust: true` 的 MCP 服务器与 trusted workspace 会绕过确认；
⑤ 沙箱 "reduces but doesn't eliminate all risks"。

#### 未能核实
- **`coreTools`**：官方 settings 参考中不存在该键（实为 `tools.core`）。
- **`autoAccept`**：**未能核实**该键；接近语义的是 `tools.allowed`、`security.enablePermanentToolApproval` 等。
- **`--allowed-tools` 的存续**：官方 reference 仍记录该 flag，但仓库有 PR #18508 提议弃用，**未合并进文档**，故当前生效状态未能最终确认。
- 顶层 `sandbox` 键（文档中在 `tools.sandbox`）。
- 依赖仓库原文的条目（schema JSON、源码常量）——GitHub 不可达。

### 3.6 OpenHands

**术语迁移**：V0 文档叫 *runtime*，V1 改叫 *sandbox*（Docker / Process / Remote），但配置开关迁移期仍叫 `RUNTIME`（`docker` 默认、`process` 即旧 `local`、`remote`）。`config.toml` 必须与启动命令同目录或用 `--config-file`；**GUI 设置 UI 优先级高于文件**。

> ⚠️ **两页官方文档矛盾**：V0 配置页把 `security_analyzer` 默认写成空字符串 `""`，环境变量页写 `"llm"` 且 `SECURITY_ENABLE_SECURITY_ANALYZER` 默认 true。**未能核实以哪个为准。**

SDK 层把两件事**拆开**：confirmation policy（`AlwaysConfirm` / `NeverConfirm` / `ConfirmRisky`）决定何时要人批；security analyzer 只输出 `LOW/MEDIUM/HIGH/UNKNOWN`。官方明确「**只设置 analyzer 不会改变确认行为**」，且 `conversation.execute_tool()` **会绕过分析器与确认策略**。

**headless**：**永远运行在 `always-approve` 模式，不可更改**；`--llm-approve` 在 headless 下不可用。CLI 全局选项含 `--always-approve`、`--llm-approve`、`--override-with-envs`、`--exit-without-confirmation`。

**最强警告（Local/Process）**：官方明确「Local Runtime **不做任何沙箱隔离**，agent 可直接访问并修改你机器上的文件」，仅限受控环境；Windows 下该模式只支持 CLI 与 headless。

### 3.7 Aider

**能改哪些文件**：只有被加入 chat session 的文件才会被编辑。方式为命令行位置参数/`--file`，或会话内 `/add`。
**只读引用**：`--read`（可多次）或 `.aider.conf.yml` 的 `read:` 列表；会话内 `/read-only`。

**git 深度绑定**：官方措辞是「aider works best with code that is part of a git repo」，无仓库时会**询问是否创建**。每次编辑自动以描述性提交信息提交，脏文件先被单独提交。可 `--no-auto-commits` / `--no-dirty-commits` / `--no-git`（官方提醒自行备份）。

**编辑范围过滤**：`--aiderignore`（默认 `.aiderignore`，位于 git 根）、`--subtree-only`、`--add-gitignore-files`（**默认 false**，即 `.gitignore` 中的文件默认不在编辑范围）。

**lint/test 与确认**：内置多语言 linter，`--auto-lint` **默认 true**；`--lint-cmd "python: flake8 …"`；测试用 `--test-cmd` + `--auto-test`（**默认 false**）。`--yes-always` 表示「对所有确认一律回答 yes」。架构/编辑器双模型：`--architect` + `--editor-model` + `--editor-edit-format`，`--auto-accept-architect` 默认 true。

**配置优先级**：`.aider.conf.yml` 按 **home → git 仓库根 → 当前目录** 顺序加载，后加载者覆盖前者；还可用 `AIDER_*` 环境变量、`.env`、命令行开关。

> **是否沙箱（必须明确）**：官方文档**没有提供任何沙箱、容器隔离或命令白名单机制**。`--lint-cmd` / `--test-cmd` / `/run` / `--suggest-shell-commands`（默认 true）都是**在本进程所在环境执行 shell 命令**，因此直接在本机运行时即在本机执行。官方给出的隔离路径只有自建/使用 Docker 镜像（`paulgauthier/aider`），容器模式下 `/run` 在容器内执行。

### 3.8 MCP（作为「工具挂载机制」本身）

**原语**：服务端暴露 Tools（可执行函数）、Resources（上下文数据）、Prompts（模板）；客户端侧原语为 Sampling、Elicitation、Logging。**Roots 是「应尊重」的协调机制而非安全边界**——规范只要求服务端 SHOULD respect，真正隔离必须靠 OS 权限或沙箱。

**传输**：`stdio`（客户端把 server 拉起为子进程，换行分帧，**stdout 不得混入非 MCP 消息**）与 `Streamable HTTP`（单一 endpoint 支持 POST/GET，可用 SSE、`MCP-Session-Id`、`MCP-Protocol-Version`；**须校验 `Origin` 防 DNS rebinding**，本地部署应只绑 127.0.0.1）。旧的 HTTP+SSE 已被取代。

**宿主如何门控工具**——官方 *Client Best Practices* 的标准做法：
- **渐进式发现**：`search_tools` 元工具 → `get_tool_details` 拉全量 schema → 执行；
- **按 server 分组展示**；
- **动态 `enable_server`/`disable_server`**（任务结束后断开以释放上下文）；
- 收到 `notifications/tools/list_changed` 时重建检索索引；
- **跨 server 数据流**：「一个 server 的工具结果是另一个 server 的不可信输入」，broker 必须对沙箱发起的调用沿用同样的人工确认策略。

**命名**：规范要求工具名 1–128 字符、区分大小写、仅 `A-Za-z0-9`、`_`、`-`、`.`，SHOULD 在**单 server 内唯一**。**跨 server 聚合的命名空间拼接约定不在 MCP 规范中**，由各宿主自定（如 DSH 用 `mcp__<server>__<tool>`）。

**官方安全指南**（*Security Best Practices*）核心条目：
| 风险 | 官方要求 |
|---|---|
| **Confused deputy** | proxy **MUST** 做 per-client consent；consent 页须显示客户端名/scope/redirect_uri 并做 CSRF 与防 iframe；redirect_uri **MUST** 精确字符串匹配；`state` 单次有效且只在同意后写入 |
| **Token passthrough** | 明确禁止的反模式；MCP server **MUST NOT** 接受任何不是显式颁发给自身的 token |
| **SSRF** | OAuth 元数据 URL 可被指向内网 / `169.254.169.254` / localhost 或经重定向、DNS rebinding 打内网；缓解为强制 HTTPS（仅 loopback 例外）、屏蔽私有/链路本地网段、校验重定向目标、服务端用 egress proxy；**不要手写 IP 校验**（八进制/十六进制/IPv4-mapped IPv6 可绕过） |
| **Session hijacking** | 会话 ID 必须安全随机；服务器 **MUST NOT** 用 session 作认证，SHOULD 绑定 `<user_id>:<session_id>`；一条攻击路径正是滥用 `notifications/tools/list_changed` 让客户端拿到「未被察觉启用的工具」 |
| **本地 MCP server 被攻陷** | 支持一键配置的客户端 **MUST** 在启动前获得明确同意并**完整展示将执行的命令**；SHOULD 标注 `sudo`/`rm -rf`/网络与文件系统访问等危险模式、在沙箱中运行、最小默认权限 |
| **OAuth 授权 URL 校验** | 客户端 **MUST** 只允许 http/https（生产必须 https），拒绝 `javascript:`/`data:`/`file:`；**MUST NOT** 用 shell 打开 URL |
| **stdio 代理提权** | 代理架构下 XSS 可升级为宿主 RCE；代理 SHOULD 沙箱化、限制文件系统、记录 stdio 使用 |
| **Scope 最小化** | 基础 scope 最小集 + 按需经 `WWW-Authenticate` 提权，避免 `*`/`all` 类大 scope |

**工具投毒（tool poisoning）**：在官方 *Security Best Practices* 与官方索引 `llms.txt` 中**均未出现该术语**。官方最贴近的强制性约束是：client **MUST** 把工具 `annotations` 视为**不可信**（除非来自可信 server）；tools 文档要求「应当始终有人在环、可拒绝工具调用」，应用 SHOULD 明确展示暴露给模型的工具、**在调用前向用户展示工具输入**、校验工具结果再喂给 LLM、设超时并记录审计日志。

**宿主门控的真实例子**：
- **OpenHands**：`[mcp]` 支持 SSE / Streamable HTTP / stdio；UI 可**禁用服务器而不删除配置与凭据**；CLI `openhands mcp enable/disable`。
- **VS Code**：本地 server 首次启动需**信任确认**；可整体启停；**按 server 分组的逐工具开关**；官方明确「**工具可用性与工具审批是两件事，启用工具不绕过审批控制**」；stdio server 可设 `sandboxEnabled` 并用顶层 `sandbox` 限制 `filesystem.allowWrite/denyRead/denyWrite` 与 `network.allowedDomains/deniedDomains`（仅 macOS/Linux），**沙箱化后工具确认会被自动批准**。

#### 未能核实
- MCP「工具投毒」术语与专门缓解措施（官方页无此术语）。
- 官方「prompt injection」专章（未见独立条目）。
- 工具名跨 server 命名空间的具体分隔符（规范未定义）。
- MCP 2026-07-28 版 tools/transports 正文细节（本轮只核实 2025-11-25 版正文 + 2026-07-28 版 Client Best Practices）。

### 3.9 从对照中得到的六条可迁移经验

1. **「工具可用性」与「工具审批」必须分开设计**（VS Code 官方措辞）。DSH 正是这么做的：`ToolRestriction` 管可见性，`guard`/`pre-execute` 管执行策略，`approval` 管人工介入——三者独立。
2. **白名单优于黑名单，deny 必须单调**。Cursor CLI 的 `deny` 优先、Gemini 的 `decision="deny"`、DSH 的 `ToolGuard`（返回理由即拒绝且**无法被后续监听器翻回 allow**）——都是同一原则。Cline 没有固定白名单（靠模型自报风险）是**最弱**的设计。
3. **忽略文件（ignore file）不是安全边界**。Cursor 官方承认 `.cursorignore` 管不了终端与 MCP；Cline 官方承认 `.clineignore` 不是访问控制边界且即将弃用。**任何 agent 的 ignore 文件都不能当权限机制用。**
4. **分类器/LLM 风险判定不是安全边界**。Cursor Auto-review 官方自称 "not a security boundary"；OpenHands 官方明确「只设置 analyzer 不会改变确认行为」。**别把安全赌在模型判断上。**
5. **确定性优先级 + admin 层是唯一能过合规的设计**。Gemini CLI 的 `tier + priority`（Default 1 < Extension 2 < **Workspace 3** < User 4 < Admin 5）是三者中唯一给出**确定性判定与不可覆盖的管理层**的机制；Claude Code 的 managed settings（「no other level, including command line arguments, can override a managed permission rule」）与 Codex 的六层配置合并同类；DSH 的等价物是「patch 层序 + `id` 定向 + 后者胜」与「bundle 层不可被 preset 覆盖」。

6. **「记住这次批准」是可用性的分水岭，而 DSH 缺这一层。** Claude Code 有「Yes, and don't ask again」（Bash 命令与域名**按仓库永久保存**）；Codex 的审批提示有 `[p] Accept and add to policy`；Gemini CLI 有 `security.enablePermanentToolApproval` 与 Policy Engine 里 `decision = "allow"` 的持久规则；**DSH 只有 `allowed-once`**（`...\dsh-user-approval\README.zh.md` 限制 2：「结果词汇包含 `allowed-once`，但不含 `allow-always`、已记住的规则、撤销或授权存储」）。

   → **在 DSH 上做长时间自主任务，正确的办法不是「忍受频繁审批」，而是「把沙箱边界预先设到任务真正需要的范围」**（见 §5 的五套配方）。DSH 用「工作区即边界」替代了「规则记忆」。

## 4. 安全与工程实践

### 4.1 最小权限原则（在 DSH 上怎么落地）

DSH 的默认姿态是相当保守的（`workspace-write` + `ask`），但**这个姿态的三个前提经常不成立**：

| 前提 | DSH 现实 | 应对 |
|---|---|---|
| 「`ask` 会真的问人」 | `ask` 只在有应答者时问；无头/不完整组合 → `unavailable` → **拒绝**（fail-closed，这条是安全的） | 无头场景**故意**用 `never`，别指望 `ask` |
| 「`workspace-write` 挡得住写」 | Windows 上 Everyone/硬链接边界可绕过；读写不同侧（读完全不设防） | 敏感仓库用 `read-only`；或让 DSH 看不到敏感目录（另开工作区） |
| 「藏掉 bash 就安全了」 | `write`/`edit` 仍在；MCP 工具仍可能写 | 三层一起收：沙箱模式 + 工具集 + 工作区范围 |

### 4.2 路径穿越防御

DSH 在**两处**做防御，机制不同：

**(a) `ctx.fs` 层（`fs-sandbox`）——规范化后检查包含关系**
证据：`...\dsh-fs-sandbox\README.zh.md`「威胁模型」：
> 「围栏是在可信代码中检查模型控制路径的策略，而非内核边界…『规范化后检查包含关系』就是该接口的完整答案。」
> 「解析到系统调用之间残留的 TOCTOU 通过写入前立即重新规范化来缩小，并为该威胁模型所接受；**内核严密边界需要 `openat2` 一类原语，其可移植性成本在此不值**。」

**符号链接**：`workspace-write` 下**立即重新规范化**目标路径再检查——「被变更的正是这个新目标，因此**工具解析后被替换的符号链接祖先也会被发现**」。证据：同上「变更如何被围栏」。`fs-local` 补充：realpath 派生的目标身份让**别名共享 stale 守卫**，且「writes through a symlink update its target without replacing the link」。证据：`...\dsh-fs-local\lib\types\index.d.ts` 模块注释。

**(b) 内核/令牌层（`sandbox-local`）** —— 这才是真边界。bwrap 用私有 PID namespace + procfs，所以「**procfs 魔法链接无法绕过挂载**」；Seatbelt 每个根都规范化（`/tmp` 就是 `/private/tmp`）；Windows 用受限令牌的 pass-2 检查。

**明确的残留风险**：
- `fs-sandbox` 的检查是**进程内策略检查，不是内核边界**——「对抗性宿主进程不在范围内」；
- **`readonly` 模式下 `read` 工具不设防**：`dsh-tool-fs\README.zh.md`「`read` 与 `read_image` 的路径授权完全由 `ctx.fs` 负责」；
- **symlink 指令文件跨信任边界**：「最终组件是 symlink 的候选文件会被解析并加载其目标，因此**克隆仓库可以将树外文件内容呈现为较低优先级的工作区指引**」——证据：`...\dsh-agent-instructions\README.zh.md`「已知限制」。**加载不受信任仓库时，请用文件系统策略门禁或 OS 沙箱限制 `ctx.fs`。**

### 4.3 环境变量泄漏

DSH 在这方面做得比多数同类好，有三层：

1. **MCP stdio 子进程**：环境以 `scrubbedParentEnv()` 为基座——**删除匹配 `/KEY|PASSWORD|SECRET|TOKEN/i` 的所有环境名 + 所有 `DSH_*`**，再合并你显式配的 `env`。证据：`...\dsh-mcp-client\README.zh.md`「环境清洗（stdio）」。
2. **模型 shell 的环境**：`ctx.shellEnv` 注册表在**每次 shell 调用**重建 `DSH_*` 命名空间——**ambient `DSH_*` 值被执行器丢弃**，只注入注册表当前快照；内置键 `DSH_HOME` / `DSH_SHELL` / `DSH_SESSION_ID` 为保留键，插件不能占用。证据：`...\dsh-shell-env\lib\index.js` 第 27–34 行、第 21–25 行、第 80–96 行。
3. **凭据存储**：`$DSH_HOME/.credentials.yaml`（provider 管理的可写文档）+ 环境变量 + 项目/用户 `.env` 回退；「Models 页面只写管理文档，**绝不物化到进程环境**」。证据：`...\dsh-base\cordis.patch.yml` 第 93–98 行注释。

**仍需注意**：
- `.env` 与 `.credentials.yaml` 都在 `$DSH_HOME` 下；`workspace-write` 模式下**模型读不到 `$DSH_HOME`（除非 cwd 在那儿）**，但**没有读侧沙箱**——如果模型能让 shell 以别的身份跑，读侧就没了。**Windows 上尤其注意：只管辖写。**
- 设置文档的 API 面：任何协议接口必须传 `redactSecrets: true`；但 README 明确警告「`redactSecrets` **并非一条可被证明的协议边界**」——只能经由 union/intersection/transform 抵达的 `role('secret')` 字段会被原样返回。证据：`...\dsh-settings\README.zh.md`「已知限制」第 1 条。**不要把 secret 放在只能经由 union 抵达的位置。**

### 4.6 审批疲劳的缓解

DSH 的结构性优点与缺点都很清楚：

**优点（防疲劳）**：
- 只有 `allowed-once`，**没有 always-allow**——不会积累一堆静默生效的规则；
- 严格的**升权阶梯** + `justification` **必须是非空的一句话句子**（`validateEscalationArgs`）——不可能「顺手点同意」；
- **非升权请求永不提示人类**——不会为无效请求打扰用户。证据：`...\dsh-sandbox\lib\types\escalation.d.ts`；
- 沙箱拒绝是**结果事实**（`sandbox: { mode, denied: true }`），不是静默重试。

**缺点（致疲劳）**：
- 每次都问 → 长任务里频繁打断；
- Web 审批面板**只能「仅本次/拒绝」**（证据：`...\dsh-client-ui-approval\README.zh.md` 限制条）——用户没有办法说「这种以后别问了」；
- **缓解手段只有两个**：`/permission` 升到 `danger-full-access`（一次性大体放开，风险高），或把工作流设计成「不需要升权」（预先用 `workspace-write` + 合适的 cwd，让绝大多数合法操作本来就在允许集内）。

> **【推断/建议】** 工程上最有效的抗疲劳做法：**把工作区 cwd 设到真正需要改的目录**，而不是设到很上层再靠升权；并在 preset 里避免挂载那些会频繁触发沙箱边界的能力（例如让模型用 `read`/`edit` 而非 `pwsh` 改文件）。

### 4.7 多智能体下的权限继承

**这是 DSH 一个设计得非常明确、且值得称赞的点。**

**规则**：**子智能体的权限 ≤ 父智能体，且审批被钉死为 `never`。**

证据：`...\dsh-subagent\lib\types\child-agent.d.ts`：

```ts
/** Policy seeded onto a child session's log at the delegation boundary. */
export interface DelegatedPolicyOverrides {
    /** The parent session's explicit sandbox-mode override, or `undefined` without one. */
    readonly sandboxMode: SandboxMode | undefined;
    /**
     * `'never'` whenever the approval capability is composed, `undefined`
     * otherwise: a delegated child acts only within the sandbox scope fixed at
     * delegation, so its asks are rejected deterministically.
     */
    readonly approvalPolicy: 'never' | undefined;
}
/**
 * Capture the policy to seed into one delegation. Call synchronously before
 * the child start's first await: a later parent switch belongs to the
 * parent's future, not to this child. **Only the parent session's explicit
 * sandbox override is captured — never deployment defaults or one-shot
 * grants** — and the approval policy is pinned to `'never'` regardless of the
 * parent's own policy.
 */
export declare function captureDelegatedPolicyOverrides(parent: Agent): DelegatedPolicyOverrides;
```

逐条解读：
1. **只捕获父会话的「显式沙箱模式覆盖」**——不捕获部署默认值，**也不捕获一次性升权授权**。所以父级刚刚获批的 `danger-full-access` **不会**传给子级。
2. **审批策略无条件钉 `never`**——子 agent **不可能**通过审批拿到更宽权限。
3. **捕获时机同步、在任何 `await` 之前**——「a later parent switch belongs to the parent's future, not to this child」。**父级后续切换模式不会追溯影响子级。**
4. 事件以 `source: 'delegation'` 追加在**未发布的创建窗口内**，且「Appends land **after any fork seed**, so fresh policy wins stale seed state; later child switches still win over these events」——**fork 继承来的旧策略被新策略覆盖**。

模型侧看到的原文（**逐字**，证据：`...\dsh-subagent\README.zh.md`「子级委派范围声明」；**本会话 runtime context 中就有这一整段**，本会话运行时观察）：

```markdown
You are a delegated subagent: your permission scope was fixed when you were started and cannot be widened from inside this session — operations that require approval are rejected automatically. When the job needs access beyond that scope, do not retry the denied operation; state the limitation in your reply so the delegating agent can handle it.
```

这段「位于沙箱策略与审批策略语句之后」——**三条运行时上下文按 沙箱 → 审批 → 委派范围 的顺序排列**（本会话 runtime context 正是这个顺序：`Current DSH file policy: workspace-write…` → `Approval policy: never…` → `You are a delegated subagent…`）。**这解释了为什么本会话的审批策略是 `never` 而父级报告的是 `ask`：子 agent 的审批被设计性地钉死为 `never`，与父级无关。**（【推断】基于 `captureDelegatedPolicyOverrides` 行为 + 本会话三段文本顺序；这是对本报告开头那处矛盾的完整解释。）

**这套设计的工程价值**：
- **不可能出现「子 agent 权限升级」**——多智能体系统最常见的横向移动路径被堵死；
- **不需要在委派时手工传权限**——自动向下收敛；
- **代价**：子 agent 无法完成需要审批的操作，必须**把限制回报给父级**由父级处理（这正是上面那段文本教的）。

**其它与权限相关的多智能体事实**：
- **深度**：`resolveChildDepth(parent, maxDepth)`——「The persisted parent header is the monotone floor, so **a resumed parent cannot delegate as if it were top-level**」；超限抛 `SubagentDepthError`。
- **子 agent 加入父方的 preset 组装**：「子 agent（subagent）会加入其父方的组装，因此它看到的工具与 prompt 段落和创建它的 agent 相同」。证据：`...\dsh-agent-presets\README.zh.md`。
- **子 agent 可以有自己的人格与工具过滤**：`ChildComposition { persona?: string; toolFilter?: ToolRestriction }`，且「a per-child restriction **intersects** with everything its chain admits」（只减不增）。证据：`...\dsh-subagent\lib\types\child-agent.d.ts` 第 71–106 行。
- **ralph**：每一轮一个全新子 agent，「工作区是唯一的跨 Round 长期记忆」，权限同受上述收敛规则约束。证据：`...\dsh-tool-ralph\README.zh.md`。
- **`maxDepth: provider-managed`**：Codex / Claude Code 子级 provider 自行管理深度（本机 preset 中这两行默认 `disabled: true`）。

### 4.7.1 ⭐ 同一次运行中的父/子审批策略对照（本报告的一手实验证据）

这是本报告作者在**同一次运行、同一个进程、同一次委派**中直接观察到的对照。它不是推断，而是两份 runtime context 原文的逐字比对。

| 层级 | approval policy | runtime context 原文（逐字） |
|---|---|---|
| **父会话**（顶层，人类交互） | **`ask`** | `Approval policy: ask. Operations that require approval may ask through the configured answerers; without an available answerer, the request fails closed.` |
| **子会话**（本报告作者；被 `subagent` 工具委派） | **`never`** | `Approval prompts are disabled in this session: actions that require approval are rejected automatically — do not request sandbox escalation (do not set sandbox_permissions).` |

**这两段文本都能在官方子系统文档里找到出处**（证据：`docs/subsystems/approval.zh.md` 与 `...\dsh-user-approval\README.zh.md`「模型体验」）：
- `ask` 的贡献文本对应官方 `ApprovalPolicy` 的 JSDoc：「`'ask'` (the default) — delegate to the composed answerers; with none composed the chain falls through to the fail-closed `'unavailable'`」；
- `never` 的贡献文本对应：「`'never'` — never prompt anyone: every ask resolves `'rejected'` deterministically. **The strict headless stance (CI, unattended runs)** and the policy whose outcome is knowable without asking.」

#### 为什么子 agent 必然是 `never` —— 这是配套设计，不是巧合

子 agent 是**后台无人值守执行**的：它没有前台人类可问。DSH 在这里做了两个**互相配套**的决定：

1. **能力上不可问** → 审批策略钉 `'never'`。证据：`captureDelegatedPolicyOverrides` 的 JSDoc：「the approval policy is pinned to `'never'` **regardless of the parent's own policy**」。
2. **边界上不放大** → 沙箱模式只继承**父会话的显式覆盖**，「never deployment defaults or one-shot grants」。证据：同上。

组合起来的语义是：**子 agent 被冻结在「委派那一刻父级显式声明的沙箱范围」内，且永远不能通过审批索取更多。** 这就是「子 agent 的权限范围在启动时被固定，无法从会话内部放宽」这句话的机制来源。

#### ⚠️ 由此产生的一个真实风险（务必在工程上处理）

> **委派给子 agent 的工作，其危险操作不会弹审批。**

具体后果：
- 父会话里一个「写系统目录」的操作会**弹审批**（`ask`）；同样的操作在子 agent 里**直接被拒绝**（`never`）——这本身是**安全**的；
- 但如果父会话在委派时**已经把沙箱放宽到 `danger-full-access`**（或该会话的显式覆盖就是 `danger-full-access`），子 agent 会**继承这个宽范围**，而**它自己的审批是 `never`**——即「**宽沙箱 + 零审批**」的组合，且**不会再有任何人工确认**。
- 换句话说：**委派会把「需要人工确认才能越界」变成「越界范围已预先授予、且不再确认」。**

**缓解措施（三条，按优先级）**：
1. **委派前不要把父会话切到 `danger-full-access`**。子 agent 会继承它。若要放宽，只放宽到 `workspace-write` 并把工作区设对。
2. **在委派提示词里显式限定范围**——这正是 DSH runtime context 里那段「委派范围声明」的价值所在：
   > `You are a delegated subagent: your permission scope was fixed when you were started and cannot be widened from inside this session — operations that require approval are rejected automatically. When the job needs access beyond that scope, do not retry the denied operation; state the limitation in your reply so the delegating agent can handle it.`
3. **用 `ChildComposition.toolFilter` 收窄子 agent 的工具集**（只减不增），让它在能力层面就够不着危险工具，而不是靠沙箱兜底。

> **【推断】** 这三条缓解里，第 2 条的效果最依赖模型遵守指令；第 3 条是结构性的（工具根本不可见），因此**对安全关键场景应优先用第 3 条**。这与 §3.9 经验 1「工具可用性与工具审批是两件事，必须分开设计」一致——安全关键时用「不可见」而不是「会拒绝」。

## 5. 「精细设定」操作手册：五套场景配方

> 下面每套配方分三层给出：**① host 层**（bundle/profile patch，或 `$DSH_HOME/cordis.patch.yml`，或 `--patch`）；**② preset 层**（`agent.cordis.yml`）；**③ 运行时**（用户操作）。凡不是从本地文件逐字核实的组合，标 **【配方/推断】**。

### 5.1 场景 A：只读调研（读代码、查资料、不落盘）

**目标**：模型可以读一切、可以上网查资料，但**绝对不能改任何文件**。

**① host 层**（`$DSH_HOME/cordis.patch.yml`）：
```yaml
# 【配方】三个 config 块整体替换，故必须重述原键
- id: sandbox-policy
  config:
    mode: read-only
    workspaceRoot: !!js process.cwd()
- id: approval
  config:
    policy: ask              # 只读模式下基本不会触发，保留以防未来加工具
- id: permission
  config:
    defaultPreset: read-only
    presets:
      read-only:        { sandbox: read-only,        approval: ask }
      workspace-write:  { sandbox: workspace-write,  approval: ask }
      danger-full-access: { sandbox: danger-full-access, approval: never }
```

**② preset 层**（新建 `~/.dsh/.agent-presets/readonly-survey/`，复制 `standard` 后改）：

```yaml
# 【配方】readonly-survey/agent.cordis.yml
- id: persona
  name: '@deepseek-ai/dsh-persona'
  config:
    prefix: |-
      You are a read-only research assistant. Your job is to read, search, and explain.
      Never attempt to modify files: this session runs under read-only policy, so
      write/edit/bash-mutations will be denied. Report findings as text in the conversation.

- id: agent-instructions
  name: '@deepseek-ai/dsh-agent-instructions'
  config: { maxBytes: 65536 }

# 只保留只读类文件工具
- id: tool-fs
  name: '@deepseek-ai/dsh-tool-fs'          # read / read_image 可用；write/edit 会被沙箱拒
- id: tool-fs-search
  name: '@deepseek-ai/dsh-tool-fs-search'
  config: { sampleOverCapGlobResults: false }

# 有网查资料
- id: tool-web
  name: '@deepseek-ai/dsh-tool-web'
  config:
    fetch: true
    fetchMaxOutputChars: 60000
    searchTimeoutMs: 60000

- id: tool-ask-user
  name: '@deepseek-ai/dsh-tool-ask-user'
- id: tool-todo
  name: '@deepseek-ai/dsh-tool-todo'

# 明确不挂：tool-pwsh / tool-bash / tool-subagent* / tool-workflow / tool-ralph / tool-jobs
# 若要更彻底，连 tool-fs 的 write 也藏不了（同一插件），靠沙箱模式兜底。
```

**③ 运行时**：`/permission` 应显示「仅可查看」。

**为什么两层都要**：host 层保证「即使 preset 里有 write 工具也写不进去」；preset 层保证「模型根本看不见写工具，不会浪费轮次尝试」。

**⚠️ Windows 特有问题**：`read-only` 下 PowerShell 会退化成 ConstrainedLanguage，所以**本场景不要挂 `tool-pwsh`**（否则模型会看到一堆莫名其妙的失败）。证据：4.2 / 2.12 节的 ACL 限制条。

### 5.2 场景 B：单目录改代码（日常开发，最常用）

**目标**：模型能读写**一个仓库**，出了这个目录就写不了。

**① host 层**：用**随附默认值即可**——`workspace-write` + `ask`（证据：`...\dsh-base\cordis.patch.yml` 第 205–241 行）。**唯一要做的是从目标目录启动**：

```powershell
cd D:\path\to\repo
dsh web                 # 或 dsh --profile headless "..."
```

这样 `SessionHeader.cwd` = 该仓库目录，`workspace-write` 的写入边界就是它。

**② preset 层**：直接用随附 `standard`（`~/.dsh/.agent-presets` 里没有同名时自动用随附的）。若要微调，复制 `standard` 改名，例如：
```yaml
# 【配方】features 分支开发模式
- id: tool-fs
  name: '@deepseek-ai/dsh-tool-fs'
- id: tool-fs-search
  name: '@deepseek-ai/dsh-tool-fs-search'
- id: tool-pwsh
  name: '@deepseek-ai/dsh-tool-pwsh'
  disabled: !!js process.platform !== 'win32'
- id: tool-bash
  name: '@deepseek-ai/dsh-tool-bash'
  disabled: !!js process.platform === 'win32'
- id: tool-todo
  name: '@deepseek-ai/dsh-tool-todo'
  config: { allowParallelInProgress: true }
- id: tool-subagent
  name: '@deepseek-ai/dsh-tool-subagent'
  config: { provider: spawn, toolName: subagent, backgroundMode: continuable }
# selftest：确认已挂的工具全集
```

**③ 运行时**：`/permission` → 「工作区内修改」。

**注意**：`workspace-write` 允许写**平台临时区**（`/tmp`、`os.tmpdir()`）——证据：`writableRoots`。所以「只在这一个目录内写」严格说不成立：**临时目录也在可写集合里**。若这不可接受，只能 `read-only`。

### 5.3 场景 C：全仓重构（跨目录、要跑构建与测试）

**目标**：模型能在 monorepo 里到处改、能跑 `pnpm install` / 构建 / 测试。

**要点**：**cwd 必须设到仓库根**（不是某个 package），否则 `workspace-write` 会拦住跨包修改。

**① host 层**：默认 `workspace-write` 即可。若构建需要写 `node_modules`（在仓库内）→ 没问题；若需要写到仓库外（例如全局缓存、`C:\Users\...\.pnpm-store`）→ **会被拒**。

**【配方】为构建任务显式放宽工作区到公共父目录**——**不推荐**（会同时放开大量无关目录）；更推荐把 pnpm store / temp 指到仓库内：

```powershell
# 会话内让构建工具把缓存写在仓库内（避开沙箱边界）
$env:PNPM_HOME = "D:\path\to\repo\.pnpm-home"
$env:TEMP = "D:\path\to\repo\.tmp"
```
> 【推断】`$env:TEMP` 改写对 DSH 的 pwsh 沙箱效果需实测：Windows ACL runner **会主动改写受限子进程的 TMP/TEMP** 到会话私有临时目录（证据：`...\dsh-sandbox-windows-acl\README.zh.md`），所以进程内设的 `$env:TEMP` 可能被 runner 覆盖。**这条必须实测，不要照抄。**

**② preset 层**：`standard` + 显式加上 `tool-jobs`（后台跑长构建）：
```yaml
- id: tool-jobs
  name: '@deepseek-ai/dsh-tool-jobs'
- id: tool-workflow
  name: '@deepseek-ai/dsh-tool-workflow'     # 跨文件批量改动的扇出
- id: tool-subagent
  name: '@deepseek-ai/dsh-tool-subagent'
  config: { provider: spawn, toolName: subagent, backgroundMode: continuable }
```

**③ 运行时**：`/permission` → 「工作区内修改」。**不要**为了图省事切「完全权限」——`danger-full-access` 会把审批也切成 `never`，一次失误就写穿到系统目录。

**替代方案（推荐）**：在**容器/远程环境**里跑 DSH，把仓库挂进去。DSH 本地沙箱「与宿主共享内核和文件系统」，容器是**替换整个能力**而非它的配置项——证据：`...\dsh-sandbox-local\README.zh.md`「何时选择」。**【推断】** 当前包清单里没有内置容器提供方，需要自建。

### 5.4 场景 D：CI / 无人值守

**目标**：无人应答审批；任务可预测；失败要响。

**① host 层**：
```yaml
# $DSH_HOME/cordis.patch.yml（CI 镜像里预置）
- id: approval
  config:
    policy: never          # 确定性拒绝，不等待人类 —— README 称这是「CI 与无人值守运行的严格无头姿态」
- id: sandbox-policy
  config:
    mode: workspace-write  # CI 里要能写工作区产物
    workspaceRoot: !!js process.env.CI_WORKSPACE ?? process.cwd()
```
证据：`...\dsh-user-approval\README.zh.md`「设置策略」：「`never` 在交互式分发之前确定性地拒绝每个请求——**这是 CI 与无人值守运行的严格无头姿态**。」

**⚠️ 关键警告**：`never` 下**任何需要升权的操作都会被直接拒绝**。所以 CI 里**必须**让工作区覆盖所有需要写的位置 —— 否则任务会在半途失败。**不要**用 `DSH_PERMISSION_MODE=danger-full-access` 图省事（它会连带把 approval 设成 `never`，且沙箱全开）；在 CI 里更危险。

**② preset 层**（CI 专用，最小可预测）：
```yaml
# 【配方】ci-runner preset
- id: persona
  name: '@deepseek-ai/dsh-persona'
  config:
    prefix: You are a CI automation agent. Work only inside the workspace. Fail loudly.
- id: tool-fs
  name: '@deepseek-ai/dsh-tool-fs'
- id: tool-fs-search
  name: '@deepseek-ai/dsh-tool-fs-search'
- id: tool-pwsh
  name: '@deepseek-ai/dsh-tool-pwsh'
  disabled: !!js process.platform !== 'win32'
- id: tool-bash
  name: '@deepseek-ai/dsh-tool-bash'
  disabled: !!js process.platform === 'win32'
- id: tool-jobs
  name: '@deepseek-ai/dsh-tool-jobs'
# 不挂 tool-web（CI 不该上网）、不挂 subagent/workflow（不可预测性）
# 不挂 plan-mode（CI 不需要人工批准计划）
```

**③ 调用方式**：用 `headless` profile（一次性任务）：
```powershell
dsh --profile headless "run the test suite and report failures"
```
证据：`@deepseek-ai\dsh\README.zh.md`：「`dsh --profile headless "job"` | 运行一个全新的持久化会话，打印最终答案并退出。」

**④ 审计取证**：会话日志在 `$DSH_HOME/sessions/`；CI 里把 `DSH_HOME` 指到构建产物目录以便归档。

### 5.5 场景 E：生产环境审查

**目标**：可以连生产（只读凭据）、可以读日志与配置，**绝对不能改任何东西**。

**① host 层**：`read-only` + `ask`（**注意：不是 `never`**——这里要的是「万一真需要改，必须有人批」，而不是「一律拒绝」）：
```yaml
- id: sandbox-policy
  config: { mode: read-only, workspaceRoot: !!js process.cwd() }
- id: approval
  config: { policy: ask }     # 需要在场的人类应答者（Web GUI 的批准面板）
```

**② preset 层**：只读工具 + MCP 型只读接缝（例如只读 DB / 日志 MCP server）：
```yaml
# 【配方】
- id: tool-fs
  name: '@deepseek-ai/dsh-tool-fs'
- id: tool-fs-search
  name: '@deepseek-ai/dsh-tool-fs-search'
- id: mcp-logs                       # 只读日志查询
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: logs
    transport: stdio
    command: npx
    args: ['-y', 'some-readonly-log-mcp']
# 明确不挂：tool-pwsh / tool-bash（最重要的一条！），tool-web（防止把敏感内容发出去）
# 不挂 subagent*/workflow/ralph（它们会创建子会话，扩大攻击面与上下文泄漏面）
```

**⚠️ 生产审查的三条硬建议**：
1. **不要给 `bash`/`pwsh`**。即使 `read-only` 挡了写，shell 仍能**读任何文件**并**打开套接字**（Windows ACL 只管辖写：「受限子进程可以读取调用者可读的任何文件并打开套接字」）——这是把生产密钥带出去的直接通道。
2. **不要给 `web_fetch`/`web_search`**，除非有 DLP。`tool-web` 一句话就能把内网内容 POST 到外部（`web_fetch` 只做「公开 HTTP(S) 目的地」校验，但那是为了 SSRF，不是为了防外泄）。
3. **凭据隔离**：用**单独的 `DSH_HOME`**（如 `DSH_HOME=D:\dsh-prod-review`），里面只放只读凭据。这样模型即使拿到 shell，`$DSH_HOME/.credentials.yaml` 也不含可写凭据。证据：凭据层级见 `...\dsh-base\cordis.patch.yml` 第 93–98 行。

### 5.6 五场景总表

| 场景 | 沙箱模式 | 审批策略 | 工作区 cwd | 必挂工具 | 必不挂工具 | 关键风险 |
|---|---|---|---|---|---|---|
| A 只读调研 | `read-only` | `ask` | 任意（只读无所谓） | `tool-fs`, `tool-fs-search`, `tool-web` | `tool-pwsh`/`tool-bash`（Windows 上 ConstrainedLanguage 噪音）, `tool-subagent*` | 忘记 Windows 的 pwsh 降级 |
| B 单目录改代码 | `workspace-write` | `ask` | **目标仓库根** | `tool-fs`, `tool-fs-search`, shell, `tool-todo` | — | 临时目录也在可写集内 |
| C 全仓重构 | `workspace-write` | `ask` | **monorepo 根** | 上面 + `tool-jobs`, `tool-workflow`, `tool-subagent` | `danger-full-access` | 构建缓存写到仓库外会被拒 |
| D CI 无人值守 | `workspace-write` | **`never`** | CI 工作区 | `tool-fs`, `tool-fs-search`, shell, `tool-jobs` | `tool-web`, `tool-subagent*`, `tool-workflow`, `plan-mode` | `never` 下升权**必**失败 |
| E 生产审查 | **`read-only`** | `ask`（需真人应答者） | 只读挂载点 | `tool-fs`, `tool-fs-search`, 只读 MCP | shell, `tool-web`, `tool-subagent*`, `tool-workflow`, `tool-ralph` | shell 能读能联网，必须掐掉 |

### 5.7 子智能体：无法自助扩权（补充说明）

任何场景下，**进程内委派出去的子 agent 都会自动收敛**：审批钉 `never`、只继承父级**显式**沙箱覆盖（不继承一次性授权）。所以：

- 想让子 agent 能写文件 → **父会话必须在委派前就把沙箱模式切到 `workspace-write`**；
- 想让子 agent 用更宽模式 → **在父级切到更宽模式**（不能单独给子级加权限）；
- 父级事后切模式**不会**影响已发出的子级。

证据：§4.7 全文引用的 `captureDelegatedPolicyOverrides` / `DelegatedPolicyOverrides`；§4.7.1 的同运行对照实验。

> ⚠️ **一个重要例外：ACP 子 agent 不受这条收敛规则约束。**
> 官方配置目录显示 `dsh-subagent-acp` 有一个 **`permission: PermissionPolicy`** 字段，取值 `reject`（默认，拒绝每个 prompt）或 **`allow`（用第一个 `allow_once`/`allow_always` 选项自动批准，且「No prompt is surfaced to a human」）**。
> 证据：`D:\Incubator\temp\05-sources\config-catalog.zh.md` → `@deepseek-ai/dsh-subagent-acp`。
> **含义**：ACP / Codex / Claude Code 这类**进程外子 agent 是另一个产品在跑**，权限由**它自己的 harness** 决定，DSH 只能决定「要不要替它自动应答权限请求」。所以 §4.7 的「子 agent 权限自动向下收敛」**只对 DSH 进程内子 agent 成立**。
> **工程建议**：挂 `dsh-subagent-acp` / `dsh-tool-subagent` 的 codex/claude-code provider 时，**显式设 `permission: reject`**，并独立审计外部子 agent 自己的权限配置（见 §3.1 的 Claude Code 与 §3.2 的 Codex 章节）。

**通用建议**（五套场景都适用）：安全关键的委派，优先用 **`ChildComposition.toolFilter` 收窄子 agent 的工具集**（结构性不可见），而不是依赖沙箱拒绝或 prompt 指令——理由见 §4.7.1 的三条缓解与 §3.9 经验 1。

| 模式 | 可写位置 | Windows 实现 | PowerShell 语言模式 |

| 策略 | 行为 | 适用 |
|---|---|---|

| `never` | 确定性拒绝，不经 waterfall | CI / 无人值守；**所有 DSH 进程内子 agent（无条件钉死）**；⚠️ **但 `dsh-subagent-acp` 的 `permission: allow` 是例外**（见 §5.7） |

## 附录 D：本报告的三个最重要结论

1. **DSH 里「精细设定工具栏」= 写一个 agent preset**。host 树在 `web` profile 下已经把 19 个 agent-plane 行全部 `disabled`，preset 才是工具/人格/指令/skill 的归属地。preset 与 shell 同等级信任，**别 mount 来源不明的 preset**。（master 的类型契约 `PresetDefinition` 证明 preset 的**唯一**能力字段就是 `plugins` —— 没有 sandbox/approval/workspace/model 字段。）

2. **DSH 的权限是「工具集 + 沙箱模式 + 审批策略 + 工作区」四件事，只有前三件能在 host 层精细配，工作区只能靠「从哪启动」定**。而且**每个会话只有一个工作区根**——Claude Code 的 `additionalDirectories`、Codex 的 `writable_roots` 在 DSH 里**没有对等物**。

3. **DSH 的沙箱只管写，不管读、不管网络，而且在 Windows 上只是 `partial` 强制**。任何「生产环境审查」「处理敏感凭据」的场景，都**不能只依赖沙箱模式**——必须同时掐掉 shell 与 web 工具，并用独立的 `DSH_HOME`。（master 增加了出站代理收敛与 SSH 沙箱后端，但两者都不是读侧或网络沙箱。）

### 补充结论 4（来自 master 真源码，供 master 用户参考）

4. **master 的「host 平面」归属有一条可复用的判据**：「当一个单元的空值与真实值无法区分时，只要它注册进的那张表是进程级的，它就不能是逐组装的。」（Agent Note `2026-08-10-host-plane-ownership-after-presets.zh.md`）
   → 用它判断新服务该放 host 还是 preset；并记住配套硬不变量：**未加入任何 preset 的 agent 在使用模型时失败**（不是静默空工具集）。

### 补充结论 5（安全上最容易被忽略的一条）

5. **DSH 给「环境变量」划了一条比沙箱更靠前的信任线**：`loadLayeredEnv` 在加载时、物化任何内容之前，**拒绝任何设置了 `PATH`/`SHELL`/`NODE_OPTIONS`/`LD_PRELOAD`/`BASH_ENV`/整个 `DSH_*` 命名空间/`HOME`/`XDG_*`/proxy 与 CA 变量的 `.env`**，理由原文：「项目的代码在 agent 的策略下运行是约定，**项目改写那份策略不是**」，且「**不设逃生门**」。
   → **实践含义**：权限开关（尤其 `DSH_PERMISSION_MODE`）只能放在**启动 shell 或 CI 环境**里，不能放在仓库 `.env` 里；同时官方承认「**项目默认可信，且不做询问**」是一处写明的残留风险。
