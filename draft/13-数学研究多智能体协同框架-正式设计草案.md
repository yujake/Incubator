## 1. 摘要与设计目标

### 1.1 这个框架要解决什么问题

它不是"让 LLM 做数学"，而是**让一组权限隔离、产出物明确、互相可审计的智能体，
把一个数学研究问题从文献推进到可复核的证据、稿件与独立审校**，并且——
这是全部设计的重心——**在每一个环节都让"没做"与"做了但没结果"无法互相伪装**。

一句话概括本框架的立场：

> **不是"多几个 agent 就更聪明"，而是"多几道权限面与验证门就更难骗人"。**

### 1.2 八个角色与它们各自的"最危险动作"

| 角色 | 产出 | 它最容易犯的错 | 结构性对策 |
|---|---|---|---|
| **A** 检索 | 文献 + 请求状态 | 把"没搜到"说成"没有" | `outcome` 受控词表 `ok/no_results/search_failed/gave_up` |
| **B** 整理 | 概念、关系 + 引文 | 把模型编的引文当原文 | `quote_verified` 三态 + 逐字回验 |
| **C** 分析 | 分析报告 | 把"没枚举完"说成"没有更多" | `truncated` 显式字段 |
| **D** 研究 | 问题、结论、检索请求 | 把"查不到"写成"研究发现" | L1/L2/L3 溯源 + `checked` 三态 |
| **E** 实验 | 实验证据 | **把"算对了"说成"证明了"** | `evidence_kind` + **schema 拒绝计算类方法拿 `proof`** |
| **F** 攻坚 | 攻坚过程 | 无限循环 / 把"卡住"说成"解决" | 三维预算 + `stalled` 必填 `best_partial` |
| **G** 撰写 | 稿件 | 写出听起来合理但没有出处的断言 | `Document.validate` 拒绝无引用断言 |
| **H** 审校 | 审校发现 | **审校者自己的判断没有证据** | `ReviewFinding.evidence` 必填非空 |

### 1.3 目标（这一版要做到的）

1. **A–H 八个角色的权限面**（工具面 + `side_effect`）是**可枚举、可打印、可断言**的事实。
2. **12 张表**的硬约束在 `validate()` 里，违反即**拒绝落库**（不是警告）。
3. **I1–I12** 十二条交互各有**终止条件/预算**与**可判定验收判据**。
4. 每条 FC 约束能回答"落在哪个文件/函数/测试里"。
5. 端到端可跑通一个真实数学研究流程（验收：`main.pdf` 独立复现，10/10 阶段，见 §9.3）。

### 1.4 非目标（这一版**不做**，以及为什么）

| 不做 | 为什么现在不做 |
|---|---|
| **真证明后端（Lean/Coq）** | 本环境无检查器。因此 `evidence_kind="proof"` 只能靠构造数据验证，**不能端到端跑通**；一个"声称检查了证明"的假后端比没有后端危险得多。 |
| **自动推理式的攻坚** | F 的 `owner ∈ {C,D,F}` 子目标**不会被自动推进**（记 `no_change`）。一个"假装在思考"的循环比不存在的循环更危险。 |
| **H 判定数学错误** | H 只判"稿件有没有把自己说清楚"（引用、证据等级、依赖闭合）。一个声称"我检查了证明"的自动审校器会制造**更高位的幻觉**。 |
| **token 预算 / 上下文压缩（FC-17 / FC-19）** | 本轮不跑长 LLM 会话（C 完全不用 LLM，D/E/F/G/H 的 LLM 钩子默认关闭）。**未落地**，见 §7。 |
| **取消语义（FC-20）** | 当前是单进程、短任务原型，没有跨进程取消的需求面。**未落地**。 |
| **多文献支持一条关系** | ✅ **已经做了**：`Relation.supporting_lit_ids` 存在于 `schema.py:365`。FC-23 的落地形态里"本项目缺口：一条关系只能引一篇文献"这句**已过期**（见 §9.4）。 |
| **禁 AI 区（FC-27）** | 需要 CI 与仓库治理面，不在本轮范围。**未落地**。 |

### 2.2 每张表：谁写、谁能读

| 表 | 主要写入者 | 只读消费者 | 说明 |
|---|---|---|---|
| `search_requests` | **A**（认领/结束/放弃） | C, D, E, F, G, H | 提交方是 D（研究缺口）、C（I3）、F（I9）、B、人，**都必须过 I7 闸门** |
| `literature` | **A**（登记）、**B**（`processed`/抽取产物） | C, D, E, F, G, H | |
| `concepts` | **B** | 全体 | C 只能通过 `graph.*`/`trace.*` 读 |
| `relations` | **B** | 全体 | **只有 B 能写**——这是"幻觉引文唯一能被自动发现"的保证 |
| `research_questions` | **D** | E, F, G, H | |
| `analysis_reports` | **C** | D, E, F, G, H | C 的唯一产出表 |
| `reprocess_requests` | 提交方 C/D，受理方 **B** | A, E, F, G, H | 与 `search_requests` **语义不同**（不是"去检索"，是"重新处理已有的"） |
| `experiments` | **E** | D, F, G, H | |
| `attack_plans` | **F** | D, G, H | |
| `documents` | **G** | D, F, H | H 只通过 `review.*` 读 + 写 `review_findings` |
| `dependencies` | **G** | H, verify | |
| `review_findings` | **H** | G, D, F | |
| `counters` / `events.jsonl` | **Store**（框架自身） | 全体（只读） | 不经角色工具面 |

> ⚠️ **只读的层次（重要，且是本框架的一条已知边界）**：
> "C/H 只读"是在**工具层**保证的——`ToolRegistry.for_role` 对 `READ_ONLY_ROLES = ("C", "H")`
> **结构性剥掉**所有 `write_local`/`network` 工具（实测泄漏 0，见 §3 与附录 A）。
> 但**存储层没有 per-agent ACL**：智能体的模块代码仍可直接 `store.tx(...)` 写库。
> 例如 `agent_c.py:336` 就是这么写自己的 `analysis_reports` 的（这是它的合法产出），
> 而同一条通道**在结构上也能写 `relations`**。见 §9.2 第 4 条。

## 3. 角色规格

> **工具面数字全部来自实测**（附录 A 的普查脚本），不是从设计文档抄的。
> 每个角色的"工具面"列给出**实测数量**与 `side_effect` 分布；
> 完整工具名清单见 **附录 B**。

### 3.1 A —— 检索

| 项 | 内容 |
|---|---|
| **职责** | 接 `search_requests`（按 I7 优先级）→ 选 provider → 检索 → 去重 → 下载到 `library/` → 登记 `literature`；认领用**租约**，失败带 `attempts` 与 `last_error` |
| **明确不负责** | 判断文献质量；抽取概念/关系（那是 B）；决定"值不值得研究"（那是 D） |
| **工具面（实测）** | **20** 个：`read` 11 / `write_local` 7 / `network` 2。独有的：`search.providers`、`search.literature`、`search.download`、`search.dedup_check`、`search.register` |
| **产出物** | `search_requests`（状态与 `outcome`）、`literature` 行、`library/<lit_id>/…` 文件 |
| **终止条件** | 请求进入 `done=true` 且 `outcome ∈ {ok, no_results, search_failed, gave_up}`；`attempts >= max_attempts` 时**显式放弃**（`gave_up`） |
| **已知边界** | ① 无检索后端时如实登记 `outcome=no_results`（`search_failed` 也允许），**不允许**把"没搜到"写成"没有"；② `gave_up` 的计数只统计"本次调用中在成功领取之前遇到的放弃条数"，**不是队列里放弃的总数**（见 §8.7）；③ `SEARCH_OUTCOMES` 是 `schema.py:76` 的受控词表 |
| **代码** | `agent_a.py`（859→ 现状以文件为准）、`tools/search_tools.py` |

### 3.2 B —— 整理

| 项 | 内容 |
|---|---|
| **职责** | 抽 PDF → 切文本（含 OCR 回退）→ 抽概念/关系 → **引文逐字回验** → 判重 → 落 `concepts`/`relations` → 把 `literature.processed` 置真；受理 I4 定向重抽取 |
| **明确不负责** | 图推理（问 C，见 I6）；决定"值不值得研究"（问 D）；**决定概念是否合并**——C 只提出候选，**合并决定权在 B**（I5） |
| **工具面（实测）** | **18** 个：`read` 12 / `write_local` 6（**无 `network`**：B 不自己上网）。独有：`ocr.backends`、`ocr.detect_text_layer`、`ocr.run` |
| **产出物** | `concepts`、`relations`（含 `quote`/`page_range`/`quote_verified`/`concept_group_key`/`dedup_key`/`supporting_lit_ids`）、`literature.processed` |
| **终止条件** | 该文献所有可抽取关系落库且 `processed=true`；重抽取受 `max_reprocess_per_relation`（默认 2）约束 |
| **已知边界** | ① **写实体先于翻状态位**（先写 relations 再置 `processed`），否则崩溃会留下"已处理但没产物"；② OCR 在本机不可用（无 `tesseract`；`easyocr` 因 torch/numpy ABI 失败），`ocr.run` 如实返回 `meta.kind="no_backend"` 而**不假装成功**；③ 引文三态是 `True/False/None`，**禁止** `if not verified` 这种把 `None` 与 `False` 合并的写法 |
| **代码** | `agent_b.py`、`extract.py`、`quoteverify.py`、`tools/ocr_tools.py` |

### 3.3 C —— 关系分析（**只读**）

| 项 | 内容 |
|---|---|
| **职责** | 建图/索引；四类分析报告（`hottest`/`paths`/`cold`/`gaps`）；**矛盾检测**；**结构重复概念检测**；**纯函数冲突检查**（I6）；**按需服务 D**（I1） |
| **明确不负责** | **写任何知识表**（只读！）；决定合并（只提出候选）；除 I3 缺口直连外的检索动作 |
| **工具面（实测）** | **17** 个，**全部 `read`**：`table.{list,get,count,schema,search}`、`fs.{list,read,search,stat}`、`graph.{build,neighbors,relations_between,stats}`、`trace.{chain,concept,literature,relation}` |
| **产出物** | `analysis_reports` 行 + `reports/NNNN-<kind>.md` 文件；返回给 D 的结构化查询结果 |
| **终止条件** | 查询有界（`max_len`/`node_budget`/`max_paths`）；超预算必须 `truncated=True`，**不许静默截断** |
| **已知边界** | ① **C 永远只读**是设计红线：C 能写就等于"绕过 B 的引文回验"，而那是唯一能自动发现幻觉引文的地方；② C 的产出（`analysis_reports`）由 `agent_c.py:336` 直接 `store.tx(...)` 写，**绕过工具层**——因为它的工具面里根本没有写工具（见 §2.2 注与 §9.2）；③ 所有评分必须能**逐项打印中间值**（每条路径 7 项 `score_breakdown`） |
| **代码** | `agent_c.py`（2,104 行级）、`tools/graph_tools.py`、`tools/trace_tools.py` |

### 3.4 D —— 研究

| 项 | 内容 |
|---|---|
| **职责** | 消化 C 的报告 → 建 `research_questions` 台账 → 三级溯源（L1 链条陈述 / L2 相关表述 / L3 文献原文）→ 判"知识不足" → **提交检索请求给 A** → 等证据回流 → 继续研究 → 写研究报告 |
| **明确不负责** | 直接检索（走 A）；直接改关系（走 B/C 的请求）；**判定矛盾谁对**（那是 C 的 `adjudicate_contradiction`） |
| **工具面（实测）** | **37** 个：`read` 23 / `write_local` 9 / `none` 5。独有的：`research.{list_gaps,poll_waiting,set_status,submit_gap,write_note}` |
| **产出物** | `research_questions`（含 `status`、`priority`、`waiting_request_ids`、`negation`、`origin`）、`research-report.md` |
| **终止条件** | 问题进入 `answered` 或 `dropped`（`dropped` **必须**写 `notes` 说明为什么放弃）。`needs_evidence` **必须**非空 `waiting_request_ids` |
| **已知边界** | ① "知识不足"必须是**可核实判据**，不许"感觉"：`a_no_keyword_hit` / `b_low_degree_unverified` / 矛盾；② `last_tool_errors` **在 `__init__` 就初始化**（曾经惰性创建 → 记录失败的代码自己炸，见 §8.5）；③ 提问**预算**尚未定值（`DEFAULTS.max_inflight_requests=20` 只限在途条数，不限"一个问题反复问"）——**未落地**，见 §7 FC-19 |
| **代码** | `agent_d.py`、`tools/research_tools.py` |

### 3.5 E —— 数值实验与形式化验证

| 项 | 内容 |
|---|---|
| **职责** | 在**独立子进程**里执行实验脚本 → 解析结构化结论 → 登记 `experiments` 行；转发形式化检查；提供三态证据查询 |
| **明确不负责** | 产出结论（**只产出证据**）；判定脚本的结论强度（等级由 `method` 推导，不由脚本自报）；使用 LLM（判读必须确定性） |
| **工具面（实测）** | **21** 个：`read` 13 / `write_local` 7 / `none` 1。独有：`verify.{check_formal,code_hash,detect_verifier,evidence_for,list_experiments,run_experiment}` |
| **产出物** | `experiments`（`claim`/`claim_key`/`method`/`evidence_kind`/`result`/`negation_kind`/`exit_code`/`code_path`/`code_hash`/`counterexample`） |
| **终止条件** | 脚本进程结束（含超时被杀）；超时与启动失败都记 `inconclusive` |
| **推导规则（唯一权威，见 `agent_e.py` 模块 docstring）** | `exit_code != 0` → `inconclusive/no_local_evidence/heuristic`；脚本打印 `REPRO_RESULT: {json}` 且 `supports` → `supports/not_proved/cross_check`；`refutes` **必须**给 `counterexample`，否则 `Experiment.validate()` 抛；**脚本自报 `evidence_kind="proof"` 一律降级为 `cross_check` 并记 notes** |
| **已知边界** | ① **计算类方法永远拿不到 `proof`**（`schema.py:758` 硬约束）；② 无 Lean/Coq ⟹ `check_formal` 返回 `checked=False, reason="no_backend"`，**不是** `verified=False`；③ `params`/`artifact_paths` 是信息性字段，不参与执行 |
| **代码** | `agent_e.py`、`tools/verify_tools.py` |

### 3.6 F —— 多轮难题攻坚

| 项 | 内容 |
|---|---|

### 4.3 `LOCK_ORDER` 与它的理由

```python
# store.py:33-47 —— 任何多表事务都必须按这个顺序取锁，否则两个事务可能互相等待。
LOCK_ORDER = ("search_requests", "literature", "concepts", "relations",
              "analysis_reports", "research_questions", "reprocess_requests",
              "experiments", "attack_plans", "documents", "dependencies",
              "review_findings", "counters")
```

两条规则（原文注释）：
1. **固定顺序**是避免死锁的标准做法；
2. **新增表一律追加在 `counters` 之前**——因为任何 ID 分配都要 `counters`，
   它必须是最后一把锁。`ID_COUNTERS` 的"发号与建行必须同锁"（`agent_e.py:579` 注释）
   正依赖这一点。

**为什么必须有锁**（`store.py` 模块 docstring 三件事）：
- **不存在"部分写入"**：临时文件 → `os.replace`，且**先校验后落盘**；
- **不存在"丢失更新"**：任何读-改-写在同一把排他锁内（A 追加文献、B 改 `processed`，
  若各自"读全表→改一行→写全表"，后写者会覆盖先写者）；
- **不存在"说不清谁改了什么"**：每次落盘追加事件，事件带**整行 upsert**（不是 diff）。

### 4.4 重建语义

`rebuild()`（`store.py:401`）：按主键折叠 `events.jsonl`，**末次写赢**（last-write-wins）。
四条要求（FC-12）与落地：
1. **信息量守恒**：重建前后诊断字段逐字段相等（`_keys` / `_quote_check`）；
2. **幂等**：连做两次，表文件逐字节一致；
3. **坏事件不得让重建抛异常**（截断的半行 JSON）；
4. **重建后 schema 字段仍被规范化**——"无损"≠"原样抄回"。

防复发测试：`tests/test_rebuild.py`（**3 条**）。
`rebuild(backup=True)` 默认先备份。

### I2 矛盾闭环（发现 → 提问 → 检索 → 消化 → **复核**）

| **是什么** | C 的 `candidate_gaps` 里**通过 veto 且 `confidence >= medium`** 的候选，直接生成 `search_requests`（`submitted_by="agent-C"`） |
| **为什么** | `gaps` 的定义就是"**应该有边却缺失**"，那正是"去找找有没有人做过"的靶子；绕道 D 只增加一次判断与一次失真 |
| **闸门** | 只允许 approved 的候选；单次 ≤ `max_gap_requests_per_run`(3)，按净分降序；与已有未完成请求**主题去重** |
| **终止条件** | 单次运行提交 ≤3；全局在途 ≤ `max_inflight_requests`(20) |
| **可判定判据** | `gaps` 跑完后新增请求 ≤ 上限，且每条主题能对应到某个 `candidate_gap`；`submitted_by` 全为 `agent-C`；优先级按 I7 表是 `medium` |
| **负控** | `submit_requests=False`（默认）时**一条都不新增** |
| **实测证据** | 验收 P2b："I3：新增请求 3 ≤ 上限 3"、"新请求 `submitted_by` 都是 `agent-C`"、"C 的请求优先级是 medium"、"**I3 负控**：`submit_requests=False` 时一条都不新增" |

### I4 定向重抽取（让 B 有事可做，而不是只顺流水线走）

| 项 | 内容 |
|---|---|
| **是什么** | C/D 针对**特定关系**要求 B 重新处理：引文不可核实 → 回全文搜等价表述；描述过短 → 回到该页附近抽更完整陈述；D 需要上下文 → 返回该页/该段原文片段（L3 溯源） |
| **为什么** | B 原是**一次性**的（处理完 `processed=true` 再不回头），于是 C 发现的问题**无法修复**。定向重抽取把 B 从"流水线工位"变成**可复访的服务** |
| **接口** | `admit_reprocess_request(existing_rows, *, relation_ids, reason, max_per_relation=None) -> dict`；`reprocess_counts(rows) -> dict[str,int]` |
| **终止条件** | 同一关系最多重抽取 `max_reprocess_per_relation`(2) 次；超限**拒绝** |
| **可判定判据** | 重抽取**只改动目标关系**、其它关系逐字节不变；超限后拒绝；`status=done ⟹ result` 非 `None` |
| **负控** | **绝不重置 `literature.processed`**（那会触发全量重抽）；`literature.json` 必须逐字节不变 |
| **实测证据** | 验收 P2b："I4：提交的 1 条重抽取请求全部有了终态"、"每条完成的重抽取都给出了 `result`"、"**绝不重置 `literature.processed`**（`literature.json` 逐字节不变）"、"**只改动目标关系**（实际改动 `[]`，目标 0000）" |

### I5 结构重复概念检测（C 发现，B 合并）

| 项 | 内容 |
|---|---|
| **是什么** | C 检测**结构上等价**的概念对（邻域完全相同，或关系集合高度重合且两者从不直接相连），交给 B 复核（按 `normalized_name`/别名/定义）→ **B 决定合并或否决** |
| **为什么** | 旧合并只看**名字**。真实文献里"群"会以"group / 群 / G"三种写法进来，名字匹配不上，图里出现**三个同义节点**，度数统计被稀释、路径搜索被污染。**结构信息是名字之外的第二路证据** |
| **接口** | `structural_duplicate_pairs(concepts, relations, *, max_pairs=None) -> list[dict]` |
| **终止条件** | `structural_duplicate_max_pairs`(200) 上界 |
| **可判定判据** | 真同义 ⇒ C 提出且 B 合并；假同义（邻域相同但显然不同）⇒ **B 拒绝并留下理由**（`merge_reason`） |
| **负控** | 同上第二条；另：C **只提出候选**，合并决定权在 B（`concepts.merged_into` 由 B 写） |
| **实测证据** | 验收 P2b："I5：1 个候选，实际合并 0 个"（保守，符合"必须保守"的设计）；`tests/test_agent_c_service.py`（30 条） |
| **必须保守的理由** | 结构等价 ≠ 同义（"所有子群都同构的两个概念"可能连着同一批邻居） |

### I6 写入期一致性闸门（B 在提交关系前问 C）

| 项 | 内容 |
|---|---|
| **是什么** | B 在**写入新关系之前**问 C："这条新关系与图中已有的关系**是否矛盾**？" 不矛盾 → 正常写入；矛盾 → 写入但标 `status="suspect"` 并记 `conflicts_with`；相似 → 走已有三档判重 |
| **为什么** | 矛盾原只能在**事后**由 C 发现。写入期闸门把发现提前，且给 B 一个判据而**不必自己实现图推理**（职责不越界：B 不懂图，C 懂） |
| **接口** | `check_conflict(draft_relation, *, existing_relations) -> dict`，返回 `conflict` 与 `weak_signals` **分流** |
| **硬约束** | **必须是纯函数**：**只吃内存数据，不碰 store**（事务内重入锁会死锁）。由 `assert_store_free()` 在**导入期**断言（§5 开头） |
| **负控** | 签名级断言"不接收 store、不打开事务"；并发（两个 B 实例）下无死锁 |
| **实测证据** | 验收 P1："I6 闸门 0 次被跳过（无'没检查'）"；`assert_store_free` 在 `interactions.py` 导入时执行（实测输出见附录 A.3） |
| **与事后检测的分工** | **I6 是写入期**（B 的每次写入都要过），**`detect_contradictions` 是事后全局扫描**（C 的四类分析之一，也是 I2 闭环的入口）。两者**共用同一个判据函数**（`opposite_flags` + `strong/weak` 分流），**不许各写一份**（FC-11） |

### I7 检索预算与优先级（A 的产能是稀缺资源）

| 项 | 内容 |
|---|---|
| **是什么** | 给 `search_requests` 加**优先级**与**配额**，A 按优先级取任务 |
| **为什么** | "知识不足就向 A 提交查询"会在 D 的循环里**被反复触发**。没有优先级与配额，A 的队列会被低价值请求填满，而**关键矛盾排在后面** |
| **接口** | `priority_rank(priority) -> int`；`resolve_priority(submitted_by, explicit=None) -> (priority, why)`；`inflight_requests(rows) -> list[dict]`；`order_pending_requests(rows, *, now=None) -> list[dict]`；`admit_search_request(existing_rows, *, submitted_by, explicit_priority=None, for_question_id=None, max_inflight=None) -> dict` |
| **默认优先级表** | D（矛盾闭环）**high** / 人 **high** / D（普通缺口）medium / C（gaps 靶子）medium / B（补定义）low / **E/F/G/H 显式登记为 low**（见 §8.3） |
| **终止条件** | 全局在途 ≤ `max_inflight_requests`(20)；同优先级 **FIFO** |
| **可判定判据** | 混合队列 ⇒ 排序里 `high` 全部在 `low` 之前，且 **A 实际取走的是 high**；超上限 ⇒ **拒绝新请求**而不是无限排队 |
| **负控** | 超限必须**拒绝**（构造超过上限的队列，断言拒绝发生） |
| **实测证据** | 验收 P2b："I7：排序里 high 全部排在 low 之前"、"I7：A 实际取走的是高优先级（`priority=high`）" |
| **排序键精确语义** | `(优先级次序, 是否"有人正持有有效租约", 提交时间, request_id)`；**空租约与已过期租约都算"能立刻取走"**（同一个桶）；最后用 `request_id` 兜底保证**全序**（否则"先 high 后 medium"这类断言会随机失败）。见 §8.4 |
| **"在途"只有一个口径** | `inflight_requests` = `done` 为假。`outcome=gave_up` **不算在途**（它是终局）。写成函数就是为了防止"一边把 gave_up 也算在途"导致配额静默失准 |

## 6. 横切机制

### 6.1 三态纪律：`True / False / None` + 受控 `reason`

**它是什么**：任何"判定"字段都必须能区分**"没做"**与**"做了但没结果"**。
布尔做不到这件事，而这两者需要**完全不同的处置**（前者装 OCR / 补数据，后者改引文 / 剔除）。

**落地清单**（每一处的"没做"形态都不同，这是关键）：

| 位置 | 三态形态 | "没做"长什么样 | 证据 |
|---|---|---|---|
| 引文校验 | `Relation.quote_verified: bool \| None` | `None` = 没校验过 | `schema.py:385`；`store.stats()` 输出 `quote_verified/quote_unverified/quote_unknown` 三个整数（实测见附录 A.5） |
| OCR | `ToolResult.meta["kind"]` | `no_backend` = 没有识别后端（**不是**"识别出空文本"） | `tools/ocr_tools.py`；验收 P1 未涉及 |
| D 的溯源 | `evidence_for(...)["checked"]` | `checked=False` = **没查**；`checked=True, experiments=[]` = **查了、没有** | `agent_e.py` 模块 docstring §"三态纪律在本模块的三处落地" |
| C 的预算 | `truncated: bool` + 未展开计数 | `truncated=True` = 没枚举完（**不是**"没有更多"） | C 的 `gaps` 报告："另有 N 条中等以上置信度候选超出 `limit=6` 未展开" |
| 检索终局 | `SearchRequest.outcome` 受控词表 | `no_results` = 搜了没有；`gave_up` = 放弃 | `SEARCH_OUTCOMES`（`schema.py:76`） |
| 形式化验证 | `checked` + `reason` | `checked=False, reason="no_backend"`（**不是** `verified=False`） | `agent_e.check_formal` |
| 依赖闭合 | `DEP_STATUSES` | `external_unavailable` + `status_reason` | `schema.py:671` |
| 问题台账 | `status` + `waiting_request_ids` | `needs_evidence` ⟹ 必须记清在等谁 | `schema.py:571` |

**判据①（"禁止把 `None` 与 `False` 合并"）的落地状况**：
代码中已按 `is True` / `is False` / `else` 三支书写（对照 `agent_b` 的引文处理），
但**没有静态检查**禁止 `if not verified:` 这种写法 —— **部分未落地**，见 §7。

### 6.2 证据等级与"计算类方法拿不到 proof"

| 机制 | 位置 |
|---|---|
| `EVIDENCE_KINDS = ("proof", "cross_check", "heuristic")` | `schema.py:633` |
| **`method != "formal"` ⟹ `evidence_kind != "proof"`** | `schema.py:758`（硬约束） |
| `proof` ⟹ `verifier_output` 非空 | `schema.py:765` |
| 子目标 `closed` ⟹ `proof_experiment_ids` 非空 | `schema.py:902` |
| `cross_check` 断言 ⟹ `disclaimer` 非空（自动填 `CROSS_CHECK_DISCLAIMER`） | `schema.py:1008` + `tools/doc_tools.py` |
| H 检查 `overclaim`（把 `cross_check` 写成证明性措辞） | `verify.py:509` + `tools/review_tools.scan_document` |
| E 的推导：脚本自报 `proof` **一律降级** `cross_check` 并记 notes | `agent_e.py` docstring §"为什么脚本自报 evidence_kind 必须被降级" |
| `COMPUTATIONAL_METHODS` 与 `EXPERIMENT_METHODS` 的**导入期一致性断言** | `agent_e.py:111` |

**为什么必须机械执行**：论文 `main.pdf` 自己写着 "No numerical output is used as a proof"——
这句话之所以要写，正因为**数值对了几千个点就想说"证明了"是这一行最自然也最危险的动作**。

**同一纪律在复核侧的一次现形（本轮新增）**：独立复核脚本第一版把 90 条里的 **55 条**
标成 `PROVED_HERE`，其中含"`B_3` 内每个顶点度数为 m"这类**有限盒子计数**——
即复核者自己犯了 FC-22。修法是**论证白名单 + 机械拒绝测量词 + fail-closed**，
并有 `--selftest-fc22` 负控证明门会响。见 §8.8。

### 6.3 派生态不许当输入

**一般化教训**：任何"缓存的 / 派生的"字段一旦被当作**输入**，
忘记计算它的那一方就会**静默拿到空结果**。所以：**派生态要么就地推导，要么在装配期断言它存在**（不许有第三种）。

**本项目的实例**：`detect_contradictions` 曾直接读行里的 `concept_pair_key`，
但 `relations` 表存的字段名是 **`concept_group_key`** ⇒ 对**直接从表里读出来的行**
（C 的 `contradictions()`、任何脚本），该函数**恒返回 `[]`**，不报错、不告警，
看起来就像"没有矛盾"。
**修正**：字段缺失时就地用 `concept_pair_key(concept_ids)` 推导（`interactions.py:244-245`），
与 `RelationGraph.group_counts` 的做法一致。详见 §8.2。

### 6.4 闸门必须在真实样本上量过假阳性率才能上

**实测数据**：25 条真实论文关系，旧"字面矛盾"判据报出 **6 条 `suspect`（24%）**，
**没有一条是真矛盾**。两个根因：
1. **逻辑错误**：`only_a != only_b`（`only_x = 命中肯定式 and 未命中否定式`）把
   "**提到肯定式**"与"**压根没提这个词**"当成两种相反态度。中文 `("是","不是")` 的"是"无处不在
   （"等号是公开问题"）⇒ 大量误报；
2. **裸否定标记不是否定主张**："**不必**用数值搜索"、"**No** numerical output is used as a proof"
   都命中否定标记，但**不是对立主张**。

**修法**：判据分两档——`strong`（一方**明确肯定** **且** 另一方**明确否定**）/
`weak`（仅否定标记出现与否不一致）；**只有 `strong` 允许驱动 `status="suspect"`**，
`weak` 进 `weak_signals` 作为线索。落地在 `interactions.py:254-290` 与 `check_conflict` 的
`conflict`/`weak_signals` 分流。
**为什么这条修正比"多报一点"更重要**：24% 的报警率意味着 `suspect` 这个标记
**不再指示任何东西**——而"**假报警比不校验更糟，因为它会训练人忽略告警**"。

**由此得出的框架级规则**：**每个新增闸门都必须在 ≥20 条真实样本上跑一遍并记录触发率。**
这两条缺陷都不是单元测试能发现的：单元测试里构造的是"人为矛盾"，它当然通过。

### 6.5 写入期闸门 vs 事后检测（I6 与 C 的矛盾检测分工）

### 6.6 失败分级（FC-13）与三分档计数（FC-10）

**FC-13 分级规则（两句话，必须记牢）**：
- **"表里已记录的缺陷被重算确认" ⇒ `warning`**（例：`external_unavailable` 的依赖 —— 那是**已经知道的边界**，不是谎报）；
- **"表里记录与重算事实矛盾（谎报）" ⇒ `error`**。

落地：`Issue(level, table, id, kind, msg)`（`verify.py:30`），`level ∈ {"error","warning","info"}`。
实测例子：`dangling_dep_external` = **warning**；`overclaim` / `dangling_dep` / `unsupported_claim` = **error**。
**若不这样分，红灯会被训练成背景噪音，于是真正的 `error` 也会被忽略。**

**FC-10 三分档**：`store.stats()` 对引文给**三个整数**（`quote_verified` / `quote_unverified` /
`quote_unknown`，实测见附录 A.5），验收 P1 输出"引文逐字回验 `verified=25 / failed=0 / unknown=0`"。
**"一个'通过率 80%'的单一数字会掩盖'20% 是失败还是未校验'这个决定性差异。"**
**未落地部分**：`verify` 本身只按 `error`/`warning` 两级统计（无 `unknown` 档），
且若将来接入 LLM，报告的"通过率"写法需要复核。见 §7。

## 8. 实测缺陷档案

> 统一五段式：**现象 / 根因 / 证据 / 修法 / 防复发**，并标注**谁发现的**。

### 8.1 `detect_contradictions` 的 `only_a != only_b` 逻辑错误（发现者：B/C 子任务；写进 `DESIGN-ROLES.md §4.1`）

- **现象**：25 条真实论文关系上，报出 **6 条 `suspect`（24%）**，**没有一条是真矛盾**。
- **根因**（两个）：① `only_a != only_b` 把"**提到**肯定式"与"**压根没提**这个词"当成两种相反态度
  （中文 `("是","不是")` 的"是"无处不在）；② **裸否定标记不是否定主张**
  （"**不必**用数值搜索"、"**No** numerical output is used as a proof" 都不是对立主张）。
- **证据**：25 条真实关系上的触发率 6/25；旧判据代码见 `DESIGN-ROLES.md §4.1` 的引用。
- **修法**：判据分 `strong`/`weak` 两档，**只有 `strong` 允许驱动 `status="suspect"`**；
  `weak` 进 `weak_signals`。现实现 `interactions.py:254-290`。
- **防复发 / 一般化**：**每个新增闸门都必须在 ≥20 条真实样本上量过触发率才能上**。
  单元测试发现不了它——测试里构造的是"人为矛盾"，当然通过。
- **教训一句话**：**24% 的报警率意味着 `suspect` 不再指示任何东西。**

### 8.2 `concept_pair_key` 派生态当输入（一次**完全静默**的失效）（发现者：B/C 子任务；`DESIGN-ROLES.md §4.2`）

- **现象**：`detect_contradictions` 对**直接从表里读出来的行**（C 的 `contradictions()`、任何脚本）
  **恒返回 `[]`**——不报错、不告警，看起来就像"没有矛盾"。
- **根因**：函数直接读行里的 `concept_pair_key`，但 `relations` 表存的字段名是 `concept_group_key`。
  只有 `agent_d` 自己悄悄补过 `concept_pair_key` 的那条路径能正常工作。
- **证据**：`interactions.py:232-238` 的注释逐字记录了这件事；
  修正后 `interactions.py:244-245` 用 `or concept_pair_key([...])` 就地推导。
- **修法**：字段缺失时**就地推导**（与 `RelationGraph.group_counts` 一致）。
- **防复发**：`tests/test_interactions.py`（48 条）覆盖 C 直接读表行的路径。
- **一般化教训**：**派生态要么就地推导，要么在装配期断言它存在（不许有第三种）。**

### 8.8 复核者自己犯了 FC-22 过度声称：`PROVED_HERE` 标签（发现者：主控复核复核产物时发现；由本报告作者修）

- **现象**：独立复核脚本报"90 项检查、0 项失败"，tally 为
  `{"PROVED_HERE": 55, "NUMERIC": 31, "QUOTED": 4}`；但大量 `PROVED_HERE` 的 `note` 是
  `degrees seen = [3]`、`|B_3|=19, |E|=21` 这类**测量记录**。
- **根因（类别错误）**：`"degrees seen = [3]"` 证明的是"**B₃ 盒子里**每个顶点度数为 3"，
  **不是**"`K(m)` 是 `m`-正则的"（后者要靠解析论证）。这正是 E 角色的 `schema.Experiment`
  专门拒绝的动作，也是 `main.pdf` 自己写 "No numerical output is used as a proof" 要防的东西。
- **证据**：逐字取自 `temp/verify_paper_independent_result.json`（修前）：
  ```
  {"claim":"K(3): all degrees in B_3 equal m (|B_3|=19)","status":"PROVED_HERE","note":"degrees seen = [3]"}
  {"claim":"girth K(3) by edge-deletion in B_3","status":"PROVED_HERE","value":6,"note":"|B_3|=19, |E|=21"}
  ```
- **修法（改机制，不是改措辞）**：① 三个标签写下可判定定义（`PROVED_HERE` 仅当带解析论证；
  `NUMERIC` 是有限范围计算，**默认落这里**；`QUOTED` 引自论文）；
  ② 加 **`ARGUMENTS` 白名单** + `record()` **机械拒绝**："论证缺失或含测量词
  （`seen/counted/sampled/observed/measured/in b_/checked/n=/enumerated`）
  ⇒ 记 `FC22_VIOLATIONS` 并**非零退出**"。
- **修前/修后**：

  | | 修前 | 修后 |
  |---|---|---|
  | 检查条数 | 90 | **101**（新增 §0"解析论证"一节 11 条） |
  | `PROVED_HERE` | **55**（含盒子计数） | **11**（每条带论证） |
  | `NUMERIC` | 31 | **86** |
  | `QUOTED` | 4 | 4 |
  | `PROVED_HERE` 缺论证 | *未检查* | **0** |
  | FC-22 违规 | *未检查* | **0** |

- **防复发（负控）**：`--selftest-fc22` 注入一条无论证的 `PROVED_HERE` ⇒ 实测
  `exit code = 1` 并打印 `[FC-22 VIOLATION]`；正常运行 `exit code = 0`。**门被证明会响。**
- **教训**：**标签只靠人写、没有机器判据，就会退化成"我觉得这条挺硬的"。**
  框架的每一条纪律都要有一个**可执行的判据**：三态要有受控 `reason`、
  证据等级要有 schema 硬约束、`PROVED_HERE` 要有论证白名单。
  **三者是同一个模式：把"声称"变成"必须交出的东西"。**

### 8.9 `Tx.alloc_id` 在计数器落后时发出已占用的号，`upsert` 按主键**静默覆盖**（发现者：D 子任务）

- **现象**：D 侧新建的矛盾问题 `(0002, 0004)` **被已存在的 `0000` 顶掉**，
  而 `new_question_ids` 还返回 `["0000"]`——**返回值在骗人**。
- **根因**：`alloc_id` 从 `counters` 取号；当 `counters` **落后于表**时它会发出**已被占用**的号，
  而写入走按主键 `upsert` ⇒ **静默覆盖**而不是报冲突。
  两个各自"正确"的设计（发号器 + 幂等 upsert）组合出一个**静默数据丢失**。
- **证据**：`store.py:152-221` 的注释逐字记录（"一次真实缺陷的修复"）。
- **修法**（`store.py:189-221`）：① 分配时在**已声明的事务表**里查占用，**占用就往后跳**；
  ② 把 `counters` 推到最终号 +1（**缓存自愈**）；③ 跳号时写一条
  **`alloc_id_skipped_occupied`** 事件（**跳号必须留痕**，否则"号为什么跳了"永远查不出来）。
- **防复发**：**`tests/test_store_alloc_guard.py`（5 条）**。
- **一般化教训**：凡是"按主键 upsert"的系统都必须问一句：**我的 ID 有没有可能重号？**
  重号的后果不是报错，而是**静默覆盖**——本项目最怕的一类失败。

### 8.10 审校者手里有刀：只读角色的工具面泄漏（发现者：G/H 子任务）

- **现象**：按角色装配出的审校者 **H 的工具面里出现 `table.update` / `fs.write` / `verify.run_experiment`**
  —— 只读角色拿到了能改数据的工具。
- **根因**：`table_tools` / `fs_tools` / `verify_tools` 注册时把**注入的全部 `ROLES`** 写进每个工具的
  `roles` 字段。于是"谁能用这个工具"被写成了"所有角色都能用"。**不是过滤逻辑错，是声明本身错。**
- **证据**：装配后遍历 `for_role("H")`，其中 `side_effect ∈ {write_local}` 的工具数 **> 0**（修复前）。
- **修法（两道，缺一不可）**：

- **为什么两道都要**：只做第 1 道，下次有人新写工具又顺手塞 `ROLES`，漏洞就回来；
  只做第 2 道，则"声明"与"实际"长期不一致，而**声明本身就是审批判据**（FC-07）。
- **防复发**：**`tests/test_tools_readonly_roles.py`（7 条）**，含
  "**声明写错也拿不到刀**"的负控、"干净声明不留痕"的防误伤、"**写工具至少有一个写角色**"

- **实测（修复后）**：`C/H 拿到写型工具 = 0/0`，`role_filter_notes = {}`（附录 A.1）。

## 9. 已知边界与未验证清单

> **这一节决定这份草案值不值得信。** 凡"没验证"的，一律不写成"已验证"。

### 9.1 数学层面的边界（**最要紧**）

1. **`Spec S̃_m = [−m, m]`（3 ≤ m ≤ 5）无法独立验证**：论文自己在 Remark 1.6 说它引用配套书
   `[6, Thm. 6.5]`、**未重证**，且 `[6]` **连出版信息都没给**，我们无法查阅。
   ⇒ 该论文 **Theorem 1.5 的"余谱"那一半依赖一个我们读不到的外部定理**。
   框架把它登记为 `external_unavailable` 是**正确行为**。
2. **`m ≥ 6` 是论文自己的公开问题**；我们对 m=6 只做**反例搜索**，**不作结论**。
3. **纯证明类结论（3 条）数值无法验证**，只做反例搜索。
4. **数值不是证明**：`K(m)` 的 `k` 归属为 `computable` 的 21 条里，
   我们提供的是**端点精确值 + Lipschitz 填隙判据 + 双通道恒等式**（三样都是证据），
   **证明仍是论文 §3 的**。
