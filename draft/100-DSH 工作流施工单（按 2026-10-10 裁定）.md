## §1 施工单 S-A：文件"读后写"（裁定 9甲，最高优先）

**【搬运来源（代码级，逐行核过）】** 别名：`POL` = `dsh-fs-observation-policy/lib/index.js`（97 行）、
`FSL` = `dsh-fs-local/lib/index.js`、`TFS` = `dsh-tool-fs/lib/index.js`、`FST` = `dsh-fs/lib/types/types.d.ts`。
- **架构先搬对（否则会把它做成一个服务）**：**策略层不持有服务、也不做 I/O** —— 它只是
  **3 个事件监听器 + 一张 `WeakMap`**（`POL:85-95`）；事件由**工具**派发（`TFS:650`/`:801`），
  **原子的版本核对由 provider 做**（`FSL:821-857`）。⇒ 我们的对应形态：
  **闸门 = 纯状态机（新模块）**、`fs_write`/`fs_edit` = provider 那一步核对、`fs_read`/`fs_write`/`fs_edit` = 观察者。
  **不要**发明 policy 服务/事件总线（我们没有事件总线，直接同步调用即可）。
- **三个状态**（判据是"条目在不在" + `kind`）：**S0 未观察**（没有条目，`POL:32-34`）、
  **S1 确认缺失** `{kind:'absent'}`、**S2 存在** `{kind:'present', version}`。
- **版本令牌不是摘要，是 stat 元组**（**这是对我原设计的更正**）：逐字
  `` `${info.dev}:${info.ino}:${info.size}:${info.mtimeNs}:${info.ctimeNs}` ``（`FSL:142-143`，
  来自 `stat(path,{bigint:true})`）；文档明写它是**不透明**的、"consumers MUST NOT interpret"（`FST:29-36`）。
  **DSH 这条路上没有任何 digest**。⇒ 我们 `fs_read` 今天那个 sha256 是**读完之后再整文件读一遍**
  （`fs_tools.py:566` 走 `_sha256`），既贵又有竞态、且 >5MB 时给 `None`（正是最该管的大文件）⇒
  **改成记 stat 元组**，sha256 只留作 `sha256=` 那个既有参数的第二道检查。
- **两个意图**：`write` ⇒ 见过 S2 就 `replaceIfVersion`，否则（S0/S1/**没有 owner**）`createIfAbsent`（`POL:51-58`）；
  `edit` ⇒ **没 owner 或 S0 ⇒ 拒 `FS_NOT_OBSERVED`**（逐字 `edit requires reading "<path>" first`，`POL:67`）、
  S1 ⇒ 拒 `FS_NOT_FOUND`、S2 ⇒ 给 `{version}` 作 CAS 依据（`POL:64-70`）。
- **同码两个出处的文案不一样，必须把"归一化"也搬**：策略层 S0 的文案是
  `edit requires reading "<path>" first`，provider 层"覆盖已存在但没读过"的文案是
  `cannot overwrite existing "<path>" without reading it first`（`FSL:828`），
  而工具层把**两者**都改写成模型看到的那一句：
  `cannot modify "<path>": file has not been read — read the file, then retry`（`TFS:547`，破折号 U+2014）。
  陈旧那一档是**保留 provider 的理由再追加** `` `${message} — re-read the file, then retry` ``（`TFS:548`）。
- **成功之后要观察"写完之后"的新版本**（写后重新 stat，`FSL:831`/`:850`/`:860-862`），
  不是意图里那个期望版本 —— 否则"同一步里连写两次"会被自己拒掉（`TFS:657`/`:810`；
  我们 `fs_tools.py:1198-1202` 的自检正依赖这一点）。
- **读过的就算（哪怕只读了窗口/被截断）**：观察用的是**读之前那一次 stat** 的版本（`TFS:274`→`:430`）；
  **确认缺失要在抛错之前记**（`TFS:276` 先 emit 再 throw）—— 否则"读一个不存在的路径以授权带防护的创建"
  这条路断了。
- **不许在 `stat`/`list`/`search` 上记观察**（DSH 只在 `TFS:276,430,657,810,1098` 五处 emit）；
  `fs_delete`/`fs_move` 在 DSH 里**没有对应物**（provider 没有 delete/rename）⇒ 若我们要
  "删了记 absent、移动就掉两个键"，那是**我们自己的扩展**，要在注释里标明不是搬运。

**【落地时的三条硬约束（都已核过）】**1. `tools/fs_tools.py` **不在** `.noai-paths` 里 ⇒ 整件事可以只落在一个**新模块** `fs_observation.py`
   + `fs_tools.py`，**一行禁改区都不碰**（禁改区只有 `tools/base.py`、`tools/__init__.py`、
   `tests/golden/*.json` 这几处与它相关）。
2. **不许加/改任何工具参数、不许动 `returns=` 字符串** —— `tests/test_tool_surface_snapshot.py:93-94`
   把 `inspect.signature(handler)` 与 `declarations`（含 `params`/`returns`）**快照进
   `tests/golden/tool_surface_snapshot.json`**，而那份金标是 `[category: eval-criteria]` 禁改区
   （要人工重冻）。新拒因走 `meta["kind"]` 是安全的（`tests/test_tools_returns_declaration.py:922-996`
   只比 `data` 的键）。
3. **owner 现成可用、且不需要动禁改区**：`agent_loop.py:3315-3316` 已经把每次工具调用包在
   `calling_as(self.my_task_id, self.role)` 里，`conductor.current_task_id` / `current_caller_role`
   都不在禁改区 ⇒ owner 取 `(current_caller_role(), current_task_id())`，
   两者皆空 ⇒ **没有 owner**（等价于 DSH 的"没有 agent session"那一支：写只能创建、编辑一律拒）。
   **不要**用 `FsContext.actor`（它是 `register()` 时定死的常量）也不要只用 `role`
   （会让同角色的并发任务互相串味）。

**【一条可选的并发保证】**：DSH 的 provider 用**按 targetKey 的 FIFO 锁**串行化
"stat → 比对版本 → 写"（`FSL:716-736`），所以并发写"一个赢、其余看到陈旧"。
我们的 `_atomic_write_bytes` 没有这把锁 ⇒ 同进程内两个 `fs_write` 可以**同时通过版本核对**（TOCTOU）。
要的话照 `FSL:726-736` 搬一个 `dict[str, threading.Lock]`（或一把全局锁）把那一段包起来。

**改动面**（落点已按上面的约束定）
1. **新模块** `src/agentflow/fs_observation.py`：`ObservedGate`（`observed: dict[owner, dict[target, obs]]`、
   `owner()`、`get/set/clear`、`write_intent()`、`edit_intent()`、`observe()`）+
   `version_of(stat_result)` + `remediate(code, message, path)`（那两句模型可见文案）。
2. `fs_read`：缺失分支**先记 absent 再抛**；成功分支在 `return ok(...)` 之前记 present
   （版本用**读之前**那一次 `target.stat()`，`fs_tools.py:501`）。
3. `fs_write`：写之前算 intent → 调 `_atomic_write_bytes` 前加两道判据
   （`existing and prior is None` ⇒ `not_observed`；版本不符 ⇒ `stale_version`）；
   **保留**今天的 `overwrite=False ⇒ kind="exists"` 那条（有判据钉着）；成功之后记"写后版本"。
4. `fs_edit`：把今天**可选**的 `sha256` 闸换成**必需**的观察闸（S0/S1/版本不符三档），
   但**保留** `sha256` 参数作为更强的第二道（`sha_mismatch` 那条被
   `tests/test_tools_fs_edit.py:92-104` 钉着，不许删）。
5. 观察表在**每趟开始时清空**（照 DSH 的 `gate.clear()`，`POL:87-89`）——
   "恢复的会话必须重读"这条因此自动成立（我们每趟新建 `AgentLoop`）。

**判据**
- 正控：新工作区里直接 `fs.edit` 一个存在的文件 ⇒ `not_observed` 拒绝（**先读后改**才过）。
- 正控：读 → 改 ⇒ 过；读 →（外部改）→ 改 ⇒ `stale_version` 且文案带
  `— re-read the file, then retry`。
- 负控（**两档必须分开**）：`fs.write` 新建一个**不存在**的文件 ⇒ 允许；
  **已存在**且没读过 ⇒ 拒（`cannot modify "…": file has not been read …`）。
- 反真空：**恢复会话（观察表为空）时正控仍然拒**。
- 写后观察：同一步里"写 → 再写同一个文件" ⇒ **不拒**（写后版本已登记）。
- 归一化：策略层与 provider 层两个 `NOT_OBSERVED` 出处，模型看到的**必须是同一句**。

**代价与风险**：真机上会出现更多拒绝（模型得先读一次）；"读过窗口也算读过"这条会**放宽**授权
（DSH 自己承认这是已知弱化：授权依据是版本新鲜度、不是视图完整性）—— 照搬它，并在注释里写明。
**风险**：观察表按进程记 ⇒ 跨进程（两个 agent 进程同写一个工作区）**互相看不见**；
DSH 在同一个 harness 进程里有 provider 锁兜着，我们没有 ⇒ 跨进程那一档只剩 `sha256` 第二道闸
（这也正是"保留它"的理由）。

**依赖**：无。可独立开工。

## §2 施工单 S-B：把 `contextbudget` 接进循环 + 口径换 DSH（裁定 7乙 + 8乙）

**【搬运来源】**（先于改动面写，因为这一节搬错了就等于白干）

  `compaction/start`（日志锁）→ 摘要 → `compaction/summary`（影子计价）→ 紧邻一条带
  `surfaceOp:{op:"replace",startSeq,endSeq}` 的 `user/message` → `compaction/end`
  （`dsh-compaction-basic/lib/index.js:446-469`、`:605-632`）。
- **我们这边没有可替换的区间**：`agent_loop.py` 的历史是一个不断增长的**字符串** `transcript`
  （`:2156-2561`、`:2614`），每次模型调用只发 system + 单条 user prompt（`modelgw.py:521-527`）——
  **没有消息数组、没有可变表层**。所以 `contextbudget.compact()` 今天**在生产代码里零调用**
  （全仓只有 `tests/test_context_budget.py` 调它；`agent_loop.py` 里那个 `compact_events` 是
  analysis 脚本的同名不同物）。
- ⇒ **顺序更正**：搬 DSH 的区间选择之前，必须先有"节点列表"（这正是 S-C 在做的事）。
  最省的做法是**复用已有的 `agent_step` 落档事件**当节点（`:2313-2314/2360-2361/2557-2558`，
  带 `index`/`shape`/`role`），把 `resume_transcript`（`:4504-4560`）当"事件→投影"的唯一拼法。
  **所以 S-C 必须排在 S-B 之前**（原 §13 的顺序已改）。

**【搬运来源（代码级，逐行核过）】** 下面每一格都可以直接照着写：

*范围选择与两道门*（`CB` = `dsh-compaction-basic/lib/index.js`）
- 比值的默认：`thresholdRatio = .8`（`CB:15`）、`retainRatio = .16`（`CB:17`），两者**互斥**于
  `retainTokens`（`CB:128-132`，同给即拒 `CB:169`）；无容量信息时先拒 `retainRatio >= thresholdRatio`（`CB:134-136`）。
- **容量标定**（唯一的 tokens 落点，`CB:108-126`）：`contextWindow` 非正整数 ⇒ 抛
  `TargetPressureConfigError`；`thresholdTokens = floor(cw*ratio)`；`retainTokens = floor(cw*retainRatio)`；
  `retainTokens >= thresholdTokens` ⇒ 抛。
- **两道门 + 中间夹一次剪枝**（`CB:899-905`）：`total < threshold ⇒ return null`；
  然后 `pruneSession` 剪一次并**复测**；仍低于阈值 ⇒ 直接返回（**剪枝可以免掉摘要**）。
- **node 0 排除**（`CB:379-382`、`:398`）：表层第 0 个节点是 `system/message` ⇒ 区间从 1 起。
- **保留尾部**（`CB:401-412`）：从尾往回**按 token 累加**到 `retainTokens` 止（`keepFromIdx`），
  再做**配对平衡回退**（`while keep > first and not balancedBefore(keep): keep -= 1`），
  返回 `{start: surface[first], end: surface[keep-1]}`。
  ⇒ **回退只改 start（往回走），所以永不切断 tool-call/result 对**（`CS:19-93` 的 `cutBalanced`
  是"长度 = 节点数 + 1 的布尔数组"，`Before(seq) = cutBalanced[idx]`，`After(seq) = cutBalanced[idx+1]`）。
- **`retainTokens = 0` 的效果**：第一轮就 `break` ⇒ **只保留最后一个节点** —— 这正是
  overflow / 手动路径传 0 的语义（`CB:891`、`:951`），也是"一次最大的平衡压缩"。
- **压力路径最多重试 1 次**（默认 `compactionRetries=1` ⇒ 最多 2 次），仍超阈值 ⇒ 抛
  `compaction still above threshold after N attempts`（`CB:906-919`）。
- **overflow 路径**绕过阈值与 retain 策略（`retainTokens=0`）、先无条件剪一次（`CB:887-890`）、
  且**只有在表层 `replaceGeneration` 前进之后**才允许 `{kind:"retry"}`（`CB:842-845`）。
- **读不到容量**：自动路径 **warn 一次 + 带完整历史继续**（`CB:803-808`，`warnedPressureConfigTargets` 去重）；
  手动路径**直接抛**（`CB:897-898`）。⇒ 这个三态（读不到 ≠ 0 ≠ 够用）必须照抄。

*剪枝器*（`PR` = `dsh-compaction-tool-result-pruner/lib/index.js`）
- 常量逐字：`PRUNE_MARKER = "\n\n[... tool result middle pruned ...]\n\n"`（`PR:8`）、
  默认 `thresholdChars 8192 / headChars 4096 / tailChars 1024`（`PR:10-14`，按**码点**计，`PR:25-27`、`:81`）。
- **配置期不变量（我们缺）**：`head + len(marker) + tail <= threshold` 否则抛（`PR:43-44`）——
  我们今天是 `head + tail < threshold`，**没算标记长度**。
- **跨块一条字符流**（`PR:94-117`，最值得照抄）：把全体 text 块拼成一条虚拟字符流，
  按 `[0,head) ∪ [tail,end)` 取保留区 ⇒ **head/tail 跨块连续，不是每块各留头尾**；
  非文本块**原序通过**；标记插在"与 `[removedStart, removedEnd)` 真正相交的第一块"里，且**只插一次**。
  ⇒ 我们 `_prune_value`（`_prune_value`/逐字符串递归，`contextbudget.py:669-697`）是"每个 str 各自留头尾"，
  后果很实在：`data` 里有 5 个 3000 字字段时**一个都不剪**（各都没超 8000），而 DSH 会剪。
- **两条自查（我们缺）**：① 没插到标记 ⇒ 抛；② 产出 `<= threshold` **且严格小于原文** ⇒ 否则抛（`PR:119`、`:122`）。
- **触发时机**：只在"压缩触发成立之后"剪一次（`CB:887-890`、`:901-904`；README:89「低于压力绝不动」）。
  ⇒ 我们**每次 `registry.call` 都剪**（`tools/base.py:1504-1510` + `tools/__init__.py:427`）——**不一致**。

*LLM 摘要那一段*（裁定 8乙 要换的就是它）

  （`CB:666-675`），**为的是复用 KV cache**（`CB:213-219` 的注释逐字说明）；最后追加一条 plugin 来源的
  user 消息 = `COMPACTION_INSTRUCTION`（`CB:220-255`，8 个固定小节 + Rules）。
- **reasoning 两个方向都排除**：发给摘要模型的只有"模型可见的 `content`"（三个包里 `grep reasoning` 零命中）；
  返回的摘要只留 `type==="text"`（`CB:354-357`）。
- 成帧：`CHECKPOINT_PREAMBLE`（`CB:257`）+ `<compacted-summary>` 包住（`CB:323-335`）。
- **提交前六检**（逐条）：① `finishError`（`error`/`aborted` 原样抛；`max-tokens` 抛
  `MAX_TOKENS`「summarization truncated at the token cap (incomplete checkpoint)」，`CB:336-352`）；

  **关闭本身失败 ⇒ 故意留下孤儿 start**（可被检出；晚于最新 `session/end-seed` 的才算 stale，`CB:483-488`、`:519-522`）。

  （我们走 `modelgw` 的 read timeout）。
- 摘要请求**不进会话模型的历史**：`summarizeWithLlm` 全程不 append（`CB:269-317`），原始输出只作

*`surfaceOp` 的精确形状（逐条，全都能直接写成断言）*
- **闭区间、恰好三个键**：`{op:'replace', startSeq, endSeq}`，两端**都含**（`SURF:165-174`；
  文档行 `SURFD:77-80` 写死 "inclusive"）；折叠时 `nodes.splice(startIdx, endIdx-startIdx+1, 事件自己的 seq)`（`SURF:375`）。
- 两个 seq 都必须**早于本事件**（`SURF:248-251`）、都必须在**当前表层里**（`SURF:258-268`）、
  且 `startIdx <= endIdx`（`:266-268`）。
- 只有**四种** surface-eligible 类型能带 `surfaceOp`（`user/message`/`system/message`/`assistant/message`/`tool/result`）；
  合格类型**必须**带、非合格类型带了就抛（`SURF:24-36`、`:182-193`）。
- `sourceEventSeqs` 必须**覆盖每一个被遮蔽节点**、**全部早于本事件**、不重复、不为空（`SURF:204-238`，缺一个就抛 `:234-237`）；
  **`assistant/message` 不许带它**（`:207-209`）。
- 两条**类型专属**的门（放在 session 层，这也是责任划分的一部分）：
  · `tool/result` 的替换**只能改 `content`、且只能替换恰好 1 个节点**（`assertToolResultRewrite`，`SURF:296-324`）；
  · **node 0 的 system prompt 受保护**：替换覆盖到 `startIdx === 0` 且那节点是 `system/message` 时，
    替换事件本身**必须也是 `system/message` 且只覆盖那一个节点**（`SURF:331-339`）。
  ⇒ **"压缩永远压不到系统提示词"是一条机器判据，不只是 policy 的自觉** —— 我们照搬时要把这条断言也搬过来。
- `shadowedRange` 是**位置 span**（types.d.ts:115-122 的警告）：上一轮替换把摘要节点放到旧区间的位置后，
  `start` 在**值上**可以大于 `end` ⇒ Python 里**不许**写 `range(start, end+1)`。

*三个事件的字段（逐字）*
- `compaction/start`：`{compactionId, [sourceCommandId], turn}`（`CB:446-452`；`turn=null` = 独立于回合的手动事务）。
- `compaction/summary`：`{compactionId, summary, rawOutput, llmStreamCall:true, shadowedRange, shadowedSeqs,
  shadowedTokenCount, provider, model, [maxTokens], [usage]}`（`CB:605-620`）。
- `compaction/end`：成功 `{compactionId, turn}`（`CB:467`）；失败 `{…, error}`（`CB:478-482`）。
- `compaction/prune`：`{shadowedRange:{start:seq,end:seq}, shadowedSeqs:[seq], shadowedTokenCount}`（`PR:162-169`）。

*"表层只变更一次 + 替换在锁对内"是怎么保证的（四层，**没有一层是 mutex**）*
1. **策略层的"锁"就是那条 start 事件**：先读 entry state 并 `assertCompactionInactive`（`CB:436-437`），
   然后**同步** append `compaction/start`（`CB:452`）—— 这两步"同步相邻"（`CB:420-423` 注释原文），
   start 一落盘就算持锁，之后才 await 摘要（`CB:461`）。`assertCompactionInactive` 只在
   "有未闭合 start **且它晚于最新 `session/end-seed`**" 时报 busy（`CB:519-522`）⇒ 跨生命周期继承来的孤儿 start 不算。
2. **策略层的不变量校验**（提交前唯一一次读改写校验，`CB:465` 之前）：自动路径比**整个表层节点数组**
   （`isDeepStrictEqual`，`CB:580-582`），手动路径只要求选中 span 仍是同一批 seq 且同价、区间外允许追加（`CB:588-597`）。
3. **session 层**：`seq` 由**日志长度派生**、调用方给不了（`SESS:1184`）；
   `validateNext(event)` 在 `log.push` **之前**跑（`SESS:1190`、`:1200`），把这次事件的"折叠计划"算好挂在
   `_pendingPlan`，真正入日志时**直接套用同一份计划**（`SURF:426-435`、`:449-465`）
   ⇒ **校验与提交同源**："验过的"和"落下的"不可能是两件事。
4. **重入墙**（`SESS:1181` `appending`）：**我们不需要搬**（`sessions.append` 是同步写一行，
   没有"发布期间"这个窗口）；但**第 1 层"start 与校验同步相邻"必须照抄**。
- 另一个必须一起搬的读数：`state.replaceGeneration` 单调递增（`SURF:376`）—— 它是 DSH 判
  "overflow 之后能不能 retry"的**唯一依据**（`CB:842`）⇒ 我们的表层 fold 里要维护同一个计数器。

*`pruneSession` 的触发语义（救活"假开"读数那一格）*
- **不挂 hook**：它是 `ToolResultPruner` 的服务方法（`PR:137`），全仓只有**两个调用点**，都在
  `compactIfNeeded` 里 —— overflow 分支无条件（`CB:887-890`）、压力分支**过了阈值门之后**（`CB:901-904`）；
  `agent/pre-step` 里**没有**剪枝调用。
- **扫的是整个当前表层**（`PR:139-146`），不是本步新增；超预算就全部替换（`PR:153-188`）
  ⇒ 第二次调用天然无事可做 ⇒ **语义上等价于"触发后只剪一次"**。
- 与我们今天的差别三条：① **时机**（它在压力确认后剪，我们每次 `registry.call` 无条件剪）；
  ② **记账**（它落一对事件、复测能看到效果；我们的 `_clip_fields` **不写任何事件**，
  "剪完是否低于阈值"这个读数在我们这边**不存在**）；③ **形状**（跨块一条字符流 vs 我们逐 str 各留头尾）。

*estimator 缺口 ⇒ 要补四件（`compaction_keep_recent` 从"条数"换"token 回积"的前置）*
1. **搬一个 estimator 模块**：`dsh-token-meter/lib/types/estimate.js`（`CHARS_PER_TOKEN=4`、
   `BLOCK_OVERHEAD=4`、`ROLE_OVERHEAD=4`、每块 `ceil(len/4)+4`），**常量名原样保留**。
   ⚠️ 已知偏差：`4 chars/token` 对 **CJK 会低估**（我们语料以中文为主）⇒ 做成配置项（默认 4 与 DSH 对数，可调小），
   并在读数里写明用的哪一档。
2. **给节点补计价读数**：`agent_step` 落事件时**同时落** `heuristic_tokens`（对**未截断**的那一份计价，
   **不要**用 `_for_record` 的截断副本 —— 那会系统性偏小）。形状照 DSH 的 `{seq, tokens, heuristicTokens}`。
3. **两套量纲折成一套**：DSH 有"route 计价"与"固定启发式"两套并存（`shadowedRouteTokenCount` vs
   `framedSummaryTokenCount`），我们**没有路由/图片计价** ⇒ 只有启发式一套，
   **这个折法必须写进注释**，否则以后有人补了路由价就会踩到 `CB:571-572` 那个不对称。
4. **压力基线**：DSH 用"usage 锚（够大就信）否则估算"；我们的 `tokens_in` 是**事后**真实 usage，
   可以当锚 ⇒ 要补的是"上一轮 usage 锚 + 本轮增量"的折法，否则每次都得全量重算。
   另：`SeamCall.to_dict()` 里**没有 `max_tokens`**（llmseam.py:106-130）⇒ DSH 那条"摘要事件记 maxTokens"
   的可重建性我们**缺这一格**，要补。
- **配对平衡的输入**：若节点 = `agent_step`，则 `cuts` **恒为全 True**（一个 step 自成完整回合）⇒
  **这一格不用实现，但必须写成断言**（节点边界 == step 边界），否则以后有人细粒度化节点就会静默切断调用/结果对。

*两条路线与我们该选哪条（子代理的建议，我同意）*
- **方案 a（照 DSH）**：剪枝挪到"触发后一次" + 落一对事件（`compaction_prune` + 带 `surface_op` 的替换）。
  好处：复测能回答"剪完是否免掉摘要"；日志可重放（**这是唯一能保住 `resume_transcript`
  "逐字一致"那条判据的做法** —— 剪枝写在事件里，重建按事件重放；只在内存里剪会让续跑那一趟看到没剪的版本）。
  代价：中等（新增"本趟已剪"状态位、`sessions.append` 要能带 `surface_op`/`shadowed`）。
- **方案 b（我们的形态）**：只把 `threshold_chars` 降到观测层阈值以下（8000 → 3000）+ 加一条
  "存在 `meta.pruned=True`"的断言。好处：改动最小、能**立刻救活假开读数**（今天那条断言恒假）。
  代价：仍然**不记账**、与 `_clip_fields` 的**动态**逐字段预算互相打架、把"剪枝"与"观测截断"折成一件事。
- **采用**：**先做 b 的最小子步（把 8000 改成 3000 + 那条断言）把假开读数救活，
  同时按 a 的形状设计落事件**，a 的实现随后。理由：b 是 a 的探针（它证明"阈值确实能触发"），
  而 a 才是裁定 8乙 要的 DSH 口径。

**判据**
- 正控：造一段超阈值的 transcript ⇒ 步骤边界真的压了一次，且事件里能看到
  `original_chars / kept_chars / shadowed / summarizer="llm"` 读数。
- 负控：未超阈值 ⇒ **一次也不压**（"没压"与"压了没效果"分开）。
- 反真空：压缩后转录里**仍然有**任务原文那一节（节点 0 不变量）。
- 三态：`contextWindow` 读不到 ⇒ 既不静默当零、也不阻断这一趟（照 DSH：
  自动路径警告一次、带完整历史继续）。
- **假开的读数必须先修**（这一条是新的，来自代码级搬运清单）：
  正控 —— 在**模型可见路径**上造一条超过剪枝阈值的结果 ⇒ 剪枝分支**真的被触发**（读数里有
  `pruned` 与省下的量）；负控 —— 阈值以下**一次也不剪**。
  **今天这一条会红**：观测层 `RESULT_CHARS=6000` / `RECORD_CHARS=2000` 都低于阈值 8000，

## §5 施工单 S-E：逐工具超时（裁定 13甲）

**【搬运来源】**（代码级，已逐行核过）
- **要搬的实现**：`dsh-tool-call-timeout-policy/lib/index.js:115-134`（`tools/execute` 包装器：
  查 `ctx.tools.get(name).timeoutMs` → `void 0` 就 `next()` 原样放行 → 装截止 → **只在"我们自己的
  那口钟"响过时**替换结果）+ `:93-109` 的替换结果 + `dsh-timeout/lib/index.js:57-73` 的 `deadline`、
  `:12-25` 的 `TimeoutReason`、`:134-138` 的 `timeoutOf`。
- **逐字搬的常量/文案**：`TOOL_TIMEOUT = "TOOL_TIMEOUT"`（**既作内部超时分类码、又作结构化错误码**）；
  模型可见文本 `Error: tool call timed out after <ms>ms`；`error.info.name = "ToolTimeoutError"`；
  注册期校验文案 `tool "<name>" timeoutMs must be a positive finite number`；
  内部 reason 文案 `` `${code} after ${timeoutMs}ms` ``。
- **一个必须搬的判据（嵌套截止的作用域）**：`timeoutOf(x, code)` 只在 `reason.code` **等于自己那口钟的
  code** 时才算"我超时了"；外层包装器的钟先响 ⇒ 读作**普通上游取消**并原样透传下游结果。
  逐字理由（`:73-80`）：防止嵌套时把自己的超时**误读**成别人的。
  每个能力有**自己的** code（`BASH_TIMEOUT`、`TASK_WAIT_TIMEOUT`、`WEB_FETCH_TIMEOUT`）——**不许合并成一个哨兵**。
- **只有网络类工具声明了它**：`dsh-tool-web/lib/index.js:838` 默认 `3e4`（30s）；
  随附的 `bash`/`read`/`write`/`edit` **有意不声明**（`README.md:123`）。⇒ 印证裁定 13甲 的"无统一默认"。

**【一个必须先解决的机制问题（已升级为待裁 12-D）】**
DSH 的超时是**协作式**的：`setTimeout` 只 abort 一个 signal，工具自己看信号收工 ——
逐字「without racing or abandoning the tool promise」（`:5-6`）。而**我们的 `ToolRegistry.call` 是同步的**
（`tools/base.py:1304-1313`），没有 await 点可以观察计时器。三条路（保真度从高到低）：
1. **ContextVar 协作式截止**（保真度最高）：照 `cancellation._CURRENT_TOKEN` 的既有形态
   （`cancellation.py:441-459`）发布一个 deadline，处理函数在检查点调 `raise_if_timed_out()`；
   代价是**每个长处理函数都要带检查点**；
2. **工作线程 + `future.result(timeout=…)`**：真墙钟截断，但**线程杀不掉**（DSH 的局限 + 新局限：
   游离线程会改共享状态，撞 `store.py` 的 `LOCK_ORDER` 与文件锁）⇒ **不建议当通用机制**；
3. **子进程**（`cancellation.run_cancellable`，`cancellation.py:486-540`）：已经能真杀，
   三态（`cancelled` / `timed_out` / 退出码）也已经分得开 ⇒ 对 `external == "exec"` 那几件（Lean/脚本）**就用它**。
**业主已裁（12-D，逐字）：「甲，不机械杀进程」** ⇒ 机制定为 **ContextVar 协作式截止**（保真度最高那条），
**乙（工作线程）不做**；同时**不做任何"机械杀进程"** —— 连起子进程那几件（Lean / 脚本）也**只走协作式**：
设截止 + 通知它收手 + **有界等待** + 到点**如实报"超时"**（不许声称"已经停住了"）。
**一处要分清**：既有的"用户叫停"那条路（`stopctl` 的 `kill_tree`）**是另一件事，不动** ——
业主要求的是**超时不许硬杀**，不是取消既有的停机能力。

**【禁改区事实（影响开工顺序）】**：`tools/base.py` 在 `.noai-paths` 里（`auth-audit`）⇒
`ToolSpec` 加 `timeout_ms` 字段、`tool()` 装饰器转发、`ToolRegistry.call` 里那次包装、
`tool_timeout_result()` 这四处**都要人写或人逐行走查 + 2 名 reviewer**（`noai_gate` 会以 1 结束）。
**业主已裁（12-G）：「按建议」** = **乙先落** —— 超时表放**新模块**（`timeout_table.py` 之类），
截止由循环在调 `registry.call` 前后设/清，**一行禁改区都不碰**，S-E 因此**可以立刻开工**；
等机制验过之后，再决定要不要把 `timeout_ms` 正式写进 `ToolSpec`（那时才走甲 + 你的逐行走查）。

**【一个不能留白的坑】**：`_call_reading`（`agent_loop.py:355-358`）会把整条结果**哈希**进连击键。
若超时结果里带上"这次等了多久"，两次超时就会产生**不同的读数** ⇒ `dead >= max_dead_loop` 可能永远
不触发（模型可以无限循环在一个超时调用上）。**必须显式选**：要么让超时结果**逐字节相同**
（把耗时放到侧信道读数里），要么给超时单独记一个计数。**业主已裁（12-E）= 甲** ⇒ **超时结果逐字节相同**
（耗时只放侧信道读数里），连击照常累加 ⇒ 一个总是超时的调用**照旧会被判停**。

**改动面**：`ToolSpec` 加可选 `timeout_ms`（**秒**，与全仓 `timeout_sec` 同单位；DSH 是毫秒 —— 单位
只在一个边界上换算）；执行期协作式截止；超时结果按上面的形状；第一批只给检索 / 下载类 / 起子进程。
**判据**：正控 —— 声明 1s 的工具在 ~1s 后收到超时结果、**进程未被硬杀**；负控 —— 未声明的工具不受影响；
**嵌套正控** —— 外层钟先响时内层必须读作"上游取消"而**不**报自己的超时（照 `timeoutOf` 的作用域）；
三态 —— 限时读不到（配置缺）时不许当 0。
**代价**：协作式意味着"忽略信号的工具会让调用方继续等"（DSH 原话）—— 接受它，或者对起子进程那几件
额外加一次"墙钟到点就收结果、进程交给清理"。
**依赖**：12-D（机制形态）与 12-E（是否计数）裁了才能开工。

## §6 施工单 S-F：**抄 DSH 的"没有内置轮次预算"**（当轮新裁定）

**这句话的落点**（我按 DSH 的原文口径翻译成我们的形态）：
DSH 的循环**不自己判停**：逐字「没有内置轮次预算——工具调用或 steering 会让当前轮次继续；
限制失控轮次的策略必须从既有生命周期扩展点（如 `agent/turn-stopping`）执行取消」
（`dsh-agent-loop/README.zh.md:200`）。

**【搬运来源（代码级）：先钉死一条事实，再给执行形态】**
- **DSH 里真的没有任何轮次/步数预算**：`AgentLoop.Config` 只有 `maxParallelToolCalls`（默认 10）
  与 `agents[]`（`dsh-agent-loop/lib/index.js:1490-1502`）；`AgentOptions` 只有
  `{provider, model, reasoningEffort, maxTokens}`（`dsh-tool-cordis/lib/index.js:5751`）；
  全仓 grep `maxTurns|maxSteps|turnBudget|stepBudget` **零命中**（`maxRounds`/`maxGoalRounds`
  在**循环之外**的 Ralph 与 goal 驱动里）。
- **但它的替代品基本不能停**：`agent/turn-stopping` 是 **serial 事件**，签名
  `Promise<void> | void`，**返回值被丢弃**（`dsh-tool-cordis/lib/index.js:5074`；调用点
  `dsh-agent-loop/lib/index.js:967` 不接返回值）；官方描述逐字「**Data decides, so listener order
  cannot change the outcome**」（`:5076`）。它能做的只有 `agent.steer/inject/followup`（把本轮
  **变长**）。真正的刹车只有 **AbortSignal**（`agent.cancel()`）。
- **DSH 唯一"从数据侧结轮"的机制是 `concludesTurn`**：工具的成功结果带 `concludesTurn: true`
  ⇒ 该步结束时收轮（`dsh-agent-loop/lib/index.js:579`、`:1117-1119`；`dsh-tools/lib/index.js:1303`；
  类型上**只有成功结果能带**，`dsh-tool-cordis/lib/index.js:8207/8223`）。
- **收一轮的全部出口**（15 行表里对我们有用的）：pre-step 被拒 ⇒ `blocked`；模型这一步没有
  tool-call ⇒ `completed`；结果带 `concludesTurn` ⇒ `completed`；撞 max-tokens ⇒ `max-tokens`；
  abort ⇒ `aborted`；其余异常 ⇒ `error`；**其余全是 AbortSignal 一族**（外部 `cancel`、dispose、
  父中断、goal 驱动取消、用户取消）⇒ **"没有内置预算"留下的不是"更聪明的自动停"，而是"只能靠外部 abort"**。

**【这条裁定该怎么执行 —— 业主已裁（2026-10-10，逐字）】**
> 「步数上限不做为硬标准，不设机器闸，但向父代理报告步数超限行为，由父代理决定继续放行还是刹停」

读成四条：
1. **不设机器闸**：`stop_reason` 里**不再有**"循环自己因步数收工"这一档 —— 步数**不是**判据。
2. **超限 ⇒ 上报**：达到报告阈值时，向**父代理**发一条**报告**（不是请求许可、不是阻塞等待），
   内容是可复核的读数：已用步数 / 此刻在做什么（最近几个形状） / 花了多少（token·usd） /
   离目标还差什么（最近几条读数）。
3. **父代理裁决**：继续放行（**默认**，循环不停、不空转）或**刹停**（走 S-H 的 `interrupt`，
   或全局停机）。M 是顶层（它的父代理就是用户）⇒ **报给用户**（`conductor.status_report` +
   一条留言/插话，必要时 `ask_user`）。
4. **保留的不是"轮次预算"而是另外两件**：**钱的闸**（`usd_budget`）与**墙钟**（`wall_clock_sec`）
   照旧拦（它们不是步数）；**判停**那一道（无进展 / 同一条路反复，S-D）也保留。

**改动面**
1. `max_steps` **不再**是收工理由：删掉"步数到顶 ⇒ `stop_reason="max_steps"`"那一支；
   保留步数**读数**（`steps_used`），并新增**报告阈值**（可配，例如 30 / 60 / 120 或一个倍率）。
2. 新增"步数超限报告"：一条会话事件 + 一条给父代理的**留言**（同一条读数两处可见）；
   报过之后**不再重复报**（除非又跨过下一档），也**不改变循环的行为**。
3. 父代理的动作走既有面：`interrupt`（S-H）/ 全局停机 / 或者什么都不做（默认继续）。
4. `--max-steps` 这个开关**改名或改语义**（"报告阈值"），注释与 `run_role` 的透传
   （`agent_loop.py:4643`、`:4706`）**以及 checkpoint 口径**要一起改 —— 否则"参数还在、含义变了"
   会让续跑读数对不上。
5. **钱与墙钟一个不减**：它们是安全阀，不是"轮次预算"。

**判据**
- 正控：一个连续 12 步都在调工具的循环**不会**因步数收工（要么自己 `final`，要么被钱/墙钟/判停拦）。
- 正控（本裁定的核心）：跨过报告阈值 ⇒ **父代理那侧确实收到一条报告**，且报告里带得上文四样读数。
- 负控：父代理**什么都不做** ⇒ 循环**继续跑**（不许把它折成"等待"或"默认停"）。
- 正控二：父代理下令刹停 ⇒ 受控收尾，`stop_reason` 记的是**父代理刹停**（不是"到了步数上限"）。
- 反真空：`stop_reason` 词表里**不许**再留一个永远不会产生的 `max_steps` 旧词。

**代价与风险**：**这是我们最贵的一次放开**（步数不设限 ⇒ 一个卡住的循环会一直跑到预算耗尽）。
缓解：① 预算与墙钟仍是硬闸；② 判停/提醒读数（S-D）照旧；③ 真跑配方里显式写一个策略上限
（"默认不限"是**能力**，不是"每趟都不限"）。
**依赖**：与 S-D（提醒/判停）同向，建议同一批落。

## §7 施工单 S-G：父代理"等"子代理 —— 学 DSH 的**通知模型**（裁定 15）

**先把 DSH 怎么"等"说清楚**（`dsh-tool-subagent/README.zh.md:132`、`:165` 逐字口径，代码级见下）：
- **可继续委派（后台）**：父代理**继续干活**，孩子的结算以**通知**到达父级；
- **前台委派**：**只在"下一步动作依赖该结果"时**才用，此时阻塞等它的最终文本；
- 两条都不是"sleep 着等"：等待是**事件驱动**的（结算事件到达 / 工具调用返回）。

**【搬运来源（代码级）：三种模式、结算怎么到父、以及我们没有的那一半】**
- **三种模式的判别式与返回值**（`dsh-tool-subagent/lib/index.js:431-488`、`:521-560`）：
  `{kind:"foreground", runId, output}`（**同步等**，工具调用在子跑完才返回，回正文）/
  `{kind:"background", jobId}`（走 `jobs`，回 `started background subagent job <id>`，
  父要自己 `job_output` 去读）/ `{kind:"continuable", subagentId}`（**无 output 字段**，
  回 `started subagent <id>`）。缺省由 `resolveDelegationRun` 决定：
  `run_in_background ?? (backgroundMode === "continuable")`（`:354-361`），
  且"没开后台能力却传了 true" ⇒ **抛**（不许静默降级 —— 这条与我们
  `SubagentBackend` 的"故意拒绝"同一条纪律，`conductor.py:365-394`）。
- **结算怎么到父**：只有 continuable 会**主动推** —— `notifySettlement`（`dsh-subagent/lib/index.js:1245-1258`）
  构造一条 **user 消息**（`createSettlementMessage` `:661-681`：`source.kind = "subagent-settled"`，
  正文 = 一句话说清"为什么停了" + `"Its closing message:"` + 子的最终输出；无输出则
  `"It left no closing message."`），然后按 **父在不在跑** 分叉：
  `parent.status === "idle" ? "queue" : "steer"`（`:1255`，`sendWaking` `:873-885`）
  ⇒ **父在跑 ⇒ 塞进下一步；父空闲 ⇒ 排一个独立 turn**。
  one-shot 后台那一路则由 jobs 推一条 notice（`dsh-tool-jobs/lib/index.js:206-227`）。
- **"子先父后"的判据我们已经有了，别重写**：DSH 的 `settlementState`（`:1192-1198`）要求
  "子的 inbox 空 **且** 它自己的 ownedChildren 空" 才 ready；我们的 `retire_ready` 用**同一判据**
  （`active_by_parent.get(tid,0) > 0 ⇒ waiting_with_children`，`conductor.py:1614-1615`）。
  可搬的只有它那一格 `"retry"`（`poke` 世代比较）：**读数期间状态又变了就重算**，
  而不是拿旧快照下结论 —— 我们缺这一格。
- **我们缺的那一半（最要紧）**：DSH 有**两个队列** —— `next-step`（运行中，最近的 step 边界收到）
  与 `next-turn` + `wakeDriver`（**空闲 ⇒ 立刻开一轮**，`dsh-agent-loop/lib/index.js:837-852`）。
  我们只有前者的一半、且载体是盘上留言（`_hear()` 每步尾读一次，`agent_loop.py:1986-2025`，
  并进**这一步的结果** `:2505`）⇒ **一个已经 `final` 收工或正在等用户回答的循环，不会被任何留言唤醒**。
  要"等"得像 DSH，这一格（唤醒）是必须补的。
- **通知要有形状契约**：DSH 的通知是带 `source{kind, form:"notice", summary}` 的 message
  （`dsh-subagent:663-680`、`dsh-tool-jobs:208-219`）；我们的是裸 dict
  （`heard.append({"id","from","channel","subject","body"})`）。
  ⇒ **搬 `source` 这一格**：没有它，"这条是子代理结算 / 插话 / 广播"在读数上分不开。
  反过来，**我们的两点比 DSH 强、别丢**：`mark_delivered` 推迟到"模型真被问过一次"才登记
  （`agent_loop.py:2261-2268`）；以及结算项带 `expects="ack"`（`conductor.py:943`）。

**改动面**（我们的形态）
1. **读数侧**：父代理收工前读一条"我名下还有几条在飞"（已有 `_in_flight_children_of`），
   把它写进收工门与状态视图（**读数，不拦**）。
2. **行为侧**：把今天"到扇出上限才等"（`fanout_wait_sec`）扩成"**有在飞的子代理就可等**"，
   但等的实现**照 DSH**：
   - 父代理**先接着干别的**（不空转）；
   - 孩子结算 ⇒ 以消息/通知到达（我们已有 `message` 形状与秘书投递）；
   - **确实没别的可干且还有在飞孩子**时，等的是"下一条事件"，**有界**（墙钟上限）；
   - 超时 ⇒ 记读数继续收工（不否决收工 —— 与裁定 1「收工由 M 判」一致）。
3. **不要**做"父代理循环里 sleep N 秒再看一次"—— 那是 DSH 明确没有的形态，
   而且会把墙钟吃掉。

**判据**
- 正控：父派了两个子任务后**不再空转**：它要么继续派别的活、要么收工前读到"还有 2 条在飞"。
- 正控：孩子结算后，父的名册/收件箱里能看到它的结果（通知到达）。
- 负控：**不许**用 `sleep` 实现"等"（判据：等待期间会话事件里没有空白的时间段，
  或直接断言"等"这条路上没有 sleep 调用）。
- 三态：等超时 ⇒ 收工**照样成立**，但门里带一条"还有 N 条在飞"的读数。

**代价**：父代理可能"收工时孩子还在飞"（这是裁定 1 允许的），代价是"父的交付可能没有孩子的结论"；
缓解是读数把它摆出来（谁在飞、飞到哪一步）。
**依赖**：与 S-H（子代理面）同一批最自然 —— "要等就得先看得见"。

### 代码级搬运清单落地之后**新冒出来的 7 个问题**（12-D ~ 12-J）
> 这 7 个不是我漏问的，是**读了 DSH 的实现之后才发现必须有人定**的 —— 每一条都卡着一整张施工单。

**12-D 超时用哪种机制？（卡 S-E）**
我们的 `ToolRegistry.call` 是**同步**的，没有 await 点可以观察计时器；DSH 那边靠 `setTimeout` + signal。
- 甲 = **ContextVar 协作式截止**（保真度最高，照 `cancellation._CURRENT_TOKEN` 的既有形态）：
  处理函数在检查点自己看信号 —— 代价是**每个长处理函数都要带检查点**；
- 乙 = 工作线程 + `future.result(timeout=…)`：真墙钟，但**线程杀不掉**，游离线程会改共享状态
  （撞 `store.py` 的 `LOCK_ORDER` 与文件锁）——**我不建议当通用机制**；
- 丙 = 只对 `external == "exec"` 那几件（Lean / 脚本）用**子进程**截止（`cancellation.run_cancellable`
  已经能真杀、三态也已经分得开），进程内的工具**不做**超时。
- **我的建议**：甲作通用 + 丙作 exec 类，明确不提供乙。**顺带一个单位问题**：DSH 是**毫秒**，
  我们全仓是**秒**（`timeout_sec`）—— 我按秒写、只在一个边界换算，除非你要照 DSH 用毫秒。

**12-E 反复超时的调用，要不要算进"判停"？（卡 S-E 的判据）**
`_call_reading` 会把整条结果**哈希**进连击键。若超时结果里带上"这次等了多久"，两次超时就是
**不同的读数** ⇒ `dead >= max_dead_loop` 可能永远不触发，模型可以一直循环在一个超时调用上。
- 甲 = 让超时结果**逐字节相同**（耗时只放侧信道读数）⇒ 连击照常累加；
- 乙 = 超时单独记一个计数，不掺进连击。
- **我的建议**：甲（少一个新机制，且"同一个超时调用连着来"正是该判停的形态）。

**12-F 提醒的连击，要不要在"新用户消息"时清零？（卡 S-D）—— 你问"哪个计数？"，这里说清**

我们循环里**同一族有三个计数**，都在一步结束时算出来（`agent_loop.py` 的步尾那一段）：

| # | 计数 | 判据是什么 | 现在用来干什么 |
|---|---|---|---|
| **① 同一个调用** | `prev_key` / `_call_key` | 连着几步「**形状 + 参数**」逐字相同（`why` 那句理由不计） | **就是要裁的那一个**：第 **3** 次 ⇒ 出【同一个调用】提醒；第 **5** 次 ⇒ `no_progress_limit` **判停**（裁定 10丙） |
| ② 同一个读数 | `prev_reading` / `_call_reading` | 连着几步**结果内容**的哈希相同（"没拿到新事实"） | 出【没有新事实】那句提醒 |
| ③ 同一条路 | `prev_stall` / `_stall_key` | 连着几步打的是**同一个动作**（不看参数） | 出"同一条路"提醒（`stall_nudge=3` / `stall_alert=6`，**只提醒、不判停**） |

**DSH 清的是 ①**（它的链就是 `(工具名, 规范化参数)`，`dsh-repeat-tool-reminder/lib/index.js:1509-1511`），
逐字承诺「**A new user message clears the count, so a fresh instruction is never treated as a loop**」；
而且它**明确不因为自己那条提醒而清零**（提醒是插件消息、不是用户消息）。
我们今天**三个都不清** —— 只在**新建 `AgentLoop`** 时归零 ⇒ **用户中途插一句新指令，之前那串计数接着算**，
于是"新指令带来的重复"可能被上一句指令的账算到头上。

- **甲** = **三个一起清**（新指令 = 新局面，三个计数都从头算）；
- **乙** = **只清 ①**（严格照 DSH 那一格，②③ 保持）；
- **丙** = **都不清**（保持今天的行为）。
- **我的建议**：**甲** —— 它防的正是"用户给了新指令，模型却被当成在死循环"；
  而且 ②③ 同样会因为新指令而失效（新指令之后"同一个读数"不再说明没进展）。
- **要你圈的**：甲 / 乙 / 丙（**你上一轮圈的那条我按这个理解写成待答**）。

**12-K "抄 DSH 的没有内置轮次预算"到底怎么执行？（这条会改你的裁定，所以单独问你）**
代码级核过之后的事实是：**DSH 的替代品基本不能停** —— `agent/turn-stopping` 是
"**Data decides**"的 serial 事件、**返回值被丢弃**（不能 veto），它能做的只是把这一轮**变长**；
DSH 唯一"从数据侧收轮"的机制是**工具结果带 `concludesTurn`**，其余出口全是 **AbortSignal** 一族。
换句话说：DSH 的"没有预算"是**把刹车交给外部 abort**，而不是"更聪明地自动停"。
而我们今天的 `max_steps` + `no_progress_limit` + `dead_loop` **是三道真的会停的闸**。
- 甲（**推荐**）= **保留闸门、改口径**：把 `max_steps` 在词表与注释里标成"**本框架自加的观察窗**
  （DSH 无此判据）"，默认值当策略上限；同时先补两样我们缺的（工具级 `concludesTurn` + per-child `interrupt`）；
- 乙 = 照字面去掉（默认 `None`），runaway 只靠数据侧判据与外部停机开关；
- 丙 = `max_steps` 只留读数（到上限不自停，改走一次"轮末 hook"由策略决定取消）。
- **要你圈的**：甲 / 乙 / 丙。**我强烈建议甲** —— 乙把最贵的风险（卡住烧到预算尽）放大了，
  而 DSH 那边之所以敢没有预算，是因为它的用户随时能按 abort。
