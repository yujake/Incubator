## §2 额度寄存器的语义（三态写死在读数里）

1. **总额**：寄存器 `<工作区>/budget.json` 里 `total_usd` + 只增的 `added[]`
   （每条带 `kind`/`usd`/`by`/`at`/`note`）。`--set`（改总额）**不抹掉**追加历史：
   两类事件记在同一份账上，抹掉后者会让"已花 7.5 而历史里只有一笔 set"变成一笔无解的账。
   坏寄存器上显式 `--set` 仍然许写（否则用户没有出口），但"丢了什么"写进回执
   （`history_lost`）—— 它不是静默覆盖；
2. **花销**：永远从 `usage_ledger` 现算（那一层本来就幂等），寄存器里**不记**花销 ——
   两处记账必然漂移，而"这趟花了多少"只有一个权威来源；
3. **三态**：寄存器在 ⇒ 用它；不在 ⇒ 回退到 `--budget-usd`；**损坏 ⇒ 回退 + 把
   `problem` 原样报出来**。第三态刻意不折成"无上限"：读不出来与没有上限是两件事；
4. **每次闸门现读**：额度可以在运行中途被追加（这就是"用户可追加预算"的实现面），
   而追加不需要重启那一趟；
5. **可为负一点点**：闸门按步与按调用检查，不是预授权 —— 扣完那一刻已经在飞的
   那一次调用仍会落账，于是最终读数可能略微越过上限。这一档如实上报
   （`exceeded`），不假装正好等于上限。

为什么不去给 M 加一个"追加预算"的动作：那会命中 `specs/m.py` / `capabilities.py`
与四份冻结快照（`draft/112` §4.3 的裁定）。本批按"盘上文件 + HTTP 端点 + CLI"做，
一条禁改区都不碰（唯一命中见 §4）。

## §3 60 秒超时是怎么回事（业主追问：谁接不到谁的返回）

**等待方是我们，不是模型。** 那 60 秒是 `ModelSpec.timeout_sec`：一次
`POST {base_url}/chat/completions` 的**客户端读超时**（`urllib.request.urlopen(..., timeout=…)`）。
超时的含义只有一句：**我们在 60 秒内没等到网关把响应体发完**。它不是模型的输出上限，
不是框架的步数/墙钟闸门，也不代表模型"没返回"——它可能正在想，只是我们不再等了。

现场读数（第一次无 Lean 模式 T2，sid `t2u1`）：

| 读数 | 值 | 说明 |
|---|---|---|
| 步 0 | **260.469 s** 成功 | 输出 12,178 tokens、推理 39,755 字 —— 合法的一步可以要 4 分钟 |
| 步 1 | 三次 `超过 60.0s 未返回` | `elapsed_sec=424.594` = 3×60 秒 + 退避（`max_retries=2` ⇒ 共 3 次尝试） |
| 离线探针 | 一条 32,768-token 的思考回复 **181.1 s** | 输出上限提高之后这个是常态，不是异常 |
| 端点自检 | HTTP 200 / `finish_reason=stop` | 端点本身没问题，"等不到"是**时限**问题 |

所以病灶是**两个数不匹配**：R62 把单次输出上限从 4096 提到 32768（否则严格 T1 会
被静默截断），而请求超时还是 60 秒 —— 于是"它想了 3 分钟"被翻译成"失败"，
而且重试三次全是同一堵墙（同一个上限）。本批把缺省改成 300 秒
（`AGENTFLOW_MODEL_TIMEOUT_SEC` 可覆盖）。

**顺带发现的第二个缺陷（归因错）**：网关这一层**从不抛异常**，它把超时折成
`ok=False` + `error_kind="timeout"`；而缝此前对"回复不 ok"一律写
`judge_failed:ModelReplyNotOk`。后果是上面那三次超时被循环算进 `bad_json_streak`，
收场措辞写成「连续 3 次没有给出可解析的 JSON」—— 三句话没有一句是真的。
归因错不是难看，是**修错地方**：坏 JSON 的处置是收紧输出协议，超时的处置是
调大上限或把这一步拆小，两者方向相反。现在：

- `judge.problem_of_reply()` 是"回复 → 失败码"的唯一映射点
  （超时 ⇒ `judge_timeout`；输出吃光 ⇒ `judge_output_limit`），
  与"异常 → 失败码"的 `judge._problem_of()` 并列；
- `LoopRun.no_reply` / `no_reply_streak` 单独计数（**不进** `bad_json`）；
- 连击到上限时 `stop_reason` 是 `model_timeout` 或 `model_output_limit`，
  收场那句话说的是"没拿到可用的回复"，并给出可行动的出路（`--resume` / 调大超时 /
  拆小这一步）；
- 回给模型的那一句纠正也换了：不是"只回一行 JSON"（它对一次超时无可行动），
  而是"把这一步拆小"；
- 续跑重建对话时按同一句还原（`resume_transcript` 的那个分支），
  "重建的那一段与当时逐字相等"这条判据不漏这一档。

**同一天发现的第三档（同一个病灶的另一个入口）**：第一次 T2 的 21 步里有 **2 步**
（步 2 与步 18）的上游回复是 `content=""` + `finish_reason=length` + 思维链
**109,397 / 96,969 字**。推理 token 与正文**共用**同一份 `max_tokens=32768`
（109397 ÷ 32768 ≈ 3.3 字/token，与中文推理的字-token 比一致）——
也就是"它想得很多，而一个字正文都没留下"。这一档此前也落成
`judge_failed:ModelReplyNotOk` ⇒ 按坏 JSON 计数、按"重念输出协议"纠正。
现在：

- `modelgw` 新增 `error_kind="output_exhausted"`（判据是那三个条件同时成立），
  计进"没查成"、**不重试**（同一个请求必然同一个结局，而重试一次要再付一整份
  输出预算 —— 那两条各 32,768 token）；
- `judge.problem_of_reply` 把它映成 `judge_output_limit`（新码，只加不删）；
- 循环把它计入 `no_reply`，纠正那句话是"下一步只回一行 JSON，把想法压到十句以内；
  要做的事本来就大就把它拆小"；
- 负控两条：同样空正文但 `finish_reason=stop` ⇒ 仍是 `bad_response`；
  被截断但一个字都没想 ⇒ 也仍是 `bad_response`（那一档是"它没想"，不是"想太多"）。

为什么**不**顺手把 `max_output_tokens` 从 32,768 再抬到 65,536：那不解决这一档 ——
上次它正好停在 32,768 上（109,397 字 ≈ 33k token），抬到 65,536 只是让一次
"想过头"多花一倍的钱，正文仍然可能一个字不剩。这一档的杠杆在**让这一步变小**
（以及纠正话术），不在上限；上限那一格留给"截断的正文"那一类（例如写到一半的 JSON）。

超时**没有**进 `settings.json` / UI：它不是角色行为，是机器级参数（本机网速），
按"一处定义"该与 `model.*` 那几个键同批做，因此与设置页一起排在下一批。
