## §1 先立三条不变量（格式是被它们逼出来的）

**F1（两类动作，互不冒充）**：沿一条**已有边**发生的是**消息**；**新起一个实例**才是**下派**。
消息不新增节点、不占开边名额、不计深度；下派反之。**禁止用"再起一个实例"实现问答/澄清**
（所有者逐字："A 和 B 两个人互相沟通别整成 A 调 B，B 调 A2，A2 调 B2…"）。

**F2（内容绝不因格式而丢）**：任何一条交流，**全文必须落盘**；进对方上下文的是**有界的信封**
（一句话 + 引用号），其余靠编号取。这一条是针对所有者 T4 的怀疑
（「"诚实且空"绝对是系统 bug 丢掉了 LLM 的工作结果」）——**格式本身不许再有"截断即丢"的余地**：
凡是要截断进上下文的，截断后的全文必须另存，且信封里带它的编号。

**F3（硬事实必须可读，且必须分类）**：搜到没搜到、取回没取回、下载成没成、实验跑没跑
——这些**硬结果**要以**受控取值**出现在交流里（不只躺在表里），且**失败要分类**
（不许把"网络坏了"折成"真的没有"）。这是 T6/T9 的落点。

## §2 一个信封，四种 kind

**一种行格式**（追加式 JSONL；沿用工作区里既有的 `manuscripts/handoffs.jsonl` 落点形态），
用 `kind` 分四类 —— 前两类是**边上的消息**，第三类是**交差**，第四类是**框架通报**：

| kind | 方向 | 是否新起节点 | 语义 | 谁写 |
|---|---|---|---|---|
| `delegation` | 父 → 子 | **是**（这条消息与"加边"同时发生） | 任务书：交给你什么、判据是什么、期望交回什么 | 父（模型） |
| `message` | 父 ↔ 子（**双向**） | **否** | 边上的传话：问、答、澄清、提醒、告知 | 父或子（模型） |
| `report` | 子 → 父 | 否（子这一趟结束时写） | **交差**：结论 + 依据 + 缺口 | 子（模型） |
| `notice` | 框架 → 父（或子） | 否 | **框架通报**：某某已结算 / 无结论 / 被停 / 超时未回 | **框架**（不是模型） |

**为什么 `notice` 必须与 `report` 分开**（DSH 的做法，`dsh-subagent/README.zh.md:133`）：
"子代理结束了"是**事实**，"子代理的结论是什么"是**内容**。二者混在一起，
就会出现"没有结论 ⇒ 看起来没结算"或者"结算了 ⇒ 假装有结论"。DSH 的兜底句是
`It left no closing message.` —— 我们照抄这个分层：**框架只通报事实，内容由模型给；
模型没给就如实写"它没有留下结论"**。

### 2.1 一块板：每行是一个**工作项**（所有者 2026-10-08 晚裁定 T16）

逐字：「留言就塞 task_board，因为**每句话都是需要有行为的**，即使是光知道个信息
也要**确认读过再消掉**。」

这条把 §2 的四种 kind 从"四种消息"改成"**四种工作项**"，也把投递语义整个换掉：

| kind | 谁写 | `expects` | 最小行为 | 算做完的证据 |
|---|---|---|---|---|
| `delegation` | 父（模型） | `work` | 干活 | 一条 `report` |
| `message` | 父或子（模型） | `ack`（默认）或 `work` | **确认读过** | 一条 ack 状态行 |
| `report` | 子（模型） | `ack` | 父**确认读过** | 父的 ack 状态行 |
| `notice` | **框架** | `ack` | 收件侧确认读过 | ack 状态行（框架也记账） |

**状态机（所有工作项共用，一步都不许跳）**：

```text
queued ──(有读者领走)──▶ claimed ──(行为完成)──▶ done
                                     ├─ acked      （expects=ack：知道了就算完）
                                     └─ completed  （expects=work：交付 + 汇报才算完）
```

三条纪律：

1. **"读到"不是"消掉"**：状态迁移与交付都写成**追加行**（append-only），
   "它读过没有""谁读的""第几步读的"三件事都必须能从账本里读出来；
2. **最小行为是 ack，不是沉默**：即使是"光知道个信息"，也要有一条确认过读过的行 ——
   "没 ack 的项"就是"还挂着的事"，这正是三态纪律要的那种可见性；
3. **消边谓词（T2）不变**：工作项的状态是**边上的事**，不是边本身；
   边只在"子全停 + 自身停"时才消。

**为什么这一条同时解决 A / B / D**：

- **A**（渲染 8 条却标记全部）：投递状态**不再是一个 bitset**，而是工作项自己的状态 ⇒
  "渲染一批、标记一批"这个形态**不存在了**；
- **B**（没有读者的角色）：代读者是它的**父**（T13）⇒ 父的 ack 就是这条工作项的行为，
  回执从此不会把"没人读"写成 `delivered`；
- **D**（插话在续跑后消失）：插话 = 用户 → M 的一条工作项（T18）⇒ 真相在**板上**，
  续跑时重建的是"**还没 ack 的项**"，不需要重放事件流。

**落点三选（`schema.py` 是 FC-27 禁改区，这条决定要所有者点头）**：

| 选项 | 机制 | 代价 |
|---|---|---|
| **甲（最贴原话）** | 给 `tasks` 加一列 `kind`（delegation / message / report / notice）⇒ **物理上真是一块板** | `schema.py` 是禁改区（`schema-migration` / `eval-criteria`）⇒ **要人写或人逐行走查 + 2 reviewer** |
| **乙（建议先走这条）** | 不动 schema：板 = **追加式账本**（`handoffs.jsonl` 扩 kind）+ 每项一条状态行；`tasks` 仍只记实例。**语义上是一块板**（一个"待办视图"把两处合成一个读法） | 物理上两块，读的人要按一个视图读（视图由 `conductor.state` 出，不进 schema） |
| **丙** | 给动作表加一个通用 `ack` 动作（`specs/*.py`）⇒ 留言变成普通 task 行 | `specs/` 也是禁改区，且会给每个角色加一条动作（权限面变动） |

**判据（先立三条，任何落点都要过）**：① 每一个非终态工作项都能被读到（"还挂着什么"是一次查询）；
② 终态工作项必有"谁在哪一步 ack/completed 的"那一行（缺 ⇒ 红）；③ 负控：
把一条工作项的 ack 行删掉 ⇒ 它必须重新变成"未完成"（不许靠内存态）。

## §3 信封的字段（草案；逐字对齐既有字段见 §9）

```jsonc
{
  "id": "0007",              // 四位号，追加式分配（既有 next_id：锁内取最大+1）
  "kind": "message",          // delegation | message | report | notice（+既有 revision）
  "created_at": "2026-10-08T16:20:11+08:00",

  // ---- 两端（谁、哪条边）—— 前两格是既有键，名字与类型都不许动（§9.1 ⓐ）
  "sender": "B",              // 既有键：8 角色 + M 之一
  "to":     "A",              // 既有键：8 角色 + M + ALL 之一（ALL 只允许出现在 notice）
  "from_task_id": "t-0042",   // 新增：发件**实例**（同一角色多实例时靠它分辨）
  "to_task_id":   "t-0031",   // 新增：收件**实例**；空 = 只到角色层
  "edge": {"parent_task_id": "t-0031", "child_task_id": "t-0042"},   // 这条边是谁的边
  "edge_action": "ingest_local",   // 这条边上原本派的是什么活（便于人读）

  // ---- 内容（F2：全文不截断；信封另有摘要）
  "summary": "取回 Terras 那条失败：provider 429，不是没有",   // ≤ 一句话，进对方上下文
  "body": "……全文……",                                        // 落盘全文，不因上下文预算被删

  // ---- 硬事实（F3：受控取值 + 分类，进上下文）
  "facts": [
    {"about": "search",  "key": "terras-zeta-graphs", "result": "rate_limited",
     "detail": "HTTP 429, retry-after=30", "at": "2026-10-08T16:19:02+08:00"},
    {"about": "fetch",   "key": "lit:0008",            "result": "fulltext_unavailable"}
  ],

  // ---- 引用与留痕
  "refs": ["lit:0008", "stmt:0003"],      // 既有前缀词表（stmt/exp/lit/rel），逐条校验在册
  "reply_to": "0006",                      // 这条在回哪一条（可选，成对可查）
  "task_id": "t-0042", "sid": "t1s",       // 既有落点字段
  "note": "…这一行是怎么来的…"              // 既有字段（模型自撰 or 框架通报；实例备注也用它）
}
```

**四条设计决定与理由**

1. **实例号必须与角色分开**：角色是**预设**、实例才是**节点**（`draft/84` §9）—— 只写角色会让
   "谁在跟谁说话"在多实例下失真（`D#1` 与 `D#2` 的收件箱不是同一个）。但**落法改了**：
   既有 `sender`/`to` 是**角色字符串**且被 `valid_recipient`/`list_all` 依赖
   （`manuscripts.py:84-91`、`:504-506`）⇒ 实例号**新增两格**（`from_task_id`/`to_task_id`），
   **不动** `sender`/`to` 的名字与类型（§9.1 ⓐⓑ）。
2. **`edge` 是必填**（`message`/`report`/`notice` 都填）：它把"这是一条**边上的**消息"
   写成数据，而不是靠"from/to 恰好是父子"来推断。查询"这条边上发生过什么"于是是一次过滤。
3. **`facts` 是数组而不是嵌进 body**：硬事实必须**机器可读 + 可分类**（F3），
   嵌进自由文本就等于没有。`result` 的取值来自**受控词表**（见 §4）。
4. **`summary` 与 `body` 分离**：进上下文的是 `summary`（+ `facts`），全文留盘（F2）。
   这一条同时回答了"长跑批上下文预算"与"结果不许丢"这对矛盾。

## §4 硬事实的受控词表（T6 分类报的落点）

| about | result 取值 | 含义（谁判） |
|---|---|---|
| `search` | `hit` / `no_results` / **`filtered_out`** / **`partial`** / `provider_unavailable` / `rate_limited` / `timeout` / `auth_failed` / `not_wired` / `query_not_applicable` / `unknown` | 一次检索尝试的终局 |
| `fetch` | `fulltext_ok` / `fulltext_unavailable` / `paywalled` / `not_found` / `bypass_failed` / `unknown` | 一次取回全文的终局 |
| `read` | `quote_verified` / `quote_mismatch` / `quote_unavailable` / `unknown` | 与"逐字比对"对齐（注意：`False` 今天被用来表达"取不回"，这一处要在本设计里一并纠正） |
| `run` | `ran_ok` / `compile_error` / `import_unavailable` / `timeout` / `crashed` / `proved` / `refuted_claim` / `unknown` | 一次实验/形式化的终局 |
| `tool` | `called_ok` / `refused` / `not_wired` / `crashed` / `unknown` | 一次工具调用为什么没成 |

**`search` 那一行的四档是 A 的只读审计（2026-10-08）逼出来的**，它今天在同一条链上被折平：

| 档 | 今天落成什么 | 证据 |
|---|---|---|
| 上游真 0 条 | `outcome="no_results"`（`done=True`） | `run_once.py:225-230` |
| **上游有、被我们的精筛滤光** | **同一个 `no_results`**（`providers.py:1310` 只在"每一路都抛错"时才抛；区分它的 `last_topicality` 只活在进程内存，A 不落盘） | `providers.py:1306-1321` |
| **部分通道失败但拿到了候选** | **折成 `ok`**：`new_ids` 非空即成功，`search_errors` 只进 `events.info`，`last_error` 留空 | `run_once.py:182-186`（真机 7 例：`p6f` r-0001..r-0004、`p6g` r-0001..r-0003，429 全被读成 `ok`） |
| 网络/TLS/超时（发出去失败） | 本来就有档：`search_failed` + `last_error` + 退避租约 ⇒ `gave_up` | `run_once.py:206-224`、`core.py:195-203` |

⇒ 于是"换一个查询串就能变成 `ok` 的请求"会被**永久判死**（`done=True` ⇒ 不重试），
而"429 下只拿到半个结果集"在两处台账里都读不出来。**这两处必须分开**，
否则 F3（硬事实分类）在格式上就写着两个不同的事实、在盘上却是同一个字。

**两条纪律**：① 每个 `result` 都必须能落到**具体那一次尝试**（带 `key` 与 `at`），
不许汇总成一个布尔；② **`unknown` 是合法值且必须允许**（三态），不许为了"好看"填一个具体值。

### 4.1 "类别要进交流留痕"落成什么（所有者 T6 的后半句）

T6 的原话是「类别要进交流留痕（**不只进表**）」。落法：**谁做完谁把类别挂在自己的那条消息上**，
不需要新动作、也不需要模型自由发挥（类别由代码从结果里读出来，模型只负责说人话）：

| 谁 | 什么时候 | 挂在哪条消息 | `facts` 里写什么 |
|---|---|---|---|
| A（检索/取回） | 每次 `run_once` / `search_literature` / 取全文之后 | 交给 M 或下游的 `report`（没有下游时由框架的 `notice` 带上） | `{"about":"search","key":<规范查询串>,"result":<词表>}`；取全文另挂 `{"about":"fetch","key":"lit:NNNN",...}` |
| B（登记/命中校验） | 登记一条文献行之后 | 给派活方的 `report` | `{"about":"read","key":"lit:NNNN","result":"quote_verified"/…}`（**空串必须能被读成"还没校验"**，见 D74） |
| E（实验/形式化） | 每次 `run_experiment` 之后 | 给派活方的 `report` | `{"about":"run","key":"exp:NNNN","result":"ran_ok"/"compile_error"/…}` |
| 任何角色的工具被拒/没接线 | 那一刻 | 该步的读数 + 收尾 `report`/`notice` | `{"about":"tool","key":"<工具名>","result":"refused"/"not_wired"}` |
| **框架** | 子行落终态时 | `notice`（§2 的第四类） | 只挂"结算事实"（`state`/`reason`），**不替模型写类别** |

三条边界：① **表与交流是两份读数，不是二选一** —— 表给机器复算，交流给人（和父）读；
② **不许把类别写进 `summary` 的自由文本里**（那就等于没有分类，F3 的整个意义在此）；
③ 框架生成的 `notice` **不许**替模型填 `facts` 的类别项（与"不代写模型结论"同一条纪律）。

## §5 投递：既有事实（**推翻 v1 的假设**）与必修项

**v1 我写的是"今天运行中的 agent 收不到新消息"——这是错的**（我引了 `draft/37` §128 的一句旧注释，
而代码里已经改了）。只读审计逐行核实后的**事实**如下（`agent_loop.py` = AL；
**行号以审计当时的基线为准**，D81 正在改这个文件，复核请按符号名定位）。

| 通道 | 读取时机 | 一趟内能否收到新消息 | 证据 |
|---|---|---|---|
| **留言**（`agent_message`） | ① `run()` 开头 `inbox_digest`；② **每个成功步之后** `_hear()` | **能**（下一步生效） | AL:1510（开头）、AL:1810（步尾）、AL:1868（拼进 transcript） |
| **插话**（`agent_interjection`） | **每步开头**一段【插话】 | **能**（下一步生效） | AL:1628-1637 |
| **用户回答** | **只在 `run()` 开头读一次** | **不能**（要等下一次 `run()`/`--resume`） | AL:1512（开头）、AL:2020-2028（每步只找 `STOP_TOKEN`，不交给模型） |
| 手稿行 / 检索请求 | 不推送 | 靠模型**主动调工具** / A 的 `run_once` 认领 | `manuscripts.read`；`agent_a/core.py:173-208` |

**所以"边上的实时传话"在留言这条通道上**已经有**一个步边界的口**（AL:1628/1810）。
但审计同时挖出四件**会静默丢**的事，格式设计必须先把它们修掉，否则新格式只会放大同一个病：

| # | 形态 | 机制 | 后果 | 盘上看得出来吗 |

| **B** | **默认部署下，发给"只跑确定性动作的角色"的留言没有读者** | 只有跑 `AgentLoop` 的角色才有步循环与收件箱；`host.DEFAULT_LLM_LOOPS = {}`，只有 `--drive` / `--subagents` 才把角色动作接进 LLM 循环（`host.py:432`、`cli.py:1499/1503-1521`）；`A.run_once` 是无参确定性动作（`agent_a/run_once.py:10`） | 发给 A 的留言**没有任何进程会读**——不是"晚点看到" | 看不出（无 `agent_inbox` 消费痕迹） |
| **C** | **批内被召唤的角色写不出 handoff** | `LlmBackend.call` 造嵌套循环时**没传 secretary**（AL:2797-2800），而 handoff 要秘书（AL:2592-2599）；`_inbound_hook`/`handoffs_digest` 在批内是 no-op（AL:1392-1398、2542） | 那一趟的交接**在盘上没有那一行** | 只有那一步 result 里的 `handoff: 未写成` |
| **D** | **插话在续跑后消失** | 插话 `+=` 进 transcript 并标 seen（AL:1633-1634），但它**不是 `agent_step` 事件**；`resume_transcript` 只重放 `agent_step`（AL:3045-3061） | 续跑后模型看不到它，也不会再被念（seen 已记） | 只有 `agent_interjection_seen`，没有"它当时说了什么" |

另外三条与"消费"直接相关（都会让一条请求**永远没人做**而盘上看着正常）：

- **被拒的消费会永久烧掉认领键**（**已修**，`draft/83` D80）：`seen` 取自**全部** `tasks` 行的
  `input_key`（含被拒行），而 `_refuse` 也写 `input_key` ⇒ 一次策略拒绝（墙钟 / 预算 / 总量 /
  并发）之后，`consume:<rid>` 这个键永久留在 `seen` 里，那条 `done=false` 的检索请求
  **跨趟也**不会再被自动认领。修法：`seen` 只认**真的被受理过**的行
  （`_occupies_fanout_slot`：只有走完写 `running` 行那一步的召唤才带 `_ADMITTED_MARK`）。
- **`consume:` 的 rid 与真正处理的 rid 可能不是同一条**（`summon("A","run_once",{})` 不传 rid，
  而 `run_once()` 按优先级自己领）⇒ 幂等键说的是"唤起过"，不是"处理过"；
- **`mark_delivered` 早于任何模型调用**（AL:1510→1530-1531）：这一趟若在首次 `ask_step` 之前就死
  （`not_wired`、步 0 撞停机开关、预算已尽），消息的"新"标记永久丢失（消息还在，但不再标新、
  且会被挤进 8 条窗口）。

⇒ **格式设计的三条硬约束（写进 §2/§3）**：
① **投递不许有"窗口截断 + 全量标记"**：进提示词的是**有界摘要**，但"哪些还没被真正读过"必须
   用**独立的读位**（读一条标一条，而不是渲染一批标一批）；
② **每个信封必须能落在"有读者的通道"上**：收件人是确定性动作角色时，要么它自己会读（今天不会），
   要么消息由**它的父**在步边界转达（这也是"父只对子负责"在通信上的必然形态）；
③ **不许用"消息已写"冒充"消息已读"**：三态（写入 / 读到 / 消费）分开，缺哪条写哪条（§3 已定）。

## §6 递归交链（T1 的格式）

**请求**（父 → 每个直接子级，走 `steer`/`queue`）：

```jsonc
{"kind": "message", "summary": "请交出你这条支链",
 "chain_request": {"depth_limit": 5, "include_settled": true, "want": ["state","open_edges","reports"]}}
```

**应答**（子 → 父，一条 `report`—类消息，body 里放结构化支链）：

```jsonc
{"kind": "report", "summary": "支链：3 个直接子级（2 已结算未交差）",
 "chain": {
   "node": {"task_id": "t-0042", "role": "B", "action": "ingest_local",
            "state": "running", "open_edges": 1, "started_at": "…"},
   "children": [ {"node": {...}, "children": [ ... ], "chain_complete": true} ],
   "unresolved": [ {"task_id": "t-0051", "reason": "no_reply", "asked_at": "…"} ],
   "chain_complete": false
 }}
```

三条纪律：① **缺的支链如实标 `unresolved`**（`no_reply` / `child_says_it_has_children_but_cannot` / `refused_by_policy`），
**不许猜**；② `chain_complete=false` 必须能被父看到（"我给你的不是全树"）；③ 这条请求本身
**占一条边上的消息**，不新增节点、不占名额（F1）。

## §7 消边（T2）与交流的关系

所有者逐字：「用消边法，且消边规定**只有子代理全停或为空（即运行中的子代理为 0）且自身停了
才能消边，这个是整体设计，不局限于控制停止」。」

落成一条可复算的谓词（**全局设计**，结算/交差/释放/读数共用）：

```text
can_release_edge(node) = (在跑的子代理数(node) == 0) and (node 自身已停)
其中 在跑 = 子行里 status ∈ {pending, running}
```

它与交流的接口有三条：

1. **消边不是"发一条消息"**：它是边生命周期的最后一步；所以 `message` 类交流**不许**
   被当作消边的凭据（"我给他发过消息"不等于"这一支收干净了"）；
2. **`report` 不是消边的必要条件**（DSH 的教训：等一个可能永远不来的模型结论会卡死）——
   终态 + `notice` 就够，`report` 有就更好（这正是 §2 把 `notice` 独立出来的原因）；
3. **`chain` 请求要能问到"还没有消边的边"**，否则"谁还挂着"这个问题读不出来。

## §11 身份与"管理工具面"：跟 DSH 学什么（编号 + 备注角色）

所有者 2026-10-08：「看看 DSH 怎么实现分清不同子代理的（似乎是编号），我们就用**编号加备注角色**。
并学习 DSH 的 `list_agents` 工具及其它管理工具」。本节是实读 DSH 后的对照与我们的方案。

### 11.1 DSH 的区分机制：**durable id + label + parent + depth**（它没有"角色"）

| 面 | DSH 的做法（逐字） | 出处 |
|---|---|---|
| 工具面 | `send_message(agent_id, message)` / `interrupt_agent(agent_id)` / `list_agents(scope?)` | `dsh-tool-subagent-control/README.zh.md:111` |
| 列表行格式 | **`<id> [<status>] — <label>`**；`descendants` 在 label 破折号**之前**插 ` parent=<id> depth=<n>`（pre-order）；读不到的候选项渲染成 `<id> [diagnostic: <reason>]`；一次性子级**有意排除**；空则 `(no subagents)` | `:153` |
| 状态三档 | `running`（driver 活跃）/ `idle`（驻留、轮次之间）/ `ready`（仅存于存储，**可恢复**而非终态） | `:153` |
| 投递回执 | 接受 ⇒ `message delivered to agent <agent_id>`，规范输出带 `messageId`；**目标的回复绝不会通过本次调用返回**（回复是另一条显式指定地址的 `send_message`） | `:139`、`:170` |
| 打断回执 | 接受 ⇒ `interrupt requested for agent <agent_id>`；self / sibling / 陈旧 / 非 ancestor **成为指明原因的出错结果**；**目标不存在或已结算仍渲染接受行**（= 它没有"到底停没停"的回执） | `:125` |
| 派活回执 | 可继续后台**恰为** `started subagent <childId>`；一次性后台 `started background subagent job <id>` | `dsh-tool-subagent/README.zh.md:194` |
| 交差通道 | 运行时生成的**结算通知**（`… finished and will do no further work …` + `Its closing message:` 或 `It left no closing message.`） | `dsh-subagent/README.zh.md:133` |
| 前台语义 | 只回**子代理最终文本**；其它结局变 `Error: <终止原因>` + 诊断 + 部分文本；**子代理的中间步骤不进父级** | `dsh-tool-subagent/README.zh.md:180` |
| 自己承认的边界 | 列表是**快照不是投递承诺**（与发布/dispose/消息竞态）；**没有分页或删除**（子会话还在就一直出现）；列表成本随子级数量线性增长 | `dsh-tool-subagent-control/README.zh.md:172-173` |

⇒ **DSH 的"区分"其实是四样东西的组合**：`id`（唯一、durable）+ `label`（人读）+ `parent`（谁的孩子）
+ `depth`（第几层）。它没有"角色/岗位"这一维 —— 所以我们不能照抄，只能**在此基础上加一维**。

### 11.2 我们的方案：**编号 + 备注角色**（`<task_id> · <role>（<备注>）`）

- **编号**：沿用我们已有的实例号 `t-NNNN`（一行 `tasks` = 一个实例，见 `draft/84` §9 的"角色是预设、实例才是节点"）。
  它天然满足 DSH 的三条：唯一、持久（append-only 台账）、跨"回合"稳定（同一行就是同一实例）。
- **角色**：我们的**预设**（A–H/V/M），DSH 没有这一维；
- **备注**：派活时由父给一个短标签（DSH 的 `label` 对应物），用于人读与模型读
  （例如 `D#3（族证据）`、`A#2（Kuchment 那一条）`）。**备注不是身份**：它可变、可空，
  身份永远是编号；备注只解决"同一角色起了多个实例时人怎么认"。
- **模型可见的三种文案**（对齐 DSH 的措辞风格，但带上角色与备注）：
  - 派活成功：`已派出 t-0042 · B（族证据）——它将独立跑，结果以交差形式回来`
  - 交差/结算：`t-0042 · B（族证据）已结算：<摘要>`，无结论时逐字 `（它没有留下结论）`
  - 传话前缀：`来自 t-0042 · B（族证据）的消息：`（对应 DSH 的 `Agent <sender-id> sent a message:`）
- **状态词表**（**只写我们真有的三态**，不许照抄 DSH 的 `ready`）：`running`（步循环活跃）/
  `idle`（实例还在、轮次之间）/**`settled`**（终态：done/failed/cancelled）。
  今天**没有"可冷恢复的实例"**（再派活是**新实例**）⇒ 不设 `ready` 档，
  以后真做了"同一实例再唤醒"再补（**宁可少一档，也不写一个做不到的状态**）。

### 11.3 我们的管理工具面（每条都注明"抄谁 / 加什么 / 为什么不抄全"）

| 工具 | 语义 | 相对 DSH |
|---|---|---|
| `agents.list(scope=children\|descendants, depth_limit?)` | 行格式抄 DSH：`<task_id> · <role>（备注） [<status>] — <摘要> parent=<id> depth=<n>`；读不到的候选项**占位**并给 reason（三态） | **加两样**：① 我们的 `descendants` 按 T1 裁定是**递归交出**（父问子、子问孙），不是本地扫描；② 带 `depth_limit` 与**逐节点截断**（DSH 自己承认"没有分页，成本线性增长"） |
| `message.send(to=<task_id>, summary, body, facts[])` | 边上的消息（`draft/85` §2-§4 的信封）；回 `messageId` + **三态回执**（写入/读到/消费），**绝不回结果** | 抄 DSH 的"只回受理"；**加**：回执（DSH 明确没有"已读/未消费"位） |
| `interrupt(task_id)` | **只停该实例当前回合**，后代继续跑、排队消息留着（与 DSH 一致） | 抄 DSH 的半径；**加**：回执（"停到没停到"要看得到，DSH 只回 accepted） |
| `stop.release(task_id)` | 拆一棵子树：**先关入口 → 信号先到 → 子先父后释放 → 消边最后**（我们的 T2 消边谓词） | **DSH 没有这个动词**（它只有 ACP 关闭/scope 销毁时才 drain）⇒ 自建 |
| `chain.report(depth_limit)` | 父叫子交出支链，递归拼（T1） | DSH 的 `list_agents(descendants)` 是**自己扫**；我们按所有者裁定改成**递归问** |
| `jobs.output(wait, timeout_ms)` / `jobs.kill(id)` | 一次性后台任务（`run_in_background` 那一档） | 抄 DSH（含"超时 resolve 不 reject、job 继续活着"这条三态纪律） |
| `agents.transcript(task_id)` | 看某个实例的完整会话（DSH：可继续子级的**详细输出来源**就是它的 transcript） | 抄；这也是 F2"全文不丢"的兜底出口 |

**不该抄的三条**：① 不设"可恢复实例（ready）"这一档（我们做不到就别写）；
② 不做 `list` 的"无上限全树"（DSH 自认成本线性增长，我们加 `depth_limit` + 截断）；
③ 不把"发送成功"当成"收到过"（DSH 的列表是快照不是投递承诺；我们把三态写死在信封上）。

### 11.4 与既有机制的接缝（落地时按这条走）

- 编号沿用 `tasks.task_id`（`t-NNNN`）与 `manuscripts` 的 4 位号；**不要新造编号器**
  （审计发现编号有**三套口径**：`manuscripts.next_id` 取最大+1、`send_message` 的 `msg_id`
  数事件条数+1、`read_messages` 的回退按**事件序号**造号 —— 前两套在 append-only 下恰好相等，
  第三套会给坏行一个可能撞号的替身；这一处要统一成"取最大+1"，坏行如实报，
  见 `draft/83` D79）。
- 备注的落点：**既有行的 `note` 字段**（`manuscripts.py:374`，模型自撰 / 框架派生，
  `draft/39` §6.4 的既有用法）—— 第一次由 `kind="delegation"` 那一行承载实例备注。
  **不许**写进 `tasks`（该表没有 `note` 字段，审计已确认）；也**不要**借用
  `tasks.input_key`（那是幂等键，`consume:<rid>` 就在那一栏，见 `draft/83` D80）。
- 列表/链应答里**只列直接子级**，孙辈由子级自己在应答里给（T1）。

### 11.5 细查回来后的逐行落地（DSH 的"身份"到底怎么实现的）

两路只读细查已回（DSH v0.1.5-rc.2，`@deepseek-ai/*` 只随包发布 `lib/`，`src/` 不存在；
凡引用 TS 源处均已用编译产物逐字替代并标注）。本节把 §11.1 的 README 口径压到代码面。

**① id 的生成、表示、稳定域**

| 事实 | 逐字 / 位置 |
|---|---|
| id **就是 child 的 session id**（同一个值），不是另发的短号 | `dsh-subagent/lib/index.js:1649` `const childId = spec.childId ?? brandString(randomUUID());`；一次性路径 `dsh-subagent-in-process-driver/lib/index.js:166` |
| 类型 = `SessionId`（branded string），取值 = `node:crypto` 的 UUID（36 字符 8-4-4-4-12），schema 只要求非空 | `dsh-session/lib/types/types.d.ts:5`、`dsh-subagent/lib/index.js:38` `const SESSION_ID_SCHEMA = z.string().min(1);` |
| **跨 Activation 稳定**（冷恢复复用同一个 id） | `types.d.ts:47` "stable across activations"；`dsh-subagent/lib/index.js:1870` `coldResume(parent, childId, …)` |
| 另有一套 `runId`（**每 Activation 新 UUID**），只进插件生命周期事件、**不参与寻址**、模型看不到 | `dsh-subagent/lib/index.js:327-331` `runId: SubagentRunId(randomUUID()), provider, id: childId` |

**② 模型看到的就是那串 UUID**（三处同一个值，没有人类可读短号）：`started subagent <id>`
（`dsh-tool-subagent/lib/index.js:486`/`:527-532`）、`Background subagent <childId> finished …`
（`dsh-subagent/lib/types/continuation-messages.js:57-58`，调用点 `index.js:1250`）、
`Agent <sender-id> sent a message:`（同文件 `:24`）。

**③ label = 派活工具的 `description` 参数，创建即冻结、不可改、与 persona 无关**

- 写入：`dsh-tool-subagent/lib/index.js:510` 与 `:529` 都是 `label: args.description`；
  语义见 `descriptor.d.ts:58-68`（"kept as the child's durable creation label so enumeration
  can identify the conversation"）与 `types.d.ts:29-30`。
- **不可改**：`dsh-subagent/lib/index.js:1425-1426` 的 `foldSubagentDescriptor` 用
  `events.find(...)` 取**第一条**为权威（折取第一条 ⇒ 后续追加不生效）。
- 渲染：`list-agents.js:118-120` `` `${entry.id} [${entry.status}]${at} — ${entry.label}` ``；
  `descendants` 才带 ` parent=<uuid> depth=<n>`（`:115-117`）。
- 可继续子级的 label 在 schema 里是 **required**（`list-agents.js:85`），**模型面无兜底**；
  空串兜底只存在于 UI（`dsh-client-ui-subagent/lib/client.js:279` `entry.label ?? entry.id`）。
- **persona 完全不进盘点面**：`persona` 是启动期配置（`dsh-tool-subagent/lib/index.js:264`、`:517`），
  只有可继续 descriptor 存一份供冷恢复（`descriptor.d.ts:75-76`）；`list_agents` 的投影只有
  `id/label/status/parent/depth`（`projection-types.d.ts:8-17`、`list-agents.js:80-89`）。
  在 `dsh-subagent/lib/index.js` 全文搜 `role|annotation|note|remark` 只命中一句注释（`:2732`）
  ⇒ **DSH 未核实到任何角色/备注机制**。

**④ 同一预设的多个实例：只靠 durable id 分辨**（label 并排展示，**不参与路由**）

- 路由/归属全按 id：`send_message` 只收 `agent_id`（`dsh-tool-subagent-control/lib/types/index.js:27-38`）；
  结算通知按 id；**重复 id 显式拒绝**（`dsh-subagent/lib/index.js:820` `… already exists`，码 `DUPLICATE_CHILD`）。
- `DUPLICATE_CHILD` 的第二种触发（编译产物逐字，源码 `continuation.js:147-155` 不随包发布）：
  `dsh-subagent/lib/index.js:1684-1690` —— **只有**调用方显式预留 `childId`
  **且** `persistence.stat(childId)` 已有持久化记录时才抛。
- `descendants` 额外用 `parent`+`depth`；`depth` 是"距根边数"（`list-children.d.ts:31-32`），**不是序号**。

**⑤ 血缘绑定与"不能换父"**

- 统一写入点 `dsh-subagent/lib/index.js:502-513`：`parentSession: parentHeader.id` / `isSeeded` /
  `origin:"subagent"` / `delegationDepth: childDepth`，落 header 于 `dsh-session/lib/index.js:1398`；
  字段定义 `types.d.ts:70-87`、`:104-109`。
- `delegationDepth` **单调取大**：`dsh-subagent/lib/index.js:147`
  `Math.max(agent.session.header.delegationDepth ?? 0, runtime ?? 0)`。
- **父只在创建时写、之后不能换**；resume 时的 `parentAgent` 是**运行时所有权**而非血缘
  （`dsh-agent/lib/types/index.d.ts:113-114`、`:315-317`），每次授权都要比对记录的父
  （`dsh-subagent/lib/index.js:966-968`，冷恢复时不符即 `UNAUTHORIZED`
  `subagent "<childId>" belongs to another parent session`）。

**⑥ 磁盘落点：目录名 = 编码后的 session id**

- `dsh-session-persistence-jsonl/lib/index.js:913-914`
  `sessionDir = join(projectDir(root,cwd), encodeSegment(id))`；`:852-862` 的 `encodeSegment`
  把安全字符原样、其余 `~XXXX` ⇒ UUID 目录名原样。
- `subagent/descriptor` **不含 id**（`descriptor.d.ts:46-79` 只有 version/mode/provider/label/
  路线/persona/toolFilter）；**父侧**的 `subagent/catalog` 才存 `childId/childCreatedAt`
  （`index.js:1509-1522`，schema `:1433`/`:1440`）。⇒ **要带角色就两处都写**。

**⑦ 没有"序号"字段；稳定 pre-order 靠双键排序**

- `dsh-subagent/lib/index.js:2209-2211` 逐字
  `/** Compare siblings by durable creation time, then id. */ function compareCorpusRecords(a,b){ return a.header.createdAt - b.header.createdAt || a.header.id.localeCompare(b.header.id); }`
- children 列表同源排序（`:2073`），DFS 组装（`:2186`、`:2188-2192` 入栈 reverse、`:2199-2205` depth+1）。

⇒ **三字段必须我们自建**：`role`（**枚举**，DSH 只有不可枚举的自由文本 label）、
`note`（人读备注）、`ordinal`（**显示层派生物**）。三条硬约束：
⒜ **ordinal 不能替代 id** —— 否则撞 `DUPLICATE_CHILD`、丢跨激活稳定性；
⒝ **ordinal 必须与 `createdAt → id` 同排序源** —— 否则 pre-order 会漂移；
⒞ `role` 要同时写进**子的 descriptor**与**父的 catalog 事件**（后者现仅有
`childId/childCreatedAt/mode/label`，是**唯一需扩的模式**），并出现在**结算通知**与
**`list_agents` 渲染**里（现只有 `id` / `id — label`）。

**读输出的等待语义（这条比工具存在更重要）**：`waitTimeoutMs` 默认 **30000**、
`maxWaitTimeoutMs` 默认 **600000**（`tool-jobs/lib/index.js:22-23`、`:168-169`），
`wait` 取 `Math.min(args.timeout_ms ?? waitDefault, waitCap)`（`:273`）；**超时是 resolve 不是 reject**
（`jobs-local/lib/index.js:237-243`，随后照常返回快照，渲染末尾 `[status: running]`，
描述逐字 "A timed-out wait returns [status: running] and leaves the job alive."）。
真正 reject 只有"调用方 abort"与"未知/他人的 job"。JobStatus 五态
`running|stopping|completed|killed|failed`（`dsh-jobs/lib/types/types.d.ts:14`）。

**结算通知是唯一"框架自动交差"**：`notifySettlement`（`dsh-subagent/lib/index.js:1244-1259`）
仅当 `activation.announced` 时投给**持久化直接父级**（父 idle ⇒ queue、忙 ⇒ steer、
父正在 teardown ⇒ inject）；文本逐字
`Background subagent <childId> finished and will do no further work unless you send it more.`
（或 `was stopped…` / `ran out of room…` / `declined the task.` / `failed before it finished.`），
随后 `Its closing message:` 或 `It left no closing message.`；
source `{kind:'subagent-settled', form:'notice', summary, senderSessionId: childId}`。

**生命周期事件不进模型历史**：`subagent/start|end`
（`dsh-subagent/lib/types/lifecycle.js:57-73`）经 `ctx.events.dispatch('emit',…)` 派发，
该文件内无任何 `session.append` ⇒ 不是会话日志事件；`subagent/descriptor` 另有明文
"log-only … never enters model history"（`descriptor.d.ts:32-33`）。
`subagent/catalog` 相反是**父会话**事件（`catalog.js:87 parent.append('subagent/catalog', …)`，
`version=0`、projection key `subagentCatalog`）；**它是否进模型历史未核实**（只有 descriptor
有那条声明）—— 落地前要自己确认，别照抄假设。

**`send_message` 的失败码表**（我们要照它设计"失败=未送达"的 receipt，别自造词）：
`UNAUTHORIZED`（sender 不是当前注册活体；非驻留子级向父发；冷恢复血缘不符）、
`PARENT_UNAVAILABLE`（父不 live；投递抛错也归到同码）、`NOT_RESUMABLE`、`ACTIVATION_CLOSING`、
`DRAINING`、`CONTINUATION_UNAVAILABLE`、`PERSISTENCE_UNAVAILABLE`、`CANCELLED`；
另有**浏览器面专用**码 `subagent/parent-unavailable|not-resumable|unauthorized|delivery-unavailable|…`
（`control-types.d.ts:116-145`）—— 这些**不进工具面**，我们只需要一套码。
`interrupt_agent` 的拒绝**发生在 residency 查询之前**（陈旧 / self / 非 ancestor，含 sibling），
而"目标不存在或已结算"则**静默 no-op 且仍回 accepted** —— 后一条是它的**回执缺口**，
正是我们 L4 要补的。

**另外两处可借的措辞**：① 后台任务完成通知逐字
`background job <id> (<kind>: <label>) finished [status: …]. Read its output with job_output.`
（`tool-jobs/lib/index.js:116-120`），空闲 owner 默认唤醒、`maxConsecutiveWakes=3`
（这条"叫醒而不是让模型轮询"值得抄）；② `subagent/end` 的 `stopReason` 五值
`completed|aborted|error|max-tokens|refusal`（`dsh-subagent/lib/types/types.d.ts:239-252`，
映射见 `lifecycle.js:143-168`）—— 比我们的 `done/failed/cancelled` 三态细，
但**它不进模型历史**（只进插件事件），所以我们在终态词表上保持三态、必要时再细分。

**挂载方式**：`dsh-base/cordis.patch.yml:343-347` 同时挂
`tool-subagent-control` 与 `tool-subagent-control/list-agents`；standard preset
（`dsh-agent-presets/presets/standard/agent.cordis.yml:169-187`）同两行，`tool-subagent` 带
`modelSelectionSettings: true` + `backgroundMode: continuable`。
**`send_message`/`interrupt_agent` 与 continuable 无关**：control 插件 apply 无条件注册
（`control/lib/index.js:21-92`），是委派的 `backgroundMode` 决定子级**能否被续**
（以及子级提示里是否出现返回指引）；一次性子级仍看得见 `send_message`，但发给父级会
`UNAUTHORIZED`（`dsh-subagent/lib/index.js:1742`）。

### 11.7 DSH 缺的、我们要补的（本节落地清单）

| # | 我们补什么 | 为什么 DSH 给不出 |
|---|---|---|
| L1 | `role` 维度（枚举、可重复、可枚举） | DSH 只有自由文本 `label`（3-5 词任务描述），既不唯一也不结构化；`persona` 不进任何盘点面 ⇒ 给不出"这个 child 是什么角色"的稳定可读标识 |
| L2 | `note`（人读备注，可空可变） | DSH 无对应字段；label 创建即冻 |
| L3 | `ordinal`（显示层派生物，与 `createdAt → id` 同排序源） | DSH 无序号字段，稳定顺序靠双键排序推出来 |
| L4 | 三态回执（写入 / 读到 / **消费**） | DSH 明确"列表是快照不是投递承诺"，只有 accepted ⓐ |
| L5 | `stop.release` 的消边谓词（子全停 + 自身停） | DSH **没有这个动词**，只有 ACP 关闭/scope 销毁时 drain |
| L6 | `chain.report` 的**递归交出** | DSH 的 `descendants` 是**自己扫**；我们按所有者 T1 裁定改成父问子、子问孙 |
| L7 | 列表的 `depth_limit` + 逐节点截断 | DSH 无分页无 cursor，README 自承 token 随子树线性增长 |
| L8 | 诊断行**不静默丢弃**且"暂时不可读"与"永久损坏"分开 | DSH 有两处静默省略：一次性子级整行丢弃、活子级 descriptor 尚未 append 时直接 `return`（`list-children.js:207-209`） |

**仍然不抄的四条（含细查新增）**：① 不设 `ready`（跨进程冷恢复）档 —— DSH 的冷恢复要
按 descriptor v3 全量重建 composition（provider/model/persona/toolFilter 快照 + 版本强制变更），
复杂度极高，我们没这个需求；② 不做一个工具面同时暴露两套句柄
（`subagentId` vs `jobId` vs `runId`，模型容易混用）；③ 不留死枚举
（`unsupported` 在 `control-types.d.ts:59-69` 自认永不产出）；④ 不把"发送成功"当"收到过"。

**唯一值得抄的元技巧**：把**授权归服务、工具零授权**写进注释与工具描述
（`dsh-tool-subagent-control/lib/index.js:96-99` 逐字 "The service authorizes the exact live
caller against the target's recorded lineage; the tool adds no authority of its own."）——
我们的同名工具同样只做适配层，权限判定集中在会话/血缘服务。
