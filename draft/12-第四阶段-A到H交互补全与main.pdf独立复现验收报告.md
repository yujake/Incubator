## 1. 第四阶段新增的东西

### 1.1 八个角色，而不是四个

第三阶段的 A/B/C/D 覆盖了"文献 → 知识 → 分析 → 问题"这条链，但**数学研究的产物不是"问题"**，
而是**证据、攻坚过程、稿件、以及对稿件的独立复核**。这四样东西性质完全不同，
每一个都对应一种"最自然也最危险的越界"：

| 角色 | 产出 | 它最容易犯的错 | 结构性对策（写进 `schema.validate`，不是文档告诫） |
|---|---|---|---|
| A 检索 | 文献 | 把"没搜到"说成"没有" | `outcome` 受控词表 `ok/no_results/search_failed/gave_up` |
| B 整理 | 概念、关系 + 引文 | 把模型编的引文当原文 | `quote_verified` 三态 + 逐字回验 |
| C 分析 | 报告 | 把"没枚举完"说成"没有更多" | `truncated` 显式字段 |
| D 研究 | 问题、结论 | 把"查不到"写成"研究发现" | L1/L2/L3 溯源 + `checked` 三态 |
| **E 实验** | **证据** | **把"算对了"说成"证明了"** | `evidence_kind` 受控词表 + **schema 拒绝计算类方法拿 `proof`** |
| **F 攻坚** | **过程** | 无限循环 / 把"卡住"说成"解决" | 三维预算 + `stalled` 必填 `best_partial` |
| **G 撰写** | **稿件** | 写出听起来合理但没有出处的断言 | `Document.validate` 拒绝无引用断言 |
| **H 审校** | **发现** | **审校者自己的判断没有证据** | `ReviewFinding.evidence` 必填非空 |

最后一行来自本项目**最贵的一课**：第三阶段评审中，评审方提出的一条"缺陷"是**错的**，
是实现方拿证据顶回来才纠正的（见 `11-…` §11）。如果审校记录可以只写"这里有问题"而不给依据，
审校就会变成**另一种幻觉来源**，而且因为它站在更高位置，**更难被纠正**。

### 1.2 三条把"过度声称"变成**写入期错误**的硬约束（FC-22）

这三条都不是注释，是 `validate()`，违反即拒绝落库：

1. **E**：`method != "formal"` 时 `evidence_kind == "proof"` → 抛。
   计算类方法（numeric/symbolic/exhaustive_search）只能拿到 `cross_check` 或 `heuristic`。
2. **F**：子目标 `status == "closed"` 但没有 `proof_experiment_ids` → 抛。
   有数值支持但无证明只能标 `supported_not_proved`——**这个状态是刻意单列的**。
3. **G**：`evidence_kind == "cross_check"` 但没有 `disclaimer` → 抛。
   而 `compose_claim` 会自动填 `doc_tools.CROSS_CHECK_DISCLAIMER`，H 精确匹配这个常量
   （若允许多种写法，审校就只能靠语义判断，而"靠语义判断"正是要避免的）。

**为什么必须机械执行**：论文 `main.pdf` 自己写着 "No numerical output is used as a proof"——
而这句话之所以要写，正是因为**数值对了几千个点就想说"证明了"是这一行最自然也最危险的动作**。
本轮 5 个复现脚本全部是数值的，全部只拿到 `cross_check`（见 §3.3）。

### 1.3 交互从 I1–I7 扩展到 I1–I12

第三阶段只有"一条链"：所有信息单向流过 `A → B → C → D`。第四阶段把它变成"一张网"，
每条新交互都给出**是什么 / 为什么 / 终止条件 / 负控**（`test/test1/DESIGN-INTERACTIONS.md`、`DESIGN-ROLES.md`）：

| 交互 | 内容 | 终止条件 | 负控 |
|---|---|---|---|
| I1 | C 作为**可调用服务**（D 点菜而不是吃套餐） | 查询有界，超预算 `truncated=True` | 服务面**只读**：三张知识表逐字节不变 |
| I2 | **矛盾闭环**：C 发现 → D 提问 → A 检索 → B 抽取 → C 复核 → 裁决 | 每矛盾 ≤2 轮、全局 ≤10；三轮仍 unresolved 标 `persistent` 停 | 真矛盾必须**在预算内终止**，不许无限循环 |
| I3 | 缺口直连 A（C 的 `gaps` 候选 = 检索靶子） | 单次 ≤3 条、主题去重 | `submit_requests=False` 时一条都不新增 |
| I4 | 定向重抽取（B 从"工位"变成"可访服务"） | 同一关系 ≤2 次 | **只改目标关系**、其它逐字节不变；**绝不重置 `processed`** |
| I5 | 结构重复概念检测（C 提出候选，**B 决定合并**） | —— | 假同义 → **拒绝并留理由** |
| I6 | 写入期一致性闸门（B 提交前问 C） | —— | `check_conflict` **签名不含 store**（避免事务内重入锁死） |
| I7 | 检索预算与优先级（A 的产能是稀缺资源） | 全局在途 ≤20，同级 FIFO | 超上限**拒绝新请求**，而不是无限排队 |
| I8 | G↔H 复审闭环 | `max_review_rounds`；超限标 `unresolved_review` 且**必须列出未解决项** | 注入无引用断言 → H 必须报 `unsupported_claim`+`error` |
| I9 | F↔E 子目标外包 | `max_persist_attempts` | 只有 `cross_check` 证据的子目标**不得** `closed` |
| I10 | D↔F 升级（问题难度分层） | F 的三维预算 | 证据不相关的问题**不得**被升级 |
| I11 | E→D 反例回流（反例是最强的信息） | 一反例一问题，按 `claim_key` 去重 | `inconclusive` 的实验**不得**触发回流 |
| I12 | G→verify 依赖闭合 | —— | `closed` 但指向不存在的 lit/exp → **必须**报 error |

### 1.4 中间逻辑的三处优化

1. **`ingest` 走向等价类**：同一份报告里的两条不同链条可能支持同一个研究点。
   按"共享 ≥1 个关系代号"或"概念集合 Jaccard ≥ 阈值"归为一类，**只研究一次**。
   （第三阶段先修过一处：4 条问题其实只对应 2 条不同链条，按 `(kind, 排序后 rel_ids)` 去重后 4→2。）
2. **证据就绪判据从"请求完成"升级为"新证据能否回答问题"**：
   第三阶段的判据是"请求 `done` 且文献都 `processed`"，但那只说明**消化完了**，
   不说明**这些新证据真的回答了那个问题**。现在增加一层：新落库的关系里是否有任何一条
   落在该问题的 `related_concept_ids` 上？没有 → 记 `evidence_arrived_but_irrelevant` 并**降优先级**。
3. **代号链是一等公民**：所有跨智能体引用都用代号链（`relation_ids`/`concept_ids`），
   自然语言只在给人看的报告里出现。这条来自第三阶段最刺痛的教训：D 曾因为"没接工具"
   而**静默拿到空证据**，却把"查不到"写成了一条听起来很合理的研究发现。

**一条硬规则：C 与 H 永远只读**（它们的全部工具 `side_effect ∈ {none, read}`，实测为 0 违规）。
这不是洁癖：一旦 C 能写，它就成为"绕过 B 的写入路径"，而 B 的引文逐字回验是**唯一**能自动
发现幻觉引文的地方——**C 写 = 绕过验证门**。H 同理：若审校者能直接改，
它就同时是"发现者"与"修正者"，于是**"发现问题"与"掩盖问题"在结构上无法区分**。

> ⚠️ **上面那个"0"是修好之后的数字，不是一开始就有的。** 实测中曾出现过
> **H 的工具面里带着 `table.update` / `fs.write` / `verify.run_experiment`**——
> 即"审校者手里有能改数据的刀"。详见 §8.1。
> 这说明"只读"**不能只靠注册时的善意**，必须是**结构性**的（现在由
> `ToolRegistry.for_role` 对 `READ_ONLY_ROLES` 强制剥离 + 7 条回归测试保证）。
> 这是本项目"**声称的约束 vs 可执行的约束**"差别的又一个实例。

## 2. 经验总结

完整清单在 `test/test2/LESSONS.md`（10 条最重要的经验 + 16 类已实测缺陷模式 +
数学研究相对软件工程的 9 处特殊性 + 60 条检查清单 + 22 条反面清单 +
**27 条带可判定判据的硬约束 FC-01…FC-27**）。这里只抄其中我认为最不该忘的五条：

1. **"没做"与"做了但没结果"必须可区分**——而且这个模式在项目里出现了**四次**
   （引文三态 True/False/None、OCR 无后端 vs 空文本、D 的 L1/L2 溯源、C 的预算截断）。
   第四次最惨：D 因为工具没接线而拿到空证据，却把"查不到"写成了研究发现。
2. **验证门 + 负控，缺一不可**。只有正向信号时，"有"与"没有"一样容易通过测试。
   本轮每一个交互、每一个复现脚本都配了负控。
3. **静默失败/静默覆盖比崩溃更危险**。崩溃会被看到，静默失败会**产出一张看起来全绿的表**。
   本轮实测到的静默失败至少有：`claim_key` 判重键选错、`concept_pair_key` vs
   `concept_group_key` 字段名失配（使 `detect_contradictions` 恒返回 `[]`）、
   `Tx.mark_dirty` 文档里有实现里没有（就地改 `tx.rows()` 会静默丢数据）、
   以及本报告 §4.3 里我自己踩的"弱断言给出假绿灯"。
4. **闸门必须在真实数据上量过假阳性率才能上**。
   实测：25 条真实论文关系上，旧的"字面矛盾"判据报出 **6 条 `suspect`（24%）**，
   **没有一条是真矛盾**。24% 的报警率意味着 `suspect` 这个标记**不再指示任何东西**
   ——而"假报警比不校验更糟，因为它会训练人忽略告警"。修正后判据分 `strong`/`weak` 两档，
   **只有 `strong` 允许驱动状态**。
5. **并发与预算是"两道闸"**：并发上限管瞬时（`max_parallel_subgoals`），
   总量上限管生命周期（`max_rounds`）。只有总量没有并发 ⇒ 一轮可以无限扇出；
   只有并发没有总量 ⇒ 扇出可以无限持续。F 的三维预算四类键缺一不可。

## 3. 验收测试：独立复现 `main.pdf`

### 3.1 被复现的论文

`D:\Incubator\test\main.pdf`——Jiaqi Yu, *Cospectral periodic graphs: the spectrum does not
determine the graph*, 2026-09-21, 8 页（未发表）。两条边都在 `V_K = {x ∈ Z^m : Σxᵢ ∈ {0,1}}`
上：`K(m)` 的边是 `{x, x±eᵢ}`；`S̃_m` 是 `Ã_{m−1}` 型仿射 Weyl 群的**腔图**，
即 `Q^∨ ⋊ S_m` 以 `{s₀,…,s_{m−1}}` 为生成元的 Cayley 图。两者都 `m`-正则、无限、顶点传递、
周期秩 `m−1`。

### 3.2 框架是怎么"独立推导"的

**这一点必须说清楚，否则验收就是假的**：框架不是自己"读懂"了论文。
`paper_seed.SeedExtractor` 由**人**提供"抽取哪些概念/关系"的选择，
但**抽取结果的正确性完全由框架验证**：25 条引文逐字回引文（`verified=25 / failed=0 / unknown=0`），
外加 3 条引文篡改负控（必须被拒）。这是 `10-…` §9 就定下的诚实边界，本轮没有偷偷放宽。

然后框架自动走完：
`检索登记 → 抽取 → 分析 → 提问 → 矛盾闭环 → 多轮攻坚 → 数值实验 → 撰写复现报告 → 独立审校 → 存储一致性校验`。

### 3.3 五个独立复现脚本

E 在**独立子进程**里执行它们（脚本是"不完全信任的代码"：可能死循环、可能 `sys.exit`），
每个脚本在 stdout 打印一行约定格式的结构化结论 `REPRO_RESULT: {json}`：

| 脚本 | 复现的内容 | 结果 |
|---|---|---|
| `exp1_k_spectrum.py` | `Spec K(m) = [−m, m]`（双通道 + 显式代数零点 + 填隙判据） | `supports` / `cross_check` |
| `exp2_girths.py` | `girth K(m)=6`；`girth S̃_m`= 6（m=3）/ 4（m≥4） | `supports` / `cross_check` |
| `exp3_chamber_spectrum.py` | `Spec S̃_m` 的区间填充性（**引文结论的数值旁证**；m=6 是公开问题） | `supports` / `cross_check` |
| `exp4_size_regularity.py` | `\|V_K/Λ\| = 2m^{m−1}`、`m`-正则性、cell 数据、Remark 3.5 | `supports` / `cross_check` |
| `exp5_noniso.py` | m ∈ {4,5} 的同度、同周期秩、**不同构**（靠围长） | `supports` / `cross_check` |

**关键纪律：脚本自报的 `evidence_kind` 一律被降级。**
`run_experiment` 的推导规则是"脚本只能报告它**观察到了什么**，证据等级由框架按 `method` 推导"；
脚本若自称 `proof`，E 会降到 `cross_check` **并把"脚本声称过 proof、已被拒绝"记进 notes**。
理由：**让被判定的对象自己当判官，等于没有判官**。

### 3.4 结论分类：33 条论文结论，我们只能独立验证 21 条

| 类别 | 条数 | 含义 |
|---|---|---|
| `computable` | 21 | 我们能独立数值验证 |
| `quoted` | 5 | 论文自己就是引用别人的（如 `Spec S̃_m`、Floquet 分解） |
| `proof-only` | 3 | 纯证明，数值无法验证（只做反例搜索） |
| `open` | 4 | 论文自己留的公开问题（如 m ≥ 6 的情形） |

**报告口径（已写进脚本，不许含糊）**：
"在采样范围内未发现反例；`Spec S̃_m = [−m,m]`（3 ≤ m ≤ 5）仍仅为引文结论 `[6, Thm. 6.5]`，
不能由本计算推出。"

### 4.1 独立复核的具体收获

**(a) 复现了 Theorem 1.5 中"能被复现的那一半"。** 对 m = 4,5：
两图同为 `m`-正则（同度），`girth K(m) = 6` 而 `girth S̃_m = 4`。
**同构保持围长**，所以两图**不同构**——这一步完全初等，不依赖任何引文。
余谱那一半依赖 §3.4 的引文缺口。

**(b) 定位并修复了一个真实的静默缺陷。** `repro_common.cycles_through_identity`
**对任何输入都返回 `(0, None)`**（"这个长度上不存在经过恒等的圈"），
而 `ball_girth` 对 m=4,r=2 **明确给出一个 4-圈**（含恒等元）。
根因是基例差一：长度 `L` 的圈经过恒等元时有 `L−1` 个中间顶点，
但代码等的是 `len(path) == length`（即 `L+1` 圈），基例**永不可达**。
改成 `length - 1` 后，对 6 组已知真值的用例全部正确。
这类缺陷的危险在于它**不报错**：它只是把一个"存在"报成"不存在"，
而下游很可能把这个空结果当成一条研究发现（正是 §2 里"没做 ≠ 做了但没结果"的又一次现形）。

**(c) 自查出错三次，全部保留在代码注释里。** 见 §4.3。

### 4.2 一个"看起来像反例"的教训

独立复核第一次跑 `Spec S̃_3` 时，采样最大特征值是 **6.0 = 2m**，正好是 `m` 的两倍，
看上去像"论文引用的定理是错的"。实际是**我自己的重复计数**：
Λ-商图与腔图 cell 的边表都是**每条无向边出现两次**（从两个端点各生成一次），
于是 `A[i,j] += χ(v); A[j,i] += conj(χ(v))` 把每个元素加了两遍，
矩阵仍然是 Hermitian、cell 仍然 `m`-正则、**只有特征值整体乘 2**。

**修正还失败了第一次**：我先改成"把无向边规范化到有序对 `(min,max)` 再累加"，
结果两个方向映射到**同一个键**，仍然被加两遍；而当时的守卫
`len(entry) == len(cell)//2` **依然通过**——因为键的个数是对的，只是值翻倍了。
这是一条**弱断言给出假绿灯**（LESSONS 的模式 P11）的教科书实例。
正确修法是先用 `set` **去重**无向边，并把守卫换成**强判据**
（`A` 的每行 `|·|` 之和不得超过度数 `m`——正是重复计数会破坏的量）。

### 4.3 本轮负面控制自己出的三个错（都保留在代码里）

| 错法 | 后果 | 教训 |
|---|---|---|
| 负控的期望值跟着注入的 bug 变（`want = 2m−1 if bug else m`） | 负控**通过了**——而一个"不可能失败"的负控比没有负控更糟，因为它被当成"门确实有效"的证据 | 断言必须始终用**论文的值**，与注入的 bug 无关 |
| 读错返回键（`eigenvalues` 而实际是 `values`） | 拿到 `None`，判据退化成恒真，"路径始终在区间内"这条检查**永远不会红** | 判据里出现 `if x is None: ok=True` 就要警觉；本轮改成"没返回就直接判红" |
| `[[1]*m] + 单位阵行` 的行秩与 1 比较 | 断言本身是假的（那矩阵秩为 `m`），正常跑就报红 | **断言写错**与**数学错**要分清；先把断言本身验一遍 |

另有一处：我为 `|B₃|`（m=6）先写了一个**猜的**期望值 92，
用独立实现算出真值 **84** 后改掉。**猜出来的期望值就是伪造的证据**，所以先算再用。

> §8 的读者是"要照着修/照着防"的人。

### 5.1 判重键选错：同一批实验被完整跑了两遍

`run_acceptance.py` 的 P5 本意是"**复用** P4 的 F 已经跑过的实验，不重跑"，
但它的查重键是 `claim_key`。而 F 是按**子目标**命名（`reproduce:main.pdf#sg1`），
P5 按**论文命题**命名（`SpecK(m)=[-m,m]`）——两者永远匹配不上。实测后果：

- `experiments` 表 **10 行、5 个脚本**，每个脚本恰好两行；
- P4 花 **247s**、P5 又花 **267s** 做同一件事；
- 而 P5 自己的判据 `登记了 10/5 条实验` 于是**必然报红**。

**修法**：查重键改成 `code_path`（**脚本**才是实验的身份），
并把判据从"总行数 == 5"改成"**每个脚本恰好一行**"——后者才同时防住
"重复登记"（行数偏多）与"漏跑"（行数偏少）两种错误，而前者只数总数，两种都会放过。

这条本身值得记下来：**判重键选错是一种静默失败**——它不抛异常，
只是把成本翻倍、把证据表弄脏，并让一个本该通过的判据以"数量不对"的面目失败。

### 5.2 其余在本轮修掉的（含前一阶段遗留）

- **P7 的落库级负控**：`h` 在构造之前就被使用（`NameError`）；
  且原实现以为 `_atomic_write` 能绕过校验，实际**校验就在 `_atomic_write` 里面**。
  修法是先用普通 `json.dump` 直接落盘注入坏数据，再让 H 去发现它——
  负控的完整形态是"注入 → 观察被抓到 → **清理**"，只做前两步会用一堆假红灯淹没真结论。
- **`verify` 的 `done_without_result` 假警报**：`outcome="no_results"`（搜索正常执行、
  确实没有命中）本来就是一个**有效终局**，却被判成 error。
  修法是只在 schema 判不出语义的那一种情况（`outcome` 缺失）才报。
  **假报警比不校验更糟，因为它会训练人忽略告警。**
- **`Tx.mark_dirty`**：文档里有、实现里没有，就地改 `tx.rows()` 会**静默丢数据**。
- **`research_tools` 的角色名写成 `agent-D`**（其余全是 `"D"`）：`build_for_role('D')`
  静默少 5 个工具，**没有任何地方报错**。现在装配期会断言所有声明角色 ⊆ `ROLES`——
  这条断言正是本轮 `无角色声明的工具 = 0` 那个数字的来源。

### 5.3 复核者自己犯了 FC-22 过度声称：`PROVED_HERE` 标签被当成"我算过了"（发现者：主控复核 G/H 侧产物时发现，由本报告作者修）

这是本阶段**最有价值的一条一手教训**，因为犯错的是"独立复核"本身——
而复核的可信度一旦有污点，整份报告都会归零。

- **现象**：独立实现报了 "90 项检查、0 项失败"，tally 为
  `{"PROVED_HERE": 55, "NUMERIC": 31, "QUOTED": 4}`。但其中大量 `PROVED_HERE` 的
  `note` 是 `degrees seen = [3]`、`|B_3|=19, |E|=21` 这类**测量记录**。
- **根因（类别错误）**：`"degrees seen = [3]"` 证明的是"**B₃ 盒子里**每个顶点度数为 3"，
  **不是**"`K(m)` 是 `m`-正则的"——后者要靠解析论证：
  *对每个 i，`x+e_i` 与 `x−e_i` 中恰好一个的和仍落在 `{0,1}`，故每个顶点恰有 `m` 个邻居*。
  "B₂ 内无圈"、"围长 = 6" 同理：盒子里的计数是 **NUMERIC**。
  把"算了几千个点都对"写成"证完了"，正是 E 角色的 `schema.Experiment` 专门拒绝的动作
  （计算类方法拿不到 `proof`），也正是 `main.pdf` 自己写 "No numerical output is used
  as a proof" 要防的东西。**框架的 E 拒绝这件事，我的复核报告却自己做了。**
- **证据（修前，逐字取自 `temp/verify_paper_independent_result.json`）**：
  ```
  {"claim": "K(3): all degrees in B_3 equal m (|B_3|=19)", "status": "PROVED_HERE", "note": "degrees seen = [3]"}
  {"claim": "girth K(3) by edge-deletion in B_3",          "status": "PROVED_HERE", "value": 6, "note": "|B_3|=19, |E|=21"}
  {"claim": "K(3): B_2 contains no cycle (so no 4-cycle)",  "status": "PROVED_HERE", "note": "|B_2|=10"}
  ```
- **修法（不是改措辞，是改机制）**：
  1. 给三个标签写下可判定的定义：`PROVED_HERE` **仅当**结果里带一段解析论证；
     `NUMERIC` = 有限范围内的计算/采样（**默认落这里**）；`QUOTED` = 引自论文。
  2. 在脚本里加一张 **`ARGUMENTS` 白名单**（每条 `PROVED_HERE` 必须写出论证原文），
     并让 `record()` **机械执行**：论证缺失、或论证里出现
     `seen / counted / sampled / observed / measured / in b_ / checked / n= / enumerated`
     这类测量词 → 记入 `FC22_VIOLATIONS` 并**以非零退出码结束**（fail-closed）。
     **标签再也不能被随手乱填。**
  3. 修好后 `PROVED_HERE` 只剩 11 条，每条都回答得出"论证写在结果文件的哪一句"。
- **修前/修后对比**：

  | | 修前 | 修后 |
  |---|---|---|
  | 检查条数 | 90 | **101**（新增 §0"解析论证"一节 11 条） |
  | `PROVED_HERE` | **55**（含大量盒子计数） | **11**（每条带论证） |
  | `NUMERIC` | 31 | **86** |
  | `QUOTED` | 4 | 4 |
  | `PROVED_HERE` 缺论证 | *未检查*（这正是漏掉的原因） | **0** |
  | FC-22 违规 | *未检查* | **0** |
  | 退出码 | 0 | 0（分布已如实） |

- **防复发（负控，FC-09）**：脚本加了 `--selftest-fc22`，注入一条**没有论证**的
  `PROVED_HERE` 断言。实测：`--selftest-fc22` → **exit code = 1**，
  打印 `[FC-22 VIOLATION] PROVED_HERE without an argument`；
  正常运行 → **exit code = 0**。**门被证明会响，不是摆设。**
- **一般化教训**：一个"标签"如果只靠人写、没有机器判据，它就会在压力下退化成
  "我觉得这条挺硬的"。**本项目的每一条纪律都要有一个可执行的判据**——
  三态要有受控 `reason`、证据等级要有 schema 硬约束、`PROVED_HERE` 要有论证白名单。
  三者是同一个模式：**把"声称"变成"必须交出的东西"。**

**（3）归因边界（必须写清楚，否则就是编故事）**：

- 症状还包括：`run_acceptance.py`、`repro_common.py`、`verify.py` 在同一分钟内被反复改写。

**处理办法**（这部分是可复用的工程经验）：

1. **不猜、先证**：用文件 mtime 时间线确定"谁在什么时候写了什么"，
   而不是假设那些失败是自己的代码造成的。
2. **改成"静默期"再跑**：把验收驱动改成"等 5 个脚本齐备**且**整棵树 ≥90 秒无写入"才启动，
   而不是固定 sleep。竞态是时间问题，固定 sleep 只是把概率改小。
3. **隔离数据根**：用 `--root verify-run2` 让验收拥有**自己的数据目录**，
   只**读**对方的 `repro/`，从而不与对方的 `acceptance-run/workspace` 争抢。
4. **分工而不是并行**：生产工作流（`repro/*.py` 与 `run_acceptance.py`）由一侧主导；
   另一侧改做**独立复核**（不共用代码的第二实现），并把发现的缺陷交回去。
   事后看这是这次唯一没有互相踩到的分工方式。

**事故的收尾**：两个智能体随后**显式划定了文件所有权**——
一方独占 `test/test1/` 与 `test/test2/`（生产 + 最终验收），
另一方只写 `draft/`（本报告），并承诺不再触碰对方的树。
这条"口头协议"之所以有效，恰恰是因为它把**隐式的并发**变成了**显式的所有权**；
而在此之前，双方都在"看见文件被改"之后才发现对方存在。

**教训（值得进下一阶段的框架设计）**：
"多智能体协作"的**协作协议本身**必须先于能力建设——
本项目花了大量精力在"表怎么锁、事务怎么写"上，但**"谁有权改哪个文件"**这件事
直到两个智能体撞在一起才被当真。在正式框架里，角色不仅要有**数据权限面**（现在的 `roles` + `side_effect`），
还要有**工作区/文件所有权**，并且**同一所有权面同时只能有一个写者**——
这正好对应 `05-智能体工作区-权限-工具栏精细化配置报告` 与 DSH 的 `leases`
机制，是本轮最该被下一阶段吸收的一条（已列入 §9 待决问题第 6 条）。

## 7. 诚实的边界（**不许含糊**）

1. **`Spec S̃_m = [−m, m]` 无法独立验证**：论文 Remark 1.6 明示引用 `[6, Thm. 6.5]`，
   且 `[6]` **连出版信息都没给**，我们无法查阅核对。
   因此 **Theorem 1.5 的"余谱"那一半依赖一个我们读不到的外部定理**。
   框架的正确行为是把它登记成 `external_unavailable`——**这不是缺陷，是正确行为**。
2. **抽取器的"选择"由人提供**（`paper_seed.SeedExtractor`），不是系统自己读出来的；
   但抽取结果的**正确性**由框架验证（逐字回引文 + 判重 + I6 闸门）。
3. **`method="formal"`（真证明）在本环境不可用**（没有 Lean/Coq），
   所以 `evidence_kind="proof"` 这条路径只能靠**构造数据**验证，
   **不能端到端跑通**。本轮 5 个复现脚本全部只拿到 `cross_check`，这是正确的。
4. **F 的 `owner ∈ {C,D,F}` 子目标不会被自动推进**——验收输出里如实写着
   "10 轮被记为 `no_change`"。这意味着"攻坚"目前**只能被工具型子目标驱动**，
   是本轮**最大的能力边界**。刻意这样做的理由：一个"假装在思考"的攻坚循环
   比一个不存在的循环更危险，因为它会产出一堆看起来在推进的轮次记录。
5. **OCR 在本机不可用**（无 tesseract 二进制；`easyocr` 因 torch/numpy ABI 与
   模型目录权限失败）。`ocr.run` 如实返回 `meta.kind="no_backend"` 而**不假装成功**。
6. **H 不能发现"数学错误"**，本轮明确不做。H 只判"稿件有没有把自己说清楚"
   （有没有引用、证据等级有没有被夸大、依赖有没有闭合）。
   一个声称"我检查了证明"的自动审校器是危险的。
7. **`verify-run`/`verify-run2` 是隔离验收的数据目录**，不是交付物；
   交付的验收入口是 `test/test2/run_acceptance.py`。

## 8. 实测缺陷档案

本节按统一的五段式记录本轮**实测到**的缺陷：**现象 / 根因 / 证据 / 修法 / 防复发测试**。
每条都注明**是谁发现的**——本项目的一条纪律是"审校者的判断也需要证据"，
同理，一条缺陷记录若说不清"谁在什么场景下撞到的"，它就无法被复核。

> 收录标准：**只有实测到的才进本节**。推测的、没复现的、只在代码里"看起来可能有问题"的，
> 一律不写（写了就会把这一节的信噪比拉到和"24% 假报警率"一样的下场，见 §2 第 4 条）。

### 8.1 审校者手里有刀：只读角色的工具面泄漏（发现者：G/H 子任务）

- **现象**：按角色装配出的审校者 H 的工具面里出现了 `table.update`、`fs.write`、
  `verify.run_experiment`——**只读角色拿到了能改数据的工具**。
- **根因**：`table_tools` / `fs_tools` / `verify_tools` 在注册时把**注入的全部 `ROLES`**
  写进了每个工具的 `roles` 字段。也就是说"谁能用这个工具"被写成了"所有角色都能用"，
  于是 `for_role("H")` 诚实地把写工具也发给了 H。这不是过滤逻辑错，是**声明本身错**。
- **证据**：装配后遍历 `for_role("H")`，其中 `side_effect ∈ {write_local}` 的工具数 **> 0**。
- **修法（两道，缺一不可）**：
  1. **声明侧**：`table_tools` / `fs_tools` / `verify_tools` 各自过 `_effective_roles`，
     写工具的角色声明**排除只读角色**；
  2. **结构侧**：`ToolRegistry.for_role` 对 `READ_ONLY_ROLES = ("C", "H")`
     **强制剥掉所有写工具**，并把被剥掉的名字记进 `role_filter_notes`。
- **为什么两道都要**：只做第 1 道，下次有人新写一个工具、又顺手把 `ROLES` 全塞进去，
  漏洞就回来了；只做第 2 道，则"声明"与"实际"长期不一致，
  而**声明本身就是审批判据**（`side_effect` 是审批的唯一可信来源，见 LESSONS 经验 9）。
  两道合起来才同时满足"声明正确"与"即使声明写错也拿不到刀"。
- **防复发测试**：`tests/test_tools_readonly_roles.py`（7 条），包含
  "**声明写错也拿不到刀**"的负控、"干净声明不留痕"的防误伤、
  以及"**写工具至少有一个写角色**"（防止第 1 道修过头，把写工具变成谁都拿不到）。
- **实测结果**：各角色工具数 A 20 / B 18 / C 17 / D 37 / E 21 / F 32 / G 32 / H 23，
  C/H 写工具泄漏 **0**（本报告 §1.5 的数字即由此而来）。

### 8.2 `alloc_id` 发出已被占用的号，`upsert` 按主键静默覆盖（发现者：D 子任务）

- **现象**：D 侧新建的矛盾问题 `(0002, 0004)` **被已存在的 `0000` 顶掉**，
  而 `new_question_ids` 还返回 `["0000"]`——即"我以为我建了两条新问题，
  实际把两条旧问题覆盖了，而且返回值在骗我"。
- **根因**：`Tx.alloc_id` 从 `counters` 取号，但当 `counters` **落后于表**时
  （例如表被直接改过、或 `rebuild` 之前的历史数据），它会发出**已经被占用**的号；
  而写入走的是按主键 `upsert`，于是**静默覆盖**而不是报冲突。
  两个各自"正确"的设计（发号器 + upsert 幂等）组合出一个静默数据丢失。
- **证据**：D 新建两条问题后，`len(questions)` 未增加且 `0000` 的内容被改写；
  返回的 `new_question_ids == ["0000"]`。
- **修法**（`store.py`）：分配时在**已声明的事务表**里查占用，**占用就往后跳**；
  并把 `counters` 推到最终号 + 1（**缓存自愈**）；跳号时写一条
  `alloc_id_skipped_occupied` 事件（**跳号必须留痕**，否则"号为什么跳了"永远查不出来）。
- **防复发测试**：`tests/test_store_alloc_guard.py`（5 条）。
- **一般化教训**：这是"**幂等写入 + 会落后的发号器**"的组合缺陷。
  凡是"按主键 upsert"的系统都必须问一句：**我的 ID 有没有可能重号？**
  重号的后果不是报错，而是**静默覆盖**——本项目最怕的一类失败。

### 8.3 `verify` 里两处"写死名单 / 与 schema 不一致"（发现者：`reprocess_requests` 崩塌由主控在跑验收时发现）

- **现象 ①**：新增 `reprocess_requests`（ID 形如 `p-0001`）后，**`verify` 自己崩掉**——
  不是报 error，是 `int("p-0001")` 抛 ValueError 把校验器带走。
- **根因 ①**：`_id_contiguity` 只把 `search_requests` 排除在"连续整数 ID"检查之外，
  其余表一律 `int(id)`。新增一张非 4 位 ID 空间的表，就把校验器打挂了。
  修法：改为按 `id_field ∈ S.ID_COUNTERS.values()` 判定，**不再写死名单**。
  同族的还有测试夹具 `conftest.sync_counters` 写死 3 个 kind，新增 5 类 ID 后同步失效。
- **现象 ②**：`done_without_result` 把合法的 `outcome="no_results"` 误报成 error。
- **根因 ②**：该检查的条件是"`done=true` 且既无 `result_lit_ids` 也无 `last_error`"，
  但**搜索正常执行、确实没有命中**本来就是一个有效终局，
  而 `schema.SearchRequest.validate` 明确允许这种组合。
  修法：只在 **`outcome is None`**（历史数据，schema 判不出语义）且无文献无错误时才报。
- **证据**：一条 A 在无检索后端时如实登记的 `outcome="no_results"` 请求让 `verify` 报 error。
- **为什么这条比"少校验"更严重**：**假报警比不校验更糟，因为它会训练人忽略告警**。
  红灯一旦变成背景噪音，真正的 error 也会被忽略。
- **一般化教训（FC-11）**：**校验器与写入方必须共享同一份规则**。
  任何"校验器里另写一份名单/条件"的地方，都会在 schema 演进时与 schema 分叉。

### 8.4 三条 schema / 契约修正

| 缺陷 | 现象与根因 | 修法 |
|---|---|---|
| `next_prefixed_id` docstring 与实现不一致 | 传 `"r-"` 会得到 `r--0001`，**而且能通过校验静默落库**——文档说的和做的不是一回事，错的那个还能存进去 | 现在**拒绝**非字母数字前缀（宁可不给号，也不要给一个看起来合法的怪号） |
| `AttackPlan.validate` 的 history 上限过紧 | "轮数用尽"那一轮**无法追加一条 `action=stop` 的如实记录**——即"**说停**"这个动作被 schema 挡住了，于是"停在预算内"这件事反而记不下来 | 上限放宽为 `+1`（给收尾记录留一格） |
| `SUBMITTER_DEFAULT_PRIORITY` 未登记 E/F/G/H | 未登记 ⇒ 靠"兜底为 low" | 补齐四个角色并**显式登记为 low**。两种写法结果相同但**语义不同**："我不认识它"与"我认识它且决定它低"——前者会在新增角色时静默降级 |

### 8.5 F 的子目标外包没有降级路径（发现者：E/F 子任务）

- **现象**：一个**缺失的脚本文件**会让 `ExperimentError` 穿过 `AgentF.step`，
  **中止整个攻坚循环**——即一个子目标的输入错误把整轮攻坚带走。
- **根因**：`AgentF._deploy_e` 没有 `try/except`。
- **修法**：降级为 `outcome="blocked"` + `blocked_reason`（**带原因**），并**继续推进其它子目标**。
- **依据（FC-21）**：**子任务可降级，整体绝不谎报成功**。
  注意这里两个方向都不能错：既不能因为一个子目标失败就整体崩掉，
  也不能把失败静默吞掉写成 `no_change`——必须写成 `blocked` 并带上原因。

### 8.6 本报告作者发现的两条

| 缺陷 | 现象 | 根因 | 修法 / 防复发 |
|---|---|---|---|
| `repro_common.cycles_through_identity` **恒返回 `(0, None)`** | 对任何输入都报"该长度上不存在经过恒等的圈"；而 `ball_girth` 对 m=4,r=2 **明确给出一个含恒等的 4-圈** | 基例差一：长度 `L` 的圈经过恒等元时有 `L−1` 个中间顶点，代码却等 `len(path) == length`（即 `L+1` 圈），基例**永不可达** | 改为 `length - 1`；对 6 组已知真值全部正确（含"m=4,r=2 无 6-圈"这一**正确**的空结果——长度 L 的圈需半径 ≥ L/2） |
| 验收 P5 的**判重键选错** | `experiments` 表 10 行 / 5 个脚本（每个两行）；P4 花 247s、P5 又花 267s 做同一件事；P5 判据 `10/5` 必然报红 | 复用判据用 `claim_key`：F 按子目标命名（`reproduce:main.pdf#sg1`），P5 按论文命题命名（`SpecK(m)=[-m,m]`），**永远匹配不上** | 判重键改为 `code_path`（脚本才是实验的身份）；判据改为"**每个脚本恰好一行**"——后者才同时防住重复登记与漏跑 |

两条的共同点值得单独指出：**它们都不抛异常**。
第一条把一个"存在"报成"不存在"（下游很可能当成一条研究发现）；
第二条只是把成本翻倍、把证据表弄脏。
**静默失败/静默覆盖比崩溃更危险**——崩溃会被看到，静默失败会产出一张看起来全绿的表。

### 8.7 本报告作者在**自己**的独立实现里犯的错（保留在代码注释中）

独立复核的价值一半来自"独立算出了同样的数字"，另一半来自"**把自己的错也抓住了**"。
本轮作者在自己代码里犯了三个错，全部保留在注释里而不是悄悄改掉：

| 错法 | 后果 | 教训 |
|---|---|---|
| 无向边被重复计数（商图与腔图 cell 两条路径各犯一次） | 特征值**恰好整体乘 2**，采样最大值 6 = 2m，"看起来像论文引用的定理是错的" | 在宣称"论文错了"之前先怀疑自己的实现；矩阵仍 Hermitian、图仍 `m`-正则，**只有谱被整体缩放**，所以外观完全正常 |
| 第一次"修正"用有序对规范化后**累加**（而非去重），且守卫 `len(entry) == len(cell)//2` **照样通过** | 重复计数**依然存在**，守卫却给了假绿灯 | **弱断言给出假绿灯**（LESSONS 模式 P11）。正确守卫是强判据：`A` 每行 `\|·\|` 之和不得超过度数 `m` |
| 负控的期望值跟着注入的 bug 变（`want = 2m−1 if bug else m`） | 负控**通过了** | 一个"不可能失败"的负控比没有负控**更糟**，因为它被当成"门确实有效"的证据。断言必须始终用论文的值 |
| 读错返回键（`eigenvalues` 而实际是 `values`） | 判据退化成恒真，"路径始终在区间内"这条检查**永远不会红** | 判据里出现 `if x is None: ok=True` 就要警觉；改成"没返回就直接判红" |
| `[[1]*m] + 单位阵行` 的行秩与 1 比较 | 断言本身是假的（该矩阵秩为 `m`），正常跑就报红 | **断言写错**与**数学错**要分清；先把断言本身验一遍 |
| 为 `\|B₃\|`（m=6）先写了一个**猜的**期望值 92 | 用独立实现算出真值 **84** | **猜出来的期望值就是伪造的证据**；先算再用 |

## 9. 待决问题（交给下一阶段）
