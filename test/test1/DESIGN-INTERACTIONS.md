# A/B/C/D 交互补全与任务重分配 —— 设计 (v0.3)

> 本文件是 `DESIGN.md`（A/B 基线）与 `DESIGN-TOOLS.md`（工具层 + C/D 基线）的**第三份**。
> 只写**尚未实现的交互**与**任务分配的调整**；前两份的既有结论不变。
>
> 目标：让 A/B/C/D 从"一条链"变成"一张网"，且每个新增交互都**可判定、可审计、可终止**。

---

## 0. 现状：目前只有一条链

```
A(检索) ──> literature ──> B(整理) ──> concepts/relations ──> C(分析) ──> analysis_reports ──> D(研究)
   ^                                                                                              │
   └──────────────────────── search_requests（缺口提问）──────────────────────────────────────────┘
```

**问题**：所有信息都**单向流过**这条链。

| 症状 | 后果 |
|---|---|
| D 只能**读已生成的 C 报告**，不能就某个具体问题**点菜** | C 的分析范围由"上一次跑的 kind"决定，而不是由 D 的当下需要决定 |
| C 发现的**矛盾/弱连接**只写进报告，没人去**修复** | 发现的问题不会回流到 B（重抽取）或 A（补检索），报告只是"记了一笔" |
| B 建概念、C 建图，但**结构上重复的概念**（同一概念两个代号）无人合并 | 图被污染，度数统计与路径搜索都被稀释 |
| A 只接 D 的请求；C 的 `gaps` 候选**本就是明确的检索靶子**，却绕道 D | 多一跳、多一次判断、多一份失真 |
| 多个请求方（C/D/人）争用 A 的检索能力，**没有优先级** | 谁先提谁先查；重要的缺口可能被无关的检索挤掉 |

## 1. 新增交互（I1–I7）

每条都给出：**是什么 / 为什么 / 接口 / 终止条件 / 如何验证**。

### I1 ⭐ C 作为**可调用服务**（D 点菜，而不是吃套餐）

**是什么**：D 不再只消费 `analysis_reports`。它可以**按需**调用 C 的查询：
`neighbors` / `relations_between` / `paths(a,b)` / `contradictions(scope)` / `structural_duplicates()`。

**为什么**：需求的原文是"D 接收 C 的报告进行系统分析"。但真实研究是**问题驱动的**：
D 在追问某个问题时需要"这两个概念之间到底有哪些链条"，而那一刻 C 早已跑完、
报告里没有恰好那一条。**让 D 能点菜，是把 C 从"批处理"变成"服务"。**

**接口**：C 暴露一个**同步、只读、有界**的查询 API；D 通过工具层调用（`graph.*` / `trace.*` 已具备大部分）。

```python
# D 侧
c = AgentC(store)                      # 只读，可反复调用
rep = c.paths("0000", "0002", max_paths=5, max_len=4)
nodes = c.neighbors("0000")
dups  = c.structural_duplicates()      # 见 I5
```

**终止条件**：查询是**有界**的（`max_len` / `node_budget`）；超预算返回 `truncated=True`，不静默截断。

**如何验证**：断言 D 在 `research()` 中对每个问题**至少发起一次** C 查询，
且查询参数与该问题的 `related_concept_ids` 相关（而不是照抄报告里已有的结果）。

### I2 ⭐⭐ 矛盾闭环（发现 → 提问 → 检索 → 消化 → **复核**）

**是什么**：把"矛盾"变成一个**能自我收敛的循环**：

```
C 检测到两条关系的陈述互相矛盾
      ↓  产出 contradiction 记录（含两个 relation_id + 代号链）
D 把它变成一条 priority=high 的问题
      ↓  按 §4.4 判据判定"证据不足"
A 检索该主题 → B 抽取 → 新关系落库
      ↓
C **重新检查这两个具体的关系**（而不是重跑整个分析）
      ↓
裁决三选一：resolved（新证据支持其中一方） / unresolved（仍矛盾） / new_contradiction
      ↓  unresolved 或 new → 继续下一轮（受预算约束）
```

**为什么**：这是需求里"**D 继续思考研究**"最有价值的形态。
"矛盾"比"缺口"更强：它说明**现有知识里有东西是错的**，而不是"还不够"。

**为什么必须闭环而不是只报告**：上一版的 `C.contradictions` 只把矛盾写进报告，
没有任何机制去**解决**它 —— 那等于把最值钱的信号丢进一个只读的桶里。

**终止条件（必须有，否则会无限循环）**：
- 每轮最多追问 `max_rounds_per_contradiction`（默认 2）；
- 全局最多 `max_contradiction_requests`（默认 10）；
- 三轮后仍 `unresolved` → 标为 **`persistent`**，写进报告并**停止追问**（人来看）。

**如何验证**：
- 构造一对**人为矛盾**的关系 + 一篇判定性文献 → 断言一轮后 `resolved`；
- 构造一对**真矛盾**（无论怎么查都不收敛）→ 断言**在预算用尽后停下**且标 `persistent`，
  **不是无限循环**。

### I3 缺口直连 A（C 的 `gaps` 候选 = 检索靶子）

**是什么**：C 的 `candidate_gaps` 里**通过了 veto 且 confidence ≥ medium** 的候选，
直接生成 `search_requests`（`submitted_by="agent-C"`），主题就是该概念组的两个概念名。

**为什么**：`gaps` 的定义就是"**应该有边却缺失**"，那正是"去找找有没有人做过"的靶子。
绕道 D 只增加一次判断与一次失真。

**但必须有闸门**：否则一次 `gaps` 可能产出 20+ 个请求把 A 淹没。

**闸门**：
- 只允许 **approved 的 candidate_gaps**（过了 veto 门 + `confidence >= medium`）；
- 单次 `gaps` 最多提交 `max_gap_requests_per_run`（默认 3），按净分降序；
- 与已有未完成请求**主题去重**（复用 `research.submit_gap` 的查重思路）。

**如何验证**：断言 `gaps` 跑完后 `search_requests` 新增 ≤ 3 条，且每条的主题能对应到某个 `candidate_gap`。

---

### I4 定向重抽取（让 B 有事可做，而不是只顺流水线走）

**是什么**：C 或 D 可以针对**特定的关系**要求 B 重新处理：

| 触发源 | 请求 | B 的动作 |
|---|---|---|
| C 发现 `quote_verified=False` | "这条引文不可核实" | 重新在**全文**里搜该陈述的等价表述；找到 → 更新 quote 与 page_range；找不到 → 保持并标 `unverifiable` |
| C 发现描述过短 / 信息量低 | "这条关系信息量不足" | 回到文献中该页附近，抽取更完整的陈述 |
| D 需要某关系的**上下文** | "给我这条关系所在段的完整语境" | 返回该页/该段原文片段（L3 溯源） |

**为什么**：B 现在是**一次性**的（处理完就 `processed=true`，再不回头）。
这让 C 发现的问题**无法修复**。定向重抽取把 B 从"流水线工位"变成"可复访的服务"。

**接口**：新增 `reprocess` 请求表（或复用 `search_requests` 的思路，但**语义不同**，
应单独一张 `reprocess_requests`：目标关系/文献、原因、状态、结果）。

⚠️ **要防幂等陷阱**：重抽取**不能**简单地把 `processed` 置回 false（那会触发全量重抽）。
必须带**目标**（`relation_ids` / `lit_id` + 原因），只在该目标上工作。

**终止条件**：同一关系最多重抽取 `max_reprocess_per_relation`（默认 2）次。

**如何验证**：断言重抽取**只改动目标关系**、其它关系逐字节不变；且超限后拒绝。

### I5 结构重复概念检测（C 发现，B 合并）

**是什么**：C 检测**结构上等价**的概念对（在图里"看起来是同一个东西"）：

- `neighbors(a) == neighbors(b)`（邻域完全相同）；
- 或 `relations(a)` 与 `relations(b)` 所涉及的关系集合高度重合，且两者从不直接相连。

把这类候选交给 B → B 复核（按 `normalized_name` / 别名 / 定义）→ 决定**合并或否决**。

**为什么**：上一版的合并只看**名字**（`dedup.find_concept` 按规范化名字精确匹配）。
真实文献里"群"会以"group / 群 / G"三种写法进来，名字匹配不上，于是图里出现**三个同义节点**，
度数统计被稀释、路径搜索被污染。**结构信息是名字之外的第二路证据。**

⚠️ **必须保守**：结构等价 ≠ 同义（"所有子群都同构的两个概念"可能都连着同一批邻居）。
所以 C 只**提出候选**，**合并决定权在 B**，且 B 必须给出理由。

**如何验证**：
- 构造两个显然同义的概念（邻域相同 + 名字规范化后相同）→ 断言 C 提出、B 合并；
- 构造两个**邻域相同但显然不同**的概念 → 断言 B **拒绝**合并且留下理由。

---

### I6 写入期一致性闸门（B 在提交关系前问 C）

**是什么**：B 在**写入新关系之前**，问 C 一个问题：
"这条新关系与图中已有的关系**是否矛盾**？"

- 不矛盾 → 正常写入；
- 矛盾 → 写入但标 `status="suspect"` 并记录 `conflicts_with=[relation_id]`；
- 高度相似（已有判重）→ 已有的三档判重处理。

**为什么**：目前矛盾只能在**事后**由 C 发现。写入期闸门把发现提前 ——
而且它给了 B 一个判据，不必自己实现图推理（**职责不越界**：B 不懂图，C 懂）。

⚠️ **但有个硬约束**：B 在**提交事务内**调用 C，而 C 需要读图。若 C 去查 store 会**重入锁**。
→ 因此这个闸门必须是**纯函数**：`C.check_conflict(draft_relation, *, existing_relations)`，
**只吃内存数据，不碰 store**。这是"共享存储 + 多智能体"下最容易死锁的地方，必须写死。

**如何验证**：断言 `check_conflict` **不接收 store、不打开事务**（签名级断言），
且在并发（两个 B 实例）下无死锁。

### I7 检索预算与优先级（A 的产能是稀缺资源）

**是什么**：给 `search_requests` 加**优先级**与**配额**，并让 A 按优先级取任务：

| 提交方 | 默认优先级 | 理由 |
|---|---|---|
| D（矛盾闭环）| **high** | 矛盾是最强信号 |
| D（普通缺口）| medium | |
| C（gaps 靶子）| medium | |
| B（补定义）| low | 可以在空闲时做 |
| 人（手动提交）| high | 人的判断优先 |

**闸门**：全局在途请求上限 `max_inflight_requests`（默认 20）；同优先级 FIFO。

**为什么需要**：需求里"知识不足就向 A 提交查询"会在 D 的循环里**被反复触发**。
没有优先级与配额，A 的队列会被低价值请求填满，而**关键矛盾排在后面**。

**如何验证**：构造混合优先级的队列 → 断言 A **先取 high 再取 medium**；
构造超过上限的队列 → 断言**拒绝新请求而不是无限排队**。

## 2. 任务重分配（明确"谁不懂什么"）

新增交互会诱使每个智能体"顺手做点别人的事"。必须明确**职责边界**，
否则会出现"两个模块各持一套判据"的经典问题（上一版 `RuleExtractor` 的 docstring 里已经警告过这一点）。

| 智能体 | **负责** | **明确不负责**（越界即 bug） |
|---|---|---|
| **A** 检索 | 检索、下载、登记文献、**按优先级取任务**、维护请求优先级 | ❌ 判断文献质量；❌ 抽取概念 |
| **B** 整理 | 抽取、判重、**引文逐字回验**、按请求**定向重抽取**、**合并决定权** | ❌ 图推理（问 C）；❌ 决定"值不值得研究"（问 D） |
| **C** 分析 | 图/索引、四类分析、**矛盾检测**、**结构重复检测**、**纯函数冲突检查**、**按需服务 D** | ❌ 写关系（只读！）；❌ 决定合并（只提出候选）；❌ 发检索请求之外的动作 |
| **D** 研究 | 问题台账、三级溯源、**决策闭环走向**（哪些矛盾值得追）、写研究报告 | ❌ 直接检索（走 A）；❌ 直接改关系（走 B/C 的请求） |

**一条硬规则**：**C 永远只读**（它的全部工具 `side_effect="read"`）。
这不是洁癖 —— 一旦 C 能写，它就会成为"绕过 B 的写入路径"，
而 B 的引文回验是**唯一**能自动发现幻觉引文的地方。**C 写 = 绕过验证门。**

## 3. 中间逻辑优化

### 3.1 `ingest` 的等价类，而不是逐条处理

上一版 D 的 `ingest` 按 `(kind, 排序后的 rel_ids)` 去重（已修）。
但更深的问题是：**同一份报告里的两条不同链条可能支持同一个研究点**。
→ 引入**问题等价类**：把"共享 ≥1 个关系代号"或"概念集合 Jaccard ≥ 阈值"的问题归为一类，
**只研究一次**，类内合并 `origin`。

### 3.2 证据就绪判据：从"请求完成"到"**新证据可回答问题**"

上一版 `poll` 的判据是"请求 `done` 且其文献都 `processed`"。
但这只说明"**消化完了**"，不说明"**这些新证据真的回答了那个问题**"。
→ 增加一层：新落库的关系中，**是否有任何一条落在该问题的 `related_concept_ids` 上**？
有 → 就绪；没有 → 记 `evidence_arrived_but_irrelevant`，并**降低该问题的优先级**
（避免同一个问题反复问同一件查不到的事）。

### 3.3 代号链是**一等公民**

所有跨智能体的引用都用**代号链**，不用自然语言描述：
`relation_ids` 决定"引用了哪条知识"，`concept_ids` 决定"关于什么"。
自然语言只在**给人看的报告**里出现。

> 这条来自上一版最刺痛的教训：D 曾经因为"没接工具"而**静默拿到空证据**，
> 却把"查不到"写成了一条**听起来很合理的研究发现**。

### 3.4 所有"空"必须三态

沿用 `DESIGN.md` §6.3 的引文三态（`True` / `False` / `None`），推广到**所有**跨智能体返回：

| 场景 | 禁止 | 要求 |
|---|---|---|
| 查询无结果 | `[]` 或 `False` | 区分"没查"（`None`）与"查了没有"（`[]` + `status="empty"`）|
| 冲突检查 | `False` | 区分"检查过、不冲突"与"没检查" |
| 重抽取 | 静默跳过 | 报告 `attempted` / `skipped_reason` |

## 4. 验证策略（每个新交互都要有**可判定的**验收）

| 交互 | 验收（可判定） |
|---|---|
| I1 C 服务化 | D 的每个问题至少一次 C 查询，且参数与问题相关 |
| I2 矛盾闭环 | 人为矛盾 → 一轮 `resolved`；真矛盾 → **在预算内终止**并标 `persistent` |
| I3 缺口直连 | `gaps` 后新增请求 ≤ 上限，且都能对应到 candidate_gap |
| I4 定向重抽取 | **只**改动目标关系（其它逐字节不变）；超限拒绝 |
| I5 结构重复 | 真同义 → 提出+合并；假同义 → **拒绝并留理由** |
| I6 写入期闸门 | `check_conflict` **签名不含 store**（无锁重入）；并发无死锁 |
| I7 优先级 | 混合队列 → 先 high 后 medium；超上限 → **拒绝而非无限排队** |

**并且：每个交互都要有一条"负控"用例** —— 构造"它不该触发的场景"，断言它**确实没触发**。
（这是上一版 `gaps` 的 veto 给的教训：只有正向信号时，"有"和"没有"一样容易通过测试。）

## 5. 待决问题

1. **I2 的"矛盾"如何判定？** 上一版只做了"两条 `statement` 互相矛盾"的**启发式**。
   数学上"矛盾"需要语义理解，纯字符串做不到。本轮：**只做可核实的形态**
   （同一概念组的两条关系给出互斥的 `quote`/`statement`，如"A 是 B" vs "A 不是 B"），
   并把 LLM 判定留作钩子。**不假装能判定一般矛盾。**
2. **I4 的 `reprocess_requests` 是新增表还是复用？** 倾向新增表（语义不同：它不是"去检索"，而是"重新处理已有的"）。
3. **I7 的优先级是否需要"抢占"？** 本轮只做**排队**，不做抢占（抢占会打断正在跑的 A，代价大于收益）。
4. **一个智能体能否同时扮演两个角色？** 本轮：不能（角色即权限面，见 §2）。
5. **要否引入"人工闸门"？** `suspect` / `persistent` 两类都需要人看，但本轮不做 UI，只在报告里显式列出。
