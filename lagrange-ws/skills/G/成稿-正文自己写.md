# 成稿：正文由你写，编译只负责编

- 名字：`成稿-正文自己写`
- 属于：`G`
- 什么时候读它：任务说「整理成论文 / 交付论文 / 稿件」，或要一份可编译的正文时
- 一句话：散文体正文 fs.write 到 out/paper/main.tex，再 paper_compile
- 会用到的动作（角色.动作）：G.build_document, G.register_dependency, G.compose_claim
- 会用到的工具：fs.write, doc.paper_compile, doc.write_mapping, doc.scan_claim

# 成稿

## 业主 2026-10-13 裁定（逐条落地）

- **正文是你写的，不是脚本生成的**：`fs.write` 写到 `out/paper/main.tex`，
  散文体、章节自己排，`\cite` / 定理环境随你；落笔前后用 `fs.read` 读回来核一遍。
- **没有「渲染脚本」「建论文包」「核锚」这回事**（2026-10-13 退场，见 `draft/117`）。
- **编译**：`doc.paper_compile` 出 `out/paper/main.pdf`。
  本机 MiKTeX 会写完 PDF 却以 `0xC0000409` 退出 ⇒ **产物与退出码分两栏读**，
  别只看退出码判成败。
- **先有对应表，再写正文**（业主 2026-10-22）：对应表用 `doc.write_mapping` 一次写三份 ——
  你只给行（正文里每条定理/引理/命题/推论/例子/实验各占一行：`kind` / `label` / `env_no` /
  `ledger_id` / `proof_no` / `file`），它调 `papermapping.write_package` 渲染出
  `out/paper/MAPPING.json`、`out/paper/MAPPING.md` 与正文附录「附录：产出对应表」，并把
  `\input{mapping-appendix}` 放进正文。**md 与附录不许手写**：判据要的是"与渲染器逐字相同"
  （`md_drifted` / `mapping_paper_mismatch`），手抄一遍就对不上。
  正文里每个定理类环境都要能在表里找到一行，表里每一行也要在正文里
  有一个环境 —— 两个方向都不许有孤儿。多证明时每条证明各占一行（`#p1` / `#p2`）。
  `file` 写**论文包内的相对路径**（绝对路径在别人机器上等于不存在）。
  顺序是死的：先 `doc.write_mapping` → 再写/改正文 → 再 `doc.paper_compile`（改完正文
  必须重编一次）。

## 引用与断言

- 每一条断言用 `G.compose_claim` 构造（判据只有一份，在工具层）；
- 外部依赖用 `G.register_dependency` 登记 —— `closed` 时必须核到**已入库**的来源（FC-23）；
- 稿件级审校由 **H** 做（`H.review`），它的判据是"正文与台账逐字一致 + L 的形式化（`formal` 位那一行）或 V 的签名"。

### 四个键最容易写错（2026-10-16 亲测，各撞了一次）

| 键 | 写什么 | 我撞到的 |
|---|---|---|
| `citations` | **带受控前缀的字符串**：`lit:000000` / `rel:000010` / `exp:…` / `stmt:…` / `doc:…` / `eval:…` | 写成 `{"lit_id": "000000"}` ⇒ 拒：`code=bad_citation_prefix`（前缀表里没有 `{'lit_id'`） |
| `evidence_kind` | **`proof` / `proof_review` / `cross_check` / `heuristic`**（证据**强度**） | 我借了 `origin` 的词写 `external_lit` ⇒ 拒：不在受控词表里（**族 2**） |
| `section` | 这一条断言归哪一节（必填） | 漏 ⇒ 关键字必填，一次性点名三个 |
| `sections`（建稿件时） | 每项是**含 `heading`** 的对象（不是 `title`） | 写成 `{"title": …}` ⇒ 拒：`sections[1] 必须是含 heading 的对象` |

⚠️ **`origin` 与 `evidence_kind` 是两个完全不同的词表** ——
`origin`（来源可追）用 `external_lit` 这类；`evidence_kind`（强度）用上面那四个。
"从文献里摘的"这个直觉会让人把前者写进后者（我就写了），**看键名再填**。

⚠️ **同一个面里有三套"kind 类"词表**（2026-10-16 亲测，我三次都借错）：

| 键 | 词表 |
|---|---|
| 命题的 `origin` | `external_lit` …（来源**可追**） |
| 断言的 `evidence_kind` | `proof` / `proof_review` / `cross_check` / `heuristic`（**强度**） |
| 依赖的 `kind` | `theorem` / `definition` / `lemma` / `proposition` / `dataset` / `experiment` / `prior_art`（**依赖是什么**） |

⚠️ **同一个键在不同工具里形状可能不同**：`page_range` 在 `compose_claim` /
`register_statement` 里是**对象**（`{"start": 1}`），而在 `register_dependency` 里是
**数组**（`[1]`）—— 照另一个工具的形状写会被拒（`page_range. 必须是数组`）。

### 依赖闭合（FC-23）为什么要你亲自核

`register_dependency(status="closed")` 时，**schema 查不出"这篇文献在不在库里"**
（它只能查字段非空）⇒ 这一条**必须由 G 用真实数据核**：
引用一篇不存在的文献，等于**把外部结论当成了自己的结论**。被拒时是**受控**的
（拒在写库之前），拒信会说明这一点 —— 补齐来源再登记，别绕过。

### G 的两个动作**返回不是字典**（同 D 那一族）

`G.render` 与 `G.refresh_markdown` 是"**只动文本/文件**"的动作 ⇒ 返回的是**文本/路径**，
别对它们取 `.get(...)`。要判成不成，看**盘上的那份 markdown 变没变**。

## `cross_check` 那一档必须自带独立 `disclaimer` 栏（最常被拒的一格）

`evidence_kind='cross_check'`（数值交叉验证、文献级判断、经验推理）的断言，
**必须显式写明**「数值交叉验证，不构成证明」—— 而且要找的是这条断言对象里
**独立的一栏 `disclaimer`**：**写进 `text` 不算，写在别的断言里也不算**。

两条路，别混：

- 用 `G.compose_claim` 构造 ⇒ 它**自动补**这一栏，用它就不会踩；
- **自己手写 `claims` 直接交 `G.build_document`** ⇒ 这一栏要**自己给**。
  落库闸门**刻意不替你补**（补了就等于把"漏写了声明"这件事藏起来 —— 那是本框架
  最忌讳的静默修复）：`compose_claim` 是构造函数，负责帮你造合规的断言；
  `build_document` 是闸门，负责拒不合规的断言。

**第 10 趟 T5 实测**：这一格在**同一次运行里连拒 3 次**（同一份稿件的 claim-1 与 claim-3
反复被拒），而 G 的手册当时一个字都没提它 —— 所以这一节是补那个缺口，不是提醒你小心。
