R68：预算轴（不限步数只限预算：寄存器 + 实时扣除 + 扣完优雅停 + CLI）与请求超时 60→300 秒

业主 2026-10-12 的验收清单里，预算与监控那两条逐字是：
「不限制步数只限预算，预算设置/显示窗口，用户可追加预算，运行消耗实时从总预算扣除，
扣完自动发优雅停止请求（可为负一点点）」「完善 Web UI（使用说明、设置窗口、接线完整），
重视体验感与多智能体系统的监控能力」。本批做预算轴的引擎部分（UI 与端点排在下一批，
施工面见 draft/112 §4.2），并补一个回答业主追问时发现的归因缺陷。

## 额度寄存器（新文件 budget.py）

- 落点：`<工作区>/budget.json` 里 `total_usd` + 只增的 `added[]`（每条带 kind/usd/by/at/note）；
- 花销**永远**从 `usage_ledger` 现算（那一层本来就幂等）：寄存器不记花销 ——
  两处记账必然漂移，而"这趟花了多少"只有一个权威来源；
- 三态：寄存器在 ⇒ 用它；不在 ⇒ 回退到 `--budget-usd`；**损坏 ⇒ 回退 + 把 problem 报出来**。
  第三态刻意不折成"无上限"：读不出来与没有上限是两件事；
- 写入原子（临时文件 + `os.replace`）；`add_usd` 只收正数，寄存器损坏时拒绝追加；
- 每次闸门**现读**：追加预算不需要重启那一趟（这就是"用户可追加预算"的实现面）；
- "可为负一点点"：闸门按步与按调用检查，不是预授权 —— 扣完那一刻已经在飞的那一次
  调用仍会落账，最终读数可能略越上限；这一档如实上报（exceeded），不假装正好等于上限。

## 实时扣除与优雅停

- `llmseam.LlmSeam` 新增 `budget_of` 回调 + `budget_limit()`：发请求前的闸门每次问一次；
  回调没给或抛异常时回退到构造期的 `usd_budget`（回退到"少花"那一侧，不许变成不限量）；
- `agent_loop.py`：步循环的预算闸门改读现读上限；耗尽时 stop_reason="budget"、
  经 stopctl 落一条跨进程停请求（by="budget"）、通知在飞子代理，final 给出两条出路
  （`agentflow budget --add`、`--resume`）；
- `autonomy.py`：多轮在每轮之前与每次 run_role 都传现读的额度；
- `cli.py`：**`--budget-usd` 第一次真的灌进 `Policy.usd_budget`**（改前只灌了墙钟 ⇒
  编排层那条闸门从来没生效过）；新增子命令 `agentflow budget --status/--set/--add`
  （`--root` 是全局参数，要写在子命令前面）。

## 请求超时 60 → 300 秒，以及"超时被记成坏 JSON"的归因修复

现场（第一次无 Lean 模式 T2，sid t2u1）：步 0 用了 **260.469 s** 才成功（输出 12,178 tokens、
推理 39,755 字），步 1 三次 `超过 60.0s 未返回`（elapsed_sec=424.594 = 3×60 秒 + 退避，
ModelSpec.max_retries=2）；离线探针量到一条 32,768-token 的思考回复要 181.1 s，端点自检
HTTP 200 / finish_reason=stop。病灶是两个数不匹配：R62 把单次输出上限提到 32768 之后，
"想得久"成了合法的一步，而客户端读超时还是 60 秒 ⇒ "它想了 3 分钟"被翻译成"失败"。
缺省改 300 秒（`AGENTFLOW_MODEL_TIMEOUT_SEC` 可覆盖）。

顺带发现的第二个缺陷：网关这一层**从不抛异常**（超时折成 ok=False + error_kind=timeout），
而缝对"回复不 ok"一律写 `judge_failed:ModelReplyNotOk` ⇒ 上面那三次超时被循环算进
bad_json_streak，收场写成"连续 3 次没有给出可解析的 JSON" —— 三句话没有一句是真的。
归因错不是难看，是修错地方（坏 JSON 收紧输出协议、超时调大上限或拆小这一步，方向相反）。

- `judge.problem_of_reply()`：网关"不抛"那条路的唯一映射点，与"异常 → 码"的
  `judge._problem_of()` 并列（timeout ⇒ judge_timeout，其余维持原串，不加新词表取值）；
- `LoopRun.model_timeout` / `model_timeout_streak` 单独计数（不进 bad_json）；
  连击到上限 ⇒ stop_reason="model_timeout"，收场那句说的是"没等到返回"并给两条出路；
- 回给模型的纠正换成"把这一步拆小"（它没说话，"只回一行 JSON"对一次超时无可行动）；
  续跑重建对话按同一句还原（"重建的那一段与当时逐字相等"这条判据不漏这一档）；
- 徽标表加一格 `model_timeout`。

## 同一天发现的第三档：思考把输出预算吃光

第一次 T2 的 21 步里有 2 步（步 2 与步 18）的上游回复是 content="" + finish_reason=length
+ 思维链 109,397 / 96,969 字 —— 推理 token 与正文共用同一份 max_tokens=32768
（109397 ÷ 32768 ≈ 3.3 字/token，与中文推理的字-token 比一致）：它想得很多，而正文一个字
都没留下。这一档此前也落成 judge_failed:ModelReplyNotOk ⇒ 按坏 JSON 计数、按"重念输出协议"
纠正 —— 而它要的处置正好相反（把这一步拆小、把思考压短）。

- modelgw 新增 error_kind="output_exhausted"（finish_reason=length 且正文空且思维链非空），
  计进"没查成"、不重试（同一个请求必然同一个结局，重试一次要再付一整份输出预算）；
- judge.problem_of_reply 把它映成 judge_output_limit（新码，只加不删）；
- 循环把它计入 no_reply（与超时同一档"没拿到可用的回复"），纠正话术是
  "下一步只回一行 JSON，把想法压到十句以内；要做的事本来就大就把它拆小"；
- 负控两条：空正文但 finish_reason=stop ⇒ 仍是 bad_response；被截断但一个字都没想
  ⇒ 也仍是 bad_response（那一档是"它没想"，不是"想太多"）；
- test_every_agent_can_think.py 的口径随之改（同一形态从 bad_response 改成 output_exhausted）
  —— 那条判据的 docstring 本来就写着"两种 finish_reason 的处方不同"，这一批把处方分开。

为什么不顺手把 max_output_tokens 抬到 65,536：上次它正好停在 32,768 上（109,397 字 ≈ 33k
token），抬上限只让一次"想过头"多花一倍的钱，正文仍然可能一个字不剩。这一档的杠杆在
"让这一步变小"，不在上限。

## 批次末自查补上的两处（各配一条判据）

- `budget.__all__` 里写着 `state`，而那个读函数早改名成 `reading`（避开与 `paperbuild.state`
  之类的重名）—— 公开面在说谎，而没有任何判据看得见（`from agentflow.budget import *`
  会当场炸，但"没人 import *"不等于"公开面是对的"）。改名字 + 新判据
  "`__all__` 里每个名字必须真的存在"。
- `write_initial` 的 docstring 说"把旧值记进 `added` 历史"，代码却把历史整份丢掉 ——
  按 docstring 改代码：改总额（`--set`）不抹掉追加历史（两类事件记在同一份账上，
  抹掉后者会让"已花 7.5 而历史里只有一笔 set"变成一笔无解的账）；坏寄存器上显式
  `--set` 仍然许写（否则用户没有出口），但"丢了什么"写进回执 `history_lost`，
  于是它不是静默覆盖。
- `docs/READING-MAP.md` 的行数：`agent_loop.py` 手抄的 5864 → 5942（判据
  `test_reading_map.py::test_the_line_counts_in_the_big_file_table_are_current`
  自己写着"改数字，别改判据"），并把这一批加的两档写进那一行说明。
