> 这份文件有两个用途：**① 说清它今天做不到什么**（免得把限制当缺陷报上来）；
> **② 登记"不做"这件事**（业主裁定过不做的，别在本仓当缺陷重新提）。
>
> 口径：**限制 = 今天的事实**（带一条复算 / 读法）；**不做 = 一次裁定**（带出处）。
> 两者都不是"缺陷清单" —— 真缺陷请照 §四 的顺序取证后再报，因为多数"看起来坏"的东西

## 三、可证伪条件（出现这些，某条结论就错了）

`draft/198` §六给的四条，逐条都是**机器可判**的（事件流 / 台账能查出来），请照原文核：

```text
· 出现两个角色同时改同一业务字段且造成丢更新（事件流里同字段、两角色同时活着、后写覆盖了有效值）
· 出现「编号重复」或「同号两行」（alloc_id 退号 / 复用）
· 写集再次漏项（表级冲突对被漏算）
· 出现第二条绕过表工具的写路（例如另一个子进程直写 data/）
```

第四条是**唯一被证实过**的一类（B2f 的 `eguard` 就是为它封的口，见
[`GUARDS.md`](GUARDS.md)）：绕过表工具写 `data/` 不经过任何行 / 表判据。

## 四、报缺陷之前先做这四件事

1. **先取证，别先假设**（`../../AGENTS.md` 规矩 R1）：拿盘上的现场证据 ——
   `sessions/<sid>.jsonl`（带 `seq` / `ts` / `kind`）、`runs/<role>-*.json`、`data/board.jsonl`、
   台账快照与它的 sha256 / mtime。**先定位现场，再谈修法。**
2. 跑一遍不变量审计：`python -m agentflow --root <ws> verify`（有 error 级发现 ⇒ 退出码 `1`）。
3. 查 [`KNOWN-UNWIRED.md`](KNOWN-UNWIRED.md)：那个模块可能本来就没接线，且已登记。
4. 回本文件 §二 对一遍：**"不做"的东西不会被"修"** —— 先确认它不在那张表里。
